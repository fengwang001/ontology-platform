# 多租户命名空间资源配额准入控制器 — 设计说明

代码位于 `quota/` 包。本文档说明模块划分、关键取舍、被放弃的方案与本地验证方法。

## 模块划分

| 文件 | 职责 |
| --- | --- |
| `quota/types.go` | 对外数据模型：`Pod`/`PodSpec`/`Defaults`/`Quota`/`Scope` |
| `quota/resource.go` | 资源名（`pods`、`requests.X`、`limits.X`）的解析与校验 |
| `quota/errors.go` | 六类错误的结构化表示与优先级 |
| `quota/defaults.go` | 准入前的默认值补全，产出记账视图 `EffectivePod` |
| `quota/scope.go` | Pod 服务等级/期限分类（`PodClass`）与作用域集合校验、匹配 |
| `quota/controller.go` | 控制器本体：命名空间/配额/Pod 的 CRUD、创建准入、原位调整、自检、并发串行化 |

数据流：`Pod` → `defaultPod`（补全）→ `classify`（定级）→ 作用域匹配 →
准入核对 → 增量记账。补全结果（`EffectivePod`）在准入时被快照保存，
之后所有记账、调整、删除、自检都基于该快照，保证"补全结果就是被记账的值"。

## 关键取舍

### 1. 增量记账 + 全量自检，而非每次准入全量求和

每个配额维护 `used map[ResourceName]int64`，准入/调整/删除只做 O(配额数 ×
每配额受限资源数) 的增量更新，与命名空间内 Pod 数量无关（性能要求的来源）。
正确性由两条独立途径保证：

- `SelfCheck(ns)`：可调用自检接口，从 Pod 快照全量重算并与记账值比对；
- 测试中的朴素模型（`model_test.go`）不维护任何计数、每次判定全量求和，
  与实现在随机操作序列上逐步对照。

被放弃的方案：每次准入时遍历全部 Pod 求和。语义最朴素，但单次准入开销随
Pod 数量线性增长，直接违反性能要求。

### 2. 单一互斥锁串行化，而非按配额/按命名空间分锁

`Controller` 所有公开方法在同一把 `sync.Mutex` 下执行，天然满足"任意并发
调用的结果等价于某个串行顺序"，且核对与记账在同一把锁内完成（check-then-act
原子），同一配额用量不会因并发准入超过硬上限。

被放弃的方案：按配额加锁或读写锁。多配额全有或全无准入需要同时锁住多个配额，
锁排序与死锁避免的复杂度远超收益；准入路径本身只做 map 查找与整数比较，
单锁不是瓶颈（见基准测试）。

### 3. 默认值在准入时快照，不回溯

`SetDefaults` 只影响之后的创建与调整；已接纳 Pod 的记账值不变。这样自检
不变量（已用量 = 适用 Pod 补全后量之和）中的"补全"有确定含义——即准入/调整
那一刻的补全结果。被放弃的方案：默认值变更后重算全部 Pod 记账，会导致已接纳
Pod 的等级与适用配额被动漂移，语义不可控。

### 4. 类别不变走增量核对，类别变化走"释放 + 重新准入"

适用配额集合是 Pod 类别（尽力型/期限）的纯函数。类别不变时集合不变，只需对
变大的资源核对超限、变小的资源释放；类别变化时等价于从原适用配额释放、对新
适用配额做一次完整创建准入（含缺失声明核对）。两条路径都是先全部核对、再统一
记账，保证全有或全无。

### 5. 超限判定要求"确有增量"

硬上限被下调到低于当前用量后，用量为 0 的准入（如 `requests.cpu: 0` 的 Pod）
不受影响；只有确实增加该资源用量且超过硬上限才拒绝（`amount > 0 && used+amount
> hard`）。这与"不增加该资源用量的准入不受影响"的要求一致。

### 6. 错误归约为六类

优先级：参数非法 > 命名空间不存在 > 重复创建 > 非法配置 > 缺失声明 > 额度超限。
每个操作按此顺序分阶段校验，前面的阶段失败即返回。准入阶段先收集"缺失声明"
与"额度超限"两类问题的第一处（配额名升序、资源名升序），缺失声明优先。

不在六类之内的情形映射如下（属于显式取舍）：更新/删除不存在的 Pod、更新/删除
不存在的配额，归为"参数非法"（引用了不存在的对象）；自检失败不属于操作错误，
返回普通 `error`。

### 7. 配额结构问题归"非法配置"，数值问题归"参数非法"

矛盾/未知作用域、硬上限资源名形式非法、尽力型配额限制非 `pods` 资源 → 非法配置；
空名称、负数量、负期限 → 参数非法。配额在新增/修改时即完成全部校验，系统中
不会存在非法配额，因此 Pod 准入路径无需再校验配额。

## 被放弃的方案汇总

- 每次准入全量求和（违反性能要求）；
- 按配额细粒度锁（多配额全有或全无下复杂度与死锁风险高）；
- 默认值变更回溯重算（已接纳 Pod 等级被动漂移）；
- 调整时对新 Pod 整体做缺失声明核对（会误伤"配额后建、存量 Pod 缺声明"的
  合法缩容/无变化调整；仅在类别迁移的重新准入中核对）；
- 用量超限后拒绝一切准入（应为只拒绝使该资源用量增加的准入）。

## 本地验证方法

```bash
# 全部单元测试（含随机对照，需 -v 查看每步操作日志）
go test ./quota/ -v

# 竞态检测（并发测试）
go test ./quota/ -race

# 性能证明一：结构性断言（准入路径不扫描 Pod 集合）
go test ./quota/ -run TestAdmissionDoesNotScanPods -v

# 性能证明二：基准（1k/10k/100k Pod 下 ns/op 应基本持平）
go test ./quota/ -bench=AdmissionScaling -benchtime=200x -run=NONE

# 覆盖率
go test ./quota/ -coverprofile=coverage.out && go tool cover -func=coverage.out

# 静态检查
gofmt -l quota/ && go vet ./quota/
```

随机对照测试（`TestRandomSequenceAgainstNaiveModel`）对 5 个种子各执行 1500
步随机操作（命名空间/默认值/配额/Pod 的增删改，含偶发非法输入），每步打印
输入、实际输出与判定依据，并逐步比对：操作结果（错误类别/配额/资源三元组）、
命名空间/配额/Pod 集合、每个 Pod 的补全记账视图、每配额每资源用量，且每步
调用 `SelfCheck`。
