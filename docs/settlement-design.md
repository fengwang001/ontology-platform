# 采购合同履约付款结算服务 — 设计说明

包路径：`ontology/settlement`。入口为 `settlement.Service`（`settlement/settlement.go`）。

## 领域模型

- 金额一律为整数分（`int64`），时间一律为整数日序号（`int64`），比例一律为万分比整数（`10000 = 100%`）。
- 合同在创建时固定：总金额、预付款总额、预付款抵扣比例、质保金比例、质保期天数、
  违约金日费率、违约金封顶比例，以及若干里程碑（应付金额 + 计划验收日）。
- 里程碑验收只有通过 / 驳回两种结果；驳回不改变计划日，可重新提交；
  通过即结算，每个里程碑至多结算一次。

## 结算流水线（关键取舍）

一次结算对同一笔应付金额 `P` 严格按固定顺序处理（`contract.settle`）：

1. **质保金** `R = ceil(P * 质保金比例 / 10000)`，以 `P` 全额为基数向上取整，全额扣留。
2. **预付款抵扣** `A = floor(P * 抵扣比例 / 10000)`，以 `P` 全额为基数向下取整；
   受两条钳制：累计不超过预付款总额，且 `R + A <= P`（保证实付非负）。
3. **历史违约金欠额**优先自剩余 `P - R - A` 中扣抵。
4. **本次违约金** `due = floor(逾期天数 * 日费率 * 合同总金额 / 10000)`；
   累计计提（已扣抵 + 欠额）不超过封顶 `floor(总金额 * 封顶比例 / 10000)`；
   剩余不足时扣到零，未扣抵部分记为欠额结转下次结算。

由此得到守恒恒等式（`Summary.Conserved`）：

```
已结算应付之和 == 累计实付(含质保金释放) + 质保金余额 + 缺陷扣抵 + 预付款抵扣 + 违约金扣抵
```

欠额不计入该和（它是"已计提未扣抵"的违约金，不是应付的分配项）。

### 关键取舍

- **封顶作用于"计提"（已扣抵 + 欠额）而非仅"已扣抵"**：规格要求"欠额同样受累计封顶约束"，
  若只对已扣抵封顶，欠额会无限累积，封顶形同虚设。
- **预付款抵扣的第二重钳制 `R + A <= P`**：规格只规定"累计不超过预付款总额"，
  但当质保金比例与抵扣比例之和超过 100% 时剩余会为负，与"实付金额不得为负"矛盾；
  因此抵扣额再钳制到 `P - R`，这是保证实付非负的最小干预。
- **验收通过即结算**：规格中逾期天数以"验收通过日"计、质保期自"验收通过日"起算，
  且"每个里程碑至多结算一次"，因此 `Accept(passed=true)` 原子地完成验收与结算，
  不设独立的结算操作（被放弃的替代方案见下）。
- **取整用 `math/big`**：`floor/ceil(a * b / 10000)` 的乘积可能溢出 `int64`，
  所有乘除统一走 `big.Int`（`settlement/muldiv.go`），结果饱和到 `int64`；
  每次调用仍是 O(1)。

## 质保金释放与缺陷

- 质保期满日 = 验收通过日 + 质保期天数；满日当天不可释放，次日起可释放（`now > 满日`）。
- 释放是显式操作 `ReleaseRetention`：存在未决缺陷时报 `state_not_allowed`（即"暂停释放"）；
  缺陷关闭后，下一次释放操作触及即可释放——这正好覆盖"缺陷关闭后的下一个操作触及时方可释放"。
- 缺陷按里程碑登记，只暂停该里程碑的质保金；释放时该里程碑已登记缺陷的罚没金额之和
  从该质保金中扣抵，扣抵以该质保金为上限，不影响其他里程碑。
- 每个里程碑以增量方式维护 `openDefects` 与 `defectPenaltySum` 两个聚合，
  登记 / 关闭 / 释放均为 O(1)，不遍历缺陷记录。

## 合同变更

- 变更单携带生效日（须 `>= now`，否则参数非法），仅可调整尚未验收通过的里程碑。
- 每个里程碑维护一条按生效日升序的版本时间线（原始版本 + 各次变更）；
  验收通过日 `d` 适用"生效日 <= d 的最新版本"（同生效日后登记者优先）。
  已验收通过或已结算的里程碑不追溯。
- 总额校验以各里程碑"最终预定值"（生效日最远的版本）求和，超过合同总金额即拒绝
  （`change_exceeds_total`），且不改变任何状态。
- 预付款总额不可变更（变更单没有该字段，从接口上排除）。
- 终止合同：已结算的保持不变；未结算里程碑的验收一律报 `state_not_allowed`；
  已扣留质保金仍按原规则释放（缺陷登记 / 关闭 / 释放在终止后仍可用）；
  欠额因不再产生结算而自然不再扣抵。

## 时钟与错误

- 服务维护单一逻辑时钟 `lastNow`（时间是不可倒退的全局量）：任何被接受操作的
  `now` 不得小于上一次被接受操作的 `now`，否则报 `clock_rollback`；
  被拒绝的操作不改变任何状态、欠额与时钟（所有校验通过后才推进时钟并落状态）。
- 错误类别（`ErrorKind`）可区分，校验严格按优先级顺序短路：
  参数非法 → 时钟回退 → 合同/里程碑不存在 → 状态不允许 → 重复结算 → 变更超出合同总额。
  每个操作的实现中校验顺序与注释编号一一对应。

## 并发与确定性

- 所有公开方法可并发调用：服务内一把 `sync.Mutex` 串行化全部操作，
  结果天然等价于某个串行顺序（即可线性化）。
- 相同操作序列重放得到完全相同的结果：全部状态转移都是确定性整数运算，
  不依赖 map 迭代顺序、地址或随机源。

## O(1) 开销与可验证性

- 合同的各类汇总（实付、质保金余额、缺陷扣抵、预付款抵扣、违约金扣抵、欠额等）
  在每次状态转移时增量维护，`Summary` 只是拷贝聚合值：O(1)。
- 结算只读取该里程碑的当前版本与合同级聚合：O(1)（变更版本时间线每个版本至多
  在验收时被消费一次，均摊 O(1)）。
- 缺陷记录可以增长，但释放 / 汇总只读每里程碑的两个聚合计数，不遍历记录。
- **验证方法**：`settlement/bench_test.go` 中 `BenchmarkSummaryScaling` 与
  `BenchmarkSettleScaling` 分别在 1k / 10k / 100k 条历史（结算 + 缺陷记录）下测量，
  实测每次操作耗时恒定（约 28ns 与约 200ns，不随历史增长）：

  ```
  go test ./settlement/ -run XXX -bench . -benchtime 2000x
  ```

## 被放弃的方案

- **独立 Settle 操作（验收与结算分离）**：规格中逾期与质保期都以验收通过日为锚，
  分离会引入"已通过未结算"的中间状态与额外的状态机分支，且"每个里程碑至多结算一次"
  使合并无损表达力，故合并为 `Accept(passed=true)` 原子完成。
- **每合同一把锁 / 无锁结构**：跨合同共享全局逻辑时钟（时钟回退判定要求全局有序），
  细粒度锁反而引入锁序问题；单互斥锁串行化简单、可线性化且足够快（单次操作百纳秒级）。
- **封顶只约束已扣抵违约金**：会导致欠额绕过封顶无限累积，与"欠额同样受累计封顶约束"
  冲突，改为对"计提总额（已扣抵 + 欠额）"封顶。
- **变更单即时覆盖旧版本（单 pending）**：多个变更的生效日可能交错（如先生效日 200、
  后生效日 100），覆盖式会丢失"先生效"的版本；改为按生效日排序的版本时间线。
- **缺陷罚没在登记时预扣**：规格要求"释放前被登记的缺陷罚没金额从该质保金中扣抵"，
  登记时预扣会在缺陷关闭后产生"退回"语义，复杂化守恒；改为释放时一次性扣抵。

## 本地验证方法

```bash
# 单元测试（19 个边界用例）+ 朴素模型对照（40 种子 x 300 随机操作）
# + 重放确定性 + 并发等价（30 种子）
go test ./settlement/ -v

# 竞态检测
go test -race ./settlement/

# O(1) 开销基准
go test ./settlement/ -run XXX -bench . -benchtime 2000x

# 静态检查
gofmt -l . && go vet ./...
```

朴素模型（`settlement/model_test.go`）独立实现同一规格：保留全部历史记录、
每次查询遍历重算（O(n)），与被测服务的 O(1) 增量聚合互为参照；属性测试逐步比较
两侧的错误类别、结算 / 释放结果与汇总，并在日志中打印每步输入、输出与判定依据
（`go test -v -run TestPropertyAgainstNaiveModel ./settlement/` 可见）。
