# 支付商户延迟结算与滚动保证金系统 — 设计说明

## 1. 系统概览

系统按营业日把商户的支付、退款与拒付扣回净额结算出款，同时按比例滚动留存
保证金、到期释放，并在商户净额为负时动用保证金。所有金额均为带符号整数
（最小货币单位），全流程无浮点，结果可精确复现。

## 2. 模块划分与协作

```
settlement/
  calendar.go   营业日日历：整数天集合，提供前后第 N 个营业日、区间枚举
  errors.go     可区分错误码（Code）与 Error 类型
  types.go      Config / PayoutRecord / ReserveBatch / Snapshot 等数据类型
  merchant.go   单商户状态机：待结算流水索引、保证金批次队列、单日结算算法
  engine.go     引擎：商户注册表、全局时钟、校验顺序、互斥锁（并发串行化）
  naive/        独立朴素模型：全量切片扫描直译规则，仅供差分测试参照
```

协作关系：`Engine` 持有 `Calendar` 与商户表；所有写操作先经 `Engine` 做
前置校验（参数、时钟、商户存在），再委托 `merchant` 完成领域校验与状态
变更；`merchant.settleDay` 是纯推进函数，逐日调用与一次追赶调用路径完全
一致，因此结果必然相同。`naive` 只依赖 `settlement` 的类型与日历，独立
重写全部结算簿记，用于随机差分测试。

## 3. 关键语义定义

- 可结算边界：营业日 t 的可结算流水为发生日 ≤「t 之前（严格早于）第 N 个
  营业日」的全部未结算流水。N=1 即 T+1（前一营业日及更早的流水到期）。
- 到期释放日：批次留存日之后（严格晚于）第 H 个营业日，含该日到账。
- 负余额结转：仅进入次日可结算净额，只能被后续流水净额与到期释放额清偿，
  不被任何其他来源冲抵。
- 资金不变式（任意时刻、任意商户）：
  `累计出款 + 保证金余额 + 结转负余额 == 已结算流水净额`。
  对单日转移逐项验证（记 S 为当日新结算流水之和）：
  - 净额非负：Δ出款 = net − 新留存 + 释放，Δ保证金 = 新留存 − 释放，
    Δ结转 = −旧结转，合计 = net − 旧结转 = S；
  - 净额为负：释放与动用均计入 Δ保证金，出款为补足后的非负余额，
    缺口结转，合计同样 = S。
  测试 `checkInvariant` 在全部单测与随机对照中逐商户校验该等式。

## 4. 单日结算算法与复杂度

每个营业日 t 的结算分四步：

1. **到期流水归集**：待结算流水按发生日聚合存入 `map[day]sum/count`，
   不同发生日各入最小堆一次；结算时弹出所有 ≤ cutoff 的日聚合。
   每个发生日入堆、出堆各一次，单日开销只与"当日新到期的发生日数"相关。
2. **到期释放**：批次保存在只追加的切片队列中（队首下标推进）。因为留存日
   严格递增且 `Advance(·, H)` 单调，到期日序 == 留存日序，队首即最早到期者，
   弹到 `releaseDay > t` 为止。每批次只被弹出一次。
3. **分支**：净额非负则留存 `ceil(net·bps/10000)` 形成新批次（以 t 为留存日）
   并出款；净额为负则先加释放额，仍为负时从队首（留存日最早）依次动用未到期
   批次补足至零，不足部分结转。同一日不可能既留存又动用（由分支互斥保证）。
4. **记账**：更新累计出款、保证金余额、结转余额，产出 `PayoutRecord`
   （出款为零也产出）。

因此单日成本 = O(新到期发生日数·log + 到期批次数 + 被动用批次数)，与历史
流水总数、历史批次总数均无关。队首空洞占比过半时压缩切片，内存同样有界。

**可验证的证明**：`BenchmarkSettleSteadyState` 分别以 1k / 10k / 100k 个
营业日的历史（每日 3 笔流水、每日留存并到期一个批次）构建商户，再测量稳态
单日结算耗时。三档历史规模相差两个数量级，若实现退化为随历史增长，ns/op
会同比拉开；实测三档基本持平（本机约 1.4µs / 1.4µs / 1.4µs 量级），
配合第 4 节的摊还论证共同构成证明。复现：

```bash
go test ./settlement/ -run '^$' -bench BenchmarkSettleSteadyState -benchtime 2000x -v
```

## 5. 校验、时钟与并发

- 所有操作携带 `now`；引擎维护 `lastNow`，`now < lastNow` 报时钟回退。
  校验全部通过前不做任何变更，时钟也只在操作被接受后推进，故被拒绝的
  操作不留痕（测试用快照前后对比 + 时钟探针验证）。
- 错误优先级由校验代码的书写顺序保证：流水为 参数非法 > 时钟回退 >
  商户不存在 > 流水编号重复 > 日期非法 > 已封账；结算为 参数非法 >
  时钟回退 > 商户不存在 > 非营业日 > 重复结算。`TestErrorPrecedence`
  对每一对相邻优先级构造并存场景验证只报第一个。
- 并发：引擎内一把 `sync.Mutex` 串行化全部写操作，效果等价于锁获取顺序
  的某个串行序；`Snapshot` 同样持锁，读到一致快照。相同操作序列重放结果
  完全相同（无随机、无时间依赖、map 仅用于查找不用于迭代，出款记录与批次
  均由确定性顺序的队列/堆产生）。`go test -race` 下并发测试通过。

## 6. 关键取舍与被放弃的方案

1. **单日聚合 map + 最小堆（采用）** vs 有序切片 / 平衡树 / 全量扫描。
   全量扫描（朴素模型所用）单日 O(历史流水)，最先被排除；有序切片插入
   O(n)；堆方案插入与弹出均摊 O(log 发生日数)，且发生日去重后堆规模有界。
2. **批次单队列（采用）** vs 释放堆 + 动用堆双堆。到期日序与留存日序一致
   （单调性论证见第 4 节），单队列即可同时服务"队首到期释放"与"队首最早
   留存动用"，省一个堆；部分动用只发生在队首，后续动用从队首继续。
3. **全局互斥锁（采用）** vs 每商户锁 + 全局时钟锁。时钟与商户表是全局
   资源，细粒度锁仍需全局同步点，收益有限而串行化论证复杂；单锁语义直白，
   天然满足"等价于某个串行顺序"。
4. **日历构造期固定（采用）** vs 运行期可扩展。可扩展日历需要处理"已计算
   的到期日因新营业日插入而改变"等难题；固定日历下 `Advance/Retreat` 只是
   二分查找。限制已文档化：日历须覆盖全部结算与保证金到期区间，超出区间的
   批次视为永不到期（`releaseDay = MaxInt64`）。
5. **拆分取模的向上取整（采用）** vs `big.Int` / 浮点。`ceil(net·bps/10000)`
   拆成 `q·bps + ceil(r·bps/10000)`（net = q·10000 + r），在 int64 内精确
   完成且不会溢出；浮点会破坏可精确复现性，`big.Int` 无必要。
6. **错误用 Code 枚举 + `errors.As`（采用）** vs 每类一个哨兵错误。枚举
   便于测试断言"只报第一个"，也便于调用方程序化分支。
7. **`now` 允许等于上次值（采用）**。规格为"不得小于上一次"，故相等合法；
   结算日 d 允许晚于 `now`（规格未禁止，结算的是营业日而非实时）。

## 7. 测试与本地验证

```bash
# 全量测试（含竞态检测）
go test -race ./...

# 查看随机对照日志（输入、输出与判定依据）
go test ./settlement/ -run TestDifferentialAgainstNaiveModel -v

# 性能证明基准
go test ./settlement/ -run '^$' -bench BenchmarkSettleSteadyState -benchtime 2000x -v

# 代码检查
gofmt -l .
go vet ./...
```

测试覆盖：

- `TestSettlementEligibilityBoundary`：发生日恰等于可结算边界 vs 差一个营业日。
- `TestReserveReleaseExactHorizon`：批次恰在第 H 个营业日释放，早一日不释放。
- `TestNegativeNetDrawsReservePartialThenRelease`：负净额动用保证金、部分动用
  后剩余到期照常释放。
- `TestNegativeCarryMultipleDays`：负余额多日结转并被后续正流水清偿。
- `TestReleaseCoversNegativeNet`：净额为负时释放额先入账且足以覆盖。
- `TestCatchUpEqualsDailySettlement`：追赶结算与逐日结算记录、快照逐字段一致。
- `TestClosedBooksRejection` / `TestRejectedOpsLeaveNoTrace` / `TestClockRollback`：
  封账补录被拒、边界日补录允许、被拒操作不改变状态与时钟。
- `TestErrorPrecedence`：两类操作全部相邻优先级的并存场景。
- `TestZeroPayoutRecordsAndReplayDeterminism`：零出款记录与重放一致性。
- `TestDifferentialAgainstNaiveModel`：40 个随机种子 × 200 个随机操作
  （混合合法/非法流水、结算、时钟回退、重复编号、封账补录），逐步比较
  错误码与出款记录，终态比较完整快照并校验不变式，日志打印输入、输出
  与判定依据。
- `TestConcurrentOperations`：多协程混合读写，`-race` 下验证不变式。
- `BenchmarkSettleSteadyState`：单日开销与历史规模无关的可验证证明。
