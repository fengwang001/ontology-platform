# 属性索引一致性子系统设计说明

## 目标与边界

本子系统在 `ontology/ontology` 内实现对象属性值与辅助索引的联合事务。一次写入同时覆盖：

- 对象实例上的属性值；
- 同一属性声明的所有索引结构；
- 批量写入涉及的多个对象；
- 对象删除时该对象的全部被索引属性。

实现重点是可证明的一致性、并发串行等价、崩溃恢复、缺失值建模和本地可执行的对拍测试。它是教学与本地验证用的完整参考实现，不伪装成分布式多副本数据库；网络复制、租约和跨节点两阶段提交不在本次边界内。

## 数据模型

### 值与缺失状态

`Value` 使用显式二元状态：

- `Missing()`：属性槽当前不存在具体值；
- `Explicit(v)`：属性被显式写成 `v`，即使 `v` 恰好等于类型零值或模式默认值。

`IndexKey` 同样带 `Present` 标记。缺失值永远映射到 `MissingKey()`；只有显式值才调用索引键函数。因此“不存在”和“显式写成默认值”不可能在索引中混淆。

### 索引布局

索引按三维结构存放：

```text
index name -> property name -> index key -> object id set
```

查询先定位单个索引和单个键，只枚举该键的对象 ID 集合，不遍历对象总表。实现中的二次校验也只检查第一轮从命中桶得到的候选，因此工作集大小随命中结果数增长，不随实例总数增长。平台不排序结果，避免引入 `O(k log k)`；测试侧排序后按集合比较。

## 并发控制

锁分为三级：

- 对象锁：控制对象生命周期，删除使用写锁，属性写入使用读锁；
- 属性锁：每个“对象 + 属性”一把锁，串行化同一对象同一属性的写入；
- 索引锁：每个索引结构一把锁，保护索引 map 的结构变更。

写同一属性时，批量内按对象 ID 排序，先取对象读锁，再取对应属性写锁，最后按索引名排序取索引锁。删除先取对象写锁，再按属性名、索引名排序获取所有相关锁。查询使用“读取候选桶 → 按对象与属性锁重验 → 重读同一索引桶成员”的两段式校验。

这保证：

- 不同对象的同属性写入互不阻塞；
- 同一对象的不同属性使用不同属性锁，不同属性的索引更新不互相串行；
- 同一对象同一属性的写入严格串行，最终值与所有索引条目来自同一个最后写入；
- 查询要么在写入前通过重验，要么在写入后通过重验，结果等价于某个串行时间点。

对象属性值使用每个属性独立的 `atomic.Value` 槽，避免不同属性并发写同一个 Go map 造成数据竞争。

## 事务与批量回滚

`WriteProperty` 在持有关联对象锁、属性锁和所有相关索引锁的临界区内：

1. 预检对象存在、属性可索引、批量内对象不重复；
2. 为每个对象记录旧值、旧键和旧索引成员关系；
3. 先写 WAL `begin`；
4. 更新该属性对应的所有索引结构；
5. 任一索引声明维护失败时，根据记录的旧成员关系撤销本事务已做的索引修改；
6. 全部索引成功后才写对象属性值；
7. 写 `prepare`、原子快照、`commit`；
8. 只有 `commit` 落盘后推进提交时钟。

批量写入中任意对象的任一索引失败都会导致整批拒绝。已变更的索引条目由同一临界区内的补偿操作恢复；时钟只在提交点增加一次，被拒绝的批量不会留下属性、索引或时钟痕迹。

删除使用同一套机制，但一个删除事务包含该对象的全部被索引属性：先移除所有相关索引，再将对象标记为删除，最后提交。对象写锁保证删除与该对象属性写入不能并发交错。

## 多索引同步

一个属性可以声明多个 `IndexDef`，每个定义有独立名称和键函数。事务记录为每个对象和每个索引结构分别保存：

- 旧索引键；
- 新索引键；
- 旧成员是否存在。

所有索引更新均在同一临界区和同一事务记录内完成。任一索引的键函数失败或声明性维护失败，都会补偿本事务对其他索引已经做的修改，属性值不会进入提交阶段。

## 崩溃点与恢复

恢复文件包括：

- `wal.jsonl`：追加式 JSONL 事务记录；
- `wal.jsonl.snapshot`：最近一次事务边界的原子对象基线；
- `wal.jsonl.pre`：提交前保存的前像快照备份。

每个事务阶段为 `begin`、`prepare`、`commit`，测试钩子覆盖：

- `CrashAfterBegin`：WAL 已记录但索引和属性都未提交；
- `CrashAfterIndex`：索引已移动、属性未变；
- `CrashAfterData`：索引与属性都已改变但未准备提交；
- `CrashAfterPrepare`：事务已准备但提交标记未落盘；
- `CrashAfterCommit`：提交标记已存在，崩溃发生在返回或日志通知前后。

恢复规则：

- 最后记录不是 `commit`：判定事务未完整生效，恢复前像并按 WAL 中保存的旧键、旧成员关系回滚；
- 最后记录是 `commit`：事务已经完整生效，保留状态；
- `commit` 后崩溃不会回滚，因为提交点定义为 commit 记录 fsync 完成。

快照通过临时文件加原子重命名替换。恢复不需要枚举“当前索引中已有的所有条目”来寻找脏数据；未决事务的补偿只遍历该事务记录中的对象、属性和索引成员关系。随进程重启装载基线快照会读取已提交基线，这是数据库启动装载成本；崩溃一致性判定和未决脏索引清理成本不随索引总条目数增长，只与最后一个未提交事务的大小相关。

## 错误优先级

错误码固定为：

1. `ErrObjectNotFound`：对象实例不存在；
2. `ErrPropertyNotIndexed`：属性不支持索引；
3. `ErrIndexMaintenance`：索引维护失败；
4. `ErrBatchRollback`：批量写入因其他实例失败而整体回滚。

校验逐条写入时先判断对象存在，再判断属性可索引，最后处理重复项和索引维护。批量中存在多个实例时，最高优先级根因会被包装为 `ErrBatchRollback` 对外报告；单实例写入仍返回具体根因。拒绝路径不修改属性、索引或提交时钟。

## 查询复杂度证明方式

不依赖口头复杂度声明，测试与代码路径共同约束查询：

- 生产查询只访问 `indexes[index][property][key]` 这一个命中桶；
- 第一次读取得到的候选集合大小就是桶内当前成员数；
- 后续只对这些候选按 ID 获取对象锁和属性锁，并重新读取同一桶确认成员身份；
- 不遍历 `objects`，也不扫描其他键桶；
- 朴素模型在测试中显式遍历全部对象，作为独立参照，而生产查询与其对拍结果一致。

因此除 Go map 常数时间哈希访问外，查询工作为 `O(k)`，`k` 是该键命中的结果数。返回顺序不稳定定，调用方需要排序时应在应用层完成。

## 朴素对拍模型

测试中的 `naiveModel` 不维护辅助索引，只保存对象真实属性：

- 写入直接更新对象属性；
- 删除直接移除对象；
- 查询遍历全部对象，用与生产代码相同的属性声明和键函数重新计算键；
- 随机测试混合创建、单写、批写、缺失值、显式默认值、删除、点查和多索引查询。

生产结果在每个随机步骤后与朴素全表扫描模型比较集合等价性。随机种子固定为 `1682`，保证失败可复现。

## 关键取舍

- 使用细粒度对象/属性/索引锁，而不是全局大锁：满足不同属性并发维护，但代价是必须严格排序加锁并做查询重验。
- 使用显式 `Present` 位而不是把零值当缺失：语义清楚，但所有键函数和 JSON 快照都必须保留该标记。
- 使用 WAL 加原子快照而不是纯内存回滚：可模拟进程重启恢复，代价是参考实现需要在事务边界序列化基线。
- 不承诺查询结果有序：保持 `O(k)`，避免把排序成本伪装成索引查询成本。
- 删除采用墓碑式对象状态和唯一 ID 假设：简化恢复重放；生产系统可在此基础上增加墓碑 GC 与 ID 版本号。

## 被放弃的方案

- 用属性零值表示不存在：无法区分 `Missing()` 与 `Explicit("")`、`Explicit(0)`，直接放弃。
- 先改属性再惰性修索引：读索引时会出现陈旧条目或新值暂时不可查，不满足任何时刻一致。
- 失败后只回滚属性或只回滚索引：会留下单边状态，无法通过切分点测试。
- 查询不持属性锁、仅读索引 map：无法保证与对象真实值对应，也无法验证索引移动中间状态。
- 全局 MVCC 时间戳：能扩展读快照，但当前需求只要求当前值查询；引入版本 GC、快照可见性和时钟选择会显著增加复杂度，因此保留为未来演进方向。
- 生产查询中排序：会使成本变为 `O(k log k)`，与“只随命中数增长”的严格表述不符，因此移到调用方或测试侧。

```bash
GOCACHE=/tmp/go-cache go test ./...
GOCACHE=/tmp/go-cache go test -race -v ./...
GOCACHE=/tmp/go-cache go test -run TestRandomOperationsMatchNaiveFullScan -v ./...
GOCACHE=/tmp/go-cache go vet ./...
GOCACHE=/tmp/go-cache go test -coverprofile=/tmp/ontology-cover.out ./...

```
