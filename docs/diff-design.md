# 快照差异比对组件设计说明

本文档说明本体平台快照差异比对组件的设计：组件划分、关键取舍、
被放弃的方案、错误模型与优先级理由，以及本地验证方法。

## 组件划分

比对管线由四个职责清晰、相互协作的部分组成，`Compare`（`compare.go`）
按固定顺序编排：

1. **结构层比对 `DiffSchema`（`schemadiff.go`）**
   比较两份快照的结构定义，产出对象类型、属性、链接类型的
   增/删/改。元素身份由稳定 ID 决定：同 ID 不同名判定为**重命名**
   （`Rename` 维度），同 ID 不同类型判定为**改型**（`Retype` 维度），
   两个维度相互独立、可同时出现在同一属性上。
   `SchemaDiff.Validate` 校验差异的内部一致性（错误类别二）。

2. **口径对齐 `BuildAlignment`（`align.go` → `align.go`）**
   在结构层差异之上构建实例层比对口径：属性按稳定 ID 对齐，
   标记被废弃的类型与链接类型。若存续对象类型的主键被移除/改型/
   更换指定，或存续链接类型的端点类型被更换，则实例身份无法跨
   快照对齐，返回错误类别三。

3. **实例层比对 `diffInstances`（`instancediff.go`）**
   按口径逐实体判定：对象区分创建/删除/更新，更新精确到具体
   属性；链接区分创建/删除，删除原因区分显式删除、端点对象被
   删除、链接类型被移除。删除原因完全由数据推导，不依赖平台
   写入的删除标记。

4. **朴素参照模型 `naive/`（`naive/naive.go`）**
   独立实现同一套规则：不读修订号与墓碑，全量连接、逐步判定，
   用于随机快照对上与主实现交叉验证。

## 数据模型关键取舍

- **稳定 ID 身份**：属性/类型以 ID 为身份，`Key`/`Name` 只是可变的
  对外名称；实例取值以属性 ID 索引。这是"重命名不得报成删除加新增"
  的根本保证：重命名在实例数据层面是零触碰的。
- **实例身份 = (类型, 主键取值)**：对象没有内部代理键，主键取值即
  身份。因此主键被改型或更换指定时，跨快照的实例对齐在语义上
  不成立——这正是错误类别三的来源，而不是静默地报成全删全增。
- **修订号 + 墓碑**：同一谱系内，每个实体携带最后修改修订号
  （`ModRev`），删除留下墓碑。比对只需检查 `ModRev > 基准修订号`
  的实体与墓碑，工作量与未变化实体总数无关（见下）。
- **取值带类型标签**：`Value` 显式携带 `Kind`，`int 3` 与
  `float 3.0` 可区分；相等性判断对数值做归一（`3 == 3.0`），
  使拓宽改型（int→float）不产生伪差异。
- **类型兼容规则**：唯一隐式兼容是 int 值可按 float 解读
  （拓宽方向）。收紧改型下，旧值按新类型解读无效时报
  `type_incompatible`，与取值真实变化（`value_changed`）是两个
  独立类别。

## 错误模型与优先级

三类错误互不相同，判定顺序固定，**顺序即依赖顺序**：

| 优先级 | 类别 | 含义 |
|---|---|---|
| 1 | `snapshot_corrupt` | 任一快照自身结构损坏（校验失败） |
| 2 | `schema_diff_conflict` | 结构层差异判定冲突（同一元素被判定为多种互斥变化） |
| 3 | `instance_basis_undetermined` | 实例层因结构变化无法确定比对口径 |

理由：实例口径（阶段 3）消费结构层差异（阶段 2）的输出，结构层
差异又消费快照本身（阶段 1）的内容。按依赖序判定，先报出的永远
是更根本的原因；若乱序，可能在损坏输入上得出看似合理的下游结论。

补充说明：对两份各自合法的快照，主实现的确定性 ID 匹配不会产生
类别二冲突——该校验是管线契约守卫，防御差异结构被内部错误破坏
（同一元素多个互斥处置、修改无任何维度、改型分类与类型不符等），
由 `schemadiff.go` 的 `Validate` 与各场景测试覆盖。

## 复杂度保证与可复核证明

同一谱系下，完整比对触及的实体工作量 `Stats.Inspected()` 只与真实
差异数相关，不随未变化对象/链接总数增长。证明方式（可复核）：

- 机制：候选集 = 目标快照中 `ModRev > old.Revision` 的实体 +
  同期墓碑；其余实体零触碰。`Stats` 精确记录候选数、墓碑数、
  基准查询数。
- 测试：`perf_test.go` 在 1k / 10k / 100k 未变化实体上施加同一组
  固定变更，断言 `Stats` 与差异结果三者完全一致（常数）。
- 例外：跨谱系（备份恢复等）快照对退化为全量连接（O(n)），
  `Stats.FullScan` 置位，结果与朴素模型仍一致。

代价：谱系内墓碑需保留至不再有需要比对的旧快照（可通过压缩
回收，留作后续工作）。

## 并发与不可变性

- 快照 `Build` 后不可变；`Builder` 写时复制，绝不原地修改既有
  `Values` 映射。
- `Compare` 是纯函数：无包级状态、无缓存、无调用间共享。
- 测试：`determinism_test.go` 反复比对 50 次结果逐字节一致；
  32 路并发比对结果一致（`go test -race`）；比对前后
  `Fingerprint` 不变证明输入未被修改。

## 被放弃的方案

- **按名称匹配属性 + 启发式重命名推断**：在"删除+新增"中猜测
  重命名。放弃原因：启发式有歧义（多对多匹配），无法保证"重命名
  必须报为标识变化"的硬要求，且会引入不可复现的判定。改用稳定
  ID 后重命名是精确事实而非猜测。
- **哈希树（HAMT/Merkle）结构共享比对**：任意快照对都能做到
  O(k·log n)。放弃原因：仍随未变化总量对数增长，不满足严格界；
  且实现复杂。修订号方案在同谱系下是严格 O(k)，跨谱系回退全量。
- **墓碑携带删除原因**：让平台在删除时记录"显式/级联"。放弃原因：
  比对结果应可从数据本身推导（端点是否存活、类型是否废弃），
  信任元数据会在元数据缺失/错误时静默出错；数据推导在跨谱系
  回退路径下同样成立。
- **主键改型后按位置/顺序对齐实例**：放弃原因：语义上就是另一批
  实体，静默对齐会制造虚假"更新"，显式报类别三错误更诚实。

## 本地验证方法

```bash
# 全量测试（含场景、并发、性能证明、随机对照）
go test ./...

# 竞态检测
go test -race ./...

# 提高随机对照规模（默认 300 对）
ONTDIFF_ITERATIONS=3000 go test -run TestRandomPairsAgainstNaive .

# 记录每次随机比对的输入、输出与判定依据（JSONL）
ONTDIFF_RECORD=/tmp/records.jsonl go test -run TestRandomPairsAgainstNaive .

# 性能证明（工作量与未变化实体数无关）
go test -run TestWorkIsIndependentOfUnchangedCount -v .

# 静态检查
go vet ./... && gofmt -l .
```

随机对照测试对每次比对记录：种子、变更操作序列、两份快照指纹、
错误类别、规范化结果 JSON（差异条目自带类别与原因，即判定依据）。
不一致时测试失败并输出完整记录；设置 `ONTDIFF_RECORD` 可全量落盘。

## 测试清单

- `scenarios_test.go`：重命名即标识变化；重命名+类型收紧同发；
  拓宽下取值可比；链接端点删除 vs 显式删除；类型整体废弃统一归因；
  先重命名后改型的三段快照；更新精确到属性。
- `errors_test.go`：错误优先级（损坏 > 口径）；类别三的三种触发；
  主键重命名不破坏口径；类别二一致性守卫各不变式。
- `determinism_test.go`：重复比对稳定；并发一致；输入不可变。
- `perf_test.go`：工作量与未变化实体数无关的可复核证明。
- `random_test.go`：随机快照对上与朴素参照模型对照（含跨谱系
  全量扫描路径），逐次记录输入/输出/判定依据。
