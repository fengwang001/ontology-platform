# 批量导入子系统设计说明

位置：`importer/`（引擎）、`importer/naive/`（独立朴素参照模型）。

## 问题回顾

导入任务由唯一标识区分，条目分布在多个带序号的块中。块可能乱序、
重复到达；条目可能引用尚未到达的块中的条目。系统需要在不等待全部
块到齐的前提下尽早落地依赖已满足的条目，并对重复、迟到、上限、
提前结束等情形给出确定、可区分的结果。

## 总体结构

```
Engine                 // 管理多个任务，任务间完全并行
 └─ job                // 单个任务的全部状态，任务内并发由一把读写锁串行化
     ├─ chunks         // seq -> 内容摘要（重复判定的唯一依据）
     ├─ entries        // 全部已知条目的状态
     ├─ pending        // 当前悬挂条目集合
     └─ waiters        // 被引用 ID -> 等待它的悬挂条目集合（悬挂引用索引）
```

一次 `SubmitChunk` 分三个阶段：

1. **受理**（任务锁内）：重复判定（序号 + 内容摘要）、序号范围检查、
   提前结束检查。受理与 `TerminateJob` 在同一把锁内完成，因此二者
   存在确定的先后顺序，并发结果等价于按该顺序串行执行（线性化点）。
2. **校验**（锁外）：条目校验器是纯函数，在锁外对每个条目执行，
   不同块的校验因此可以并行，互不阻塞。
3. **提交**（任务锁内）：注册条目并触发事件驱动的悬挂解析。

## 关键设计决策

### 悬挂引用：索引 + 事件驱动，而非全表扫描

条目转为终态（落地/失败/超时）时，只通过 `waiters` 索引唤醒直接等待
它的悬挂条目（O(度数)），环检测与超时清扫只扫描 `pending` 集合。
因此解析开销只随**当前悬挂引用数量**增长，与已处理条目总数无关。

可证明性：`Stats.EvalOps` / `Stats.ScanOps` 两个计数器记录解析过程中
的条目求值与扫描次数。测试 `TestDanglingOverheadIndependentOfProcessed`
构造两个落地条目数相差两个数量级的任务，执行相同的“悬挂-解析”序列，
断言两个计数器的增量完全一致——若实现退化为遍历全部已处理条目，
该断言必然失败。

### 失败传播优先于悬挂等待

评估悬挂条目时先检查引用是否已确定失败（Failed/Timeout/Conflict 均为
终态失败），是则立即以“传播失败”判定，不再等待其余未知引用——这
直接实现了错误类别优先级：传播失败（2）高于超时（3）与自身校验（4）。

### 循环引用（含双向悬挂）的规范语义

并发到达的两个块互相引用时，任何“先到等后到”的策略都会死锁。本设计
采用**封闭环判定**：在悬挂条目构成的依赖图中，一个环（强连通分量）
只有在封闭时——环内每个条目的每个引用要么已落地、要么在环内——才
被判定为循环引用失败（归入条目校验失败类别）。

封闭条件是必要的：若环内条目还引用着环外尚未确定的条目，它未来可能
因传播失败（优先级更高）而非循环被判定，提前打破环会导致类别错误。
封闭环之间互不可达，判定顺序无关，因此引擎（增量触发）与朴素模型
（批量触发）必然收敛到同一结果。对拍测试曾借此发现两版实现
（“所有环同时判定”“DFS 顺序逐个判定”）在“环+环外引用”场景下的
分歧，统一为封闭环规则后 3000+ 随机种子全部一致。

### 块数上限与超时清扫

`arrived == maxChunks` 且当前提交是最后一个在途提交（`inflight == 1`）
时执行超时清扫：仍存在未知引用的悬挂条目判定为超时失败，并沿引用
传播。`inflight` 条件是关键：并发受理的块必须全部提交完毕后才能
判定超时，否则“提交顺序”会影响结果，破坏与串行模型的等价性。
已落地条目不参与清扫，不受影响。

### 重复到达

- 序号相同、内容摘要相同：幂等忽略（`OutcomeDuplicate`），即使任务
  已提前结束也如此——它是空操作，不违反“新块被拒绝”。
- 序号相同、内容不同：判定为 `CategoryChunkConflict`（最高优先级），
  已确定结果一律不变；首次出现于该冲突块中的条目被标记为
  `StatusConflict`，使该错误类别可通过查询观察到。

### 错误类别优先级

固定优先级（高 → 低）：块冲突 > 传播失败 > 悬挂超时 > 条目校验失败
（含循环引用）> 提前结束拒绝。受理阶段按此顺序检查（冲突先于提前
结束被报告）；条目判定中传播失败先于自身校验、超时先于校验生效。

## 被放弃的方案

- **等待全部块到齐再处理**：违背“尽早落地”要求，仅作为对拍参照
  （`importer/naive`）保留。
- **每次状态变化后全表扫描悬挂条目**：实现最简单，但开销随已处理
  条目总数增长，违反约束，被 `waiters` 索引 + 事件驱动取代。
- **所有环同时判定 / 按 DFS 顺序逐个判定**：在“环+环外未确定引用”
  场景下与优先级规则冲突（见上文），被封闭环规则取代。
- **超时清扫不看在途提交**：并发下两个都已受理的块会因提交先后
  得到不同结果（一个超时、一个落地），被 `inflight` 门控取代。
- **冲突重复块静默忽略或覆盖**：违反“已确定结果不可改变且必须
  可观测”的要求，改为独立的冲突错误类别。

## 本地验证方法

```bash
# 全部测试（含竞态检测）
go test -race ./...

# 关键用例
go test -run TestCrossChunkDanglingAutoLand ./importer      # 跨块悬挂自动落地
go test -run TestPropagationOnReferencedFailure ./importer  # 失败立即传播
go test -run TestMaxChunksTimeout ./importer                # 上限超时
go test -run TestDuplicate ./importer                       # 重复到达两种情形
go test -run TestBidirectionalDangling ./importer           # 双向悬挂
go test -run TestDanglingOverhead ./importer                # 开销与总数无关的证明
go test -run TestTerminationRaceDeterminism ./importer      # 提前结束竞态确定性
go test -run 'TestDifferential' ./importer                  # 与朴素模型随机对拍

# 代码检查
gofmt -l .
go vet ./...
```

日志：通过 `WithLogger` 注入 `*slog.Logger`，引擎会打印每个块的受理
结果（序号、内容摘要、受理/重复/拒绝及原因）与每个条目的判定结果
及依据（等待哪些引用、落地、失败类别、超时、循环成员）。
