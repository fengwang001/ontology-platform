# 跨对象类型字段绑定兼容性校验 —— 设计说明

## 1. 问题与判定模型

链接类型可以声明：其链接实例以左侧对象类型字段 `L.f` 与右侧对象类型字段
`R.g` 作为绑定依据。两侧字段各自声明取值类型（`FieldType`）与取值约束
（可缺失 `Nullable`、枚举集合 `Allowed`）。兼容性判定的数学表述为：

- 记两侧取值空间（含缺失）为 `D_L`、`D_R`；
- 绑定建立时**一次性声明**一个确定对应关系 `C ⊆ D_L × D_R`（显式映射表，
  或取值域一致时的恒等对应），运行期不可更改；
- **双向绑定**要求 `C` 是双射：左→右是全函数且右→左是全函数（双向唯一）；
- **单向绑定**只要求声明方向上是确定性全函数（每个入参恰好一个像）。

关键取舍：**判定基于声明出来的对应关系，而不是取值集合的交集**。
两侧集合即使大量重叠，只要关系不是所要求方向上的全函数，就判定不兼容；
非空交集永远不会单独成为放行理由（测试 `TestIntersectionIsNotCompatibility`
专门钉住该行为）。

## 2. 四类结论与优先级

`Verdict` 精确区分四类（外加方向拒绝）：

1. `field_deleted`：一侧绑定依据字段已删除，绑定**定义本身失效**。
2. `incomparable_types`：当前版本两侧类型无法比较，**无法判定**。
3. `non_bijective`：对应方式不是双向唯一（双向声明下两个方向都不成立，
   或声明方向上的函数性不成立）。
4. `one_way_only`：声明为双向，但实际只有一个方向存在确定全函数。
5. `direction_denied`：单向绑定被从反方向使用（查询/写入入口给出，
   不静默退化为双向处理）。

**删除判定优先于其余三类**：`evaluateLocked` 在进入类型/关系检查之前
先检查字段存活，因为后三类检查都以字段仍存在为前提。

### “不是双向唯一”与“只单向可对应”如何分开

以关系模型（而非两个 map）承载声明：`relation[l] = {r...}`。

- 左→右全函数：每个 `l`（含缺失哨兵）恰好一个像；
- 右→左全函数：每个 `r`（含缺失哨兵）恰好一个前像；
- 双向：两者同时成立 → `compatible`；
- 仅其一成立 → `one_way_only`（声明阶段拒绝双向绑定）；
- 都不成立（如双方都有漏映射、前向多值碰撞等）→ `non_bijective`。

注意“多对一”（两个左值映射到同一右值）是**合法的左→右函数**，
它破坏的是反向唯一性，因此双向声明下得到 `one_way_only` 而不是
`non_bijective`；它在单向 `left_to_right` 声明下完全合法。

## 3. 方向性

- `Bidirectional`：声明时就要求双射，`DeclareBinding` 对非双射直接返回
  `ErrBidirectionalRejected`，不等到反方向首次使用才暴露。
- `LeftToRight` / `RightToLeft`：只校验声明方向的全函数性。
  反方向 `Query` 返回 `direction_denied`，写入入口同理必须拒绝。
- 注意单向的全函数只要求“方向上每个入参有唯一像”，**不要求对端域被覆盖**
  （右→左全函数不要求左值都有前像）。

## 4. 缺失取值

- 缺失是取值空间中的独立元素（哨兵 `missingKey`），参与全部全量性/
  唯一性判断，不被排除在检查范围外。
- 是否“左侧缺失 ⇄ 右侧缺失”由 `MissingPolicy.MapMissing` 决定，
  该字段是 `BindingSpec` 的一部分，绑定建立时固定，运行期无修改入口。
- 仅一侧可缺失时，缺失在对端没有可落的取值：
  双向声明 → `one_way_only`；缺失侧作为入参方向的单向声明 →
  `non_bijective`；反方向的单向声明可以兼容。
- `nullable × mapMissing × direction` 的全部组合由
  `TestCheckMissingCombinations` 穷举覆盖。

## 5. 变更、隔离与历史实例

- 字段定义**版本化且不可变**：`UpdateField` 追加新版本，`DeleteField`
  追加一个墓碑版本；历史版本对象永不原地改写。
- 字段变更只重新核验**引用该字段的链接类型**；每个链接类型有独立的
  `bindingState`（缓存结论、阻断位、所依据版本号），同一字段被多个
  链接类型引用时，判定与状态相互隔离（`TestLinkTypesAreolated`）。
- 重新核验后若不再满足要求：置阻断位，**新的绑定查询/写入被拒绝**，
  但**不删除、不改写任何既有链接实例**，历史绑定关系保持不变，
  等待显式处理（`TestBreakChangeBlocksButKeepsInstances`）。

## 6. 实例遍历开销的可验证上界

要求：一次重新核验遍历的既有实例数 ≤ 使用该绑定依据的实例当前存活总数，
且不随两侧对象类型历史实例总量增长而增加。

实现：`MemoryInstanceStore.VisitLive` 在锁内先对**当前存活集合**拍快照，
核验只遍历该快照：

- 快照大小恒等于调用开始时刻的存活数，遍历数不可能超过它；
- 已删除实例自创建删除起就不再进入任何快照（不是“遍历后跳过”），
  因此对象类型历史上存在过的实例总量不会带来额外开销；
- 存储层维护按链接类型的累计访问计数 `Visits`，测试用
  `实例数 + 历史垃圾实例 + 两次核验` 断言每次恰好遍历当前存活数。

纯对应关系检查本身只取决于两侧字段定义（枚举域是有限的），为 O(|D_L|+|D_R|)，
与链接实例数量无关；实例遍历仅用于给既有存活实例盖核验版本戳/供后续治理，
接口层把 `InstancesLive` 与 `InstancesSeen` 一并写入核验结果和审计记录，
可事后核对上界。

## 7. 并发语义

目标：字段变更与绑定查询的任意交织，其结论等价于某种全序串行执行
（线性一致），不得读到跨两次变更之间、对应不到任何串行时刻的判定。

实现：

- 所有元数据（字段版本切片、链接状态、审计日志）由单个 `sync.RWMutex`
  保护；字段版本发布与核验结论缓存在同一临界区内原子完成。
- 查询不是无条件读缓存：读路径比较缓存所依据的 `(左版本, 右版本)` 与
  当前版本，滞后则当场在锁内重新核验。因此返回结论永远对应
  “字段版本对 → 结论”映射中的某个确定点。
- 并发正确性不靠人工论证，而由
  `TestConcurrentLinearizabilityVsNaive` 验证：一个独立的、刻意朴素的
  串行参考模型保留全部不可变字段版本；并发查询带回它实际观测到的
  版本号，模型用该版本对复算结论，两者必须逐观测一致。任何“中间态”
  都会因版本对查不到一致结论而失败。另附
  `TestNoIntermediateStateBetweenTwoUpdates` 的定向交织断言。

被放弃的方案：

- *每个字段一把锁 + 双检*：两个字段锁的获取顺序容易与查询形成死锁/
  倒序读，且两字段版本与链接缓存的联合原子性需要额外协调；在当前
  元数据规模下单锁更简单且正确性可证。如未来成为热点，可按链接类型
  分片，但必须保留“版本对 + 结论”原子发布这一不变量。
- *删除实例级联撤销*：违反“历史绑定保持不变”的要求，明确不做；
  不兼容只影响新查询/新写入。
- *运行期动态缺失策略 / 动态映射表*：会让历史绑定的语义随时间漂移，
  明确禁止；要改对应方式必须重新声明绑定。
- *跨类型隐式转换*（如 int→string 自动）：隐式转换的唯一性依赖值域，
  不安全；跨类型必须显式声明两两映射，否则判 `incomparable_types`。

## 8. 审计

每次核验（声明、字段变更触发、显式重算、查询触发的滞后重算）追加一条
`AuditEntry`：两侧字段定义快照、两侧版本号、`CheckBasis`（两侧取值域、
前向/反向冲突值、漏映射左值、无前像右值、缺失是否成对处理）、结论、
触发原因、存活/实际遍历实例数。`AuditLog()` 返回副本，供事后核对。
