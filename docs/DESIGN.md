# 跨对象类型聚合视图子系统 — 设计说明

## 1. 目标与范围

在本体平台上支持一类聚合视图：声明一条**固定长度**的有向链接路径

```
source --hops[0]--> t1 --hops[1]--> ... --hops[k-1]--> target
```

对起点对象类型的每个实例，汇总其沿该路径**恰好行走 k 跳**能够到达的
全部**不同**终点实例在某数值属性上的取值，取最大值。无可达终点时结果为
明确的“不存在”（`Result.Absent`），不使用任何默认数值。

交付物：

- `ontology/`：线程安全的最小本体存储（对象类型 / 实例 / 链接 / 属性）。
- `aggview/`：视图声明、定长路径遍历、增量维护、环检查、结构化类型扩展、
  变更日志、查询接口。
- `aggview/*_test.go`：场景测试、开销上限证明、并发串行等价、朴素模型对拍。

## 2. 核心数据模型

- `ontology.Store`
  - `types`、`objects(id -> Object{Type, Attributes})`、`links(id -> Link)`。
  - 邻接索引 `outgoing[from] -> linkID set`、`incoming[to] -> linkID set`。
  - 一把 `sync.RWMutex`：写变更（链接增删、属性写）持写锁，查询持读锁。
  - 对外提供普通方法与 `...Locked` 变体；引擎在“存储 + 视图”的**同一个
    临界区**内只调用 `Locked` 变体，避免重入死锁。

- `aggview.viewPath`
  - 每跳保存关系名与“该跳终点允许的对象类型集合”（`map`，可结构性扩展）。

- `aggview.aggState`（每个视图一份）
  - `reachable[s]`：起点 `s` 当前可达的**不同终点实例集合**（存在性）。
  - `terms[s]`：上述终点中被汇总属性存在者 `t -> value`（贡献）。
  - 二者分离是关键：可达集合用于回答“能否到达 / 是否 absent / 开销上界”，
    贡献表用于求最大值。属性缺失的终点计入可达但不参与最大值。

## 3. 路径遍历：按层集合 BFS（天然处理环与重复到达）

`reachable(g, path, src)` 维护“当前层实例集合”，逐层用邻接表展开，**每层
按实例 ID 去重**：

- 同一终点经由任意多条走法（不同中间实例组合、并行链接）只出现一次，
  因而“重复到达只贡献一次”。
- 深度固定为跳数 k：即使图中存在回边/自环，第 k 层的集合也是有限的，
  每层集合去重保证不会无限展开、也不随走法数量指数膨胀。
- 环上“本身是终点类型”的实例只要在第 k 层可达，就被计入一次且仅一次。

反向遍历 `sourcesReaching` 同理：从某节点沿前 i 跳**反向**按层 BFS，
得到能在 i 跳到达它的实例，并用 `levelTypeOK` 做“路径层次类型”过滤。

时间复杂度只与去重后访问到的实例数和相关链接数有关，与走法总数无关。

## 4. 环的静态排除与运行时拒绝（错误类别 3）

需求同时要求“路径允许存在环并正确处理”和“静态无法排除环时运行时拒绝
某次变更”，二者通过**分层策略**调和：

- 声明期 `staticallyCycleFree()`：把每个路径位置允许的类型展开成“位置
  类型序列”（位置 0 为起点类型，位置 i+1 为第 i 跳类型集合，末位置为
  终点类型）。若所有位置的类型两两不相交，则任何实例都不可能在行走中
  回到自身类型所在的位置——环在类型层面被排除。此时**任何**链接变更都
  不会报环错误，遍历由按层去重保证终止（见测试 `TestCycleStaticallySafe`、
  随机对拍中的多跳不相交类型路径）。
- 若不能静态排除（典型：自反类型集合，如 `A --r--> A`），新增链接时
  `cycleIntroduced` 做保守的局部检查：链接两端属于同一被允许类型且存在
  起点能经对应前缀到达链接起点，则拒绝本次变更并回滚（见
  `TestCycleHandled`、`TestNoPartialStateOnRejectedChange`）。

这是一个有意的、保守的取舍：宁可拒绝一小类无法静态证明有界的结构变更，
也要保证定长语义可判定；能静态排除的常见跨类型路径则完全不受影响。

## 5. 增量维护

所有写操作都在 `Store` 的写锁内完成“校验 → 影子备份 → 改存储 → 维护视图
→ 失败回滚”，因此并发变更天然串行化，查询永远看到某个串行一致的状态。

### 5.1 新增链接（第 i 跳）

1. 候选起点 = 能沿**前 i 跳**到达 `link.from` 的起点实例（反向按层 BFS，
   按路径层次类型过滤）。这精确圈定“本链接可能为谁提供新走法”。
2. 对每个候选在新图上重算可达终点集合，与旧集合做**集合差异**：
   - 集合不变（新链接只是冗余走法）→ 不更新、不进入受影响集合（不多算）。
   - 集合变化 → 用新集合整体重建该起点的可达集合与贡献。
3. 受影响起点集合、判定依据写入变更日志。

### 5.2 删除链接（第 i 跳）

采用经典 prefix/suffix 受影响对公式的前缀半边，并且必须在**删除前的图**
上计算候选：候选 = 删除前能沿前 i 跳到达 `link.from` 的起点（存在经过本
链接的长度 i 前缀走法）。然后在删除后的图上对这些候选重算并做集合差异。
候选在删链前抓取，避免把“只能经本链接到达”的起点漏掉（测试
`TestSingleAndMultiHop` 中删除唯一前缀后回到 absent）。

### 5.3 终点属性写入

只遍历“当前可达集合包含该终点”的起点（不可达起点完全不碰）：

- 更新该起点对该终点的贡献值。
- 仅当**旧值恰好是该起点当前最大值来源且新值变小**时，才重新确定最大值；
  此时 `maxOf` 只扫描该起点现存贡献者，扫描条目数 ≤ 其当前真实可达终点
  总数，绝不扫描任何与该起点无关的实例。变大不触发重新扫描。

## 6. “最大值重定”开销上界（可证明）

`WriteAttr` 返回 `CostStats{Reexamined, Reachable}`：

- `Reachable` = 需要重定最大值的起点的当前真实可达终点数之和；
- `Reexamined` = 实际扫描的贡献者数量之和，恒有
  `Reexamined <= Reachable`。

`TestAttrDecreasePicksNewMax`（3 个可达终点 ⇒ 恰好扫描 3）与
`TestCostBound`（6 个不同终点 + 1 条重复到达 ⇒ `Reachable=6` 且
`Reexamined<=6`）对该上界做了断言级验证。

## 7. 并发串行等价

- 单把 `sync.RWMutex` 把每次“链接增删 / 属性写 + 全部视图维护”包成一个
  原子临界区；查询只持读锁且不修改任何状态。
- 因而任意交织都等价于把这些变更按某个全序串行执行；不存在“只应用了
  一部分变更”的可观察中间态。
- `TestConcurrentSerializability`：6 个变更 goroutine + 1 个持续查询
  goroutine 在 `-race` 下运行，结束后每个起点结果必须等于朴素模型在最终
  存储上的重算结果。

被放弃的方案：更细粒度的按跳/按视图锁（能提高并发度，但需要 MVCC 或
两阶段锁来保证查询不读到撕裂状态，复杂度与出错面大得多）。在本问题规模
下，单写者临界区 + 读多写少场景的 RWMutex 是更简单且可证明正确的取舍。

## 8. 结构化变更：跳类型集合新增成员

`AddHopType(view, hop, type)`：

- 校验类型已注册、跳索引合法后，把新类型并入该跳允许集合并标记
  `open=true`（此后该视图走运行时环检查策略）。
- 在扩展后的图上对全部起点做一次全量对齐：原有可达关系是扩展后可达关系
  的子集，因此**既有连通关系不会被判定失效**，只会新增可达终点。
- `TestStructuralHopTypeExpansion` 验证：扩展前 A→C 被类型拒绝；扩展后
  生效、最大值更新；删除新链接后立刻回到旧值，证明旧连通关系仍然有效。

## 9. 错误模型与固定优先级

sentinel：`ErrTypeMismatch < ErrInstanceNotFound < ErrCycleDetected
< ErrMaintenanceFailed`（数字越小优先级越高）。各入口按此顺序裁决：

1. **类型不匹配**：路径声明非法（空关系/空类型集合/未注册类型）；链接
   关系被某视图某跳使用但端点类型不符合该跳及相邻层声明；重复链接 ID；
   结构扩展的类型/索引非法。
2. **实例不存在**：链接端点或属性写入对象 / 查询起点不存在。
3. **运行时环**：非静态无环视图中，新增链接引入无法静态排除的环。
4. **维护失败回滚**：维护阶段任何失败（测试用 `InjectFault` 注入），
   存储改动撤销 + 受影响视图状态从深拷贝影子恢复。

所有错误在改动存储**之前**完成可判定的校验（类型、实例、环）；不可在
改图前判定的维护失败则通过影子状态 + 反向操作整体回滚。

## 10. 与朴素模型对拍

`naiveOracle`（测试内独立实现）不依赖任何增量状态：每次都从存储快照
（对象、属性、链接）出发，用独立的按层去重 BFS 重算每个起点的最大值。
`TestRandomDifferential` 使用固定随机种子，对 1/2/3 跳路径、40 个随机
图、每图 200 步“随机加链 / 随机删链 / 随机属性写”序列，每步后逐起点比较
引擎与朴素模型，覆盖增删维护、属性变小重定、重复到达、环安全路径等。

## 11. 关键取舍与被放弃方案

- 放弃“走法计数（walk counting）矩阵”做增量：能精确表达多走法，但需要
  为每条链接维护前后缀贡献，属性变小仍需枚举可达终点；复杂度高。按层
  集合 BFS + 受影响起点集合差异更直接，天然去重、天然处理环。
- 放弃维护全局有序堆来求最大值：属性频繁写时堆的惰性删除复杂，且不满足
  “只扫描该起点可达终点”的局部性要求；当前方案重定只扫单起点贡献表。
- 并发选择单 RWMutex（见 §7），放弃细粒度锁 + MVCC。
- 环采用“静态可证明无环则全放行，否则保守拒绝”的分层策略（见 §4）。

## 12. 本地验证方法

```bash
export GOCACHE=/tmp/gocache      # 如默认缓存目录只读
go test ./...                    # 全量
go test -race -v ./aggview       # 竞态 + 详细用例
go test -run TestRandomDifferential -v ./aggview   # 随机对拍
go vet ./... && gofmt -l .
```

日志：每次被接受的变更经 `Engine.Log()` 返回结构化记录（操作、输入、
逐视图受影响起点集合与判定依据），见 `TestChangeLog`。
