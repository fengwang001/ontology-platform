# 血液透析机位排程与感染隔离系统 — 设计说明

## 1. 目标与范围

系统在整数分钟时间域 `[0, 10^7]` 内维护机位、患者、周期性治疗方案与一次性治疗，
保证：

- 任意时刻任意机位不会同时承担两次治疗或处于两次治疗之间的消毒占用；
- 隔离区机位上相邻两次治疗感染类型一致，否则间隔不少于深度消毒时长；
- 阴性只进普通区，乙肝/丙肝只进隔离区，待定只进普通区观察位；
- 同一患者治疗不重叠，且满足最短恢复间隔；
- 方案分配、故障改派、感染状态变更全部“全有或全无”；
- 并发调用等价于某一串行顺序，相同操作序列重放得到完全相同的分配；
- 为一次治疗寻找可行机位的开销不随机位/全中心历史治疗总数增长。

## 2. 模块划分

所有代码位于 Go module `ontology` 下：

| 路径 | 职责 |
| --- | --- |
| `hemo/types.go` | 枚举（感染状态、区域）、`Chair`、`Patient`、`Treatment`、`Plan`、`Config` |
| `hemo/errors.go` | 七类错误码与优先级、`OpError` |
| `hemo/timeline.go` | 固定时间域上的 4 层 64 叉基数 trie，O(1) 前驱/后继 |
| `hemo/system.go` | 引擎状态、时钟、消毒间隔与区域准入判定 |
| `hemo/placement.go` | 原子分配：患者校验 → 同机位优先 → 按开始时刻贪心 |
| `hemo/api.go` | 登记/查询类对外 API 与只读视图 |
| `hemo/plans.go` | 周期方案展开与全有或全无提交 |
| `hemo/ops.go` | 故障停用/恢复、感染状态变更、取消（单次/整方案） |
| `hemo/naive/` | 独立朴素参考模型：所有判定线性扫描全部历史 |
| `hemo/fuzz/` | 1500 组随机操作序列差分测试与 JSONL 逐步日志 |
| `cmd/hemodemo/` | 端到端可运行演示 |

模块间只通过 `System` 的小接口协作；朴素模型不 import 生产包任何内部
结构（只共享常量语义），保证两实现真正独立。

## 3. 关键数据结构与复杂度证明

### 3.1 为什么不用有序切片或平衡树

- 有序切片：找前驱/后继用二分是 O(log n)，但插入/删除是 O(n)，历史长了
  取消与改派都会退化。
- 区间树/线段树：能做区间冲突查询，但为得到“紧邻的两次治疗”仍需 O(log n)，
  且分配时要反复检查，常数较大。
- 平衡树（红黑/B 树）：可行，但 Go 标准库无泛型有序容器，自绘树复杂且
  仍随历史增长有 O(log n) 次指针跳转。

被放弃的方案：按天分桶 + 桶内有序切片。该方案在“天”维度已经与历史
总量无关，但桶内仍 O(log n) 或 O(桶内 n)；当大量治疗集中在同一天（如
三班倒满负荷）时桶内会堆积，无法严格满足“与历史无关”的要求。

### 3.2 固定时间域基数 trie

时间域固定为 `[0, 10^7]`，需要 24 位。采用 4 层、每层 64 路（6 位）的
基数 trie：

```
层 0: bits 18..23   层 1: bits 12..17
层 2: bits 6..11    层 3: bits 0..5（叶子，64 分钟一格）
```

每个内部节点只有一个 `uint64` 占用位图 + 64 个稀疏子指针；叶子桶保存
开始时刻落在同一 64 分钟格内的治疗。由于同一机位的治疗（含消毒尾）互不
重叠，一个叶子桶在已提交数据上至多 1 个元素。

**前驱/后继代价**：从根到叶固定 4 层；目标子树为空时用位图指令
（`bits.TrailingZeros64` / `bits.Len64`）向兄弟回绕，最坏多访问常数个
节点。因此每次前驱或后继访问的层数恒为 4（外加常数次回绕），**与已存储
治疗总数 n 完全无关**。空节点不分配，空间仍为 O(n)。

**可行机位判定**：一次治疗在一个机位上只需要：

1. 机位在开始时刻可用（故障窗口列表，当前模型下窗口数量很少）；
2. 区域/观察位准入（O(1)）；
3. 前驱治疗：`pred.End + gap(pred, 候选) <= 候选.Start`；
4. 后继治疗：`候选.End + gap(候选, succ) <= succ.Start`。

其中 gap 是相邻感染类型决定的常规/深度消毒时长，全部 O(1)。所以一台机位
的可行性 = 两次 trie 邻接查询 = O(1) 历史无关；为一次治疗扫描全部 C 台机位
为 O(C)，并且只触及该机位候选时刻附近的常数个治疗。

**可验证方式**：

- `ProbeStats` 统计 trie 层数访问、位图扫描与叶子项扫描次数；
- `TestProbeBoundIndependence` 在 1,000 与 100,000 两档历史下断言三次计数
  完全相同（实测均为 `{LevelVisits:10 BitmapScans:6 ItemsScanned:1}`）；
- `BenchmarkFeasibilitySmall/Large` 对照两档耗时：
  1,000 条历史 172.7 ns/op，100,000 条 182.8 ns/op（几乎不变）；
- `BenchmarkNaiveScanSmall/Large` 对照朴素全量枚举：23.6 µs → 3.05 ms，
  线性增长约 129 倍。

## 4. 规则语义的形式化

### 4.1 占用与消毒

治疗 t 占用机位 `[Start, End)`，`End = Start + Duration`。对同一机位相邻的
前序 a、后序 b（按开始时刻），要求

```
b.Start >= a.End + gap(a.inf, b.inf, zone)
```

其中

- 普通区：永远是后序治疗所需的常规消毒（实现取前序感染对应的常规时长，
  配置上为每类状态给出常规值）；
- 隔离区、且 a/b 分别为 HBV/HCV：取 `DeepDisinfect`（恰等于允许）；
- 隔离区、类型相同：取该类型常规消毒。

待定期观察位使用“待定常规消毒”配置。待定患者与阳性不会落到同一机位
（区域不同），因此不存在跨类型的待定深度消毒问题。

### 4.2 患者恢复

同一患者相邻两次治疗要求 `b.Start >= a.End + MinRecovery`；这是机位约束之
外的独立约束，优先级高于机位不足。

### 4.3 方案展开

周锚点为时间 0：分钟 t 的星期 = `(t / 1440) mod 7`，星期 0 为第 0、7、14 …
天。对有效区间 `[ValidFrom, ValidTo]` 内、选中星期的每一天生成一次治疗，
开始时刻 = `day*1440 + DayStart`；治疗结束超出 `ValidTo` 的出现次数被丢弃。

### 4.4 分配规则

对方案全部出现次数（以及一次故障/状态变更涉及的全部治疗）：

1. 先逐条做患者自身冲突校验，任一失败 → 整批拒绝（患者冲突码）；
2. 若不存在“锁定机位”的条目（故障/状态变更才有锁定），依次按机位编号升序
   寻找能**单独承载全部次数**的机位；找到则所有次数都放该机位；
3. 否则按开始时刻升序（相同开始按输入顺序），逐条取编号最小可行机位；
4. 任何一条放不下 → 整批回滚，已暂存条目全部丢弃，正式状态不变。

故障/状态变更条目的“锁定机位”就是其当前机位：先尝试留任，留任不可行时才
按编号最小改派。这样精确实现“原机位仍可行则保持，否则改派到编号最小”。

### 4.5 故障

`FaultChair(now, at, until, chair)`：

- 登记互不重叠的故障窗口 `[at, until)`；
- 开始时刻落在窗口内的治疗取出并按开始升序重新分配（锁定到原机位，而原机位
  在窗口内不可用，所以必然改派到其他机位）；
- 正在进行（`Start < at < End`）的治疗不在 `Start >= at` 集合中，留在原位；
- 恰在 at 结束的治疗视为已完成，也不动；
- 任一条改派失败 → 回滚全部移动并撤销该故障窗口的登记；
- 恢复只把当前窗口在 now 处截断，不回溯已改派的治疗。

支持为同一机位登记多个互不重叠的未来窗口，这使“按天掩码机位”成为可能。

### 4.6 感染状态变更

合法迁移：待定 → 阴/HBV/HCV；阴性 → HBV/HCV。其它迁移报状态冲突。
`ChangeInfection(now, at, …)` 只重核 `Start >= at` 的治疗；先取出（保留原机位
快照）再以新状态重放锁定分配；任一失败整批回滚，患者状态也回退。

### 4.7 取消

- 单次取消要求 `Start > now`（已开始报状态冲突）；删除即同时释放机位与
  其后的消毒占用（消毒尾不是独立对象，由相邻关系隐式表达）；
- 整方案取消要求全部存活出现均未开始；
- 取消绝不引起其他治疗提前或改派。

## 5. 错误优先级

实现按固定顺序短路：参数非法 → 时钟回退 → 对象不存在 → 状态不符 →
感染隔离冲突 → 患者自身冲突 → 无可行机位。

- 参数非法在加锁/查对象之前检查；
- 时钟回退在任何对象查询之前检查（因此即使对象 ID 不存在，时钟回退也优先
  报出）；
- 分配阶段先查患者冲突，再做机位分配；机位失败时，若所有机位区域上都不
  合格（或无可用合格机位），归类为感染隔离冲突，否则为无可行机位。

被拒绝操作在任何状态修改前返回，因此时钟（`lastNow`）也不变。

## 6. 并发与确定性

`System` 内一把 `sync.Mutex` 串行化所有变更操作；整个“暂存—可行性—提交”
过程持锁，天然原子。可行性不依赖随机数或 map 迭代序：机位总是按 ID 升序
遍历，开始时刻相同时按输入顺序（方案出现序号）稳定排序。相同输入序列必然
得到相同分配（`TestConcurrentSerializability` 还做了两次串行重放比对）。

## 7. 独立朴素模型与差分测试

`hemo/naive` 用一个扁平 map 存全部治疗，每条可行性判定都线性扫描该机位
（或该患者）的全部历史；它重新独立实现展开、同机位优先、贪心、故障改派、
状态变更与取消，与生产代码没有共享数据结构。

`hemo/fuzz` 生成 1500 组、每组 40 步的随机操作（加权覆盖全部操作类型，
时间多数单调、偶尔制造回退，故障既有未来窗口也有覆盖“进行中”的过去窗口），
对双引擎逐步骤比对：

- 成功/失败一致（错误码整数相同）；
- 成功后全部存活治疗的 `(ID, 方案, 序号, 患者, 机位, 开始, 结束, 感染)`
  逐行相同；
- 患者当前感染状态相同。

每一步的输入、判定依据、两引擎错误码与错误文本、当步之后的完整状态都写入
`hemo/fuzz/testdata/logs/differential.jsonl`（每行一条 JSON，60,000 行）。

## 8. 本地验证方法

```bash
export PATH=$PATH:/usr/local/go/bin   # 如环境未全局安装 go
export GOCACHE=/tmp/go-cache          # 如默认缓存目录不可写

go build ./...
go vet ./...
gofmt -l .

# 全部单测（含边界规则、并发 race、探测计数）
go test -race ./hemo/

# 1500 组差分（可调参数）
go test ./hemo/fuzz/ -run TestDifferential1500 \
  -seqs 1500 -ops 40 -v

# 两档历史规模性能对照
go test ./hemo/ -run NONE \
  -bench 'BenchmarkFeasibility|BenchmarkNaiveScan' -benchtime=200x

# 端到端演示
go run ./cmd/hemodemo
```

## 9. 关键取舍清单

- 消毒尾不建成独立对象：改为相邻两次治疗间的可计算约束，取消即天然释放，
  也避免“悬空消毒”；代价是查询某时刻机位状态时要由前驱推导，而这正是 trie
  O(1) 邻接查询的用途。
- 同机位优先的可行性试算不触碰正式暂存集合：先纯函数式试探，再开干净的
  admission 做贪心，避免试探污染（这是开发中发现并修掉的一个真实缺陷）。
- 故障窗口设计成列表而非单一区间：允许登记多个互不重叠的未来窗口，规则
  文本只要求单次故障语义，扩展为列表不改变单次语义，却使测试中“按天掩码”
  可以直接用公共 API 构造。
- 朴素模型保持故意低效（每次 O(n)），它只用于差分，不进生产路径。
- 单机位同感染类型深度消毒的配置按“深度消毒单一时长 + 每类常规时长”
  建模；若业务后续要求 HBV/HCV 各自不同深度值，只需扩展 `Config` 与
  `gapAfter` 一处。
