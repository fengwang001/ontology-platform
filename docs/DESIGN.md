# 对象实例存储：属性级并发写入与冲突判定设计

## 1. 目标与判定口径

每个对象实例支持属性粒度的乐观并发控制。记一次写入 `W` 的**相关集合**为

```
Rel(W) = WriteSet(W) ∪ ⋃ ReadScope(hook_i, W)     // 本实例部分
       ∪ { (linkedInstance, p) : hook 声明经由链接字段读取 linkedInstance.p }
```

- 两次写入的相关集合不相交 ⇒ 都成功，后提交者在最新已提交版本之上合并，版本号严格 +1。
- 相关集合相交（写-写、写-读、读-读任一种方向）⇒ 后进入冲突判定的一方得到
  `ConflictProperty`。
- 基线版本号只表示调用方预期起点；所有判定在提交时刻、持锁状态下基于当时最新已提交
  状态重新计算。

## 2. 三类互斥错误与判定顺序

| 类别 | `ConflictKind` | 可判定方式 | 触发条件 |
| --- | --- | --- | --- |
| 已删除 | `ConflictDeleted` / `errors.Is(err, ErrInstanceDeleted)` | kind + sentinel error | 目标实例当前 head 为逻辑删除（优先级最高） |
| 基线落后 / 重复 | `ConflictStaleBase` / `ErrStaleBase` | kind + sentinel error | 实例不存在、基线版本不存在或超前、对已存在实例 `Create`、幂等键重复 |
| 属性级冲突 | `ConflictProperty` / `ErrPropertyConflict` | kind + sentinel error | 相关集合与基线之后的任一已提交足迹相交 |

判定顺序固定为 **删除 → 重复/基线 → 属性**，因此任意一次写入最多命中一类。
校验钩子的 `Validate` 失败不属于三类冲突，返回包裹 `ErrRejected` 的错误，且
**不产生 Decision 之外的任何状态变化**（不分配版本、不走时钟、不留实例）。

## 3. 版本、快照与时钟

- 版本号是每实例独立的严格递增整数（`head+1`），只在持目标实例锁时分配。
- 每次成功写入在存储级逻辑时钟上恰好 +1（`atomic.Uint64`）。时钟只用于（a）成功/拒绝
  路径可从外部观测的区分，（b）随机测试中的候选串行顺序；**版本分配不读取时钟值**。
- 快照一旦构造即不可变：每个版本保存按属性名排序的 `(k,v)` 列表与一次性计算的
  规范化 JSON 字节串。合并写基于 head 快照构造全新快照，旧版本任何字段都不原地修改，
  因此任意版本的 `Read` 永远字节级一致。

## 4. 提交协议（两阶段，无全局写锁）

1. **无锁阶段**：读取目标基线快照，调用该类型每个 hook 的 `Declare` 得到读范围；
   链接字段通过基线快照解析为具体实例 ID；未显式钉住的外部版本取当时的外部 head。
2. **加锁阶段**：收集 `{目标} ∪ 读范围内的链接实例`，按 `ObjectID` 字典序依次取
   每实例互斥锁（防死锁）。
3. **持锁裁决**：运行 `Validate` → 删除检查 → 幂等/基线检查 → 相关集合计算 →
   标记比较（第 5 节）。
4. **提交**：合并属性 → 构造新快照 → `head+1` → 更新标记 → 时钟 +1 → 追加 Decision。
   任何一步失败都在修改状态之前返回。

因为每个实例的状态（版本、标记、Decision）只在其自身锁下读写，而同一实例的全部
提交被其锁完全串行化，跨实例提交又按全局序取锁，故系统的每个交错执行都等价于
某种按实例锁授予点排列的串行执行（不可产生仅在并发下出现的中间状态）。

## 5. O(1) 于历史长度的冲突证据

朴素判定需要扫描基线之后的全部版本足迹，代价随历史线性增长。这里每个实例只维护

```
localMark: Property -> Version   // 每个属性最后一次被相关集合触及的版本
```

裁决 `W`（基线 `b`，外部实例 `id` 观测版本 `obs_id`）时：

- 本实例属性 `p`：比较 `localMark[p] > b`；
- 链接实例 `id` 的属性 `p`：在 `id` 的锁下比较 `id.localMark[p] > obs_id`。

比较次数恰好等于 `|Rel(W)|`，与历史版本总数无关。每次比较都作为
`ConflictEvidence{Object, Property, Observed, Committed, Hit}` 写入该次
`Decision`。`TestConflictCostIndependentOfHistory` 在 1 版与 200 版历史上断言
证据条数相同；标记与朴素扫描的一致性由随机差分测试里的 `naiveRuleConflicts`
逐条复核。

## 6. 链接与间接相关

链接本身只是一个普通属性（其值是被指实例 ID）。**唯一**使两个实例产生跨实例冲突
关联的是 hook 声明的外部读：`PropertyRef{Link:"link", Local:"p"}` 表示“经由本实例
的 `link` 字段指向的实例，读取其 `p`”。被指实例在 `p` 上的版本一旦越过写入方观测到
的版本，下一次对指向实例的写入即判 `ConflictProperty`；被指实例的无关属性变化、或
没有任何 hook 声明读取它的指向实例写入，都不构成冲突。

## 7. 决策日志与可重放性

每次进入裁决的尝试（含成功、三类拒绝、hook 拒绝）都在目标实例锁下追加一条
`Decision`：声明基线、提交时 head、写集合、hook 读范围、外部观测版本、最终相关集合、
全部标记比较证据、裁定类别与理由。测试可仅凭 Decision 序列重放朴素规则（见
`naiveRuleConflicts`），无需额外对外状态。

## 8. 关键取舍

- **每实例锁 + 排序取锁**，而不是单全局锁：不相交属性集、不同实例的写可真正并行；
  放弃了无锁 CAS 方案（跨实例读范围使单字 CAS 无法原子覆盖多个 `localMark`，还要
  自行处理锁序，复杂度与可证性都更差）。
- **合并采用“后提交者基于最新 head 合并”**而非多版本 fork：符合“合并为同一基线之上
  的新版本”的要求；放弃了整实例悲观锁（会错误拒绝不相交并发写）。
- **标记表替代历史扫描**：保留 Decision 日志用于审计/重放，热路径不扫历史；放弃了
  “仅保留写集合足迹”的方案——它无法捕获仅经由 hook 读集合产生的冲突。
- **逻辑时钟只做观测证据与串行序编号**：版本严格性由每实例计数器保证，时钟回拨/跳变
  都不会影响版本正确性；放弃了用物理时间戳生成版本号（违反“不得依赖时钟取值”）。
- **快照不可变 + 规范化 JSON**：以额外内存换取“旧版本读取字节不变”，避免了读时加锁
  拷贝。
- 被放弃的方案：MVCC 依赖图、CRDT、整实例串行化——前两者对“相关集合相交即拒”的
  强语义支持过度或不足，后者无法满足属性级并行。
