# 对象整体删除与属性历史独立删除 — 设计说明

## 问题

本体平台需要两套互不隶属的逻辑删除机制：

- **整体删除**：对象级墓碑，删除后对象及其全部属性的全部历史记录对一般查询一律不可见，全有或全无。
- **单独删除**：针对某一条属性历史记录的删除标记，只影响该记录本身的可见性。

两者存在单向约束：对象处于整体删除状态时，拒绝一切针对其属性历史记录的单独删除/撤销操作；复活后该约束解除，且复活不隐式改动任何单独删除标记。

## 核心取舍

### 1. 两套标记物理分离，整体删除为 O(1) 墓碑

对象整体删除状态是 `objectState.deleted` 一个布尔位；每条历史记录的单独删除状态是 `HistoryRecord.Deleted`，按记录独立存储。整体删除/复活只翻转对象级布尔位，**绝不遍历**历史记录，因此开销与记录总数无关。

可见性不在写入时物化，而在**查询时**按三层条件合成（见下）。这是本设计最关键的取舍：用查询时的一次分支判断，换取写入时的 O(1) 与标记的彻底解耦——两套标记互不覆写，复活天然保留所有单独删除状态，无需任何"恢复交织连续性"的补偿逻辑。

### 2. 三层可见性判定（查询时合成，固定层序）

`QueryVisibleValue(object, property, at)` 依次核对：

1. **对象层**：对象整体删除 → `OBJECT_DELETED`；
2. **记录层**：时间维度定位到的候选记录被单独删除 → `RECORD_DELETED`；
3. **时间层**：`at` 之前无任何生效记录（无候选）→ `NOT_CURRENT`。

三层互斥，首个未通过的层即归类原因。候选记录通过二分查找 `ValidFrom <= at` 的最大者定位（历史按时间升序追加，写入时强制单调）。

注意"记录被单独删除 ∩ 记录已非最新"这一组合：候选记录由时间层唯一定位，被删除的旧记录一旦不再是候选，其删除标记不影响查询结果——这正体现两套机制互不隶属。

### 3. 错误判定次序固定

单独删除/撤销操作按固定次序只报第一类错误：

`ErrObjectNotFound` → `ErrRecordNotFound` → `ErrObjectDeleted` → `ErrRecordAlreadyDeleted`

判定在 `checkRecordOp` 中顺序短路，不依赖任何内部状态细节。撤销单独删除对"本未被删除的记录"是幂等空操作（规格只禁止重复删除，未禁止重复撤销；选择幂等可避免引入规格外的第五类错误）。

### 4. 并发：单互斥锁串行化 = 可线性化

所有操作（含查询）在同一把 `sync.Mutex` 下执行，天然等价于某个全局顺序。操作日志在锁内追加并分配全局序号，因此日志顺序就是线性化点顺序——并发测试据此把日志重放到朴素实现上逐步核对输出，证明无中间态泄漏（查询不可能看到"对象标记已改、记录标记集合未一致"的状态，因为查询与写操作互斥）。

## 被放弃的方案

| 方案 | 放弃原因 |
| --- | --- |
| 整体删除时把标记下推到每条历史记录 | O(N) 写入，违反开销约束；且复活需区分"本来就是单独删除"与"整体删除下推"，需额外标记位，交织连续性恢复复杂易错（朴素参照实现 `NaiveService` 即此方案，仅作测试对照） |
| 派生可见性视图（删除时重建可见记录索引） | 重建成本随历史总量线性增长；视图与源标记可能不一致，引入第二类真相 |
| 记录删除用集中式 `map[RecordID]bool` 墓碑表 | 与内联标记等价，但快照比对与日志需额外间接层；内联到记录更直观，且二者本就是"各自独立存储" |
| 撤销单独删除对未删除记录报错 | 规格只定义四类错误；引入第五类会破坏"四类互斥"的判定面，故选幂等空操作 |
| 读写锁（查询走 RLock） | 查询需追加操作日志（带全局序号），读锁下写日志需第二把锁或原子序号，收益不抵复杂度；演示规模下互斥锁足够 |

## 操作日志

每次操作在锁内追加一条 `LogEntry`：操作类型、输入（对象/记录/属性/时间点）、输出（错误或查询结果）、以及据以判定的三层条件取值快照（`TriCondition`）。日志序号即全局线性化顺序，可直接驱动重放验证。

## O(1) 性质的可验证证明

两种方式，均可在测试中复现核对：

1. **确定性计数**：`Service.recordFlagWrites` 统计对记录删除标记的写入次数。`TestDeleteRestoreCostIndependentOfHistorySize` 在 100 与 10000 条记录下执行整体删除+复活，断言计数增量为 0；`TestObjectDeleteDoesNotTouchRecordFlags` 进一步逐条比对前后快照，证明标记未被覆写。
2. **基准测量**：`BenchmarkDeleteRestore` 在 100 / 10,000 / 1,000,000 条记录下测量删除+复活耗时，ns/op 保持同一量级（实测 100~2000ns，与 N 无关）。

## 正确性验证（本地复现）

```bash
go test ./...                 # 全部单元测试
go test -race ./...           # 竞态检测（并发线性化测试）
go test -run TestDifferentialRandomOps -count=1 ./ontology   # 2 万步随机差分
go test -bench=DeleteRestore -benchtime=200x -run=NONE ./ontology  # O(1) 基准
```

- **差分测试**：固定种子的随机操作序列（创建/追加历史/整体删除/复活/单独删除/撤销/查询），每步比对 `Service` 与 `NaiveService` 的错误与查询结果，结束逐条比对全部标记快照。
- **并发测试**：8 个 goroutine 交织执行四类操作与查询，随后按日志顺序重放到朴素实现，逐条核对输出与最终快照。
- **多轮交替**：`TestDeleteRestoreCyclesConsistency` 交替执行单独删除/撤销与整体删除/复活共 5 轮，验证状态与朴素实现一致。
