# 对象实例存储与双时态可见性子系统 — 设计说明

## 1. 要解决的问题

在同一套版本链上让三件事自洽：

1. **乐观并发写入**：每次写入必须声明它基于的前序版本号（凭证）；凭证过期即拒绝。
2. **逻辑删除与复活**：删除是“不携带新业务内容、但占用系统时间版本号”的特殊写入；删除之后的再次写入是复活，而不是新主键。
3. **双时态回溯**：业务时间（事实何时成立）与系统时间（事实何时被记录）是两条正交的轴，任意 `(系统时间 S, 业务时间 T)` 都要能确定性地还原当时的状态。

## 2. 模块划分

| 包 | 职责 | 不做什么 |
| --- | --- | --- |
| `internal/instance` | 持久化、版本号单调分配、凭证仲裁、最早边界、最新指针、并发串行化 | 不解释双时态坐标如何定位 |
| `internal/bitemporal` | 每个主键独立的双时态索引：业务起点有序集合 + 同起点覆盖链、历史重建 | 不感知负载内容与删除语义 |
| `internal/api` | 对外读写门面、凭证字符串解析、错误归一化、结果标记（`ALIVE/DELETED/NEVER_WRITTEN`） | 不持有任何裁决状态 |

依赖方向是单向的：`api → instance → bitemporal`，因此不存在环。

## 3. 数据模型

### 3.1 版本

每条被接受的写入产生一条不可变 `Version`：

```
SysVersion  int64   // 全局单调，严格递增，从 1 开始
BizStart    int64   // 业务时间起点（>= 0）
Base        int64   // 乐观凭证：所基于的前序 SysVersion，0 表示要求该主键尚不存在
Deleted     bool    // 是否逻辑删除
Payload     string  // 事实内容（删除为空）
```

每个 `(对象类型, 主键)` 维护：

- `commits []Version`：只追加的完整版本链，任何记录都不物理丢弃；
- `index bitemporal.Index`：随每次提交产生的新索引快照。

### 3.2 业务时间是半开区间

业务时间不用“起点 + 终点”成对存储。每个起点 `sᵢ` 的区间终点由**起点更大的下一条记录**隐式确定：

```
[sᵢ, sᵢ₊₁)  —— 没有 sᵢ₊₁ 时终点开放 (+∞)
```

这样“追溯写入过去的一个起点”不需要改写任何已有记录，只需插入一个新区间并截断它右侧的区间。

### 3.3 同业务起点的覆盖

同一业务起点可被多次写入。它们构成一条按系统时间升序的覆盖链。查询 `(S, T)` 时：

1. 取所有 `起点 ≤ T` 的业务起点中最大的那个 `s*`；
2. 在 `s*` 的覆盖链里取 `SysVersion ≤ S` 的最后一条。

系统时间更晚的记录覆盖对方的**可见性**，但两条记录都物理保留，因此把 `S` 拨回过去仍能看到旧值。

### 3.4 逻辑删除与复活

删除提交与普通提交进入完全相同的版本链与索引，仅 `Deleted=true`。因此：

- 删除起点截断它左侧存活区间的业务终点；
- 删除之后更大起点上的普通写入自然形成复活区间；
- `HistoryAsOf` 能还原 `存活 → 删除 → 复活` 三段，删除绝不会被当成“主键整体失效”。

## 4. 双时态索引的关键取舍

### 4.1 选择：每键一棵持久化（不可变）treap

索引是一棵以业务起点为键的 treap：

- 树按 `BizStart` 有序，支持 `floor(T)`（≤T 的最大起点）；
- 每个节点挂一条同起点的系统版本链（升序切片，二分查找）；
- 节点优先级是 `splitmix64(BizStart)` 的**确定性**哈希，所以树结构只由“存在哪些起点”决定，与插入顺序、并发交织无关；
- 所有更新走**路径拷贝**：旧快照永不被修改。

为什么需要持久化：查询 `AsOf(S, T)` 要的是“系统时间 S 那一刻的索引形状”。由于追溯写入可能在很晚的 `S` 才插入一个很小的业务起点，可变索引无法回答“过去看不到它”。持久快照让每次提交后旧根继续代表旧时刻。

### 4.2 查询算法（带可见性的 floor）

普通 BST floor 在“节点对 S 不可见”时会出错：一个尚未提交的起点不能作候选，但它两侧都可能存在可见起点。算法因此推广为：

- `key > T`：只可能在左子树；
- `key ≤ T` 且 `chain[0] ≤ S`：节点可见，更新候选，继续向右找更大可见起点；
- `key ≤ T` 但不可见：先在右子树找更大可见起点，找不到再回退到左子树。

访问沿至多 O(树高) 的根到叶路径，叠加覆盖链上的 O(log k) 二分。

### 4.3 复杂度（与规模的关系）

- 双坐标定位：`O(log m + log k)`，`m` = 该主键不同业务起点数，`k` = 同起点覆盖次数；`m+k ≤` 该主键历史版本总数。**不随版本数线性增长**。
- 每个主键一棵独立索引：查询不触碰其它键，**不随对象类型下实例总数增长**。
- 写入：`O(log m)` 次路径拷贝 + 链追加（摊还 O(1)）。

可执行的验证见 `internal/instance/complexity_test.go`：2 万个不同起点时一次定位只访问 10 个节点；再插入 5000 个**无关主键**后访问数完全不变（=10）；同起点 2 万次覆盖时访问 31（树深 + 链二分）。规模从 100 增到 20000（200 倍），访问数增长倍数被断言在常数范围内。若实现退化为线性扫描，这些断言会失败。

### 4.4 被放弃的方案

1. **朴素双数组 / 全量线性扫描**：语义最直白，但查询 O(版本总数)，直接违背复杂度要求。它被保留下来作为测试里的**参照模型（oracle）**，而不是生产实现。
2. **每个业务起点一条可变有序数组 + 全局当前视图**：无法表达“系统时间回溯时某起点尚不存在”，除非再维护一套按系统时间的反向索引，两套索引一致性难证明。
3. **复制整棵排序切片（copy-on-write 全量）**：持久化且查询好写，但每次写入 O(m) 复制，写放大随历史线性增长。
4. **持久化 AVL/红黑树**：复杂度与 treap 相同，但旋转/再平衡的路径拷贝代码更复杂；treap 的确定性哈希用更少代码给出随机平衡树的期望对数高，且结构对重放稳定。
5. **区间线段树 / R-tree**：适合二维重叠区域查询，但本题区间是“起点即决定终点”的一维铺砌，floor 查询足够，二维结构属于过度设计。

## 5. 写入仲裁与拒绝次序

所有判定集中在 `Store.Write` 的同一临界区内，按题目要求**只报第一个命中原因**：

1. `INVALID_ARGUMENT`：对象类型为空、主键为空、业务起点非法（<0）、凭证格式非法、存活写入负载为空；
2. `OPTIMISTIC_CONFLICT`：凭证 ≠ 当前最新 `SysVersion`（键不存在时最新为 0）；
3. `BEFORE_EARLIEST_BIZ`：业务起点 < 该键已确认提交的**最早**起点（最早可追溯边界）。

关键点：**系统版本号在全部校验通过后才 +1**。因此被拒绝的写入：

- 不占用系统时间序号（全局时钟不变，无空洞）；
- 不改变最新版本指针；
- 不进入版本链，也不调用索引 `Apply`，双时态索引完全看不到它。

最早边界取该链**第一条**提交的 `BizStart` 且对所有后续写入恒定。起点**等于**边界是允许的（同起点覆盖），只有严格小于才拒绝。

## 6. 并发等价串行

- `Store` 用一把 `sync.RWMutex`，写入在 `Lock()` 临界区里完成“校验 → 分配版本号 → 追加版本 → 更新索引快照”全流程，因此提交点是原子的。
- 两个基于同一前序版本的并发写入：先进入临界区者成功并推进最新指针，后者凭证立即失配而冲突，**不可能都成功**。
- 系统版本号本身就是全局提交顺序的编号；任何交织的结果都等价于按该编号排序的某种全局串行序列。

## 7. 确定性与重放

- 系统时间在本实现中是存储子系统分配的**逻辑单调时钟**（1,2,3,…）。题目只要求“单调、链内严格递增、不回退”，逻辑时钟天然满足，并且让重放逐字节可复现、测试不依赖墙上时间。
- 树优先级是业务起点的纯哈希，不依赖插入顺序。

重放同一组 `(起点, 凭证, 删除标记, 负载)` 操作：拒绝/接受结果、版本号、索引形状、任意双时态查询结果全部一致。`TestDeterministicReplay` 与差分测试都对此做了断言。

若要对接真实墙上时间，只需把“版本号分配器”替换为单调递增的时间戳源（`now ≥ last+1`），仲裁与索引逻辑不变。

## 8. 查询结果三态

| 情况 | 标记 | 含义 |
| --- | --- | --- |
| 键从未写入，或 `S` 早于该键首版本，或 `T` 早于任何已声明起点 | `NEVER_WRITTEN` | 该时点看不到任何事实 |
| 定位到的版本 `Deleted=true` | `DELETED` | 事实在该业务时点不成立（仍返回删除版本号与起点） |
| 定位到普通版本 | `ALIVE` | 返回版本号、业务起点与负载 |

“从未写入”与“写过但当前处于删除区间”因此被严格区分（前者无版本，后者携带删除版本）。

## 9. 本地验证方法

```bash
# 工具链（仓库要求 Go 1.26+）
export PATH=$PATH:/usr/local/go/bin
export GOCACHE=/tmp/gocache   # 仅当默认缓存目录只读时需要

go test -race -v ./...        # 全量 + 竞态检测，打印每次操作的输入/输出/依据
go test ./...                 # 常规全量
go vet ./...
gofmt -l .
```

测试矩阵：

- `TestSameBizStartOverride`：等业务起点、不同系统时间的覆盖与回溯；
- `TestDeleteResurrectThreePhases`：存活/删除/复活三段，沿业务轴与系统轴双向切片；
- `TestQueryBoundaries`：查询时点早于任何记录、晚于全部记录、从未写入键；
- `TestRejectionOrder`：三类拒绝的固定次序，且拒绝不消耗版本号；
- `TestOptimisticConcurrencyRace`：32 个 goroutine 持同一凭证竞争，恰一个成功，无版本号空洞，`-race` 下无数据竞争；
- `TestDeterministicReplay`：操作序列重放得到相同版本链；
- `TestRandomDifferential`：4000 次随机写入/删除/双时态查询，与独立维护全量版本的朴素线性扫描 oracle 逐条对照（已用 5 个随机种子重复验证）；
- `TestQueryComplexityGuards`：2 万版本规模的访问计数上界与“实例总数无关”断言。

每次操作都通过 `TRACE`/`QUERY`/`RAND` 日志打印**输入、实际输出、以及据以判定的版本与时间依据**，用 `-v` 即可查看完整审计轨迹。
