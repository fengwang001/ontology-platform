# 变更流消费与补偿子系统 — 设计说明

## 1. 职责与总体结构

子系统消费本体对象与动作产生的变更流，对每条"动作已成功执行"事件
触发一个关联的补偿型动作，并保证：

- 补偿动作的多项副作用原子生效（全部生效或全部不生效）；
- 同一条变更事件引发的补偿恰好执行一次；
- 故障重启后可从已提交边界续作，不重放已生效部分。

```
ontology/
  types.go     事件、副作用、补偿计划构造器等公共类型
  errors.go    四类互斥错误与固定优先级
  dedup.go     O(1) 事件去重器 + 决策审计日志
  journal.go   补偿执行历史（预写日志）与生命周期状态机
  store.go     并发安全的本体对象存储
  consumer.go  消费流水线：去重 → 分派 → 执行/续作/撤销
cmd/server/    演示入口
```

所有持久化状态集中在 `Storage`（Deduper + Journal + ObjectStore），
`Consumer` 本身无状态。进程崩溃后用同一 `Storage` 构造新的
`Consumer` 即完成"重启"，这是故障注入测试的基础。

## 2. 关键设计决策

### 2.1 事件身份与重复判定规则

每条事件携带两个标识：

- `EventID`：标识一次投递；
- `ActionExecutionID`：标识一次真实的动作执行。

判定规则：

| 情形 | EventID | ActionExecutionID | 判定 |
|---|---|---|---|
| 网络重试的重复投递 | 相同 | 相同 | 重复，跳过 |
| 独立等价调用 | 不同 | 不同 | 新事件，各自补偿 |
| 标识矛盾 | 相同 | 不同 | 无法判定（错误） |
| 标识矛盾 | 不同 | 相同 | 无法判定（错误） |
| 标识缺失 | 空 | 任意 | 无法判定（错误） |

要点：**负载等价性不参与判定**。两次参数与效果完全相同的调用只要
标识全新，就是两次独立的真实执行，各自触发一次补偿；只有标识完全
相同的投递才被去重。这要求变更流上游为每次真实执行分配唯一的
`ActionExecutionID`、为每次投递分配唯一的 `EventID`（重试沿用原值），
这是系统与上游之间的显式契约。

### 2.2 恰好一次 = 去重 + 幂等续作

恰好一次由两层机制合成，而非单点保证：

1. **去重层**（`Deduper`）：两张哈希表（按 `ActionExecutionID`、按
   `EventID`）做 O(1) 判定。重复投递不直接丢弃，而是进入
   `resumeOrSkip`：补偿已达终态才跳过，仍处于 `InProgress` 则续作——
   这正好覆盖"崩溃后事件被重新投递"的场景。
2. **执行层**（`Journal`）：补偿计划在首次副作用提交前整体落盘
   （预写日志），每项副作用有幂等键 `actionExecutionID#序号`。
   续作时跳过已提交项，只施加剩余项，因此 `OpAdd` 这类非天然幂等
   的操作也不会被重复施加。

### 2.3 原子性：校验前置 + 前向恢复

补偿动作的原子性分两个相位保证：

- **提交点之前**：先构造完整计划并通过全部校验（目标存在性、结构
  合法性），任一失败则一项副作用都不施加——"全部不生效"。
- **提交点之后**：采用前向恢复（forward recovery）。一旦第一项
  副作用提交，补偿越过不可逆点，必须执行到完成；崩溃后由续作
  机制完成剩余部分——逻辑上"全部生效"。

`apply` 与 journal 落盘在消费端全局锁内构成原子提交点；故障注入点
只定义在每项提交之后。生产部署中 journal 与对象存储应同事务化
（见 §4 被放弃的方案）。

### 2.4 撤销规则（确定性，不依赖时刻）

原始动作的撤销事件到达时，按补偿记录的持久化状态判定：

- 已提交副作用数 == 0（含记录尚不存在）→ 补偿放弃（`Abandoned`），
  此后原始成功事件乱序到达也不再执行；
- 已提交副作用数 ≥ 1 → 补偿必须继续完成，撤销不介入。

由于所有消费在同一全局锁内串行化，"撤销"与"补偿首次提交"在全局
顺序中有确定先后，结果只取决于该顺序，与撤销发生的具体物理时刻
无关。

### 2.5 错误分类与优先级

四类互斥错误，同一条事件同时满足多类条件时只报告数值最小者：

1. `IdentityUndecidable` — 标识缺失或矛盾。身份不明时一切后续
   处理无从谈起，故最优先。
2. `HistoryMissing` — 已部分生效但续作所需历史缺失。部分生效状态
   的风险高于尚未开始的状态，故优先于后两类。
3. `TargetMissing` — 目标对象不存在或已被撤销。
4. `AtomicityViolation` — 计划构造失败或结构校验失败。

任一错误发生时处理立即停止：提交点之前失败则零副作用；提交点之后
失败（续作时发现历史缺失/目标消失）则停在已提交边界上，已生效
部分不扩大、不回滚。

### 2.6 可串行化与无关并发修改的共存

`Consumer.Consume` 全程持有一把全局互斥锁，任意并发消费序列的可
观察结果等价于按锁获得顺序的串行执行——这是最朴素的可串行化
实现（取舍见 §4）。

补偿续作**不以对象版本作为是否继续的依据**：续作只查询自己的
journal，不检查对象是否被无关事件修改过。无关并发修改与续作在
全局顺序中串行交错，各自生效、互不干拒。被放弃的方案是乐观并发
控制（版本比对失败即拒绝续作），它会导致补偿永远无法完成的活锁。

### 2.7 去重开销的 O(1) 证明

`Deduper` 用哈希表索引全部历史事件，单次判定至多 2 次哈希探测，
与累计事件总量无关。可独立验证的方式：`Deduper.Probes()` 暴露累计
探测计数，`TestDedupConstantCost` 断言处理 2n 条事件（n 新 + n 重复）
后探测数恰好为 3n——若实现退化为线性扫描，该等式立即不成立。

### 2.8 可审计性

每次去重判定追加一条 `DecisionRecord`：输入事件标识、所对照的历史
事件标识（`ComparedAgainst`）、结论与理由、序号与时间戳。
`TestModelConformance` 断言日志条数与消费次数严格相等，保证
"每次判定都有记录"不被破坏。

## 3. 本地验证方法

```bash
go test ./... -race -count=1   # 全量测试（含竞态检测）
go test ./ontology -run TestModelConformance -v   # 随机序列模型对照
go test ./ontology -run TestDedupConstantCost -v  # O(1) 去重证明
go run ./cmd/server                               # 演示
```

测试覆盖：

- `dedup_test.go`：重复投递 vs 独立等价调用的边界穷举（两标识维度
  全组合）、决策日志审计、O(1) 探测计数证明；
- `consumer_test.go`：恰好一次、独立等价调用各补偿一次、3 个崩溃点
  的故障注入续作、续作与无关并发修改共存、撤销规则两分支、
  64 并发重复投递恰好生效一次、64 并发不同事件的可串行化结果；
- `errors_test.go`：四类错误各自触发 + 三组多条件并存时的优先级；
- `model_test.go`：独立朴素模型（线性扫描去重 + 切片状态机）与
  被测系统在 5 个随机种子 × 600 步操作序列下逐步对照，操作涵盖
  新事件/重复投递/等价调用/撤销/崩溃重启/标识损坏。

## 4. 被放弃的方案与取舍

- **基于负载哈希/内容指纹去重**：无法区分"重试"与"独立等价调用"，
  会把真实的二次调用误判为重复。放弃，改用显式身份契约（§2.1）。
- **乐观并发控制（对象版本比对）**：续作时检测到对象被无关修改即
  拒绝，会使补偿在热点对象上永远无法完成（活锁），且违反"无关
  修改应共存"的要求。放弃，改用全局锁串行化 + journal 自描述续作。
- **分片锁/每对象锁提升并发度**：全局锁实现最简单且正确性易于
  论证，但吞吐受限。生产化可按 `ActionExecutionID` 分片加锁（同一
  事件的判定与续作仍串行），本交付为保持可验证性未做。
- **补偿回滚（backward recovery）**：部分生效后出错即撤销已生效
  部分。但已生效副作用可能已被下游观察，回滚无法保证真正的
  "未发生"，且与"错误时保持在确定边界"的要求冲突。放弃，改用
  前向恢复。
- **journal 与对象存储分离**：当前 `apply` 与 journal 落盘在同一
  临界区内相继完成，二者之间理论上存在崩溃窗口。生产部署应将
  二者置于同一事务存储（或改用效果外发/CDC 模式）。本交付以
  注入点定义提交边界，窗口问题在设计约束内显式声明。
- **内存实现**：全部存储为内存结构，便于故障注入与模型对照；
  接口（`Storage` 聚合）已按可替换为持久化实现设计。
