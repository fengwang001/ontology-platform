# 静脉用药配置中心排程与稳定期判定系统 — 设计说明

包路径：`ontology/pivas`。系统由五个职责清晰、相互协作的模块组成：

| 模块 | 文件 | 职责 |
| --- | --- | --- |
| 错误分类 | `pivas/errors.go` | 可区分错误码，声明顺序即上报优先级 |
| 类型与配置 | `pivas/types.go` | 药品、医嘱、洁净台配置、存放方式、受理结果 |
| 目录与时钟 | `pivas/ops.go`、`pivas/center.go` | 药品目录、禁忌配对、洁净台登记、单调时钟 |
| 排程内核 | `pivas/schedule.go`、`pivas/model.go` | 可行安排搜索、紧急连锁顺延、取消、批次队列维护 |
| 快照与自检 | `pivas/dump.go` | 确定性状态快照、系统级不变量校验 |

## 语义要点

- **时钟**：`now ∈ [0, 10^9]`，被接受操作推进时钟；被拒绝的操作不改变任何状态与时钟。
  参数校验先于时钟校验（错误优先级：参数非法 > 时钟回退 > 药品不存在 > 禁忌配对 >
  溶媒不兼容 > 避光冲突 > 无可行安排）。
- **目录快照**：医嘱受理时把各药品稳定秒数最小值、避光需求、溶媒快照进医嘱记录，
  之后的目录变更（含禁忌配对增删）对已受理医嘱不追溯。
- **有效期**：送达时刻 = 批次完成时刻 + 运送时长；有效期 = 完成时刻 + 稳定秒数（恰到期已失效）。
  因此“送达在有效期内”等价于 `运送时长 < 稳定秒数`，与批次时刻无关——
  这是排程搜索可以把有效期判定折叠为存放方式静态判定的关键观察。
- **按时**：送达时刻 ≤ 要求送达时刻（恰等于为按时）。
- **批次**：同台、同溶媒、同外袋形态；容量与“数量→时长”对照（严格递增）在登记时校验。
  新批次开始时刻 = `max(now, 台最早可行时刻 freeAt)`；`freeAt` 由“已完成历史下限
  （最后完成批次结束+清场）与队尾批次占据”重组计算，取消、顺延、完成清除后均保持一致。
- **普通医嘱**加入既有批次：后续批次开始时刻一律不得改变（由于队列总是紧凑排布，
  这等价于“只能加入队尾批次”，见下）；**紧急医嘱**允许连锁顺延，顺延后所有受影响
  医嘱的按时约束逐一验证，任一失败则该候选不可行。
- **择优**：送达最早 → 台编号小（字符串序）→ 既有批次优先于新开批次 → 队列下标小。
  存放方式不参与显式 tie-break：其影响已体现在送达时刻中；完全并列时按室温→冷藏的
  枚举顺序取先者（确定性）。
- **取消**：仅未开始批次中的医嘱；批次时长随数量变化，批次与后续批次开始时刻不变；
  空批次移除；已开始（`start <= now`）或已取消报状态不符，未知医嘱报医嘱不存在。
- **并发**：所有公开操作持同一把互斥锁，结果等价于调用进入临界区的串行顺序；
  全部遍历使用排序后的台编号与队列顺序，重放同一操作序列得到完全相同的状态。

## 关键取舍

1. **有效期约束静态化**。`送达 < 完成 + 稳定` ⟺ `运送 < 稳定`，使搜索只需按存放方式
   做一次 O(1) 判定，批次内既有医嘱在时长增加后只需复查“按时”一项。
2. **`freeAt` 单调维护 + 接受时清除（purge）**。已完成批次只在操作被接受时从队首清除
   （每批次均摊 O(1)），拒绝的操作绝不动状态；`freeAt` 记录“已完成历史下限”，
   避免清除后丢失“清场间隔尚未结束”的信息。曾考虑在搜索时惰性清除各台队列，
   但拒绝路径会留下副作用，且快照可比性变差，故放弃。
3. **新批次只追加到队尾**。创建时取台最早可行时刻；插入到既有未开始批次之间会改变
   既定开始时刻，与“普通医嘱不得改变后续批次”的语义冲突，故放弃“紧急医嘱插队开批”方案，
   紧急性只体现在“加入既有批次可连锁顺延”。
4. **避光外袋由医嘱显式声明**。医嘱含 `LightProofBag` 标志；含须避光药品而未声明避光袋
   报“避光冲突”，批次按实际外袋形态编组。曾考虑完全由药品推导外袋形态，但那样
   “避光冲突”错误永不可达，且无法表达“非避光药品也使用避光袋”的合理场景，故放弃。
5. **溶媒兼容 = 类别相等**。药品登记溶媒类别，医嘱选择溶媒，全部相等才兼容；
   未引入任意兼容关系图，保持判定 O(药品数) 且语义明确。
6. **禁忌配对用规范化二元组哈希集合**。判定与配对总数无关（O(1)/对）；
   朴素模型用线性扫描作对照。
7. **错误即值**：`*pivas.Error{Code, Msg}`，调用方可机器判定类别，测试按码断言。

## 被放弃的方案

- **批次内统一存放方式**：让批次同时按存放方式分组。放弃原因：规格只要求同溶媒、
  同外袋形态；按订单粒度选择存放方式可在同批内共存，且送达时刻按各自运送时长计算即可。
- **取消后重排压缩队列**：取消后把后续批次提前。规格明确“批次不得因取消而提前开始”，放弃。
- **全局事件队列驱动批次状态**：用堆维护“批次开始/完成”事件。放弃原因：单调时钟 +
  接受时队首清除即可均摊 O(1) 达到同样效果，且无不必要的堆分配。
- **乐观并发（无锁目录 + 分台锁）**：复杂度远超收益；单互斥锁串行化天然满足
  “等价于某个串行顺序”与确定性重放。

## 复杂度与可验证证明

- **受理开销与历史已完成批次数无关**：已完成批次在每次接受操作时从队首清除，
  每个批次一生至多被清除一次（均摊 O(1)）；搜索只遍历当前队列（未开始批次 + 至多一个
  运行中批次）。基准 `BenchmarkAdmissionCompletedHistory` 在 1 千与 5 万已完成批次
  两档规模下对照，稳态单次受理耗时应基本持平。
- **禁忌配对判定与配对总数无关**：哈希集合单次查询 O(1)。基准
  `BenchmarkIncompatibilityCheck` 在 1 千与 100 万配对两档规模下，分别测量命中
  （报禁忌配对）与未命中（通过判定）两条路径，耗时应基本持平。

## 本地验证方法

```bash
export PATH=$PATH:/usr/local/go/bin   # Go 1.26+
go test ./...                          # 全部单元测试 + 1500 组随机序列对照
go test -race ./...                    # 竞态检测
go test ./pivas/ -run TestDifferentialAgainstNaive -v   # 查看每步输入/输出/判定日志
go test ./pivas/ -run XXX -bench . -benchtime 1000000x  # 两档规模复杂度对照
gofmt -l . && go vet ./...             # 格式与静态检查
```

测试覆盖：有效期恰到期与晚一秒、送达恰等于要求时刻、冷藏/室温取舍、避光冲突、
批容量恰满、清场间隔恰好够与差一秒、紧急插入连锁顺延成功与整体拒绝、目录变更不追溯、
取消后重排不提前、时钟回退、错误优先级、参数非法各分支、并发不变量；
并与独立朴素模型（`pivas/naive_test.go`，线性扫描、保留全部历史批次）对照
1500 组随机操作序列，逐步比对输入、输出与最终快照，另设重放确定性测试。
