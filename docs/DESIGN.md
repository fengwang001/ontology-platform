# 链接记录修复裁决组件（linkrepair）设计说明

## 1. 问题

快照文件中的链接实例记录可能因局部损坏出现：

- 残留：只能确定一端对象，另一端丢失或不可解析；
- 悬空：记录完整，但引用了同一次恢复中已判定不可用的对象；
- 重复：多条记录指向完全相同的一对对象；
- 基数冲突：同一端对象在一个有上限（含上限 1）的链接类型下，
  出现了多个不同的对方实例。

组件需要在恢复时保证结果满足链接类型声明的基数约束，且上述四类
异常必须**互斥、可区分、按固定优先级**报告。

## 2. 包结构与职责划分

| 文件 | 组件 | 单一职责 |
| --- | --- | --- |
| `linkrepair/model.go` | 数据模型 | 链接类型、基数、原始记录、判定结果、计数 |
| `linkrepair/validator.go` | `Validator` | 单条记录结构有效性判定 |
| `linkrepair/referencer.go` | `Referencer` | 两端对象引用可用性核对 |
| `linkrepair/arbiter.go` | `Arbiter` | 去重与基数冲突裁决 |
| `linkrepair/repair.go` | `Repair` | 编排四阶段流水线、统计与确定性输出 |

入口 `linkrepair.Repair(Snapshot) Result` 是纯函数。

## 3. 固定裁决优先级（四类互斥原因）

每条输入记录最终恰好属于“保留”或四类舍弃原因之一：

1. `malformed_structure`：结构损坏无法解析（类型缺失/未知、任一端缺失、
   声明基数非法）。残留记录**整体舍弃**，不用默认值或猜测补全。
2. `reference_unavailable`：结构完整，但任一端对象不在本次恢复的
   可用对象集合内。悬空记录必须在基数裁决前淘汰，
   否则它可能“赢走”一个本不该存在的基数槽位。
3. `cardinality_conflict`：在有上限的基数分组中按固定优先规则竞争失败。
4. `duplicate_record`：与保留记录的 `(类型, From, To)` 完全相同。

**顺序理由**：结构不完整的记录没有可解析的引用与语义，最先淘汰；
引用不可用的链接即使参与裁决也没有合法意义，次位淘汰；
基数冲突与重复是语义不同的两类异常——去重在进入基数分组**之前**折叠，
保证每个基数分组内同一内容只出现一次，二者永不混报。

## 4. 固定优先规则（不允许任意选择）

裁决不得依赖 Go map 迭代顺序等非确定因素，规则完全基于数据自身：

1. **去重**：同一内容键保留原始快照位置 `Offset` 最小的一条。
2. **基数选择**：某分组候选数 `n > cap` 时，按
   “对方实例 ID 字典序升序、相同 ID 再按最小 Offset 升序”排序，
   保留前 `cap` 个，其余判 `cardinality_conflict`。
   - `cap = 1` 即“一端最多关联一个对方实例”；
   - `cap = k` 即带数量上限的多关联，超出部分同样可复现地裁决；
   - `cap = -1 (Unbounded)` 不做限制。
3. **双端独立取交集**：`MaxFrom`（From 端拥有的不同 To 数）与
   `MaxTo`（To 端拥有的不同 From 数）各自独立算出允许集合，
   最终保留二者交集。两个方向的计算互不依赖，处理顺序不影响结果；
   一条链接即使两个方向都竞争失败，也只登记**一条**舍弃记录，
   `GroupKey` 同时列出它输掉的分组与各组胜者 Offset，便于复核。
4. **多类型独立**：分组键包含链接类型。同一对象在 A、B 两种
   链接类型下的冲突分别独立裁决，互不影响候选取舍。

`Offset` 只反映记录在原始快照中的位置；快照不变、规则不变，
重复执行任意次结果完全相同（见
`TestDeterministicConcurrentAndImmutable`）。

## 5. 关键取舍

- **选择字典序 + Offset 作为固定优先规则**，而不是“最新记录”“随机挑选”
  或“首次遇到”：首次遇到依赖输入遍历顺序，随机/最新依赖运行时状态，
  都无法满足“固定不变、重复执行不漂移、并发一致”。
  字典序是数据的全序，Offset 是快照赋予的天然、最终且唯一的平局键。
- **先去重后基数**，而不是先基数后去重：后者会让同一损坏片段的
  多个副本占据多个竞争位置，可能把合法的不同对方候选挤出槽位，
  也会让“重复”与“基数冲突”归因混淆。
- **引用核对先于基数**：悬空链接没有合法身份，不能参与槽位竞争。
- **两个基数方向独立计算再取交集**，而不是按某一方向先裁再过滤：
  顺序式做法会把另一方向的结果耦合进来，双向独立取交集是
  顺序无关的，天然确定。
- **纯函数 + 输出全排序**：`Kept` 按 `(Type,From,To)`、
  `Dropped` 按 `Offset` 排序，内部 map 只用于查找，不出现在输出顺序里。

## 6. 被放弃的方案

- **时间戳/版本号决胜**：损坏快照无法保证时间戳可信且单调；
  题面也只保证“固定规则”，故放弃，改用 ID 字典序 + 快照位置。
- **引用不可用时“保留但标记悬空”**：违反“结果中不得存在引用不可用
  对象的链接”的硬约束，放弃。
- **对全量记录一次性排序裁决**：在无冲突数据上也付出
  `O(N log N)` 成本，违背“开销只与冲突局部相关”，放弃，
  改为哈希登记 + 仅对超限分组排序。
- **把四类异常塞进一个错误码再附说明**：无法程序化区分，
  放弃，使用四个强类型常量 `Reason`。
- **朴素模型与正式实现共享内部函数**：会退化成“自己证明自己”，
  放弃；差分测试包不 import 任何内部符号，独立重写判定流程。

## 7. 复杂度与“工作量只与冲突局部相关”的复核方式

- 结构判定与引用核对：对全部记录各一次 O(1) 检查，`O(N)`。
- 去重与双向分组登记：每条幸存记录常数次哈希写入，`O(N)`。
- 排序：**只在候选数超过 cap 的分组内**执行，组内代价
  `O(s log s)`，`s` 为该组候选数；无冲突分组不排序。
- 结果通过 `Stats.ConflictGroups`（超限分组数）与
  `Stats.ConflictGroupWork`（这些组内候选数之和）直接暴露
  “真正发生冲突的局部范围”。

可复核测试：`TestConflictWorkProportionalToConflictSites` 构造
10000 条互不冲突的记录，断言 `ConflictGroupWork == 0`；
再注入 3 个大小分别为 4/2/5 的局部冲突点，断言
`ConflictGroups == 3`、`ConflictGroupWork == 4+2+5 == 11`。
即总记录数增长不会让冲突裁决工作量失控，它只随实际冲突点增长。

## 8. 并发与不可变性

`Repair` 不写入 `Snapshot`（内部 map/slice 均新建或拷贝），
不持有跨调用可变状态。`TestDeterministicConcurrentAndImmutable`
以 16 个 goroutine 并发调用同一份损坏快照并逐次比对
`reflect.DeepEqual`，同时在 `-race` 下运行并校验输入快照前后不变。

## 9. 测试与本地验证

- 单元测试（`linkrepair/`）覆盖：
  - 单一基数下 2 个、3 个冲突候选；
  - 带上限（cap=2）恰好超出 1 个；
  - 反向基数 `MaxTo=1`；
  - 残留不完整记录、未知/缺失类型；
  - 引用不可用对象；
  - 重复与基数冲突混合且归因不混淆；
  - 同一对象同时卷入两种链接类型、两类独立裁决；
  - 反复执行 + 并发一致 + 输入不被修改；
  - 恢复结果满足全部声明基数约束；
  - 冲突工作量只与实际冲突点相关。
- 差分对照（`linkrepair/linkrepairtest/`）：独立朴素参照模型
  `NaiveRepair`（逐步独立判定，不共享内部实现）与正式实现
  在 2000 个固定种子随机构造的损坏集合（1–40 条记录、
  1–4 种链接类型、随机 cap/对象失效率/损坏注入）上逐条比对
  保留集合与每个 Offset 的舍弃原因。
- 每次裁决的输入、输出与判定依据记录于
  `linkrepair/linkrepairtest/testdata/adjudication-log.txt`
  （case、seed、类型基数、可用对象、逐条输入→输出→原因、
  最终保留集合与统计）。
