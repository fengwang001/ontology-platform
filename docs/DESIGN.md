# 支付预授权额度账务系统 — 设计说明

位置：`payledger/` 包。本文记录关键取舍、被放弃的方案与本地验证方法。

## 模块划分

| 文件 | 职责 |
| --- | --- |
| `doc.go` / `types.go` | 包文档、配置（有效期 E、容差基点）、授权状态与快照类型 |
| `errors.go` | 可区分错误类别 `ErrKind`，声明序即优先级序 |
| `ledger.go` | 外观 `Ledger`：互斥锁、全局时钟、账户索引、授权编号全局索引 |
| `ops.go` | 全部变更操作与查询的内部实现（先校验后生效两段式） |
| `account.go` | 账户（额度/已入账/持有跟踪器）与授权记录（纯数据 + 派生函数） |
| `hold.go` | `holdTracker`：按过期日聚合持有的懒结算结构（查询复杂度核心） |
| `treap.go` | 带子树和的笛卡尔树，支撑已过期桶的任意历史时刻求和 |

协作关系：`Ledger` 串行化并维护时钟与全局索引；`ops.go` 按优先级
完成全部校验后，调用 `account`/`authorization` 的派生函数计算，并通过
`holdTracker` 增量维护"有效持有总额"这一聚合，使查询免于逐授权求和。

## 关键取舍

1. **过期是派生属性，不是存储状态。** 授权记录只存 `expiryDay` 与终结
   标志；`expired = now > expiryDay` 在求值时计算。因此"过期自动释放"
   不需要任何触发操作，可用额度天然是（已接受操作, now）的纯函数，
   相同操作序列重放结果完全相同。

2. **单一互斥锁串行化。** 所有公共方法在临界区内完成"校验 + 生效"，
   结果自动等价于某串行顺序；捕获的入账与持有减少在同一临界区提交，
   任何时刻都观察不到一半。放弃分账户锁：时钟是全局单调的（"上一次
   被接受操作"不区分账户），全局锁的串行语义最直接且足够正确。

3. **先校验、后生效，校验顺序硬编码。** 每个操作先按固定优先级完成
   全部检查（参数非法 > 时钟回退 > 编号重复 > 不存在 > 已终结 >
   超容差 > 额度不足；退款链单独定义），全部通过才触碰状态与时钟，
   因此被拒绝的操作严格不留痕（含不占用授权编号、不推进时钟）。

4. **持有聚合 = 活跃桶（map+最小堆）+ 墓园（带子树和的 treap）。**
   可用额度 = 额度 - 已入账 - 有效持有，前两项是标量，关键是第三项
   不能逐授权求和。`holdTracker` 把持有按截止日分桶：
   - 前向查询（now ≥ 水位）：弹出堆顶所有 `day < now` 的桶结算进墓园，
     每桶一生只结算一次，**均摊 O(1)**；
   - 回溯查询（now < 水位）：墓园 treap 上做一次 `O(log G)` 区间和。
   两条路径都不扫描授权记录，也不触碰其他账户。

5. **查询对缓存的结算是语义中性的。** `Available` 会把过期桶从活跃侧
   移入墓园（改变内部缓存布局），但不改变任何可观察结果——结果始终
   是（已接受操作, now）的纯函数，满足"查询不修改状态"。

6. **查询语义：仅"过期性"按查询 now 求值。** 状态与累计额（已捕获/
   已退款/累计授权）取当前值。推论：非负不变式"可用额度 ≥ 0"对所有
   不早于当前时钟的时刻成立（归纳可证：每类操作生效后，任意
   q ≥ clock 的可用额度都不小于操作时刻校验过的下界）；早于时钟的
   回溯查询是确定性的假设求值，可能把后续入账与当时未过期的持有
   混合，不承诺非负。该语义在 `doc.go` 明示，且生产实现与朴素模型
   在任意查询时刻逐值一致（随机对照测试覆盖）。

7. **增量授权只按增量金额校验额外可用额度**，成功后剩余持有按定义
   `max(0, 累计授权 - 累计捕获)` 重算并迁移到新截止日的桶——这自然
   处理了"超额捕获后再增量"时持有恢复量小于增量金额的情形，且
   `持有增量 ≤ 增量金额` 保证可用额度不为负。容差上限随新累计授权额
   重新计算（只可能放宽，故增量本身无需容差检查）。

8. **容差上浮向下取整**：`上限 = 累计授权 + floor(累计授权 × bps / 10000)`，
   纯整数运算，无浮点误差，重放确定。

## 被放弃的方案

- **每次查询遍历账户全部授权求和（朴素法）**：保留为 `naive_test.go`
  对照模型，但查询开销随历史授权数线性增长，违反复杂度要求，
  仅用于测试对照。
- **逐日水位推进（按天逐个结算）**：单日 O(1)，但 now 大跨度跳跃时
  单次查询 O(时间跨度)，空转天数无桶可结算，被最小堆取代。
- **纯 treap（不区分活跃/墓园）**：任意时刻查询都是 O(log D)，但
  过期桶永不清理导致 D 随历史增长，且前向查询退化为 O(log)，
  不如"堆均摊 O(1) + treap 兜底回溯"的组合。
- **堆 + 破坏性结算（无墓园）**：均摊 O(1) 且最省内存，但"远期查询
  把桶结算掉之后，合法操作（now 只需 ≥ 操作时钟）落在其前"时无法
  正确回答回溯查询，正确性不完备，故加墓园。
- **查询推进时钟**：可免疫上述交错，但违反"查询不得修改状态"，放弃。
- **授权记录存 createdDay 以支持"创建前时刻"的物理一致回溯**：
  只能部分修复回溯查询的时代错乱（入账/持有仍按当前累计额求值），
  却要给持有聚合引入第二维，复杂度代价大；选择明示语义（取舍 6）。

## 本地验证方法

```bash
# 全部单元测试（边界、优先级、不留痕、退款、调额、查询纯度等）
go test ./payledger/

# 随机对照：5 组参数 × 40 种子 × 1500 步，与独立朴素模型逐步比对
# 错误类别、多时刻可用额度、授权快照，并断言可用额度非负
go test -run TestDifferential ./payledger/

# 打印每步输入/输出/判定依据的日志（对照测试的详细模式）
go test -v -run TestDifferentialLogged ./payledger/

# 竞态 + 并发不变式 + 重放确定性
go test -race ./payledger/

# 查询复杂度证明：N 增长两个数量级，查询耗时/分配保持平坦
go test -bench=. -benchmem -run='^$' ./payledger/
```

基准实测（linux/arm64）：历史授权 N=1,000 与 N=100,000 时查询均为
约 22.8 ns/op、0 分配；账户数 M=100 与 M=100,000 时查询约 31–39 ns/op、
0 分配。结构化断言见 `complexity_test.go`：结算后活跃侧缓存为空、
查询不触碰其他账户的跟踪器。
