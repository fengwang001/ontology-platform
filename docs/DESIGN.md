# 乐观重试下基数约束一致性：设计说明

## 1. 问题与目标

链接类型可在 A/B 两侧声明**单侧基数上限**：某个实例在该侧最多关联多少个对端实例。
对持有约束的实例做更新时，调用方以乐观方式提交（携带读到的基线版本）。
当基线落后时，引擎在**同一逻辑请求**内部发起**有限次数**重试。要求：

- 每次重试必须基于**当时最新**的版本与关联关系重新判定，绝不复用第一次尝试读到的数量/集合。
- 三类拒绝原因互斥、可区分、有固定优先顺序：
  **版本冲突 `VERSION_CONFLICT` → 基数不满足 `CARDINALITY_VIOLATION` → 重试耗尽 `RETRIES_EXHAUSTED`**。
- 失败的中间尝试对外完全不可见（版本、关联、时钟均无变化）。
- 只剩一个名额的并发竞争必须**恰好一方成功**，不能超额，也不能名额空置却全败。
- 重试预算有硬上限，不存在长期饥饿。
- 单次基数判定开销 **O(K)**（K=本次涉及的约束数），与当前关联总数 N 无关，并提供可验证证据。
- 并发历史必须等价于某种**串行顺序**。

## 2. 总体结构

| 文件 | 职责 |
| --- | --- |
`ontology/types.go` | 领域类型：`LinkType`、`Cardinality`、`ConstraintKey`、`Request`、`AttemptRecord`、`Result` 等 |
`ontology/errors.go` | 三类互斥终态代码与输入错误 |
`ontology/store.go` | 内存存储：每实例独立互斥锁、版本、链接集合、**基数计数器**、原子 CAS 提交 |
`ontology/audit.go` | 每次尝试的“重新读取”（版本 + K 个计数 + 全量链接快照） |
`ontology/engine.go` | 有限次乐观重试引擎与三类终态分类 |
`ontology/naive.go` | **独立实现**的朴素串行重试参考模型（无锁、单 goroutine） |
`ontology/api.go` / `cmd/server` | JSON DTO 与最小可运行 HTTP 服务 |

## 3. 关键设计与取舍

### 3.1 每实例一把锁 + 锁内 CAS，天然串行化

每个实例有独立 `sync.Mutex`；一次提交的
“**取当前版本 → 版本比较 → 逐约束基数校验 → 写入链接与计数 → 推进版本**”
全部在该实例锁内的同一临界区完成。因此：

- 版本比较与基数校验之间不存在窗口，并发提交被严格串行化；
- 最后一个名额不会被两个请求同时看到（互斥保证**恰好一方**成功）；
- 临界区内要么完整提交，要么零变更返回，失败尝试从结构上就不可能留下状态。

一次提交触碰多个实例（链接两端）时，按实例 ID 升序加锁，杜绝多实例死锁。

### 3.2 O(1) 基数判定：维护计数，而不是数链接

每个实例为每个约束维护一个整数计数 `counts[ConstraintKey]int`，
在提交成功时随链接集合一起在锁内增量维护。基数判定只读取这 K 个计数：

```
满足 ⇔ current + delta ≤ max
```

`delta` 由本次请求在该约束上的净新增（已合并同链接重复操作的净效果）得出，
所有查表均为 O(1) map 操作。判定**不遍历**链接集合，故开销不随 N 增长。

全量链接集合只在审计路径 `readForAttempt` 中快照一次，**不参与判定**。
这通过包内读计数器区分：`counterReads`（决策读）与 `scans`（审计扫描）分开统计。

**证据（不引入对外暴露状态）：**

- `TestCardinalityDecisionO1Evidence`：在 N=0/10/100/1000 下断言单次成功尝试的
  决策计数读恒为常数（K 个约束 × 重读 + 锁内校验），审计扫描恒为 1；
- `BenchmarkCardinalityDecision`：N=100 与 N=10000 的纯判定耗时同量级（亚微秒），
  用 `go test -run=NONE -bench=. ./ontology` 可复现。

### 3.3 每次尝试都重新读取，旧数据在结构上无法带入

引擎每次尝试的开头调用 `readForAttempt`（版本 + 计数 + 链接快照），
这些值都是循环体内的局部变量，上一轮的读取没有任何变量/字段被复用；
随后由 `SettleHook` 注入并发事件，再执行锁内 CAS。
第 2 次及以后尝试的期望版本取自**本次**重读版本，而非历史值。

审计记录统一取“**判定时点**”的状态（CAS 之后再做一次同一时点重读），
因此 `AttemptRecord` 里的版本、快照、逐约束判定依据三者一致，可脱离引擎重放。

### 3.4 三类互斥原因与优先顺序

单次尝试结局 `AttemptOutcome` 三选一：`OutcomeConflict` / `OutcomeCardinality` / `OutcomeCommitted`。
终态拒绝在重试预算维度上分类：

1. **版本冲突优先**：锁内 CAS 发现版本不匹配 → 本次尝试只记 `OutcomeConflict`，零变更。
   即使此刻基数也已满，本次尝试仍**只命中冲突一种原因**，并继续重试
   （名额可能在下次尝试前被释放）——冲突尝试的基数读数只作为审计依据记录。
2. **基数优先于耗尽**：某次尝试版本匹配，但在最新读取下任一目标侧约束不满足 →
   终态 `CARDINALITY_VIOLATION`，精确给出是哪个 `ConstraintKey`，不再消耗预算。
3. **重试耗尽最后判定**：连续 `maxAttempts` 次尝试都因版本冲突失败 →
   终态 `RETRIES_EXHAUSTED`，消息明确说明是预算耗尽而非业务规则不满足。

多约束：一次请求涉及的每个目标侧约束分别生成独立 `ConstraintVerdict`；
任一不满足则整单拒绝，且不会部分提交。

### 3.5 幂等

对已存在链接重复“新增”、对不存在链接“移除”为幂等 no-op：
版本匹配且全部约束通过但净变化为零时，返回成功且**不推进版本、不改状态**。

### 3.6 无饥饿

预算为 `maxAttempts`（默认 5）。引擎**不睡眠、不插入随机退避时钟**
（因此不存在“时钟状态被失败尝试改变”的问题）。
一个请求被后来者连续抢先的次数最多 `maxAttempts`，之后必然得到确定性终态。

## 4. 并发正确性（串行等价）

- **临界区原子性**把每个提交变成不可分割的串行步骤；
  链接集合是按 `(type,A,B)` 去重的 map，计数与集合在同一临界区内同步维护。
- 任意并发历史的可见结果等价于“按各提交拿锁的先后”排成的某种串行顺序。
- 最后名额竞争：只有一个请求能在锁内观察到 `current+delta ≤ max` 并提交，
  其余在其之后拿锁者基于被更新后的计数判定，至多因基数被拒或重试后因耗尽被拒。

## 5. 朴素串行参考模型与对照测试

`naive.go` 是**刻意不共享算法代码**的第二份实现：
单 goroutine、无锁，用普通 map 顺序执行“重读 → 钩子插队 → 版本比较 → 基数校验 → 提交”。
它的每一步本身就构成一种合法串行顺序。

`TestDifferentialRandomized` 随机生成 400 组脚本（每请求独立实例，杜绝跨请求预测），
用同一脚本同时驱动生产引擎与朴素模型，逐字段比对：

- 每次尝试读到的版本、全量链接快照、逐约束判定（current/delta/max/satisfied）；
- 每次尝试结局；最终成功/拒绝代码；提交后版本；
- 每一步结束后两世界的链接集合、版本、计数。

另含固定脚本覆盖：空出名额成功、预算恰好耗尽。
真实并发由 `TestConcurrentSingleSlotExactlyOneWinner`（2/8/32 goroutine）
与 `TestConcurrentBoundedRetriesNoStarvation` 在 `-race` 下验证赢家唯一性与预算上限。

## 6. 被放弃 / 未采用的方案

- **判定时实时 `len()` / 遍历链接集合**：实现简单但判定 O(N)，违背开销要求，放弃；
  改为显式计数（3.2）。
- **数据库风格行版本 + 应用层二次查询**：会在“版本比较”和“基数读取”之间留窗口，
  需要额外锁或可串行化隔离级别；本实现把两者收进同一临界区，避免窗口。
- **冲突后看到基数满就立刻业务拒绝**：会错误地把“本次尝试的冲突原因”和
  “终态业务拒绝”混为一次命中，且名额可能稍后释放，违背“每次尝试只命中一种原因”
  与“重试中基数反复变化以最新为准”。改为：冲突尝试继续重试，终态基数只在版本匹配的尝试给出。
- **无界重试 / 随机退避睡眠**：前者饥饿，后者引入时钟副作用且仍无界；改为硬性预算、零睡眠。
- **跨实例全局大锁**：正确但牺牲吞吐；改为每实例锁 + 按 ID 排序加锁。
- **在一次请求里同时强校验对端实例的反向约束**：会要求持有对端实例锁并可能多跳加锁。
  本实现的契约是：每个实例的侧约束由以该实例为目标的请求负责；
  链接两端计数都会在提交时维护，但一次 `Update` 的业务校验范围是其目标实例承担的侧约束。

## 7. 本地验证方法

```bash
# 工具链（如 go 不在 PATH）
export PATH=$PATH:/usr/local/go/bin

go test ./...                         # 全量测试（含 400 组随机对照）
go test -race ./...                  # 竞态检测
go test -run NONE -bench=. ./ontology  # O(1) 判定基准
gofmt -l . && go vet ./...           # 格式与静态检查

go run ./cmd/server                  # 启动演示服务 :8080
```

演示请求：

```bash
curl -s -X POST localhost:8080/update -d '{
  "instance":"x","baseline":0,
  "ops":[{"typeId":"owns","side":"A","other":"y1","add":true}]}'
```

响应中的 `reason` 为 `VERSION_CONFLICT` / `CARDINALITY_VIOLATION` /
`RETRIES_EXHAUSTED` 之一；`attempts` 数组完整记录每次尝试，可据此重放核验。
