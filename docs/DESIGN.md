# 批量更新原子性 — 设计说明

本文记录本体平台“跨对象类型多实例批量更新”的关键取舍、被放弃的方案与
本地验证方法。实现位于 `ontology/` 包。

## 1. 需求复述与判定语义

一个 `Batch` 由若干实例写操作 `Operation`（全量属性替换，`Props == nil`
表示删除）和若干链接操作 `LinkOp`（增/删一条无向类型化链接）组成。提交
`Commit` 的判定顺序固定为，且四类失败互斥：

1. **内部重复声明** `FailureDuplicateWrite`：同一实例在批次内出现两次，
   或同一条链接在同批中既被增又被删（方向归一化后比较）。
2. **版本冲突** `FailureVersionConflict`：对批次内每一个实例逐一核对调用
   方声明的 `BaseVersion` 与当前版本；不存在实例的当前版本定义为 0。任一
   不符整批拒绝，不跳过。不同实例允许声明各自不同的基线，系统不使用任何
   “批次统一版本号”。
3. **校验钩子拒绝** `FailureHookRejected`：每个操作按其对象类型注册的
   `Hook(current, proposed)` 检查；钩子拿到的是深拷贝，无法修改存储。
4. **基数约束** `FailureCardinality`：在**整批全部生效后的最终链接状态**
   上一次性校验，包括端点类型匹配、不得指向被删除/不存在实例、以及每个
   受影响实例在每个受影响链接类型上的 `Min..Max` 度数。

优先级严格满足：重复 > 版本 > 钩子 > 基数。例如基线落后且钩子也会拒绝
时，返回版本冲突；钩子与基数同时不满足时，返回钩子拒绝。

## 2. 原子可见性与回退

- 判定与状态切换在单个临界区内完成：提交门 `commitMu` 串行化“校验+切换”
  段，状态互斥 `p.mu` 保护所有 map。外部读 `Read`/`ReadMany` 只取 `p.mu`，
  因此任何读要么看到批次前、要么看到批次后的完整状态，`ReadMany` 一次调用
  里所有快照共享同一个逻辑时钟值 `Tick`，不存在跨批次的拼接视图。
- 失败路径在任何状态写入之前 `return`（或仅写日志），因此回退是天然的：
  没有“先改后撤销”。被拒绝批次不修改任何版本号、链接关系，也不推进逻辑
  时钟（`Tick` 只在成功提交时自增一次）。测试
  `TestFailedBatchDoesNotAdvanceClockOrVersions` 与
  `TestVersionConflictPartialBatch` 专门验证这一点。
- 版本号语义：新建实例版本 1；更新版本 +1；删除移除记录（重建时以基线 0
  重新开始，见 `TestDeleteResurrectAndLinks`）。删除实例与其残余链接的“断
  链 + 删除”必须在同一批次内一起提交，否则最终状态出现悬空链接，按基数阶
  段拒绝。

## 3. 并发控制：为什么是提交门 + 状态互斥

要求等价于“存在某种串行顺序”，即可线性化/严格可串行化。我们实现并评估
过三档方案：

| 方案 | 结论 |
| --- | --- |
| 朴素全局大锁（参考模型 `naiveModel`） | 语义正确，但把所有提交串行化；仅作为差分测试的独立参照实现，不作为线上路径。 |
| 每实例严格两阶段锁（sorted 2PL）+ 邻接闭包 | 尝试过。链接基数使得“相关实例”不是静态集合：两个初始不相交的批次可能通过各自新增的边连接同一基数邻域，需要沿链接图求连通分量闭包；闭包在并发增边下会变化，必须配合非阻塞 `TryLock` 重试与提交前重读。实现复杂且重试路径易出错。 |
| **提交门 + 状态互斥（最终选择）** | 内部重复检查在门外完成（纯批次内计算，零全局竞争）；取到门后在 `p.mu` 下一次性完成“快照→版本→钩子→基数→切换→时钟→日志”。这与朴素大锁在可观察行为上完全等价（因此严格可串行化），但把互斥范围限制在纯内存的、只触及批次相关实例的计算上，无 I/O、无系统调用，临界区极短。 |

关键取舍：在“单进程内存存储、钩子为纯函数”的范围内，可串行化要求对
相互影响的批次进行某种形式的串行；提交门以最少的机制（一把 `TryLock`
自旋门 + 一把状态锁）给出与全局锁相同的保证，同时保持决策工作量只与批次
规模相关。要扩展为多进程/持久化存储时，提交门对应事务管理器里的
certifier/串行化令牌，状态互斥对应 WAL 追加的原子段——接口与判定顺序
不需要改变。

## 4. 判定开销与“不随实例总数增长”的证据

- 判定阶段只枚举：批次写实例、链接端点、以及这些实例在**现有链接图**中的
  连通分量（邻接表 `adj` 按实例索引，不扫描全部链接）。对不与批次相连的
  背景实例零访问。
- 证据以**不额外对外暴露状态**的方式给出：`Stats().InstanceInspections`
  是包内决策计数器，统计一次提交实际查阅的实例记录数。测试
  `TestDecisionCostIndependentOfStoreSize` 在 0 / 100 / 1 000 / 10 000 个
  背景实例下提交同一个固定两实例批次，计数恒为 2。
- 邻接表的存在意味着基数校验是“按受影响实例的度数”工作，而不是“按系统
  实例总数”工作。需要注意的诚实边界：连通分量闭包在极端情况下（例如全库
  被一个链接类型串成一个大连通分量）可能较大；这是链接基数语义本身决定
  的最小相关集，而不是实现引入的额外扫描。生产中可用链接类型/分区作用域
  进一步收窄。

## 5. 审计日志与重放

`Journal` 记录每一次提交尝试（成功与各类失败），条目 `JournalEntry`
包含：序号、完整批次输入、判定时各相关实例的基线快照 `Base`、失败类别
与明细、钩子执行记录、成功时的新版本/新状态/相关链接集合与 `Tick`。
失败条目 `Tick=0`。可配置 JSONL 落盘（`NewJournal(path)`）。

差分测试会从空库重放整个日志到独立的朴素模型，逐条比对成败，并比较最终
实例与链接指纹（`TestRandomizedDifferential`、
`TestJournalRecordsAllAttemptsAndReplays`）。

## 6. 验证方法（本地）

```bash
export PATH=/usr/local/go/bin:$PATH GOCACHE=/tmp/gocache GOPATH=/tmp/gopath
go test -race -count=3 ./...
go test -cover ./ontology/
go vet ./...
gofmt -l .
```

测试层次：

- 单元：成功路径/版本/时钟；四类失败与优先级；逐项基线；回退后版本、属性、
  时钟不变；基数边界（恰好 2 通过、3 拒绝、删到 0 触发 Min）；删除+断链
  原子提交与重建；重复链接增删。
- 并发可见性：6 个重叠写 + 4 个 `ReadMany` 读者压测，断言单次多读同一
  tick、tick 单调不回退、无半批次可见。
- 交集批次：50 次“共享一个实例、基线相同”的两批次并发，断言恰有一个成功、
  另一个版本冲突且无副作用。
- 差分/线性化：10 个固定随机种子，8 个批次在真实引擎上并发执行；用一个
  独立实现的朴素全局加锁串行模型（`naive_model_test.go`，不共享任何锁/索引
  代码）做全排列搜索，断言成功集合、最终实例状态与链接状态在某种串行顺序
  下完全一致；并用日志从空库重放再核对一次。
- 开销：决策查阅实例数不随库大小增长。

## 7. 被放弃的其他想法

- MVCC/SI：快照隔离天然允许并发读，但对“整批最终基数”需要串行化验证
  （SSI），实现与证据成本远高于当前内存场景，放弃。
- 先写暂存区再 CAS 切换：在钩子执行期间释放锁会产生决策过期，需要重试与
  再验证；在纯内存模型下收益为零，放弃。
- 把失败也推进一个“失败序号”时钟：会违反“回退不得改变任何时钟状态”，
  明确不做。
