# 岗位编制与录用通知管理服务 — 设计说明

## 1. 目标与判定口径

服务围绕一条不变量构建：

> 任意时刻，对任意岗位：`已占用 = 在岗人数 + 未决通知数 ≤ 编制总数`。

- 时间是整数日序号，单调不回退；只有**被接受的操作**（含成功的查询）才推进时钟。
- 未决通知 = 状态 `PENDING`（待答复）或 `ACCEPTED`（已接受待入职）。
- 在岗 = 状态 `ONBOARDED` 且未离职。
- 通知状态机：
  `PENDING → ACCEPTED → ONBOARDED`（办理入职后占用从“未决”转为“在岗”）；
  终结分支：`REJECTED`（拒绝）、`EXPIRED`（答复截止后惰性过期）、
  `WITHDRAWN`（答复前撤回）、`CANCELED`（接受后协商取消）、
  `ABANDONED`（超过入职宽限惰性放弃）。

所有临界判定均为“两端含、恰等允许”：

| 判定 | 允许 | 拒绝 |
| --- | --- | --- |
| 薪资带宽 | `low ≤ salary ≤ high` | 越界且无例外 |
| 答复 | `now ≤ deadline` | `now > deadline` |
| 入职宽限 | `entry ≤ now ≤ entry+grace` | `now > entry+grace` |
| 拒绝/放弃冷却 | `now-blockDay ≥ cooldown` | `now-blockDay < cooldown` |
| 编制下调 | `newTotal ≥ occupied` | `newTotal < occupied` |

季度按 90 日固定划分：`quarter(day) = day / 90`（整除）。day 89 属 Q0、day 90 属 Q1。
例外审批按 `(岗位, 季度)` 登记固定次数，**仅在发放成功时**扣减；
被拒绝的发放（含整批失败）不消耗任何次数。

## 2. 关键取舍

### 2.1 并发等价：粗粒度互斥锁

`Service` 内只有一把 `sync.Mutex`，每个公开方法在整个判定+写入区间持锁。
因此每个操作都是原子的，任意并发交错等价于这些原子操作的某个合法串行顺序，
从结构上排除了“两个发放同时看到还有 1 个编制”的超占用竞态。

**被放弃的方案：细粒度锁 / CAS 计数器。**
编制判定需要同时读取冻结标志、薪资带宽与例外额度、候选人未决索引、
冷却日期、岗位占用并写入新通知，涉及多对象；细粒度锁需要推导加锁顺序，
极易产生死锁或 TOCTOU 漏洞，而本服务没有吞吐基准要求，粗锁更可验证。
`go test -race` 与并发风暴/串行对照测试共同覆盖这一结论。

### 2.2 惰性过期是“被触及”的结算，且随接受/拒绝决定物化与否

通知不在后台到期。当一次操作在时刻 `now` **触及**相关通知时，才进行结算：

- 针对某份通知的操作（答复/入职/撤回/取消/查询该通知）：结算该通知；
- 针对岗位的操作（发放、编制调整、占用查询）：结算该岗位全部当前未决通知；
- 发放校验候选人唯一性时：额外结算该候选人当前未决通知。

题面同时要求“**被拒绝的操作不得改变任何状态、占用与时钟**”，
这与“为判定而做的整岗结算可能释放他人占用”存在表面冲突。
解决方式是**事务化结算**：

1. 操作开始时建立结算事务 `settleTx`，所有计数/索引/状态变更都登记逆操作；
2. 判定在这个“已结算视图”上进行；
3. 操作被接受 → 提交结算并推进时钟；操作被拒绝 → `rollback()`，
   包括他人通知的到期状态变更一并撤销，时钟不推进。

这保证了“过期”的真正含义是：**在一次被接受的操作中第一次被触及**。
朴素参考模型用“深拷贝工作副本、失败丢弃副本”的方式独立实现同一语义，
差分测试逐状态字段比对，从而验证该口径而非验证实现的自我重复。

**被放弃的方案：**
- *后台定时器*：违反“不得依赖后台定时”，且测试难以确定性复现；
- *读时即物化、拒绝也保留*：违反“被拒绝操作零副作用”，
  并且会让一次失败的发放偷偷替别人释放编制，改变后续判定。

### 2.3 发放判定 O(1) 于历史通知总数

发放路径**从不扫描历史通知**，只读取以下以 map/计数器维护的结构：

- `onboardedCnt[pos]`、`pendingCnt[pos]`：占用恒等式两项，`O(1)`；
- `candidatePending[cand]`：候选人唯一未决通知，`O(1)` 判定“是否已有未决”；
- `pendingByPos[pos]`：岗位**当前**未决通知集合，大小 = 未决数 ≤ 编制总数，
  仅在整岗惰性结算时遍历，不随历史增长；
- `lastBlock[cand][pos]`：最近一次拒绝/放弃日，冷却判定 `O(1)`；
- `exceptionByKey[pos/quarter]`：例外剩余额度，`O(1)`。

“已占用”恒等于两个计数器之和，因此编制满判定不依赖任何通知列表。
可验证方式见 `BenchmarkIssueWithHistory`：在制造 1k/10k/50k 份
已终结历史通知后，对同一满编岗位计时发放，ns/op 不随 N 增长。

**被放弃的方案：** 每次发放遍历该岗位全部 offer 重算占用——
实现最简单但复杂度 `O(历史总数)`，正是题面禁止的形态。
该形态保留在朴素模型中，但仅作为测试预言机，不进入生产路径。

### 2.4 错误优先级

错误码按下列固定顺序只报第一个（数值即优先级，1 最高）：

1. `INVALID_PARAM`  2. `CLOCK_ROLLBACK`  3. `NOT_FOUND`
4. `INVALID_STATE`  5. `FROZEN`  6. `HEADCOUNT_FULL`
7. `BAND_EXCEEDED`  8. `PENDING_EXISTS`  9. `COOLDOWN`  10. `EXPIRED`

批量发放先做整批公共检查（参数逐项取下标 → 时钟 → 岗位 → 冻结），
再按岗位满、带宽/例外、未决、冷却的顺序逐项检查；
同类别报下标最小者，失败下标通过 `Error.Index` 返回。
岗位级错误（时钟、岗位不存在、冻结）不属于任何一项，下标为 -1。

### 2.5 冷却口径

只有**拒绝**与**放弃**写冷却日期（`lastBlock`）；
过期、撤回、取消、离职均不触发冷却。
批次内同一候选人重复出现视为“会持有两份未决”，按 `PENDING_EXISTS` 拒绝。

### 2.6 时钟与拒绝操作

`now < 0` 归类为参数非法；否则在已设置时钟且 `now < 上一次接受 now` 时报回退。
被拒绝的操作不推进时钟，因此用相同/更小的 `now` 重试合法。

## 3. 模块布局

| 文件 | 职责 |
| --- | --- |
| `staffing/types.go` | 岗位/通知/例外/快照等数据结构与状态枚举 |
| `staffing/errors.go` | 错误码、优先级数值、`Error{Code,Index}` |
| `staffing/service.go` | `Service` 状态、索引字段、构造与日志钩子 |
| `staffing/internal.go` | 时钟、事务化惰性结算、占用/冷却/索引原语 |
| `staffing/admin.go` | 岗位/候选人/例外登记、冻结、编制调整 |
| `staffing/issue.go` | 单发与批量发放、错误优先级、例外扣减 |
| `staffing/lifecycle.go` | 答复/入职/撤回/取消/离职/查询 |
| `staffing/snapshot.go` | 纯读取快照与 `CheckInvariant` 不变量校验 |
| `staffingtest/` | 独立朴素模型、随机差分、并发等价、重放、基准桥接 |

`Snapshot` 是**纯读取**：不结算、不校验/推进时钟，
因此可以在任何时刻拿到“截至上一次被接受触及”的精确状态，便于断言与对照。

## 4. 本地验证方法

```bash
export PATH=$PATH:/usr/local/go/bin GOCACHE=/tmp/gocache

go test -race -count=1 ./...                      # 全量 + 竞态
go test -v ./staffing                             # 边界用例
go test -v ./staffingtest                         # 朴素模型差分/并发/重放

# 逐步日志（每步输入/输出/判定依据）输出到文件
STAFFING_LOG=$PWD/docs/diff-sample.log \
  go test -run TestNaiveDifferential -count=1 ./staffingtest

# 发放判定不随历史通知总数增长的可验证证据
go test -run=NONE -bench=BenchmarkIssueWithHistory -benchtime=2000x ./staffing

go vet ./... && gofmt -l .
```

差分测试（`TestNaiveDifferential`）运行数百条随机世界、每条上百个操作，
每步同时驱动真实服务与朴素模型，比较返回码、批量下标、分配的通知 ID
以及完整状态（岗位/候选人/通知全部字段/例外余额/占用计数），
并对每步快照执行 `CheckInvariant`。随机源固定，失败可稳定复现。

## 5. 明确的建模选择（可能的争议点）

- 入职早于约定入职日：报 `INVALID_STATE`（状态不允许，而非参数非法——
  参数本身合法，只是当前不能办理）。
- 接受答复时 `entryDate < now`：报 `INVALID_PARAM`。
- 对已过期/已放弃通知做撤回/取消/入职/答复：统一报 `EXPIRED`，
  因为结算发生在状态判定之前（已不属于“未决/已接受”）。
- 已接受通知不可撤回，只能 `Cancel`；取消不写冷却。
- 离职以“当前在岗的候选人”定位；重复离职返回 `INVALID_STATE`，
  在岗计数有非负保护，不可能为负。
- 冻结不影响占用与既有通知的答复/入职；恢复开放后即时可发。
