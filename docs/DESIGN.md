# 跨对象类型权限传播模块 — 设计说明

## 1. 要解决的问题

一个动作在一次事务中同时对多个**对象类型**的实例执行直接操作，并沿**链接类型**
级联影响其它实例。权限检查必须沿这些关联路径传播，并与动作的原子性相容。

模块满足以下硬性约束：

1. 除直接目标外，还要对级联触及的实例做权限检查；级联有有限深度上限，
   可声明沿某些链接类型不传播（`NoPropagate`）；环上每个实例只检查一次。
2. 级联实例对主体不可见时有两种**互斥**模式：整体拒绝（不泄露其存在），
   或跳过该实例及其影响继续执行；未执行部分不改变任何属性/版本/链接。
3. 多层级授权结论由明确的合并规则归约：`MergeAll`（逐层全部放行）或
   `MergeAny`（任一层放行）；结果与层级访问顺序无关。
4. 动作全有或全无：拒绝时实例、链接、审计、时钟均无可观察变化；允许时
   直接操作与被允许的级联影响作为一个不可分割整体生效。
5. 错误按**固定且唯一**的优先顺序汇报。
6. 跳过模式记录被跳过实例及其影响范围，但不泄露其任何属性。
7. 并发动作可串行化；被拒绝动作不影响后续动作。
8. 单次动作的权限检查次数只随该动作声明/实际触及的实例数增长。

## 2. 包结构

- `ontology/`
  - `model.go`：领域类型（对象类型/链接类型/实例/边/动作声明/报告/审计/快照）。
  - `errors.go`：`ErrorKind` 与固定优先级。
  - `authz.go`：`Decider`（可见性 + 分层授权判定）接口。
  - `store.go` / `memstore.go`：存储抽象与内存实现，内置**事务暂存区**。
  - `propagate.go`：有限深度、环去重、`NoPropagate` 的传播与结论合并。
  - `engine.go`：编排（校验→深度→可见性→授权→原子提交→审计→日志）。
  - `validate.go`：动作声明合法性。
  - `jsonlog.go`：JSON Lines 调用日志（输入/输出/传播依据/调用前状态）。
- `ontology/naive/`：**独立维护的朴素参照实现**，刻意不共享生产代码的数据
  结构与算法，仅供差分测试对照。
- `ontology/difftest/`：在大量随机关系图与动作（序列）上逐项对照两者。
- `cmd/server/`：入口占位。

## 3. 关键模型与取舍

### 3.1 层级 = 传播路径上的一个被检查点（重要取舍）

需求描述的"多个层级"存在两种可实现的解读：

- 方案 A（被放弃）：对**每个**被触及实例，在深度 0..d 的每一层都调用一次
  授权器，再跨层合并。问题是：同一个实例被重复评估多轮，检查次数随
  `O(depth²)` 增长，且"对一个深处实例在层级 0 检查什么操作"语义含糊。
- **方案 B（采用）**：传播路径上**每个被触及实例恰好贡献一张票**：
  - 层级 0：直接目标实例，检查其直接操作；
  - 层级 k≥1：经第 k 条链接首次到达的实例，检查在该实例上施加的级联操作。

  所有票（允许/拒绝/弃权）按 `MergePolicy` 归约。该模型下：

  - `MergeAll`：所有**非弃权**票都允许才放行；
  - `MergeAny`：存在一张允许票即放行；
  - 全部弃权：两策略都拒绝（默认安全）。

  归约只依赖票的多重集，因此**天然与访问顺序无关**；每个实例只检查一次，
  检查次数为 `O(实际触及实例数)`。`mergeDecisions` 的纯函数单测
  （`TestMergeOrderIndependence`）直接验证顺序无关性。

### 3.2 环与深度：确定性最短深度 BFS

传播用 BFS，实例**首次到达**即固定其（最短）深度与 BFS 父子关系；之后经更长
路径或环回边再次到达，只合并待施加操作、不重新扩展。因此：

- 环上每实例只被检查/记录一次，遍历必然终止；
- 首次到达深度是"最短传播深度"，与边/规则的书写或枚举顺序无关
  （规则按链接类型排序、邻居按实例 ID 排序，两侧实现都如此）。

环回边回到直接目标时，不把级联操作叠加到根（根只执行其直接操作）。

### 3.3 深度上限是纯图结构事实，且优先于可见性

错误优先级要求"传播深度超限"先于"直接/级联不可见"汇报。但遍历又不能沿
不可见节点扩展（否则会借由它们"看到"更多实例）。为同时满足两点，传播分两步：

1. **深度预扫描**：一次与主体可见性无关的最短深度 BFS（仍尊重 `NoPropagate`），
   只回答"是否存在只能在 `>MaxDepth` 深度首次到达、且经由可传播边的实例"。
   该结果不含任何实例身份信息进入对外错误（错误消息无实例标识）。
2. **可见性敏感的触及遍历**：只沿主体当前可见的实例扩展并施加影响。

`NoPropagate` 规则到达的节点仍被记录并施加其影响，但标记为终点，不再向外
扩展；作为传播终点，它不参与越界判定。

### 3.4 不可见实例的两种互斥模式

- `RejectOnInvisible`：任一被触及实例不可见即整体拒绝（错误优先级第 4 类），
  错误与报告不携带不可见实例的属性。
- `SkipOnInvisible`：不可见实例记入 `Skipped`，动作继续；遍历**不从该实例
  扩展**，于是只有"经过它才能到达"的后继被自然剪除。一个实例若还能经一条
  全可见的独立（更短）路径到达，则它在那条路径上已被访问为可见，不会被误跳。

跳过记录只包含：实例 ID、深度、被抑制的**操作类型**、剪除子树大小。
不包含任何属性值。剪除子树大小由 BFS 父子树精确计数（不同跳过根的子树
互不重叠）。

悬空链接（指向已被先前动作删除的实例）不作为存在实例：不泄露为"不可见"，
不参与授权，视为自然终点。

### 3.5 全有或全无：暂存区 + 单一互斥锁

- `MemStore` 在 `Begin()/commit()/rollback()` 之间维护**变更集**。在提交前
  的任何阶段失败都只是丢弃变更集，基础状态、时钟、审计、链接均不变。
  `commit()` 在引擎持锁期间一次性应用变更并推进时钟，因此外部无法观察到
  "部分类型已更新、部分仍旧"的中间状态。
- `Engine` 用单个 `sync.Mutex` 串行化所有 `Execute`。由此得到可串行化：
  任意并发执行等价于按**锁获取顺序**的某个串行执行；被拒绝动作在该顺序中
  不写入任何状态。这是一种刻意的简单强一致取舍（见"被放弃方案"）。

### 3.6 同一实例多种级联影响的顺序

同一实例可能同时被更新与删除（经不同链接/规则到达）。生效顺序固定为
`read → update → delete`，**删除若存在则最终胜出**，与规则声明或边枚举顺序
无关。生产侧与朴素参照都按此固定顺序执行，保证终态一致。

## 4. 错误的固定优先顺序

`errors.go` 中编号越小越优先，`Engine.Execute` 严格按此顺序短路：

1. `RejectInvalidDeclaration`：声明参数本身不合法（空主体/目标、未知操作、
   负深度、重复直接操作/级联规则、未知模式等）。
2. `RejectDepthExceeded`：存在超过声明上限的可传播可达实例。
3. `RejectDirectInvisible`：主体对直接目标实例不可见（`OpCreate` 目标尚不存在，
   免可见性检查）。
4. `RejectCascadeInvisible`：级联触及实例不可见且模式为整体拒绝。
5. `RejectDenied`：通过合并规则后最终判定拒绝。

被拒绝的动作不触碰暂存区、不推进时钟、不写审计。

## 5. 检查次数的规模无关性（可观测证明）

`Engine` 通过 `countedDecider` 装饰 `Decider`，在**接口边界**统计
可见性检查与授权检查次数，并把总和写入 `Report.Checks`。这是不依赖内部
实现细节的可观测计数（从调用方看得到）。

在单层票模型下，每个被实际触及的实例：1 次可见性 + 1 次授权，
检查次数 = `Θ(直接目标数 + 级联触及数)`，与系统中对象类型/链接类型/实例的
**总规模**无关。测试：

- `TestCheckCountIndependentOfTotalScale`：保持动作声明与触及集合不变，
  把系统总实例/边从 0 增到 10000，断言 `Checks` 完全不变。
- `TestCheckCountScalesOnlyWithTouchedSet`：改变 `MaxDepth` 从而改变实际
  触及集合，断言 `Checks = 2 × 触及实例数`，随触及集合线性增长。

## 6. 日志与审计

- `JSONLogger`（`jsonlog.go`）对每次调用写一行 JSON，含：输入动作、
  是否提交、失败原因、检查次数、完整传播路径裁决依据（每实例的深度/经由
  链接类型/票）、跳过记录、以及调用前世界快照。由 `TestJSONLogger...` 验证。
- 审计只在**提交**时追加一条 `AuditRecord`（序号=提交后时钟），记录直接操作、
  实际生效的级联影响、跳过实例与检查次数。跳过记录只含"存在且不可见"级别的信息。

## 7. 被放弃的方案

- **每实例跨 0..d 多层重复授权**：见 3.1，检查次数平方增长且语义含糊，放弃。
- **规则级各自的深度上限**：曾为每条 `CascadeRule` 设独立 `MaxDepth`。
  当同一节点可经多条不同规则、在不同深度到达时，"以哪条路径的深度为准"会
  产生与遍历顺序相关的歧义；需求只要求"有限的传播深度上限"。故收敛为
  **动作级单一 `MaxDepth`** + 每规则 `NoPropagate` 开关，语义无歧义。
- **基于 MVCC/2PL 的多版本并发**：能提高并发度，但显著增加复杂度且非需求
  必需。当前以单锁串行化换取简单、可证明的可串行化；存储接口已抽象，
  后续可在不改裁决逻辑的前提下替换为多版本存储。
- **提交前就地修改 + 失败时补偿回滚**：补偿动作难以覆盖所有副作用且易泄漏
  中间态。改用变更集暂存，提交才生效，拒绝天然零副作用。

## 8. 本地验证方法

```bash
# 环境：Go 1.26+（go version）
go test ./...                       # 全量测试（含随机差分）
go test -race -v ./...              # 竞态 + 详细
go test -coverprofile=cov ./... && go tool cover -func=cov
go vet ./...
gofmt -l .                          # 无输出即格式干净
```

差分测试规模可在 `ontology/difftest/diff_test.go` 调整
（`iterations`、`sequences`、`seqLen`）。随机用例使用固定种子，失败时输出
完整动作声明与图/授权矩阵（`Env.Dump()`），可稳定复现。
