# 实例并发控制设计说明：乐观更新 + 动作独占占用

本文档说明 `ontology` 包如何在同一对象实例上同时提供两种并存的并发控制，
并逐条对应需求中的正确性条件、关键取舍、被放弃的方案与本地验证方法。

## 1. 模型与术语

- 实例（`rec`）：含 `version`（单调版本号，初始 1）、生命周期状态 `state`、
  属性 `props`、链接 `links`。
- 普通更新：`Store.Update` / `Store.Link`，纯乐观，调用方提交自己读取时的
  `baseVersion`。
- 动作（Action）：`Store.TryAcquire` 申请一个或多个实例的**独占占用权**，
  成功后拿到 `Lease`；动作在占用期内通过 `Stage` 暂存状态机转换，最终
  `Commit`（原子发布 + 释放）或 `Release`（放弃 + 释放），并可用
  `Heartbeat` 续约。

## 2. 核心机制

### 2.1 单一临界区 + 每实例占用槽

整个 `Store` 用一把 `sync.Mutex` 串行化**所有判定与状态发布**。每个实例
记录上有一个占用槽（`holder` + `expiresAt` + 单调 `token`）。

- 判定只发生在持锁临界区内，因此每次外部调用在日志序号（`Decision.Seq`）
  上有唯一的线性化点。
- 外部读取（`Snapshot`）在同一把锁内拷贝完整状态。动作的暂存修改保存在
  `Lease.staged`，占用期间对存储中的已发布数据零改动；`Commit` 在同一个
  临界区内同时完成「发布全部属性/状态变更、版本 +1、清空占用槽」。
  因此任何读取要么看到占用开始前的完整状态，要么看到占用结束后的完整状态，
  不可能读到中间属性组合。

### 2.2 占用申请：立即拒绝、不阻塞、不排队、不部分持有

`TryAcquire(actionID, keys, ttl)` 的判定全部在一次加锁内完成：

1. 键集合规范化：去重并按字典序（**全局规范序**）排序。
2. 第一遍检查存在性并惰性裁定过期占用。
3. 第二遍按规范序检查占用槽：**任一**键被其他存活占用持有，立即整体拒绝，
   不写入任何占用槽——申请方不可能「拿到一半」。

拒绝结果两类、可单独识别：

- 单键申请冲突 → `OutcomeOccupied`（“实例已被占用”）。
- 多键（跨链接）申请冲突 → `OutcomeLockConflict`（跨实例占用冲突）。

判定从不阻塞、从不自动排队重试；是否重试完全由调用方决定，且每次重试都是
一次带新判定结果的新申请。

### 2.3 跨实例死锁预防：规范序 + 原子全有或全无

需求场景：两个动作各自需要一组通过链接关联的实例，且以不同顺序申请。

采用的确定性规则：**所有申请都把键规范化为同一全局序，并且在单一临界区内
原子地「全拿到或全不拿到」**。因为系统内不存在「持有 A 等 B」的中间状态
（多键授予不可分割），等待环在结构上不可能形成。

当两方确实竞争同一组实例时，结果完全确定、可预先推导：

- 临界区给出的判定顺序即日志 `Seq` 顺序；先被判定的申请获得占用，
  后被判定的申请必然得到 `OutcomeLockConflict`（拒绝决策里带有
  `ConflictKey` 与当前 `Holder` 作为证据）。
- 因为不存在「各持一部分」，冲突中至少一方必然被拒绝，不可能两方都停住。

注意：可推导的是**裁决规则**（按规范序原子申请，冲突时后到者让先持有者），
不承诺某个特定 goroutine 一定先到；真实到达顺序由日志 `Seq` 记录，
任意给定交错下谁被拒绝是唯一确定的，且重放日志必然复现同一结果。

### 2.4 普通更新的判定顺序

`Update`/`Link` 在同一临界区内按固定顺序给出四类互斥结果：

1. `OutcomeOptimisticRejected`：目标实例当前被存活占用持有（含冲突键、
   持有者）。**占用判定先于版本判定**——即使 `baseVersion` 错误，占用期间
   也先返回占用拒绝。
2. `OutcomeVersionStale`：未被占用但版本号不等于当前版本。
3. `OutcomeCardinality`（仅 `Link`）：链接基数超限。
4. `OutcomeCommitted`：通过，写入并 `version++`。

占用拒绝与基数/版本拒绝都不改变版本号。占用释放后，调用方必须以释放时刻
的最新版本重新读取再提交；沿用旧版本只会得到 `OutcomeVersionStale`——
不存在「沿用占用前旧版本却成功」的路径。

### 2.5 动作中止与租约：唯一失效裁定依据

持有方可能崩溃 / goroutine 中止而未显式释放。规则：

- 每次授予都记录 `expiresAt = 唯一时钟.Now() + ttl`，并附单调围栏 `token`。
- “占用是否仍然有效”的**唯一**裁定依据是：系统唯一 `Clock` 的当前读数是否
  已达到 `expiresAt`。在到期之前，即使怀疑持有方已中止，也绝不提前转交
  （`TestLeaseExpiryAndFencing` 验证 TTL 边界前仍为 `Occupied`）。
- 到期判定是**惰性**的：在下一次触碰该实例（任何申请/更新/读取）时，于
  临界区内清槽并追加一条 `lease_expired` 决策。之后新申请方可获得占用。
  因此占用不会因持有方中止而永久悬挂，也不会在能确定中止之前被释放。
- 存活的持有方用 `Heartbeat` 续约。旧持有方“晚到”的 `Commit/Release`
  通过 `持有者 + expiresAt + token` 三重校验被拒绝（`OutcomeInvalidLease`），
  不可能误伤新持有方——即经典 fencing token 防护。

时钟被抽象为 `Clock` 接口（生产用 `WallClock`，测试/重放用 `FakeClock`），
使失效裁定完全确定、可重放，不依赖真实睡眠。

### 2.6 可观察、可重放的判定日志

每次申请、更新、链接、心跳、提交、释放、惰性过期都产生一条 `Decision`：

- 字段：`Seq`（全局判定序号）、`At`（裁定时钟读数）、`Kind`、`Caller`、
  `Keys`（规范化后）、`BaseVer`、`TTL`、`Token`、暂存 `State/Patch/Links`、
  `Outcome`、`Reason`、`Holder`、`ConflictKey`、`NewVersion`。
- 输入、判定依据（当前版本/持有者/到期时刻）与结果齐全，单独依据日志即可
  重放整条历史（测试中的朴素模型正是只消费日志完成独立裁决）。

### 2.7 O(1) 判定开销与可验证证据

判定只访问：目标键的 map 槽（O(1) 平均）+ 申请键数（动作自身的规模，
与系统规模无关），不扫描实例表、不扫描占用表。`BenchmarkAcquireVsScale`
与 `BenchmarkUpdateVsScale` 在 100 / 10,000 / 100,000 个实例（且并存上万条
占用记录）下对比每次判定耗时，结果不随规模增长，即为不依赖额外对外状态的
可验证证据（代码 + 基准输出本身即可复现）。

## 3. 串行化等价性

所有可线性化点都在同一把锁上，按 `Decision.Seq` 排列即构成一个合法的全局
串行顺序：

- 占用申请/提交/释放在该顺序中各占一个点；占用的生命周期是
  `[acquire.committed, commit/release.committed]` 的闭区间。
- 成功的普通更新其线性化点必落在所有占用区间之外：区间内的更新一律得到
  `OutcomeOptimisticRejected`（`assertNoUpdateInsideOccupancy` 直接扫描日志
  验证不存在区间内成功更新）。
- 因而该串行顺序中占用期间不插入任何普通更新，最终版本与属性等价于按此
  顺序逐个串行执行所有操作的结果。

## 4. 关键取舍

- **单把全局互斥锁**：换取最强、最易论证的原子性与“零中间态”可见性，
  判定本身为 O(1) map 访问；临界区内不做 I/O、不回调用户代码，持锁时间极短。
  放弃了更高吞吐的分片锁 / MVCC（见 §5）。
- **全有或全无的多键授予（无序等待图）**：彻底消除循环等待，代价是竞争激烈
  时多键动作成功率下降，需要调用方重试（重试是显式的、可观测的新决策）。
- **租约 + 惰性过期**：不依赖后台扫描线程即可保证不悬挂、不误放；代价是一个
  已死占用在 TTL 内仍会拒绝他人，TTL 需按动作心跳能力设定。
- **暂存于 Lease、提交时整体发布**：天然保证原子可见性，代价是暂存内容不被
  其他读取看到（这正是需求要求）。
- **拒绝而非抢占**：后到者让先持有者，不抢占运行中的动作，保证动作一旦获得
  占用即可运行至自身终态（除非自身租约失效）。
- **结果码四（七）类互斥**：把“单键占用拒绝”和“跨实例冲突拒绝”拆成不同码，
  满足调用方单独识别与统计的需要。

## 5. 被考虑但放弃的方案

- **阻塞等待 + 条件变量 / 等待队列**：需求明确禁止排队与阻塞，且队列会制造
  饥饿与唤醒公平性问题；改为立即拒绝 + 调用方显式重试。
- **两阶段加锁（先逐键申请、冲突回滚）**：会出现“各持一部分再互等”的窗口，
  必须额外引入死锁检测/规避；规范序 + 单临界区原子授予直接消除该窗口。
- **Wait-die / wound-wait 等基于事务年龄的图式方案**：仍需逐键持有与等待，
  实现与证明更复杂；本方案的等待图恒为空，无需维护图或全局事务年龄。
- **分片锁 / 每实例锁**：可提高并发度，但多键原子申请需要确定性锁序且易在
  实现中引入顺序缺陷，读端为保证“无中间态”还需额外的版本快照机制；当前规模
  与持锁时长下单锁更简单可证。若未来成为吞吐瓶颈，可在不改变对外语义与
  结果码的前提下内部分片（仍按规范序加锁）。
- **MVCC（多版本 + 提交时校验写集）**：对跨实例“占用期间一切普通更新必须
  拒绝”这类悲观互斥语义并不直接匹配，且会暴露中间多版本；不采用。
- **后台 reaper 线程主动回收过期租约**：引入额外线程与唤醒时序不确定性；
  惰性过期在唯一裁定依据下行为等价且更易重放。

## 6. 本地验证方法

```bash
# 全量测试（含竞态检测）
go test -race ./...

# 随机交错序列对照朴素全局串行模型（40 个种子，多 goroutine）
go test -race -run TestRandomizedAgainstNaiveSerial -v ./ontology/

# O(1) 判定开销证据：对比 100 / 10000 / 100000 规模下单次判定耗时
go test -bench . -benchmem -run '^$' ./ontology/

go vet ./...
gofmt -l .
```

覆盖的边界场景：

- 占用期间并发普通更新全部得到 `OutcomeOptimisticRejected` 且版本不变。
- 多实例跨链接申请的各种给出顺序（正序/逆序/乱序、两两重叠）。
- 占用刚释放瞬间 64 个更新竞争：恰有 1 个按当时最新版本成功，其余版本落后。
- 租约 TTL 边界（到期前不误放、到期后可重新获得）、僵尸释放的 fencing 防护、
  心跳续约。
- 四类拒绝结果互斥可辨，且占用判定先于版本判定。
- 随机操作序列：逐条决策与独立朴素全局串行模型对照，最终版本/属性一致，
  并验证无成功更新落入占用区间。

每次尝试的输入、判定依据与结果都在 `Store.Log()` 中，可导出 JSON 重放核验。
