# 住院护理给药时间表系统 — 设计说明

## 1. 模块划分（职责单一、相互协作）

代码位于 `medschedule/`，纯数学与状态机分离：

| 文件 | 职责 |
| --- | --- |
| `types.go` | `Status`、`Point`、`PRNDose` 等共享类型 |
| `errors.go` | 九类错误码与优先级 |
| `schedule.go` | **纯函数**计划点数学：固定间隔等差列、固定时点日列、分段、二分定位 |
| `system.go` | 系统时钟、药品目录、过敏登记、患者+药品最近给药表、并发锁 |
| `orders.go` | 医嘱开立校验、停嘱、原子改嘱 |
| `admin.go` | 按时给药、拒服、漏给补给、PRN 给药（含全部判定） |
| `query.go` | 区间计划点与 PRN 记录查询 |
| `naive.go` / `naive_ops.go` | **独立朴素参考模型**：物化全部点逐点重放，仅供差分测试 |

生产路径从不引用朴素模型；朴素模型也不复用生产实现的判定代码，
只共用无状态的数学工具（日起点、区间生成）。两套实现因此能真正互相证伪。

## 2. 关键不变量与取舍

### 2.1 时钟与“拒绝无副作用”

- 全系统单调时钟存于 `System.now`；每个操作**先**完成参数校验、时钟校验与全部业务校验，
  全部通过、准备提交时才调用 `commitClock(now)` 推进时钟并落状态。
- 因此被拒绝的操作既不改状态，也不推进时钟。改嘱的两步（停旧、开新）在同一个临界区内，
  任一步失败则都不落库（`ReplaceOrder`）。
- 所有方法进入后先取同一把 `sync.RWMutex`（查询用读锁，变更用写锁），
  任意并发交错都等价于某个串行顺序；`go test -race` 验证无数据竞争。

### 2.2 计划点不物化（性能核心）

固定间隔与固定时点医嘱都不存历史点，只保存“可数学生成当前序列”的最小信息：

- 固定间隔：保存**分段** `segs []intervalSeg{start, cut, madeUpAt}`。
  - 初始一段从首次时刻起按 `H` 无限延伸；
  - 补给成功时把当前最后一段在 `cut = now+H` 处截断，另起一段从 `now+H` 开始。
  - 查询时用二分找到最后一个 `start <= lo` 的段，只生成与区间相交的段与点，
    与历史走过多少点无关。
- 固定时点：仅保存升序的日内时点集合；任意区间的点由“日起点 + 时点”直接枚举，
  日数只与区间宽度有关。

被处理的点落在 `records map[计划时刻]Status`，数量等于真实处理次数，与历史长度无关；
`lastAdmin` 只存每个“患者+药品”最近一次实际给药时刻（O(1) 做跨医嘱安全间隔判定）。

### 2.3 状态的即时判定（漏给不需要任何触发）

未记录的点在查询/登记时按调用时刻 `now` 即时计算：

- 活跃医嘱：`p + W < now`（严格）→ 漏给；否则待给。
- 已停嘱（停嘱时刻 `s`）：只按停嘱分界，与查询时刻无关——`p + W < s` → 保持漏给，
  否则作废；已有记录（给药/补给/拒服）原样保留。

### 2.4 按时窗口与登记

- 窗口为闭区间 `[p-W, p+W]`，两端恰取等都合法。
- 登记给药/拒服时，取窗口含 `now` 且未处理的点；窗口不重叠由开立约束 `间隔 > 2W` 保证。
- 实际给药（不含拒服）还要满足“同一患者同一药品”最近实际给药间隔 ≥ 药品最小安全间隔，
  跨所有医嘱、含已停嘱医嘱与 PRN；恰等于允许。

### 2.5 补给与固定间隔重排

- 可补给目标唯一：当前序列中已漏给、未处理，且其**下一个计划点窗口尚未开始**
  （`now < next-W`，恰等于窗口起点即拒绝，此时按错误优先级报“无对应计划点”）。
- 补给也要过同药品安全间隔。
- 固定时点补给后序列不变。
- 固定间隔补给成功后：
  - 旧网格中**补给点之后、新段起点之前**的点作为作废尾巴保留（可被查询到，便于审计）；
  - 新段起点及以后的时间区域由从 `now+H` 起的新网格接管，旧网格点不再单独落库。
  - 这保证查询输出无重复点，且旧段作废尾巴长度严格小于一个 `H`，不随历史增长。

### 2.6 PRN（必要时）

PRN 医嘱没有计划点。每次请求依次判定：
同医嘱距上次实际给药 ≥ PRN 最小间隔（恰等允许）→ 同患者同药品安全间隔
→ 滚动窗口 `(now-86400, now]`（开区间，恰在 `now-86400` 的剂量不计入）内次数 `< 上限`。
错误分别报间隔不足 / 次数超限。

### 2.7 错误优先级

严格按题目顺序，只报第一个：
参数非法 → 时钟回退 → 对象不存在 → 状态不符 → 过敏冲突 →
无对应计划点 → 间隔不足 → 次数超限 → 补给不允许。
实现上每个方法按该顺序提前返回；`Error.Code` 可程序化区分。

## 3. 被放弃 / 考虑过但未采用的方案

1. **物化所有计划点并后台扫描漏给**：实现最直观，但查询与触发会随历史点数线性增长，
   直接违反“开销不得随历史计划点总数增长”。保留为 `NaiveModel` 仅用于差分对照。
2. **给每个点建一个定时任务/时间轮**：引入真实时间与并发复杂度，且漏给要求
   “随时间自然体现、不依赖调用触发”，纯函数即时判定更简单且可重放。
3. **补给后把旧网格全部标记作废**：会产生无限多点无法表示；也会在新旧网格重叠处产生重复。
   最终采用“分段 + 短作废尾巴 + 新段接管”的表示。
4. **用数据库事务做原子改嘱**：单进程内存模型下用一把锁即可提供可串行化与原子性，
   无需外部依赖；若未来持久化，同样的“全部校验后提交”顺序可直接映射到事务。
5. **按操作类型分多把锁提高并发**：跨医嘱的安全间隔共享 `lastAdmin`，细粒度锁收益小、
   易出错；当前读写锁已满足“等价于某串行顺序”。

## 4. 性能论证（可验证）

- 复杂度：区间查询为 `O(k + log S)`，其中 `k` 是区间内（固定时点另加当前窗口附近）的点数，
  `S` 是补给分段数；登记类操作只做常数个近窗点计算。二者均与“医嘱已走过的历史点总数”无关。
- 实证：`TestCostIndependentOfHistory` 对同一固定间隔医嘱构造
  很短（约 1 千点）与很长（1 千万点）两档，查询同一个 1000 秒宽区间：
  - 高效实现两档单次查询耗时基本相同（实测约 0.99×，~4.9μs）；
  - 朴素模型长档约为短档的 ~1500×（与点数增长同阶）。
  - 另可用 `go test -bench . -benchmem` 复现四个 Benchmark。

## 5. 本地验证方法

需要 Go 1.26+（仓库 `go.mod` 已声明）。

```bash
# 本环境 Go 在 /usr/local/go/bin；若 go 不在 PATH：
export PATH=$PATH:/usr/local/go/bin
export GOCACHE=/tmp/gocache          # 仅当家目录缓存不可写时

go test ./...                         # 全量（含 1500 组差分与性能断言）
go test -race ./...                   # 并发无竞争
go test -v ./medschedule              # 查看边界用例与性能日志
go test -bench . -benchmem ./medschedule
go vet ./... && gofmt -l .
```

- 随机差分的**逐步输入 / 两实现输出 / 判定依据**写入 `medschedule/diff_trace.log`
  （可用环境变量 `MEDSCHED_DIFF_LOG=/tmp/x.log` 改路径）。
- 边界取等用例集中在 `boundary_test.go`；差分生成器在 `diff_gen_test.go`。
