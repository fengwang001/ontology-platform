# 事件溯源对象状态重建子系统 —— 设计说明

## 1. 问题与范围

本体平台中，对象类型形成单继承层级：子类型继承父类型的属性定义，
并可以**收窄覆盖**部分属性的取值范围，或声明父链中不存在的新属性。
对象实例的全部历史以追加式事件记录（实例创建、属性赋值、类型演变），
子系统负责：

- 按事件逻辑顺序重建实例在任意历史截止时刻的状态；
- 在类型演变点正确切换属性继承/覆盖的适用规则；
- 用事件发生时刻生效的**规则版本**解释该事件；
- 区分四类重建错误并按固定优先级报告；
- 保证并发追加/重建的可线性化；
- 保证重建开销不随累计类型演变次数线性增长。

## 2. 核心语义决策

### 2.1 双重时钟

- `Seq`：事件存储在追加时分配的序号，是同一实例内事件的**权威顺序**
  （线性化由存储层的互斥锁保证，见 §4）。
- `Time`：客户端提供的逻辑时刻，同一实例内必须**严格递增**，用于
  截止时刻过滤与规则版本选择。并列（相等）或倒退的时刻意味着记录
  顺序与逻辑时刻相互矛盾、无法确定先后，重建时报 `ErrAmbiguousOrder`。

重建结果只依赖事件记录本身（`Seq` + `Time` + 负载），与事件到达的
物理顺序无关：物理顺序在追加时已被锁串行化为 `Seq`，此后不再参与解释。

### 2.2 类型演变的“即时重校验”

每个属性赋值事件在**其发生时刻**按当时生效的类型定义与规则版本解释
（追加时严格校验，越界拒绝；重建导入流时越界赋值按未发生处理）。
演变之前的赋值不会被之后的类型定义“重新解释”。

当类型演变事件（目标类型 `T'`，时刻 `t`）被应用时，执行一次状态迁移：
当前持有的全部属性取值按 `T'` 在 `t` 时刻生效规则版本下的有效定义
重新校验，**不再合规的取值被丢弃**（回到未设置状态）。这覆盖两种情形：

- 取值越出 `T'` 下收窄后的范围（如子类型 `[4,4]` 下持有的 `8`）；
- 属性在 `T'` 下根本不存在（子类型新增属性随退回父类型而失去意义）。

该处理是确定性的：它只取决于事件流内容与规则版本，不依赖事件到达顺序。

### 2.3 规则版本化

- 规则版本按 `ValidFrom` 严格递增追加，追加后不可变；
- 时刻 `t` 生效的版本 = 最后一个满足 `ValidFrom <= t` 的版本
  （**左闭区间**：`t == ValidFrom` 归属新版本）；
- 由于新版本只允许以更大的 `ValidFrom` 追加，任何历史时刻的版本归属
  一经确定永不改变（`TestVersionAssignmentImmutable` 验证）；
- 截止时刻同样是闭区间上界：`cutoff == 首事件时刻` 可以重建。

### 2.4 错误分类与优先级

| 优先级 | 错误 | 触发条件 |
|---|---|---|
| 1 | `ErrAmbiguousOrder` | 截止前缀内存在时刻并列/倒退的并列记录 |
| 2 | `ErrCutoffBeforeFirstEvent` | 截止时刻早于实例首个事件 |
| 3 | `ErrUndefinedTargetType` | 演变（或创建）目标类型在事件时刻的版本中未定义 |
| 4 | `ErrInvalidEvolutionPath` | 源/目标类型不在同一条继承链上 |

同一次重建中多个条件同时成立时只报告优先级最高者
（`TestRebuildErrorPriority` 验证）。优先级 1、2 在重放前检查；
3 先于 4 是因为目标类型未定义时无法讨论路径合法性。
并列记录位于截止时刻之后时不影响本次重建（只检查截止前缀）。

所有重建路径均为**只读**：失败不写入任何补偿/修正事件；
追加校验在克隆状态上试算，失败追加同样无可观察改动。

## 3. 重建成本：快照索引

事件存储为每个实例维护快照索引：

- 每次**类型演变事件**应用后落一次快照；
- 每 `SnapshotInterval`（64）个事件强制落一次快照。

重建时二分定位截止前缀，再命中最近的快照，只重放快照之后的后缀。
由于任意两次快照之间至多 64 个事件，单次重建的逐事件重放开销为
**常数上界**，与该实例累计的演变总次数无关。

**独立验证方式**：每次重建返回 `RebuildStats{EventsTotal, EventsReplayed,
SnapshotUsed, ...}`，`TestRebuildCostIndependentOfEvolutionCount` 将演变
次数从 100 放大到 10,000（事件总量 204 → 20,004），断言 `EventsReplayed`
恒为 3（≤ 64）；`BenchmarkRebuildCurrent` 可用
`go test -bench=BenchmarkRebuild -benchmem .` 复核墙钟时间。

## 4. 并发模型

`Store` 用一把 `sync.RWMutex` 串行化全部操作：追加在写锁内完成校验、
赋序号、落盘、更新当前状态与快照；重建在读锁内完成检查与重放。
每个操作的线性化点位于其临界区内，因此任意并发调用都等价于某个全局
串行顺序。`TestConcurrentAppendRebuildLinearizable` 在 `-race` 下验证：
并发重建观察到的每个状态都等于最终事件流某个前缀的朴素重放。

## 5. 被放弃的方案

- **读时懒过滤（保留失效取值，查询时再过滤）**：与即时重校验在
  “子→父→子”往返场景下结果不同——懒过滤会让旧值在回到子类型时
  “复活”，语义上把解释权交给了查询时刻，违背“取值按记录时的定义
  解释”的原则，且无法给出稳定的历史状态。放弃。
- **演变时保留越界取值并打标记**：状态需要额外携带“失效但保留”的
  取值集合，所有读路径都要理解标记，复杂度高于收益。放弃。
- **无锁/MVCC 事件存储**：单实例事件流是天然串行资源，读写锁已足够；
  无锁结构只会增加正确性风险。若未来需要水平扩展，可按实例分片加锁，
  语义不变。放弃。
- **用当前最新规则版本重放全部历史**：实现最简单，但直接违背
  “历史事件按当时版本解释”的要求。放弃。
- **允许任意改写历史规则版本**：会破坏历史重建的可重现性；
  改为只允许单调追加版本。放弃。

## 6. 测试与本地验证

```bash
go test ./...            # 全量测试
go test -race ./...      # 竞态检测（并发线性化用例）
go test -bench=BenchmarkRebuild -benchmem .   # 重建成本基准
ONTOLOGY_AUDIT_DIR=/tmp/audit go test -run 'TestExhaustive|TestRandom' -v .
```

覆盖要点：

- `replay_test.go`：演变即时重校验、四类错误与优先级、截止边界、
  只读保证、判定记录；
- `version_test.go`：规则版本跨越事件流、切换点左闭归属、
  版本归属不可变、目标类型“当时未定义”；
- `differential_test.go`：三级链上长度 ≤5 的全部演变序列穷举
  （363 例 × 每个前缀截止时刻）、2000 步随机操作序列下优化路径与
  独立朴素模型（`naive.go`）逐条对照；每次判定的输入、所依据的规则
  版本与对照结论写入 JSONL 审计日志（目录由 `ONTOLOGY_AUDIT_DIR`
  指定，缺省为测试临时目录，路径见测试日志）；
- `concurrency_test.go`：并发追加/重建的可线性化与确定性（`-race`）；
- `cost_test.go`：基于 `RebuildStats` 的重建成本常数上界证明。

## 7. 已知边界

- 快照保存在内存中，重启后需从事件流重建索引（事件流本身是持久事实）；
- 快照空间开销为 O(演变次数 + 事件数/64)，以空间换时间；
- 逻辑时刻暂由客户端保证唯一性来源（生产环境应替换为混合逻辑时钟）；
- 继承限定为单继承链，多继承需要重新定义“最近声明”的消解规则。
