# 快照导出协同组件设计说明

本体平台需要在持续有新写入到达的情况下，导出一份全量快照以及紧随其后的
增量记录流，使下游消费方能够将两者无缝拼接，还原任意时点上系统完整且
自洽的状态。本文档说明组件的划分、关键取舍、被放弃的方案与本地验证方法。

实现位于 `snapshot/` 包。

## 核心模型：以 LSN 为唯一事实来源

所有写入（对象类型实例、链接实例、动作执行记录）首先进入**接受日志**
（`Journal`）。写入被"接受"的唯一含义是：在日志互斥锁下获得一个全局唯一、
单调递增的逻辑序号 **LSN** 并追加到日志末尾。由此得到三个推论：

- **接受顺序** = LSN 的全序，与墙上时钟无关；
- **快照边界** = 一个具体的 LSN `N`，一旦确定不随后续写入变化；
- **增量归属** = 纯函数 `classify(lsn, N)`，与判定发生的实际时刻无关。

快照内容直接由日志前缀 `[1, N]` 重放物化得到，不经过任何可能滞后的中间
介质，因此"边界之前已接受但尚未落入快照介质的写入"在定义上不可能被遗漏；
边界之后的写入不在前缀内，在定义上不可能被包含。

### 重合情形的固定规则（R1）

边界 `N` 是**含端点**的：`LSN <= N` 归快照侧，`LSN > N` 归增量侧。一笔写入
的接受时刻与边界"恰好重合"即 `LSN == N`，恒判给快照侧。规则唯一、固定、
可复现，不依赖判定时刻、重试次数或并发交错。

## 组件划分

| 组件 | 文件 | 职责 |
| --- | --- | --- |
| `Journal` | `snapshot/journal.go` | 写入接受、LSN 分配、并发线性化支点 |
| `BoundaryDeterminer` | `snapshot/boundary.go` | 边界位点的确定与合法性校验 |
| `Classifier` | `snapshot/classify.go` | 增量归属判定（O(1)，带操作计数器） |
| `Checker` | `snapshot/checker.go` | 原子性与引用完整性的跨写入核对 |
| `Coordinator` / `Session` | `snapshot/exporter.go` | 编排：边界 → 快照 → 增量流，错误优先级执行 |

## 原子性：增量记录 = 一笔完整事务

下游可以用快照拼接**任意前缀**的增量流，因此增量流的每一个切割点都必须
是事务安全的。唯一对任意前缀都成立的切分方式是：**一条增量记录恰好承载
一笔完整事务**（一次动作执行的全部对象/链接修改与动作执行记录本身）。

`Journal.AppendTransaction` 把一笔事务的写入作为连续区间追加；但日志也
接受逐条写入（`AppendRaw`），因此同一事务的写入可能被其他事务隔开。
`Checker` 按日志顺序核对（规则 R4）：同一事务号只能在一个连续区间出现，
再次出现即报**原子性冲突**并拒绝本次导出中尚未输出的部分——已输出的
快照与增量保持有效，冲突写入不会被静默跳过。

## 引用完整性：按可见性顺序核对

`Checker` 维护"当前可见对象"集合：快照核对通过后初始化为快照中的对象，
随后每条增量记录核对（规则 R5）：记录新增链接的两端对象必须已可见，或在
同一事务内新建（同事务内对象与链接的先后顺序不限，因为它们同时可见）。
链接先于端点对象可见（包括"链接在快照内、端点对象在增量中"的情形）即报
**引用完整性冲突**。

## 边界位点的确定

- **自动模式**（`Auto()`）：取不超过当前日志尖端的最大**事务安全**位置
  `N`——不存在既有 `LSN<=N` 又有 `LSN>N` 的写入的事务。尖端恰好在事务
  中间时回退到最近的安全点。
- **显式模式**（`At(n)`）：调用方指定位置。位置超出日志尖端（规则 R2，
  位置尚不存在）或切分事务（规则 R3）时，报**边界定义冲突**。

边界冲突在 `BeginExport` 时、任何输出产生之前判定。

## 错误分类与固定优先级

四类错误，优先级固定（数值越小越优先）：

1. **边界定义冲突**（`ErrBoundaryConflict`）：边界未定义时，归属判定与
   完整性核对都失去参照系，必须最先判定；
2. **原子性冲突**（`ErrAtomicityConflict`）：可见性的最小单元是事务，
   单元本身无法界定（写入被隔开）时，引用完整性核对没有意义；
3. **引用完整性冲突**（`ErrReferentialConflict`）：依赖前两层成立后才能
   判定；
4. **资源不足**（`ErrResourceExhausted`）：环境性、瞬态的失败，不能掩盖
   确定性的逻辑错误，否则同一输入在不同负载下会报告不同错误，破坏可复现性。

执行方式：边界冲突在会话开始前判定；每个输出决策点上按 R4 → R5 → R6 的
顺序检查；时间上先到达的决策点先报告（不做无界的前瞻扫描）。会话一旦报错
即终止，后续调用返回同一错误，已输出部分不撤销。

## 并发等价性

`Journal` 的所有公开操作在同一把互斥锁下完成：每条写入的接受、每次边界
读取、每段日志读取都是原子的。因此多路写入与多路快照读取的任意并发交错，
都等价于按锁的获得顺序串行处理这些请求——这就是可串行化见证。
会话（`Session`）本身由单消费者使用，会话间不共享可变状态。

## O(1) 归属判定及其复核方式

`Classifier.Classify` 只做一次整数比较（`lsn <= boundary`），不访问任何
随数据规模增长的结构。提供两种可复核的证明手段：

1. **操作计数器**：`Classifier` 接受可选的 `OpCounter`，每次判定恰好累加
   一次比较。`TestClassificationConstantWork` 在 10 / 1,000 / 100,000 条
   写入的日志上断言：比较次数恒等于被判定记录数（每条恰好 1 次），与总
   规模无关。
2. **基准测试**：`BenchmarkClassify` 在 1,000 与 1,000,000 规模下测量单次
   判定耗时（实测均约 0.29 ns/op、0 分配），任何人可用
   `go test -bench=Classify -benchmem ./snapshot` 复测。

## 被放弃的方案

- **墙上时钟作为边界**：时钟有分辨率与回拨问题，"重合"无法唯一定义，
  判定结果依赖判定时刻，不满足可复现性。放弃，改用 LSN。
- **从物化存储直接读快照**：物化存储可能滞后于接受日志，会遗漏"已接受
  但尚未落盘"的写入。放弃，快照一律由接受日志前缀重放。
- **逐条写入作为增量记录**：任意前缀拼接会把一笔事务切开，无法满足
  原子性。放弃，改为一条增量记录承载一笔完整事务。
- **无锁/细粒度并发**：读写在 LSN 分配上存在天然的全序点，无锁化只能
  换来复杂度。当前以单互斥锁保证线性化，吞吐足够；若未来成为瓶颈，
  可在保持 LSN 全序的前提下做分段锁，语义不变。
- **发现冲突时跳过冲突写入继续导出**：会破坏"恰好等于"的语义并让下游
  得到不可复现的结果。放弃，采用"拒绝其余部分、保留已输出部分"。

## 本地验证方法

```bash
# 全部单元测试 + 500 组随机序列与朴素参照模型对照
go test ./snapshot/

# 查看每次对照的输入、输出与判定依据（JSON 逐条记录）
go test -v -run TestPropertyAgainstNaiveModel ./snapshot/

# 并发线性化测试（竞态检测）
go test -race -run TestConcurrentLinearizable ./snapshot/

# O(1) 归属判定的基准复核
go test -bench=Classify -benchmem -run=XXX ./snapshot/
```

测试覆盖：写入接受时刻与边界恰好重合（`TestBoundaryTieGoesToSnapshot`）、
跨边界事务的归属（`TestCrossBoundaryTransaction`）、对象与链接各种交织
顺序下的引用完整性（`TestReferentialIntegrityInterleavings`）、原子性冲突
拒绝与已输出前缀保留（`TestAtomicityConflictRejectsRemainder`）、四类错误
的固定优先级（`TestErrorPriority*`）、资源不足（`TestResourceExhaustion`）、
O(1) 判定（`TestClassificationConstantWork`）、随机序列对照朴素模型
（`TestPropertyAgainstNaiveModel`，每次对照以 JSON 记录输入、实际输出与
判定所依据的规则）、并发线性化（`TestConcurrentLinearizable`）。
