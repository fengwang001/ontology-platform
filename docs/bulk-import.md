# 批量导入子系统设计说明

位置：`bulkimport/`（引擎）、`bulkimport/naive/`（对拍用朴素模型）、
`bulkimport/*_test.go`（测试）。

## 问题模型

一次导入任务（job）由唯一 ID 区分，条目分布在若干带序号的块中。
块可以乱序、重复、并发到达；条目可以引用尚未到达的块里的条目。
系统不等全部块到齐，尽早落地依赖已满足的条目，并对每个条目给出
可查询、两两可区分的确定状态。

## 架构

```
Manager ── 管理若干 job（创建、提交块、关闭、查询、统计）
  └─ job ── 每个任务一台状态机，三阶段处理一个块：
       1. 注册（持锁）：重复判定 / 关闭拒绝 / 上限拒绝，占位序号
       2. 校验（无锁）：逐条目跑 Validator，独立块之间完全并行
       3. 提交（持锁）：声明条目 → 分类 → 传播 → 破环 → 超时清扫
```

关键数据结构（全部在 `job` 内，受同一把互斥锁保护）：

- `entries`：已声明条目表（ID → 状态记录）。
- `dangling`：悬挂索引，**引用目标 ID → 等待者集合**，只保存当前仍
  处于悬挂状态的引用边。
- `waiters`：当前等待中的条目集合。
- `chunks`：序号 → 内容哈希，用于重复判定。
- `conflicts`：内容不一致的重复块记录，供查询时报 `EntryConflicted`。

## 核心机制

### 重复判定（需求 1、5）

判定只依赖「序号 + 内容哈希」（FNV-64a，对条目 ID 排序、字段排序、
引用排序后的规范化内容），与到达时间无关：

- 序号未见过 → 接受并处理。
- 序号见过且哈希一致 → `ChunkDuplicate`，不重新处理条目（测试用计
  数 Sink 证明没有重复落地）。
- 序号见过但哈希不同 → 以独立错误类别 `ErrKindChunkConflict` 拒绝；
  已确定的处理结果不可变，冲突被记录下来供查询。

### 悬挂引用与自动重试（需求 2、3）

条目提交时，未落地的引用目标被记入 `pending` 集合，并在
`dangling[target]` 上登记反向边。目标落地或失败时，`drain` 只弹出
`dangling[target]` 中的等待者：

- 目标落地 → 等待者移除该引用；引用全部满足则落地。
- 目标失败 → 等待者**立即**以 `ErrKindRefFailed` 失败并沿引用链传
  播，不会无限期等待一个已确定失败的引用。

查询等待中的条目时，`WaitingOn` 对每个引用区分
`target_not_arrived`（所在块还没到）与 `target_pending`（已声明但
自身仍在等待）。

### 块数上限与悬挂超时（需求 4）

`MaxChunks > 0` 时，当「已到达块数 == 上限」**且所有已注册块都提
交完毕**（`inflight == 0`）时，所有仍悬挂的条目判定为
`ErrKindDanglingTimeout` 最终失败；已落地条目不受影响。
`inflight` 计数是必要的：并发场景下最后一个块可能已注册但仍在提
交中，它可能正是悬挂目标的声明者（竞态测试
`TestBidirectionalDanglingConcurrent` 曾暴露此问题）。

### 双向悬挂 / 循环引用（需求 7）

每次提交后，在等待者图上跑迭代式 Tarjan SCC。若一个强连通分量是
真环（大小 > 1 或自环）且**所有成员的引用目标都已声明**（没有指
向未到达块或分量外等待者的边），则该环永远无法解析，立即以
`ErrKindValidation`（"circular reference"）确定性失败，并沿引用
传播。有出边的环（例如还引用未到达的块）保持等待，不被误判。

### 提前结束（需求 8）

`CloseJob` 与 `SubmitChunk` 的注册阶段在同一把锁上串行化，这就是
线性化点：块要么先注册成功（则必定被完整处理），要么看到
`closed` 而被拒绝（`ErrKindJobClosed`）。最终结果必然等价于两种
先后顺序之一，已落地条目不受影响。注意：提前结束**不会**终结仍
悬挂的条目（规格只把终结判定绑定在块数上限上），需要终结语义
的任务应声明 `MaxChunks`。

### 错误优先级（需求 10）

`ErrorKind` 的枚举值即固定优先级（数值小者优先）：

1. `chunk_conflict`（序号重复且内容不一致）
2. `ref_failed`（引用条目已确定失败）
3. `dangling_timeout`（达到块数上限）
4. `validation`（条目自身校验失败）
5. `job_closed`（提前结束后到达的块）

另加第 6 类 `chunk_limit_exceeded`（超过声明块数的新块），优先级
最低。优先级通过**判定顺序**落实：块级按 冲突 → 关闭 → 上限 的
顺序检查；条目级采用声明式语义——引用已失败立即判 `ref_failed`，
条目自身的校验错误**延迟到其引用全部解析后才生效**，这样更
高优先级的 `ref_failed` / `dangling_timeout` 总能胜出，且最终状
态与块到达顺序无关。

## 关键取舍

1. **校验错误延迟生效**：带校验错误且引用未解析的条目先保持
   pending，而不是立即失败。代价是这类条目的失败 verdict 来得稍
   晚；收益是最终状态与块到达顺序无关，且天然满足全局错误优先
   级。这是与朴素模型能对拍一致的关键语义。
2. **提交临界区串行、校验并行**：每个 job 一把锁，注册/提交是
   O(块大小 + 受影响等待者) 的短临界区；昂贵的条目校验在锁外完
   全并行。放弃了「完全无锁」或「分片锁」方案：正确性论证复杂度
   高，而提交路径本身极短。
3. **环判定为失败而非整环原子落地**：循环引用（SCC）以
   validation 类失败，而不是把整环作为一个批次原子落地。后者对
   本体场景也有意义，但失败语义与「朴素模型拓扑排序遇环即失败」
   一致，便于对拍，且结果确定。
4. **Sink 在锁内调用**：落地回调在提交临界区内同步执行，保证
   「落地」与状态转移原子一致；文档要求 Sink 必须快速且不得回调
   Manager。放弃了异步落地队列（会引入「已落地但未持久化」的中
   间态，破坏结果确定性）。
5. **条目 ID 首次声明获胜**：同一条目 ID 在不同块中重复声明时，
   后者以 validation 失败（结果只体现在该块的 `ChunkResult` 中），
   引用绑定到首次声明。
6. **提前结束不终结悬挂条目**：`CloseJob` 只拒绝新块；悬挂条目
   的最终失败只由块数上限触发（规格如此）。

## 被放弃的方案

- **等待全部块到齐再处理**：即 `naive/` 模型，不满足「尽早落
  地」，仅作为对拍基准保留。
- **按引用计数扫描全表解析**：每次落地后扫描全部条目找等待者，
  开销随已处理条目总数增长，违反需求 6，被悬挂索引取代。
- **事件溯源 / 重放**：所有到达事件落日志、查询时重放。确定性
  好，但查询与重复判定的实现复杂度高，且对本需求规模没有必要。
- **整环原子落地**：见「关键取舍 3」。

## 悬挂记录开销证明（需求 6）

结构上：解析引用的唯一路径是 `dangling[target]` 的哈希查找与等
待者集合弹出；破环与超时清扫只遍历 `waiters`（当前悬挂条目）；
代码中不存在任何对 `entries` 全表的遍历。

可执行的证明（`TestDanglingIndexCostIndependentOfProcessedEntries`）：

- `Stats.EntryTableScans` 是不变量探针，恒为 0；
- 分别落地 1,000 与 20,000 条无引用条目后，再解析 5 个悬挂引用，
  两种规模下 `Stats.WaiterPops` 都恰好等于 5（只触及等待者本
  身），与已处理条目总数无关；
- 对照组 `naive.Model.FullScans` 随条目总数增长，体现两种实现的
  复杂度差异。

## 本地验证方法

```bash
export PATH=$PATH:/usr/local/go/bin   # 如 go 不在 PATH

# 全量测试（含竞态检测）
go test -race ./...

# 随机对拍：增量引擎 vs 朴素模型，300 个随机场景
# （乱序、重复注入、冲突注入、提前结束）
go test ./bulkimport/ -run TestDifferentialRandom -v -count=10

# 开销证明
go test ./bulkimport/ -run TestDanglingIndexCostIndependentOfProcessedEntries -v

# 日志判定依据（每个块/条目的输入、结果与原因）
go test ./bulkimport/ -run TestLoggingDecisions -v

# 检查
gofmt -l . && go vet ./...
```

日志：引擎通过 `slog` 输出每个块的到达/重复/冲突/拒绝与每个条目
的落地/失败/悬挂及判定依据（`WithLogger` 注入；默认丢弃）。
