# 派生属性索引一致性子系统 — 设计说明

## 1. 问题与模型

索引对象不是对象自身的属性，而是它经由某条**链接类型**连接到的目标对象上的属性：

```
Manager.deptCode  ⇝  memberOf → Dept.code
Employee.mgrDept  ⇝  reportsTo → Manager.deptCode   （第二级来源本身也是派生值）
```

系统必须在三类变化下保持一致：

1. 源属性写入；
2. 链接增删（包括唯一性被破坏）；
3. 上述变化与实例删除并发/交织。

### 1.1 核心概念

- `LinkType{Name, SrcType, DstType, Unique}`：有向链接。`Unique` 是链接**基数**约束
  （建边时每个源实例至多一条出边）；它与派生索引的“声明要求唯一”是两个独立概念。
- `DerivedIndex{SrcType, PropName, Link, DstProp}`：在 `SrcType` 实例上维护派生属性
  `PropName`，取值经由 `Link` 唯一指向的目标实例的 `DstProp`。
- 派生声明构成以 `(对象类型, 属性名)` 为节点、以“取值来源”为方向的有向图（派生 DAG）。

### 1.2 索引状态（明确的不可索引，而非“任选一个”）

每个 `(下游实例, 派生属性)` 的状态四选一：

| 状态 | 条件 | 是否出现在查询结果 |
| --- | --- | --- |
| `StateIndexable` | 恰好一条链接、目标存在、来源属性有值（多级时递归可索引） | 是 |
| `StateMissingSource` | 无链接目标 / 目标实例不存在 / 递归链断裂 / 源实例被删除 | 否 |
| `StateNotUnique` | 声明要求唯一但当前存在多条同类型出边 | 否 |
| `StateNoValue` | 唯一目标存在，但来源属性未设置（`Has=false`） | 否 |

当一个实例经多条同类型链接指向不同源实例时，**绝不挑选任意一个**取值；
索引立即转为 `StateNotUnique`，且该转变与链接改变在同一个原子单元内可见。

## 2. 关键取舍

### 2.1 并发控制：全局 RWMutex + 每操作事务工作副本（严格可串行化）

所有公开方法在同一把 `sync.RWMutex` 下串行化：

- 写操作：持写锁 → 深拷贝 `storeState` 得到工作副本 → 在副本上完成“真值修改 +
  全部分层下游重算” → 成功则一次性指针替换提交，任一步失败则丢弃副本。
- 读操作（`QueryIndex`/`Resolve`/`Snapshot`）：持读锁，读与写互斥、读之间并发。

因此任何读写交织都等价于这些原子单元按某个全序逐一执行，天然满足
“查询等价于发生在某个与变更次序一致的时间点”。

**为什么放弃更细粒度的锁 / OCC / MVCC**：需求的核心是可证明的原子单元与串行等价性，
而不是吞吐；细粒度锁会让“链接改变与索引更新同单元可见”“三者交织不漏操作”的证明
复杂化。全局串行化把证明缩减为“单元内全成功或全不发生”，且 `-race` 测试简单可靠。
接口层（`Store` 方法签名）不暴露锁，后续可用分片锁/MVCC 替换而不改动调用方。

### 2.2 传播：沿派生 DAG 的分层 BFS，显式去重

源属性写入或链接增删产生种子集合 `(派生节点, 受影响实例)`，随后：

1. 在当前层重算这些实例的索引状态（先从旧索引桶摘除，再按新状态入桶/标记不可索引）；
2. 沿派生 DAG 的 `dependents` 边，用**当前真实入边集合** `incoming[target][link]`
   计算下一层实例；
3. `done[(节点,实例)]` 与每层 `dedupAffected`、`reindex` 内的 `seen` 三重去重。

由此可以精确陈述需求中的数量性质：

> 一次源属性写入触及的下游更新数量，恰好等于当前真实指向该源实例的下游实例数量，
> 跨层求和后每个 `(节点,实例)` 只计一次；不指向它的实例不会被触及。

`TestExactDownstreamCountNoDuplicates` 对 50 个真实下游 + 1 个指向别处的兄弟实例
断言返回的 `propagationLevel.instances` 总数恰为 50、无重复、无越界。

### 2.3 多级传递

来源属性本身是派生属性时，`evaluate` 沿派生 DAG 递归求值；实例创建时物化其全部
派生属性的初始状态，因此多级链路上的任何一跳变化都由 2.2 的 BFS 继续向下传播。
递归携带 `onPath` 作为环路双保险（正常情况下被 schema 注册期检测挡住）。

### 2.4 循环传递：注册期、生效前检测

注册新派生声明等价于向派生 DAG 加入边 `source -> downstream`。当且仅当
`downstream` 沿**既有**边已能到达 `source` 时，加入后成环。此时拒绝注册、
不写入任何状态（`TestCyclicDerivationRejectedBeforeActivation` 验证两节点互指与
三节点长环均在生效前被拒，且被拒声明不可查询）。

### 2.5 删除级联

- 删除**下游**实例：摘除它自身全部派生条目与查询命中；维护其出/入边索引；
  不触碰其他仍指向同一源的实例。
- 删除**源**实例：在同一工作副本内先删全部入边（真值），再对受影响下游做传播
  重算——此时它们必为 `StateMissingSource`；随后提交。源删除与其下游转不可索引
  因此在同一单元内完成。

### 2.6 错误优先级（固定、全局唯一裁决点）

`classify` 按 `ErrorKind` 数值从小到大取最高优先级：

1. `KindSourceNotFound`（源对象实例不存在）
2. `KindLinkTypeNotSupported`（链接类型不支持派生索引 / 对派生属性直接写入）
3. `KindNotUnique`（链接不唯一导致不可索引 / 唯一基数建边被拒）
4. `KindCyclicDerivation`（循环传递声明在生效前被拒）
5. `KindDownstreamUpdateFailed`（下游索引更新失败导致整单元回滚）

一个操作收集所有候选错误后统一交给 `classify`，多条件并存时报告最高优先级。

### 2.7 原子回滚的可测性：故障注入钩子

`SetIndexFailHook` 在每次下游索引更新**应用前**被调用；返回错误则传播立即中止，
`SetAttribute` 丢弃工作副本。测试用它证明：源属性写入与下游更新同生共死，
不会出现“源已改、索引半更新”的中间态。

### 2.8 变更日志

`Journal` 为每个成功提交的单元记录 `ChangeRecord`：操作名、输入参数、
分层 `propagation`（每层的类型/属性、**受影响下游实例集合**、逐实例判定依据）。
可 `SetOutput(io.Writer)` 同步打印；对拍测试即把日志落到 buffer 以便失败时复盘。

## 3. 被放弃的方案

- **惰性求值（只在查询时沿链接现算）**：读路径简单，但“源写入必须与下游更新同单元、
  任一失败整体回滚”“精确触及数量证明”“大批量源写入的单元语义”都无法成立，放弃。
- **事件队列 / 异步传播**：天然暴露“已反映两个操作、漏掉第三个”的中间状态，
  与需求的即时可见性和串行等价性直接冲突，放弃。
  接口上保留了未来把同步传播换成同步批处理的空间，但不会引入异步可见性。
- **细粒度行锁 + 合并更新**：能提升吞吐，但原子单元与多跳交织的证明成本高，
  当前规模下不划算，留作存储后端演进项。
- **在链接结构上强制唯一来表达派生唯一性**：会把“多条边合法存在但索引不可索引”
  这一状态建模成“禁止建边”，无法表达 `StateNotUnique`。因此链接基数与派生唯一性
  被刻意拆成两个独立概念（见 1.1/1.2）。

## 4. 代码地图

| 文件 | 职责 |
| --- | --- |
| `ontology/schema.go` | 类型/链接/派生声明注册，派生 DAG 与环检测 |
| `ontology/store.go` | 内存真值、反向入边索引、索引桶、深拷贝事务、快照 |
| `ontology/derive.go` | 四态求值（含多级递归）、单节点重算与去重 |
| `ontology/propagate.go` | 分层 BFS 传播引擎（精确数量/不重复/故障中止） |
| `ontology/tx.go`, `tx_instance.go`, `tx_internal.go` | 原子变更单元、Multi、删除级联 |
| `ontology/query.go` | 索引查询与状态解析（读锁、串行化读） |
| `ontology/errors.go` | 错误类别与固定优先级裁决 |
| `ontology/journal.go` | 变更日志（输入/下游集合/判定依据） |
| `ontologytest/naive.go` | 独立朴素全量重算模型（不共享任何增量逻辑） |
| `ontologytest/differential.go`, `ops.go`, `assert.go` | 随机操作生成、三者交织事务、逐步全量对拍 |
| `cmd/demo/main.go` | 可运行最小场景 |

## 5. 本地验证方法

需要 Go 1.26+（本机若 `go` 不在 PATH，使用 `/usr/local/go/bin`）。

```bash
# 编译与静态检查
go build ./...
go vet ./...
gofmt -l .

# 全量测试（含随机差分对拍与删除/交织场景）
go test ./...

# 竞态检测 + 详细输出
go test -race -v ./...

# 覆盖率
go test -coverprofile=coverage.out ./...
go tool cover -func=coverage.out

# 可运行演示（日志打印每次变更的输入、受影响下游集合与判定依据）
go run ./cmd/demo
```

差分对拍（`ontologytest`）构造 Region→City→Store 两层派生图，随机生成：
源属性写/清空、两类链接增删、三者（写源 + 删旧链 + 建新链）随机顺序的 `Multi`
原子单元、源实例删除并同 ID 重建；每个原子单元后都用朴素模型对**逐实例四态**与
**每个键值桶的完整查询结果**做全量比对。测试默认跑 12 个种子 × 300 步，
可在 `differential_test.go` 调整规模。
