# 对象实例并发控制设计说明

本体平台为对象实例更新提供两种并存的并发控制方式：

- **普通属性更新**：乐观并发控制，调用方携带期望版本号，冲突即拒绝；
- **动作（Action）触发的生命周期状态机转换**：必须先获得实例上的独占占用权，
  占用期间普通乐观更新一律被拒绝（不排队），释放后恢复乐观规则。

实现位于 `ontology/` 包，本文说明关键取舍、被放弃的方案与本地验证方法。

## 核心机制

### 1. 单一互斥锁 + 暂存-提交（staged commit）

`Store` 内所有判定与状态变更都在同一把互斥锁的保护下完成，每个操作
（更新、申请、暂存、提交、中止、心跳）都是原子判定点。动作在占用期间的
属性变更先写入句柄内的暂存区，`Commit` 时才原子地落入实例并递增版本；
`Get` 只能读到已提交状态。因此外部任意一次读取要么看到占用开始之前、
要么看到占用结束之后的完整状态，永远看不到动作执行到一半的中间属性组合。

### 2. 乐观更新

`Update(caller, id, expectedVersion, mutations...)` 的判定顺序固定：

1. **占用冲突**：实例被未过期租约占用 → `RejectInstanceOccupied`；
2. **基数/必填约束**：违反对象类型约束 → `RejectCardinality`；
3. **版本落后**：`expectedVersion != currentVersion` → `RejectVersionStale`。

占用冲突的判定先于版本落后判定；任何拒绝都不会改变实例版本号。
占用结束后，调用方必须用释放时刻的最新版本重新发起（旧版本会得到
`RejectVersionStale`），系统不沿用占用开始前的版本。

### 3. 独占占用权：非阻塞申请 + 租约 + 栅栏令牌

- `Acquire` 是纯粹的 check-and-set：实例被占用时**立即**返回
  `RejectOccupiedByAction`，不阻塞、不排队、不由系统自动重试。
- 每次授予颁发**实例级单调递增的栅栏令牌**（fencing token），
  持有方的暂存/心跳/提交都校验令牌；令牌不匹配即 `RejectOccupancyLost`。
- 占用附带**租约**（lease）：持有方需用心跳续期。
  **判定占用是否失效的唯一依据是"当前时间 ≥ 租约截止时间"**，
  时间来源是可注入的 `Clock`。持有方异常中止（无心跳、无显式释放）时，
  租约到期后占用可被后续申请方接管；到期之前绝不提前释放。
  旧持有方"复活"后的任何写入都会因栅栏令牌不匹配而被拒绝，
  因此不会出现占用权永久悬挂，也不会出现双写。

### 4. 跨实例占用的确定性死锁规避

规则：**所有动作必须按实例 ID 升序申请占用**。动作当前持有的最大实例 ID
记为 `max(held)`，申请 `id < max(held)` 时立即以 `RejectOrderConflict`
拒绝。该规则是经典有序锁（ordered locking）的非阻塞变体：

- 持有-等待的循环依赖在结构上不可能形成（偏序关系无环）；
- 谁被拒绝完全由实例 ID 的全序预先决定，与调度时序无关，可预先推导；
- 判定只需读取该动作的 `heldMax`，O(1)。

### 5. 四类拒绝结果互斥且可单独识别

| 拒绝码 | 含义 |
| --- | --- |
| `RejectOccupiedByAction` | 占用申请被拒绝：实例已被另一动作占用 |
| `RejectInstanceOccupied` | 占用期间的普通乐观更新被拒绝 |
| `RejectVersionStale` | 乐观更新因版本落后被拒绝 |
| `RejectOrderConflict` | 跨实例占用违反升序规则被拒绝 |

另有 `RejectCardinality`（基数约束）与 `RejectOccupancyLost`（栅栏令牌
失效）作为辅助拒绝码。全部通过 `RejectError.Code` 以机器可判的方式返回。

### 6. 可串行化

所有判定与生效都在同一临界区内完成，因此并发执行等价于按临界区先后
的某个串行顺序；占用窗口内普通更新只会被拒绝而不会插入生效，满足
"占用期间不允许插入任何普通更新"的串行等价要求。审计日志的全局序号
（`AuditRecord.Seq`）就是这一串行顺序的可验证物证。

### 7. O(1) 判定开销

拒绝判定只涉及：一次实例哈希表查找、一次动作 `heldMax` 查找、
一次租约时间比较。不遍历实例表或占用记录表。证据见下文基准。

### 8. 审计日志

每次占用申请与每次更新尝试（以及暂存/提交/中止/心跳）都会记录：
全局序号、时间、操作类别、实例、行为方、结构化输入（期望版本、变更、
栅栏令牌）、判定依据（当前版本、占用持有方、令牌、已持有集合）与结果码。
日志支撑确定性重放核验（见 `TestRandomizedAgainstNaiveSerialModel`）。

## 被放弃的方案

- **阻塞式互斥锁 / 等待队列**：与"申请方必须立即收到明确拒绝、不允许
  阻塞等待、不允许系统自动排队重试"的要求直接冲突，放弃。
- **等待-死亡（wait-die）/ 伤害-等待（wound-wait）**：需要动作优先级
  并允许撤销他方占用，语义更重；非阻塞约束下"等待"分支无处安放，
  且撤销正在执行的动作会破坏占用期间的原子可见性。改用升序规则后，
  死锁在结构上被排除，无需运行时仲裁。
- **每实例一把锁**：多实例占用需要按固定顺序嵌套加锁，与升序规则等价
  但实现更复杂、读路径还要额外处理暂存可见性；单锁 + 暂存区更简单，
  且本场景吞吐瓶颈不在锁竞争。
- **基于版本号的占用标记**（把占用信息编码进实例版本）：会让"占用期间
  普通更新不得改变版本号"与"释放后按最新版本判定"的语义纠缠不清，
  且无法支撑栅栏令牌。占用记录独立于版本号保存。
- **后台租约扫描回收**：回收线程引入"何时判定失效"的第二时间源，
  与"唯一判定依据"冲突；改为申请方在临界区内惰性判定（lazy expiry），
  判定依据唯一且 O(1)。

## 本地验证方法

```bash
# 全量测试（含竞态检测）
go test -race ./...

# 随机操作序列 vs 朴素全局串行模型对照（重放审计日志）
go test -race -run TestRandomizedAgainstNaiveSerialModel -v ./ontology/

# 跨实例交错顺序的确定性
go test -run TestCrossInstance -v ./ontology/

# O(1) 判定开销证据：三种拒绝判定在 1k/10k/100k 实例规模下的 ns/op
go test -run xxx -bench=Scaling -benchtime=2000x ./ontology/

# 演示程序
go run ./cmd/server
```

基准结果（linux/arm64 示例）：三种拒绝判定在实例总数从 1,000 增长到
100,000（含 50,000 条并存占用记录）时，单次判定均稳定在亚微秒至
约 2 微秒区间，无随规模增长的趋势，且证据完全通过公开 API
（`Acquire`/`Update` 的返回与计时）获得，不依赖任何额外对外暴露的状态。
