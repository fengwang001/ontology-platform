# 对象生命周期状态机与校验钩子触发范围子系统 — 设计说明

## 模块划分

| 模块 | 文件 | 职责 |
| --- | --- | --- |
| 状态机定义与转移执行 | `ontology/lifecycle.go` | 对象类型声明（阶段集合、允许的有向转移、终态）、实例状态、转移执行与串行化、轨迹记录 |
| 钩子注册与触发范围解析 | `ontology/hooks.go` | 按具体转移 `(from,to)` 与按阶段进入点注册钩子；O(命中数) 解析 |
| 错误归一化 | `ontology/errors.go` | 四类可区分的拒绝原因、固定判定次序、`*Error` 上下文携带 |
| 朴素对照模型 | `ontology/naive/naive.go` | 独立实现：全部声明存切片、每次全量遍历，仅用于差分测试 |

## 关键取舍

### 1. 触发范围解析：双哈希索引而非全量扫描

`HookRegistry` 内部维护 `map[Edge][]*Hook` 与 `map[Stage][]*Hook` 两个索引。
`Resolve(from, to)` 只做两次哈希查找并拼接结果，扫描的钩子数恒等于命中数。
可验证性由两点保证：

- `HookRegistry.LastResolveScanned()` 暴露最近一次解析实际触碰的钩子数，
  `TestResolveScannedEqualsHits` 断言在总钩子数 23 / 2003 / 200003 下扫描数恒为 3；
- `BenchmarkResolve` 在总量 100 / 10000 / 1000000 下耗时应基本平坦（本地实测均约 30ns/op）。

放弃的方案：注册时把进入钩子展开复制到每条允许边上（空间换时间）。
放弃原因：展开后注册/注销复杂度与边数耦合，且自转移语义（"只触发声明在
`(s,s)` 上的具体转移钩子"）在展开表中需要额外标记区分来源，容易出错；
双索引的解析开销已经是 O(命中数)，没有必要再优化。

### 2. 自转移不做任何特判

自转移 `s->s` 在解析层与普通转移走同一条路径：具体转移钩子按 `(s,s)`
精确匹配（未声明则不触发，也不会误触发 `(s,other)` 的钩子），进入钩子按
目标阶段 `s` 命中（照常触发）。特判只会引入"默认跳过/默认触发"的错误空间，
因此明确放弃对 `from == to` 的任何分支处理。同时自转移本身也必须是声明的
边 `(s,s)`，否则按"转移关系未允许"拒绝。

### 3. 终态检查内联在转移执行器中，而非作为"系统钩子"

曾考虑把终态限制实现为一个优先级最高的内置钩子，复用钩子管线。
放弃原因：需求规定终态限制优先于钩子校验且钩子不得被触发；若把终态检查
放进钩子管线，"钩子不得触发"就需要在管线内再开特例，反而模糊语义。
现在的实现是转移执行器内按固定次序的四个检查点：
参数非法 → 终态 → 关系未允许 → 钩子校验，命中即返回，次序即需求次序。
### 4. 失败原子性：先校验后提交，副作用回退交给钩子声明

转移执行是"全部钩子通过后才写实例阶段"的两段式结构，因此不存在
"钩子跑了一半"的中间阶段——阶段字段只在所有钩子通过后赋值一次。
钩子的记录副作用（`HookContext.Emit`）是否随失败撤销，由钩子注册时声明的
`CommitSemantics` 决定：`RollbackOnFailure` 的条目在失败时打上
`RolledBack` 标记，`CommitOnFailure` 的条目（如审计日志）保留。
采用"打标记"而非"物理删除"，是为了让回退本身也可被审计与测试观测。

### 5. 并发：实例级互斥锁串行化

每个 `Instance` 持有自己的 `sync.Mutex`，`Transition` 全程持锁：
读取起始阶段、四类检查、钩子执行、阶段提交都在同一临界区内。
因此并发请求的最终效果天然等价于按锁获得顺序的全局串行执行，
每条轨迹记录的 `From` 必然等于前一条记录结束时的阶段（无分叉）。
放弃的方案：CAS 乐观并发（读阶段→跑钩子→CAS 提交）。放弃原因：
钩子执行期间阶段可能被并发转移改变，CAS 失败后需要重跑钩子，
而钩子副作用的重跑语义（重复 Emit、重复审计）无法对用户隐藏；
串行执行以可预测的代价换来确定性与重放一致性。

### 6. 轨迹即真值：重放一致性

每次转移请求（无论成败）都追加一条 `TransitionRecord`（起始/目标阶段、
按序的钩子触发记录、错误类别）。由于记录是在持锁的串行临界区内追加的，
轨迹顺序就是全局串行顺序；按轨迹中的目标阶段序列重放同一组请求，
必然得到完全相同的阶段轨迹与钩子触发记录（`TestConcurrentTransitionsNoFork`
对此做了重放断言）。

## 本地验证方法

```bash
# 全量测试（含竞态检测）
go test -race ./...

# 查看测试打印的输入/输出/判定依据
go test -v ./ontology/

# 差分对照（300 个随机种子 × 每种子最多 200 条随机请求，与朴素模型逐条对照）
go test -v -run TestDifferentialAgainstNaive ./ontology/

# 解析复杂度佐证（总量 100/10000/1000000 下耗时应平坦）
go test -run - -bench BenchmarkResolve ./ontology/

# 静态检查
gofmt -l .
go vet ./...
```
