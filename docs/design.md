# 双上限图遍历设计说明

## 目标

图遍历同时接受两个互相独立的上限：

- `MaxDepth`：沿任意一条路径最多扩展的跳数，`0..MaxDepth` 都属于合法返回深度。
- `ResultLimit`：整次遍历最多计入结果的路径数。

两个上限不换算、不折抵。路径到达深度上限时仍先作为一条结果计入；随后若结果条数上限已满，才由条数逻辑阻止其他未完成分支。

## 返回模型

`TraverseResult` 返回：

- `Paths`：实际计入的路径，按确定遍历顺序排列。
- `Truncated`：没有被完整展开的分支及其互斥截断原因。
- `SnapshotID`：本次遍历读取的图快照版本。
- `CompletedPaths`：成功计入的路径数。

四类原因如下：

- `depth_only`：该分支先满足深度停止条件，且计入路径后仍有结果名额。
- `limit_only`：该分支在尚未达到深度上限时，结果名额已经耗尽。
- `depth_before_limit`：当前路径恰好在深度边界被计入，并且这次计入恰好填满结果名额；该路径的下一跳因深度上限本来就不允许扩展。
- `limit_before_depth`：结果名额已经耗尽后才轮到该分支；该分支前缀已位于深度边界，若有名额还会被计入但不能继续向下扩展。

一条已经自然结束的叶子路径若没有下一跳，说明不存在被深度阻止的分支，不生成深度截断记录。它是否因为填满结果上限而导致其他兄弟分支停止，由那些兄弟分支各自携带 `limit_only` 或 `limit_before_depth`。

## 确定展开顺序

遍历采用单线程迭代深度优先搜索，避免调度和并发改变归类。

1. 起始对象作为深度 0 的第一条路径。
2. 对当前对象收集所选方向的链接，方向顺序固定为 `outgoing` 后 `incoming`。
3. 同一节点的候选边按 `(目标对象 ID, 链接类型)` 升序排序并去重。
4. 子路径按升序逆序压栈，从而按升序弹栈处理。
5. 不依赖 goroutine、channel 或 map 迭代顺序。

因此，同一快照、同一请求参数下，路径与截断标记分布逐字节相同。

## 上限交互

每条候选路径弹出栈时：

1. 若结果名额已耗尽，当前待处理分支不再做任何“完成它更划算”的优先处理，直接归入条数截断；深度已到边界时标记为 `limit_before_depth`，否则为 `limit_only`。
2. 若仍有名额，先计入当前路径，再判断深度。
3. 深度边界且计入后满额时标记 `depth_before_limit`，并清空剩余待处理分支。
4. 深度边界但未满额时标记 `depth_only`。
5. 未满深度但计入后满额时，当前前缀标记 `limit_only`，其直接下一跳和所有既有待处理分支都按同一规则排空；深度边界上的下一跳为 `limit_before_depth`。

已经在栈中的“半展开分支”与尚未入栈的分支没有优先级差异：满额后不会继续递归其后代，只记录当前被阻止的前缀。

## 快照一致性

`Graph` 用读写互斥锁保护当前版本指针。所有写操作采用 copy-on-write 生成新的 `graphState` 和新的版本号；`Snapshot()` 在锁内复制当前状态指针后立即释放锁。

快照持有的旧 map 和邻接切片不会被后续写操作修改，因此遍历期间其他 goroutine 增加对象或链接不会影响本次路径、上限触发顺序或标记分布。其结果等价于在 `Snapshot()` 成功时刻读取到的确定不可变版本。

## 错误顺序

错误按以下固定顺序只返回第一类：

1. `ErrStartNotFound`
2. `ErrInvalidMaxDepth`
3. `ErrInvalidResultLimit`
4. `ErrEmptyLinkDirections`

所有错误都在分配结果和写入遍历日志前返回，因此拒绝请求不产生部分结果。

## 计数开销

结果计数只维护两个整数：`accepted` 与 `limit`。

- `acceptOne()` 是固定次数的整数比较和加法。
- `reached()` 是一次整数比较。
- 判定是否已满不需要保存已收集路径 ID，也不需要随 `ResultLimit` 增长的集合、队列或哈希表。

因此，“是否达到结果条数上限”的额外时间和空间均为 O(1)，不会随后限数值超线性增长。返回路径本身仍需要 O(返回路径总长度) 空间，这是结果载荷，不属于上限判定开销。

`TestResultCounterReachedIsConstantSpaceAcrossLimits` 对 1、10、1,000、100,000 四个上限复现检查 `reached()` 的零分配；`BenchmarkResultCounterReachedDoesNotGrowWithLimit` 输出耗时和分配，便于人工比较不同上限。

## 朴素对照

测试中的 `naiveTraverse` 是独立递归实现，不使用生产代码的显式栈和排空函数。它按相同的排序邻接序递归访问路径，并以独立控制流记录第一触发条件。随机测试构造 500 组小图、随机起点、方向集合、深度上限和条数上限，逐条比较路径、前缀和截断原因。

## 关键取舍

- 选择不可变快照而不是遍历期间持有图锁：读遍历不会阻塞写请求，且最容易证明并发修改下的等价性。
- 选择显式迭代 DFS 而不是 goroutine 池：消除调度不确定性，也更容易在满额时立即停止所有分支。
- 选择记录每个被阻止的直接前缀，而不是聚合计数：调用方能准确定位每条不完整分支及互斥原因。
- 选择按对象 ID 和链接类型排序，而不是保留链接插入顺序：跨数据库重建或批量导入后仍有稳定语义。

## 放弃的方案

- 广度优先搜索：可以做，但对“同一分支上两上限先后触发”的语义不更直观，还需要维护跨层队列；本需求没有要求按层优先。
- 遍历期间持有全局图读锁直到结束：快照一致性简单，但长遍历会阻塞写操作，不适合本体平台。
- 满额后继续完成已经部分扩展的路径：违背“不得因已投入开销给予特殊待遇”，也会使条数上限无法及时停止图访问。
- 用一个笼统的 `truncated=true` 标记：无法区分深度、条数及同分支先后关系，不满足调用方错误处理和恢复需求。
- 用 map 记录已访问对象来剪枝：会把不同路径错误合并，破坏“路径总数”和逐路径截断标记。
