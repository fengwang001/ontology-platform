# 最大需量控制器设计说明

`demand` 包实现工业用户的最大需量控制器：按滑动窗口平均功率逼近合同需量，
预测越限时按优先级切除可控负荷，未越限时在最短接入/断开约束下恢复负荷。

## 模块划分

包内按职责拆分为相互协作的模块（文件）：

| 模块 | 职责 |
| --- | --- |
| `config.go` | 控制器配置与负荷参数的定义及校验 |
| `errors.go` | 五类可区分错误（`errors.Is` 判定）及校验次序约定 |
| `history.go` | 电量台账：只记录滑差边界时刻的累计电量，常量内存 |
| `peak.go` | 实测需量峰值记录（并列取较早窗口结束时刻） |
| `loads.go` | 负荷注册表：接入/断开状态、锁定、计时起点 |
| `predict.go` | 切除集合选择（最少个数、优先级和最大、编号字典序最小） |
| `evaluate.go` | 越限预测：标量功率界计算、切除阶段、恢复阶段 |
| `controller.go` | 控制器主体：上报校验与受理、串联各模块、并发串行化 |
| `ops.go` | 运维操作：负荷增删、锁定/解锁、峰值查询 |

协作关系：`Report` 校验通过后由 `history` 入账并触发 `peak` 记录，随后
`evaluate` 用 `history` 的窗口电量与 `loads` 的负荷状态计算功率界，越限时调用
`predict` 选出切除集合，未越限时按恢复规则逐个试接；动作回写 `loads`。

## 关键取舍

### 1. 滑差边界累计电量台账（评估开销与历史无关）

窗口只在滑差整数倍时刻结束，而窗口长是滑差的整数倍，因此**所有窗口的起点与
终点都是滑差边界**。于是只需记住每个滑差边界时刻的累计用电量；两次上报之间
功率恒定，区间内任意边界的累计电量可线性插值。评估时只需查询
`窗口长/滑差` 个边界，而早于 `当前时刻-窗口长` 的边界永远不会再被任何未结束
窗口引用，直接裁剪。

效果：内存占用恒为 `窗口长/滑差 + 1` 个条目，单次评估开销只与负荷数和重叠
窗口数有关，与历史上报次数完全无关。由 `TestBoundaryRetentionBounded`（结构
断言）与 `TestEvalCostIndependentOfHistory`（10 万条与 100 万条历史两档对照，
实测比值 1.00）双重验证。

### 2. 所有窗口约束合并为单个标量功率界

每个未结束窗口的预测约束为 `已发生电量 + 假定功率 × 剩余时长 ≤ 合同需量 ×
窗口长`。已发生电量与假定功率无关，因此每个窗口等价于 `假定功率 ≤ 界_w`，
全部窗口取最小即得单一标量界 `bound`：

- 切除阶段：所需降幅 `R = 当前功率 - bound`，问题化为"选出额定功率和不小于
  R 的最优子集"；
- 恢复阶段：逐个试接等价于检查 `当前功率 + 额定 ≤ bound`；
- `bound < 0` 表示某窗口已发生电量本身已超限，任何切除都无法挽回，直接切除
  全部可切除负荷并标记仍越限。

### 3. 切除集合选择：贪心定基数 + 两个动态规划精确解并列

三层判定依次是：个数最少 → 优先级数字之和最大 → 编号序列字典序最小。

- 个数最少：按额定功率从大到小贪心，交换论证可证最优；
- 优先级和最大：在"恰好 k 个、额定和 ≥ ceil(R)"约束下做记忆化 DP（额定功率
  建模为整数千瓦，故 `ceil(R)` 为整数阈值）；
- 字典序最小：以求得的最大优先级和为目标，用可行性 DP 按编号升序贪心重构
  （每个编号"能选就选"）。

正确性由独立朴素模型（暴力枚举全部子集）在随机对照测试中逐步验证。

### 4. 浮点语义

内部计算使用 `float64`。针对性测试与随机对照测试均选取二进制可精确表示的
数值（整数功率 × 整数秒），"恰好等于合同需量不算越限"的等号判定因此是精确
的。若现场数据含任意小数且对边界等号有硬性要求，可换用精确有理数，见
"被放弃的方案"。

### 5. 并发：单互斥锁串行化

所有公开方法（上报、增删负荷、锁定/解锁、峰值查询）共用一把 `sync.Mutex`，
任意并发调用等价于某个串行顺序（可线性化），实现简单且无竞态（`go test
-race` 验证）。评估本身是毫秒以下的纯内存计算，锁竞争不是瓶颈。

### 6. 规格解释性决策（已在代码注释与测试中固化）

- **首条上报只建立时钟**：其电量无法归属到任何区间，予以忽略；
- **时刻回退且电量为正**视为平均功率无穷大，归入数据非法（与"数据非法 >
  时刻回退"的次序一致）；回退且电量为零才是时刻回退；
- **关键负荷** = 优先级数字等于当前全部负荷中最小值的负荷（可有多台），永不
  被切除；新增更小优先级负荷会改变关键集合，自下一次评估生效；
- **锁定只影响切除**：锁定已断开的负荷不会使其恢复（该操作本身不触发评估），
  但后续正常评估的恢复流程不排斥被锁定的断开负荷；
- **删除负荷**：按规格字面，接入或断开状态的负荷删除均被拒绝（状态不允许），
  即已存在的负荷不可删除；
- **负荷新增**默认为接入状态，最短接入计时自添加时刻（控制器当前时间）起算；
- 额定功率建模为**正整数千瓦**（配置中的合同需量、窗口、滑差按规格为正整数）。

## 被放弃的方案

- **保留全部上报历史 + 前缀和/二分查找**：评估开销为 O(log n + 窗口数)，内存
  随历史线性增长，不满足"开销不得随历史上报次数增长"的要求，被方案 1 取代。
  该思路保留在测试用的朴素模型中作为对照实现。
- **精确有理数（big.Rat）记账**：可彻底消除浮点等号风险，但累计电量的分母会
  随上报区间长度连乘膨胀，需要定期约分且实现复杂；在测试数据可选取精确可
  表示值的前提下收益不足。
- **切除选择纯贪心**（按额定或优先级排序直接取）：对"个数最少"最优，但无法
  保证后两层并列判定最优（反例：额定 1 的负荷优先级极高时会输给任意大功率
  负荷），故仅用于定基数，并列判定交给 DP。
- **无锁并发（原子状态 + CAS）**：状态横跨台账、负荷、峰值三块，多字不变量
  难以无锁维护，正确性风险远高于收益。
- **评估触发式峰值记录**（每次评估扫描全部已结束窗口）：与方案 1 的增量记录
  相比重复计算，已并入上报处理流程一次完成。

## 本地验证方法

```bash
# 全量测试（含朴素模型随机对照、并发冒烟）
go test ./demand/

# 竞态检测
go test -race ./demand/

# 查看随机对照中每步的输入、输出与判定依据
go test -v -run TestRandomAgainstNaive ./demand/

# 历史长度两档对照（10 万 vs 100 万条上报），验证评估开销与历史无关
go test -v -run TestEvalCostIndependentOfHistory ./demand/

# 结构断言：台账条目数恒有界
go test -v -run TestBoundaryRetentionBounded ./demand/

# 单次评估开销基准
go test -bench=BenchmarkReport -benchmem -run=NONE ./demand/

# 静态检查
gofmt -l demand/ && go vet ./demand/
```
