# 对象逻辑删除与可见性服务 — 设计说明

包路径：`ontology/lifecycle`（Go 1.26）。

## 1. 状态机

四种互斥状态，转换只能沿固定方向发生：

```
                 delete(deadline>now)
   ┌────────┐ ─────────────────────────▶ ┌──────────────┐
   │ alive  │                             │    grace     │
   │        │ ◀───────────────────────── │ (待撤销宽限) │
   └────────┘        undo (now<deadline)  └──────────────┘
        │                                        │ now>=deadline
        │ freeze(d>0)                            │ （系统惰性归档）
        ▼                                        ▼
   ┌──────────────┐  now>=freezeDeadline   ┌──────────────┐
   │    frozen    │ ─────────────────────▶ │   archived   │
   │ (保留期冻结) │   （系统惰性/显式归档） │  （终态）     │
   └──────────────┘                        └──────────────┘
```

| 请求 | 合法来源状态 | 结果 |
| --- | --- | --- |
| `Delete(deadline)` | `alive` | → `grace`，记录宽限截止时刻 |
| `Undo` | `grace` 且 `now < deadline` | → `alive`，抹除本次删除对查询的影响 |
| `Freeze(d)` | `alive` 且 `d > 0` | → `frozen`，截止时刻 = `now+d`，一次性确定 |
| `Archive` | 到期由结算进入 `archived` | 幂等成功 |

`archived` 是终态，任何转出都被拒绝。

### 1.1 到期处理：惰性结算（lazy settlement）

需求规定“截止时刻恰好到达而未撤销，须在之后下一次任何涉及该对象的操作中
转入已归档，不消耗调用方额外请求”。实现采用惰性结算而非后台定时器：

- 服务内部持有一份**物化当前状态**（`record.state` + 两个截止时刻）；
- 每次操作（含查询、出边查询、被拒绝的转换）进入临界区后先调用
  `settleLocked`：`grace/frozen` 且 `now >= deadline` 即落为 `archived`；
- 该动作不修改系统时钟（时钟只能由外部推进，见 `Clock`），
  对被拒绝的转换也照常结算（拒绝的是调用方动作，不是时间的流逝）。

临界时刻语义统一为 `now >= deadline` 即到期：截止时刻前一纳秒仍可撤销，
截止时刻本身撤销即报第 2 类错误（来源状态已不再允许），
随后对象为 `archived`。冻结期同理：前一纳秒撤销/归档报第 4 类，
恰好到期时显式 `Archive` 放行。

### 1.2 被放弃的方案

- **后台定时器/定时任务扫描**：需要额外调度器，时钟与状态更新分散在两个
  线程，测试里无法精确复现“恰好到达”；且空转扫描浪费。放弃，改为惰性结算。
- **宽限期接受调用方提前显式归档**：会产生 `grace→archived` 的调用方方向，
  与“只能由系统在到期时归档、撤销是宽限期内唯一出口”的语义冲突。放弃：
  宽限期内 `Archive` 报第 2 类错误，归档只可能由到期结算产生。
- **每次查询回放全部转换历史**：实现简单但历史读取量 O(n)，直接违反需求 9。
  降级为仅供测试的 `NaiveReference`，生产路径只读物化状态。
- **每条出边各自带删除状态**：允许边独立隐藏，违背“边的可见性完全跟随源
  对象”。数据模型里边没有任何状态字段。

## 2. 可见性规则

| 身份 | alive | grace | frozen | archived |
| --- | --- | --- | --- | --- |
| 一般使用者 `user` | 可见，返回属性 | 视为不存在 | 视为不存在 | 视为不存在 |
| 数据管理员 `admin` | 全部可见 | 可见（含属性/宽限截止） | 仅状态 + 冻结截止时刻，**属性强制不返回** | 可见（含属性） |

对象不存在时，两种身份都得到 `Exists=false, Visible=false`（不存在属于
系统事实，不按身份区分）。

出边链接（`Edge`）无删除状态字段。`ViewEdges` 与 `GetView` 使用同一套
来源状态判定：源对象对某身份不可见 ⇒ 全部出边不可见。`ViewWithEdges`
在同一临界区内成对返回二者，保证同一次查询不可能对对象与边得出互相
矛盾的结论。

## 3. 错误模型与判定次序

四类哨兵错误（`types.go`），互斥且按固定次序只报第一类：

1. `ErrObjectNotFound` 对象实例不存在；
2. `ErrInvalidTransition` 请求方向不被当前（结算后）状态允许；
3. `ErrInvalidTime` 宽限截止时刻 `<= now`，或冻结时长 `<= 0`；
4. `ErrFrozenNotExpired` 冻结未满时撤销或归档。

次序在代码中是结构性的：`mutateLocked` 先查存在性，再惰性结算，
然后回调内依次判“方向 → 参数 → 冻结保护”。因此：

- `frozen` 上再次 `Freeze`，即使传入非法时长也先报第 2 类；
- 不存在对象配非法参数，仍只报第 1 类；
- `frozen` 未满的撤销/归档，方向本身被视为“等待冻结期满”的情形，
  报第 4 类而不是第 2 类（测试 `TestErrorOrderFixed` 固定该次序）。

任何拒绝都不写状态、不改截止时刻；日志中拒绝条目恒有
`StateBefore == StateAfter`。

## 4. 并发与线性化

`Service` 用单把 `sync.Mutex` 串行化所有读写；状态、截止时刻、审计序号、
对象与边集合都只在持锁期间访问。每个公共操作整体处于临界区（包括
“读取时钟 → 结算 → 判定 → 追加审计 → 写日志”），因此：

- 所有操作的效果等价于某个全局顺序的串行执行（可线性化）；
- 查询不会观察到“两个状态之间”的中间形态；
- 不存在对已归档状态的重复结算（到期归档在审计中只出现一条，
  见 `TestConcurrentFreezeExpirySettlesOnce`）。

时钟是外部依赖（`SystemClock` / `FakeClock`），服务只读 `Now()`，
永不写时钟，所以“被拒绝的转换不得修改系统时钟”由构造保证。

单锁的取舍：当前规模下单锁最简单且可证明正确；争用成为瓶颈时可改为
按对象 ID 分片的锁，结算与审计序号保持各自临界区即可，对外语义不变。

## 5. 历史复杂度与可验证证明

- 生产判定路径只读取一条物化记录（当前状态 + 两个截止时刻），
  **不读取** `AuditLog`。`AuditLog` 接口只有 `Append`，没有读取方法，
  生产代码在类型层面就无法扫历史。
- `CountingAuditLog` 包装审计日志，统计任何路径读到的历史条数。
  `TestVisibilityTouchesNoHistoryRecords` 先制造 100+ 条转换历史，
  再在多个时点反复查询并断言观测窗口内历史读取增量恒为 **0**，
  与历史长度无关——该断言随测试运行可复现核对。
- 同一测试对朴素实现计数：`NaiveReference.stateAt` 每次都遍历全部事件，
  读取量 == 事件条数（线性）。两套实现信息量的差异在测试里直接可比对。

## 6. 审计与操作日志

- `AuditLog`（只追加）：每次**被接受**的状态转换一条 `Transition`
  （序号、对象、时刻、from/to、类别、截止时刻、操作者）。到期结算记
  `auto-archive`；恰好到期的显式 `Archive` 复用该结算，不额外追加事件，
  所以归档事件全局恰好一次。
- `Logger`：每次操作（含被拒绝、对象不存在）一条 `LogEntry`，
  记录操作、对象、身份、输入参数、判定时刻、结算前后状态、
  accepted/rejected 输出与错误文本。

## 8. 关键取舍小结

1. 到期用惰性结算而非定时器：确定、可测、无额外请求。
2. 物化当前状态 + 只追加审计：查询 O(1) 历史触达，审计仍完整。
3. 单把互斥锁：以最小代价获得可线性化，分片留作未来优化。
4. 冻结对象对管理员只暴露状态与截止时刻：属性在返回路径上被显式抹除，
   而非依赖调用方自觉不读。
5. 朴素回放实现保留在生产包内但不被生产代码引用，作为随机对账的
   “独立维护的模型”，与生产实现共享同一组类型与错误语义。
