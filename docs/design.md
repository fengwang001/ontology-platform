# 厢式货车配载与卸货顺序校验系统 — 设计说明

## 1. 问题与建模

车厢为从车头到车尾编号 `1..Z` 的有序分区，每区有载重上限（克）与容积上限（cm³）。
货物有编号、重量、体积、卸货停靠点序号（1 最先卸）与四类类别（普通、食品、易燃、氧化）。
所有量为正整数，**恰好等于上限视为允许**。

四类装货约束：

1. **顺序（后卸靠前）**：任意两件在车货物，停靠点序号更小（更早卸）者所在分区编号
   不得小于序号更大者所在分区编号。分区 1 为车头，故早卸货物必须位于编号更大（靠车尾）
   的分区；编号相等（同区混装）允许，**区内不做顺序要求**。
2. **隔离**：同区不得同时有易燃与氧化；食品不得与易燃、氧化任一同区；其余不限。
3. **载重**：区内重量和 ≤ 载重上限。
4. **容积**：区内体积和 ≤ 容积上限。

装货选择：在满足全部约束的分区中选**编号最小**者，结果确定。

## 2. 模块划分

代码按职责拆分为相互协作的小模块（`van` 包内）：

- `types.go` / `types_string.go`：领域类型（`Cargo`、`Category`、`RejectReason`）、
  错误哨兵与可读文案。
- `compartment.go`：`zone` 分区聚合状态。维护重量和、体积和、区内停靠点最小/最大值、
  类别存在性位图、区内货物映射。`put` 为 O(1) 增量更新；`remove` 后按区内剩余货物重建聚合。
- `placement.go`：纯判定逻辑。`compatible` 类别兼容矩阵；`firstViolation` 返回某分区对
  候选货物的**首个**不满足约束（顺序→隔离→载重→容积）。
- `service.go`：`Service` 门面。持有分区切片、货物编号→分区映射、已到达停靠点；
  用一把 `sync.RWMutex` 保证并发安全；实现单件/批量装货、卸货、查询。
- `model/naive.go`：**独立编写**的朴素参照模型（见 §7），不共享 `van` 内部代码。

## 3. 关键取舍：顺序约束的聚合判定

题面顺序约束是“任意两件货物”的成对关系。若朴素地为每个候选分区枚举全部在车货物，
复杂度为 O(Z·N)。我们将其化简为只依赖每分区两个标量（`minStop`、`maxStop`）。

设候选货物停靠点为 `c.Stop`，拟放入分区 `k`。跨分区要求（同区豁免）：

- 对所有在 `k` 之前（更靠车头，编号 `< k`）的分区 `i`：
  其中货物都应是“同停靠点或更晚卸”，否则会出现“早卸货反而更靠前”。
  等价于 `minStop(i) ≥ c.Stop` 对全部前置分区成立。
  实现中只需检查“最靠近车尾的前置分区”的 `minStop`（前缀最小值单调），
  但为直观起见代码扫描全部前置分区，仍为 O(Z)。
- 对所有在 `k` 之后（更靠车尾，编号 `> k`）的分区 `j`：
  其中货物都应是“同停靠点或更早卸”，即 `maxStop(j) ≤ c.Stop`。

同区不检查顺序（区内混装、区内顺序不作要求）。

**放置判定只读取分区级聚合标量，从不枚举 `zone.items` 里的任何货物记录**，
因此对车上已装货物总数 N 不敏感：`Service.chooseZone` 为 O(Z) 时间、O(1) 额外空间、
0 次堆分配。基准实测（10 个分区，必然被容量拒绝的候选）：

```
BenchmarkChoose_100Cargo-20    ~88 ns/op   0 B/op   0 allocs/op
BenchmarkChoose_10000Cargo-20  ~88 ns/op   0 B/op   0 allocs/op
```

货物总数扩大 100 倍，单次放置判定耗时与分配完全不变。`TestPlacementZeroAlloc`
用 `testing.AllocsPerRun` 对 100 件与 10000 件两种规模断言每次调用 0 次分配，
可随构建反复验证。

> 推导推论：在一个已满足约束的布局上，纯“顺序冲突”作为**整体**失败原因不会出现——
> 总能找到顺序可行的分区（最靠后可混装的边界分区），实际失败一定还伴随隔离/超重/超容。
> 但“顺序”仍作为**单个分区的首个不满足约束**参与严重度归并。

## 4. 失败原因归并

每个分区按固定优先级顺序返回首个不满足约束：
`顺序冲突 > 隔离冲突 > 超重 > 超容`。枚举常量即按此严重度从高到低编号。
整体原因取所有分区首因中**严重度最低**的一类（枚举数值最大者）。
因此“只要有分区仅因容积不足而失败，就报超容”。判定从编号最小分区开始，
遇到第一个四约束全过的分区即选定，天然满足“选编号最小可行分区”。

## 5. 并发、事务与拒绝优先级

- 单一 `sync.RWMutex`：写操作（装/卸）取写锁，查询（`Remaining`/`Location`/
  `ArrivedStop`）取读锁并返回**拷贝**。任一时刻的状态都是某个已完成操作之后的一致快照，
  读者绝不会读到批量装货进行到一半的状态。
- **批量装货全有或全无**：参数预检（正整数、类别合法）与批内编号重复（判为参数非法）
  在锁外完成；取锁后逐件试放并记录落点，任一件失败则按记录逆序 `remove` 回滚，
  返回最小下标失败件（`BatchError.Index`）及其原因。
- 拒绝优先级严格为：参数非法 → 编号重复 → 停靠点已过 → 四类约束失败。
  被拒绝的操作在任何写之前返回，状态零变化。
- **卸货状态机**：
  - `stop ≤ 已到达最大序号` → `ErrProcessed`（已处理），无状态变化；
  - 越级且车上仍有更小序号货物 → `ErrOrderError`，**不推进**进度；
  - 空停靠点 → 成功、无卸下货物、推进进度；
  - 正常 → 卸下该停靠点全部货物（返回升序编号）并推进进度。
- **中途装货**：开始卸货（`arrived>0`）后，新货停靠点必须 `> arrived`，
  否则 `ErrStopPassed`，该检查先于四类约束。

## 6. 确定性

放置只依赖当前分区聚合与候选货物，无随机、无 map 迭代顺序依赖、无时钟输入。
相同操作序列在相同分区定义下重放，逐件得到完全相同的分区编号
（`model/diff_test.go::TestDeterministicReplay` 断言）。

## 7. 被放弃的方案

- **每件货物逐条枚举的 O(Z·N) 判定**：直观但随车上货物数增长，不满足
  “单件判定考察的在车记录数不得随总数增长”。降级为参照模型保留在 `model` 包，
  专门用于差分测试，不进入生产路径。
- **每分区一把锁 / 细粒度锁**：可提高写并发，但批量回滚需跨分区加锁，易死锁且
  顺序判定跨分区，收益不抵复杂度。单把锁配合读锁足以保证线性一致与快照语义。
- **MVCC / copy-on-write 快照**：能提供无锁读，但本场景读多为轻量聚合、写需强一致，
  引入版本链与 GC 属过度设计。
- **在 loc 之外再维护停靠点→货物索引**：卸货会用到，但分区已有 `minStop` 与 `items`，
  卸货本就是低频批量操作，直接在分区内按 `Stop` 收集即可，避免冗余索引一致性问题。

## 9. 测试覆盖索引

- `van/van_test.go`：载重/容积恰等于上限与超一、类别兼容矩阵全组合、隔离冲突、
  四类原因严重度归并（顺序/超重、顺序/超容）、编号重复与参数非法、批量全有或全无、
  卸货顺序错误/空停靠点/已处理、中途装货与拒绝优先级。
- `van/order_check_test.go`：顺序约束使靠前分区后来不可行的跨区布局。
- `van/concurrency_test.go`：并发读快照一致、批量并发原子性，并在每次成功写后
  校验四类不变量（容量、跨区顺序、隔离、账实一致）。
- `van/placement_bench_test.go`：放置判定 0 分配、不随货物总数增长。
- `model/diff_test.go`：独立朴素模型对照 200 条固定种子随机操作序列，逐步比对
  分区选择、错误类别、失败下标、剩余容量、定位与进度；日志含每次输入/输出/判定依据。
