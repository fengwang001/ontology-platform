# 对象实例存储与双时态可见性子系统 — 设计说明

## 模块划分

| 模块 | 包 | 职责 |
| --- | --- | --- |
| 存储与版本仲裁 | `store` | 版本链持久化、乐观并发仲裁、系统时间单调分配、逻辑删除、拒绝排序、WAL 与重放 |
| 双时态索引 | `index` | 单主键的双时态索引（持久化 treap）与历史重建 |
| 读写门面 | `service` | 对外读写接口、凭证格式解析、错误归一化 |

依赖方向：`service -> store -> index`，单向无环。`index` 只感知
`(bizStart, sys, seq)` 三元组，不感知业务内容；`store` 持有版本链本体，
索引查询返回版本号后到版本链取向量。

## 核心语义决策

### 业务时间区间在"可见前缀"内解析

版本的业务时间区间为 `[bizStart, 下一个更大的 bizStart)`，开区间端开放。
关键取舍：**"下一条记录"在查询系统时间 `sysQ` 决定的可见前缀
（sys ≤ sysQ 的版本集合）内确定**，而不是在全部已提交版本内确定。

理由：双时态查询的意义在于"站在系统时间 sysQ 那一刻能看到什么"。
若用全量已提交版本解析区间，那么一次新的追溯写入会改变过去系统时间
查询的答案（已发生的历史视图被未来篡改），回溯查询将失去意义，也无法
满足"重放同一操作序列得到完全相同查询结果"的确定性要求。该选择与
SQL:2011 双时态语义一致：系统时间维度的 as-of 结果对后续提交免疫。

在此决策下，查询规约可化简为可索引的形式：在可见前缀内，业务区间覆盖
`bizQ` 的版本，其业务起点必为可见集合中 `<= bizQ` 的最大起点 `s*`
（若 `s1 < s2 <= bizQ` 两个起点都存在，则 `s1` 的区间终点 `<= s2 <= bizQ`，
不可能覆盖 `bizQ`）；同一 `s*` 下取系统时间最晚者（后提交者覆盖先提交者，
两条记录都保留）。因此：

> 查询 = 系统时间数组二分定位可见前缀 + 业务起点有序集合前驱查找。

### 最早可追溯边界

"该主键已确认提交的最早可追溯边界"实现为**该主键已提交版本的最小业务
起点** `minBiz`。新写入的 `bizStart < minBiz` 被拒绝（相等允许，走覆盖
规则）。含义：主键的"史上最早事实"一旦确认即不可再向前追溯改写，
防止历史起点被无限前移导致区间结构失去锚点。首次写入无边界限制。

### 逻辑删除与复活

删除是 `KindDelete` 版本：占版本号、占系统时间、声明业务起点、无业务
内容。它在索引中与普通版本同等参与区间结构，命中时返回 `DELETED`
标记而非"不存在"。复活只是删除之后的一次普通写入（业务起点落在删除
区间内的任意位置）：若与删除版本业务起点相等，按"系统时间晚者覆盖"
生效；若更晚，则把删除区间截为 `[delBiz, resurrectBiz)`。删除前、删除
中、复活后三段由三个版本各自的区间自然表达，删除不被当成主键整体
失效（主键的最新版本指针、边界、索引全部继续工作）。

### 系统时间分配

系统时间取自可插拔 `Clock`（生产为 `RealClock` = UnixNano），并在主键
内做单调钳制 `sys = max(now, lastSys+1)`：同一主键内严格递增、绝不
回退，即使物理时钟回拨。被拒绝的写入不调用时钟、不占序号。

### 拒绝次序与原子性

写入路径按固定次序检查，只报第一个命中的原因：

1. 参数非法（对象类型/主键为空、`bizStart` 越界、凭证为负或服务层
   凭证格式不符 `v<N>`）；
2. 乐观并发凭证与当前最新版本号不一致；
3. 业务起点早于 `minBiz`。

全部检查在提交前完成；WAL 追加也在内存提交之前。任何拒绝都不消耗
版本号、不移动最新指针、不进入索引。

### 并发模型

每个主键一把互斥锁（实例表本身一把锁保护）。同一主键的写入在锁内
完成"读最新版本号 -> 校验 -> 提交"全过程，因此：

- 不可能出现两个写入基于同一前序版本都成功（第二个进入临界区时
  最新版本号已变，凭证校验必失败）；
- 全局效果等价于按锁获得顺序的串行执行；不同主键之间无共享状态，
  任意交错都等价于某个全局串行序；
- 重放确定性：提交序列完全由（操作序列, 时钟序列）决定。测试与重放
  使用 `FakeClock`；WAL 记录完整提交结果，`Replay` 按记录原样重建，
  版本链与查询结果逐位一致（`TestReplayDeterministic`、
  `TestDifferentialAgainstNaive` 验证）。

## 索引结构与查询复杂度证明

每个主键一棵 `index.Chain`：

- `sys[]`：已提交版本的系统时间，天然有序，二分定位可见前缀 `k`；
- `roots[]`：`roots[k]` 为前 `k` 次提交后的**持久化 treap** 根。
  treap 键为业务起点，值为该起点最新版本号；优先级由键经 splitmix64
  确定性导出（重放得到相同结构）。每次提交路径复制 `O(log n)` 个
  节点，旧快照全部保留，原地零修改。

单次查询 = 一次二分（`O(log n)`）+ 一次 treap 前驱下降（期望
`O(log n)`，随机 treap 期望高度约 `3·log2 n`）。与主键版本总数 `n`
无关线性增长，与对象类型下实例总数无关（每主键独立结构，实例表为
哈希定位 `O(1)`）。

**可验证方法**（不依赖重新遍历历史）：

1. `Chain.LastQueryVisited()` 精确统计单次查询访问的 treap 节点数。
   `TestChainQueryVisitedBound` 在 `n = 2^18` 个版本上执行 2 万次随机
   查询，断言最大访问节点数 `<= 6·log2(n)+10`（实测 40），且远小于
   `n/100`，从计数器层面排除线性增长。
2. `TestQueryCostIndependentOfInstanceCount` 在实例总数从 1 涨到
   20001 前后，对同一主键执行同一查询，断言访问节点数完全不变。
3. `TestDifferentialAgainstNaive` 用独立实现的线性扫描朴素模型在
   4000 个随机操作 + 收尾全坐标扫描下逐条对照，证明索引快路径与
   朴素语义逐位等价。

## 被放弃的方案

- **全量区间物化（写入时切割区间记录）**：写入时需回填既有版本的
  区间终点并产生额外的系统时间维修正记录，写路径复杂且仍需解决
  as-of 系统时间的快照问题；区间端点隐式推导已足够。
- **全量提交集上解析区间（解释 A）**：被否决，因为它让未来的追溯
  写入改变过去系统时间查询的答案，破坏回溯语义与重放确定性。
- **每次写入重建索引 / 查询时线性扫描**：写入 `O(n)` 或查询 `O(n)`，
  不满足查询开销约束；仅保留为测试中的对照模型。
- **全局单锁串行化所有主键**：简单但牺牲跨主键并发；每主键锁已
  足以保证等价串行序。
- **物理删除 / 主键级失效标记**：直接违反"记录必须保留"与"删除后
  可复活、三段历史可还原"的要求。
- **区间树（interval tree）**：区间端点本身由起点集合隐式决定，
  维护区间树是冗余的；前驱查找已把查询化简为 `O(log n)`。

## 本地验证方法

```bash
go test ./...            # 全量单测 + 差异对照
go test -race ./...      # 并发仲裁的竞态检测
go test -v ./service/ -run TestDifferentialAgainstNaive   # 查看逐操作日志
go test -v ./index/ -run TestChainQueryVisitedBound       # 查看复杂度上界实测
go run ./cmd/server      # 端到端演示（写入/删除/复活/回溯/WAL）
```

## 已知边界

- 持久化为 JSON Lines WAL + 全量重放恢复；未做快照压缩与增量检查点
  （恢复时间为 `O(历史长度)`），属于后续优化项。
- 内存占用为 `O(n log n)`（持久化 treap 路径复制），如需更紧的内存
  可换用持久化 B+ 树或定期合并快照，查询复杂度不变。
