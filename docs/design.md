# 多卷一致性组快照协调服务 — 设计说明

## 1. 目标与范围

协调若干“一致性组”的快照生命周期，覆盖：

- 组管理：2–16 个卷；每个卷最多属于一个组；成员增删仅在组空闲时允许。
- 快照三阶段：冻结中（`Freezing`）→ 已冻结（`Frozen`）→ 已结束（提交或中止后回到空闲）。
- 冻结中逐卷确认；已确认卷的新写入按到达次序排队，未确认卷照常应用。
- 最后一个确认的时刻即快照点；该刻一次性固化各卷截止点（已应用最大写序号）。
- 提交只在已冻结阶段允许，生成快照记录后解冻并按各卷到达次序排水；中止不生成记录，同样解冻排水。
- 两类超时自动中止（冻结截止、最长保持），与手工中止等价；边界取等有效、严格越过才触发。
- 所有操作携带单调时间戳；拒绝严格按“参数非法 → 时钟回退 → 超时检测 → 操作自身判定”排序。

## 2. 模块划分

实现位于 Go 包 `cg`，各文件职责单一、相互协作：

- `cg/errors.go`：可区分的错误类型 `Error` 与有序枚举 `Kind`
  （`InvalidArgument, ClockBackward, NotFound, Conflict, StateError,
  DuplicateConfirm, QueueFull`），以及 `KindOf`。
- `cg/types.go`：对外值类型（`Config`、`GroupSpec`、`Phase`、`WriteResult`、
  `SnapshotRecord`、查询视图）。
- `cg/volume.go`：单卷状态——写序号 `seq`、冻结队列 `queue`、容量；
  `apply` 立即应用、`enqueue/queueFull` 排队、`drain` 解冻后按序分配序号。
- `cg/group.go`：组与进行中快照的纯状态机——`begin`、`needsQueue`、
  `confirm`（含“是否最后一个确认”）、`dueAutoAbort`、`commit/abort`
  （统一走 `freezeAndDrain`）。
- `cg/coordinator.go`：并发与规则入口。单一互斥锁把所有操作串行化；
  `run` 是统一的判定次序骨架；组/卷注册与成员变更。
- `cg/coordinator_ops.go`：发起、确认、提交、中止、写入、只读查询等具体操作。
- `cg/trace.go`：决策日志接口 `Tracer` 与行式实现 `LogTracer`，逐条打印
  输入、输出、拒绝类别与判定依据（含自动中止原因）。
- `cg/cgtest/naive*.go`：**独立编写的朴素逐事件参考模型**，刻意不使用
  任何快速路径（线性切片扫描、无哈希捷径），从规范重新推导全部规则。

这种切分把“状态怎么变”（`volume/group`）与“什么时刻、按什么顺序允许变”
（`coordinator`）分开，便于分别测试和用独立模型交叉验证。

## 3. 关键数据结构与不变量

- `volume.seq uint64`：已应用写入数，初值 0；只有真正应用才自增。
  被拒绝（队满丢弃等）的写入绝不占用序号。
- `volume.queue []queuedWrite`：该卷冻结期间的 FIFO；`queuedWrite` 记录
  到达时刻与载荷，保证解冻后可按原到达次序重放并精确复现序号。
- `snapshot.pending int`：尚未确认的卷数，初值为成员数。
- `snapshot.confirmed map[string]bool`：已确认卷集合。
- `snapshot.cutoffs map[string]uint64`：只在“最后一个确认关闭冻结窗口”的
  那一刻做一次 O(m) 读取，固化为不可变快照点向量。

组不变量：`snap == nil` 表示空闲；非空闲时同一组最多一个快照。
卷不变量：每个卷至多被一个组的成员切片与全局卷表登记。

## 4. 判定次序（统一骨架）

所有操作进入 `Coordinator.run`，严格四段：

1. **参数校验**：非空标识、组规模 2–16、卷列表无重复、deadline ≥ 发起时刻。
   失败立即拒绝，**不推进逻辑时钟**，不留任何状态痕迹。
2. **时钟回退**：`t < lastTime` 报 `ClockBackward`，同样不留痕。
   通过后把 `lastTime` 置为 `t`；即使该操作随后被操作性原因拒绝，
   时间也已被接受（时间推进本身是事实）。
3. **超时检测**：在操作自身判定前，对其目标组执行 `timeout`。
   一旦 `t` 严格越过边界就自动中止（解冻排水），再继续本操作判定。
   这解释了“冻结截止后，对该组的任意操作（含只读查询）都会先中止”。
4. **操作自身判定**：如存在性、组冲突、状态、重复确认、队满等。

因此每类错误只报次序最靠前的一种；`Kind` 的数值顺序即优先级。

## 5. 时间与超时边界

- 冻结中：`t > deadline` 触发自动中止；`t == deadline` 的确认有效。
- 已冻结：`t > point + MaxFreezeHold` 触发自动中止；提交恰在
  `point + MaxFreezeHold` 有效。
- 采用严格不等号，边界时刻的成功操作先于超时判定（超时条件在该时刻为假）。
- 自动中止与手工中止都调用同一个 `freezeAndDrain`，行为完全等价；
  区别仅在日志里标注 `auto-abort: <原因>`。

## 6. 两类常数开销（可验证）

### 6.1 一次写入是否需要排队 — O(1)

`group.needsQueue(volID)`：

- 一次 `snap == nil` 判断；
- 一次阶段读取：`Frozen` 直接返回 true（逐卷无额外工作）；
- `Freezing` 下仅一次哈希查询 `confirmed[volID]`。

不遍历成员，也不读取任何队列长度以外的数据；`queueFull()` 是
`len(queue) >= cap` 的 O(1) 比较。证据见
`BenchmarkWriteQueueDecision`：成员 2/4/8/16 且该卷已积压 1000 条排队写入时，
判定耗时恒定在约 345 ns/op，且不随成员数或已排队数增长。

### 6.2 确认是否为最后一个 — O(1)

`snapshot.pending` 为未确认计数。每次 `confirm` 只做一次
`confirmed[id]=true`、`pending--` 与 `pending>0` 比较；`pending` 归零即最后
一个确认，与组大小无关。关闭窗口时为读取各卷当前序号做且仅做一次 O(m)
扫描（`cutoffs` 是规格要求的全量截止点，无法低于 O(m)）。证据见
`BenchmarkConfirmNonLast`：只计时确认本身时，成员 2→16 耗时基本恒定
（约 0.9–1.1 µs）。

> 排水（drain）对每条排队写入都是 O(1)，总量 O(Σ q_i)，这是应用每条
> 排队写入所必需的下界，不属于“是否排队 / 是否最后确认”的判定开销。

## 7. 并发与确定性

- `Coordinator` 用一把 `sync.Mutex` 串行化全部操作，因此并发调用等价于
  某个合法串行顺序；`go test -race` 下并发测试通过。
- 全部可观察结果只由“操作 + 时间戳”决定，无随机、无后台定时器
  （超时是惰性检测的时间推进结果）。相同操作序列重放得到完全相同的
  快照记录与写序号，见 `TestDeterministicReplay`。
- 超时不在后台线程触发，避免了“没人调用也突变”的不可复现性：
  自动中止总发生在“引起检测的那个操作”内部、且在其自身判定之前。

## 8. 被放弃的方案

- **后台定时器/看门狗**：会引入真实时间与异步调度，使同序列重放不可复现，
  且无法保证“发生在引起检测的操作之前”。改为在每次携带时间的操作内惰性
  判定，天然可复现。
- **确认时遍历成员判断是否全部确认**：O(m)，不满足常数要求；改用
  `pending` 计数，一次自减与比较即可。
- **写排队判定扫描成员或全组队列**：随 m、Σq 增长；改为阶段读取 +
  单次哈希查询 + `len/cap` 比较的 O(1) 路径。
- **提交时才回溯计算截止点**：截止点是“最后确认那一刻”的已应用最大序号，
  延迟计算会被后续未确认卷的写入污染。改为在关闭冻结窗口的瞬间一次性固化。
- **给“已结束”保留显式阶段对象**：提交/中止后组即空闲，保留终结快照对象
  会与“同一时刻最多一个进行中快照”的判定纠缠。改为结束即清空 `snap`，
  最近一次**已提交**记录单独保存在 `lastSnap`（中止不留记录）。
- **细粒度每卷锁**：虽然可提高并行度，但跨卷快照点需要全局一致判定，
  锁顺序复杂且难证明可串行化。单锁简单且足够表达规格，并用基准保证热路径
  判定仍为常数开销。

## 9. 本地验证方法

```bash
# 需 Go 1.26+；若 go 不在 PATH：
export PATH=$PATH:/usr/local/go/bin
# 沙箱环境下构建缓存目录可重定向：
export GOCACHE=/tmp/gocache GOTMPDIR=/tmp

go test ./...                       # 单元 + 朴素模型随机对照
go test -race ./...                 # 竞态检测
go test -v ./cg/                    # 查看每个边界用例
go test -bench=. -benchmem ./cg/    # 两个常数开销的可验证证据
gofmt -l . && go vet ./...
```

随机对照（`TestRandomDifferential`，默认 120 个种子、每种子 240 个随机
操作）会把真实实现与独立朴素模型在每个事件后做全量状态比对（每卷写序号、
排队数、阶段、最近快照记录的快照点与各卷截止点），并用 `LogTracer`
逐条打印操作输入、输出、拒绝类别与判定依据。快速冒烟可用 `go test -short`。
