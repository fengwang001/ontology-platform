# 分块快照完整性校验与跨类型聚合导出 — 设计说明

## 1. 目标与范围

本体快照按对象类型（person、org、…）拆分为多个**相互独立的块文件**。加载方在不
信任任何一方的前提下，仅凭落盘字节完成三类判断：

1. **块级完整性**：每个块自己的内容是否被篡改（SHA-256）；
2. **块级数量一致性**：块头声明的记录条数与实际可解析条数是否一致；
3. **跨块引用**：类型间链接字段能否在目标块中解析，且在目标块不可信时给出
   **保守（不可判定）**结论，而不是武断地判为悬空或有效。

聚合视图是“全有或全无”，但单块的部分可用性独立保留。

## 2. 磁盘格式（见 `docs/format.md`）

导出目录：

```
manifest.json          # 本次导出覆盖的类型清单
chunk_<type>.json      # 每个对象类型一个块
```

块信封字段：`type`、`version`、`declared_count`、`payload_hex`、
`payload_sha256_hex`。校验和认证的对象**恰好是**随后解码、解析的载荷字节：
载荷为规范 JSON（`encoding/json` 序列化记录切片），以十六进制存放。

### 关键取舍

- **载荷与信封分离、校验和只覆盖载荷**：被认证的字节就是被消费的字节，篡改后
  要么 hex 解码失败、要么 SHA-256 不符，不可能“损坏的字节解析出合法数据且校验
  通过”。放弃的方案：把整个文件做 checksum——无法单独声明“头部条数”这一需要在
  认证后才使用的字段，且任何信封演进都会使历史快照失效。
- **十六进制而不是裸 JSON 嵌套**：便于按字节翻转模拟损坏（`FlipPayloadByte`），
  且“认证域边界”明确。放弃的方案：JWS/签名信封——本需求只防意外损坏/篡改检测，
  不引入密钥分发；签名是正交增强，可在信封加签名字段而不改变判定模型。
- **manifest 只描述覆盖范围**：范围外请求（最高拒绝优先级）由此判定。manifest
  自身损坏属于“导出不可读”（I/O 错误），不与五类业务错误混报。

## 3. 判定流水线（严格顺序）

对每次请求重新从磁盘读取（只读、无缓存、无共享可变状态）：

1. **完整性阶段（块内、互相独立）**
   - 文件不可读 / 信封不可解析 / 类型名不符 / hex 不可解码 / SHA-256 不符 /
     载荷无法解析为记录数组 → `checksum_failed`。
   - 该结论只取决于本块字节，其他块的任何状态都不能改变它。
2. **数量阶段**
   - `len(parsed) != declared_count` → `count_mismatch`，**整块不可信**，
     已解析出的记录全部丢弃（`Records=nil`），即使其中部分记录单独看起来完好也
     不采信，也不产出任何引用判定。理由：截断与虚增不可区分，局部采信会掩盖
     “丢失了多少、丢了谁”。
3. **引用阶段（仅对两阶段都通过的块）**，对每条链接独立判定：
   - 目标类型不在导出覆盖范围 → `dangling`（覆盖范围内不存在任何匹配对象）；
   - 目标块存在但状态非 ok（校验失败或数量不一致）→ `target_untrusted`
     （悬空与否**不可判定**，既不默认悬空也不默认有效）；
   - 目标块可信 → 在目标块 id 哈希集合中做 O(1) 成员判定，存在=`resolved`，
     不存在=`dangling`。

**双向引用**：两个方向是两条独立的链接出现（occurrence），各自走一遍上述判定；
一个方向有效绝不是另一方向有效的证据。

## 4. 请求模型与拒绝优先级

- `Verify(dir)`：返回完整 `Report`（每块状态 + 每条引用判定），不做请求级拒绝。
- `ExtractBlock(report, type)`：只要该块自身两阶段通过即可取出记录——**部分可用
  性**，与聚合能否生成、外发引用是否悬空无关。
- `LoadType(type)`：等价于单类型 `Aggregate`，要求该块两阶段通过**且**其全部
  外发引用可解析。
- `Aggregate(types)`（空 = 覆盖范围内全部类型）：所有参与块都两阶段通过且所有
  外发引用可解析才产出视图；否则返回 `LoadError`，按固定优先级排序、逐条报告
  命中块与原因：

```
out_of_scope > checksum_failed > count_mismatch
             > dangling_reference ≈ target_untrusted（两类并列、分别报告、不混报）
```

命中范围外即短路，不再对该请求做低优先级诊断；其余层级会把所有命中项都列出
（确定性排序：优先级 → 类型 → 记录 → 字段）。五类错误用 `ErrorKind` 明确区分，
`target_untrusted` 永远不会被更尖锐的 `dangling` 覆盖。

### 放弃的方案

- “只要块校验通过就允许加载、悬空引用仅告警”：会让调用方在图不完整时静默使用
  残缺聚合。改为：单块取用走 `ExtractBlock`（显式、局部），请求级加载严格拒绝。
- “目标块不可信就判悬空”：这是武断结论，损坏的块里可能恰好存在目标对象；规范
  明确要求保守，因此引入独立的 `target_untrusted` 类别。

## 5. 并发、幂等与可重复性

- `Loader` 不持有任何按导出变化的状态；`Verify` 只做 `ReadFile` 与纯计算，
  不写、不移动、不删除任何文件 → 只读校验天然幂等，被拒绝的请求不可能改变导出
  或既有结论。
- 同一份未变动的落盘导出是确定性纯函数：遍历顺序按类型排序，引用按记录/字段
  出现顺序判定，findings 稳定排序 → 多 goroutine 并发、多轮重复得到字节级一致的
  规范化结论（测试 `TestConcurrentRepeatedVerifyDeterminism`，32×5 并发，并在
  前后对目录做字节指纹比对）。
- 决策日志 `DecisionLogger` 按次请求独立传入，内部加锁；不参与判定语义。

## 6. 与规模无关的性能要求及证明方式

- 每个可信目标块的 id 集合构建一次：`idIndex`（线性探测开放寻址哈希表，负载率
  ≤0.5，FNV-1a）。构建 O(N) 一次；**单次成员判定期望 O(1)，检查的槽位数不随
  目标块总记录数 N 线性增长**。
- 可验证方式有两层：
  1. 代码层面：`idIndex.ProbeCount()` 暴露建表后每次 `Add/Has` 的实际槽位探测
     总数，判定逻辑中不存在对目标切片的遍历（朴素模型里才故意保留线性扫描）。
  2. 测试层面：
     - `TestSingleLookupProbeBound`：N=16384 时一次查询仅个位数探测（线性扫描
       需要 16384 次），直接打印对照；
     - `TestMembershipLookupIsConstantProbeCount`：N 从 64→1024→16384 放大 256
       倍，平均每查探测次数保持 ~2 不随 N 增长。
  3. 差分层面：`TestDifferentialVsNaiveModel`（300 组随机导出×随机损坏组合）把
     真实实现与一个**独立编写的朴素线性扫描校验模型**逐块、逐引用比对结论。

## 7. 日志

每次判定都经 `DecisionLogger.Log(stage, input, output, basis)` 记录“输入 / 输出 /
依据”，`go test -v` 与 demo 均打印。阶段：`manifest`、`checksum`、`count`、
`refs:skip`、`ref`。

## 8. 本地验证方法

```bash
export PATH=$PATH:/usr/local/go/bin GOCACHE=/tmp/gocache
gofmt -l .
go vet ./...
go test -race -v ./snapshot/
go test -coverprofile=/tmp/cov ./... && go tool cover -func=/tmp/cov
go run ./cmd/snapshotdemo -damage targetcount   # none|flip|count|dangle|targetcount
```

测试覆盖（只列覆盖面）：

1. 数量不一致块内部分记录本身可解析/校验，但整块不得采信；
2. 目标块不可信时引用的保守结论（不是悬空也不是有效）；
3. 聚合视图整体不可生成时，已通过校验的单块仍可取用；
4. 双向跨块引用两个方向独立判定；
5. 多次并发加载结论一致、可重复，且导出字节不被修改；
6. 与独立朴素模型对照随机构造的损坏组合（300 轮种子）；
7. 日志打印每次判定的输入、输出与依据；
8. O(1) 成员判定的探针计数验证。
