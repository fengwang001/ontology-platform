# 门诊药房处方调剂：库存预留与欠药补发系统 — 设计说明

## 1. 模块划分

```
pharmacy/
  types.go    公共类型：配置、处方/药品查询结果、状态枚举、常量（有效期 72h、数量上限等）
  errors.go   七类可区分错误，声明顺序即报告优先级
  engine.go   引擎核心：逻辑时钟、事件推进、回滚日志、预留/欠药/终止的共用机制
  ops.go      公开操作：登记、入库、受理、取药、取消、两个查询（参数校验在此）
  list.go     欠药队列（侵入式双向链表，unlink 保留指针以支持回滚）
  heap.go     事件最小堆，按 (时刻, 创建序号) 排序，支持任意删除（回滚用）
  debug.go    Snapshot / CheckInvariants：可验证性接口
  naive/      独立朴素模型（全量扫描 + 整体深拷贝），仅用于差分测试
  *_test.go   单元测试、差分测试（≥1500 组）、性能证明测试、两档规模基准
```

职责流向：`ops.go` 做参数校验（保证错误优先级）→ `engine.run` 做时钟检查、
事件推进、执行、失败回滚/成功走钟 → 领域逻辑（`allocate`、`terminate` 等）
只操作 `list.go`/`heap.go` 提供的数据结构。

## 2. 关键设计取舍

### 2.1 逻辑时钟 + 懒推进（而非后台定时器）

“失效与再分配随时间自然体现、不依赖任何调用触发”用**懒推进**实现：所有观察
（操作与查询）都先调用 `advance(now)`，把不晚于 `now` 的事件按 `(时刻, 创建序号)`
顺序处理完，再执行操作。由于系统的全部可观察行为都经过 `advance`，其结果与
“时间连续流动、事件到点即触发”不可区分，且完全确定、可重放。

- 连锁：再分配产生的新预留失效时刻为 `起始+R+1`，若仍不晚于 `now`，堆循环自然
  接续处理，无需特殊代码。
- 同时刻事件按创建序号（FIFO）依次处理，重放结果完全相同。

**放弃的方案**：真实定时器/后台 goroutine —— 结果依赖调度，无法精确复现，
也无法满足“相同操作序列重放得到完全相同的结果”。

### 2.2 回滚日志（journaling）实现“被拒绝的操作不改变任何状态与时钟”

难点：拒绝判定（如整单缺药、无有效预留、取消已自然过期的处方）依赖 `now`
时刻的事件推进结果，而被拒操作连事件推进的效果都不得留下。

方案：操作进入 `run` 后开启日志，之后**所有**状态变更（计数器、标志位、
链表链接、堆增删、map 插入、事件序号）都先记录逆操作；任一环节返回错误即
逆序回放。链表 `unlink` 保留节点的前后指针，使重新链接是 O(1) 的纯指针恢复。

**放弃的方案**：
- 只读预检（不推进事件直接判定）：对“整单缺药”需要 `now` 时刻的可用量，
  等价于另写一套投机执行，复杂度更高且易与主逻辑不一致；
- 整体深拷贝（朴素模型采用了它）：每次操作 O(状态规模)，不满足性能要求。

### 2.3 欠药队列：每药一条 FIFO，作废/满足即摘除

欠药登记次序为“先按处方受理时刻，再按受理先后”。由于时钟单调，受理时刻
非递减，**插入顺序即分配顺序**，每药一条 FIFO 队列即可，无需排序。

关键：作废（过期/取消）与满足的欠药行在**发生时**即从队列 O(1) 摘除
（行内保存队列节点指针），因此队列中永远只有活的欠药行：

- 到货/失效再分配只扫描当前活欠药行，且首个分到 0 的行即终止扫描
  （可拆零可用量为 0、不可拆零不足一盒时，后续行同样分不到）；
- 欠药总量是药品上的 O(1) 计数器，登记/分配/作废时维护。

**放弃的方案**：懒删除（扫描时跳过死节点）—— 一次到货会扫过全部历史死
节点，开销随历史处方总数增长，违反要求。`TestVoidedBackordersRemovedEagerly`
证明：2 万条作废欠药行后，到货扫描步数为 0。

### 2.4 事件堆按 (时刻, 创建序号) 排序

同一时刻的预留失效与处方过期按创建先后处理，保证确定性。失效的预留/已终止
处方的事件采用惰性跳过（弹出时检查 `active`/`status`），每个事件只进堆一次、
出堆一次，摊还 O(log n)。

### 2.5 并发：全局互斥锁

所有公开方法持有同一把 `sync.Mutex`，并发调用等价于锁的获得顺序这一串行
顺序，天然满足“等价于某个串行顺序”。`go test -race` 验证无数据竞争，
并发压测后 `CheckInvariants` 通过。

**放弃的方案**：按药品分锁 —— 一次操作涉及多药品（整单受理、处方过期释放
多行）与全局时钟，锁序复杂且收益不明；当前瓶颈不在锁。

### 2.6 查询也是操作

查询带 `now`、推进事件并走钟（被拒绝的查询同样不改变任何状态）。这样
“状态在某时刻的样子”有唯一定义，差分测试可以逐步比对。

## 3. 语义要点（与规格逐条对应）

- 预留失效时刻 = 起始 + R + 1（第 R 分钟仍有效）；处方失效时刻 = 开具 + 4320 + 1。
- 不可拆零取整：可用量 ≥ ⌈d/box⌉·box 时预留该取整量（**多出不算欠药**），
  否则预留 ⌊avail/box⌋·box（可为 0）；欠药 = max(0, d − 预留)。
- 再分配（到货/失效/过期/取消触发）使用与受理完全相同的 `reserveAmount` 规则，
  新预留起始时刻 = 触发时刻。
- 整单发放：任一行 `reserveAmount < 需求` 即整单拒绝（缺药），无副作用。
- 取药取走全部有效预留；欠药行保持欠药；全部行满足（含取整）且已发放则完成。
- 过期/取消：先作废自身欠药行，再释放自身有效预留并分配给**其他**处方的
  欠药行（自身欠药已作废，自然不会分到）。
- 错误优先级：参数非法 > 时钟回退 > 对象不存在 > 状态不符 > 处方过期 >
  缺药 > 无有效预留；参数校验在时钟检查之前，时钟检查在事件推进之前。

## 4. 性能：可验证的证明

### 4.1 基于内部计数的确定性证明（测试断言，非计时）

引擎维护 `Stats{EventsProcessed, ReservationsReleased, BackorderScanSteps,
ReservationsAllocated}`。测试在两档历史规模（1,000 vs 100,000 张历史处方）
下断言计数**完全相等且等于理论值**：

| 测试 | 断言 |
|---|---|
| `TestInboundReallocCostIndependentOfHistory` | 到货分配 25 单位给 5 条欠药行：扫描步数两档均为 4 |
| `TestExpiryReallocCostIndependentOfHistory` | 1 预留失效级联：事件 1、释放 1、新预留 3、扫描 4，两档一致 |
| `TestVoidedBackordersRemovedEagerly` | 20,000 条作废欠药行后到货：扫描步数 0 |

### 4.2 两档规模基准对照（`go test -bench`）

本机（linux/arm64）`-benchtime 20000x` 实测：

| 基准 | 历史=10,000 | 历史=200,000/300,000 |
|---|---|---|
| `BenchmarkDrugBackorderQuery` | 43.4 ns/op | 33.1 ns/op |
| `BenchmarkInboundReallocation` | 29.5 µs/op | 32.2 µs/op |
| `BenchmarkExpiryCascade` (K=500) | 625 µs/op | 682 µs/op |

两档差异在噪声范围内，与“开销不随历史增长”一致；严格证明以 4.1 的计数
断言为准（计时受缓存/调度影响，只作佐证）。

## 5. 测试与本地验证

```bash
go test ./...                 # 单元 + 差分(默认1500组) + 性能证明
go test -race ./...           # 竞态检测
go test ./pharmacy/ -run XXX -bench . -benchtime 20000x   # 两档规模基准
PHARMACY_FUZZ_SEQS=5000 PHARMACY_FUZZ_SEED=1 \
  PHARMACY_FUZZ_LOG=/tmp/fuzz.log go test ./pharmacy/ -run TestDifferentialFuzz
gofmt -l . && go vet ./...
```

- 单元测试（`engine_test.go`）：取药窗口第 R 分钟/晚一分钟、有效期恰等于、
  取整向上/向下与多出不算欠药、整单拒绝无副作用、连锁失效与再分配、
  欠药先到先得与同时刻并列、过期与取消释放后的分配、取药后欠药保持、
  错误优先级、被拒操作原子性（含事件推进不泄漏）。
- 差分测试（`fuzz_test.go`）：默认 1500 组随机序列（约 7.4 万步），每步
  比对正式实现与朴素模型的错误码、查询输出与**全量状态快照**，并校验全局
  不变量（可用量非负、已发放+有效预留 ≤ 累计入库、不可拆零整盒倍数、
  欠药计数/队列一致、每个有效预留恰有一个失效事件）。日志逐行打印
  每步输入、双方输出与判定依据。
- 确定性（`TestReplayDeterminism`）：同一序列两个实例重放，输出与终态一致。
- 并发（`TestConcurrentSafety`）：8 goroutine 混合操作后不变量保持。

## 6. 已知边界与取舍说明

- 处方与历史事件不物理删除（审计需要），内存随历史线性增长；所有**操作
  开销**不随历史增长（见 §4）。
- 事件堆中已失效事件的弹出摊还到其创建时刻之后的操作上，每个事件只弹出
  一次，不改变再分配复杂度的结论。
- 重复登记药品/重复受理处方归入“状态不符”（规格未单列，文档化于此）。
