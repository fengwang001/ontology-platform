# 批量导入校验钩子可见性子系统 — 设计说明

## 1. 目标与约束

子系统保证大批量实例导入时，每条记录的前置校验钩子看到的「同批次其他
记录」范围严格等于：**全局存储中已提交状态 + 本批次列表中排在它之前、
且已经通过前置钩子校验并应用的记录**。同时两种整体语义
（`AllOrNothing` / `BestEffort`）、批次级后置钩子、三类可区分错误的
优先级、确定性重放与可验证的可见性解析开销必须自洽。

代码位于 `batchimport/` 包，由三个职责分离的模块协作：

| 模块 | 文件 | 职责 |
| --- | --- | --- |
| 分批执行 | `runner.go` | 参数校验并行编排、按列表顺序触发钩子、提交/撤销、聚合报告 |
| 钩子触发与批内可见性 | `view.go`、`registry.go` 中的 `HookContext` | 分层覆盖视图、应用序号与可见上界、撤销日志、步数计量 |
| 错误归一化 | `errors.go` | 参数非法 / 前置钩子失败 / 后置钩子失败三类错误 |

`registry.go` 另含对象类型注册表与全局实例存储，是三个模块共享的领域模型。

## 2. 核心设计

### 2.1 暂存覆盖层 + 应用序号 + 可见上界

批次执行时不直接改写全局存储，而是写入批次私有的暂存覆盖层
（`staging`）。每个暂存条目带一个单调递增的「应用序号」`seq`，
覆盖层维护游标 `cursor`（已通过前置钩子并应用的条目数）。
第 i 条记录的钩子做 `Get(type,id)` 时：

1. 先查覆盖层：命中且 `seq < cursor` 才可见（单次哈希探测，O(1)）；
2. 未命中再穿透到全局存储（也是单次哈希探测）。

因此：

- 排在当前记录之后的条目要么尚未写入，要么序号 ≥ cursor —— 天然不可见；
  可见状态不是批次开始前的静态快照（之前的成功记录已可见），
  也不是整批完成后的最终状态（未来记录不可见）。
- 尽力而为语义下钩子失败的记录不调用 `apply`，`cursor` 不推进，
  它不计入后续记录的可见范围，最终提交时也不会进入全局存储。

### 2.2 提交与撤销

- **提交**：`AllOrNothing` 在全部前置钩子通过、批次级后置钩子也通过后，
  把覆盖层合并进全局存储；`BestEffort` 结束时合并所有成功条目。
  合并全程持有 `Registry.mu` 全局锁。
- **撤销**：覆盖层记录写入前状态的逆序日志（`journalEntry`：写入前
  该主键是否存在、旧值）。`rollback` 按应用的逆序回放：曾经存在则
  恢复旧值，否则删除条目。由于批次全程持锁、全局存储在提交前从未被
  触碰，逆序回放后覆盖层为空、全局存储原封不动，系统状态与批次开始前
  逐字节一致（`TestPostHookRollsBackWholeBatch` 等以最终快照断言）。

### 2.3 批次级后置钩子

仅 `AllOrNothing` 触发：所有记录通过前置钩子后，覆盖层即「整批都已
应用但尚未提交」的最终状态，后置钩子通过同一分层视图（此时 cursor 覆盖
全部条目）读到最终状态；涉及多个对象类型时按类型名字典序依次触发，
保证可重放。任一后置钩子失败 → `rollback` 整批（含全部单条记录）。
`BestEffort` 永不触发后置钩子。

### 2.4 两阶段执行与内部并发度无关

执行分为：

1. **参数校验阶段**（与顺序、钩子状态无关）：未知类型、空主键、未知字段、
   字段类型不符，可用任意 worker 数并行执行；同批次主键重复作为输入列表
   的静态非法属性在这一阶段统一检测（多组重复全部报告）。
2. **顺序阶段**（持全局锁、单线程）：按列表下标逐条做
   重复判定 → 前置钩子 → `apply` 推进游标，随后后置钩子与提交/撤销。

钩子可能依赖此前记录派生的、尚未确定的值（如聚合统计）。这类派生值
通过 `HookContext.Scratch()` 这个整批共享、按列表顺序增量更新的暂存区
维护（测试钩子 `sumPreHook` 即要求每条记录 amount 严格等于「可见前缀和
+1」）。由于读取与推进都发生在顺序阶段，无论参数校验阶段用多少
 goroutine，每条记录的钩子判定与最终清单完全一致
（`TestConcurrencyDeterminism` 以并发度 1/2/4/8/16 对照）。

### 2.5 跨批次串行等价

`Registry.mu` 是一把全局互斥锁，`Batch` 在整个顺序阶段（钩子 + 覆盖层 +
提交）期间持有它。并发发起的独立批次因此被赋予某个全序的临界区串行
顺序，最终效果等价于按该顺序逐一应用（`TestConcurrentBatchesSerializable`
以 12 个不相交主键并发批次断言 24 条全部落库）。同一批次重放（相同注册表
初始状态 + 相同列表）走完全确定的代码路径，逐条结果与最终状态相同
（`TestReplayDeterminism` 三次重放对照）。

### 2.6 错误归一化与优先级

`errors.go` 定义 `Kind` 三值（`KindInvalidParam` / `KindPreHook` /
`KindPostHook`）与归一化错误 `Error{Kind, Index, Reason}`，可用
`errors.As`（或 `AsImportError`）区分。拒绝严格按以下次序只报第一个命中：

1. 参数非法（字段类型、未知类型/字段、空主键、同列表主键重复）——
   `AllOrNothing` 下任何参数非法都在触发任何钩子之前拒绝整批；
2. 单条记录的前置钩子失败；
3. 批次级后置钩子失败（仅 `AllOrNothing`）。

`AllOrNothing` 因错误中止时 `Report.Err` 为第一个命中的归一化错误，
`Records[i].Reason` 同时标注各条记录自身的拒绝原因；`BestEffort` 的
`Err` 恒为 nil，每条结果（成功/失败/原因）独立给出，顺序与输入一致。

### 2.7 可见性开销的可验证证明

`staging.get` 对覆盖层与底层存储各做至多一次哈希探测，单次解析 O(1)，
与批次总长度无关；钩子若选择枚举可见主键（`VisibleIDs`），成本与
「实际可见记录数」同阶。覆盖层内置步数计数器 `steps`，每条记录钩子
调用前后的差值记录到 `RecordResult.VisibilitySteps`，即该记录实际
命中的已暂存记录数：

- `TestVisibilityCostIndependentOfBatchLength`：批次长度 N 取
  20/160/1280/5120，末条记录固定访问 3 个已暂存主键，
  `VisibilitySteps` 恒为 3；不访问视图的记录恒为 0。
- `TestVisibilityStepsScaleOnlyWithAccessedRecords`：N 固定为 400，
  实际访问数 k 取 1/4/16 时步数恰好为 1/4/16。

两个方向共同证明：步数只随实际访问数变化，不随批次总长度变化。

## 3. 关键取舍

- **单把全局锁而非行级/类型级锁**：规格只要求跨批次最终效果等价于某个
  全局串行顺序，单锁实现最简单、可证明、无死锁面；代价是批次之间完全
  串行。批次内大量 CPU 工作（字段校验）在锁外并行，锁内只保留必须有序的
  钩子与提交。
- **写入暂存覆盖层而非「先改后补偿」**：全局存储在提交前完全不被触碰，
  撤销只需丢弃/逆序回放覆盖层，从机制上杜绝「撤销后残留」，也避免了
  撤销钩子、补偿动作等额外语义。
- **派生值交给钩子通过 Scratch 自维护**：平台不内置聚合引擎。钩子按顺序
  增量更新 Scratch（O(访问量)），既满足「依赖未确定派生值也能确定性解析」，
  又不强迫平台扫描全前缀。
- **并行只放在参数校验阶段**：前置钩子存在顺序依赖（可见前缀），
  任何并行求值都需要用户声明依赖或引入 speculative 执行，复杂度与
  出错面都不值得；规格要求的「任意内部并发度结果一致」由两阶段边界
  天然保证（`concurrency` 参数只影响校验 worker 数）。

## 4. 被放弃的方案

- **批次开始前给每个钩子做全量快照**：违背「必须包含之前已通过记录的
  效果」，且快照成本随批次/存量线性增长，放弃。
- **并行触发钩子、按序号等待依赖**：需要钩子显式声明读写集并处理
  失败记录对依赖图的影响；与「派生值可能尚未确定」的场景结合后无法
  保证确定性，放弃，改为严格顺序触发。
- **先直接写全局存储、失败时逐条反向补偿**：补偿语义复杂（需要反向钩子、
  且补偿本身可能失败），且并发批次会读到未提交数据；放弃。
- **后置钩子复用前置钩子通道逐条触发**：后置钩子是批次级、只触发一次且
  语义仅存在于 `AllOrNothing`，混用会使错误归属与触发次数产生歧义，放弃。
- **重复主键只报第一个就停止检测**：尽力而为语义需要完整逐条清单，
  多组重复必须全部出现在清单中（`Err` 仍是第一个命中的参数错误）。

## 5. 本地验证方法

```bash
# 环境中 go 位于 /usr/local/go/bin；构建缓存按需重定向：
export PATH=$PATH:/usr/local/go/bin
export GOCACHE=/tmp/gocache GOPATH=/tmp/gopath

go test -race -v ./...          # 全量测试（含竞态检测，打印输入/输出/判定依据）
go test ./... -count=10         # 重复运行，含 400 轮/次随机差分
go test -run TestRandomDifferentialAgainstNaive ./batchimport -v   # 仅随机对照
go test -run TestVisibilityCost ./batchimport -v                   # 仅开销证明
go vet ./... && gofmt -l .      # 静态检查与格式
```

测试结构：

- `batchimport_test.go` / `extra_test.go`：顺序可见性、两种语义差异、
  后置钩子整批撤销、错误优先级、并发度一致性、跨批次串行等价、重放确定性。
- `differential_test.go`：400 轮随机种子状态 + 随机批次（随机注入字段类型
  错误、小主键空间制造重复、合法/非法 amount 混合、标签冲突），生产实现与
  `helpers_test.go` 中的朴素模型逐条比对成功标志、错误类别、批次级错误与
  最终全量状态；每轮打印输入、实际输出与判定依据。
- `cost_test.go`：上述两个方向的开销证明。
- 朴素模型（`naiveModel`）独立维护一份全量 map 状态，严格按列表顺序逐条
  应用并同步触发钩子，不使用覆盖层，与生产实现无共享代码路径。
