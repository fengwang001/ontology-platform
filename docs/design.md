# 权限分级抢占式乐观并发控制 — 设计说明

## 问题

本体平台中，不同动作（Action）携带不同权限等级，并发地对同一对象实例
发起乐观更新（读快照 → 计算修改 → 带基线版本提交，冲突则重试）。要求：
一旦更高权限动作的写入真实生效，所有权限更低、仍处在重试循环中、且其
判定基线已被该次写入推进的动作，必须立即以"被抢占"终止，而不是基于过期
基线空转到耗尽重试预算。

## 核心语义

对一次提交尝试（动作权限 `p`，判定基线 `baseline`），判定顺序为：

1. **抢占判定（纯查询）**：若存在已生效写入 `W` 满足
   `W.priority > p` 且 `W.version > baseline`，判 `Preempted`，立即终止，
   不消耗重试预算，不产生任何状态变化。
2. **普通冲突判定**：若实例当前版本 `!= baseline`，判 `Conflict`，
   消耗一次重试预算；预算耗尽则判 `RetriesExhausted`。
3. **提交**：版本 +1、实例逻辑时钟 +1、应用属性修改、登记水位线。

因为判定 1 先于判定 2，而预算耗尽只能由判定 2 触发，所以"抢占先于预算
耗尽"由判定顺序天然保证。四类结果（冲突重试 / 抢占终止 / 预算耗尽 /
成功提交）互斥：冲突重试是尝试级结果，后三者是动作级终态。

同权限不适用抢占（条件为严格大于 `>`），同级竞争由互斥锁下的到达顺序
裁定，后到者走普通冲突重试。高权限动作不免疫任何判定：它与同级冲突
照常重试，与更高权限冲突同样被抢占。

## 关键数据结构：按权限分层的水位线

每个对象实例维护一个 `priorityWatermark`：

- `entries`：按权限等级升序的 `(priority, maxVersion)` 数组，
  记录每个等级最近一次已生效写入的版本；
- `suffixMax[i] = max(entries[i:].maxVersion)`：后缀最大值数组。

抢占判定 = 二分找到第一个 `priority > p` 的位置 `i`，检查
`suffixMax[i] > baseline`。时间 `O(log L)`、空间 `O(L)`，
`L` 为不同权限等级数量（有界小常数），**与并发竞争同一实例的动作
总数无关**。登记写入为 `O(L)`（仅在新等级首次出现时插入）。

为什么必须按等级分层而不是只记"最高权限的一次写入"：反例——
`v2` 处生效一个 `p10` 写入，`v5` 处生效一个 `p7` 写入；动作 `p5`
基线 `v3` 应被 `v5` 的 `p7` 写入抢占，但"最高权限写入" `(p10, v2)`
的版本 `2 <= 3` 会漏判。因此判定条件是"存在 `W.priority > p` 且
`W.version > baseline`"，必须保留每个等级的版本水位。

## 被放弃的方案

- **只记最近一次提交 `(version, priority)`**：上述反例会漏判
  （高权限写入之后又有低权限写入覆盖了"最近"记录）。
- **每实例维护等待者列表 / 条件变量广播**：抢占判定开销随并发动作
  总数线性增长，违反开销约束；且动作间产生显式耦合，生命周期管理
  （超时、泄漏）复杂。
- **全局版本号 + 权限位图**：位图把权限等级限制为固定位数，且仍需
  每等级版本信息才能表达"基线被该次写入推进"，未简化问题。
- **在读取快照时做抢占判定**：不够。快照之后、提交之前仍可能有更高
  权限写入生效，判定必须发生在提交临界区内。

## 串行化论证

每个实例的提交临界区由互斥锁保护，判定日志在持锁期间追加，因此
日志顺序与每实例的判定顺序一致。所有生效写入按日志中的提交顺序
即构成一个等价串行顺序：

- 每个提交动作的基线等于其前一个提交者的版本（重放可验证）；
- 被抢占动作从未生效，不占串行位置，因此"更高权限动作的生效位置
  不得落在因它而被抢占的低权限动作之后"自动成立；
- 抢占终止只读水位线，不触碰版本、属性、时钟。

## 可验证性与日志

`Store` 维护全局判定日志（`Event`：动作、权限、基线、结果、提交后
版本/时钟/修改），`Executor.Run` 返回每次尝试的完整记录
（`Result.Attempts`）。两者足以离线重放核验每一次判定。

`refmodel` 包是独立实现的参照模型（不共享水位线代码，用 map + 线性
扫描重算抢占条件），消费日志与结果并校验：

- 每条冲突事件：当时版本确实落后，且不满足抢占条件（否则应判抢占）；
- 每条抢占事件：存在更高权限且版本推进基线的已生效写入（证据提交
  的日志位置严格在前）；
- 每条提交事件：不满足抢占条件、基线与当前版本一致，重放后的版本、
  时钟与日志一致；
- 每个动作：尝试序列以冲突开始、以三类终态之一结束，冲突次数与
  重试预算的关系正确（耗尽 ⇔ 冲突次数 = 预算 + 1），基线严格递增；
- 重放终态与真实存储终态逐对象一致。

## 本地验证方法

```bash
go test ./... -race -v          # 场景测试 + 随机对照测试
go test ./ontology/ -run xxx -bench BenchmarkPreemptCheck -benchtime 100000x
```

- 场景测试：同权限竞争、低权限被抢占、交替分层抢占、高权限不免疫、
  抢占先于预算耗尽、抢占纯查询性。
- 随机对照：20 个种子 × 40 个随机权限动作 × 3 个实例并发执行，
  与 `refmodel` 对照，断言四类结果均被真实触发。
- 开销证据：`TestPreemptCostIndependentOfContenders` 断言 5000 个
  竞争者后水位线仍只追踪 4 个等级；基准显示已生效写入总数从 10
  增长到 100000 时单次抢占判定耗时基本平坦（约 257ns → 355ns，
  残余差异为日志数组增长的缓存效应，与判定本身无关）。
