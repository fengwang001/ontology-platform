# 批量更新设计说明

本文档说明 `ontology` 包中跨对象类型、多实例原子批量更新（`Store.ApplyBatch`）
的设计取舍、被放弃的方案以及本地验证方法。

## 1. 语义目标

一个批次 `BatchInput` 包含若干 `BatchItem`，每项写入恰好一个实例，并可携带
若干链接边增删（`EdgeDelta`）。语义约束：

1. 整批原子生效或整批不生效；批次发布过程对外部读者不存在可观察的中间阶段。
2. 每项携带自己的基线版本（`Baseline`），逐项与当前版本核对，任一落后即整批
   因版本冲突被拒绝，不跳过该项。
3. 每项变更经过其对象类型注册的校验钩子（`ObjectType.Validate`），钩子看到的
   是整批全部生效后的镜像，任一项拒绝即整批回退。
4. 链接基数（`LinkType.SrcMax/DstMax`）在整批最终镜像上一次性计算，不依据
   任何“某一项单独生效”的瞬时状态。
5. 回退不改变任何实例版本、属性、链接边或任何业务时钟，即使钩子已经执行过。
6. 并发批次等价于某个串行顺序（可串行化），不允许只有真并发才能产生的交叉状态。
7. 判定开销只与批次自身工作集相关，不随系统实例总数增长。

## 2. 互斥的四类失败与固定判定顺序

| 顺序 | 阶段 | `FailureKind` | 触发条件 |
| --- | --- | --- | --- |
| 0 | `duplicate` | `duplicate_declaration` | 同一批次两个 item 写同一实例；最先检查，且不读取任何存储状态 |
| 1 | `version` | `version_conflict` | 任一 item 声明基线 != 该实例当前版本（不存在即 0） |
| 2 | `validation` | `validation_rejected` | 类型/结构检查或对象类型钩子返回拒绝原因 |
| 3 | `cardinality` | `cardinality_violated` | 最终镜像上某端点度超过 `SrcMax`/`DstMax` |

早阶段失败短路掉之后所有阶段，因此四种结果天然互斥且顺序固定
（版本冲突优先于钩子拒绝，钩子拒绝优先于基数；重复声明优先于全部三者）。
实现见 `ontology/txn.go` 中按上述顺序排列的直线代码，
`TestVersionConflictBeatsValidation` 等用例锁定该优先级。

## 3. 并发控制：确定性有序加锁 + 单提交临界区

采用两层同步：

- **每个实例一把互斥锁**（`Store.locks`，惰性创建）。任何涉及多实例的操作都按
  `InstanceID` 字典序升序加锁，锁图因此无环，杜绝死锁。
  批次的加锁集合 = 全部被写实例 ∪ 全部链接增删边的两个端点。
  发布边会触碰这些端点，故把它们全部纳入锁集合是可串行化的必要条件。
- **一张全局表锁 `tabMu`**。批次在持有实例锁后一次性 `tabMu.Lock()`，在该写
  临界区内完成状态快照、全部判定和最终发布；读者（`Snapshot`/`GetOne`/
  `HasEdge`）在实例锁内以 `tabMu.RLock()` 取一个公共线性化点。

`tabMu` 的解锁点就是**唯一提交点**：此前一切计算都发生在调用方私有的影子
（`shadowView`）上，不触碰已提交状态；此后外部读立刻看到整批全部实例的最新
状态。

### 为什么这同时给出原子可见性与可串行化

- 读者要么在提交点之前取快照（看到旧的全部），要么在之后（看到新的全部），
  不存在“一半新一半旧”的窗口。`TestConcurrentReadersNeverSeeTornState` 持续
  读取成组实例并断言它们始终来自同一批次。
- 两个批次若实例集合相交，则至少共享一把实例锁，必然被强制排序；若不相交，
  其提交点在 `tabMu` 上仍被全局排序。因此任意并发历史都对应“按提交点排序”
  的一个合法串行历史。随机化测试枚举全部排列证明这一点（见第 7 节）。

## 4. 私有影子与“最终镜像”判定

加锁后把工作集内实例深拷贝进 `shadowView.instances`，把本批边增删折叠进
`shadowView.edges`（增=true / 删=false）。之后：

- 先构建每个 item 的**提议镜像**（新建版本 1；更新版本 +1，属性为全量替换），
  立刻安装进影子；
- 链接的类型与端点存在性检查、对象类型钩子、基数计算全部读取这个最终影子。

因此“同批先删一条边再加一条边，最终度不变”会通过，而按瞬时状态判定会错误
拒绝。`TestCardinalityEvaluatedOnFinalImageNotIntermediate` 正是该边界：
`member` 的源端上限 2，已有两条边的实例在一批中删一加一，最终度仍为 2，必须
提交。

回退即“什么都没安装”：影子是局部对象，拒绝路径只是不执行 `publish` 并解锁；
无需补偿式撤销，因而钩子执行与否不影响存储。版本号只在 `publish` 中对最终
提交的实例 +1，被回退的批次不留下任何版本/边/时钟痕迹
（`TestRejectedBatchAfterHookRunsLeavesNoTrace`）。

## 5. 基数判定的复杂度：只与批次相关

朴素做法是扫描全边表统计度，代价随全局数据量增长，被明确放弃（见第 8 节）。
本实现维护**按端点的邻接索引**：

- `outAdj[端点][链接类型] = 邻居集合`、`inAdj` 同构（入边）；
- 一批边增删只可能改变被触碰端点的度，故只需考察本批边增删涉及的端点；
- 每个端点的最终度 = 它自己的邻接表基数，按本批 overlay 增删修正
  （`finalDegree`）。

复杂度为 O(被触碰端点数 × 各端点自身度 + 批次边增删数)，与系统总实例数、
总边数无关。`JournalRecord.InstanceTouches` 逐项记录判定过程中读取过的
实例状态计数；`TestDecisionTouchesOnlyBatchInstances` 断言 200 个实例的
存储中一个两项批次只触碰这 2 个实例，`TestCostIndependentOfTotalInstances`
进一步在 10 与 2000 个实例的存储上断言该计数完全相同。这就是“不依赖额外
对外暴露状态即可验证的证据”：记录由引擎自身产出，随每个批次返回并写入日志。

## 6. 时钟与重放日志

- `commitClock`：业务提交时钟，仅在 `publish` 成功路径上 +1。被拒绝的批次
  不推进它（`CommitSeq()` 可读、`TestJournalReplayReproducesFinalState` 断言
  重放后时钟值 == 日志中的提交条数）。
- 每次尝试（提交或拒绝）都在 `JournalRecord` 中完整留痕：输入深拷贝、加锁
  顺序、逐项基线观察（声明值/观察值/是否匹配）、逐个钩子调用与拒绝原因、
  逐端点基数观察（度/上限/是否满足）、判定阶段、最终版本。日志只能通过
  `Journal()` 深拷贝读出，外部无法篡改引擎内部状态。
- 钩子契约要求**纯且确定**（不得改状态），因此用日志记录的输入在同构空存储
  上重放，判定结果与最终状态逐位复现（见重放测试）。

## 7. 测试策略

全部测试在 `ontology/*_test.go`：

- 边界单测：整批提交与版本推进；批次内部分实例基线落后导致全批拒绝；
  重复声明最先判定且零副作用；版本 > 钩子 > 基数的优先级；
  基数“恰好不满足”（度 = 上限+1）整批拒绝且边不可见；基数在最终镜像上判定；
  钩子已执行后拒绝不留痕；显式的交集批次并发（B0={a,b}, B1={b,c}, B2={a,c}
  每轮恰一个提交、两个版本冲突）。
- 随机化线性izability（`TestRandomizedEquivalentToSomeSerialOrder`）：
  固定种子生成 5 个高重叠随机批次（含随机陈旧基线、随机钩子拒绝、随机边增删、
  随机内部重复声明），枚举 5! 种串行排列喂给**独立实现的朴素全局加锁模型**
  （`naiveEngine`：一把全局大锁、普通 map、基数用全局边扫描，代码形态刻意与
  生产引擎不同），收集“(每批次判定, 最终状态摘要)”的全部可能结果；再把同一
  批输入在真实引擎上栅栏齐发并发执行多轮，断言每次结果都落在某个串行排列的
  结果集合内。另外在同一随机顺序上逐批对照两个引擎，判定与状态摘要必须逐位
  一致。
- 重放（`TestJournalReplayReproducesFinalState`）：并发跑完后，用日志记录的
  全部输入在空存储上重放，断言判定复现、最终状态摘要与提交时钟一致。

运行：

```bash
export GOCACHE=/tmp/gocache   # 若默认缓存目录只读
go test -race ./...
go test -race -count=10 ./ontology/
go vet ./...
gofmt -l .
```

## 8. 关键取舍与被放弃的方案

- **放弃：全局大锁串行化一切。** 正确但无关批次之间也互相阻塞，且无法作为
  “只按批次工作集付代价”的证据。它仅保留在测试里作为朴素参照模型
  （`naiveEngine`），刻意写得简单、独立，用来交叉验证而不是参与生产。
- **放弃：MVCC + OCC 提交时重试。** 能做到无锁读取，但“整批钩子在最终镜像
  上判定 + 链接基数最终态判定”需要先把整批工作集物化并做提交时校验，复杂度
  与中止/重试的可观测语义（失败分类、时钟要求）都更高；本需求没有要求读不
  阻塞，有序加锁 + 单写临界区用小得多的复杂度直接给出可串行化与线性izable 读。
- **放弃：先逐项目标点提交、失败再补偿回滚。** 会产生外部可观察中间态，违反
  原子可见性；且补偿路径在崩溃语义下需要 undo 日志。影子镜像 + 单一发布点没有
  回滚代码路径，天然满足“生效前任何中断都不改状态”。
- **放弃：基数判定扫描全边表。** 代价随全局规模增长；改为按端点邻接索引，只
  触碰本批端点，并以 `InstanceTouches` 给出可验证证据。
- **取舍：`tabMu` 是一把写互斥的表锁。** 不同批次的写在发布瞬间互斥，但判定
  期间彼此在各自实例锁上排队；读多写少时读者拿 `RLock` 不互相阻塞。若未来写
  竞争成为瓶颈，可将表锁分片而不改变“单提交点”语义；当前规模下简单性优先。
- **取舍：实例锁条目只增不删。** 删除锁会让“锁与数据生命周期”耦合并引入
  竞争窗口；条目体积为一个 `sync.Mutex` 指针，可接受。
- **取舍：属性为全量替换而非 patch。** 全量替换让“最终镜像”无歧义、可深拷贝、
  可重放；patch 合并需要额外冲突合并语义，与整批原子判定目标不匹配。
- **取舍：钩子必须纯且确定。** 这是日志可重放的前提；钩子通过 `BatchView`
  只能读深拷贝，无法改存储。

## 9. 代码地图

- `ontology/types.go`：注册表、对象/链接类型、实例、边与边增删、钩子签名。
- `ontology/batch.go`：批次输入/结果与 `BatchView` 只读视图接口。
- `ontology/errors.go`：四类互斥失败与 `BatchError`。
- `ontology/store.go`：存储结构、有序加锁、线性化读、日志读取。
- `ontology/view.go`：批次私有最终镜像 `shadowView`。
- `ontology/txn.go`：五阶段判定（重复/基线/结构与钩子/基数/发布）。
- `ontology/publish.go`：单点发布、邻接索引维护、时钟与日志落账。
- `ontology/journal.go`：重放证据记录结构。
