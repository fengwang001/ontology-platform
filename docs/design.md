# 权限决策审计回放模块 — 设计说明

## 1. 目标与范围

`audit` 包为 ontology 平台提供权限决策的审计与回放能力：

- 权限规则版本化：每次变更生成新版本，旧版本完整保留，版本间有唯一确定的全序。
- 每次实际访问判定生成一条不可变审计记录（主体、目标、请求、判定时刻、结果、所依据的规则版本标识与内容哈希）。
- 历史回放：仅依据记录中登记的版本标识对应的规则内容与记录中的输入，重新执行裁决并与原结果比较。
- 不一致归因：区分"该版本规则内容被篡改"（完整性破坏）与"原判定过程本身有缺陷"（历史误判）。
- 纠正记录：只追加、不修改原始记录；支持链式再次纠正；三态合法性查询。
- 固定优先级的错误分类；全部操作可线性化；回放的版本读取开销与版本总数无关。

## 2. 核心模型

### 2.1 三条追加式哈希链

系统维护三条各自独立的追加链，链内顺序由单调序号唯一确定：

| 链 | 元素 | 标识 | 哈希 |
|---|---|---|---|
| 规则版本链 | `RuleVersion` | `rv-<seq>` | `ContentHash`（内容哈希）+ `ChainHash`（链哈希） |
| 审计记录链 | `AuditRecord` | `ar-<seq>` | `SelfHash`（字段哈希）+ `ChainHash` |
| 纠正记录链 | `Correction` | `cr-<seq>` | `SelfHash` + `ChainHash` |

- 内容哈希：`sha256(Canonical(RuleSet))`，`Canonical` 为确定性 JSON 序列化。
- 链哈希：`H(kind || prevChainHash || selfHash)`，形成防篡改的链式结构。
- 单条目的完整性校验是 O(1) 的：重算条目自哈希并与条目登记的前向链哈希联验，无需遍历全链。

### 2.2 审计记录登记版本哈希

`RecordAccess` 在写入记录时，把判定所依据版本的 `ContentHash` 一并登记进 `AuditRecord.VersionHash`。
这是回放时区分两类不一致的关键：

- 回放时若 `当前存储版本的内容哈希 != 记录登记的 VersionHash`（或版本条目自身校验失败），
  说明该版本的内容在判定之后发生了不应发生的改变 → `ReplayVersionTampered`（完整性破坏）。
- 否则用该版本内容以纯函数 `Evaluate` 重算，若与记录结果不同，
  说明原判定过程本身有缺陷（例如依赖了未登记的缓存状态）→ `ReplayMisjudgment`（历史误判）。

### 2.3 纠正链与三态查询

- 纠正记录只追加；`Supersedes` 必须指向同一原始记录当前纠正链的链头，
  首条纠正的 `Supersedes` 为空。链的顺序即全局纠正序号顺序，唯一确定。
- 有效结论 = 纠正链链头的 `CorrectedTo`（无纠正时 = 原始记录结果）。
- 三态回答：
  - `ALLOW_AS_RECORDED`：有效结论 = 原始结果 = 允许；
  - `DENY_AS_RECORDED`：有效结论 = 原始结果 = 拒绝；
  - `CORRECTED`：有效结论 ≠ 原始结果（存在未被后续纠正否定的纠正改变了结论）。
- 查询是日志状态的纯函数，不读取时钟，因此结果与查询发出的时刻无关。

### 2.4 错误分类与固定优先级

`ErrorPriority` 定义唯一全序（数值小者优先汇报）：

1. `ErrVersionNotFound` — 回放记录登记的版本标识不存在；
2. `ErrAuditIntegrity` — 原始审计记录自身完整性破坏；
3. `ErrCorrectionTargetMissing` — 纠正指向不存在的原始记录。

回放按此顺序检查：先版本存在性，再记录完整性，再版本内容完整性（后者作为回放结论
`ReplayVersionTampered` 而非错误返回，因为它是"发现"而非"拒绝"）。
所有被拒绝的请求在校验通过前不发生任何写入，对既有数据零影响。

## 3. 关键取舍

### 3.1 判定与审计分离

`RecordAccess` 的 `result` 由平台决策点（PDP）给出，审计模块只如实记录；
回放使用模块内的确定性纯函数 `Evaluate` 独立重算。
这正是审计的意义所在：如果回放复用 PDP 的判定路径，就无法发现 PDP 的缺陷。
误判在测试中通过"记录的结果与规则内容不符"自然构造。

### 3.2 单互斥锁实现可线性化

所有公开操作在 `store.mu` 临界区内完成。单锁使"任意并发调用的结果等价于某个
串行顺序"这一性质按构造成立（临界区顺序即串行化点），代价是写吞吐受限。
对本模块的负载特征（低频写、审计路径不在请求热路径上）这是合理取舍；
若未来需要更高并发，可演进为分片锁或 MVCC，但对外语义不变。

### 3.3 回放开销的可观测证明

版本存储为 `map[VersionID]*RuleVersion`，回放只按键读取目标版本一次。
该性质不依赖内部细节即可观测：`Replay` 返回 `ReadStats{VersionsScanned, VersionBytesRead}`，
测试断言：

- `VersionsScanned == 1` 恒成立；
- `VersionBytesRead == len(Canonical(该记录登记的版本内容))`，
  且在版本总数从 1 增长到 300 时保持不变（`TestReplayCostIndependentOfVersionCount`）。

### 3.4 完整性校验为 O(1) 单点校验

每条目登记 `SelfHash` 与前向 `ChainHash`，校验单条目只需两次哈希计算，
不随链长增长。代价是：若攻击者同时篡改某条目及其全部后继的链哈希则无法检测——
本模块信任边界为"存储可能被局部篡改，但攻击者不能重算全链"（如 WORM 存储/异地锚定）。
需要更强保证时可在链头做外部锚定（签名/透明日志），接口无需变化。

## 4. 被放弃的方案

- **内容寻址版本标识（hash 即 ID）**：相同内容的两次提交会坍缩为一个版本，
  破坏"每次变更生成新版本"与版本全序的语义，放弃；改为单调序号 ID + 内容哈希字段。
- **回放时遍历全链校验**：保证更强但使回放开销随记录总数增长，
  违反"回放开销仅与目标版本内容规模相关"的约束，放弃；改为 O(1) 单点校验。
- **纠正记录就地标记原始记录**（如在原记录上写 `supersededBy` 指针）：
  违反"不得修改原始记录任何字段"，放弃；纠正关系完全由纠正链侧向表达。
- **读写锁（RWMutex）**：回放/查询看似只读，但读统计与日志事件需要共享状态，
  且单锁已满足需求，为简化正确性论证放弃。
- **错误用单一 `error` 多值返回**：Go 惯例不支持多错误优先级语义，
  采用"按固定优先级检查、返回首个命中的分类错误 + `ErrorPriority` 可查询"。

## 5. 日志

每次公开调用产生一条 `Event{Op, Input, Output, Basis, Err, At}`：

- `Input`：调用的全部入参；
- `Output`：最终输出（ID / 回放结论 / 三态结果）；
- `Basis`：裁决依据（版本标识与内容哈希、记录序号、纠正链构成）；
- `Err`：拒绝原因（分类错误）。

提供 `MemoryLogger`（测试/审计检查）与 `JSONLLogger`（JSON Lines 落盘）。

## 6. 测试策略

- `replay_test.go`：回放一致 / 误判 / 版本篡改 / 版本缺失 / 记录缺失、
  旧版本保留、版本顺序确定性、回放开销与版本总数无关、日志完整性。
- `correction_test.go`：纠正改变三态、链式覆盖（含重申原判的回归）、
  三态查询与时间无关、各类拒绝（目标缺失/链头不符/跨记录/自纠正引用缺失）、错误优先级。
- `integrity_test.go`：完整性破坏全部组合边界——版本内容、记录结果、记录版本引用
  （悬空/调换）、记录链哈希、版本+记录同时破坏、版本删除+记录破坏、篡改隔离性、
  被拒绝操作零副作用、返回值深拷贝隔离。
- `concurrency_test.go`：并发混合调用后版本/记录序号连续无空洞无重复
  （可线性化的可观测证据）；并发纠正热争下链仍然确定有序。`-race` 通过。
- `differential_test.go`：朴素参照实现 `naiveSystem`（线性扫描、独立存储，
  仅共享纯函数裁决语义 `Evaluate`），在 5 个随机种子 × 400 步的
  随机规则版本/访问/回放/纠正/查询/篡改注入序列上逐项对照输出、错误分类与读取统计，
  并在终态全量对照所有版本、记录与纠正链。
