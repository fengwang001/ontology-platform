# 物业费账单服务设计说明

## 模块划分（`billing/` 包，6 个 .go 文件）
- `config.go`：构造参数（宽限 G、日利率、上限比例、三级阈值）与五级错误码，校验在 `NewService` 完成。
- `bill.go`：账单状态机；滞纳金以 1/(RateDen*CapDen) 为最小单位的整数累计，分数部分天然结转；`stageAt` 纯函数算催缴阶段。
- `apply.go`：缴款冲抵（到期日→创建序排序，先滞纳金后本金，三阶段整缴否则跳过）与关账判定。
- `service.go`：所有操作按固定次序校验（参数→时钟→存在→状态→金额），全部通过后才落状态并推进时钟；查询只读。
- `service_test.go` / `differential_test.go`：单元测试 + 朴素模型随机对照。

## 关键取舍
- **惰性物化 + 纯函数试算**：累计只在被接受的操作时落账（`accrueTo`），校验与查询用不改状态的 `accruedUnitsAt`，保证"被拒绝的操作不留痕"（含时钟）。
- **争议语义**：争议日当天起停计，裁定日当天恢复；争议天数只增不减，阶段随时间单调，故"只向前"天然成立，无需额外锁存。
- **调减重算**：上限与日累计基数都按裁定后本金重算；已累计超出新上限的部分不回扣（与"已缴不退"一致），仅停止增长。
- **查询复杂度**：每户只维护未关账账单的有序切片，关账即移除；`TotalDue` 只扫该切片。`scanCount` 埋点由测试断言其等于未关账数、与历史总量无关。
- **并发**：单互斥锁串行化全部操作，等价于某串行序；确定性来自排序切片与整数运算，重放必一致。

## 被放弃的方案
- 事件溯源 + 查询时重放：查询开销随历史增长，违反复杂度约束。
- 每日定时任务推进滞纳金/阶段：引入后台时钟与竞态，惰性计算更简单且可重放。
- big.Rat 进主路径：性能与复杂度不值；改用通分后的整数单位，朴素模型才用 big.Rat 做独立参照。
