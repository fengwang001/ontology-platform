# 多态动作分派机制设计说明

本文档说明本体平台中“一个动作对多种对象类型通用、各类型注册各自执行逻辑”
时，调用方发起调用后如何分派到正确执行逻辑，以及运行期替换、并发撤销、
放宽审计等情形的处理取舍。代码位于 `ontology/` 包。

## 1. 问题与关键不变量

需要同时满足以下不变量：

1. 动作（`Action`）只有接口：输入/输出形状与前置/后置条件，不含执行逻辑。
2. 执行逻辑（`Implementation`）由具体对象类型注册；分派沿实例当前绑定类型
   的继承来源向上查找，取第一个“已注册直接处理”的类型。
3. 该查找与属性取值规则完全独立：实现只遍历静态类型继承链，不读取任何
   属性解析结果，也不共享缓存。
4. 运行期可替换执行逻辑；替换前已发起的在途调用用旧逻辑执行到底，替换后
   发起的调用用新逻辑。
5. 放宽拒绝（旧逻辑拒绝、新逻辑接受）必须在注册时声明放宽范围
   （`Relaxation`）；超出声明范围的行为差异不阻止注册，但必须能被事后审计发现。
6. “显式放弃直接处理（waive）”与“从未注册（absent）”是两种可区分状态；
   waive 时查找跳过本层继续向上。
7. 查找过程中对象被并发撤销，则本次调用整体失败；查找完成、逻辑已开始运行
   之后的撤销由执行逻辑自身后置校验负责，分派器不再介入。
8. 四类失败必须可区分，且两种“无法分派”在任何逻辑执行前判定，优先级高于
   “查找中撤销”和“前置/后置条件不通过”。
9. 查找遍历的链长不超过“具体类型到首个命中祖先的实际深度”，与系统中其它
   互不相关类型的注册数量无关。
10. 并发的替换注册与调用发起交织时，每次调用等价于在某个全局全序下串行执行。

## 2. 核心抽象

- `Action`（`types.go`）：纯接口声明，含接口级 `Precondition` / `Postcondition`。
- `Implementation`（`types.go`）：`Pre` / `Execute` / `Post` 三段式，注册后
  不可变。
- `ObjectType`（`objecttype.go`）：单继承节点，`Parent` 指针在本设计中不可变；
  `chain()` 返回 `[self, parent, ...]`，遍历不依赖任何注册表状态。
- `Instance`（`objecttype.go`）：持有当前绑定类型与独立的撤销锁；`Revoked()`
  可并发读取。
- `generation`（`registry.go`）：一次不可变的注册代次，持有实现指针、放宽
  声明与全局序号；替换只追加新代次，旧代次不被修改也不被释放（在途调用与
  审计都要引用它）。
- `slot`（`registry.go`）：每个 `(action, type)` 的三态槽位：
  `stateAbsent` / `stateWaived` / `stateRegistered`。
- `Relaxation`（`audit.go`）：`Covers(input)` 谓词声明放宽范围。
- `DispatchTrace`（`dispatch.go`）：每次调用记录发起序号、分派路径、每跳依据、
  命中类型与命中依据（直接/继承）、命中代次、是否观察到 waive、最终结果与
  错误类别，供事后核对。

## 3. 关键取舍

### 3.1 用一把互斥锁定义“调用发起时刻”

“调用发起时刻”被精确定义为：分派器获取注册表互斥锁并为本次调用分配全局
序号（`Registry.touchLocked`）的那一瞬间。锁内完成：

- 沿继承链解析；
- 撤销检测（逐跳）；
- 命中代次与前置条件判定。

锁外只做执行（`Execute`）与后置校验。因为解析与所有注册/waive/替换在同一把
锁上互斥，调用解析到的注册表状态必然对应全局序号轴上某个确定时刻，不存在
“介于两次替换之间”的代次。执行不持锁，长任务不阻塞注册，且其实现指针是
不可变快照，替换无法改写它。

被放弃的方案：
- *读多写少用 RWMutex + 原子指针*：理论上读可并行，但“撤销发生在解析中途”
  与“替换发生在解析中途”都需要把一次多跳解析界定为单个原子区间，RWMutex
  仍需在读路径上升级或借助顺序锁，正确性证明更复杂；当前解析本身只是沿静态
  数组做常数时间 map 读取（长度 ≤ 实际命中深度），临界区极短，单锁更简单、
  更容易证明线性化。若未来解析成为瓶颈，可在不改变“一次解析一个原子区间”
  语义的前提下替换为 RCU/epoch 方案。
- *调用时拷贝整张注册表快照*：实现简单但成本随系统中注册总量增长，直接违反
  深度/规模上界要求（不变量 9），放弃。

### 3.2 不可变代次而不是就地替换

替换 = 追加 `generation` 并切换 `slot.current`。在途调用在锁内拿到的是
`*generation` 指针，锁外执行期间注册表如何变化都不影响该指针。这是“在途
调用用旧逻辑执行到底”的根本机制，也让审计可以直接比较相邻两代。

### 3.3 三态槽位，waive 不删除信息

`absent`（从未注册）与 `waived`（显式放弃）用独立枚举区分。waive 只影响
查找动作（跳过本层），不抹掉历史；历史代次保留在 `slot.history` 中。

### 3.4 放宽：注册时必检 + 事后审计，不追求静态完备

- 注册/替换时用调用方提供的探针语料执行 `checkRelaxationRequired`：只要
  发现“旧拒新收”而未提供非空 `Relaxation`，直接拒绝注册
  （`reasonRelaxRequired`），满足“放宽必须在注册时声明”。
- 探针不可能覆盖全部输入，因此审计 `Audit` 独立存在：对每对相邻代次在给定
  语料上逐输入比较，差异（放宽/收紧/输出变化）若不被 `Covers` 覆盖，就生成
  一条不可变的 `AuditFinding`。系统不阻止“声明范围小于实际行为”的注册
  （题目明确不要求阻止），但保证事后一定可发现。

被放弃的方案：
- *要求形式化规约并自动证明包含关系*：表达力与工程成本不匹配；用“注册期
  必检 + 可插拔探针审计 + 永久 finding”覆盖题目要求的检测能力。

### 3.5 撤销：解析期分派器管，执行期实现自己管

`resolveLocked` 逐跳检查 `obj.Revoked()`。对象在解析窗口内被撤销即判
`ClassObjectRevoked`，即便祖先存在实现也不执行写入。解析窗口在锁内，
`Revoke` 与之的关系只有两种串行结果：撤销先生效（调用失败）或后生效（调用
已解析并进入执行，此时由实现自身 `Post`/后置校验决定），不存在“用了撤销前
逻辑继续写”的模糊态。

### 3.6 错误分类与优先级

四类错误（`DispatchErrorClass`）：

| 类别 | 触发条件 | 判定时机 |
| --- | --- | --- |
| `ClassNoDispatch` | 具体类型及所有祖先均 `absent`/无实现 | 任何逻辑执行前 |
| `ClassWaivedNoDispatch` | 链上出现 waive，但最终无任何实现 | 任何逻辑执行前 |
| `ClassObjectRevoked` | 解析窗口内对象被撤销 | 解析期（结构上有实现时才有意义） |
| `ClassCondition` | 实现前置/后置或接口后置不通过 | 分派成功之后 |

实现细节：解析只走到“首个已注册类型”的深度；若一路无注册，则按是否见过
waive 区分前两类（此时即使对象已撤销，按题目“无法分派优先”仍归类为无法
分派）；若找到实现且解析窗口内观察到撤销，则归为撤销；前置/后置只在已确定
命中代次后运行。

## 4. 深度上界（可验证）

`resolveLocked` 沿 `chain()` 顺序读取槽位，遇到第一个 `stateRegistered`
即以带标签的 `break walk` 终止（注意：Go 中 `switch` 内裸 `break` 只跳出
`switch`，必须用标签才能终止外层循环——该缺陷曾被测试
`TestDispatchDepthBound` 捕获并修复）。

因此检查跳数 `Hops`：

- 命中时 = 具体类型到首个注册祖先的实际深度；
- 与系统中注册了该动作的其它类型数量无关（它们不在本实例链上，遍历时根本
  不会被访问；注册表按 `action -> type -> slot` 两级 map 组织，单跳 O(1)）；
- 完全无实现时遍历整条链，这是不存在“命中深度”的唯一情形。

`TestDispatchDepthBound` 通过注册 200 个互不相关类型并断言跳数保持 3 来
机器验证该上界。

## 5. 线性化论证与对照测试

注册变更（register/replace/waive）与调用发起共享 `Registry.seq` 单调序号，
且都在同一把锁内取得序号并生效。因此存在一个由锁获取顺序给出的全序；每次
调用解析到的状态等于该全序中它发起位置上的注册表状态。

`TestConcurrentReplaceAndInvokeLinearizable` 用 40 个并发替换与 8×60 次并发
调用压测，然后：

1. 取注册表的变更日志与分派器的调用轨迹（各自带全局序号）；
2. 按序号合并成一个串行操作序列；
3. 用一个**独立的朴素模型** `naiveModel`（纯 map + 题目描述的朴素向上查找）
   重放该序列；
4. 断言真实运行中每次调用使用的代次序号与命中类型，与朴素模型在该串行位置
   的预测逐一相同。

该测试在 `-race -count=5` 下稳定通过。

## 6. 每次调用的可核对记录

`DispatchTrace` 字段：`CallSeq`（发起位置）、`Action`、`ObjectID`、
`ConcreteType`、`Path`（每跳类型与依据 direct/inherited/waived/absent）、
`Hops`、`HitBasis`、`OwnerType`、`GenSeq`、`SawWaive`、`Result`、
`ErrorClass`。配合 `Registry.MutationLog()` 可离线重放与审计。

## 8. 范围与后续可扩展点

- 当前为单继承；多继承/线性化 MRO 可在 `ObjectType.chain()` 处替换，分派
  状态机不变。
- 类型层级当前不可变；若支持运行期改父类型，应让“改父类型”也进入同一把锁
  与同一全序，并对实例绑定做版本化。
- 审计语料由调用方提供；可接入线上调用采样语料实现持续审计。
- 单锁在解析极重时可用 epoch/RCU 扩展，但必须保留“一次解析一个原子区间”。
