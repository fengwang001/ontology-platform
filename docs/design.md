# 刀具库寿命管理服务 — 设计说明

## 1. 目标与范围

多个加工通道并发向刀组申请可互相替代的刀具，系统按「寿命预占 → 记账 / 中止 /
破损 → 换新」的生命周期给出确定结果，并区分「无刀可用」与「暂无余量」。

代码按职责拆为四个协作模块（均在 `toollife` 包内）：

| 文件 | 职责 |
| --- | --- |
| `types.go` | 值对象与枚举：寿命口径、选刀模式、刀具状态、配置与各操作的输入/输出视图。不含逻辑。 |
| `errors.go` | 可区分的错误码与统一构造：参数非法 / 不存在 / 冲突 / 状态不允许 / 无刀可用 / 暂无余量。 |
| `group.go` | 刀组内核：刀具可变状态、申请台账、顺序选刀与失败原因分类、寿命/千分比纯函数。不做加锁决策。 |
| `service.go` | 服务门面：参数校验、错误优先级、加锁与并发串行化、申请编号全局归属、生命周期流转与日志钩子。 |

## 2. 关键数据模型

- `holder`：一把刀的可变状态 `{status, used, reserved, warned}`。`remaining`
  以 `max(limit-used, 0)` 计算，宽松模式允许 `used > limit`，剩余寿命永不为负。
- `group`：`[]*holder` 保持配置顺序（选刀顺序），同名 `map` 做 O(1) 编号定位；
  `requests map[string]*request` 是申请台账。
- `request`：`{estimated, toolID, open, settled, actual, exhaustedAtSettle}`。
  申请记录必须永久保留——同一申请编号的幂等回放与冲突检测依赖它。
  `exhaustedAtSettle` 是记账时刻的结果快照：换新会从 `byID` 删除旧编号，
  此后对历史申请的**重复记账回放**不能再去读那把已不存在的刀（早期版本在此处
  解引用空指针，由随机对照测试暴露后修复）。
- `Service.owner`：`申请编号 -> 刀组` 的全局索引，用于跨刀组的同编号冲突判定。

## 3. 选刀规则与「两种失败」的判定依据

顺序扫描刀组，第一把满足条件的刀即中选；单刀判定 `canCarry` 为纯函数：

- 共同前提：`status == available`（破损 / 已耗尽 / 已锁定一律跳过）。
- 严格模式：`used + reserved + est <= limit`（预占后仍可承载，边界等值可中选）。
- 宽松模式：`used + reserved < limit`（申请时未占满即可，本次允许超出上限）。

全部不满足时，用以下依据区分错误：

- **暂无余量（ErrNoMargin）**：存在至少一把「可用且 `used < limit`（刀本身没耗尽），
  但本次无法承载」的刀——余量只是被未结算预占占住，预占释放（记账/中止）后可能再成功。
- **无刀可用（ErrNoTool）**：其余情况——空组，或所有刀都破损 / 锁定 / 已耗尽。

该区分在 `group.pick` 一次扫描内同时完成，不需要第二轮遍历。

查询视图里的 `CurrentPick` 回答「此刻下一把轮到谁」：第一把
`available && used+reserved < limit` 的刀，与具体预计消耗无关。

## 4. 生命周期流转的关键取舍

- **记账**：`reserved -= estimated; used += actual`。差额自然处理——`actual`
  小于预计表现为净释放，大于预计表现为净补记，无需特判。宽松模式超上限照常入账；
  仅当刀处于「可用」且 `used >= limit` 时才转为已耗尽；破损/锁定刀照常记账但
  **保持原状态**（规格明确要求记账仍生效）。
- **预警**：只在记账路径计算 `floor(used*1000/limit)`，要求
  `before < 阈值 && after >= 阈值` 且本刀 `warned == false`。预占不触发；
  阈值为 0 不预警（0‰ 永远“已达标”，无从跨越）；换新重建 `holder`，`warned`
  随之归零，重新具备资格。
- **破损**：未结算预占原样保留（记账仍计入已用），此后跳过选择。重复上报幂等。
- **换新**：仅破损刀可换；`reserved != 0` 一律拒绝（拒绝不改任何状态）。
  新刀在**原切片下标**原地替换并重建 map 项，顺序位置稳定，已用归零。
- **锁定/解锁**：锁定不影响既有预占，只影响后续选择；解锁不强行恢复可用——
  若 `used >= limit` 则落为已耗尽。重复锁定幂等；解锁未锁定刀报状态错误。
- **中止**：释放预占、不计消耗；重复中止幂等；已记账申请不能中止。
- **幂等与冲突**：申请重复提交（同组同预计消耗）回放原结果并置 `Replayed`；
  同编号不同预计消耗 / 不同刀组 → 冲突。记账重复提交（同实际值）幂等，
  不同实际值 → 冲突。被拒绝的操作在校验全部通过前不触碰任何可变字段。

### 错误优先级（从高到低）

参数非法 → 刀组/刀具不存在 → 申请冲突 → 状态不允许 → 无刀可用 / 暂无余量。
实现中先做纯参数校验，再查存在性，最后在刀组锁内做内容冲突与状态判定。

## 5. 并发模型

- 每个刀组一把互斥锁 `group.mu`，组内所有读写（含选刀）都在锁内完成，
  因此多通道同组申请天然等价于某个串行顺序，严格模式下不可能把同一份余量预占两次。
- 全局 `Service.mu`（RWMutex）只保护「刀组注册表」；`ownerMu` 只保护编号归属表，
  临界区都只有几条 map 指令，不阻塞其他刀组。
- **加锁顺序固定为：刀组锁 → 归属表锁**（申请路径），其余路径只取其中一把，
  锁序无环，不会死锁。
- 刀具 `byID` map 的所有读写（含换新删除、按编号取刀）都必须在刀组锁内；
  早期版本「先无锁查 map 再补锁」被 `-race` 随机测试抓到，已改为
  `lookupToolLocked` 持锁返回。
- 查询在刀组锁内拷贝出不可变快照 `GroupView` 后释放锁，避免返回内部指针。

## 6. 复杂度与「不随历史增长」的可验证证明

- 选刀：对组内 `n` 把刀顺序扫描一次，每把 O(1)，共 **O(n)**。
- 申请台账按编号哈希存取：命中幂等 / 记账 / 中止均为期望 **O(1)**，
  台账规模不出现在选刀路径上。
- 验证方式（`toollife/scale_test.go`）：
  - `TestHistoryScaleIndependent`：刀具数固定为 8，历史台账取 100 与 100000
    两档（相差 1000 倍），各跑 2000 次实时申请+中止对比平均耗时。
    实测比值约 **1.03**（阈值 < 2.5）；若选刀遍历历史，比值应接近 1000。
  - 反向对照：刀具数 8 → 800 且构造「必须扫完全部刀」的失败路径，
    平均耗时随刀具数明显增长（实测约 2.2×，机器不同会有差异，但方向稳定），
    证明扫描的成本花在刀具上而不是历史上。
  - 另提供 `BenchmarkApplyHistory100 / BenchmarkApplyHistory100k` 供人工对照。
    注：10 万历史档基准可见约 2× 的常数级差距，这是更大哈希表带来的
    缓存/内存页效应（台账按规格必须永久保留以支持编号幂等），不是随历史
    线性增长——断言测试的 1000 倍对照已经排除线性关系。

## 7. 被放弃的方案

1. **全局单锁串行所有刀组**：实现最简单，但不同刀组互不相关却互相阻塞，
   多通道并行度差。改为每刀组一把锁，注册表与归属表用独立短临界区。
2. **选刀时遍历申请台账汇总每把刀的预占**：直观但选刀变成
   O(历史申请数)，直接违背「开销只与刀具数相关」。改为在刀具上直接维护
   `reserved` 合计，申请 / 记账 / 中止时增量更新。
3. **给每把刀单独加锁**：选刀要跨多把刀试选，必然出现多锁获取顺序问题；
   而选刀、记账都要求对「整组顺序与余量」做一致判定，收益为零、死锁面更大，
   故选择组级锁。
4. **无剩余寿命时把 `remaining` 存成负数**：查询展示会泄露内部口径，
   且宽松超上限属于合法状态。改为 `max(0, limit-used)`，已用本身仍可超过上限。
5. **换新时保留旧 `holder` 仅改状态**：旧编号语义会变得含糊（旧申请记在哪把刀？）。
   改为切片下标处整体替换为全新对象，并把记账结果快照进申请记录。

## 8. 本地验证方法

```bash
# 环境需要 Go 1.26+；若 go 不在 PATH：
export PATH=$PATH:/usr/local/go/bin
# 沙箱内默认 GOCACHE 只读时：
export GOCACHE=/tmp/gocache

go test ./...                       # 全量测试
go test -race -count=30 ./toollife  # 并发压力 + 竞态（30 轮）
go test -v ./toollife               # 查看每个用例打印的输入/输出/判定依据
go test ./toollife -run TestRandomDifferential -v   # 400 轮随机模型对照
go test ./toollife -run TestHistoryScaleIndependent -v  # 历史两档开销对照
go test ./toollife -bench BenchmarkApplyHistory -run '^$'
go vet ./... && gofmt -l .
```

测试日志通过 `Service.SetLogger` 注入，生产默认无日志输出；所有判定依据
（如「used+reserved=10 占满且刀仍可用 → 暂无余量」）均直接打印在用例日志中。
