# 三单匹配与付款放行设计说明

## 目标

系统围绕采购订单、收货和发票维护最小必要状态，在数量容差、价格容差、多张发票、多次收货、收货冲销、供应商冻结和提前付款折扣共同存在时，给出可区分的业务结果或拒绝原因。所有金额单位均为分，时间单位均为非负整数秒。

## 模块划分

- `model.go`：采购订单、订单行、收货、发票、付款和结果类型；不包含判定逻辑。
- `errors.go`：强类型 `Error` 与错误码，区分参数非法、时钟回退、对象不存在、供应商冻结、状态不符和各类业务拒绝。
- `validation.go`：纯输入校验，只判断参数自身是否合法，不读取可变业务状态。
- `store.go`：内存聚合、全局单调时钟、对象索引、并发互斥和操作编排。
- `policy.go`：收货容差/冲销、逐行三单匹配、原子提交、折扣与账期计算。
- `logger.go`：日志接口、标准库适配和测试用捕获日志。
- `service_test.go`：确定性边界测试与并发不变量测试。
- `naive_model_test.go`：独立朴素模型与大规模随机操作对照。

## 状态与索引

订单行只保存判定必需的四个累计字段：

- `ordered`：订购量。
- `unitPriceCents`：订单单价。
- `received`：当前累计净收货量。
- `invoiced`：已放行发票累计占用量。

服务维护三张主索引：

- `orders[orderID]`
- `invoices[invoiceID]`
- `lineIndex[(orderID, lineID)]`

发票保存原始行内容，所以被保留发票在补收货后可以重新判定；失败时不更新任何 `lineRecord.invoiced`，因此不会占用匹配额度。

## 判定规则

### 收货

正向收货后的数量上限为：

```text
ordered + floor(ordered * overReceiptPermille / 1000)
```

冲销先计算 `received - quantity`：

1. 小于 0，拒绝为 `negative_receipt`。
2. 小于已放行发票占用量，拒绝为 `receipt_invoice_held`。
3. 超过超收上限，拒绝为 `over_receipt`。

只有全部检查通过才更新累计收货量。

### 发票

一张发票明确属于一个采购订单和一个供应商。逐行按原下标从 0 开始检查，并返回第一个失败行：

1. 订单行不存在：`order_line_not_found`。
2. `abs(invoicePrice - poPrice) > floor(poPrice * priceTolerancePermille / 1000)`：`price_mismatch`。
3. `历史已放行量 + 本发票此前行暂存量 + 当前行量 > received`：`over_invoiced`。

同一张发票内可以多次引用同一订单行；本行判定时会把该发票前面行的数量放入 `staged`。只有所有行通过后才一次性把数量提交到订单行。价格容差和数量边界均为“恰等通过，超过 1 拒绝”。

被保留的发票继续占用发票号，但不占用订单行数量。重新判定成功时使用重新判定请求的时间作为放行时刻。

### 付款

付款只允许针对已放行但未付款的发票。设放行时刻为 `approvedAt`：

- `payTime <= approvedAt + discountPeriodSeconds`：支付 `amount - floor(amount * discountPermille / 1000)`。
- `payTime > approvedAt + paymentPeriodSeconds`：支付成功但标记逾期。
- 折扣期之后、账期之内支付全额且不逾期。

## 拒绝优先级

总体优先级固定为：

```text
参数非法 -> 时钟回退 -> 对象不存在 -> 供应商冻结 -> 状态不符 -> 业务拒绝
```

发票提交在此基础上细化为：参数非法、时钟回退、发票号重复、供应商冻结、供应商与订单不一致、逐行业务判定。供应商冻结期间发票提交或重新判定直接拒绝，不创建或保留发票记录。

任何拒绝都在修改聚合状态和推进全局时钟之前返回，因此不会改变状态与时钟。

## 并发、线性化与确定性

所有公开操作在同一个 `sync.RWMutex` 写锁内完成“读状态、校验、修改、推进时钟”。因此并发调用的结果等价于这些操作按获得锁的顺序串行执行。由于成功操作的请求时刻单调，失败操作不改时钟，重放相同输入序列会得到相同状态和结果。

关键不变量：

- 任意订单行 `invoiced <= received`。
- 冲销后仍有 `invoiced <= received`。
- 收货量不超过订购量与向下取整超收额之和。
- 被保留发票不贡献 `invoiced`。

单把锁是有意取舍：三单匹配中多个字段必须在同一事务内一致提交，细粒度锁或通道流水线会显著增加死锁、锁顺序和部分提交风险；当前数据规模下单把写锁最简单、可证明且足够。

## 复杂度证明

设一张发票有 `k` 行。

- 订单、发票和订单行均通过哈希索引定位，单次查找为平均 `O(1)`。
- 每行只做一次订单行查找、常数次整数比较和金额计算；同一订单行在本发票内的暂存通过 `staged[lineID]` 维护。
- 发票全部成功后提交数量也是一次 `k` 行遍历。

因此一次提交或重新判定的时间复杂度为 `O(k)`，额外空间复杂度为 `O(k)`。该过程不遍历订单集合、历史收货集合或历史发票集合，成本不随订单总数、收货记录总数或历史发票总数增长。

## 被放弃的方案

- 扫描所有收货记录计算累计收货：放弃，因为会让发票判定随历史收货数量增长，且无法直接维护冲销后的净数量。
- 保存每次收货并在冲销时撤销指定收货单：放弃，因为需求是按订单行冲销数量，不是红冲某一张原始收货单；逐单引用会引入额外配对语义。
- 被保留发票预占数量：放弃，因为需求明确失败发票不占用匹配额度；预占会错误阻止后续其他发票。
- 逐行独立提交：放弃，因为整张发票必须全有或全无，部分提交会破坏“任一行失败则整张保留”。
- 发票跨多个采购订单：放弃，因为账期、折扣期和折扣千分比属于订单，跨单会使付款条件产生歧义；API 要求发票声明一个订单。
- 数据库事务：本交付聚焦可重放的内存领域模型；接口把策略与存储隔离，后续可用数据库唯一索引和单行/聚合事务替换存储层。

## 日志

可选注入 `Logger`。服务日志记录：

- 操作输入：对象号、供应商、订单、行数、数量、是否冲销、时间等。
- 操作输出：接受/拒绝、状态、金额、失败行、失败码、折扣、逾期标志。
- 判定依据：订单价、发票价、价格容差额、历史已开票量、本发票暂存量、新增量和实际收货量。

随机朴素模型也独立打印输入、输出和决策中间量；两边分歧时测试失败信息会附带模型日志。

## 本地验证

仓库环境若未把 Go 放入 `PATH`，使用 `/usr/local/go/bin/go`，并可指定可写缓存：

```bash
GOCACHE=/tmp/go-build-cache GOPATH=/tmp/gopath /usr/local/go/bin/go test ./...
GOCACHE=/tmp/go-build-cache GOPATH=/tmp/gopath /usr/local/go/bin/go test -race ./...
GOCACHE=/tmp/go-build-cache GOPATH=/tmp/gopath /usr/local/go/bin/go vet ./...
/usr/local/go/bin/gofmt -l .
```

随机对照默认运行 200 条时间线，每条 120 个操作，覆盖收货/冲销、提交、保留重判、冻结/解冻和付款。可用固定种子直接复现：

```bash
GOCACHE=/tmp/go-build-cache GOPATH=/tmp/gopath /usr/local/go/bin/go test -run TestRandomOperationsMatchNaiveModel -v ./...
```

复杂度还提供基准实证。基准预先构造 10/1000 个订单和每订单 10/100 条历史收货，然后反复对目标单行发票执行完整提交判定（以稳定的超开保留结束，不逐次污染目标数量）：

```bash
GOCACHE=/tmp/go-build-cache GOPATH=/tmp/gopath /usr/local/go/bin/go test -run '^$' \
  -bench BenchmarkSubmitOneLineInvoice -benchtime=1000x ./...
```

本地小样本结果中，历史规模扩大 1000 倍订单和 100000 条收货后，单行发票判定仍在同一微秒量级；理论复杂度仍以 `O(k)` 证明为准，基准用于防止未来误引入历史扫描。
