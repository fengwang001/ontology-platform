# 配送车辆路线执行监控设计说明

## 模块划分

- `types.go`：领域类型、错误哨兵、配置、站点、行程结果和操作日志。
- `simulation.go`：无状态纯推演。输入站点状态、行驶时长表、连续驾驶种子和起始下标，输出各站结果。
- `monitor.go`：线程安全状态机，负责参数校验、时钟、拒绝原子性、上报、取消、ETA 发布和后缀重算。
- 测试中的 `naiveState`：独立朴素模型。每次根据全部已接受操作从行程起点推演，用于与生产增量状态机随机对照。

## 推演规则

每个普通候选站计算：

1. 从最近物理到达锚点取得行驶段。
2. 若累计连续驾驶加本段行驶严格大于上限，在离开锚点前加入规定休息。
3. 到达早于窗左端点则等待；恰在右端点准时；晚于右端点迟到。
4. 软窗迟到正常服务；硬窗迟到标记为 `StatusSkipped`。
5. 等待加服务总时长不短于休息时长时，连续驾驶清零；恰等于也清零。

硬窗跳过站不服务、不停留，但仍是物理到达点。推演器保存两类锚点：

- 物理锚点：最近实际到达的站点，可用于逐段行驶和连续驾驶累计。
- 服务锚点：最近实际服务并离开的站点，用于状态解释和取消、上报的顺序语义。

实际上报不允许改变已经发生的过去，因此只能在当前未上报、未跳过、未取消的站点发生；接受后，该站和之后站点重新推演。

## ETA 发布

- 首次推演为每个未到达、未跳过、未取消的站点发布 ETA。
- 重新推演后，差值绝对值严格大于防抖阈值才更新；恰等于阈值不更新。
- 若新推演 ETA 距当前时钟小于或等于锁定窗口，则不再更新，旧发布值保留。
- 已到达、已上报、已跳过或已取消的站点不再持有发布值。
- 后缀重算生成的节点会先复制旧发布元数据，再由发布器重新判定，避免“重算节点无发布历史”而误发布。

## 后缀复杂度

`nodeResult` 保存 `prevPhysicalIndex`。更新时：

- 用 ID 索引 O(1) 定位站点。
- 用操作站前一个结果中的前驱下标 O(1) 取连续驾驶种子。
- 从受影响起点单遍扫描到路线末尾。
- ETA 发布也从操作点开始扫描后缀。

因此，一次接受操作的工作集是受影响后缀，访问次数为 `N-pivot+O(1)`，不随 pivot 之前的站点数增长。`TestSuffixSimulationDoesNotVisitPrefix` 使用推演仪器直接断言访问次数。

## 并发与原子性

`Monitor` 内部使用单一互斥锁保护时钟、站点状态、推演结果和发布状态。所有并发调用的结果等价于某一个串行顺序。拒绝路径在校验全部通过后才复制并提交状态，因此不会更新时钟或结果。

## 关键取舍

- 选择单锁串行化，而不是无锁结构：领域状态存在强顺序约束，单锁更易证明线性化，且路线站数通常较小。
- 选择纯函数式推演器：便于朴素模型、重放、后缀单元测试和未来持久化事件源接入。
- 选择同时保存物理锚点与服务锚点：硬窗跳过、连续驾驶和后续行驶时长是三种不同关注点，强行只用一个锚点会混淆“到达但不停留”和“完成服务”。
- ETA 发布元数据与调度结果分开：调度时刻可因新信息改变，但对外承诺必须遵循防抖和锁定策略。

## 被放弃的方案

- 每次更新全量重算：语义最简单，但不满足开销不随前缀增长的要求，只保留在测试朴素模型中。
- 每个站点独立增量补丁：看似高效，但连续硬窗跳过和连续驾驶传播需要跨站上下文，容易产生不一致。
- 无锁 CAS 更新：冲突操作会频繁重试，且无法直接保证复杂拒绝优先级和状态回滚。

## 本地验证

```bash
GOCACHE=/tmp/go-cache-ontology /usr/local/go/bin/go test -race -count=1 ./...
GOCACHE=/tmp/go-cache-ontology /usr/local/go/bin/go vet ./...
```

随机测试会构造 300 个随机行程，并在每个行程上执行混合上报、取消和拒绝操作；每步都与独立朴素模型比较完整快照。失败时输出种子、配置、站点、非对称行驶时长表、操作输入、双方错误和判定依据。
