# 备份重建裁决组件设计说明

## 1. 问题界定

本体平台把四类数据分别独立备份：

| 类别 | 固定顺序 | 领域依赖 |
| --- | --- | --- |
| 对象类型定义 `Type` | 0 | 无 |
| 对象实例 `Object` | 1 | 所属类型定义 |
| 链接实例 `Link` | 2 | 两端对象实例 |
| 动作执行记录 `Action` | 3 | 涉及的全部对象与链接 |

每一类备份都可能整体缺失、整体损坏，或部分记录损坏。裁决组件只做两件事：

1. 判定每条记录是否可重建、给出可复核的判定依据；
2. 在所有满足依赖的重建顺序中，按固定规则选出**唯一**顺序，并显式标出“某一类已重建完成”的时点。

裁决是纯只读操作：同一输入多次并发裁决，输出完全一致，且输入快照不被修改。

## 2. 组件划分

代码位于 `restore/` 包，职责切分为两层，互不知道对方的内部数据结构：

- **单类内部可用性判定（`classifier.go`）**：只看某一类备份自身。
  产出 `ClassStatus`：`ClassOK` / `ClassPartial` / `ClassUnavailable`，
  以及记录级的原始状态（完好 / 损坏）。它不做任何跨类推断——
  类型定义整体缺失时，即使对象实例切片里残留了 `TypeKey`，也不允许反推类型。
- **跨类别依赖核对与排序（`dependency.go` + `adjudicator.go`）**：
  从快照推导依赖图，做记忆化恢复判定、环检测、唯一拓扑排序，
  并按固定优先级汇总错误。`reassess.go` 处理重建中途新发现的损坏。

`model.go` 只放数据结构与对外入口；`audit.go`/`query.go` 分别负责
审计落盘与逐条复核；`naive.go` 是仅供测试对照的朴素参照模型。

## 3. 判定流程

### 3.1 单类判定

对每个类别独立执行：

1. `Missing` 或 `CorruptAll` 为真 → `ClassUnavailable`，
   类内所有记录标为“类整体不可用”种子死点（无论切片是否残留数据）；
2. 否则统计记录状态：完好与损坏并存 → `ClassPartial`；全部损坏 → `ClassUnavailable`；
   全部完好（含空备份）→ `ClassOK`。

部分损坏时，完好记录照常进入后续判定，绝不因为同一备份中存在坏记录而放弃好记录。

### 3.2 依赖图与逐条恢复判定

依赖边 `from -> to` 表示 `from` 依赖 `to` 先完成：

- 对象 → 类型；链接 → 两端对象；动作 → 涉及对象/链接（去重、逐一保留）。
- 引用指向不存在记录的边保留为**悬空引用**，引用方按断引用判死。

对每条记录按固定次序核对（`resolveWithMemo`）：

1. 目标不存在 → 断引用；
2. 目标在种子死点集合 → 沿用种子原因（类整体不可用 / 自身损坏）；
3. 依赖按 `(类别序, 键序)` 逐一核对，第一个失败原因沿链向上传播；
4. 全部通过 → 可恢复。

类型整体缺失的优先级高于普通级联：若一条动作最终因类型整体缺失而不可恢复，
其原因链上保持 `ReasonClassUnavailable`，便于与“部分损坏级联”区分。

动作记录的每个对象/链接依赖被逐一核对，恰好在可恢复边界上的依赖也不例外：
全部依赖落在可恢复侧才可恢复；任一项落在不可恢复侧即判死，没有“不确定”中间态。

### 3.3 环检测

在“种子死点之外的活节点”子图上做三色 DFS：

- 回溯边标出环成员；环成员与依赖环成员的全部下游节点记为 `ReasonCycle`，
  它们的重建顺序无法确定，不进入计划。
- 同类环（含自环，只可能来自畸形数据）只影响环成员及其下游，
  **不连坐**类内其余完好记录。
- 跨类别反向依赖环（例如类型反向依赖对象）额外破坏固定类别序：
  这类屏障在拓扑排程阶段自然无法定位，相关记录不会进入计划。

### 3.4 唯一重建顺序

排程使用带**类别屏障**节点的 Kahn 拓扑：

- `barrier_c` 依赖类别 c 的全部可恢复记录；所有更高类别的记录依赖 `barrier_c`。
- 每轮在入度为 0 的节点中取序键最小者。序键固定为：
  屏障 `(类别rank+1, 0)`，记录 `(类别rank, 1, 记录键)`。

由此得到的计划形如：

```
type:* → barrier:type → object:* → barrier:object → link:* → barrier:link → action:* → barrier:action
```

屏障步骤直接回答题面要求：任何一类数据在其依赖数据之前不会被标记为已重建完成；
同类内、不同类间的并列全部由固定序键裁决，不存在任何自由选择，
因此重复裁决永远得到同一计划。某类没有可恢复记录时不生成该类屏障，
空备份不会凭空阻塞更高类别。

## 4. 错误的固定优先级

`Errors` 严格按以下顺序输出（同级内按类别、记录键排序）：

1. `ErrClassUnavailable`：某类备份整体缺失/整体损坏。
   这是“结论失去依据”级别的问题，必须最先报告——类型整体不可用时，
   其下一切实例/链接/动作的讨论都没有意义，且禁止从残留片段反推类型。
2. `ErrCascade`：部分不可用导致的级联不可重建（含自身损坏、断引用、
   依赖落在不可恢复侧）。这是结构层面可独立确定的问题，先于排序问题。
3. `ErrCycle`：循环依赖导致顺序无法确定。环只在仍可能恢复的子图上判定，
   已经整体不可用的部分无需再谈顺序，因此排在级联之后。
4. `ErrNewDamage`：重建过程中途新发现的损坏。它是运行期事件，
   只能叠加在此前结论之上，故最后报告。

单条记录的多重原因按同一优先级体现在其 `Reasons` 中，不产生模糊结论。

## 5. 中途新发现损坏（Reassess）

`Adjudicate` 得到计划后，若执行到一半发现新损坏，调用 `Reassess(prev, snap, progress, report)`：

- `Progress.Completed` 中已完成的记录标记为 `ReasonAlreadyCompleted`，
  **结论不撤销**，并继续作为后续记录的可用依赖；
- `DamageReport.NewlyCorrupt` 与 `NewlyClassUnavailable` 成为运行期死点，
  立即停止依赖它们的后续重建——实现上是在最新快照上重算全部依赖；
- 被新损坏级联阻断但此前可恢复的未完成记录，标 `ReasonBlockedByNewDamage`，
  归入优先级4，与初始裁决的前三类错误严格区分；
- 已完成节点即使出现在新损坏报告中也不回滚。

## 6. 关键取舍与被放弃的方案

- **放弃“凭残留实例猜测缺失类型”的恢复策略**：这会使裁决结果依赖猜测规则，
  破坏确定性与可复核性。题面明确禁止，因此类型整体不可用时一律级联判死。
- **放弃“部分损坏即放弃整类”**：部分可用必须保留好记录。实现上把
  “类整体不可用”与“记录级损坏”分成两个独立的种子来源。
- **放弃深度优先或插入序拓扑**：两者对并列节点的选择依赖输入顺序，
  无法保证跨调用一致。改用固定序键的 Kahn，输出唯一且可解释。
- **放弃把屏障语义编码成“类状态位”**：类状态位无法表达跨类反向依赖。
  显式屏障节点让“何时可标记一类完成”成为普通拓扑约束，环也自然暴露。
- **放弃环连坐整类**：同类环只说明环上成员无法排序，不影响类内无关记录；
  连坐会高估损坏范围，也与朴素参照模型的逐步判定不符。
- **朴素模型不做复用优化**：`naive.go` 刻意用不动点迭代 + 独立三色 DFS，
  不共享裁决器的图算法，避免“用被测算法证明自己”。

## 7. 复杂度与可复核方式

设记录数为 V、依赖边数为 E。

- 全量裁决：建图 O(V+E)（含去重排序，最坏 O(E log E)），
  恢复判定是一次记忆化 DFS O(V+E)，环检测 O(V+E)，
  Kahn + 每轮最小选取 O((V+C) log(V+C))（C 为屏障常数 4）。
- 单条记录：`CheckSession.Check` 返回本次沿依赖链**实际查看的边数**
  （`EdgesLooked`）。会话内记忆化使每条边只被展开一次；
  新记录命中缓存是 O(1) 查表，因此一条记录的增量判定开销上界是
  其自身依赖链长度，不随总规模增长。

`TestPerRecordWorkBoundedByChainLength` 用 40 长链 + 长度 1 的旁挂短链
直接断言：长链尾查看 39 条边，短链查看 1 条边，与总规模无关。
这是不依赖复杂度证明手段的、可运行的复核方式。

## 8. 并发与只读

- `Adjudicator` 无字段、无共享可变状态；每次裁决在局部 `engine` 上工作。
- 32 goroutine 并发裁决同一带损坏快照的测试（`-race` 下）逐字段比较，结论一致。
- `TestReadOnlySnapshot` 对裁决前后的快照做 JSON 序列化比对，保证零修改。

## 9. 本地验证

```bash
go test ./...
go test -race ./...
go vet ./...
go test -coverprofile=coverage.out ./... && go tool cover -func=coverage.out
```

随机对照审计文件由测试生成在 `testdata/fuzz/cases.jsonl`
（每行一个用例：固定 seed、输入快照、类状态、逐条结论与依据、计划、错误码、
与朴素模型是否一致），可直接人工抽查或做离线复核。
