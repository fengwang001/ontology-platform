# 商家出餐节奏与压单控制系统 — 设计说明

## 模块划分（kitchen 包，6 个 .go 文件）
- `estimate.go`：开工推定纯函数。制作位小顶堆 + 等待订单一次模拟调度，
  预约单按 (目标开工时刻, 接单序号) 参与，循环次数恰为等待订单数。
- `throttle.go`：压单状态机。进入仅由被接受的即时单准入判定触发，
  退出由准入判定/完成报告/排队单取消后的假想单重推触发，事件严格交替。
- `kitchen.go`：订单生命周期、全局单调时钟、暂停/恢复、单互斥锁并发协调。
- `errors.go`：哨兵错误，按规格次序逐个判定，只报第一个命中。

## 关键取舍
- 开工采用懒推进：只在被接受操作的末尾按确定次序开工，开工时刻取
  max(制作位空出时刻, 订单可开工时刻)；拒绝的操作连时钟都不推进，
  因此"被拒绝则零副作用"天然成立，重放结果逐位一致。
- 推定与实际开工共用同一套优先级规则（已到点预约单 > 即时单按接单序），
  推定中空闲制作位用真实空出时刻（可早于 now），使"目标开工时刻不晚于
  本单推定开工时刻的预约单计入"成为模拟的自然结果而非特判。
- 时钟只在操作被完全接受后推进；校验（checkClock）与推进（acceptClock）分离。
- 性能证明不依赖计时：EstimateOps 计数器记录每次推定调度的订单数，
  测试断言 2000 笔历史前后同一判定的增量完全一致（只等于当前等待订单数）。

## 被放弃的方案
- 事件堆/时间轮驱动开工：状态机更复杂，且拒绝操作的"零副作用"难以保证。
- 完成时按完成报告反向重算全部承诺：会破坏已发出承诺的稳定性，规格只要求
  重新推定压单状态，故承诺取货时刻在接单时一次性确定。
- 计时基准证明性能：在 CI 上不稳定，改用调度计数器做确定性证明（另附基准）。

## 本地验证
- `go test ./kitchen/`：阈值恰等、滞回、预约计入/插队、提前完成退出、
  暂停、取消降等待、事件交替、错误次序、并发上限、历史无关性。
- `go test -race ./kitchen/`：并发交错下等价于某串行序。
- `go test ./kitchen/ -run TestRandomSequenceMatchesNaive -v`：三个场景
  （稠密/稀疏/单位高提前量）随机序列与独立逐秒朴素模型及重放实现逐步比对，
  日志含每步输入、输出与判定依据。
- `go test ./kitchen/ -run XXX -bench .`：1 万笔历史后准入判定耗时恒定。
