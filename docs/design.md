# 动作事务审计溯源子系统 — 设计说明

## 1. 目标与不变量

子系统由三类职责清晰分离的模块协作完成：

| 模块 | 文件 | 职责 |
| --- | --- | --- |
| 动作事务执行 | `audit/executor.go`、`audit/store.go` | 执行/回退动作、订正，保证动作与审计原子生效 |
| 审计记录与存证 | `audit/log.go` | 只增序列、每类型单调连续序号、SHA-256 哈希链存证、篡改检测 |
| 重放重建 | `audit/replay.go`、`audit/naive.go` | 周期快照快速区间重放 + 朴素线性参考模型 |

核心不变量：

1. 序号在**同一对象类型**内从 1 开始严格递增、无空洞；提交、回退、订正都占序号；审计写入失败不占序号。
2. 回退记录 `Before == After`（明确“未生效”），与提交记录通过 `Kind` 区分；重放跳过回退。
3. 审计记录与状态变更**同生同灭**：审计先落盘，状态才在同一把类型锁内提交；审计失败则丢弃事务暂存，状态保持原样。
4. 记录只增、不可改、不可删；订正以新记录追加，原记录原样保留。
5. 订正记录必须指向已提交动作，不能指向另一条订正记录。
6. 同一类型上的执行/订正由一把类型锁串行化，因此并发结果等价于某个全局串行顺序；序号不会重复或出洞。
7. 区间 `(from,to]` 重放是纯函数：同区间任意多次结果完全相同，读取记录数只与区间长度和快照间隔有关，与历史总长无关。

## 2. 审计记录模型（`audit/model.go`）

```
Record {
  Seq       int64    // 类型内单调连续序号，从 1 开始
  Kind      Kind     // ACTION(提交) / ROLLBACK(回退) / CORRECTION(订正)
  ActionID  string   // 动作标识
  Changes   []Change // 本次涉及的全部实例及 Before/After
  TargetSeq int64    // 仅订正：被订正动作的序号
  PrevHash  []byte   // 前一条记录哈希
  Hash      []byte   // 本条记录全字段哈希
}
Change { Instance, Before, After string }
```

- 注册新实例也是一次经过审计的提交动作（`ActionID = "register:<实例>"`，`Before=""`），因此**仅凭审计序列即可独立重建包含初始值在内的全部历史**，无需任何旁路元数据。
- 值被建模为不透明字符串（生产中可替换为 JSON/protobuf 序列化字节），审计不解释其内部结构。

## 3. 原子性：审计与状态同生同灭

`Executor.Execute` 在**每对象类型一把锁**内严格按下列步骤执行：

1. 从 `StateStore.Begin` 取得基线快照的私有事务视图；校验参数（目标实例必须存在）。
2. 在私有视图上产生写入意图（`Txn.Write` 只写私有 map，底层状态一行不动）。
3. 业务函数返回 `ErrActionRolledBack` ⇒ 生成 `Before==After` 的回退记录，追加审计，丢弃暂存；状态不变。
4. 否则调用 `AuditLog.Append`：
   - `Append` 在类型锁内“失败判定 → 分配序号 → 计算哈希链 → 落入切片”，失败注入发生在分配序号之前；
   - 追加失败 ⇒ `Txn.Rollback()` 丢弃私有视图，返回 `AuditWriteError`。底层状态自始至终未被触碰，天然撤销，且不占序号；
   - 追加成功 ⇒ 紧接着在同一临界区 `Txn.Commit()`，状态对外可见。

由于“审计落盘”和“状态提交”在同一把类型锁内先后紧邻完成，且状态在审计成功前只存在于私有视图，因此不会出现“状态已变但审计缺失”，也不会出现“审计存在但状态未变”。

> 单机内存模型下这把锁就是线性化点；若演进到崩溃恢复的持久化部署，线性化点应放在“WAL/审计记录 fsync 成功”之后再应用状态（WAL 本身即审计序列），恢复时重放审计即可。这是被放弃的替代方案中刻意保留的方向（见 §7）。

## 4. 只增日志、序号与不可篡改存证

- 每类型一个 `logShard`：`Append` 持该 shard 锁，序号 = `len(records)+1`，因此并发序号严格递增、无重复、无空洞。
- 记录一旦写入，外部只能通过 `At/Range` 拿到**深拷贝**；API 层不提供任何 update/delete。
- 哈希链：`H_n = SHA256(序号 || 类型 || ActionID || TargetSeq || 全部(Instance,Before,After) || H_{n-1})`。`VerifyChain` 重算全部哈希并核对序号连续性，任何对历史记录的修改/删除/插入都会被检测到（测试 `TestImmutableTamperDetected` 直接篡改底层切片验证）。

## 5. 订正语义

订正记录追加在序列尾部，携带 `TargetSeq` 与每个实例订正后的值。

采用的语义（关键取舍）：

- **订正替换其指向动作的“增量”，但不倒装之后发生的独立写入。**
  重放到订正序号时，若某实例当前值仍来源于原动作（前向 provenance 指向 `TargetSeq`），就替换为订正值；若该实例在原动作之后又被更晚的提交写过，则保留更晚写入的值。
- 该规则与“从头重算：把原动作换成新值、然后把后续记录照常叠加”完全等价，因而确定性、可重入。
- 对同一原动作允许多次订正（链式采用最新订正值，通过 `frame.eff[targetSeq]` 维护）；但一条订正记录本身不能成为订正目标（参数非法）。
- 订正动作也在同一临界区把订正值应用到活动状态（仅替换当前值仍等于原动作 After 的实例），保证活动状态 == 重放终态。

校验顺序（只报第一个命中的原因）：

1. 参数非法：目标实例不存在；被订正序号不存在；被订正的是订正记录/非提交记录；订正实例集合与原记录不一致。
2. 审计写入失败（`AuditWriteError`）。

两类错误是不同类型（`*IllegalRequestError` vs `*AuditWriteError`），可用 `errors.As` 区分。

## 6. 区间重放与“开销只与区间长度相关”

### 快速重放器（`Replayer`）

- 订阅日志追加事件，前向维护一个状态帧 `frame{values, prov, eff}`，每 `interval` 条记录存一个**不可变周期快照**。每条追加仅做常数次 map 更新（摊还 O(1)）。
- 重放 `(from,to]`：二分找到“不晚于 from 的最近快照”，从该快照克隆后只扫描到 `to`。
  审计读取条数 ≤ `interval + (to-from)`（起点态与终点态各扫描一次，故上界约 `2*interval + 区间长度`），**不含历史总长因子**。
- `StateFrom/StateTo/Events` 由同一基础重放计算；回退记录不产生事件；订正按 §5 产生差异。

### 朴素模型（`NaiveModel`）

独立维护（不共享快照/索引），每次重放都 `Range(0,toSeq)` 从序号 1 线性扫描全部记录。它显然正确但成本随历史线性增长，作为差分测试的预言机。

### 可验证的成本证明

`AuditLog` 暴露 `ResetReadCounters/RangeReadCount` 统计区间重放实际读取的记录条数。
`TestReplayCostIndependentOfHistoryLength` 在历史长度 500 与 1000 下分别重放一个固定长度 10 的尾部区间：

```
历史长度 500：快速重放读取 = 102；朴素从头扫描 = 501
历史长度 1000：快速重放读取 = 102；朴素从头扫描 = 1001
```

快速重放两次读取量相同且有与历史无关的常数上界，朴素模型随历史线性增长——以可执行的测量证明“重放开销不随历史记录总数增长”。

## 7. 关键取舍与被放弃的方案

- **放弃“订正无条件覆盖当前值”**：若原动作之后有独立写入，无条件覆盖会倒放历史、使重放不具备“叠加后续记录”的自然语义，且与朴素重算不一致。改为 provenance 判定（§5）。
- **放弃“序号全局跨类型连续”**：需求明确序号范围是“同一对象类型”，按类型分 shard 既满足语义又允许类型间并行；跨类型的全局次序仅用于等价串行化论证，不分配全局号。
- **放弃“审计失败也占号”**：占号会在“仅尝试但未持久化”的情形制造需要特殊标记的空洞语义；需求要求空洞指“成功分配但缺失”，而注入失败发生在分配之前，因此失败不占号、随后动作拿连续序号。业务回退占号（它确实完成了一次可记录的尝试）。
- **放弃基于外部数据库/消息队列的方案**：为保证离线可测、零第三方依赖、竞态可在 `go test -race` 下验证，采用进程内类型锁 + 内存日志 + 哈希链；持久化演进路径已在 §3 标注（审计即 WAL，fsync 后应用状态，崩溃后重放）。
- **快照选择周期 checkpoint 而非每次全量**：每条追加摊还 O(1)，区间重放有常数上限；全量快照会让追加变 O(n)。
- **值用不透明字符串**：把序列化/schema 演进留给上层，审计只保证字节级前后镜像与可哈希性。

## 8. 本地验证方法

需要 Go 1.26+（本仓库 `go.mod` 要求 1.26.5）。若 `go` 不在 PATH 且默认构建缓存只读，可：

```bash
export PATH=$PATH:/usr/local/go/bin
export GOCACHE=/tmp/gocache

go run ./cmd/auditdemo        # 端到端演示
go test -race -v ./...        # 全量测试（含竞态检测，打印输入/输出/依据）
go test -run TestReplayCostIndependentOfHistoryLength -v ./audit
go vet ./... && gofmt -l .
```

测试清单：

- `TestCommitVsRollbackDistinction`：提交/回退在序列中的区分、回退占号、重放跳过。
- `TestAuditFailureRollsBackAtomically`：审计失败导致状态与审计一致回退、无空洞；与参数非法可区分且参数非法优先。
- `TestCorrectionOverridesOriginal`：订正覆盖原记录影响、原记录不被替换、订正不得指向订正、区间幂等。
- `TestImmutableTamperDetected`：篡改被哈希链拒绝。
- `TestConcurrentNoGapNoDup`：200 个并发动作序号无重复无洞，终态 == 串行重放。
- `TestReplayCostIndependentOfHistoryLength`：重放读取量的历史无关性度量。
- `TestRandomDifferential`：5 个随机种子 × 300 轮随机“提交/回退/审计失败/参数非法/订正”，每轮 3 个随机区间 + 全量终态，快速重放器与朴素线性模型逐条对照。
