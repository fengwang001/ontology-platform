# 权限固化导出与事后审计追溯器 — 设计说明

## 1. 问题与目标

本体平台的对象快照导出，需要把“导出那一刻执行主体对各属性的权限判断”**固化进导出结果本身**：

- 哪些属性因无权限被排除；
- 排除依据是继承链上**实际命中的那一条规则**的标识与内容；
- 之后无论继承链如何变更（覆盖新增、覆盖删除回落、继承关系重组、规则删除），**已完成的导出结果与依据均不变、不消失、不改变含义**；
- 审计溯源能对任意历史导出回答“当时为什么排除了该属性”。

## 2. 核心模型

- **类型与继承**：每个类型持有一条**有序父链**。解析顺序为「派生类型在前」的先序 DFS、首次出现保留（见 `ontology/chain.go`）。
- **规则位置（命中点）**：规则声明位置由三元组 `(declaringType, subject, attribute)` 唯一确定，对应稳定 `RuleID`。这正是审计要求的“直接声明在哪个类型上”，可唯一确定命中点，无需输出整条继承链路径。
- **规则解析**：对某主体/属性，沿解析顺序找到**最近声明**的规则即命中并停止；无命中走默认策略。
- **默认策略 = ALLOW**：无规则或命中 `ALLOW` 都纳入导出；只有命中 `DENY` 才排除并固化依据。这是一个明确取舍（见 §7）。

## 3. 关键机制：内容寻址的不可变规则档案

这是满足“标识永久保留且不漂移含义”的关键，位于 `ontology/archive.go`。

- 每次 `PutRule` 都把规则当前内容固化为一个 **`RuleVersion`**：
  `VersionID = "rv_" + sha256(ruleID, declaringType, subject, attribute, effect)` 的前缀。
- 档案 `map[VersionID]*RuleVersion` **只增、不改、不删**。
- 因为标识是**规则内容的哈希**：
  - 规则被修改后，新内容得到**新 VersionID**，旧标识仍解析到旧内容；
  - 规则被删除，只删除“当前生效指针”，档案中的旧版本保留；
  - 继承关系重组不触及档案，历史依据照常解析；
  - 标识永远不可能“指向一个变了含义的规则”——含义变了标识必然不同。
- 导出记录 `ExportRecord.Excluded[*].VersionID` 保存命中版本标识；`Trace` 用它做**一次哈希表读取**取回命中时刻内容快照。

### 与规模无关的性能（可验证）

- 解析一条固化依据 = `archive.resolve` 中的**单次 map 访问 O(1)**，与该类型体系历史规则变更总次数 `N` **无关**，不扫描任何变更历史。
- `ruleArchive.reads` 对解析访问计数；`TestSealedBasisResolutionIsConstantTime` 在 500 次与 5500 次变更后分别断言解析访问次数恒为 `1`。这是确定性的结构证明，而非易抖动的计时基准。
- 导出时的继承解析为 `O(属性数 × 继承链上类型数)`，同样不读取历史变更；只有变更事件日志会随时间增长，它只用于审计/重放，不在判定热路径。

## 4. 数据固化内容

- **导出记录**（`ExportRecord`，只增存储于 `Platform.exports`）：`ExportID`、类型、对象、主体、发起时刻全局序号 `Seq`、纳入属性 `Included`、属性值快照 `Values`、以及每个被排除属性的 `ExclusionRecord`。
- **排除依据记录**（不可变）：属性、`VersionID`、`RuleID`、`DeclaringType`、`Effect`。
- **审计返回**（`TraceResult`）：命中规则标识、命中时刻的完整 `RuleVersion` 内容快照、以及直接声明类型（包含在版本快照内）。
- 对外返回的导出/规则对象一律给**副本**，调用方无法篡改档案与历史记录。

## 5. 并发与串行化

- `Platform` 用**单一互斥锁**保护全部状态；`Export`、`PutRule`、`DeleteRule`、`SetParents` 全程持锁。
- 因此任意并发交错都严格等价于某个**全局串行顺序**。导出在持锁区间内完成“线性化 → 逐属性命中判定 → 固化写入”，不可能混入之后才生效的调整。
- 每次成功状态变更加载单调 `Seq`；导出记录携带发起时 `Seq`。
- `Platform.events` 是只增变更事件日志，可重建任意 `Seq` 时刻的规则状态。并发测试据此重放，逐一核对每次导出的固化结果恰好等于其发起时刻状态。

### 被放弃的并发方案

- 多版本并发控制（MVCC）/快照隔离：语义正确，但本问题规模下单锁已足够且更易审计；为单一判定点引入版本链与 GC 属于过度设计，列为后续演进项。
- 无锁/细粒度分段锁：会让“发起时刻”的线性一致证明复杂化，且与“可审计的全局串行顺序”目标不符，放弃。

## 6. 错误类别与拒绝优先级

稳定错误类别（`ontology/errors.go`，用 `KindOf(err)` 程序化区分）：

| 类别 | 触发场景 |
| --- | --- |
| `OBJECT_TYPE_NOT_FOUND` | 导出/变更时对象类型不存在；非法继承（悬空父、成环）也归此类别 |
| `SUBJECT_NOT_FOUND` | 导出时执行主体不存在（仅当类型存在后才检查） |
| `EXPORT_NOT_FOUND` | 审计溯源时历史导出记录不存在 |
| `ATTRIBUTE_NOT_EXCLUDED` | 属性在该次导出中**当时未被排除**（明确报告，而非记录缺失） |

- 导出拒绝优先级：**类型不存在 > 主体不存在**；其余属性逐一判定，不视为错误。
- 审计拒绝优先级：**导出不存在 > 属性未被排除**。
- 被拒绝的请求在校验阶段直接返回，**不推进 `Seq`、不写任何记录/规则/关系**（有测试断言）。
- `Trace` 为只读：幂等、结果可重复、不推进 `Seq`。

## 7. 关键取舍

- **默认 ALLOW**：无显式规则即可见。这样“排除”一定对应一条真实命中的 DENY，排除依据永远非空、可审计；若默认 DENY，“因无规则而排除”的情形没有规则标识可固化，会破坏“每次排除都附规则依据”的要求。
- **单继承语义用有序父链表达**：保留多父类型的有序线性化能力（去重先序 DFS），同时命中点仍唯一。放弃 C3/MRO：更强但复杂，对“最近声明命中 + 唯一命中点”的需求没有必要。
- **内容哈希作 VersionID（而非自增序号）**：自增序号会在规则删除后可能被重指或需要墓碑保护；内容寻址使“含义不变 ⇔ 标识不变”成为不变量，天然防重指。哈希碰撞以 SHA-256 截断 24 字节，概率可忽略。
- **只增档案不做 GC**：保证历史可永久审计；存储成本是“历史不同规则内容数”，对审计型系统可接受。
- **对象不单独建注册表**：导出以 `TypeID`（+ 可选 `ObjectID` 标签、属性值）为输入，错误类别严格限定为需求规定的四种，不额外引入“对象不存在”类别。

## 8. 判定日志

- `DecisionLogger` 接口在每个属性判定后输出一条 `DecisionLogRecord`（JSON 行日志器 `NewJSONLogger`），包含输入（导出、序号、主体、类型、属性）、输出（INCLUDE/EXCLUDE）与依据（命中版本、规则、声明类型、效果）。
- 生产可用 stderr/文件 sink；测试用内存 sink 断言。

## 9. 本地验证方法

需 Go 1.26（仓库环境位于 `/usr/local/go/bin`）。无第三方依赖，纯标准库。

```bash
export PATH=$PATH:/usr/local/go/bin
export GOCACHE=/tmp/gocache GOPATH=/tmp/gopath   # 仅当 HOME 缓存只读时

go test ./...                 # 全量测试
go test -race ./...           # 竞态检测
go test -v -run ExamplePlatform ./...
go vet ./...
gofmt -l .
```

测试覆盖（均在 `ontology/*_test.go`）：

1. 命中规则删除 + 继承重组后历史依据仍可解析（`immutability_test.go`）；
2. 同一属性在相隔多次导出中因覆盖新增/覆盖替换/删除回落/关系重组固化不同依据（`successive_exports_test.go`）；
3. 审计对“未被排除”与“记录不存在”的区分、拒绝优先级、只读幂等、拒绝不改变状态（`errors_audit_test.go`）；
4. 并发导出与规则调整交错下，固化结果对应发起时刻状态（事件日志重放对照，`concurrency_test.go`，`-race`）；
5. 与**独立朴素继承规则快照模型**的随机构造反演差分测试（`differential_test.go`，600 步随机交错，失败时打印随机种子）；
6. 规模无关的 O(1) 解析可验证断言（`performance_test.go`）；
7. 每次判定输入/输出/依据的日志断言（`logging_test.go`）；
8. 端到端可运行示例（`example_test.go`）。

> 差分测试在开发过程中实际抓到过一个生产缺陷：继承线性化最初误用“后序翻转”，在先序 DFS 语义下会选到错误祖先的规则；已修正为先序 DFS 并有差分测试长期回归。
