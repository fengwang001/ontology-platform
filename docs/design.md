# 快照导出协同组件设计说明

## 1. 核心模型

组件处理三类记录：

- 对象记录：`Record.Kind == object`；
- 链接记录：`Record.Kind == link`，必须包含 `SourceID` 与 `TargetID`；
- 动作执行记录：`Record.Kind == action`。

写入以事务为单位进入系统。`prepare` 只表示该事务有一条候选修改，尚未被接受；只有 `commit` 会获得一个全局、连续、只增的提交号 `CommitLSN`。`abort` 的事务不会获得提交号，也不会进入任何状态。

逻辑边界是一个整数提交位点：

- `0` 表示空快照；
- 正整数边界必须等于某个已接受的 `CommitLSN`；
- 归属区间为左闭：`CommitLSN <= boundary` 进入快照，`CommitLSN > boundary` 进入增量；
- 当提交时刻与边界位点重合，即 `CommitLSN == boundary`，固定归入快照，消除任意选择和重试差异。

在线请求使用 `AutoBoundary`（`-1`）时，边界在请求被串行调度执行的那一刻冻结为当前最新提交号。冻结之后，正在准备但尚未提交的事务不会进入快照，即使其 `prepare` 在墙钟时间上早于快照请求；它将来提交时整体成为一条增量。

## 2. 组件划分

- `BoundaryManager`（`snapshot/boundary.go`）负责解析边界、返回最新已接受位点，并只比较两个整数判定增量归属。
- `Validator`（`snapshot/checker.go`）负责跨写入核对事务原子性、记录合法性、链接引用完整性和资源上限。
- `Exporter`（`snapshot/exporter.go`）是纯函数式重放器，输入事件序列和边界，输出快照帧、有序增量帧、错误帧或完成帧。
- `Coordinator`（`snapshot/coordinator.go`）负责在线并发交互。所有写入和快照读取通过同一个 FIFO actor 队列串行化，保证可串行化；快照冻结后，后续提交在同一临界区追加为增量。

## 3. 原子性与引用完整性

一个事务中的所有对象、链接、动作修改缓存在同一个事务缓冲区内。提交时：

1. 先构造该事务的候选完整状态；
2. 对整组记录做引用完整性检查；
3. 通过后才分配提交顺序、提交整组记录；
4. 快照中将整组记录整体应用；增量中也把整组记录放入同一条 `Delta`。

因此不会出现“同一动作的对象修改已可见、链接修改尚不可见”的状态。即使对象和链接的 `prepare` 与其他事务交错，只要没有 commit，它们都不可见。

链接引用完整性在每个已提交事务形成的状态上检查：任何已可见链接的两个端点都必须存在于对象集合中。对象与链接在同一事务内的写入顺序可以任意，因为检查发生在整组修改的候选状态上。

删除采用最终状态语义：导出保存每类记录的当前值，`delete` 会移除对应记录。若某一已提交状态会留下端点不存在的可见链接，则该提交被拒绝。

## 4. 输出协议

纯导出器输出 `[]ExportFrame`：

- 第一个相关帧是不可变 `Snapshot`，携带冻结边界；
- 后续每个增量帧携带一个完整事务的 `Delta`；
- `Done: true` 表示给定事件序列已重放完；
- 出错时发送 `Error` 帧后停止尚未输出的部分。

在线 `Coordinator.Export` 会消费纯导出器产生的快照与历史增量，但不消费一次性 `Done` 帧；流保持打开，继续接收快照边界之后的提交。

已经输出的帧不会被回滚。错误只阻止尚未输出的事务或修改，这使下游可以保留已经确认的快照和增量前缀。

## 5. 错误分类与优先级

错误固定分为四类：

1. `boundary_definition_conflict`：边界不是 `0` 或现有提交号、提交号不连续、未知事件/记录类型、事件元数据破坏了日志位点定义。
2. `atomicity_conflict`：空事务提交、重复提交、提交后再写入、未提交事务残留、提交事件夹带记录等。
3. `referential_integrity_conflict`：链接缺少端点或端点对象在候选最终状态中不存在。
4. `resource_exhausted`：已提交事务数或记录数超过显式资源上限。

判定顺序固定为“边界 → 原子性 → 引用完整性 → 资源”。

理由：

- 边界首先定义“比较什么、在哪个前缀上解释日志”；边界无效时，后续归属没有确定语义。
- 原子性其次确定“哪些记录构成一个可观察状态转换”；事务边界不成立时，不能把部分记录送入完整性检查。
- 引用完整性只能对已经完整的事务状态判断。
- 资源不足是一种被迫中止策略，而不是数据语义违规；只有在同一事件本身语义有效时才报告资源，避免资源错误掩盖可复现的数据冲突。

`Limits` 中负数（可使用 `NoLimits`）表示不限，`0` 表示零容量，避免 Go 零值无法区分“默认不限”和“不允许任何记录”。

## 6. 并发正确性

`Coordinator` 内部只有一条无锁数据路径：所有操作封装为闭包，发送到一个无并发消费者的 FIFO 队列。

- 写事务的 `Begin`、`Append`、`Commit`、`Abort` 是队列操作；
- 快照读取选择边界和物化快照在同一个队列任务内完成；
- 快照之后新接受的提交也在提交所在队列任务中发送到对应导出流。

因此，对任意外部并发交错，系统实际执行都等价于这些队列任务按 FIFO 顺序的某个串行执行。唯一可能影响观察结果的是任务入队顺序，但每个可能结果都与该顺序下的串行执行完全一致。

## 7. 复杂度与可复核性

边界归属函数只执行一次整数比较：`commitLSN <= boundary`。

- 时间复杂度：`O(1)`；
- 空间复杂度：`O(1)`；
- 分配次数：测试通过 `testing.AllocsPerRun` 断言为 0；
- 工作量不读取对象表、链接表、动作表，也不扫描已处理记录，因此不随记录总数增长。

复核方式可以是代码审查、编译后汇编检查、分配测试或形式化证明；本实现提供 `TestBoundaryClassificationIsConstantWork` 作为可重复运行的机器复核。

需要区分：归属判定是 `O(1)`；首次物化全量快照仍需重放边界前事务，复杂度与快照内容规模相关；检查某一提交后的所有链接目前与当前状态规模相关。

## 8. 被放弃的方案

- 墙钟时间边界：被放弃。分布式时钟回拨、重试和并发交错会使同一笔写入在不同判定中得到不同归属。
- 右开或 tie-break 到增量：可以实现，但与“边界位置之前且包含边界处已接受写入”的自然左闭直觉不一致。最终固定为左闭，并明确重合时归属快照。
- 每条 prepare 独立分配序号：被放弃。这会把一个事务的候选修改提前变成可观察事件，破坏整笔事务原子性。
- 导出期间临时放宽引用完整性、随后补偿：被放弃。题面要求任意快照加增量前缀都自洽，不能把悬空链接暴露给下游。
- 为读请求加读写锁而不统一串行化：被放弃。边界选择与快照物化之间仍需证明线性一致；单 FIFO actor 更简单、可审计，适合本组件作为协同核心。
