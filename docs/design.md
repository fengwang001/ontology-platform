# 链接基数约束与批量导入原子性 —— 设计说明

## 1. 目标与范围

本子系统解决两个耦合问题：

1. **链接类型的基数上限校验**：每个链接类型可分别声明起点侧与终点侧的上限
   （恰好一、至多一、具体正整数 N，缺省为无限制），创建链接时任一端超限即拒绝。
2. **大批量导入的原子性**：一批有序链接在「全有或全无」与「尽力而为」两种
   整体语义中按调用方声明的一种执行；批内基数占用必须是累积的。

由三个职责单一的模块协作：

| 模块 | 文件 | 职责 |
| --- | --- | --- |
| 基数账本 | `ontology/ledger.go` | 链接存储、两端逐实例计数、单条创建/删除、同锁串行化 |
| 批量导入 | `ontology/importer.go` | 分批提交、批内去重、全有或全无的回退、逐条结果清单 |
| 错误归一化 | `ontology/errors.go` | 四类可区分错误与唯一的拒绝原因优先级 |

## 2. 核心数据结构

- `links map[LinkKey]struct{}`：链接类型 + 有序实例对唯一确定一条链接，
  存在性/去重是 O(1) 映射访问。
- `counts map[countKey]int`：键为 `(链接类型, 端, 实例)`。这是**逐实例**的
  增量计数，而不是按类型或按对象类型维护的总量。

创建成功时同时写入 `links` 并把两端两个计数各 +1；删除时逆操作，计数降到
0 即删除映射项。账本不变式：

```
对任意 (lt, side, instance)：
  counts[(lt, side, instance)] ==
    | { l ∈ links : l.type == lt ∧ 该端实例 == instance } |
```

测试中的 `countsMatchNaive` 每一步都用全量重数校验该不变式。

## 3. 校验链与错误优先级

单条创建与批量导入中的每一条共用同一套判定（导入器仅多一步批内重复检查），
严格按顺序只返回第一个命中原因：

1. 参数非法 `invalid_argument`：链接类型未注册、起点实例不存在、终点实例
   不存在、有序对在本批次内重复、有序对在存储中已存在；
2. 起点一侧基数超限 `source_cardinality_exceeded`；
3. 终点一侧基数超限 `target_cardinality_exceeded`。

删除一个不存在的链接是独立类别 `link_not_found`，与「基数已满导致创建被拒」
永不可混淆。错误统一为 `*LinkError`，可用 `AsLinkError` 按 `Code` 区分。

> 两端的基数结论本身相互独立；「只报一个原因」是错误归一化的要求。当两端
> 同时超限时，起点的原因先报；另一端的超限并未被「吞掉」——因为整条链接
> 不会创建，下一次重试时仍会重新独立计算。

## 4. 批量导入语义

整批在账本的同一临界区内执行，天然等价于全局串行序列中的一个操作。

- **批内累积**：第 i 条的校验看到的是前 i-1 条已接受后的账本状态，不使用
  批次开始前的快照。
- **全有或全无**：逐条校验并落库；一旦某条失败，立即把本批次此前接受的
  有序对全部删除并释放两端计数，随后的条目标记为 `skipped`。回退后账本与
  批次开始前逐项一致（差分测试每步核对计数与链接集合）。
- **尽力而为**：失败条目标记 `rejected`，不写库、不计数，后续条目照常处理；
  批内重复的第二次出现以 `invalid_argument` 被跳过，第一次出现不受影响。
- 被拒绝的条目**从不**调用写入路径，因此不可能占用基数或留下痕迹；
  全有或全无的中间态接受项也会被显式撤销。

结果清单 `BatchReport.Results` 与输入等长且同序，每条带状态
（`accepted / rejected / rolled_back / skipped`）与归一化错误。

## 5. 并发、可见性与确定性

- `Ledger` 用一把 `sync.Mutex` 保护全部读写，`Importer` 复用同一把锁。
  因此所有创建、删除、批量导入都存在唯一的线性化点，最终效果等价于某一
  全局串行顺序；不可能出现两个并发创建都读到「还剩 1 个名额」而后都成功。
- 删除的计数释放在同一临界区内完成，释放对后续创建的可见时刻就是删除的
  生效时刻，没有异步/延迟窗口。
- 操作逻辑不含随机、不依赖 goroutine 调度，重放同一序列得到同一状态
  （`TestDeterministicReplay`）。

## 6. 复杂度论证（校验不随链接总量增长）

校验一条待创建链接只做固定次数的映射访问：

| 步骤 | 次数 |
| --- | --- |
| 链接类型声明 | 1 |
| 起点/终点实例存在性 | 2 |
| 有序对去重 | 1 |
| 起点实例计数 / 终点实例计数（仅声明了上限时） | 0–2 |

合计 4–6 次，与该对象类型（乃至整个系统）的链接总数无关；它只依赖「该
具体实例当前的占用计数」这一标量。可验证手段有两个：

- `Ledger.CheckCost(linkType)` 直接返回上述工作单位数；
  `TestValidationCostIndependentOfTotalLinks` 在 0 / 512 / 2048 / 4096 条
  链接下断言该值恒为 6，并对照朴素模型必须扫描全部 n 条。
- `BenchmarkCreateDeleteAtFixedOccupancy` 在 10000 条链接的账本上反复
  创建/删除同一有序对（占用恒定为 1），ns/op 恒定（本机约 320 ns）。

## 7. 关键取舍与被放弃的方案

- **放弃「批量前预扫描、之后统一提交」**：预扫描基于批次前快照，无法表达
  批内累积占用，且与并发操作组合后需要两阶段锁；本实现采用「同锁内逐条
  校验即落库 + 失败回退」，语义直接、回退路径可被逐元素审计。
- **放弃每类型一个总数计数**：基数是端点局部的，按类型计数无法判断某个
  具体实例是否超限，反而需要回表遍历；逐实例计数键才让校验成为 O(1)。
- **放弃分片锁 / 无锁 CAS**：它们能提高吞吐，但会让「两端独立计数 + 批量
  原子回退」的全局顺序难以定义与重放。在正确性优先的前提下，单锁最简单、
  可证明线性化；吞吐扩展（分片到实例键）留作后续不改变语义的优化。
- **放弃惰性删除/延迟释放**：会制造「删除已生效但名额仍被占」的窗口，
  直接违反可见性要求；释放在删除临界区内同步完成。
- **ExactlyOne 与 AtMostOne 都按上限 1 处理**：「恰好一」包含「必须存在」
  的下限语义，属于链接完整性的另一类问题（通常在对象读取时校验），本子系统
  只负责创建期上限，避免把两种校验混在同一错误类别中。
- **朴素模型保留在测试包而非生产代码**：它 O(n) 重数的用途就是作为差分
  参照，放进生产路径会重新引入题目明确禁止的重复遍历。

## 8. 本地验证方法

```bash
# 全量测试（含输入/输出/判定依据的逐条日志）
go test ./...

# 竞态检测
go test -race ./...

# 只看随机差分（25 个种子 × 80 个随机操作，逐条打印）
go test ./ontology/ -run TestDifferential -v

# 复杂度验证与基准
go test ./ontology/ -run TestValidationCost -v
go test -bench=BenchmarkCreateDelete -run=^$ ./ontology/

go vet ./... && gofmt -l .
```

测试覆盖：批内累积导致后序条目被拒（前序条目独立合法）、两种语义对同一
输入的差异、恰好等于上限与超出一个的边界、删除释放后立即被并发创建占用、
单名额高并发下不超卖、同序列重放确定性，以及与朴素全量重数模型的大规模
随机逐条对照（链接集合与每实例计数双一致）。
