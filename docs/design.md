# 权限变更生效时序管理模块 — 设计说明

## 1. 问题与模型

每条权限规则变更携带两条相互独立的时间轴：

- **提交时刻** `Committed`：变更进入系统、参与排队的时刻。
- **生效时刻** `Effective`：变更开始约束访问判定的时刻，满足 `Effective >= Committed`。

一条变更 `Change` 的字段：`ID`（固有且全局唯一）、`Subject`、`Label`、
`Kind`（`Grant` / `Deny` / `Revoke`）、`Committed`、`Effective`、
`DependsOn`（可选，指向其内容所依赖的前置变更）、`Target`（仅 `Revoke` 使用）。

时刻用逻辑时钟 `Tick int64` 表示，由调用方提供；引擎自身不推进时钟，
因此同一输入（变更集合 + 查询时刻）的任何复算必然得到同一结果。

### 叠加全序

同一 `(Subject, Label)` 上的变更按 `OrderKey = (Effective, Committed, ID)` 全序排列：

1. 生效时刻早的在前；
2. 生效时刻相同则提交时刻早的在前；
3. 两者都相同则按固有唯一 `ID` 字典序。

第 3 级只依赖变更自身固有标识，与内容、提交顺序、内存地址均无关，
因而对相同输入的任意两次重算得到完全一致的叠加顺序。

### 查询语义（双轴可见性）

对时刻 `T` 的访问判定，只纳入同时满足 `Committed <= T` 与 `Effective <= T`
的变更。排队中的变更（`Effective > T`）与“未来提交”（`Committed > T`）
对该判定完全不可见。没有任何存活规则时采用**默认拒绝**。

## 2. 核心机制

### 2.1 单遍重放 `replay`

对已按 `OrderKey` 排好序的可见变更流做单遍重放（`temporal/replay.go`）：

- `Grant/Deny`：当且仅当其 `DependsOn` 前置此刻仍存活时成立；
- `Revoke`：当且仅当其目标此刻存活时成立；成立后立即杀死目标，
  并沿“谁依赖了谁”的**反向依赖边做 BFS 传递杀死**，这正是
  “后续依赖变更必须重新纳入考察”的确定化实现；
- 最终判定取全序上最后一条存活的 `Grant/Deny`；不存在则默认拒绝。

撤销是一条新的变更（不可修改/删除历史），且其自身也有生效时刻：
新基线**从撤销的生效时刻起**成立，更早的历史视图不受影响。
这与“历史查询可重复读”不冲突——该保证的前提是规则集合不再变化，
而一条更晚生效的撤销在历史查询时刻本就不可见。

### 2.2 排队撤回

`Withdraw(id, at)` 仅在 `at < Effective` 时成功，且变更被物理移出索引。
于是撤回后的变更对任何时刻（包括撤回前执行过的历史查询）都不可见：
因为那些历史查询的时刻上它本就尚未生效；一旦移出，它在未来也永不出现。
对已生效变更的撤回固定以 `ErrCodeWithdrawAlreadyEffective` 拒绝，
必须改用提交 `Revoke` 变更来覆盖/撤销。

### 2.3 追溯撤销的重新考察结论

提交 `Revoke` 时（提交时刻目标必须已生效，否则作为通用拒绝），
引擎同步给出 `Reassessment` 列表：枚举同一 `(Subject, Label)` 上
**生效时刻晚于被撤销目标**、且沿 `DependsOn` 链（传递）依赖该目标的每条后续变更，
分别在“无撤销”与“有撤销”两个世界重放，确定性地报告：

- `StillValid`：新基线下是否仍然成立；
- `EffectChanged`：其成立状态是否因本次撤销而改变；
- `Reason`：可读原因。

不依赖被撤销状态的变更（如测试中的 `independent`）不在列表中，
杜绝“简单假定不受影响”。

### 2.4 固定唯一的错误优先顺序

| 顺序 | 错误码 | 触发 |
|---|---|---|
| 1 | `EffectiveBeforeCommit` | 生效时刻早于提交时刻 |
| 2 | `QueryBeforeHorizon` | 查询时刻早于系统已知最早记录时刻 |
| 3 | `WithdrawAlreadyEffective` | 撤回已生效变更 |
| 4 | `Generic` | 重复 ID、未知目标、目标尚未生效却走撤销等 |

任何被拒绝的提交/撤回在落任何状态变更之前返回，排队状态与时钟不受影响
（由 `TestErrorPriorities` 固化）。

### 2.5 并发与可串行化

`Engine` 内部以单一 `sync.RWMutex` 串行化写操作（提交/撤回），
读路径（判定）持读锁且只读不可变切片。每个公开方法整体在锁内完成，
因此外部可观察到的任意并发交错都等价于某个逐条串行执行顺序。
审计日志在自带互斥锁内生成全局递增 `seq` 并写入，日志顺序同样对应一条串行化序列。
测试用 `-race` 验证无数据竞争（`TestConcurrentSerializability`）。

## 3. 查询开销的可观测证明

引擎为每个 `(Subject, Label)` 维护一个按 `OrderKey` 有序的变更桶。
一次 `Decide` 只在目标桶内做一次线性筛选 + 单遍重放，从不扫描其他桶。

更重要的是，这一性质以**不依赖实现细节的可观测字段**对外暴露：
`Decision.Examined` 等于“截至该时刻对该主体与该标签确实生效过的变更数”。
`TestQueryCostIndependentOfTotalRecords` 证明：

- 灌入 2000 条其他主体的变更、1000 条目标主体但尚未生效的排队变更后，
  目标查询的 `Examined` 与系统累计 1 条记录时**完全相同**，
  即不随系统累计提交总数 `len(Snapshot())` 增长；
- 每新增 1 条对目标在该时刻确实生效的变更，`Examined` 恰好 +1，
  证明它只与“截至该时刻对该主体与该标签确实生效过的变更数量”相关。

## 4. 关键取舍

1. **逻辑时钟而非墙钟**：由调用方提供 `Tick`，引擎纯函数化，天然支持任意历史
   时刻查询、可重复读与确定性随机差分测试；放弃了引擎内部物理时钟方案
   （会使历史复算依赖运行时刻，破坏可重复性）。
2. **依赖显式声明（`DependsOn`）而非内容推断**：“内容依赖于某状态”无法从
   Grant/Deny 字面值可靠推断，显式前置边使传递撤销确定、可解释、可测试；
   放弃了隐式数据流分析方案（语义模糊且不可判定边界过多）。
3. **撤销是带生效时刻的新变更**：保证历史不可变（不可改/删已生效记录），
   新基线从撤销生效时刻起；放弃了“撤销立即改写全部历史”的方案
   （会使已给出的历史判定被篡改，违背可重复读）。
4. **撤回采用物理移除**：被撤回变更从未生效，移除后对过去与未来均不可见，
   语义最简；放弃了“保留墓碑再过滤”的方案（徒增扫描成本与状态）。
5. **单把 RWMutex**：优先保证严格可串行化与代码可审计；未采用分段锁/无锁结构，
   因为正确性证明成本高于其吞吐收益（桶级分片是明确的后续扩展点）。
6. **朴素参照刻意异构**：`NaiveEngine` 从提交/撤回事件日志线性重建当前集合、
   全量筛选重放，与引擎共享的只有模型定义与 `replay` 纯函数，
   最大化差分测试发现偏差的能力。

## 5. 本地验证

```bash
export PATH=$PATH:/usr/local/go/bin GOCACHE=/tmp/gocache
go test -race ./...                 # 全量（含竞态检测）
go test ./temporal/ -v              # 逐个用例
go test -run TestRandomDifferential -v ./temporal/  # 40 组随机序列差分
go vet ./...
gofmt -l .
```

测试构成：

- `TestSameEffectiveTieBreaks`：同生效时刻的提交时刻/ID 两级破并；
- `TestHistoricalRepeatableRead`：历史可重复读 + 严格忽略未来提交/生效变更；
- `TestQueuedWithdrawInvisible`：排队撤回对任意时刻不可见；
- `TestRetroactiveRevokeCascade`：追溯撤销沿依赖边传递、独立变更不被波及、
  撤销生效前的历史视图保持不变；
- `TestCombinedBoundary`：同刻叠加 + 撤回 + 追溯撤销 + 历史复读的组合边界；
- `TestRandomDifferential`：40 个随机种子、每序列 400 次操作，并在结尾对
  全部 (主体,标签,时刻) 网格与朴素参照逐项对照，同时校验 `Reassessment`
  结论与重放存活状态自洽；
- `TestConcurrentSerializability`：并发提交/撤回/判定（`-race`）；
- `TestQueryCostIndependentOfTotalRecords`：开销可观测证明；
- `TestAuditCompleteness`：审计日志含输入、输出/错误、时序依据、序号与墙钟。
