# 权限沿链接类型图传播与覆盖网关 — 设计说明

## 问题模型

平台维护一个有向图：节点是对象类型（ObjectType），边是链接类型
（LinkType）。主体（Subject）对某对象类型的显式授权可以沿“参与
传播”的链接类型扩散给下游对象类型；目标类型可声明覆盖规则改写
或阻断传播结果。网关对外提供两类操作：

- 变更：对象类型注册/移除、链接类型增删改、覆盖规则设置/追加、
  授权（允许/否定/撤销）。
- 判定：`Decide(subject, target)` 返回最终生效的权限动作集合、
  拒绝原因与完整判定依据。

## 核心语义

### 传播与深度

- 链接类型声明 `Propagates` 与 `MaxDepth`；`MaxDepth == 0` 表示不
  参与传播，仅用于本类型的直接授权。
- 穿越链接 `L` 时剩余深度变为 `min(rem, L.MaxDepth) - 1`；结果
  `>= 0` 才允许穿越。因此“剩余深度恰为零的那一跳”仍然生效，
  再往外一跳自然终止——这是正常结果（`ReasonDepthExhausted`），
  不是错误。
- 每条链接的深度同时是“穿越该链接后还能走多远”的上限（取
  `min`），因此一条链路的有效传播半径被途经每条链接各自的
  深度共同约束。

### 状态模型（关键取舍 1）

传播遍历的状态是 `(当前类型, 来源类型, 剩余深度)`：

- 携带的权限集合永远是“来源类型的直接授权”。非覆盖类型原样
  透传；穿越 `replace` 覆盖类型后来源被替换为该类型自身；
  `replace-and-block` 类型直接终止该路径。
- 用“来源类型”代替“权限集合”做状态 key，是因为集合只会在
  覆盖点被整体替换，等价类就是来源类型。这把状态数从
  `类型数 × 2^|动作集|` 压到 `类型数 × 来源数 × (深度上限+1)`，
  是性能证明的基础。
- 每个 `(类型, 来源)` 只保留已处理的最大剩余深度，更低深度的
  重复到达被跳过（备忘录）。

### 并集与覆盖

- 多条路径（不同起点或不同链接类型）到达同一目标同一主体时，
  取各路径结果的并集。
- 目标声明覆盖时，覆盖结果**替换**整个并集（只保留目标自身的
  直接授权），而不是与并集再合并。被丢弃的并集仍记录在
  `Decision.Contributions` 中供审计。
- 两种覆盖形态可区分：`replace` 替换后继续向下游传播（下游
  看到的是该类型的直接授权）；`replace-and-block` 额外阻断
  下游。一个类型任意时刻只有一条生效规则（`SetOverride` 为
  替换语义）；`AddOverrideRule` 提供追加语义，与既有规则形态
  不同时返回 `ErrConflictingOverrides` 且不改状态，从机制上
  杜绝“同一目标两种覆盖同时生效”的矛盾状态。

### 显式授权优先

最终权限 = `(显式允许 ∪ 传播并集) − 显式否定`。显式允许与显式
否定都按动作粒度压过传播结果，与显式授权覆盖的范围大小无关。

### 环路

- 只有参与传播的链接（`Propagates && MaxDepth > 0`）构成的子图
  需要无环；深度为 0 的链接可以在图中成环。
- 写路径（`AddLinkType`/`UpdateLinkType`）在提交前对传播子图做
  三色 DFS 环路检测，成环则拒绝并完整回滚，报
  `ErrPropagationCycle`。
- 判定路径另有防御性检测（仅从授权起点可达的子图），即便状态
  被绕过写路径破坏，也报环路错误而不是沿环静默传播。
- 环路错误与深度耗尽严格区分：前者是 `ErrPropagationCycle`，
  后者是 `ErrNoPermission` + `ReasonDepthExhausted`。

### 拒绝优先级

`Decide` 的检查与归因顺序：

1. 对象类型不存在 → `ErrObjectTypeNotFound`
2. 传播配置含环路 → `ErrPropagationCycle`
3. 显式拒绝 → `ErrNoPermission` + `ReasonExplicitDeny`
4. 覆盖阻断 → `ErrNoPermission` + `ReasonOverrideBlocked`
   （`replace` 形态为 `ReasonOverrideReplaced`）
5. 深度自然耗尽 → `ErrNoPermission` + `ReasonDepthExhausted`
6. 其余 → `ErrNoPermission` + `ReasonNoGrant`

普通无权限（`ErrNoPermission`）与全部配置性错误可用
`errors.Is` 区分。

## 并发设计（关键取舍 2）

单一 `sync.RWMutex` 串行化全部读写：

- 每个导出方法整体持锁，因此所有并发调用等价于某个全局串行
  顺序，任一时刻的判定对应该顺序下的确定前缀（线性一致）。
- 所有变更先校验后提交，失败操作不触碰任何状态（链接类型采用
  “先试挂、检测、失败回滚”）。
- 被放弃的方案：分片锁/无锁图（读扩写比例未知时复杂度远超
  收益，且难以保证“判定对应确定前缀”）；MVCC 快照（当前规模
  下读锁已足够，引入版本化只会增加内存与理解成本）。若未来
  判定延迟成为瓶颈，可在不改语义的前提下换成 copy-on-write
  快照。

## 性能论证（与规模无关）

`Decide` 考察的状态数被 `可达类型数 × 来源数 × (深度上限+1)`
约束，边松弛次数被 `可达边数 × 来源数 × (深度上限+1)` 约束，
二者都只取决于**从该主体授权起点可达的传播子图**，与平台内
链接类型总数、对象类型总数无关。判定结果中的 `Decision.Stats`
（`EdgesExamined`/`StatesVisited`）把考察量暴露给调用方；
`TestDecisionWorkIndependentOfPlatformSize` 在平台总规模放大
30 倍而可达子图不变时断言两次判定的 Stats 完全相等，构成可
验证的证明。

## 被放弃的方案

- **按路径枚举的判定**：语义最直白但路径数随图规模指数增长，
  且无法满足与规模无关的性能要求。仅保留为测试中的朴素参考
  模型（`model_test.go`），与优化引擎在随机图上逐条对照。
- **否定项沿链传播**：让显式否定也参与传播会引入“允许/否定
  沿不同路径赛跑”的歧义，题面只要求显式否定在目标处优先，
  因此否定项保持局部生效，语义更简单且可预测。
- **判定结果缓存**：授权/图变更频率未知，缓存失效逻辑会显著
  增加并发正确性风险；当前备忘录遍历已满足性能要求，不引入。

## 本地验证方法

```bash
# 全量测试（含随机模型对照、性能证明、并发）
go test ./...

# 竞态检测 + 查看每次判定的输入/输出/依据日志
go test -race -v ./ontology

# 仅跑朴素模型对照
go test -run TestAgainstNaiveModel -v ./ontology

# 仅跑规模无关性证明
go test -run TestDecisionWorkIndependentOfPlatformSize -v ./ontology

# 演示程序
go run ./cmd/server
```
