# 特种设备检验周期与超期管控系统 — 设计说明

## 1. 模块划分

代码全部位于 `speq` 包，按职责拆分为相互协作的小文件：

| 文件 | 职责 |
| --- | --- |
| `calendar.go` | 公历 ↔ 整数日序号换算、日历月加法（月末截断） |
| `errors.go` | 错误码（六类、有次序）、使用登记拒绝原因（五类、有次序） |
| `config.go` | 类别配置：周期月数、提前检验窗口、启封最小保障、预警提前天数 |
| `model.go` | 对象内部模型、检验结果枚举、快照/预警条目 DTO |
| `system.go` | 系统门面：存储、读写锁、单一全局操作日期 |
| `helpers.go` | 到期索引维护与到期日原子更新 |
| `register.go` | 类别登记、设备/附件首次登记（首次检验合格日 → 到期日） |
| `inspection.go` | 合格 / 有条件合格 / 不合格的到期日重算规则 |
| `seal.go` | 封存、启封顺延、最小保障校验、封存期检验锚点 |
| `attachment.go` | 附件挂接/转移及资格校验、摘除辅助 |
| `use.go` | 设备可使用性判定（拒绝原因次序）、使用登记 |
| `scrap.go` | 报废与挂接关系自动脱离 |
| `warnings.go` | 到期区间查询、设备触发附件聚合与排序 |
| `treap.go` | 按 `(到期日, 编号)` 排序的随机平衡树（对数级索引） |
| `state.go` | 只读快照查询（测试与外部观察用） |

`speqtest/naive` 是**独立编写的朴素参考模型**：不 import `speq`，
日历改用标准库 `time` 重写，所有查询线性扫描，专门用于差分测试。

## 2. 关键数据约定与取舍

### 2.1 日期与日历月

- 整数日序号 0 固定为公历 `0001-01-01`。
- 日历月加法按公历推算，目标月份无对应日号时取该月最后一天
  （如 1 月 31 日 +1 月 → 2 月 28/29 日）。
- 有效期含到期日当天；`查询日 > 到期日` 才算超期。

### 2.2 单一全局操作日期

系统只维护一个 `lastDate`：任一**被接受**的带日期操作都使其单调不减。
拒绝的操作不推进日期。这样"日期回退"的判定与操作种类、对象无关，
语义简单且可证明。曾考虑"每对象一条日期线"，放弃原因：题目明确
"上一个被接受操作的日期"为全局概念，且多日期线会让跨对象的挂接/
转移产生复杂的因果排序问题。

### 2.3 检验到期日规则

- 合格：当 `检验日 <= 原到期日` 且 `原到期日 - 检验日 <= 提前窗口`
  （含窗口边界与到期日当天）时，以**原到期日**加一周期；
  否则（过早或已超期）以**检验日**加一周期。
- 有条件合格：新到期日 = `min(合格规则结果, 检验日 + 整改限期)`。
  题目未禁止整改限期为 0，故允许（到期日压到检验日当天）。
- 不合格：立即停用，到期日不变；只有后续**合格**才能恢复。
  有条件合格**不**恢复停用（整改未通过正式复检）。

### 2.4 封存与启封

- 封存前置：对象未超期、未不合格停用。封存即暂停计时（不参与超期与预警）。
- 普通启封顺延天数 = `启封日 - 封存日`（按相差天数计）。
- 封存期内允许检验。引入 `sealAnchor`（封存期内最近一次检验日期）：
  启封只顺延 `启封日 - sealAnchor`，即"检验重算后经过的封存天数"，
  避免把检验已经重算掉的时间重复顺延。
- 启封前检查：`新到期日 - 启封日 < 启封最小保障天数` 则拒绝，
  必须先在封存状态下检验。

### 2.5 附件与可使用性

- 附件至多挂一台设备：模型中附件持 `host` 单值，转移即改值。
- 设备附件集合 `attachments[device] set` 使可使用判定只遍历
  **该设备自己的附件**，开销 O(k)，与系统对象总数无关。
- 拒绝原因次序固定：设备封存 > 设备停用 > 设备超期 > 缺少安全阀 >
  附件不满足。附件原因先按编号升序排序，再按"封存 > 停用 > 超期"
  取第一个命中，从而给出"编号最小的不满足附件"。
  （题目未规定附件同时有多种问题时的次序，此处选择上述内建次序。）
- 附件超期/封存/停用不修改设备字段，判定时即时派生。

### 2.6 预警

只有**未报废、未封存、未停用**的对象进入到期索引：

- 索引键为 `(到期日, 编号)`，用 treap 支撑 O(log n) 插入/删除与
  O(log n + 命中数) 的区间有序扫描。
- 每类别有自己的预警提前天数；扫描上界取"最大预警提前天数"，
  在扫描回调内再按各类别窗口精确判定。
- 设备条目合并两类来源：自身命中、附件触发；排序键
  `SortExpiry = min(自身到期日, 最早触发附件到期日)`，
  仅由附件触发（自身已超期）时排序键取附件到期日。

### 2.7 报废

报废是终态：任何后续操作返回"对象已报废"。
设备报废 → 挂接附件全部脱离；附件报废 → 从其设备摘除。
报废时同步从到期索引移除。

### 2.8 并发

系统用单一 `sync.RWMutex`：写操作取写锁，只读判定/快照/预警取读锁。
所有被接受操作因此天然等价于某一串行顺序（互斥顺序）。
放弃了"细粒度分桶锁"等方案：本题对象间耦合（附件↔设备、全局日期、
共享索引）强，细粒度锁复杂度高、收益小；粗锁下临界区都是内存计算，
争用不是瓶颈。

## 3. 错误模型

操作错误码（严格次序）：

1. `ErrInvalidParameter` 参数非法
2. `ErrDateRegression` 日期回退
3. `ErrNotFound` 对象不存在
4. `ErrScrapped` 对象已报废
5. `ErrIllegalState` 状态不允许
6. `ErrConditionNotMet` 条件不满足

所有变更在**全部校验通过之后**才落盘（先校验、后修改），
保证被拒绝操作不改变任何状态与日期。

使用登记的业务拒绝使用独立的 `RejectError`（携带原因与附件编号），
与操作错误码区分开；它仍然遵循"参数非法 > 日期回退 > 不存在 > 已报废
> 种类错误"的校验链，通过校验后才做可使用性判定。

## 4. 被放弃的方案

- **跳表替代 treap**：也可做到 O(log n)，但 Go 手写跳表节点与层数
  管理更复杂；treap 递归旋转代码更短、树高可直接断言，选 treap。
- **容器堆（最小堆）**：只能服务"最近到期"单向查询，无法支持
  任意日期窗口的左右边界与有序遍历，放弃。
- **关系数据库**：本题要求内存并发与可复现实验，引入数据库会掩盖
  算法本质，放弃。
- **每对象日期线**：见 2.2。

## 5. 本地验证方法

```bash
# 需要 Go 1.26+
go test ./...                 # 单元测试 + 6 万步随机差分 + 性能对照
go test -race ./...           # 竞态检测
go vet ./...
go run ./cmd/demo             # 打印输入/输出/判定依据的业务演示
```

验证产物：

- `testlogs/diff_random.log`：40 个种子 × 1500 步随机操作序列的
  输入、输出、错误码（与朴素模型逐步对照，快照与预警结果必须一致）。
- `testlogs/perf_two_tiers.log`：对象总数 2k/20k 两档、命中条数
  固定的预警查询耗时与 treap 高度对照。
- `testlogs/demo.log`：完整业务流的输入/输出/判定依据。
