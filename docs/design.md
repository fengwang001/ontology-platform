# 医院门诊药房库存预留与欠药补发：设计说明

## 1. 模块划分

- `pharmacy/model.go`：领域常量、药品、处方、处方行、预留与事件类型；纯取整规则。
- `pharmacy/inventory.go`：每药品欠药 FIFO 队列、有效预留/欠药总量、到货或释放后的分配。
- `pharmacy/events.go`：取药窗口与处方有效期的小顶堆、按分钟批处理、级联释放与再分配。
- `pharmacy/operations.go`：药品登记、入库、处方受理的参数校验、错误优先级与整单事务性拒绝。
- `pharmacy/system.go`：并发互斥、全局时钟、取药、取消、处方查询和药品查询。
- `pharmacy/preflight.go`：取药前只读试算，保证“无有效预留”的拒绝不推进时间、不产生副作用。

## 2. 关键状态与公式

- 在库量：累计到货减去已取走数量。
- 有效预留量：当前尚未到失效时刻、未取消且未取走的预留数量之和。
- 可用量：`on_hand - active_reservation`。
- 欠药总量：所有未取消、未过期、未完成行的剩余欠药数量之和。
- 可拆零：预留量 `min(remaining_demand, available)`。
- 不可拆零：
  - 可用量足以覆盖向上取整需求时，预留 `ceil(d / pack) * pack`；多出整盒不计欠药。
  - 否则预留 `floor(available / pack) * pack`，可以为 0。
- 取药窗口：区间 `[start, start + R]` 有效；`start + R + 1` 失效。
- 处方有效期：区间 `[issued, issued + 4320]` 有效；`issued + 4321` 过期。

## 3. 时间事件与级联处理

系统维护一个事件小顶堆，包含：

1. 预留失效事件；
2. 处方过期事件。

任一被接受的操作在读取或写入前，将所有 `event_at <= now` 的事件依次处理。同一分钟采用批处理：

1. 先处理该分钟所有处方过期事件，作废其欠药并释放预留；
2. 再处理该分钟所有预留失效事件；
3. 同一处方行的多个预留只重新登记一次欠药；
4. 汇总本分钟释放库存的药品；
5. 按药品 ID 稳定排序，逐药品按欠药队列分配。

同一分钟内新产生的预留如果窗口为 0，可能产生新事件；按时间先后继续弹出。不同药品之间按药品 ID 建立确定性顺序；需求只规定同药品欠药次序，因此该跨药品顺序是实现取舍，不影响任何单药品公平性断言。

## 4. 欠药公平队列

每个药品维护一个 `container/list`：

- 初始受理产生欠药时，追加到队尾，因此按“受理时刻 + 受理先后”排队。
- 到货或释放后，只扫描该药品的欠药队列。
- 可拆零药品可连续满足队首和后续队列；不可拆零药品若队首都不足一盒，则停止本轮，不能越过队首给后续处方。
- 预留超时后，该行仍未满足时重新登记欠药。重新登记保留处方受理次序，同时带有重新进入队列的时刻与序号，避免同一释放时刻已等待的欠药被错误抢占。

查询欠药总量直接读取 `drug.debt`，不遍历历史欠药行。

## 5. 拒绝操作与错误优先级

错误按以下优先级返回：

`参数非法 -> 时钟回退 -> 对象不存在 -> 状态不符 -> 处方过期 -> 缺药 -> 无有效预留`。

- 参数非法和时钟回退在任何状态推进前检查。
- 整单受理先完整校验所有行，缺药则不创建处方、预留或欠药。
- 取药若当前无有效预留，使用只读试算判断处理到 `now` 后是否会因事件获得库存；若不会，直接返回且不推进时钟。
- 取消仅适用于未完成且未过期处方；过期边界在推进事件前判断，拒绝不会释放库存。

## 6. 并发与确定性

所有公开方法持有同一个互斥锁，因此并发调用等价于某种串行交错。相同输入序列在单线程重放时由以下规则保证完全一致：

- 全局处方受理序号；
- 小顶堆事件序号；
- 同分钟药品按 ID 排序；
- 每药品欠药队列使用确定的链表顺序。

## 7. 被放弃的方案

- 每次查询扫描全部处方和预留：实现简单，但再分配与药品欠药查询会随历史处方总数增长，被放弃。
- 为每次部分分配立即提交再递归触发所有事件：容易让同一分钟释放被部分分配结果打断；改为同一分钟先汇总释放、再统一分配。
- 用数据库事务或持久化作为本任务前提：需求聚焦精确状态机和可重放性，当前实现采用内存模型，测试可直接验证。
- 为欠药行反复搜索全局处方表：无法满足受影响药品局部复杂度；改为行持有处方反向指针、药品持有独立队列。

## 8. 复杂度

- 到货/释放再分配：`O(k + q)`，其中 `q` 是受影响药品本次扫描的欠药行数，`k` 是本药品被释放预留数；事件堆操作为 `O(log E)`，不扫描全局处方。
- 药品查询：`O(1)` 读聚合字段，外加 `O(log E)` 的待处理事件弹出摊销。
- 处方查询：`O(l)`，`l <= 8`。
- 取消：`O(l + k)`，只处理该处方行与其预留。

## 9. 本地验证

```bash
# Go 工具链若不在 PATH，可使用 /usr/local/go/bin/go
go test ./...
go test -race ./...
go test -run TestRandomComparisonWithNaive -v ./pharmacy
go test -run '^$' -bench AffectedDrugOnly -benchtime=100x ./pharmacy
```

随机测试使用独立朴素模型，逐分钟扫描全部处方与预留，连续重放 1500 组随机操作序列；每个随机用例日志包含逐步输入、输出和判定依据，失败时完整打印。

基准两档分别保留 1,000 和 50,000 张已完成历史处方，在固定 20 个热药品欠药行上执行到货分配和查询。`-benchtime=1000x -count=3` 的参考结果约为：

- `BenchmarkAffectedDrugOnlySmall-20`: 981.4 / 937.2 / 1132 ns/op
- `BenchmarkAffectedDrugOnlyLarge-20`: 1306 / 1141 / 1086 ns/op

两者耗时同量级，没有出现从 1,000 到 50,000 历史处方约 50 倍增长，表明操作不随历史处方总数线性扫描；小幅差异来自内存规模、分配器和缓存效应。绝对耗时会随机器变化。
