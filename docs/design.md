# 分层配置版本化发布与解析系统 — 设计说明

## 1. 目标与范围

系统提供四层（全局 / 环境 / 区域 / 实例）配置的登记、原子发布、叠加解析、
显式取消、按键合并、层级锁定、历史读取与回滚。核心代码位于
`layerconfig/`，对外门面为 `layerconfig.Store`。

层级限定规则：

| 层 | 限定名 |
|---|---|
| 全局 `LayerGlobal` | 无 |
| 环境 `LayerEnv` | `Env` |
| 区域 `LayerRegion` | `Env` + `Region` |
| 实例 `LayerInstance` | `Env` + `Region` + `Instance` |

解析目标允许只给到环境或区域，此时叠加链只包含从全局到该层的范围。

## 2. 模块划分

| 文件 | 职责 |
|---|---|
| `errors.go` | 唯一错误类型 `Error{Kind,Detail}` 与七类错误及优先级 |
| `layer.go` | 层级枚举、`Scope` 合法性、叠加链构造、扁平键编解码 |
| `schema.go` / `registry_extra.go` | 键模式登记（类型/必填/范围/合并方式），非版本化 |
| `pmap.go` | 持久化分片 Map：不可变、结构共享、单键 O(1) |
| `state.go` | 不可变快照、工作集、写入归一化与提交（copy-on-write） |
| `publish.go` | 发布校验流水线（参数→键→类型→批内冲突→锁→必填） |
| `resolver.go` | 叠加解析：覆盖 / 追加去重 / 取消 / 未设置 |
| `store.go` | 并发安全门面、版本历史、原子快照切换、回滚 |
| `probe.go` | 仅供测试验证结构共享的白盒探针（非 API） |

模块协作方向是单向的：`Store` → `publish`/`resolver` → `state`/`pmap`
→ `schema`/`layer`，解析函数以依赖注入的方式传给发布流水线，避免环依赖。

## 3. 关键数据结构

### 3.1 不可变快照 `state`

每个版本对应一个 `*state`：

- `writes`：`(scope,key) → writeEntry`，`writeEntry` 要么是值，要么是取消标记；
- `locks`：`(scope,key) → 锁存在`；
- `exists`：出现过的环境/区域/实例身份集合，用于必填校验，无需扫描全部写入。

`state` 一经提交永不修改。发布在私有可变 `workingState` 上折叠，校验通过后
才 `commit` 成新的 `state`；被拒绝的发布只丢弃工作集，`Store` 完全无感。

### 3.2 持久化分片 Map（`pmap`）

`pmap` 是 64 桶的固定分片数组，每桶是一个普通不可变 `map[string]entry`。

- `get(key)`：一次 FNV 哈希定位桶，O(1)，不触碰其它桶；
- `set/delete`：只复制命中的那个桶，其余 63 个桶按引用共享；
- 根是固定大小的值数组，更新根只复制 64 个 map 头，与键总数无关。

因此一次单键发布的新增存储只与“被改动的桶”有关，绝不复制整个配置。
测试 `TestStructuralSharingNoFullCopy` 用反射比较相邻版本桶 map 的指针身份，
实测单键发布后 **63/64** 个写桶保持共享，并用 `TotalWriteShardMaps`
统计全部历史版本中不同桶 map 的数量，证明其远小于 `版本数×64`。

### 3.3 存在性索引

某环境/区域/实例是否“存在”，以任一层写入中是否出现其限定名为准（全局不产生
具名身份）。每次发布在折叠完成后，从“仍然存活的写入”重建身份索引。这样
“最后一个写入被 clear”的身份会立即消失，必填校验随之放宽。成本与存活写入数
成正比，与历史版本数无关。

## 4. 解析语义

对目标 `Scope` 构造从全局到目标层的链（≤4 层），每层对该键至多一次
`pmap.get`：

- 覆盖型（所有标量，以及 override 列表）：最后存活的值生效；
- 追加型列表：从宽到窄拼接，用集合去重，元素保留其**最早出现位置**；
- 取消标记：作废当前累积（标量值与已拼接列表都清空），更窄层后续写入仍叠加；
- 全程无存活值：`Resolved{Present:false}`（未设置），与空串 `""`、空列表
  `[]string{}` 严格区分（空列表在解析时归一为非 nil 的空切片）。

每次解析固定 ≤4 次 Map 查找，复杂度与总键数、总层数、历史版本数无关。

## 5. 发布校验流水线与错误优先级

错误类别优先级（数字小者优先报告）：

1. `InvalidArgument`（空批次/空键/非法层限定/未知 Op/回滚目标为负）
2. `VersionNotFound`（读取/回滚引用不存在的版本）
3. `KeyNotRegistered`
4. `TypeOrRange`（整数超出 `[Min,Max]`；追加用于非列表等模式非法也在此层之前
   的登记阶段拒绝）
5. `LockConflict`
6. `BatchConflict`（同一次发布内同一 `(scope,key)` 出现多于一条变更）
7. `RequiredMissing`

发布按以下顺序短路，保证报告的总是最高优先级错误：

1. 参数合法性；
2. 所有键已登记；
3. 写入值类型/范围；
4. 批内同目标冲突；
5. 折叠进工作集（值 / 取消 / 清除 / 锁 / 解锁）并重建存在性索引；
6. 锁约束（在候选结果上判定，见下）；
7. 提交候选，对每个已存在身份逐一键解析做必填校验。

### 5.1 锁的精确语义

- 某层对某键上锁后，**更窄层**不得写值或写取消；
- 上锁层本身、以及更宽层**不受约束**；
- 同一发布内“同时上全局锁 + 更窄写入”在候选上也会被判 `LockConflict`；
- 若上锁生效前更窄层已存在该键的值/取消，发布直接拒绝，要求先清理
  （用 `OpClear` 单独发布）；同层写入不阻止上锁；
- 环境/区域锁只约束同一条环境/区域前缀下的更窄层，其它环境不受影响；
- 锁可解除（`OpUnlock`）。

## 6. 版本、回滚与历史读取

- 初始版本为 `0`，配置为空；每次成功发布版本号 +1；失败版本不变。
- 版本历史保存的是 `*state` 快照头；由于 `state`/`pmap` 持久化，相邻版本
  共享绝大多数桶，历史存储不会随每次发布复制整个配置。
- `Rollback(t)`：
  - `t<0` → `InvalidArgument`；`t` 不存在 → `VersionNotFound`；
  - `t==current` → 无操作，不产生新版本；
  - 否则产生一个**新版本**，内容与 `t` 完全相同（四张持久化 Map 直接共享），
    旧版本与之前所有版本继续可读；
  - 提交前用**当前最新键模式**重跑必填校验；目标版本自身在当时有效，因此
       一般总是成功，唯一失败来源是其间键模式被修改（例如改成必填）导致旧内容
    不再满足。
- 读取可指定任意历史版本，`version<=0`（负或 0 之外统一处理为：负数=当前，
  `0`=初始空版本）；合并方式永远按**最新模式**解释（模式不版本化）。

## 7. 并发模型

- 一个 `sync.RWMutex`：`Publish`/`Rollback`/`RegisterKey` 取写锁，
  `Resolve*` 取读锁，多读者并行、写者独占；
- 当前版本头通过 `atomic.Pointer[snapshot]` 发布。`snapshot` 内含不可变
  `*state` 与历史切片；读者拿到快照头后只遍历不可变数据；
- 任意并发操作的结果等价于某一串行顺序（写操作的全序 + 读操作在其读锁区间
  对应的快照），解析不可能观察到发布进行到一半的中间态。`go test -race`
  下的 `TestConcurrentLinearizability` 验证无数据竞争且状态始终一致。

## 8. 关键取舍

1. **固定 64 分片 vs 真正的 HAMT/树结构共享**：选择固定分片，因为读取要求
   严格的 O(1) 且“可验证地不随规模增长”。HAMT 理论上写放大是 O(log n)，
   实现复杂度高、常数大；64 桶使根复制恒为 64 个 map 头、单键更新只复制一个
   桶，语义与性能都容易用测试直接证明。
2. **不可变持久化 Map vs “每次全量复制快照”**：全量复制实现最简单，但每次
   发布 O(全部键) 存储，直接违反需求；朴素模型（测试中的参考实现）保留了
   全量复制写法，仅作行为对照，生产路径使用结构共享。
3. **事件溯源（只存 changelog）**：曾考虑只存变更日志、读取时回放。缺点是历史
   解析成本随历史长度增长，违反“解析不随版本数增长”；即便做快照分层，也会引入
   周期性压缩等运维复杂度。最终选择持久化数据结构：写入 O(改动桶)、读取
   O(链长) 且与版本数无关。
4. **取消是独立标记而非“写空值”**：空串/空列表是合法值，不能复用为取消，
   因此引入 `writeCancel` 显式标记，未设置与空值得以严格区分。
5. **存在性索引每次从存活写入重建**：增量维护在“clear 掉最后一个写入”时需要
   引用计数，复杂且易错；重建只遍历存活写入（不含历史版本），在同一版本内是
   有界的，并且让“身份消失”语义精确。
6. **必填校验在发布候选上逐身份解析**：保证“发布后的视图”被直接检查，而不是
   用近似规则；代价是 O(已存在身份 × 必填键)，这恰是必须保证有值的结果规模。
7. **模式非版本化**：需求明确历史读取也按最新模式解释；登记只校验模式自身，
   不即时校验数据，模式变更导致的不合法只在下次发布/回滚时暴露。

## 9. 被放弃的方案

- **整库一把互斥锁 + 每次发布深拷贝**：正确性容易，但解析在发布期间要么阻塞、
  要么可能读到半成品；存储也随版本×配置膨胀。已放弃。
- **读时跨版本回放事件**：解析随历史增长，被性能要求否决。
- **锁用全局计数判断是否存在窄层写入**：跨键总数会误报（A 键的窄写入阻止
  B 键上锁）。实现中一度采用，测试设计复核时发现，改为遍历身份索引按
  `(scope,key)` 精确判断。
- **同发布内允许“先 clear 再 write 同目标”视为顺序操作**：需求要求同一层同一键
  的冲突变更判为非法，因此实现采用“每个 `(scope,key)` 至多一条变更”的强约束，
  语义无歧义。

## 10. 本地验证方法

```bash
# 环境（本机 Go 未在 PATH 中）
export PATH=$PATH:/usr/local/go/bin
export GOCACHE=/tmp/gocache

# 演示
go run ./cmd/demo

# 全量测试
go test ./...

# 竞态 + 详细日志（功能/差分/并发测试均打印每次操作的输入、实际输出与判定依据；
# 失败时日志自动随测试输出，成功时可用 LC_TEST_VERBOSE=1 查看）
go test -race -v ./...
LC_TEST_VERBOSE=1 go test -v ./layerconfig -run TestRandomDifferential

# 性能：解析不随键数、版本数增长；结构共享不复制全配置
go test ./layerconfig -bench BenchmarkResolve -benchtime=200000x -run '^$'
go test -v ./layerconfig -run 'TestResolutionIndependentOfVersions|TestStructuralSharingNoFullCopy'

gofmt -l .
go vet ./...
```

实测参考（arm64，本机）：

- 键数 1k → 16k → 64k，解析约 196 / 241 / 286 ns/op、每次恒为
  96 B、2 allocs；增长来自缓存效应，无算法性增长。
- 2000 个版本 vs 10 个版本，解析单次耗时约 1.31×（阈值 5×）。
- 单键发布后 63/64 写桶跨版本共享；全部历史仅保留 65 个不同写桶 map
  （全量复制上界为 128）。
- 随机差分：5 个种子、每种子 1500 步随机发布/回滚/解析（注入非法参数、未知键、
  超范围值、批内重复），并在末尾对“每个版本 × 每条解析链 × 每个键”做全扫描，
  与独立朴素模型逐步一致。
