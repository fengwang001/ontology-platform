# 证券交割日终批处理设计说明

## 1. 领域模型

核心类型位于 `settlement/types.go`：

- `System`：线程安全的结算系统，持有营业日、账户、指令、到期日索引和批处理游标。
- `OrderInput`：不可变的成交指令输入。
- `Order`：内部指令状态，记录累计交割量、剩余量、状态与累计失败营业日数。
- `Position`：账户现金和各证券数量的查询快照。
- `Balances`：罚金或补偿的应付、应收台账。
- `ProcessResult`：单日批处理的可审计结果，包含每条指令的判定、罚金和强制了结明细。

所有数量、价格、现金均使用 `int64`。乘法和累计用 `math/big.Int` 预检，溢出按参数非法处理，避免静默回绕。

## 2. 并发与原子性

所有公开方法通过同一个 `sync.RWMutex` 串行化写操作：

- `RegisterOrder`、`ProcessBusinessDay`、`SetLogger` 使用写锁。
- 查询方法使用读锁，并返回深拷贝。

这保证并发调用的结果等价于某个串行顺序。相同操作序列因为指令按编号确定性排序、罚金和补偿按相同规则累计，所以会得到完全相同的头寸、罚金和状态。

批处理先完整收集候选指令并生成全天计划，在所有参考价、乘法和台账累计校验通过后才写入头寸与状态。参数错误时，临时弹出的到期日桶会回滚，保证被拒绝操作不留痕。

## 3. 日终批处理算法

### 3.1 候选集合

某日批处理的候选指令包括：

1. 已过应交割日、尚未完成或强制了结的滚动指令，保存在 `active`。
2. 到期日不晚于当日的新指令，保存在按到期日排序的最小堆 `dueHeap` 和 `byDue` 桶中。

候选指令最终按指令编号升序排序。已完成或已强制了结的指令不留在 `active`；处理完的到期桶立即删除。因此单日不会扫描历史已了结指令。

### 3.2 批首头寸与批内占用

计划阶段只读取批处理开始时的头寸，维护两类占用：

- `securityReserved[seller][security]`：更早指令已经确定从该卖方的批首持仓中占用的券。
- `cashReserved[buyer]`：更早指令已经确定从该买方批首现金中占用的款。

第 `i` 条指令的可交割量为：

```text
min(
  剩余未交割量,
  卖方批首该证券数量 - 更早指令占用的该卖方该证券数量,
  (买方批首现金 - 更早指令占用的买方现金) / 单价
)
```

不允许部分交割时，若可交割量小于当日请求量，则交割量归零。

早先交割收到的券和现金只进入当天批末增量，不会在计划阶段被后续指令使用，所以天然满足“次日才可用”。

### 3.3 DVP 原子生效

计划阶段累计每条指令的：

- 卖方券减少量；
- 买方券增加量；
- 买方现金减少量；
- 卖方现金增加量。

所有指令判定结束后一次性应用这些增量。券和款总是成对转移，因此不会出现只交券或只付款的中间状态。

### 3.4 失败责任与罚金

若交割后仍有剩余量，当日记一次失败。责任方在任何交割归零处理前、基于批首可用头寸判断：

- 若当日请求量大于卖方扣减更早占用后的可用券量，责任方为卖方；
- 否则责任方为买方。

两边都不足时卖方优先。责任方逐日独立判断，允许随头寸变化切换。

罚金为：

```text
ceil(剩余量 * 单价 * 罚率基点 / 10000)
```

罚金只写应付、应收台账，不改变现金头寸。

### 3.5 强制了结与补偿

失败营业日数达到配置值 `B` 时，在当日罚金计入后立即强制了结：

- 指令状态变为 `forced`；
- 未交割量作废；
- 指令从后续候选集合移除。

若当日责任方为卖方，补偿为：

```text
max(0, 当日参考价 * 交割后剩余量 - 原单价 * 交割后剩余量)
```

补偿同样只记应付、应收，不改变现金。买方责任时没有补偿。

## 4. 状态语义

- `pending`：尚未发生任何成功交割，可能已有零交割失败。
- `partial`：至少交割过一部分，但仍有剩余量。
- `completed`：剩余量为零。
- `forced`：累计失败日数达到 `B`，剩余量作废。

## 5. 错误优先级

批处理：

1. 参数非法，例如日值非正、参考价表为空、缺少证券价格、价格非正或整数溢出；
2. 非营业日；
3. 批处理次序错误。

登记指令：

1. 参数非法；
2. 指令编号重复；
3. 买方或卖方账户不存在；
4. 应交割日早于最近已完成批处理营业日。

这里有一个刻意选择：非营业日首先属于输入参数不合法，只有能在营业日集合中找到该日时才进入次序判断。

## 6. 复杂度

设：

- `k` 为当日候选指令数；
- `d` 为当日及之前尚未弹出的到期日桶数量，实际每个桶只会弹出一次；
- `a` 为候选指令涉及的账户/证券组合数。

主要成本为：

- 弹出到期桶：`O(k + d log D)`，`D` 为尚未到期的不同到期日数量；
- 指令编号排序：`O(k log k)`；
- 逐条计划与应用：`O(k + a)`。

历史已完成或强制了结指令不会留在 `active`，对应到期桶也已删除；`orders` 仅用于按编号查询，不参与日终扫描。测试 `TestProcessDayDoesNotScanHistoricalClosedOrders` 会先制造大量已了结历史指令，再断言调度结构中只剩一个新指令，并测量后续日处理时间。

## 7. 关键取舍

- 使用粗粒度互斥锁而非多版本并发：结算批处理要求强次序和可重放，单一锁更简单且错误面更小。
- 使用两阶段计划/应用：避免同批内把刚收到的券款提前用于后续指令，也让参数拒绝天然可回滚。
- 保留全量 `orders` 供查询，但不把它放入批处理扫描路径：同时满足状态可追溯和单日复杂度要求。
- 罚金和补偿作为独立台账：它们不参与 DVP 现金守恒，避免把“应收/应付”错误地当作已结算现金。

## 8. 被放弃的方案

- **逐笔立即改头寸**：会让同批早先收到的券或现金被后续指令误用，必须额外冻结流入，规则更容易出错。
- **每日扫描全部历史指令**：实现简单但复杂度随历史总量增长，不满足性能要求。
- **按到期日维护单一切片并线性插入/删除**：在乱序登记未来到期日时仍可能引入线性维护成本，因此改为最小堆。
- **用浮点数计算罚金和补偿**：可能产生不可复现的舍入差异；所有金额都使用整数和显式向上取整。

## 9. 本地验证

如果系统 `PATH` 中没有 Go，可使用仓库环境中的工具链：

```bash
export PATH=/usr/local/go/bin:$PATH
export GOCACHE=/tmp/ontology-gocache
```

常用命令：

```bash
go test ./...
go test -race ./...
go test -v ./settlement
go test -run TestRandomOperationsAgainstNaiveModel -v ./settlement
go vet ./...
```

测试包含：

- 应交割日等于当日；
- 部分交割与整笔失败；
- 券款两边都不足时卖方优先；
- 同批占用和收到券次日才可用；
- 失败日数恰达 `B`；
- 买方责任无补偿、卖方正补偿、负补偿取零；
- 错误优先级和拒绝不留痕；
- 头寸与总券/总现金守恒；
- 并发调用；
- 200 个随机操作序列与独立朴素模型逐日对照。
