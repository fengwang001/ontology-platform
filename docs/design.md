# 动作执行的前置/后置校验职责分离设计

本文档说明本体平台动作（Action）执行机制的关键设计取舍、被放弃的方案与本地验证方法。
实现位于 `ontology/` 包，测试与之一一对应。

## 1. 阶段划分与职责分离

一次动作调用被严格划分为五个阶段（`ontology/engine.go`）：

| 阶段 | 职责 | 可观察的状态 |
|------|------|--------------|
| 0. 声明矛盾检查 | 读取注册时缓存的分析结果 | 无（纯查表） |
| 1. 目标存在性检查 | 目标对象在已提交快照中存在 | 一致快照 |
| 2. 前置校验 | 评估全部前置条件，收集**所有**不通过项 | 仅已提交快照（`StateView`） |
| 3. 计划生成 | `Apply` 在内存中累积写入计划 | 快照 + 内存计划 |
| 4. 后置校验 | 按声明顺序评估，**首个**失败即决定性条件 | 仅统一计划视图（`PlannedView`） |
| 5. 提交 | 乐观并发校验后原子应用 | 已提交状态 |

职责分离通过**输入类型的结构性隔离**保证，而非依赖约定：

- `PreCondition.Eval` 的入参是 `PreInput{Params, State *StateView}`。
  `StateView` 在执行开始前于锁内拷贝，类型上不存在任何访问写入计划的途径，
  因此前置条件**不可能**观察到本次执行的未提交写入。
- `PostCondition.Eval` 的入参是 `PostInput{Params, State *PlannedView}`。
  `PlannedView` 是“已提交快照 + 最终写入计划”的叠加视图，全部对象共享同一
  快照基线；后置条件拿不到原始快照，也就无法重新评估前置条件的判断依据。
- 引擎只在前置阶段调用 `PreCondition`、只在后置阶段调用 `PostCondition`，
  后置阶段不会重新评估任何前置条件（有专门测试
  `TestPreconditionNotReevaluatedInPostPhase` 守护）。

两个阶段的条件声明是两个独立列表（`ActionType.Preconditions` /
`ActionType.Postconditions`），各自独立演进、互不出现在对方的求值环境中。

## 2. 失败语义的不对称性

题面要求的不对称性被显式编码：

- **前置失败**：评估全部前置条件，`Rejection.FailedPreconditions` 返回**所有**
  不通过的条件 ID（`TestPreFailureReturnsAllAndKeepsState`）。
- **后置失败**：按声明顺序短路，`Rejection.DecisivePostcondition` 只返回导致
  本次放弃的决定性条件，其余本可能失败的条件不求值、不报告
  （`TestPostFailureDiscardsPlan` 中断言 `always-fails` 不出现）。

## 3. 拒绝路径的状态不变性

- 对象版本号、全局提交序号、对象历史序号、动作类型历史序号**只在提交成功的
  临界区内分配**。前置失败与后置失败发生在提交之前，因此不消耗任何版本号或
  序号，也不进入任何历史序列（`TestRejectionConsumesNoVersionsOrSequences`
  验证失败后成功调用的版本/序号连续无空洞）。
- 后置失败时写入计划是纯内存结构，整体丢弃即与从未尝试等价；失败被记入
  **独立的失败轨迹**（`Store.failureTrail`），与对象状态完全隔离。
- 前置失败不进入失败轨迹（题面只禁止其进入历史序列；本实现选择仅留存校验
  审计日志，见第 6 节），该选择记录在案。

## 4. 声明矛盾的定义期检测

一个动作的全部前置（后置）条件必须同时通过，因此以下情形意味着声明自相矛盾：

1. **互斥对**：条件声明 `Excludes`（“本条件通过隐含对方必然不通过”），
   同一阶段内出现互斥对或自斥 → 矛盾；
2. **描述子联合不可满足**：每个条件可附带描述子（`Descriptor`）——
   条件通过的**必要条件**，用参数上的 int64 比较布尔表达式表达。
   全部描述子的合取不可满足 → 不存在任何输入让全部条件通过 → 矛盾。

描述子 SAT 通过枚举原子真值指派（2^a，a 为原子数，上限 20，超出则放弃该
项分析）并做逐字段区间一致性检查判定，是可判定过程。

**开销证明**：分析只在 `Registry.Register` 中执行一次并缓存在
`ActionType.analysis`；`Registry.analysisRuns` 计数器只随注册增长。
`TestContradictionAnalysisCostIndependentOfInvocations` 注册后执行 1000 次
调用并断言计数器不变——分析开销与历史调用次数无关，只与声明本身的条件数
与原子数相关。

矛盾声明默认在注册时被拒绝（定义期暴露配置错误）；`PermitContradictory`
选项允许强制注册以演示运行期类别，此时执行在阶段 0 即被拒绝，优先于其余
三类（`TestContradictionCategoryHasHighestPriorityAtRuntime`）。

## 5. 并发控制：乐观并发（BOCC）

- 执行开始时在锁内拷贝一致快照；校验与计划生成不持有任何锁。
- `StateView` 登记读集：每个被读对象的版本（或“不存在”事实），链接以
  全局代际号 `linkGen` 整体跟踪。
- 提交时在锁内校验读集与当前已提交状态一致，然后原子应用计划、递增版本、
  追加历史。读集校验通过 ⇒ 该执行等价于在提交点原子发生 ⇒ 被接受调用集合
  按提交序号构成可串行化全序。
- 校验失败 → `RejectConcurrentInvalidation`（目标被并发修改/撤销），
  计划整体丢弃并记入失败轨迹。

**目标缺失的优先级**：目标对象在执行开始时不存在按并发撤销类别处理，
且该检查固定在前置校验之前——相同输入多次执行结果稳定
（`TestMissingTargetPriorityIsStable`）。

正确性由 `TestConcurrentExecutionsEquivalentToSerialOrder` 验证：4 个随机
种子 × 480 次并发调用，被接受调用按提交序号重放到**独立的朴素串行实现**
（`ontology/naive.go`，无锁无快照、独立编写）上，最终对象属性、版本号、
对象历史、动作类型历史逐项相等，且账户总额守恒、无负余额。

## 6. 审计

每次校验（前置/后置、通过/失败）都追加一条 `ValidationRecord`，包含：

- **输入**：调用 ID、动作类型、参数、目标对象；
- **依据**：校验期间读取的对象版本（-1 表示“对象不存在”这一事实）与链接代际；
- **结论**：各条件求值结果（前置为全集，后置为到决定性条件为止的前缀）与整体结论。

审计序号独立于对象版本号与历史序号。失败轨迹记录可回指相关校验记录序号。

## 7. 被放弃的方案

| 方案 | 放弃原因 |
|------|----------|
| 悲观锁（按对象加锁执行全程） | 多对象动作需要全局锁序，死锁风险与实现复杂度高；读多写少场景下并发度更差。乐观方案的无锁校验路径更简单且同样可证可串行化。 |
| 全局版本号代替读集 | 任何并发提交都会使所有在执行调用失败，误伤不相关对象的调用；读集方案只让真正冲突的调用失败。 |
| 冲突后自动重试 | 会把“并发撤销”这一必须暴露的类别隐藏在引擎内部；交由调用方决定是否重试。 |
| 对任意条件函数做静态矛盾分析 | 一般函数的可满足性不可判定。改为要求作者提供描述子（必要条件元数据）+ 显式互斥声明，使分析可判定；描述子缺失时退化为只做互斥检查。 |
| 后置条件也穷举失败项 / 前置条件短路 | 题面明确要求不对称语义，非实现自由。 |
| MVCC 版本链快照 | 当前全量拷贝快照更简单；接口（一致快照 + 读集校验）与存储内部解耦，可平滑替换。 |

## 8. 已知限制

- 快照为全量拷贝，适合中小规模状态；大规模部署需替换为 MVCC。
- 链接读集以全局代际号跟踪，任何链接写入会使所有读过链接的在执行调用冲突
  （保守但正确）。
- 描述子只覆盖 int64 参数比较；描述子未覆盖的不可满足性无法在定义期发现。

## 9. 本地验证方法

```bash
# 全量测试（含竞态检测）
go test -race ./...

# 关键测试
go test ./ontology -run TestPreFailureReturnsAllAndKeepsState      # 前置失败路径
go test ./ontology -run TestPostFailureDiscardsPlan                # 后置失败路径
go test ./ontology -run TestContradiction                          # 声明矛盾
go test ./ontology -run TestConcurrentExecutions -race -v          # 并发 vs 串行对照
go test ./ontology -run TestValidationRecords                      # 审计记录

# 演示
go run ./cmd/server

# 静态检查
gofmt -l . && go vet ./...
```
