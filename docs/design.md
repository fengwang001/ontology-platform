# 嵌套动作事务与校验钩子触发顺序子系统 — 设计说明

## 1. 问题与目标

动作是对若干对象实例的一组写入（创建 / 更新 / 删除）的集合，原子生效。
动作执行体内允许调用另一个（或同一）动作定义，被调用动作的写入并入
发起方的事务边界：最外层动作提交或回退时，内外全部写入作为一个不可
分割的整体一起生效或一起撤销。

每个对象类型可注册前置 / 后置校验钩子，本子系统要保证嵌套场景下两层
钩子的**触发范围、可见快照与短路规则**精确且一致，并在并发与重放下
保持确定性。

## 2. 模块划分与协作

```
cmd/server        演示入口
spec              共享数据模型（Schema / Write / ActionDef），无行为逻辑
errs              错误归一化：三类可区分错误 + 后置聚合报告
hooks             钩子注册表（Registry）与触发调度器（Dispatcher）、
                  只读状态视图接口（StateView）、触发记录（Record）
tx                事务边界管理：已提交存储、工作副本、写入校验、
                  O(1) 只读视图、提交换入 / 回退丢弃
engine            执行引擎：解释动作定义、编排嵌套调用、
                  基于序号的轮转调度（串行化 + 重放确定性）
naive             独立实现的朴素对照模型（测试 oracle）
```

一次最外层调用的协作流程：

1. `engine` 等待轮转序号（并发串行化，见 §6），轮到后向 `tx.Store`
   开启事务（对工作状态做一次全量深拷贝，每事务仅一次）。
2. `engine` 递归解释动作体。每个写入步骤依次：
   - `tx.Validate`：参数校验（目标实例存在性、字段类型），失败即
     归一化为 `errs.KindInvalidArgument`，整个事务回退；
   - `hooks.Dispatcher.FirePre`：按注册顺序触发该类型的前置钩子，
     钩子通过 `tx.View()` 拿到**写入生效前**的只读视图（含外层已应用
     但未提交的写入），任一失败即短路，归一化为 `errs.KindPreHook`，
     整个事务回退；
   - `tx.Apply`：写入应用到共享工作副本。
   嵌套调用递归进入下一层，**共享同一个 `tx.Tx`**，因此内层写入与
   外层写入处于同一事务边界。
3. 全部写入应用完后（事务尚未提交），`hooks.Dispatcher.FirePost`
   对本事务实际写入过的类型，按**全局注册顺序**触发一次后置钩子；
   失败不短路，按注册顺序收集全部失败，聚合为 `errs.PostHookError`。
4. 任一步失败：`tx.Rollback` 丢弃工作副本（已提交状态从未被触碰，
   不留任何痕迹）；全部成功：`tx.Commit` 将工作副本原子换入。

## 3. 关键取舍：事务工作副本（copy-on-begin）

**采用的方案**：最外层事务开始时对已提交状态做一次全量深拷贝，
所有层级（任意嵌套深度）的写入直接应用到这一份共享工作副本上；
提交 = 指针换入，回退 = 丢弃。

由此自然得到的性质：

- **可见性**：内层前置钩子与外层前置钩子读的是同一份工作副本，
  「看到外层未提交写入」无需任何特殊机制；
- **O(1) 快照**：钩子要的「写入生效前状态」就是当前工作副本本身，
  构造视图只是包装一个指针（见 §5 的证明）；
- **O(1) 回退**：丢弃指针，与嵌套深度、写入总数均无关；
- **整体原子性**：内外层写入在同一副本上，提交 / 回退必然同生共死，
  不存在「只回退外层保留内层」的构造可能。

**代价**：每个最外层事务开始时有一次 O(已提交对象总量) 的深拷贝。
对本子系统的规模（动作平台的事务通常是几十到几千个对象）这是合理
开销，且它与「嵌套深度」「事务内写入数」无关——这正是需求约束的
两个维度。

**被放弃的方案**：

| 方案 | 放弃原因 |
| --- | --- |
| 分层 overlay（每层嵌套一个增量层，读取时逐层回溯） | 读取与快照开销随**嵌套深度**线性增长，直接违反「快照开销不得随调用深度增长」的约束 |
| 原地修改 + undo 日志 | 回退开销随**已应用写入总数**增长；前置钩子看到的「写入生效前状态」需要从 undo 日志重建，同样随写入数增长 |
| 持久化（不可变）数据结构，如 HAMT | Go 标准库无现成实现，自研引入的复杂度与常数因子远超收益；copy-on-begin 已满足全部渐近约束 |
| 每次钩子触发时全量深拷贝快照 | 即朴素模型的做法，开销随状态总量 × 钩子次数增长（差分测试中作为对照组量化展示） |

## 4. 错误归一化与报告优先级

`errs` 模块把动作调用的拒绝归一化为三种可相互区分的类别
（`errs.KindOf` / `errs.IsKind` 判定）：

1. `invalid-argument`：目标实例不存在、写入内容类型不符、未知字段等；
2. `pre-hook-failed`：前置钩子失败，携带钩子名与动作调用路径；
3. `post-hook-failed`：后置钩子失败，**聚合形式**
   （`errs.PostHookError.Failures` 按钩子注册顺序排列）。

优先级 **参数非法 > 前置钩子失败 > 后置钩子失败** 由执行顺序自然
保证：每个写入步骤先校验参数再触发前置钩子，任一步失败立即中止
整个事务，后置钩子阶段根本不会到达；因此参数非法与前置钩子失败
永远不会出现在后置聚合报告中。后置钩子阶段内不短路：全部后置钩子
都触发，失败按注册顺序聚合一并报告，报告后整体回退。

嵌套深度保护（`engine.ErrDepthLimit`，默认 64）属于引擎防护而非
动作拒绝，刻意不归一化进三类错误。自调用（动作调用自身）是允许的，
由深度保护终止。

## 5. O(1) 快照开销的证明

**命题**：判定某一层前置钩子应当看到的「写入生效前状态」的开销，
不随当前事务已嵌套的调用深度或已应用写入总数的增长而增长。

**机制**：`tx.Tx.View()` 的实现是 `&view{data: t.working}` ——
包装一个指针，不拷贝、不遍历任何数据。钩子只在调用期间持有视图，
视图在钩子返回后即失效（接口约定），因此不需要物化快照。

**可验证的证明**（`engine/snapshot_proof_test.go`）：

1. *插桩断言*：`tx.Store` 统计 `ViewCopiedEntries`（构造视图时拷贝的
   字段条目数）。测试在 depth ∈ {1,2,4,8,16} × writes ∈ {1,10,100}
   的网格上执行嵌套动作链，断言该计数**恒为 0**；
2. *次数断言*：`ViewCreated` 恒等于「前置钩子触发次数 + 1（提交阶段）」，
   即不存在随深度或写入数增长的隐藏构造循环；
3. *对照组*：朴素模型每次前置钩子都全量深拷贝，其
   `SnapshotCopiedEntries` 在同一网格下从 1 增长到 1,280,800，
   证明测试网格本身足以区分 O(1) 与 O(n) 实现；
4. *基准*：`BenchmarkViewConstruction` 在已应用 0 / 100 / 1000 /
   10000 条写入的事务上测量视图构造，实测均为约 1.6–2.2 ns/op
   （linux/arm64），与写入总数无关。

## 6. 并发串行化与重放确定性

`engine` 采用**基于序号的轮转调度**：每个最外层调用携带全局序号
（`Execute` 自动分配，`ExecuteWithSeq` 显式指定），引擎内部维护
轮转游标，只有序号等于游标的调用获得执行权，执行完毕后游标前进。
因此：

- 同一时刻至多一个事务在执行，并发调用的最终效果**等价于按序号
  的全局串行顺序**；
- 一个最外层动作内部的全部嵌套写入在该串行顺序中占据**同一个
  位置**（事务边界内不可能插入其他最外层动作的写入——测试用前置
  钩子观察「他方事务的 marker 必须成对出现」验证）；
- 重放同一组调用序号序列，得到完全相同的最终状态与钩子触发记录
  （`TestReplayDeterministic` 用不同的 goroutine 提交顺序重放两轮，
  逐字节比较状态与钩子日志）。

注意：`Execute`（自动序号）与 `ExecuteWithSeq`（显式序号）不要在
同一引擎上混用；显式序号必须从当前轮转位置开始连续，否则靠后的
调用会等待缺口被补齐。

## 7. 测试与本地验证方法

```bash
# 全量测试（含竞态检测）
go test -race ./...

# 查看判定依据输出（输入、实际输出、对照依据）
go test -v ./engine/ -run TestRandomNestedSequencesMatchNaive
go test -v ./engine/ -run TestSnapshotCostIndependentOfDepthAndWrites

# O(1) 视图构造基准
go test ./engine/ -run '^$' -bench BenchmarkViewConstruction

# 演示
go run ./cmd/server
```

测试矩阵：

| 测试 | 覆盖的需求 |
| --- | --- |
| `TestNestedPreHookSeesOuterUncommittedWrites` | 嵌套前置钩子看到外层未提交写入 |
| `TestPostHookFiresOnceAtOutermost` | 后置钩子只在最外层触发一次，看到最终状态 |
| `TestPostHookFailureRollsBackEverything` | 后置失败时全部写入（含嵌套）回退 |
| `TestPreHookFailureAbortsImmediately` | 前置失败立即中止后续写入与嵌套调用，整体回退 |
| `TestPostHookAggregation` | 多个后置失败按注册顺序聚合报告 |
| `TestErrorPrecedence` | 三类错误的报告优先级与可区分性 |
| `TestSelfCallDepthLimit` | 自调用与深度保护 |
| `TestConcurrentOutermostActionsSerializable` | 并发最外层动作可串行化、无交错 |
| `TestReplayDeterministic` | 重放确定性 |
| `TestSnapshotCostIndependentOfDepthAndWrites` + 基准 | O(1) 快照开销证明 |
| `TestRandomNestedSequencesMatchNaive` | 40 组随机嵌套动作序列与朴素模型逐条对照（错误类别与文本、最终状态、钩子记录），打印输入、实际输出与判定依据 |
| `tx` 包测试 | 写入校验规则、校验可见未提交写入、提交 / 回退语义 |

朴素模型（`naive`）是与正式引擎**独立实现**的对照 oracle：它独立
维护事务日志（每次写入记录逆操作，回退时逐条反向回放）、逐步应用
写入、在固定时点（每次写入前 / 提交前）调用钩子，且每次前置钩子
前都对整个状态做全量深拷贝作为快照。两个实现只共享 `spec`（数据
模型）、`errs`（错误类别）与 `hooks` 包的接口类型，不共享注册表、
调度器与存储实现。
