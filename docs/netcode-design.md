# 服务端权威输入处理与客户端预测对账设计

## 模块职责

- `netcode/server.go`：服务端仲裁。维护时钟、玩家权威位置、已接收序号、已处理序号、待处理输入和每个 Tick 的确认。
- `netcode/client.go`：客户端预测。输入立即按相同移动规则更新本地位置，只保存尚未确认的输入。
- `netcode/rules.go`：纯规则。校验配置、执行单步上限拒绝、位置截断，服务端与客户端共用，避免两套规则漂移。
- `netcode/types.go`：输入、接收结果、确认、Tick 结果等跨模块数据类型。

## 关键规则

1. 接收阶段只做序号与积压检查，不改变位置。
   - 序号必须等于已接收最大序号加一。
   - 重复序号幂等返回原接收结果，不再次入列。
   - 缺口直接拒绝，不改变已接收序号、待处理序列和时钟。
   - 待处理输入达到 `P` 时返回积压已满，同样不推进任何序号。
2. Tick 阶段统一移动。
   - `now` 必须严格大于上一次成功 Tick 的 `now`。
   - 每个玩家每个 Tick 至多处理 `K` 个输入，按序号升序。
   - `|delta| > M` 时拒绝，位置不变，但消耗配额并推进已处理序号。
   - 合法移动后截断到 `[0, W]`；截断仍为接受。
3. 对账阶段以权威位置重置基线。
   - 只接受已处理序号严格变大的确认；旧确认和重复确认忽略。
   - 丢弃所有不大于已处理序号的未确认输入。
   - 确认中列出的服务端拒绝序号也从待重放集合剔除。
   - 从权威位置开始，按序号升序重放其余未确认输入。

## 关键取舍

- 使用每个玩家独立的有序待处理切片，而不是全局优先队列。输入在每个玩家内已经按连续序号进入，全局队列既增加锁竞争，也增加跨玩家堆排序成本。
- 服务端维护“活跃玩家”列表。只有待处理输入非空的玩家才会进入 Tick，处理完且队列清空后移出，因此 Tick 不遍历所有已注册玩家。
- 服务端为每个序号保留接收收据直到进程状态被显式淘汰，用于重复请求的幂等返回。待处理输入本身仍最多保留 `P` 个，被拒绝接收不会进入。
- 客户端只保存未确认输入。确认到达时用二分找到第一个大于已处理序号的位置，前缀不再扫描；之后只遍历剩余未确认输入。
- 确认中同时给出权威位置和服务端拒绝集合。这样被服务端拒绝的输入不会在回滚重放时再次按本地“预测成功”处理。
- 所有公开方法在模块内用互斥锁串行化。调用方可以并发调用；可线性化执行点由模块内锁顺序确定。本模块没有跨对象锁，因此不会产生锁环。

## 被放弃的方案

- **Tick 时扫描全部玩家**：实现最简单，但 Tick 成本随空闲玩家总数增长，不满足要求。
- **全局输入堆按 `(玩家, 序号)` 排序**：能统一处理输入，但每个 Tick 仍需识别有输入的玩家，且堆操作为 `O(log n)`；按玩家有序切片只需 `O(K)`。
- **客户端保留全部历史输入**：回滚容易实现，但确认应用必须扫描历史，长期运行成本不可接受。
- **只靠权威位置修正，不发送拒绝集合**：无法区分“被截断接受”和“超步拒绝”，客户端重放会错误地再次应用被拒绝输入。
- **在接收时立即移动**：会破坏服务端 Tick 配额和统一时钟语义，也无法把同一 Tick 的输入作为同一权威批次处理。

## 复杂度

- `Submit`：平均 `O(1)`；只访问单个玩家状态并向有序尾部追加。
- `Tick`：`O(sum(min(K_i, len(pending_i))))`，只遍历活跃玩家；另对有变化玩家标识符做字典序排序以稳定确认输出。
- `Client.AddInput`：`O(1)` 摊还；立即预测并把输入放到未确认尾部。
- `Client.ApplyConfirmation`：二分前缀为 `O(log n)`，随后只重放剩余未确认输入，总计与剩余未确认输入数成线性关系，不扫描已确认历史。
- 空间：服务端每玩家待处理输入为 `O(P)`；客户端只保存未确认输入。

## 可复现性

- 相同的配置、注册初始位置、提交顺序、Tick 时间和确认投递顺序产生相同状态。
- Tick 内确认玩家顺序使用玩家标识符字典序，`TickResult.Players` 提供稳定顺序；确认 map 允许调用方按任意网络次序投递。
- 随机测试使用固定种子 `2026100600 + case`。每个用例独立构建真实模块和独立朴素模型，比较每次提交、Tick、确认和最终状态。
