# 权限变更生效时序模块设计

## 1. 领域模型

每条 `Change` 都有两条独立时间轴：

- `SubmittedAt`：提交时刻，决定该记录何时进入系统，以及同一生效时刻的叠加顺序。
- `EffectiveAt`：生效时刻，决定该记录何时可参与访问判定。

约束 `EffectiveAt >= SubmittedAt`。在 `EffectiveAt` 到达前，记录处于排队状态，不影响任何查询。

权限记录按 `(subject, label)` 隔离。变更类型：

- `PUT`：设置该主体、该标签的允许或拒绝结果。
- `REVOKE`：显式撤销同一条时间线上的一条既有记录；新 `PUT` 可以覆盖旧 `PUT`，但旧记录不会被删除。

同一生效时刻的总排序为：

```text
EffectiveAt, SubmittedAt, Change.ID
```

`Change.ID` 是调用方提供的固有且全局唯一标识，因此相同输入重放得到完全相同的叠加顺序，不依赖 map、goroutine 或内存地址。

## 2. 历史查询

对时刻 `t` 的查询只采用同时满足下列条件的记录：

- `SubmittedAt <= t`
- `EffectiveAt <= t`
- 未在其生效前被撤回

系统维护按实际状态翻转时刻排序的事件日志。查询重放到 `t` 后，由最终仍处于 active 状态的 `PUT` 中排序最靠后者给出 `ALLOW` 或 `DENY`；没有 active `PUT` 时返回默认 `DENY`。

事件日志只追加状态翻转，不重写已确认历史。后续提交或撤回会从原始记录重新物化该 subject-label 时间线，因此已完成的历史查询结果可重复读。

## 3. 排队撤回与生效后撤销

排队记录只允许在严格早于 `EffectiveAt` 的时刻撤回。撤回后：

- 记录保留 tombstone，仍可解释曾经发生过的提交与撤回。
- 记录不进入任何时刻的有效规则集合。
- 已生效记录不能修改或删除，只能提交新的 `REVOKE` 或新的 `PUT`。

尝试在 `WithdrawnAt >= EffectiveAt` 撤回时返回 `WITHDRAW_ALREADY_ACTIVE`。

## 4. 依赖与级联重估

`REVOKE` 本身也是一条可被后续撤销的记录。系统为每个 subject-label 维护：

- 原始变更记录；
- `record ID -> dependents` 的撤销依赖；
- `revokerCount`，表示当前有多少条 active 撤销记录指向该记录；
- 实际激活/失活事件日志。

激活条件：

- `PUT`：未撤回且没有 active 撤销者；
- `REVOKE`：未撤回、没有 active 撤销者，且其目标当前 active。

当一条撤销记录自身被撤销时，其目标重新满足激活条件，就会在该撤销真正发生的时刻恢复；依赖该状态的后续撤销记录会在同一个物化边界被重新扫描，直到状态达到确定性不动点。撤销环在提交时被拒绝，避免因果无唯一解。

如果一条后续撤销在其原生效时刻因前提不存在而没有激活，它不会追溯激活；只有其前提后来建立并再次满足条件时，才从状态实际翻转的时刻起生效。

## 5. 并发与错误优先级

所有公开方法由同一个互斥保护，调用结果等价于某个串行顺序。这个选择优先保证强线性一致和代码简单；读写锁、分片锁、无锁时间轮询等优化见“放弃的方案”。

固定错误汇报顺序：

1. `EFFECTIVE_BEFORE_SUBMIT`
2. `QUERY_BEFORE_HORIZON`
3. `WITHDRAW_ALREADY_ACTIVE`

其余校验（重复 ID、未知 ID、同 subject-label、撤销环等）是领域结构错误，不改变上述三类规定错误的优先顺序。所有拒绝都在修改队列和最早记录下界之前返回。

## 6. 查询复杂度与可观测证明

物化结构按 `(subject, label)` 分区，其他主体、其他标签以及尚未生效的排队记录不会进入查询事件流。

`QueryResult.ExaminedChangeID` 是不依赖内部锁、指针或 map 迭代顺序的外部可观测证明：

- 它列出截至查询时刻，在该 subject-label 时间线上曾经实际进入 active 状态的记录；
- 不包含其他 subject-label；
- 不包含仍在排队的记录；
- 不包含前提从未成立、因此从未实际生效的 no-op 撤销；
- 其长度只随该 subject-label 确实生效过的记录数增长，不随系统累计记录总数增长。

`TestExaminedProofBoundedByEffectiveSubjectLabelChanges` 构造大量其他主体、其他标签和本 subject-label 的排队记录，断言外部观察到的 `len(ExaminedChangeID)` 仍只等于相关且已生效记录数。

当前物化实现为了优先保证语义正确，在懒推进边界使用小规模不动点重扫；它不改变查询外部可见的 `ExaminedChangeID` 上界。更高写入吞吐版本可把依赖级联改为持久化的拓扑增量传播，接口和事件证明无需变化。

## 7. 朴素参照与测试

`NaiveReference` 是独立维护的参照实现：

- 保存原始提交和撤回；
- 每次查询都重新筛选满足两条时间轴的记录；
- 逐生效边界反复扫描，直到 active/revokerCount 达到不动点；
- 不共享生产实现的增量物化数据结构。

测试包括：

- 同一生效时刻按提交时刻、ID 叠加；
- 历史查询可重复读；
- 排队撤回在任何查询时刻不可见；
- 已生效记录不可直接撤回；
- 撤销一条撤销记录后的恢复与后续撤销级联；
- 拒绝提交/撤回无副作用；
- 并发提交、撤回、查询的 race 检测；
- 120 个固定随机种子、每个 120 个操作的差分测试，逐项比较生产实现和朴素参照。

每次 `Submit`、`Withdraw`、`Decide` 都写入审计记录，字段包括：

- `Call`
- `Input`
- `Output`
- `TemporalBasis`

## 8. 放弃的方案

- **只用生效时刻排序**：无法满足同一生效时刻按提交时刻叠加的要求。
- **提交后立即覆盖旧状态**：会让排队变更提前影响当前判定。
- **直接删除已生效记录**：不能保留可审计、可追溯的历史，也无法支持历史查询。
- **把撤回当成普通失效事件**：撤回发生在生效前时，该记录从一开始就不应有任何效果，不能在事件流中留下激活事实。
- **只处理直接目标，不重扫依赖者**：撤销一条撤销记录时，后续依赖旧基线的撤销记录可能被错误保留或遗漏。
- **依赖 map 迭代或 goroutine 完成顺序**：不能提供确定性，不满足可重复计算要求。
- **全局无锁时间轮**：吞吐潜力更高，但会显著增加并发证明和撤回/后到达物化的复杂度；当前需求更重视正确语义与可审计性。
