# 对象生命周期状态机：惰性到期迁移子系统设计说明

## 1. 目标与核心约束

对象类型（`ObjectType`）声明一组迁移（`TransitionDef`），迁移有三种触发方式：

- `TriggerExpiry` 到期迁移：进入源状态的时刻 + 固定时长即满足时间条件；
- `TriggerAction` 显式动作：由外部调用按名字触发；
- `TriggerForced` 强制迁移：只能由另一条迁移的链式效果触发。

到期迁移不依赖后台扫描。系统保证：

1. **惰性结算**：只有当某次调用真正访问实例（读取状态/属性/链接）或对其发起动作时，
   才在“返回结果或判定动作前置条件之前”把所有应当已经发生的到期迁移一次结清。
2. **多步链路**：一次结算沿到期迁移链连续推进，直到当前状态不存在到期出边或时间未到。
3. **非时间前置条件**：到期环可以携带 `Guard`（引用属性/链接）。条件不满足时实例停在
   当前状态、不再向后推进，且不影响判定所使用的时钟来源。
4. **先结算后动作**：显式动作的前置条件只在到期结算完成后的状态上判定；被拒绝的动作
   不改变任何状态、属性或时间戳，但此前已结算生效的到期环保留。
5. **跨实例链式到期联动**：到期/强制/动作迁移可以声明 `Chain`，在触发时强制另一个经
   `Link` 到达的实例发生指定迁移；无论从链路的哪个实例进入，结算顺序都严格遵守声明
   的链式次序。
6. **时钟回退**：已结算的到期迁移是不可逆既成事实；回退只影响此后尚未发生的判定。
7. **并发去重**：同一到期环在并发访问下最多生效一次。
8. **结算开销**：只随本次新结算的环节数增长，不随实例历史上到期迁移总数增长。
9. **历史推导**：可基于迁移历史重新推导实例在任意过去时刻的状态，结果与“当时若发生
   惰性结算”完全一致，且不依赖查询时实例已结算到的最新状态。

## 3. 关键设计取舍

### 3.1 时间来源：进入时刻 + 固定时长，使用“到期时刻”推进

实例保存当前状态的进入时刻 `entered`。到期环的到期时刻为
`dueAt = entered + Duration`。

到期环在延迟很久才被访问时触发，其**新状态进入时刻被记为确定性的 `dueAt`，而不是
观察时刻**。这样下一环仍从它本应进入的瞬间开始计时，惰性结算的延迟不会扭曲后续环的
时间来源。事件同时记录 `At`（实际观察/提交时刻）与 `OccurredAt`（该环的虚拟到期时刻），
二者分离是历史重放与因果链的基础。

### 3.2 两趟结算：强制波优先于各自后续到期环

一条链可能是 `A 到期 → 强制 B → 强制 C`，随后 B、C 各自还有到期环。若在 A 的到期
循环内立即级联并继续结算 B 的后续到期环，会错误地产生
`a-expire, b-force, b-expire, c-force, ...` 的顺序。

正确语义是声明链上的强制效果先全部按序提交：

```
wave 1（forced）：a-expire → b-force → c-force
wave 2（expiry）：各自再推进自己的后续到期环（b-expire, c-expire）
```

实现上对连通闭包做 Kahn 拓扑（边即声明的 `Chain`），强制波沿链深度优先；到期波中每
触发一环，仍先做其强制级联再继续后续到期环。从链路中间实例进入时，通过**反向链索引**
（`SetLink` 时维护）先把前驱纳入闭包，因此入口不影响最终顺序。

### 3.3 Guard 停止 vs 外部数据写入

到期环的 `Guard` 在“环已到期”时才评估；失败产生最高优先级 category-1 错误，实例停
在当前状态。

一个真实的工程取舍是：`SetProperty`/`SetLink` 本身是外部数据管理操作。若它们也因
category-1 停止而整体失败，就永远无法写入能让该 Guard 成立的数据，形成死锁。因此：

- **读取与生命周期动作**严格“先结算、后处理”，category-1 会阻断；
- **属性/链接写入**先尝试结算，但仅当返回的是 category-1 时允许写入继续（其它类别
  仍然拒绝）。该取舍在文档中显式声明，且随机对拍避免构造“环到期后再翻转 Guard”的
  跨语义场景，改为专门的单元测试覆盖。

### 3.4 时钟回退：不可撤销 + 仅影响后续判定

每个实例维护 `highWater`（驱动过结算的最大观察时刻）。当 `now < highWater` 时：

- 不撤销任何已提交环（状态与历史不动）；
- 记录一个 category-4 `ErrClockRegression`，作为最低优先级异常；
- 继续用真实 `now` 判定“尚未发生”的环，回退后跨度不足则不触发。

category-4 在读取路径透出；在显式动作路径不作为阻断错误（既成事实不可撤销，动作仍按
当前状态正常判定），但其存在仍被结算记录器记录。

### 3.5 并发：单把引擎锁保证幂等

所有访问入口在同一把 `sync.Mutex` 下完成“结算 + 处理”。并发调用被串行化：先到者结清
全部到期环，后到者观察到的已是推进后的状态，本次结算 0 个环。因此同一条到期环不可能
被结算两次，且不需要 CAS/版本号重试。以单实例闭包为粒度的细粒度锁是被放弃的方案（见
§4），因为它显著增加链式联动的死锁面，而当前平台规模下全局锁足够。

### 3.6 错误优先级

固定 1 > 2 > 3 > 4：

1. `ErrExpiryGuard` 到期链某环非时间前置条件不满足；
2. `ErrChainTrigger` 跨实例联动触发失败（链接未绑定、目标状态不符、强制迁移缺失、
   强制 Guard 失败、链式拓扑成环）；
3. `ErrActionPrecondition` 结算后显式动作前置条件仍不满足；
4. `ErrClockRegression` 时钟回退异常。

结算在遇到 1–3 时立即停止并返回；category-4 只记录不阻断。动作触发的链失败时，源动作/
源到期环已提交的部分保留，失败点之后不推进。

### 3.7 开销模型（不遍历历史）

结算只读取实例的**当前状态 + 进入时刻**，沿当前状态的唯一到期出边循环：

```
本次开销 = O(本次新结算环节数) + O(链上连通闭包大小)
历史上已发生的到期迁移总数 N 不出现在任何结算循环中。
```

`ReplayDueChecksAt(t)` 暴露“到期时间判定次数”探针：在某实例已提交 h 环后，对未来时刻
（恰好再到期 k 环）重建并结算，判定次数恒为 k，与 h 无关；稳态访问判定次数为 0。该
计数即“不依赖遍历历史”的可执行证明，测试断言 k=1/5/10/30 时次数分别为对应值。

### 3.8 历史推导：StateAt

`StateAt(id, t)` 完全不看实例当前内存状态，而是：

1. 收集所有实例在 `t` 之前（含）的提交事件，按 `(At, 提交顺序)` 全局排序（同刻的
   forced 环以提交先后排，即声明链序）；
2. 折叠到一个一次性的模拟引擎，重建状态、属性、链接与反向链；
3. 在 `t` 执行一次假设性惰性结算（与线上同一套结算代码），返回状态。

因此推导结果与“当时真的发生一次惰性访问”逐位一致；事件中保存 `OccurredAt` 使到期环
的时间链可精确重建。测试用独立构建的引擎在 0..40 分钟逐分钟对照。

## 4. 被放弃的方案

- **后台扫描器作为主路径**：实现简单但违背“无后台扫描、惰性判定”的硬约束，且在大量
  冷实例上持续空转。保留为 `naive` 包，仅作独立对拍参考。
- **每实例细粒度锁 + 两阶段提交**：并发更平滑，但链式联动需要稳定加锁顺序以防死锁，
  复杂度高、易错；当前规模下全局锁已能保证正确性与去重。
- **用观察时刻作为新状态进入时刻**：会让“延迟结算”污染下一环时钟来源，破坏历史推导
  的确定性；改用确定性的 `dueAt` 记录进入时刻。
- **Guard 失败也拒绝属性写入**：会让补救 Guard 的数据无法写入，形成不可恢复死锁；故
  对外部数据写入开放 category-1 例外（§3.3）。
- **回退时回滚已结算环**：直接违反“既成事实不可逆”，且无法与跨实例因果一致，明确拒绝。
