# 重复保险多保单理赔分摊与限额消耗系统 — 设计说明

## 1. 目标与规则摘要

同一标的被多张同时生效的保单覆盖时，按损失补偿原则分摊一次事故：

1. **独立赔付额** `cap_i = min(max(损失 - 免赔额_i, 0), 剩余保额_i)`。
2. **普通条款（Ordinary）先赔**：总赔付 `P_ord = min(Σcap_i, 损失)`；
   各保单先取 `floor(P_ord * cap_i / Σcap)`，余数按
   `(生效日, 保单编号)` 字典序循环、每次一单位、只补给“尚未到独立赔付额”
   的保单。
3. **超额条款（Excess）后赔**：仅在 `未补偿 = 损失 - P_ord > 0` 时介入，
   `P_exc = min(Σcap_j, 未补偿)`，在超额保单之间使用完全相同的比例/余数
   规则。
4. 任何赔付 `≤ 独立赔付额 ≤ 剩余保额`，所有赔付之和 `≤ 损失`。
5. **更正**某事故损失后，该事故及其后登记的事故按序号从该事故开始重算；
   重算结果必须与“从头顺序重放”完全一致。
6. **注销**自指定日起对“当天及以后新登记”的事故生效；历史事故不变。
   注销日不得早于该保单覆盖过的任一事故发生日（覆盖与是否实际赔到钱无关）。

## 2. 模块划分

```
internal/
  claim/          生产实现
    types.go       输入/输出类型、条款枚举、哨兵错误
    treap.go       按标的维护的“生效区间增广 Treap”
    allocate.go    纯函数：一组保单的比例 + 余数分摊
    engine.go      System：登记/更正/注销/查询、冻结参与者、增量重放
    *_test.go      定向、随机对照、并发、复杂度、分摊单元测试
  naive/          独立朴素参考模型（事件日志 + 全量线性重放）
docs/
  CLAIM_DESIGN.md 本文件
  CLAIM_USAGE.md  API 使用说明与本地验证方法
```

职责上严格分三层：

- `treap` 只回答“某标的、某日有哪些未在该日之前被注销的保单”，不含金额；
- `allocate` 是无状态纯函数，输入候选独立赔付额，输出各保单份额；
- `engine` 管理并发、状态、参与者冻结与增量重算，是唯一持有可变状态的层。

朴素模型 `internal/naive` **不调用生产代码的任何分摊/索引逻辑**，自己以
“事件日志 + 嵌套线性扫描 + 逐单位补余数”重新实现全部规则，用于差异测试。

## 3. 关键数据结构

### 3.1 事故与“参与者冻结”

- 事故按登记先后保存在切片中，序号即切片下标；`accByID` 做编号到序号映射。
- 每个事故在**登记当时**快照 `participants []string`（覆盖保单编号集合）。

这个快照是满足两条语义的关键：

- 事故之后才新增的保单，即便生效期回溯覆盖事故日期，也不参与其重算；
- 更正重放只需读快照，不必、也不会重新做一次“当前保单集合”的区间查询。

### 3.2 每标的的增广 Treap（区间刺点查询）

区间 `[StartDay, EndDay]]` 以 `(StartDay, PolicyID)` 为 BST 键，随机
优先级保持期望平衡；每个子树缓存 `maxEnd = 子树内最大 EndDay`。

刺点查询 `coveringAt(day)` 走树并剪枝：

- 节点 `StartDay > day` 时，右子树必然全部开始更晚，只进左子树；
- 某子树 `maxEnd < day` 时整棵跳过；
- 节点命中条件为 `StartDay <= day <= EndDay && CancelDay > day`。

**注销节点不从树中删除**。提前注销（例如注销日 19）的保单仍可能覆盖在
19 日之前才登记、发生日为 18 的事故；删除节点会把这类合法参与者漏掉
（该缺陷在随机对照中被真实抓到并修复）。注销只把节点 `CancelDay` 从
`+∞` 改为指定日。

### 3.3 每保单参与台账（支持“只重算受影响后缀”）

每个 `policyRec` 除 `paid`（累计已赔）外，维护三条等长、严格按事故序号
递增的台账：

```
participationSeq  []int   // 该保单参与过的事故序号
participationPaid []int64 // 对应赔付额
participationCum  []int64 // 赔付额前缀和
```

更正从序号 `from` 重算时：

1. 收集 `from..` 事故中出现的保单集合 `T`（只遍历受影响事故的参与者）；
2. 对每个 `p ∈ T`，用 `SearchInts(seq, from)` 二分定位切分点 `cut`，
   从前缀和 `O(1)` 读回“固定前缀已赔总额”，截断台账到 `cut`；
3. 顺序调用 `computeResult` 重算后缀，重新追加台账。

因此保单的剩余保额恢复**不扫描任何未受影响事故**。

## 4. 分摊算法与取整

- 比例底数用 `math/big.Int` 计算 `pot * cap / sum`，防止
  `pot * cap` 在 `int64` 上溢出（结果金额仍为 `int64`）。
- 余数分配把候选按 `(StartDay, PolicyID)` 排序后组织成双向循环链表；
  每次给当前节点一单位，达到其独立赔付额即从链表摘除。
  - 每访问一个节点必发出一单位，故总步数恰为余数单位数；
  - 与朴素“逐单位从头扫描、跳过已满者”严格等价（由
    `TestShareGroupMatchesUnitSteps` 2000 组随机输入验证）。
- `S = 0`（所有独立赔付额为零）时总赔付为 0，直接返回空赔付。

普通与超额两轮使用同一函数；第二轮的“pot”是
`min(Σcap_excess, loss - P_ord)`，所以普通足额赔付时超额 pot 为 0，
超额保单不产生任何赔付。

## 5. 错误模型与优先级

哨兵错误（用 `errors.Is` 判定）：

`ErrInvalidArg` > `ErrDuplicateID` > `ErrNotFound` > `ErrPolicyCancelled`

- 结构性参数检查（空编号、保额 ≤ 0、负免赔额/损失、日期为负、生效>到期、
  注销日 > 到期日、条款类型非法）在加锁/查状态前完成；
- 之后依次查重复、查存在；
- 注销的两个“业务参数”规则——注销日 ≤ 到期日、注销日不早于已覆盖事故
  最大发生日——属于参数非法，优先于“已注销”；
- 所有拒绝路径都在任何状态变更之前返回（`TestRejectedOperationsLeaveNoTrace`
  通过前后结果与剩余保额比对验证“不留痕”）。

保单编号与事故编号共用一个唯一性命名空间（任一类型先占用即重复）。

## 6. 并发与确定性

- `System` 用一把互斥锁串行化所有变更与读；可线性化，结果等价于某个
  串行顺序（`TestConcurrentSerializable` 用 `-race` 验证竞争添加/竞争
  注销恰有一个赢家，其余分别是“重复”/“已注销”）。
- Treap 优先级来自确定性计数器的固定混合（fixed-mix）哈希，不使用随机
  种子，因此**相同操作序列在任何机器上重放得到完全相同的树形与赔付**。

## 7. 复杂度

设一次事故覆盖保单数为 `k`、该标的有效保单数为 `P`：

- **登记**：区间刺点 `O(k log P)` 次节点访问（Treap 期望高度 `O(log P)`，
  每条命中路径 `O(log P)`；常数因子的剪枝由 `maxEnd` 提供），分摊
  `O(k log k)`，总计与**全部事故数 N 无关**。
- **更正**：恰好重算“更正事故 + 其后全部事故”，对每个受影响事故做与
  登记同阶的工作；每个受影响保单的固定前缀恢复是“一次二分 + 一次 O(1)
  前缀和”。总计只与**受影响事故及其覆盖保单数**有关，与未受影响事故数
  无关。
- 保单新增/注销为 Treap 的期望 `O(log P)`；查询为 `O(log P)` 或
  `O(k log P)`（含支付明细时）。

### 可验证的证明方式

`System.Stats()` 暴露三个内部工作量计数器：索引节点访问数、重算事故数、
前缀台账查找数。测试以可执行的方式断言（非仅纸面声明）：

- `TestRegistrationCostIndependentOfAccidentCount`：覆盖保单固定为 3，
  事故总数从 200 增长到 3200，新登记走访的索引节点数恒定为 3、重算事故
  数恒为 1；
- `TestCorrectionCostOnlyAffected`：受影响后缀固定为 50，未受影响前缀
  从 200 增长到 3200，一次更正的重算事故数恒为 50、前缀恢复查找数恒为
  4（即该后缀涉及的保单数），不随后缀之前的事故数增长。

此外 `System.ReplayConsistencyOK()` 会用台账从零完整重放全部事故，逐事故
比对支付明细并逐保单比对累计已赔，作为“增量状态 == 从头重放”的运行时
不变量检查（定向测试与随机对照测试都会触发）。

## 8. 被放弃的方案

- **每标的保存活动保单切片 + 登记时线性扫描**：实现最简，但登记成本随
  保单数增长，且无法证明“与总规模解耦”；放弃。
- **注销即从索引物理删除**：在“注销日晚于注销操作时已登记的事故日”时
  正确，却会错误剔除“注销日早于注销操作、事故在注销日之前但登记更晚”
  场景下的合法参与者；随机对照抓到后改为“节点保留 + CancelDay 过滤”。
- **更正时扫描所有事故恢复各保单前缀已赔**：直观但使更正成本随未受影响
  事故数线性增长，直接违反需求；改为每保单 `(序号, 赔付额, 前缀和)`
  台账 + 二分定位。
- **余数用“最大余数法”一次分完**：存在独立赔付额为 0 或在到达 pot 前先
  触顶的保单时会错分（余数可能 `≥` 候选数，且可分多轮）；改为规则字面
  语义的循环补位，并用朴素逐单位实现做差分验证。
- **朴素模型复用生产分摊代码**：会让对照测试失去独立性；朴素模型自己用
  64 位安全的小金额场景与逐单位循环独立实现全部规则。
- **时间/随机数驱动 Treap 优先级**：破坏确定性重放；改为确定性计数器哈希。

## 9. 不变量汇总

- 每张保单累计赔付 `≤ 保额`（随机对照每次操作后检查剩余保额非负）；
- 每事故总赔付 `≤ 损失`，每个支付 `≤ 该保单独立赔付额`；
- 普通总赔付 + 超额总赔付 `≤ 损失`，超额仅在普通未足额时支付；
- 增量维护状态与从头重放一致（`ReplayConsistencyOK`）；
- 被拒绝操作不产生任何可观察变化。
