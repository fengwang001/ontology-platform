# 快照格式兼容性校验组件设计说明

本组件解决：某版本格式的消费方读取另一版本格式产出的快照时，依据对象类型
结构变化（属性增删改与必填性变化）判定快照对该消费方**可读 / 需降级 / 必须拒绝**。

代码位于 `compat/` 包，按职责分为四个协作部分：

| 部分 | 文件 | 职责 |
| --- | --- | --- |
| 版本号范围判定 | `compat/version.go` | 可比较的版本号与闭区间识别范围 |
| 类型系统 | `compat/schema.go` | 属性取值集合的包含（`Contains`）与子集（`SubsetOf`）判定 |
| 属性级规则引擎 | `compat/judge.go` + `compat/change.go` | 单级兼容规则判定，固定优先级 |
| 传递性核对 | `compat/chain.go` | 跨多个中间版本的逐级核对 |

另有 `compat/naive.go` 作为朴素参照模型，专供测试对照。

## 核心模型

- **Format**：一个格式版本 = 完整物化的 `Schema` + 相对前驱版本的**变更日志**
  `Changes`（增/删/改类型/改必填，逐条属性级记录）。
- **Snapshot**：格式版本号 + 实际对象数据（对象类型 → 对象 → 属性 → 取值）。
- **Profile**：消费方上下文 = 编写时依据的版本 `At`、可识别版本闭区间
  `Accepts`、读/写场景 `Mode`、明确声明不依赖的属性集合 `Independent`。
- **Verdict**：等级（`compatible` / `degraded` / `incompatible`）+ 命中类别 +
  判定依据（`Issues`）+ 降级说明（`Notes`）+ 工作量统计（`Stats`）。

## 判定规则的方向性统一

所有规则都归结为“消费方侧（old）”与“数据侧（new）”两个状态的比较，
与版本新旧方向无关；沿演化链反向行走（消费方比快照新）时，对变更日志
**逐条取逆并反转顺序**（`invertAll`），使同一套规则覆盖两个方向：

- **新增属性**：可选 → 兼容（记录忽略说明，不影响可读性）；必填 → 读取场景
  降级忽略（`degraded`），写入场景禁止（`required-missing`）。
- **删除属性**：消费方仍依赖 → `required-missing`；声明不依赖 → 兼容。
  数据侧仍出现该属性取值 → `deleted-property-present`（格式不一致，不静默丢弃）。
- **取值类型变化**：要求数据侧类型 ⊆ 消费方侧类型（子集关系）。满足则兼容
  （涵盖“放宽对读取旧数据兼容”）；不满足则用**实际数据**证明全部既有取值
  仍落在消费方理解的范围内，证明失败 → `type-incompatible`（涵盖“收紧除非
  可证明否则不兼容”）。
- **必填性**：必填改非必填 → 任何消费方兼容；但消费方仍要求必填且读取的是
  历史数据时，按历史数据中该属性是否始终存在判定。非必填改必填 → 读取兼容，
  写入场景禁止（`required-missing`）。

## 错误类别与固定优先级

四类错误互不相同，判定顺序固定，命中靠前类别即不再判定靠后类别：

1. `version-out-of-range`：版本号超出可识别闭区间，直接拒绝，**不做任何
   属性级判定**（`ChainVerdict.Steps` 为空）。
2. `required-missing`：必填属性缺失（含“删除的属性仍被依赖”“写入场景无法
   产出新增/新晋必填属性”“历史数据缺失消费方必填属性”三种来源）。
3. `type-incompatible`：取值类型不兼容且数据证明失败。
4. `deleted-property-present`：已声明删除的属性仍在数据中出现取值。

跨版本核对时，总顺序定义为 **(级序号, 类别优先级)** 的字典序：逐级前进，
每级内部按类别优先级判定，首级命中即停止。该顺序确定且无歧义。

## 传递性

兼容性不可传递：`JudgePath` 从消费方编写版本出发，沿演化链**逐级**把
“消费方 × 该级版本”的净变化完整判定一遍，每级给出独立 `StepVerdict`
（含依据），命中失败即停止，绝不跳过中间版本直接给结论。`Judge` 是
`JudgePath` 最终结论的便捷封装。

注意 `TestChain_NoTransitiveInference` 展示的反例：消费方对 v2 兼容、
v2 对 v3 兼容，但消费方对 v3 不兼容（v2 新增可选属性、v3 将其改为必填，
写入场景下逐级核对在第二级命中 `required-missing`）。

## 并发安全

`Judge` / `JudgePath` 是纯函数：全部输入（`Profile`、`[]Format`、`Snapshot`）
按约定视为不可变，判定过程只读共享输入，所有中间状态（净变化表）为每次
调用私有。因此任意并发查询与某次串行逐一查询结果等价。
`concurrency_test.go` 用 32 goroutine × 50 次重复查询与串行基准做
`reflect.DeepEqual` 对比，并在 `-race` 下运行验证。

## 判定开销只与变化的属性相关

关键取舍：**每个格式版本携带相对前驱的变更日志**，判定只消费变更记录，
对首次触及的属性做一次 map 查找确定消费方侧状态，**从不扫描全量 Schema**。
每级判定在 `Verdict.Stats.PropertiesInspected` 中记录实际检查的变更条数，
提供可复核证据。

`cost_test.go` 的复核方式：同样的变更记录，向 Schema 注入 10 个与 5000 个
永不变更的属性，两次判定的 `PropertiesInspected` 完全相等（=2）；而朴素
模型的检查数随属性总数增长——两者对照即证明开销只与变化的属性相关。

## 被放弃的方案

- **全量 Schema 差集判定**（即朴素模型的做法）：每次判定 O(属性总数)，
  无法满足“开销只与变化属性相关”，仅保留为参照模型。
- **相邻版本两两判定后传递合成**：把“消费方↔v1”“v1↔v2”…的相邻结论合成
  最终结论。放弃原因：(a) 题面明确禁止传递推断；(b) 相邻判定对“先放宽再
  收紧”等净零变化会误报（中间版本的潜在取值并不出现在最终快照中）。
  现方案每级都回到“消费方 × 该级版本”的净变化，语义更直接。
- **数据侧逐版本留存历史数据**：中间级别的数据依赖检查（必填存在性、类型
  收紧证明、删除属性残留）本可要求每级一份数据。放弃原因：快照只有一份
  实际数据，统一用最终快照数据做全部数据依赖检查，语义明确（“这份快照
  是否可读”）且实现简单；代价是无法区分中间版本当时的数据状态。
- **版本号仅按主版本拒绝**：过于粗糙，无法表达闭区间识别范围；现采用
  三元组字典序比较 + 闭区间。

## 本地验证方法

```bash
# 全量测试（组合规则、版本边界、传递性、并发等价、开销复核、随机对照）
go test ./...

# 竞态检测（并发查询等价性）
go test -race ./compat/

# 与朴素参照模型在 3000 条随机演化序列上对照，并记录每次判定的
# 输入、输出与依据（JSONL）
COMPAT_FUZZ_LOG=/tmp/compat-fuzz.jsonl go test ./compat/ -run TestAgainstNaiveModel

# 同一对照的 fuzz 入口
go test ./compat/ -run xxx -fuzz FuzzJudgePathAgainstNaive -fuzztime 30s

# 静态检查
gofmt -l . && go vet ./...
```

测试覆盖：

- 属性增/删/改类型/必填性变化的各种组合（`judge_test.go`），含四类错误的
  两两优先级用例；
- 版本号恰好落在可识别范围上下边界、刚好越界的情形（`judge_test.go`、
  `version_test.go`）；
- 中间版本数量为 0/1/2 的传递性判定（`chain_test.go`）；
- 并发查询与串行等价（`concurrency_test.go`，配合 `-race`）；
- 开销只与变化属性相关的可复核证据（`cost_test.go`）；
- 与朴素参照模型在大量随机演化序列上对照并记录判定日志（`fuzz_test.go`）。
