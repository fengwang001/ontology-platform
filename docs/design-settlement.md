# 采购合同履约付款结算服务 — 设计说明

包路径：`settlement/`。本文档记录关键取舍、被放弃的方案与本地验证方法。

## 1. 领域模型与不变式

- 金额一律 `int64` 分，时间一律 `int64` 日序号，比例一律万分比整数（分母 10000）。
- 服务维护全局单调时钟：`now` 小于上一次**被接受**操作的 `now` 即报时钟回退；
  被拒绝的操作不改变任何状态、欠额与时钟。
- 每个合同增量维护七个累计量：累计实付、质保金余额、缺陷扣抵、预付款抵扣、
  违约金扣抵、违约金欠额、已结算应付之和。任意时刻满足守恒：

  ```
  累计实付 + 质保金余额 + 缺陷扣抵 + 预付款抵扣 + 违约金扣抵 == 已结算应付之和
  ```

  欠额不计入该和（它是"尚未从任何应付款中扣到"的金额，不对应任何已结算应付的去向）。

## 2. 结算流水线（一次结算的固定顺序）

1. **质保金**：`ceil(应付 × 质保金比例 / 10000)`，以应付全额为基数，向上取整。
2. **预付款抵扣**：`floor(应付 × 抵扣比例 / 10000)`，以应付全额为基数，向下取整；
   再受"累计抵扣 ≤ 预付款总额"约束，超出部分不抵扣。
3. **违约金**：本次计提 `floor(逾期天数 × 日费率 × 合同总额 / 10000)`，
   再受"累计计提（已扣抵 + 欠额）≤ 封顶"约束。扣抵顺序为**欠额优先**：
   可扣额度 = 前两项扣减后的剩余；先扣结转欠额、再扣本次计提；
   扣不完的部分成为新欠额结转到下次结算。欠额天然受封顶约束，
   因为欠额只来源于已被封顶约束过的计提。
4. **实付** = 剩余 − 本次违约金扣抵，不为负。

非负性证明：创建合同时校验 `质保金比例 + 抵扣比例 ≤ 10000`，于是
`ceil(a·r1/B) + floor(a·r2/B) ≤ ceil(a·(r1+r2)/B) ≤ a`，剩余非负；
违约金扣抵又不超过剩余，故实付非负。

所有乘除用 `math/big` 计算中间量（`mulDivFloor`/`mulDivCeil`/`penaltyOf`），
杜绝 int64 溢出与浮点误差，保证任意边界下可精确复现。

## 3. 关键取舍

- **单一互斥锁串行化**：所有操作经 `Service.Execute` 唯一入口在锁内完成，
  并发调用天然等价于某个串行顺序。配合 `Recorder`（锁内追加实际操作顺序）
  与 `Replay`（在全新服务上重放并逐步比对结果），"并发等价"与
  "相同序列重放结果相同"都是可机器验证的，而非口头承诺。
- **显式释放而非自动扫描**：质保金释放是显式操作 `ReleaseRetention`。
  "满日当天不释放、次日可释放""未决缺陷暂停、关闭后下一操作触及时释放"
  都映射为对该操作的确定性校验（不满足则报"状态不允许"，不推进时钟）。
  这避免了"每个操作隐式触发释放"带来的状态突变不可预期问题。
- **全局时钟而非每合同时钟**：规格中"上一次被接受操作"未限定合同，
  取更严格的全局解释；串行化实现下二者都可行，全局更简单且可重放。
- **变更条款按生效日解析**：每个未验收里程碑保存 `(生效日, 序号) → (金额, 计划日)`
  序列，验收通过日解析"生效日 ≤ 通过日"的最新条款。变更总额校验按
  "各里程碑最终适用金额之和 ≤ 合同总额"计算（已验收的按实际验收额，不追溯）。
- **欠额计入累计计提**：封顶约束作用于"已扣抵 + 欠额"，因此欠额同样受封顶约束，
  且终止合同后欠额不再扣抵（不再产生新结算）。
- **错误优先级用检查顺序保证**：每个操作严格按 参数非法 → 时钟回退 → 不存在 →
  状态不允许 → 重复结算 → 变更超出总额 的顺序检查，命中即返回，只报第一个。

## 4. 被放弃的方案

- **惰性自动释放质保金**（每个操作先扫描到期质保金）：被拒绝的操作不得改变状态，
  隐式释放会让"拒绝不改变状态"的语义复杂化（拒绝前要不要先释放？），
  且汇总随查询时间隐式变化，不利于精确复现。放弃。
- **事件溯源 + 每次重放全量日志得到汇总**：汇总查询开销随历史增长，
  直接违反复杂度要求。放弃；改为增量累计 + 测试中用朴素模型全量重算对照。
- **float64 或定点 int64 直接乘除**：浮点有舍入误差，int64 连乘会溢出
  （逾期 × 费率 × 总额可达 10^4 × 10^4 × 10^18）。放弃，改用 big.Int 中间量。
- **每合同一把锁**：能提升并发度，但全局时钟使跨合同操作仍有顺序依赖，
  收益有限而串行化证明更复杂。放弃，保留单锁。

## 5. 复杂度与可验证性

- 结算、释放、缺陷登记/关闭、变更、终止、汇总查询均为 O(1)
  （变更的总额校验为 O(里程碑数)，里程碑数属合同配置而非历史记录）。
- 缺陷只维护 `未决数` 与 `罚没累计` 两个计数器用于释放判定，不遍历历史缺陷。
- 验证方式：`TestSummaryConstantWork` 断言在 2000 条缺陷记录的历史下
  `Summary` 零分配（常数工作量）；`TestNaiveModelDifferential` 用 O(历史)
  重算的朴素模型逐步对照 O(1) 增量汇总，二者始终相等即复杂度和正确性的双重证据。

## 6. 本地验证方法

```bash
export PATH=$PATH:/usr/local/go/bin
go build ./... && go vet ./... && gofmt -l .
go test -race -count=1 ./settlement/                 # 全量 + 竞态检测
go test -run TestNaiveModelDifferential -v ./settlement/  # 查看每步输入/输出/判定依据
go test -run TestConcurrentEquivalence -race -v ./settlement/
```

测试覆盖：质保金向上取整与预付款向下取整的零头、预付款恰抵清与超额截断、
违约金恰触封顶、欠额结转与优先扣抵、驳回后重验的逾期、质保满日恰等与次日、
缺陷暂停/关闭后释放/罚没封顶/按里程碑隔离、变更不追溯与未来生效日、
变更超额拒绝、终止后处理、拒绝优先级、拒绝不改变状态与时钟、重放确定性、
并发等价、守恒，以及 40 个随机种子 × 200 步的朴素模型对照。
