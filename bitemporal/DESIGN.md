# 双时态快照格式版本兼容判定组件 — 设计说明

## 1. 问题与范围

本体实例的属性取值携带两条相互独立的时间轴：

- **有效时间轴（valid time）**：事实在业务世界中成立的时间；
- **事务时间轴（transaction time）**：事实在系统中被记录的时间。

快照导出格式在不同版本之间，对“是否记录每条轴”以及“区间端点闭合/开放
方式”有不同约定。本组件在版本升级或降级时回答两个问题：

1. 双时态信息能否被正确保留？
2. 若必然损失，具体损失的是什么（哪条轴、哪些时点的归属）？

组件只做**判定与迁移投影**，不负责序列化本身。

## 2. 模块划分

按题面要求拆成三个职责清晰、相互协作的部分（另有薄的装配层）：

| 文件 | 职责 |
| --- | --- |
| `interval.go` | 区间值模型、时点归属、**记录自身时态区间自洽性校验** |
| `record.go` | 双时态记录及其两条轴的自洽性入口 |
| `boundary.go` | **边界语义比较**：点集等价转换、归属差异判定与 witness 时点 |
| `version.go` | 格式版本注册表（记录哪些轴、各自端点约定） |
| `judge.go` | **版本间信息留存规则判定**：固定优先级编排、损失/填充报告、批量判定 |
| `migrate.go` | 单步迁移投影与多跳路径组合（纯函数式产出新记录） |

## 3. 关键建模取舍

### 3.1 时间域：离散整数时点

区间端点用 `int64` epoch 表示，合法业务域为
`[MinFinite, MaxFinite] = [-2^62, 2^62-1)`。选择离散域而不是连续实数，
是因为快照版本的边界差异（`[a,b]` vs `[a,b)`）只有在**离散时点域**上
才能给出确定、可复核的答案：

- `[10,20]` 与 `[10,21)` 包含完全相同的整数时点集合，因此对任何整数
  查询时点归属判定相同——差异不造成影响，判为兼容；
- `[10,MaxFinite]` 无法在域内写成半开区间（需要域外端点 `MaxFinite+1`），
  时点 `MaxFinite` 的归属必然改变——判为不兼容，并给出该 witness；
- 空区间 `[s,s)` 无法表示为闭区间（`[s,s]` 非空），时点 `s` 的归属
  必然改变——判为不兼容。

“边界差异是否改变归属”因此不是主观标注，而是对端点邻域时点逐一核对
`Contains` 的客观结论（见 `boundary.go` 中 `boundaryProbePoints`）。

**被放弃的方案**：在连续时间模型下比较边界。连续域中闭/半开的差异只在
零测集上不同，无法构造整数 witness，也无法回答“某查询时点归属是否不同”；
而且实际系统时间戳总是离散存储。故放弃。

### 3.2 固定判定优先级（四类互不相同的结论）

`judge.go` 严格按以下顺序短路判定：

1. `record_invalid` — 记录自身区间不自洽（含 `start > end`、域外端点、
   无法识别的边界模式），以及“记录数据与所声明源版本不一致”（源版本
   声称记录的轴在记录中缺失）；
2. `incompatible` — 源/目标都记录的轴上，边界语义差异使某个查询时点
   归属判定不同（带 witness）；
3. `info_loss` — 仅由“记录与否”差异引起：目标不记录某条源记录的轴，
   报告具体丢弃的轴（例如降级到仅事务版本时明确报告
   “损失的是 `valid_time`”，绝不笼统报“格式不兼容”）；
4. `unknown_version` — 源或目标版本号不在注册表中。

**理由（为何是这个顺序）**：

- 自洽性是数据本身的性质，与选用什么版本对无关；若不最先暴露，同一条
  坏记录在不同版本对下会得到不同类别结论，既不稳定也会掩盖数据问题。
  题面也明确要求“在格式兼容性判定之前先行拒绝”。
- 边界不兼容改变的是**保留下来的轴**的查询语义，无法靠“丢弃一条轴”
  消解，属于硬错误；信息损失是主动、可精确描述的投影，故硬错误优先。
- 轴记录与否的差异是可投影、可报告的，排在硬错误之后。
- 版本识别只是一次查表，前三级均不依赖该查表结果即可独立判定
  （坏记录即使版本号也不认识，仍应先报坏记录），故置于最后。

### 3.3 缺失轴的唯一填充规则

源不记录、目标记录的轴（典型：仅事务格式升级到双时态格式），按
**全局唯一、与实例无关、不允许人工逐例指定**的规则填充：

> 填充为覆盖全部业务时间的“永恒区间”
> `[MinFinite, MaxFinite+1)`（闭端格式下等价记为
> `[MinFinite, MaxFinite]`）。

语义是“该轴上无信息 ⇒ 对所有查询时点成立”，与“快照只陈述已知事实”
的解释一致，且确定性、可复核。不存在未定义状态。

**被放弃的方案**：

- *按实例人工指定*：题面明确禁止，且不可自动化、不可复现；
- *用事务时间轴复制填充有效时间轴*：两条轴语义独立，互相借用会把
  “录入时间”伪装成“业务成立时间”，制造看似精确实则错误的数据。

### 3.4 多跳迁移：损失不恢复、按轴累计

`MigratePath` 逐跳投影并合并判定，规则：

1. 某跳丢弃的轴，后续跳即使遇到记录该轴的版本，也只能得到固定填充值，
   原始值不会“复活”；
2. 损失/填充按轴归并去重，一条轴在整条路径上只报告一次；
3. 任一跳出现硬错误（不自洽/不兼容/未知版本）整体失败。

需要向使用者明示的一条**基础事实（取舍说明）**：若中间经过一个
“更弱”的版本（记录的轴是源与目标记录轴集合的真子集），则信息论上
不可能对全部取值都保证“多跳结果 == 直迁结果”——被中间版本丢弃的轴
在直迁路径中本可保留。因此本组件的保证是：

- 多跳迁移**绝不恢复**已损失信息、**绝不凭空新增**损失类别
  （同样的端点版本对、且中间版本不更弱时，多跳与直迁逐条一致，
  见 `TestPathEquivalence` 第 1 组）；
- 先升级后降级（v3→v1→v3）的最终记录与直迁完全相同，
    填充出的有效时间在降级时被丢弃，不会残留（第 2 组）；
- 经过更弱中间版本（v1→v3→v1）时，重新出现的轴**只能**是固定
  永恒填充值，测试显式锁定这一行为，而不是悄悄保留原值
  （第 4 组）。

**被放弃的方案**：在记录里携带隐藏的“原始值影子字段”以便往返后恢复。
该方案违反快照格式自身的信息边界（降级导出的字节里根本没有该信息），
也会让“导出再导入”泄露目标格式明确声明不保留的数据。

### 3.5 并发、不变性与复杂度

- `Judge`/`CompareBoundary`/`Migrate` 均为纯函数：只读注册表与记录，
  迁移结果写入**新分配的记录**，输入记录永不修改；无包级可变状态，
  天然并发安全，重复调用结果恒定。
- 每条记录只遍历固定两条轴、做常数次区间运算，单条 O(1)；
  `JudgeBatch` 总开销 O(n)，n 为记录数，空间 O(n)（输出切片）。
  `TestBatchLinearComplexity` 用加倍法（2 万 → 8 万条）实测耗时比，
  线性期望约为 4，二次则约为 16，以此作为可复核的经验证据。

## 4. 内置版本

| 版本 | 有效时间 | 事务时间 | 端点约定 |
| --- --- --- --- |
| v1 | 记录 | 记录 | 闭 |
| v2 | 记录 | 记录 | 半开 |
| v3 | – | 记录 | 闭 |
| v4 | – | 记录 | 半开 |
| v5 | 记录 | – | 闭 |
| v6 | 记录 | – | 半开 |
| v7 / v8 | – | – | 不适用 |

覆盖“两条轴各自记录与否”的全部 4 种组合；可通过 `Registry.Register`
注册自定义版本。

## 5. 本地验证方法

```bash
# 全量测试（含 -race 并发判定）
go test -race ./...

# 随机对照（4000 个随机版本迁移场景 × 朴素参照模型）
# 并导出每次判定的输入/输出/依据：
BITEMPORAL_LOG=/tmp/judge.log go test ./bitemporal/ -run TestRandomDifferential -v

# 复杂度复核
go test ./bitemporal/ -run TestBatchLinearComplexity -v

go vet ./...
gofmt -l .
```

测试覆盖清单（对应题面逐条）：

- 两条轴记录与否的全部组合（`TestAxisPresenceCombinations`）；
- 边界不一致导致归属改变（域末闭区间、半开空区间）与不改变
  （普通闭/半开互转）两类情形（`TestBoundaryMembership`）；
- 两条轴各自的区间不自洽，以及其最高优先级（`TestRecordInvalid`）；
- 固定优先级（`TestPrecedenceOrder`）；
- 4000 组随机场景与按规则逐步独立实现的朴素参照模型
  （`naive_ref_test.go`）逐条对照，五类结论均实际出现，并记录每次判定的
  输入、输出与依据；
- 并发 64 goroutine × 100 次重复判定的完全一致性与记录不变性
  （`TestDeterminismAndConcurrency`）；
- 多跳路径与直迁一致性、先升后降/先降后升、损失不恢复
  （`TestPathEquivalence`）；
- O(n) 复杂度的加倍法实测（`TestBatchLinearComplexity`）。
