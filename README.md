# ontology-platform

本体服务平台（对标 Palantir Foundry Ontology）。

## 分布式资源冲突协调器（脏/净叉）

`dining` 包实现了 Chandy–Misra 脏/净叉协议，用在冲突图上协调相邻进程
对共享资源的独占访问。代码位于 `dining/`，可运行演示在
`cmd/dining-demo/`。

### 模型与初始定向

- 冲突图是无向图：顶点是进程，边表示两个进程竞争同一资源。
- **每条冲突边恰好一份**：一把叉（资源本身）与一枚请求令牌（叉
  要么被某端点持有，要么在消息中在途；令牌同理）。
- 初始时叉在**标识较小的一端且为脏**，令牌在另一端。
- 进程状态按 `思考(thinking) -> 饥饿(hungry) -> 进餐(eating)` 循环；
  只有持有某进程全部邻边叉时它才能进餐。

### 叉与令牌的收发规则

- **变饥饿**：饥饿进程对每把“缺少且自己持有令牌”的叉，把令牌作为
  请求（`Request` 消息）发给对方；令牌随请求进入在途。
- **收到请求**（令牌随消息到达接收方）：
  - 手中该叉为**脏**且自己**未在进餐**：把叉洗净后发出（`Fork` 消息，
    收到的叉恒为净），令牌留在自己手里；
  - 若自己**仍饥饿**：立即用手里这枚令牌再向对方请求该叉；
  - 叉为**净**，或自己**正在进餐**：暂存该请求（记录在持有者一侧）；
  - 叉在途时到达的请求：令牌留在接收端，等待净叉交付。
- **进餐结束**：手中所有叉变脏，并立即满足此前暂存的请求（洗净发出）。
- **消息网络**：`Network` 接口被注入（默认 `QueueNetwork`）。同一有向
  信道严格 FIFO（只能投递队首），不同信道之间的消息允许任意交错，
  由调用方决定何时 `Deliver` 哪条消息。

### 脏/净的作用：为什么不会死锁、饿死

- **脏**表示“持有者自上次使用以来还没有应请求让出过”。脏叉被请求时
  持有者必须立即洗净让出，且请求方从此对该资源拥有优先权；**净**叉则
  允许持有者先吃，请求被暂存到本次进餐结束。
- 由叉的位置与脏净导出边上的**优先关系**（箭头 `u -> v` 表示 `u` 优先
  于 `v`）：
  - 脏叉：`请求方 -> 持有者`（持有者必须让）；
  - 净叉被持有：`持有者 -> 请求方`（持有者先吃）；
  - 净叉在途：`接收端 -> 发送端`。
  初始时所有叉为脏且位于小端，所有箭头都按编号“大端 -> 小端”，初始
  优先图无环。协议只在脏叉应请求被洗净让出时把该边箭头反向，且这一
  反向发生在持有者自愿让出时——Chandy–Misra 证明该翻转序列不可能使
  全图成环，故**优先关系始终无环，系统不可能死锁**。
- **无饿死**：某进程的请求送达持有者后，若叉是脏的立即得到净叉；若
  叉是净的或对方正在进餐，请求被暂存，而持有者本次进餐一结束就必须
  洗净发出。因此“**该邻居在请求者进餐前至多再进餐一次**”，沿无环
  优先图归纳可知每个饥饿进程最终都能收齐叉并进餐。
- 相邻进程不可能同时进餐：它们共边的叉任意时刻只有一把，进餐要求
  持有全部邻边叉，故相邻两端不可能同时满足进餐条件。

`Coordinator.CheckInvariants()` 在任意快照上机器校验上述性质：
叉/令牌各恰好一份、相邻不同时进餐、优先图拓扑排序无环、暂存请求
与脏净规则一致。

### 拒绝语义（错误可区分、拒绝零副作用）

以下操作被整体拒绝并返回可区分的哨兵错误（`errors.Is` 可判定），
被拒绝的操作不改变任何进程、叉、令牌或网络队列：

- 建图：`ErrEndpointMissing`（端点不存在）、`ErrSelfLoop`（自环）、
  `ErrDuplicateEdge`（重复边，含反向重复）；
- 状态转移：`ErrNoSuchProcess`、`ErrNotHungry`、`ErrNotEating`、
  `ErrMissingFork`（思考或饥饿缺叉时进餐）、`ErrHungryToThink`
  （饥饿退回思考）、`ErrEatingToThink`、`ErrAlreadyThinking`、
  `ErrNotEating`（结束不在进餐中的进程）；
- 投递：信道空/消息不是队首/边或端点不匹配均为 `ErrNoSuchMessage`，
  端点不存在为 `ErrNoSuchProcess`，自环信道为 `ErrSelfLoop`。

### 并发、确定性与日志

- 所有状态转移与投递都在协调器互斥锁内原子完成，可被多 goroutine
  并发调用；锁序固定为 `Coordinator.mu -> QueueNetwork.mu`，网络不
  回调协调器，无死锁。
- 相同的操作与投递序列重放结果完全相同：邻边按规范化顺序遍历，
  `QueueNetwork.Pending()` 按有向信道键排序输出。
- 每次操作都通过 `Logger` 打印**输入、输出与判定依据**：`SliceLogger`
  收集到内存供断言/重放比对，`StdLogger` 输出可读文本。

### 本地验证

```bash
# 单元测试（初始定向、脏叉让出并立即再请求、净叉/进餐中暂存、
# 非法转移、不存在消息投递、拒绝零副作用）
go test ./dining -v

# 环形 5 进程与完全图 K4 各 1000 次随机交错，逐步校验全部不变量，
# 并检查“请求送达后邻居至多再进餐一次”与公平排空后无饿死；
# 另含相同操作/投递序列的重放确定性比对
go test ./dining -run 'TestRandomInterleaving|TestBoundedOvertake|TestReplay' -v

# 竞态检测（含 8 goroutine 并发调用状态转移与投递）
go test -race ./...

# 可运行演示：打印每条判定日志（输入/输出/判定依据）
go run ./cmd/dining-demo

# 代码检查
gofmt -l .
go vet ./...
```

## 环境要求

- Go 1.26+（`go version` 确认）

## 运行

```bash
# 拉取依赖
go mod tidy

# 直接运行
go run ./cmd/server

# 编译后运行
go build -o bin/server ./cmd/server
./bin/server
```

## 测试

```bash
# 全量测试
go test ./...

# 带竞态检测与详细输出
go test -race -v ./...

# 单个包 / 单个用例
go test ./ontology
go test -run TestObjectType ./ontology

# 覆盖率
go test -coverprofile=coverage.out ./...
go tool cover -html=coverage.out
```
