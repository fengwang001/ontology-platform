# ontology-platform

本体服务平台（对标 Palantir Foundry Ontology）。

## 环境要求

- Go 1.26+（`go version` 确认）

## 运行

```bash
# 拉取依赖
go mod tidy

# 直接运行
go run ./cmd/server

# 编译后运行
go build -o bin/server ./cmd/server
./bin/server
```

## 测试

```bash
# 全量测试
go test ./...

# 带竞态检测与详细输出
go test -race -v ./...

# 单个包 / 单个用例
go test ./ontology
go test -run TestObjectType ./ontology

# 覆盖率
go test -coverprofile=coverage.out ./...
go tool cover -html=coverage.out
```

## 代码检查

```bash
gofmt -l .
go vet ./...
```

## 锁管理器（`lockmgr`）：基于年龄的死锁预防

`lockmgr` 包实现 wound-wait 风格的死锁预防锁管理器，无需构造等待图。

### 伤害与排队规则

- 事务 `Begin` 时获得从 1 起连续递增的年龄号，号小者更老。
- `Acquire(txn, key)` 申请键的独占锁：
  - 键空闲 → 授予；
  - 持有者就是自己 → 视为已持有，不改变任何状态；
  - 持有者比申请者年轻 → **伤害（wound）**持有者：其全部锁立即释放、
    其在任何键上的排队请求一并撤销、状态变为已伤害，随后本键授予申请者；
  - 持有者比申请者老 → 申请者进入该键的等待队列。
- 任何锁被释放时（提交、中止或被伤害），队列中**年龄号最小**的等待者获锁，
  其余继续等待，获得者回到活跃。
- 已伤害事务只能 `Restart`：回到活跃、**年龄号不变**、不持有任何锁。
- `Commit` 要求事务活跃；`Abort` 在活跃、等待、已伤害时都允许，
  均释放全部锁与排队请求。
- 非法操作按固定顺序只报第一个原因（键为空 → 事务不存在 → 已提交或已中止 →
  已被伤害 → 正在等待；重启非已伤害事务报独立原因），被拒绝的操作不改变任何状态。

### 为什么不会出现等待环

等待边只会从**年轻**事务指向**年老**事务：老事务申请被年轻事务持有的键时，
直接伤害对方夺锁，绝不排队；只有年轻事务会等待老事务。沿任意等待路径，
事务年龄号严格递减，而年龄号有限，因此不可能回到起点构成环。
既然无环，就无需构造或检测等待图。

### 为什么重启要保持年龄号

被伤害的事务重启后若领取新年龄号，它会变成最年轻的事务，
可能反复被伤害而饥饿（活锁）。保持年龄号不变则保证：
比它老的事务数量有限且终会提交或中止，它终将成为系统中最老的事务，
此后任何申请者都比它年轻、只能排队等它，它不会再被伤害，
因此重试次数有界、终能完成。
