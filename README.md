# ontology-platform

本体服务平台（对标 Palantir Foundry Ontology）。

## 环境要求

- Go 1.26+（`go version` 确认）

## 运行

```bash
# 拉取依赖
go mod tidy

# 直接运行
go run ./cmd/server

# 编译后运行
go build -o bin/server ./cmd/server
./bin/server
```

## 测试

```bash
# 全量测试
go test ./...

# 带竞态检测与详细输出
go test -race -v ./...

# 单个包 / 单个用例
go test ./ontology
go test -run TestObjectType ./ontology

# 覆盖率
go test -coverprofile=coverage.out ./...
go tool cover -html=coverage.out
```

## 代码检查

```bash
gofmt -l .
go vet ./...
```

## 基于令牌环的分布式终止检测器

`termination` 包实现经典的 Dijkstra–Scholten 令牌环终止检测（环形拓扑、0 号为
发起者）。基本消息与探测令牌都经过可注入网络（`Network`/`MemoryNetwork`）异步
投递，允许任意延迟；`Send`、`Deliver`、`BecomeIdle`、`PassToken` 均为并发安全，
由检测器内部单一互斥锁串行化。

### 状态与规则

- 每个进程有状态（活跃/空闲）、颜色（白/黑）与计数器：发送一条消息计数 +1，
  接收一条计数 -1；只有活跃进程能发送；接收消息使进程转为活跃且变黑。
- 令牌带颜色与累计值。持有者空闲时才能把令牌从 `i` 传给 `i-1`（0 传给
  `n-1`）；活跃持有者、非持有者传递都被拒绝。
- 非发起者传出令牌前：累计值加上本进程计数器；本进程为黑则令牌变黑；随后
  本进程变白。
- 发起者空闲时负责发起新一轮：令牌置白、累计值为 0、自身变白。

### 为什么必须同时有“颜色”和“计数”

- 计数保证“没有在途消息”。全局恒等式 `Σ count[i] == 在途消息数` 在每次
  发送/投递后同步维护。令牌累计各非发起者的计数，加上发起者计数，回到 0 时
  恰好等于“本轮采样窗口内未被匹配的发送数”，据此可以排除仍在网络中延迟的
  消息。
- 颜色保证“不会有进程在令牌经过之后又变活跃”。计数和为 0 并不能覆盖这样的
  赛跑：一条消息在令牌经过其接收者之后才到达，发送的 +1 与接收的 -1 已经
  互相抵消（计数和为 0），但接收者被重新激活并变黑。接收即变黑、令牌经过时
  把黑色带上、发起者看到黑令牌就拒绝终止，正好堵住这个误报窗口。
- 二者缺一不可：只看颜色无法排除“消息还在网络上、尚未到达任何进程”的情形
  （此时没有任何进程变黑）；只看计数无法排除“令牌过后消息才到达”的赛跑。

### 宣告条件

令牌回到空闲发起者时，当且仅当以下条件同时成立才宣告终止并报告轮数：

1. 发起者空闲；
2. 发起者为白，且令牌为白（本轮令牌经过的每个进程在经过时都是白的）；
3. 令牌累计值 + 发起者计数器 == 0（本轮窗口内没有未匹配的发送，即无在途消息）。

否则发起者立即发起新一轮。宣告时必有：全部进程空闲、无在途消息、各计数之和为 0。

### “至多两轮”上界的理由

设系统从某一轮令牌在环上传递期间进入真正静止（无在途消息且全员空闲）。

- 静止之后不会再有新消息，因此任何进程都不会再变黑；静止后令牌尚未经过的
  进程会以白色放行令牌。
- 唯一的“黑”只可能来自静止之前、令牌经过某进程之后到达的消息：该黑色最多
  让当前这一轮失败一次。
- 下一轮发起时令牌重新置白、所有进程不再有机会变黑，且累计值 + 发起者计数
  必为 0（无在途消息），因此下一轮令牌回到发起者时一定宣告。

故真正终止之后、只要令牌持续被传递，其后发起的轮次中至多两轮（静止所在轮
与其后的一轮）必然宣告。

### 拒绝原因（相互可区分，被拒操作不改任何状态）

`ErrInvalidN`、`ErrProcessOutOfRange`、`ErrIdleSender`、`ErrSendToSelf`、
`ErrMessageNotFound`、`ErrNoToken`、`ErrActiveHolder`、`ErrAlreadyIdle`、
`ErrTerminated`，可用 `errors.Is` 判别。
