# ontology-platform

## 费用分账与净额清算设计
1. 模块边界：`domain.go` 放状态模型，`allocate.go` 只管逐日归属，`service.go` 管校验、锁、账本、清算和争议，`errors.go` 固化错误次序。
2. 日期统一用左闭右开整数区间；同房间占用也是区间判交，退出日可交接给下一住户。
3. 金额先拆到天：`floor(金额/天数)`，余数金额从覆盖区间最早日期逐日发放。
4. 同一天按人头时整除，余数按住户连续在住起点升序、再按房间序号升序逐个发放。
5. 按面积时先发放面积比例的向下整数额，剩余 1 元仍按同一确定性次序发放。
6. 当天无人在住时，找当天之后最早开始的房间占用段；同日取房间序号最小者，没有未来占用则归房东。
7. 换房用连续区间表达，换房日属于新区间；因此当天按新房面积，但人头分摊身份不变。
8. 净额只存规范化住户对 `(min,max)` 的一个整数，正负号表示方向；新增账单直接重算并自然支持方向反转。
9. 房东作为虚拟对手方参与当前净额守恒；查询接口只面向两名真实住户。
10. 选择“状态变更后全量重算当前净额”，放弃逐账单增量打补丁，避免争议、换房和退出叠加时出现重复计数。
11. 清算不直接截取当前净额，而从逐日份额重建“截至退出日、仅含真实住户对”的独立清算账本。
12. 初始清算保存每对住户基线；之后每张新增、争议或裁定账单只生成该账单对应的补充清算。
13. 争议期间账单从当前净额剔除；系统保留争议前份额快照，用负向边生成撤销补充。
14. 裁定后解除争议并按裁定金额重归属；已退出住户收到相对基线的补充，不修改原清算。
15. 争议只能一次，裁定只能一次，裁定金额不得高于原金额，争议窗口按录入时 `now` 起算。
16. 所有写操作由同一把互斥锁串行化；查询用读锁，因此并发结果等价于某个合法串行顺序。
17. `NetBetween` 只做一次 map 查找，不遍历账单或清算，平均 O(1) 且空间为 O(住户对)。
18. 被放弃方案：为每张账单维护应收/应付双向流水。它写路径更快，但清算截断和争议回滚需要额外投影，易破坏守恒。
19. 被放弃方案：退出后冻结身份。需求要求后补账单仍归属退出人，故保留区间和历史份额。
20. 错误严格按“参数、时钟、不存在、重叠、状态、金额”返回第一个错误；所有检查和状态变更均在锁内原子完成。

## 文件
- `domain.go` / `allocate.go`：住户区间、账单份额、逐日人头/面积/余数与无人日承接。
- `service.go`：入住、换房、退出、账单、争议、裁定、并发和查询。
- `errors.go`：错误码与错误类型。
- `service_test.go`：边界、守恒、拒绝次序、并发和 O(1) 基准。
- `naive_test.go`：独立朴素模型、随机序列和逐步判定日志。
