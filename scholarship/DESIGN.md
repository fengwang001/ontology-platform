# 奖学金评定引擎设计说明

## 模块划分（scholarship 包）
- `types.go` 数据模型、五类可区分错误（固定优先级）、配置校验（等级下限单调性等）。
- `eligibility.go` 单学生单等级资格判定：恰等于下限视为达到；处分解除时刻 ≤ 评定时刻视为已解除；多规则不满足按 处分>不及格>学分>平均成绩 报首条。
- `ranking.go` 三级排序键（平均成绩/学分/荣誉积分降序），三级全同才并列，同名次按人数跳号。
- `allocate.go` 等级→院系→并列组分配、边界并列组整组放弃并回流、机动池跨院系授予、已确认钉住。
- `engine.go` 变更操作（成绩更正/处分登记与解除）、确认、重评入口，单互斥锁串行化。

## 关键取舍
- 平均成绩作为输入直接给定，引擎不做加权计算；float64 精确比较使“恰等于”语义可复现。
- 重评 = 用当前数据从零计算 + 已确认钉住；不保存任何历史评定快照，故重评开销与历史次数无关，用 `Stats.StudentReads` 计数器在测试中验证（100 次重评后与首次读取量相同）。
- 资格判定只读单条学生记录（`CheckEligibility` 的 StudentReads 恒为 1），与总数无关。
- 已确认钉住：保留原等级，先占本院系名额、不足再占机动池，FromPool 按本次占用重算；确认者必出现在后续结果中，故“奖励不存在”与“已确认”不会同时成立。
- 机动池中放不下的并列组跳过并继续扫描后续组；院系内则停止并回流——不对称性直接来自规则原文。
- 并发：单互斥锁全串行化即等价于某串行顺序，未采用细粒度锁（复杂度高于收益）。

## 被放弃的方案
- 增量重评：难以证明与从零评定完全一致，违背可复现性优先级。
- 历史快照/事件溯源：使重评开销随历史增长，直接违背约束。
- 定点数成绩：输入即给定均值、无中间运算，精确比较已足够。

## 本地验证
- `go test ./scholarship/`：枚举用例（边界取等、解除时刻相等、三级并列、并列组填满/超一人、降级再并列、跨院系机动池并列、确认冲突、名次互换、拒绝优先级逐对）。
- `go test -race ./scholarship/`：并发等价串行。
- `go test -run TestRandomDifferential -v ./scholarship/`：40 组随机数据+操作序列与朴素模型逐步对照，日志含每步输入/输出/判定依据。
- `gofmt -l . && go vet ./...`。
