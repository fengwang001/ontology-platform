# 服务网格流量路由：设计说明

包路径：`ontology/servicemesh`（仅依赖 Go 标准库）。

## 1. 模块划分

| 文件 | 职责 |
| --- | --- |
| `types.go` | 对外数据模型：路径/头条件、规则、策略、配置、端点、请求、结果 |
| `errors.go` | 可区分错误类别（参数非法/版本冲突/校验失败/无路由/无可用端点）与校验子类（权重/策略/遮蔽）及最小规则序号 |
| `match.go` | 纯函数匹配语义：去查询串、段边界前缀、头三态匹配、路径覆盖、头蕴含、匹配项覆盖 |
| `policy.go` | 策略逐字段继承与生效策略校验 |
| `build.go` | 发布期三阶段流水线：结构校验 → 权重/策略/遮蔽校验（严格优先级）→ 索引编译；遮蔽判定 |
| `compile.go` | 不可变编译产物：路径段 trie、值前缀 trie、头倒排索引及请求期 `lookup` |
| `copy.go` | 发布入参与读取结果的双向深拷贝隔离 |
| `mesh.go` | `Mesh` 门面：原子发布（版本 CAS）、子集快照注册、请求分流、分桶、端点轮询 |

## 2. 关键语义与取舍

### 2.1 匹配

- 请求路径先在首个 `?` 处截断去除查询串；片段（`#`）按普通字符对待（本模块不解析 URI 片段）。
- 前缀是**段边界**前缀：`cond` 等于请求路径，或请求路径紧随其后以 `/` 开头。因此 `/a` 匹配 `/a`、`/a/b`，不匹配 `/ab`。
- 头名用 `strings.ToLower(TrimSpace(...))` 归一化（不区分大小写），值原样比较（区分大小写）。多值头的任一值满足条件即满足。
- 规则内多个匹配项为“或”，匹配项内路径与各头条件为“且”。规则严格按声明顺序取首个命中，匹配项按声明顺序作为并列依据。

### 2.2 分桶

`bucket ∈ [0,9999]`。按目标声明顺序，权重 `w` 恰好承接连续 `w*100` 个分桶值，零权重承接 0 个。实现为单次顺序累加区间判定；测试对全部 10000 个分桶做了全枚举（`z=0/a=3000/b=7000`）。

### 2.3 子集与端点

子集注册是整份原子快照替换；快照内就绪端点稳定地排在前部，选中子集后以原子计数在就绪端点间轮询。子集未登记或就绪数为 0 → 无可用端点，**不改道、不改状态**：轮询计数仅在确有就绪端点时自增。

### 2.4 策略继承

三个字段均为指针（`*time.Duration`/`*int`），nil 即“缺省”，因此重试次数 `0` 是合法值。生效策略逐字段“规则覆盖 → 服务默认 → 未设置”。

校验只作用于**生效策略**：
- `PerAttemptTimeout <= Timeout`（两者皆设置时）；
- `MaxRetries * PerAttemptTimeout <= Timeout`（三者皆设置时）。

兜底目标使用服务默认策略，因此“存在兜底目标”时默认策略必须自洽；没有兜底且没有任何规则继承某默认字段时，该默认字段不会作用于请求，不做生效校验。

### 2.5 发布校验顺序（错误优先级）

1. **参数非法**：nil 配置、规则无匹配项/无目标、路径形态非法（不以 `/` 开头、空段、非根尾斜杠）、空头名、非法头操作符、负超时/负重试等结构问题。
2. **版本冲突**：编译校验全部通过后，在互斥区内比较 `baseVersion` 与当前版本。
3. **校验失败**，同一份配置多问题并存时只报第一类、同类报规则序号最小者：
   1. 分权重类：子集名空、权重越界、和不等于 100（规则按序号，兜底记 -1 且排在规则之后）；
   2. 策略类：所有规则生效策略先于兜底默认策略；
   3. 遮蔽类：规则 `r` 的**每一个**匹配项都被其**前面某一条**规则的**某一个**匹配项完全覆盖。
4. 运行期：无路由 < 无可用端点。

覆盖（蕴含）判定：
- 路径：精确只覆盖相同精确；前缀覆盖以其为段边界前缀的精确/前缀。
- 头：前者（遮蔽方）的**每个**头条件都必须被后者（被遮蔽方）的**某个同名**头条件蕴含——
  精确蕴含同值精确、以其开头的前缀、存在；前缀蕴含更短/等长前缀与存在；存在只蕴含同名存在。

注意蕴含方向是“前者更严格”：若请求满足前者的精确条件，则必满足后者更宽松的条件，于是后者匹配的请求集合包含前者。

### 2.6 原子性、不可变性与并发

- 编译与校验在当前状态之外完成；只有全部通过后才在互斥区内做版本比较与一次 `atomic.Pointer.Store`。任何失败路径都不触碰当前配置与版本。
- 每次请求对服务状态做**一次**原子读，拿到整份不可变快照，执行期间不受并发发布影响 → 不可能观察到“发布到一半”。
- 服务表本身用 copy-on-write 的 `atomic.Pointer[map[...]]`：新增服务时复制整张表再原子替换，路由读路径因此**永不持锁**；互斥锁只用于服务增删与版本判定。
- 发布时深拷贝入参，`GetConfig` 与 `Route` 返回的策略也都是深拷贝，调用方持有引用无法修改内部状态（有专门测试篡改入参与返回值）。
- 可串行化：并发发布同一基版本时恰一个成功、其余版本冲突，版本严格单调加一；并发路由只可能观察到发布前或发布后整份配置之一。

## 3. 性能设计（为何不随无关规则/端点数线性增长）

朴素做法对每个请求线性扫描全部规则。本实现把匹配预算挪到**发布期**构建两级索引：

1. **路径段 trie**：路径按 `/` 切段，请求沿 trie 下行，只访问根到终止节点这 `d+1` 个节点（`d` 为路径段数）。前缀匹配项挂在途经节点，精确匹配项只挂在终止节点——因此 `/ab` 绝不会触及 `/a` 节点上的精确项。
2. **头条件倒排**（每个 trie 节点内，前缀路径与精确路径各一套）：
   - 精确值：`头名 -> 值 -> matcherIDs`；
   - 值前缀：`头名 -> 按字节的值前缀 trie`，沿请求值下行枚举所有“条件值是请求值前缀”的条目；
   - 存在：`头名 -> matcherIDs`。

   每个匹配项从其全部头条件中选一个**驱动条件**（精确 < 前缀 < 存在，扇出最小优先）进入倒排，其余头条件在候选上直接校验。请求只对“自己实际携带的头名”做倒排枚举。

由此，一次请求评估的候选只来自其路径前缀链上的 trie 节点、以及与请求头相关的倒排桶；与请求路径、头都不相关的规则**永远不会被触及**。开销为
`O(路径段数 + 相关匹配项数 × 剩余头条件数)`，与服务内规则总数、端点总数无关。端点选取为 O(1)（就绪端点连续存储 + 原子计数取模）。

“相关匹配项”仍可能多（例如大量同路径同头的规则），但它们与该请求确实相关，且首个命中后即停止——这是规则顺序语义决定的必要工作量。

### 可验证证据

- `TestComplexityIndependentOfUnrelatedRules`：1k/5k/20k 条无关规则下，探针统计的“实际枚举候选数”恒为 1。
- `TestLatencyDoesNotGrowWithRulesOrEndpoints`：规则与端点同时扩大 20 倍，单请求平均耗时比值 ≈ 0.9（阈值 4）。
- 基准（本机，20001 条规则）：
  - 索引实现 `BenchmarkRouteUnrelatedRules` ≈ **755 ns/op**；
  - 朴素扫描 `BenchmarkRouteNaiveScan` ≈ **95 µs/op**（约 126 倍差距，随规则数扩大）。

## 4. 被放弃的方案

- **请求期线性扫描**：实现最简单、与规则顺序天然吻合，但单请求开销随规则总数线性增长，直接违反性能要求。仅保留为测试中的朴素参考模型。
- **全量正则/单一前缀树混合路径**：难以同时表达精确与段边界前缀，且容易在中间节点误召回（开发中实际出现过“精确项在中间节点被收集”的缺陷，已用“精确项只在终止节点评估 + 前缀/精确双套头索引”修复并由测试回归）。
- **对规则文本做预计算的“非黑即白可达性”静态分析**：遮蔽判定本就是发布期 O(n²) 的匹配项覆盖问题，n 为规则数，属于发布开销；请求期不需要这类分析。
- **更激进的头条件复合索引（多条件合取的位图交并）**：能进一步压缩多条件场景的候选，但复杂度高、位图随规则数分配反而引入与规则总数相关的请求成本；当前单驱动倒排已满足“不随无关规则数增长”，故不采用。
- **RWMutex 包裹配置**：读路径仍需锁开销且易出现读半更新状态；改为不可变快照 + 原子指针，读完全无锁。

## 5. 本地验证方法

需要 Go 1.26+。若默认构建缓存只读，可指定临时缓存：

```bash
export GOCACHE=/tmp/gocache GOPATH=/tmp/gopath

go fmt ./...
go vet ./...

# 全量测试（带每次操作输入/输出/判定依据日志）
go test -v ./servicemesh

# 竞态 + 并发可串行化
go test -race ./servicemesh

# 只看复杂度证据与基准
go test ./servicemesh -run 'TestComplexity|TestLatency' -v
go test -bench=. -benchmem -run=^$ ./servicemesh

# 关闭详细操作日志
SM_LOG=0 go test ./servicemesh
```

## 6. 使用示例

```go
m := servicemesh.NewMesh()

to := 500 * time.Millisecond
cfg := &servicemesh.ServiceConfig{
    Default: servicemesh.Policy{Timeout: &to},
    Rules: []servicemesh.Rule{{
        Matches: []servicemesh.MatchItem{{
            Path:    servicemesh.PathMatch{Kind: servicemesh.PathPrefix, Path: "/api/v1"},
            Headers: []servicemesh.HeaderMatch{{Name: "x-env", Op: servicemesh.HeaderExact, Value: "prod"}},
        }},
        Targets: []servicemesh.Target{{Subset: "canary", Weight: 10}, {Subset: "stable", Weight: 90}},
    }},
    Fallbacks: []servicemesh.Target{{Subset: "stable", Weight: 100}},
}
ver, err := m.Publish("orders", cfg, 0) // 首次发布基版本 0，成功返回 1
m.RegisterSubsets("orders", map[string][]servicemesh.Endpoint{
    "canary": {{Name: "10.0.0.1:8080", Ready: true}},
    "stable": {{Name: "10.0.0.2:8080", Ready: true}},
})
res, rerr := m.Route("orders", servicemesh.Request{
    Path:         "/api/v1/orders/42?ref=email",
    HeaderValues: map[string][]string{"x-env": {"prod"}},
    Bucket:       500, // [0,999] canary，[1000,9999] stable
})
```
