# 骑手顺路合并派单 — 设计说明

1. 模块切分：`domain.go`（订单/骑手/停靠/耗时源/状态）、`schedule.go`（到达与离开推定）、
   `feasibility.go`（插入位置枚举、可行性与两级选择）、`dispatcher.go`（生命周期、时钟、区域索引与并发）、
   `naive.go`（独立穷举对照模型）。
2. 时刻全部为整数秒，由协调器维护单调时钟；拒绝次序固定为参数非法→时钟回退→对象不存在/状态不符→无可行骑手。
3. 推定规则：到达=前一停靠离开+边耗时；取货离开=`max(到达, 就绪)+停留`，送达离开=到达+停留。
   完成停靠时报告时刻成为实际离开（仍受“不早于到达/就绪”约束），锚点前移，次序永不改变。
4. 耗时源只可查询，不假设三角不等式；边缺失（`ok=false`）即视为经过该边的插入不可行。
5. 区域与耗时拓扑解耦：取货点经可注入的 `Config.RegionOf` 映射到商家服务区域；缺省取点自身为区域。
6. 枚举全部 `(pi,di)` 且 `pi<di` 的插入；可行性同时检查新单承诺、每个在途订单承诺与单次绕路上限、容量、同区。
7. 选择分两级且均为全序：骑手内按（在途总延后, 新单到达, pi, di）；骑手间按（总耗时增量, 持有数, ID 字典序）。
   朴素模型曾错误地把两级扁平混排，已在差分测试中暴露并修正为“先骑手内选最优再骑手间比较”。
8. 总耗时增量口径：`末停靠离开 - 骑手出发时刻` 的插入前后之差，空序列定义为 0。
9. 三种无可行原因按优先级仅返回一种：同区全满→无位置满足新单承诺→满足新单但在途超承诺/超绕路。
10. 取消采用“先重算后验证”：任何保留送达到达变晚即整体拒绝并返回 `ErrCancelWouldDelay`，不做部分变更。
11. 并发用单一互斥锁把判定与变更原子化，等价于某一串行全序；容量检查与序列写入同临界区，杜绝超卖与一单多属。
12. 被放弃方案：乐观锁/版本号（语义上仍需回滚串行化，复杂度更高）；按送达点区域匹配（题意为取货商家区域）；
    增量式 ETA 传播（在边不满足三角不等式时正确性更难论证，当前 O(n²) 位置 × O(n) 推定已足够且可复现）。
13. 性能：单骑手判定只遍历其 `Pending`（已完成停靠立即出列），与历史长度/平台总量无关；
    候选骑手经 `region→set` 索引收集，与其他区域骑手数无关。两处均由计数型耗时源在测试中断言。
14. 正确性交叉验证：`naive.go` 不共享选择/索引代码，仅共用类型与推定规则；
    随机差分测试逐字段比对每步结果、错误种类、骑手/位置/时刻及终态，并打印每步输入、输出与判定依据。
15. 本地验证：`GOCACHE=/tmp/gocache go test -race -v ./dispatch/`、`go vet ./...`、`gofmt -l dispatch`。
