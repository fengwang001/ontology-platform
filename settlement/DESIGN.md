# 证券交割日终批处理系统 — 设计说明

## 1. 模块划分

| 文件 | 职责 |
| --- | --- |
| `system.go` | 系统骨架：配置校验、账户存储、营业日索引、并发互斥 |
| `order.go` | 指令输入 `Order`、状态枚举、查询视图等纯类型 |
| `register.go` | 指令登记：参数/重复/账户/日期校验与候选结构插入 |
| `batch.go` | 日终批处理：候选合并、占用判定、DvP 提交、罚金、强制了结 |
| `query.go` | 账户/指令只读查询（深拷贝，不改状态） |
| `report.go` | `BatchReport`/`OrderDecision` 判定明细，供可复现日志 |
| `errors.go` | 六个可 `errors.Is` 区分的哨兵错误 |
| `naive/naive.go` | 按需求文字逐行重写的独立朴素模型（差分测试用，不共享任何代码） |

## 2. 关键规则与取舍

### 2.1 批处理次序

错误优先级固定为 **参数非法 > 非营业日 > 次序错误**。
次序定义：第一次批处理必须是营业日集合的第一天；之后每次必须是“上一批处理日
在排序后营业日数组中的下一个元素”。因此跳过、重复、倒退、在最后一个营业日
之后继续调用，都报 `ErrOrdering`。

### 2.2 当日判定与批内占用

- 批处理开始时冻结头寸快照；判定期间**只累计占用（`usedSec`/`usedCash`），
  不回写头寸**，因此早先指令收到的券与现金当日不可用（“T+1 可用”）。
- 可交割量 = min(未交割量, 卖方可用券, 买方现金/单价)；
  不允许部分时，不足额即交 0。
- 全部判定完成后，在同一临界区内一次性提交所有交割腿（先校验后提交），
  券与现金同时变动，物理上不可能只发生一边。

### 2.3 责任方

以**判定后**仍未交割量与卖方可用券比较：`sellerAvail < remaining` 即卖方，
否则买方。两边都不足时因此归卖方。罚金按该剩余量对应原现金额独立按日计算：
`ceil(cashAmount * bps / 10000)`。罚金与补偿都只写应付/应收，不改变现金。

### 2.4 强制了结与补偿

累计失败营业日数在罚金计入后立即与 B 比较，达到即取消（`StatusForceClosed`），
当日状态不再滚动。仅当当日责任方为卖方时记补偿：
`max(0, refPrice*remaining - price*remaining)`，负取零。责任方可逐日不同，
因此买方责任导致强平时没有补偿（买方已在当日为其责任付罚金）。

### 2.5 登记时序

登记错误优先级：**参数非法 > 编号重复 > 账户不存在 > 日期已过**。
需求只禁止“应交割日早于最近批处理日”，所以应交割日 **等于** 最近批处理日
的指令仍允许登记，并立即进入滚动集合 `overdue`，在下一营业日首次判定。
所有被拒操作在校验阶段返回，不触碰任何可变状态。

### 2.6 并发与确定性

所有公开方法用同一把 `sync.Mutex` 串行化（查询返回深拷贝），
因此并发结果等价于某一合法串行交错；状态转移只依赖操作参数，
不含时间、随机或 goroutine 调度因素，同序列重放结果逐字节相同。

### 2.7 单日复杂度（可验证证明）

未了结指令只存在于两个结构中：

- `byDay[d]`：应交割日为 `d` 的有序桶；
- `overdue`：此前失败、仍在滚动的有序指令。

单日批处理把 `overdue` 与 `byDay[day]` 做一次有序合并（各自按编号升序，
归并 O(n)），完成后 `delete(byDay, day)`，已完成/已强平的指令**不再保留在
任何候选结构中**（仍保留在 `orders` 仅供查询）。因此：

> 当日工作量 = O(当日候选指令数)，与历史已了结指令总数无关。

实证：`go test -bench=BenchmarkDayCost`。本机结果（300 次均值）：

```
closed=1000/open=50    9494 ns/op
closed=1000/open=200  33937 ns/op
closed=10000/open=50  12078 ns/op
closed=10000/open=200 33622 ns/op
```

历史已了结量扩大 10 倍，单日耗时基本不变；当日候选扩大 4 倍，耗时约 3.6 倍。

## 3. 被放弃的方案

1. **扫描全部指令**：朴素模型即如此（O(历史总数)/日），实现简单但直接违反
   “单日开销只与当日待处理指令数相关”，只保留在 `naive` 包做对照。
2. **判定时即时回写头寸**：会让批内早先交割收到的券/现金当日即可用，
   违反“次日才可使用”；改为快照 + 占用累加 + 末尾统一提交。
3. **用全局优先队列/堆**：登记与滚动都要改键，且与“按编号升序”的要求
   不自然；改为两个有序切片归并，登记插入 O(当日桶大小)，
   对日终批场景（登记并发量分散在各日）足够且行为直观。
4. **罚金/补偿立即改动现金**：需求明确“不改变现金头寸”，因此只入
   `feePay/feeRecv/compPay/compRecv` 四个科目，查询独立可见。

## 4. 本地验证方法

```bash
# 单元 + 2000 条随机差分序列（-v 可看到每个场景的输入/输出/判定依据日志）
go test -v ./settlement

# 竞态检测
go test -race ./settlement/...

# 复杂度实证
go test -run=NONE -bench=BenchmarkDayCost -benchtime=300x ./settlement

go vet ./... && gofmt -l .
```

`TestRandomDifferential` 同时驱动引擎与 `naive` 模型：每步登记/批处理后
逐账户（券、现金、四类应付应收）与逐指令（已交割量、失败日数、状态）全量比对，
错误类别按优先级语义比对。随机用例刻意混入非法参数、不存在账户、重复编号、
非营业日、跳日等，被拒操作同样验证双方均不留痕。
