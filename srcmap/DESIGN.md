# 源码映射合成与反查服务 — 设计说明

## 1. 模块划分

代码位于 `srcmap/` 包，四个职责相互独立的文件：

| 文件 | 职责 |
| --- | --- |
| `srcmap.go` | 核心数据类型（`Segment/Line/Mapping/LookupResult`）、`New`、`Lookup` |
| `validate.go` | 输入校验、唯一规范形式（canonical form）、行/段查找索引 |
| `compose.go` | M2∘M1 合成算法（扫描 + 边界切分） |
| `service.go` | 以名字管理映射、错误优先级、并发线性化 |
| `errors.go` | 四类可区分错误（`ErrorCategory`） |

对外入口：`cmd/server`（HTTP）与包级 API（`srcmap.New/Compose`、`Service.Register/Compose/Query`）。

## 2. 数据模型

- 生成位置与原始位置的坐标域均为闭区间 `[0, 10^9]`。
- 一行内段按生成列**严格递增**。每个映射段覆盖
  `[start, nextStart)`；行内最后一个段向右无限延伸（“直到行尾”）。
  这是标准 source-map 语义：末段的无限延伸是数学模型本身，不存储终点。
- 未映射段是显式的：它占据一段生成列区间，表示“这一段刻意不映射”，
  与“行首之前没有任何信息”区分开。
- 映射段内原始列以斜率 +1 增长：`origCol = seg.origCol + (queryCol - seg.start)`。
  这是查询与合成中“段内偏移”的唯一计算规则。

## 3. 点查询

对 `(line, col)`：

1. 位置越界（坐标不在 `[0,1e9]`）→ 参数非法。
2. 二分定位生成行（`sort.Search`），行不存在 → 未映射，**不跨行回溯**。
3. 二分取“起点 ≤ col 的最后一段”；`j < 0` 或命中未映射段 → 未映射。
4. 否则按斜率计算原始列；结果 `> 1e9` → **位置溢出**。

复杂度：行定位 `O(log R)`，段定位 `O(log S_line)`，与该映射的**总段数**
无关（只与被查行的段数有关），与坐标数值大小无关。
`BenchmarkLookupSublinear` 在 100k 段行上稳定约 5 ns/op，可作为可验证证据。

## 4. 合成算法

记号：M2 = 最终→中间（单源），M1 = 中间→原始。逐步语义是
`Lookup_M1(Lookup_M2(line, col))`，任一步未映射则整体未映射。

直接对每个最终列逐步查询是 `O(1e9)`，不可接受；对“M2 每段 × M1 每段”
枚举则是乘积。本算法：

```
for 每个 M2 行:
  for 该行每个 M2 段 seg2, 覆盖最终列 [start, limit)，limit=下一段起点（末段为 1e9+1）:
    若 seg2 未映射: 输出一个未映射段
    否则:
      j = 二分定位 seg2 的中间入口列在 M1 行中命中的段
      c = seg2.start
      while c < limit:
        中间列 mid = seg2.origCol + (c - seg2.start)
        end  = min(limit, 下一个 M1 段起点对应的最终列)
        按当前 M1[j] 产出映射/未映射输出段，起点为 c
        c = end; 仅当确实跨越了 M1 边界时 j 才前进（j 只进不退）
  对本行输出做规范化
```

关键点：

- **只在真正被跨越的 M1 边界处切开**。M1 段指针 `j` 在每个 M2 段内
  单调前进，从不回扫，因此每个 M1 边界在整条最终行上最多被访问一次
  （外加一次二分定位入口）。
- `end` 用 M2 下一段起点封顶，**中间段绝不会越过 M2 本行下一段起点**；
  M2 的下一段对应另一个中间位置，由外层循环处理。
- M2 未映射段、M1 行缺失、命中 M1 未映射段，都输出显式未映射段，
  交给规范化决定保留/省略/合并。
- M2 作为“最终→中间”必须 `sourceCount==1` 且映射段源索引为 0；
  合成结果的源列表完全取自 M1，M2 的源索引 0 不进入结果。

### 复杂度（可证明）

对一条最终行，设 M2 段数为 `p`、M1 被跨越的边界数为 `k`、输出段数为 `q`：

- 每个 M2 段一次二分：`O(p log S_M1)`；
- 内层循环总迭代次数 = `p + k + 1`（每段至少一次，每次跨边界加一次）；
- 每个 M1 边界只被消费一次，`k ≤ q`。

故单条最终行为 `O(p log S + q)`；全局为
`O(|M2|·log S_M1 + |输出|)`，**不含 `|M1|·|M2|` 乘积项，也不含坐标
数值项**（不枚举列号、不按行号开数组，行号稀疏地存于有序切片）。
`BenchmarkComposeLinear`：规模 ×4 时时间约 ×3（0.51ms→1.57ms），
线性而非平方（平方应约 ×16），是可复现的经验证据。

## 5. 唯一规范形式

对每行按段顺序左到右归约，三条规则：

1. **行首未映射段省略**——它不提供任何信息（查询落在段前本就未映射）。
2. **相邻未映射段只保留第一个**——中间的分界不改变查询结果。
3. 后一段是前一段的“延伸”时丢弃：同源、同原始行，且
   `prev.origCol + (seg.start - prev.start) == seg.origCol`。

没有任何段的行整体省略。这三条规则是查询函数的精确等价格林化：
逐点查询函数完全由“每个生成列返回什么”决定，而任何不改变该函数的
段分界都会被规则 2/3 消除，任何行首未映射都会被规则 1 消除。
归约从左到右确定性执行，因此**含义相同的映射规范形式逐字相同**——
登记与合成都经同一 `canonicalize`，`TestCanonicalEquivalence` 与
300 组随机等价构造对照均验证了这一点。

## 6. 位置溢出的取舍

规格要求合成时“任一结果原始列超过 1e9 报位置溢出”。难点在于末段
无限延伸：无法对无穷区间逐点检查。采用的判据是：

- 每个输出映射段在其**起点**检查（溢出若在段内首次发生，其前一个
  输出段或同一 M1 段的起点必已合法，真正的越界起点必是某个新切开的
  输出段起点）；
- 同时对该输出段在**可表示域内的最远点** `min(end-1, 1e9)` 检查，
  从而捕捉“段起点恰好顶格、下一可查列即溢出”的情形。

因此末段不会仅仅因为“向无穷延伸”而被误判——只有 `[0,1e9]` 内确实
存在越界原始列时才报错。点查询在返回前也做同一上界检查，使合成后
的映射不会在查询时才暴露溢出。

## 7. 错误类别与优先级

四类错误（`errors.go`，可用 `srcmap.CategoryOf(err)` 判别）：

| 类别 | 触发 |
| --- | --- |
| `invalid_argument` | 数值越界、行/列未严格递增、源索引越界、M2 非单源/源索引非 0、查询位置越界 |
| `name_not_found` | 合成/查询引用未登记名字 |
| `duplicate_name` | 登记重名、合成结果名已占用 |
| `position_overflow` | 合成或查询得到的原始列 > 1e9 |

优先级固定为：**参数非法 > 未找到 > 重复名字 > 位置溢出**。
实现顺序：登记先锁外完成全部参数校验（失败不触碰状态）；合成在读锁
快照内判定未找到/结果名占用，再做 M2 单源校验（参数非法），最后
`compose` 才可能报位置溢出；提交时持写锁复查结果名，杜绝竞态。
被拒绝的登记/合成都不改变任何状态（合成成功前不写表）。

## 8. 并发与线性化

`Service` 用一把 `sync.RWMutex` 保护 `map[string]*Mapping`：

- 合成开始时在**同一次读锁临界区**里同时取出 M1、M2 两个不可变映射
  并检查结果名，保证它看到的是操作开始时刻的一个一致快照，不会
  “读到一半状态”；
- 计算在锁外进行（不放大临界区），提交时加写锁复查结果名后写入；
- 已登记映射构造后不再修改（`New` 拷贝输入并冻结），读者无需对其加锁。

由此所有已接受操作都等价于按某个全序串行执行（读快照→计算→写锁
提交是标准“先读后写、提交时复检”的线性化模式）。`TestErrorsAndService`
中 16 个 goroutine 并发登记/合成/查询，`go test -race` 无告警。

## 9. 被放弃的方案

- **按最终列逐列逐步查询**：语义最直白，但 `O(坐标上界)`，无法满足
  “不随行列号数值增长”；仅保留为测试里的朴素模型（密网格暴力枚举）。
- **M2 段 × M1 段笛卡尔枚举**：实现简单但最坏 `O(p·q)`，被明确禁止；
  现方案用“只进不退的边界指针”降到输出敏感的线性。
- **区间树/线段树做行内查找**：段天然有序且静态，有序切片 + 二分更
  简单、缓存友好；动态结构（如平衡树）对不可变映射没有收益。
- **用 JSON 字符串表示段、运行时解析**：类型不安全且慢；改为强类型
  `Segment`，HTTP 层只做一次 JSON 编解码。
- **给段存储显式终点**：会让“末段到行尾”的无限语义需要哨兵值，且
  相邻段终点/起点冗余；最终采用“起点 + 末段无限”的经典模型。

## 10. 本地验证方法

```bash
export PATH=$PATH:/usr/local/go/bin
export GOCACHE=/tmp/gocache   # 本机默认缓存目录只读时需要

go test -v ./srcmap                       # 全量场景 + 随机对照（打印输入/输出/判定）
go test -race ./...                       # 竞态检测（含 HTTP 端到端）
go test -run xxx -bench . ./srcmap        # 亚线性查询 / 线性合成基准
go vet ./... && gofmt -l .                # 静态检查与格式
go run ./cmd/server                       # 启动 HTTP 服务（ADDR 可改端口）
```

测试覆盖清单（`scenarios_test.go` / `random_test.go`）：

- 段内偏移在 M1 边界处切开；末段无限延伸时的多次切开；
- M2 中间段不越过下一段起点；M1 未映射段产生显式未映射；
- 取等命中、行首未映射省略、相邻可延伸段合并、空行省略；
- 规范形式对不同构造的等价映射逐字一致；
- 多张映射连续合成的结合性（50 组随机三映射）；
- 300 组随机映射与逐列朴素模型（0..24 密网格）完全一致；
- 错误类别、优先级、重名/缺名、M2 单源约束、位置溢出、16 goroutine 并发。

所有测试日志均通过 `fmt.Printf`/`t.Logf` 打印每次输入、输出与判定依据
（`go test -v` 可见）。
