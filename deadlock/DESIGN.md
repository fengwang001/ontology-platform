# 多实例资源分配：死锁检测与最小代价消解

包 `deadlock` 实现多实例（每类资源可有多个实例）系统中的“备选请求”分配、
图归约死锁检测和按代价逐个回滚牺牲者的死锁消解。所有公开方法都可被并发
调用：内部用一把互斥锁把每个方法（`Resolve` 连同整个多步消解过程）线性化，
对外等价于某个串行顺序，观察者看不到只中止一部分牺牲者的中间状态。

## 状态

- `avail[r]`：每类当前可用实例数，初值 `T[r]`。
- `alloc[p][r]`：进程 `p` 持有数，初值 0。
- `rb[p]`：进程已被回滚次数，初值 0；存活进程恒有 `rb[p] < L`。
- `alive[p]`：是否存活；`rb[p]` 加到 `L` 后永久中止，`alive=false`。
- `blocked[p]` 与 `alts[p]`：是否阻塞及其 1~3 个备选向量，每个进程至多一个。
- `bseq[p]`：阻塞序号；全局计数器 `nextBSeq` 初值 0，**仅真正发生阻塞时**
  加一并赋给该进程，授予与被拒绝的操作都不耗序号；序号不回收。

不变量（任何操作返回后成立）：

- 守恒：`avail[r] + Σ alive(p) alloc[p][r] = T[r]`，`avail[r] ≥ 0`。
- 授予不动点：不存在“某个备选 ≤ avail”的阻塞进程，即阻塞一定因为放不下。

## Request：先到先授予 + 备选“任选其一”

`Request(p, alts)` 中 `alts` 是 1~3 个长度为 R、非负、非全零的向量。

- 按**列出顺序**找第一个对所有 r 满足 `alt[r] ≤ avail[r]` 的备选（first fit，
  不是“最合适”），授予它：`avail -= alt`、`alloc[p] += alt`，返回
  `Granted{AltIndex}`。备选全放不下时**不做任何部分授予**，进程进入阻塞并
  登记整组备选与新的 `bseq`。
- 永不可满足校验：考虑进程已持有量，只有当**每个**备选都存在某 r 使
  `alloc[p][r] + alt[r] > T[r]` 时才整体拒绝（`ErrRequestImpossible`）。
  备选语义是“任选其一”，单个超大的备选只会永远不被选中；这与题面示例一致——
  示例中进程 1 已持有全部资源 1（`[0,2]`，T₁=2），仍能带着第二备选 `[0,1]`
  （会超出 T）的备选组阻塞，因为其第一备选 `[1,0]` 仍可行。
- 错误只报第一个，Request 顺序：参数非法 → 进程不存在（越界或已永久中止）→
  进程已阻塞 → 永不可满足。被拒绝操作不改变任何状态，也不耗 `bseq`。

## Release 与授予不动点

`Release(p, vec)`：vec 非全零、非负、长度 R、逐类不超过 `alloc[p]`；先
`alloc -= vec`、`avail += vec`，然后做授予不动点：

> 在全部阻塞进程中选 **bseq 最小且当前存在可满足备选** 的进程（先到优先，
> 但队首要能被满足，不是严格 FIFO），授予其**第一个**可满足备选并解除阻塞，
> 重复直到没有可授予者。

因此后到的小请求可以在 Release 后越过先阻塞的大请求；一次授予改变 avail
后可能连锁解锁更后的进程，一次 Release 返回按授予先后排列的
`(进程, 备选下标)` 列表。`Resolve` 每步回滚后执行同一个不动点。

## Detect：图归约与净增量推导

`Detect()` 不改状态，用银行家式图归约：

1. `Work = avail`；每个**未阻塞**的存活进程（无论是否持有资源）都被视为
   “总会结束并释放全部持有量”，故把其 `alloc` 全部加入 `Work`。
2. `Finish = ∅`。反复按进程编号升序扫描尚未 Finish 的阻塞进程：若其任一备选
   `alt ≤ Work`，则它可以取得该备选后结束；加入 Finish。
3. 结束时不在 Finish 的阻塞进程（编号升序）即死锁集合。

**净增量为什么是 `alloc` 而不是 `alloc+alt`**：该进程取得备选 alt 时先从
Work 中“消耗” alt，随后进程结束把“取得的 alt 与原先持有的 alloc”一并归还，
一进一出抵消 alt，净增恰好是 `alloc[p]`。

`checks`（非导出计数器，经 `Checks()` 读取最近一次 Detect 的值）记录一次
Detect 中“检查阻塞进程能否被满足”的次数。设阻塞进程数为 b：每次成功归约后
只需重新扫描，第 k 趟至多检查 b−k+1 个未完成进程，总计不超过
b(b+1)/2，证明算法不是在枚举完成顺序。单趟升序扫描足以收敛，因为 Work 单调
不减、可行性条件关于 Work 单调。

## Resolve：最小代价牺牲者

`Resolve()` 原子地反复：

1. 计算死锁集合；为空则结束。
2. 在死锁集合中**持有量总和大于 0** 的进程里选代价最小者（持 0 的死锁成员
   如纯等待者不参与选择）：

   `cost(p) = Σ_r alloc[p][r]·c[r] · (1 + rb[p])`

   回滚次数越多越贵（翻倍计权）；代价并列取编号小者。
3. 回滚牺牲者：`alloc[p]` 全部并入 `avail`，阻塞请求取消（不阻塞、持有 0、
   bseq 不回收），`rb[p]++`；若 `rb[p] == L` 则永久中止（不再存在，后续对它
   的操作报 `ErrProcessNotFound`），否则仍存活、可再次 `Request`。
4. 执行一次授予不动点，记录该步连锁授予列表。

非空死锁集合中必有持资源者：操作结束时授予不动点保证任何阻塞进程都放不下
当前 avail；若死锁成员无人持有资源，则被阻塞的资源只能由非阻塞持有者或
Finish 集合中的进程提供，那些进程本就可归约，矛盾。

返回每步 `(牺牲者, 代价, 该步授予列表, 是否永久中止)`。`Resolve` 返回后
`Detect` 必为空。

Release 的错误顺序：参数非法 → 进程不存在 → 进程已阻塞 → 归还超过持有。

## 本地验证

```bash
# 全量测试（含 2000 组随机序列对照、最坏链 checks 上界、并发）
go test ./...

# 竞态检测
go test -race ./...

# 打印随机对照日志：输入、输出，以及“枚举完成顺序”朴素 oracle 的判定依据
go test -run TestRandomDifferential -v ./deadlock

# 只跑规格示例 / checks 最坏输入
go test -run 'TestSpecExample|TestChecksWorstChain' -v ./deadlock

go vet ./...
gofmt -l .
```

随机对照（`differential_test.go` 中的 `naiveState`）独立实现一个朴素判定器：
对阻塞进程的所有完成顺序做 DFS（按子集枚举所有可行前缀），出现在任一可行
前缀中的进程为非死锁，补集即死锁集合；2000 组随机 `Request/Release/Detect/
Resolve` 序列下逐操作比对授予、拒绝原因、bseq、死锁集合与消解步骤，并校验
守恒、avail 非负、阻塞即放不下、存活 rb<L 等不变量。
