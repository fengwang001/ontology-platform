# 履约时效承诺与超时赔付 — 设计说明

1. 模块划分：`sla.go` 承诺冻结/事件状态机/并发协调；`treap.go` 两个隐式键树堆（天气端点差分、订单按原始承诺时刻索引）；`attribution.go` 分段归因；`adjudication.go` 档位裁决/申请窗口/自动裁决/账目；`model.go` 参数与校验；`errors.go` 可程序化区分的错误码。
2. 承诺冻结：接受时把容许时长、档位表、窗口、上限等全部快照进订单；`UpdateConfig` 只影响之后接受的订单。
3. 天气延展采用“接受时前缀查询 + 登记时推送”的混合方案：接受订单对点 `promisedAt` 做一次差分前缀和；之后新天气只推送给承诺时刻落在 `[l,r)` 的未送达订单。两个来源的天气集合按时间互斥，不会重复计数。送达即冻结，枚举跳过已送达订单，故送达后登记的天气天然不追溯。
4. 复杂度：裁决只读订单内 O(1) 字段（承诺、延展、各事件时刻、快照档位），不扫描天气表与订单表。天气登记 O(log W + k)，接受 O(log W)，与其他订单数量无关。基准 `BenchmarkClaimFixed` 对比 `BenchmarkClaimManyWeather`（各铺 10 万天气/订单）单笔均约 400ns，同阶即不增长的可验证证据。
5. 放弃的方案：① 裁决时扫描全部天气事件 —— O(W)，直接违背性能要求；② 纯推送 —— 漏掉“天气先登记、订单后接受”的订单；③ 送达时重新前缀查询 —— 会让送达/裁决耗时随天气总数 O(log W) 增长，且与“送达冻结”的心智模型不一致。
6. 并发：单把互斥锁串行化所有写操作，事件次序用阶段枚举强约束；锁内完成校验→变更→记账，被拒操作在校验阶段返回、不落任何状态，拒绝的接受不推进时钟。因此结果等价于某一串行顺序，赔付有 `adjudicated` 幂等位保证恰好一次，重放只依赖整数时刻因而确定。
7. 拒绝次序按规格固定：参数非法 → 时钟回退 → 不存在 → 已取消 → 状态类（事件次序/已改址/已赔付）→ 窗口类（未送达/超窗/无延误），每个操作只返回第一个命中错误。
8. 边界：天气与窗口均左闭右开；档位取等归高档、超最高归最高；归因余量截断为 0；并列按 商家>骑手>平台>用户，全零且有延误归平台；用户责任裁决记账但赔付 0，仍占用“唯一一次”。
9. 本地验证：`go test -race ./sla/`（覆盖面 + 并发恰好一次）；`go test -run TestDifferential -v ./sla/`（独立朴素全量重算模型对拍，逐步打印输入/输出/判定依据，40 个随机种子）；`go test -run XXX -bench BenchmarkClaim -benchtime=20000x ./sla/`（复杂度对照）。
