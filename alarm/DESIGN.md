# 报警生命周期管理设计说明

## 模块划分

- `types.go`：优先级、角色、状态、错误类别、操作和查询 DTO。
- `state.go`：无锁、无 I/O 的报警状态机转移规则。
- `point.go`：单点运行态、可见性判定和解除屏蔽时的展示状态。
- `chatter.go`：震荡滑动窗口，窗口语义为左开右闭 `(at-window, at]`。
- `expiry.go`：屏蔽到期最小堆，避免每次操作扫描全部报警点。
- `activity.go`：操作员可见报警集合、四层排序和出现时刻日志。
- `conditions.go`：系统工况信号维护，条件抑制不属于操作员行为。
- `runtime.go`：错误优先级、权限、原子拒绝、懒到期和可见性协调。
- `operations.go`：触发、返回、确认、手动屏蔽、解除、停用、启用、列表和报警率接口。

## 生命周期

状态机严格按以下转移执行：

- 正常、返回未确认 → 激活未确认；重复触发是无副作用空操作。
- 激活未确认 → 返回未确认；激活已确认 → 正常。
- 激活未确认 → 激活已确认；返回未确认 → 正常。

屏蔽和条件抑制不改变状态机，只改变是否进入活动列表。停用期间触发和返回被忽略；启用后一律为正常，必须等待下一次触发。

## 屏蔽与确认状态

手动屏蔽与震荡自动屏蔽共用同一份屏蔽状态。手动屏蔽允许操作员或工程师执行，要求非空原因、非紧急报警，且高/低优先级分别受不同时长上限约束；停用和启用仅工程师可执行。

解除屏蔽或条件抑制时，系统使用 `unacknowledgedOnShow` 保存“隐藏期间发生过新激活”这一事实：

- 新激活发生在屏蔽或抑制期间时置位。
- 激活期间确认不会抹掉尚未展示的新激活事实。
- 新生命周期正常结束、启用或真正处理后清除。
- 真正展示时以激活未确认呈现。

这避免了操作员对隐藏报警的确认被错误地沿用到解除后的新激活。

## 震荡抑制

每次真正从非激活进入激活时，向该点的窗口追加一个时刻。进入激活前先裁剪窗口：

```text
保留 t，当且仅当 current-window < t <= current
```

窗口内次数达到阈值且优先级不是紧急时，系统自动屏蔽配置时长，原因记录为 `震荡`。屏蔽期间触发不追加到窗口。

## 条件抑制

每个报警点配置工况名集合；任一工况信号为真即抑制。条件变化按工况名索引受影响点，而不是扫描全部点。条件抑制没有时长限制，不计入震荡，不要求操作员权限。

手动屏蔽与条件抑制是独立隐藏条件，两者同时存在时必须都解除才出现。

## 活动列表与报警率

活动集合只保存当前处于三种非异常状态且未屏蔽、未抑制、未停用的点。排序为：

1. 紧急 > 高 > 低。
2. 激活未确认和返回未确认优先于激活已确认。
3. 最近进入激活时刻更早者优先。
4. 编号字典序。

活动项首次加入集合时记录一次出现时刻。报警率在有序出现时刻切片上二分统计 `(at-duration, at]`。同一报警隐藏后再次出现会重复计数。

## 错误次序与拒绝原子性

错误严格按以下顺序判定：

```text
参数非法 > 时钟回退 > 报警点不存在 > 无权限 > 状态不允许 > 屏蔽时长超限
```

所有错误都在更新 `lastClock`、处理到期或修改点状态之前返回。停用点上的触发和返回不是错误，按需求忽略，但仍推进已接受操作的时钟。

## 并发

服务使用一个互斥锁串行化所有状态修改与一致性快照。每个调用在锁内完成验证和状态迁移，因此并发结果等价于某个按调用进入临界区顺序排列的串行历史。

## 复杂度

- 单点触发、返回、确认、屏蔽、解除、停用、启用：期望 `O(log S)`，其中 `S` 是未处理的到期项数量；状态查找为 `O(1)`，不扫描历史。
- 条件变化：`O(k log S)`，其中 `k` 是绑定该工况的点数。
- 活动列表：`O(A log A)`，只遍历和排序当前活动报警 `A`；若调用方接受流式有序结果，可进一步用专门的有序索引降到 `O(A)`。
- 报警率：`O(log M)`，其中 `M` 是累计出现次数；只做二分，不重放事件。

到期采用懒处理：只有接受的新操作或查询到达相应时刻时才弹出到期项，因此没有后台线程和数据竞争。

## 关键取舍

- 选择互斥锁而非每个点一把锁：全局单调时钟、错误原子性和跨点条件更新都需要统一顺序，单锁语义最容易证明；工业控制室命令量通常远低于内存哈希与小堆的吞吐瓶颈。
- 选择懒到期堆而非定时协程：避免后台线程在无人查询时修改状态，也避免大量定时器同时触发造成尖峰。
- 活动列表在查询时排序：实现简单、内存只维护活动项，且排序只与当前活动报警数量相关；如果未来查询 QPS 很高，可替换为分层有序集合。
- 报警率保存出现时刻而非全部事件：满足统计且不随总历史事件数增长；代价是不能从该结构恢复完整审计历史。

## 被放弃的方案

- 每个点独立锁：难以定义全局时钟回退和条件批量更新的可串行化顺序，容易产生死锁或跨锁不一致。
- 后台定时器自动解除屏蔽：会引入异步状态突变和日志时序问题，测试也难以精确复现。
- 每次查询重放全部事件：实现直观但列表和报警率都会随历史增长，不满足性能要求。
- 用一个“是否未确认”布尔值替代完整状态：无法同时表达返回未确认、已确认和隐藏期间新激活这三类语义。

## 本地验证

```bash
PATH=/usr/local/go/bin:$PATH GOCACHE=/tmp/go-cache-ontology go test ./...
PATH=/usr/local/go/bin:$PATH GOCACHE=/tmp/go-cache-ontology go test -race ./...
PATH=/usr/local/go/bin:$PATH GOCACHE=/tmp/go-cache-ontology go test -v ./alarm
PATH=/usr/local/go/bin:$PATH GOCACHE=/tmp/go-cache-ontology go test -run '^$' \
  -bench 'BenchmarkService(100|5000)Points' -benchmem ./alarm
```

本机一次基准结果中，活动报警固定为 10 条，总点数从 100 增至 5000 时，触发与列表耗时基本不随总点数增长。该基准可重复运行，结果应关注两档的数量级和相对差异，而不是固定数值。
