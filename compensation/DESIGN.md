# 动作副作用补偿回滚子系统 — 设计说明

## 1. 问题与不变量

一个动作声明一组**有序副作用子操作**（属性集合修改 / 链接创建删除 / 级联校验钩子），
按声明顺序依次生效。任一子操作失败时，必须把此前已生效的副作用按生效的**逆序**逐一撤销，
使对象图恢复到动作开始前的可观察状态。

实现必须维持以下不变量：

1. **生效与登记同单元**：子操作生效与其逆操作登记在同一个不可分割的处理单元内完成，
   不存在「已生效未登记」或「已登记未生效」。
2. **只补偿已生效部分**：失败子操作本身及其后子操作永不补偿。
3. **补偿不中断**：单个逆操作失败或抛异常只记录，不中止其余逆操作；异常不允许穿透补偿流程。
4. **失败状态冻结**：逆操作失败的对象，其对象图状态停留在补偿失败前的样子，后续相关逆操作跳过。
5. **污染态**：补偿失败涉及的对象进入污染态，显式修复前拒绝参与任何新动作，
   且拒绝发生在新动作的任何子操作之前。
6. **最早编号**：每个污染对象永久记录其**第一次**污染补偿中最早失败的子操作编号，
   后续污染不覆盖。
7. **判定优先级**（与补偿是否发生、是否成功无关）：
   `CONTAMINATED > BUSINESS_REJECTED > CONTENTION > COMPENSATION_FAILED`。
8. **并发**：互不相交对象子集的并发补偿等价于某串行顺序；争用同一属性/链接的一方
   在任何可观察改动之前被拒绝，拒绝不改变时钟戳与版本号。
9. **补偿开销**：逆操作的选取与执行是对动作内逆操作栈的反向扫描，O(k)（k=本次动作已生效步骤数），
   不随历史成功补偿总次数增长。

## 2. 模块结构

```
compensation/
├── types.go       分类、子操作、动作、结果、Tracer 接口
├── graph.go       对象图、对象/链接状态、守卫注册表、污染登记表、全局登记编号
├── effects.go     四类子操作的「生效 + 逆操作登记」原子单元与逆操作本体
├── executor.go    动作执行主流程：预检 → 守卫 → 生效 → 补偿 → 污染落账
├── tracer.go      打印型 Tracer（输入/逐步结果/最终判定）
└── *_test.go      全量测试与对拍
```

## 3. 关键取舍

### 3.1 「同单元生效+登记」如何在没有事务内存的 Go 里成立

不引入外部事务或 WAL，而是用**结构与锁序**消除中间状态：

- 每个 `effectAndRegister` 在持有被修改对象写锁（属性）或图锁+两端对象写锁（链接）的临界区内，
  先修改业务状态，紧接着把逆操作闭包 append 到当前动作的本地栈；
- 临界区内两次动作之间**没有任何可能失败的调用**（没有 IO、没有锁申请、没有用户代码），
  因此从语言层面不可能在两步之间被打断或报错；
- 逆操作闭包捕获恢复所需的旧值（旧属性、旧存在性、旧链接端点），闭包构造是纯内存操作。

被放弃的方案：
- *先登记后生效（两阶段）*：需要「待提交」标记和崩溃恢复路径，语义上允许「已登记未生效」的观察窗口，
  与需求冲突；
- *WAL/事务日志*：为进程内内存对象图引入持久化依赖，超出问题边界，且无法简化失败语义。

### 3.2 补偿顺序与失败汇总

- 逆操作存放在动作本地栈，补偿时从栈顶向栈底扫描，天然严格逆序，选取成本 O(1)/步；
- `inverse.run` 内部 `defer recover` 把异常转换成 `panicked=true` 的失败记录，
  补偿循环只看记录，异常不可能穿透；
- 维护本次补偿的 `poisoned` 集合：一旦某对象出现在硬失败记录中，之后任何触及它的逆操作
  标记 `Skipped` 并跳过执行——保证失败对象不被「进一步改动」；
- 注意区分：**跳过不产生新的污染对象**。污染只来自真正执行且失败/异常的逆操作；
  污染编号也只从这些「硬失败」记录中取最小值。该语义由测试
  `TestDifferentialAgainstNaiveModel`（对拍）与 `TestSkipAfterPoisoned` 共同钉死。

### 3.3 污染最早编号

- `Graph.taints map[id] -> {earliestStep, entry}` 受独立 RWMutex 保护；
- `commitTaints` 先在本次硬失败记录中为每个对象取最小子操作编号，
  再以「已存在则不写」的方式落账，第一次污染永久保留（含其全局登记编号）。

### 3.4 并发控制：为什么是属性/链接粒度的守卫而不是整图锁

- 守卫键：`prop:<obj>|<attr>`、`link:<linkID>`、`hook:<obj>`。
  需求规定争用单位是「同一对象的同一属性或同一条链接」，属性级守卫让同对象不同属性真正可并行，
  同时互不相交子集的动作在守卫层面零交集；
- 动作开始时把全部守卫键排序后逐个 `TryLock`：
  任何一个获取失败立即释放已获取部分并返回 `CONTENTION`，
  全部获取发生在第一次生效之前，所以拒绝时**不可能**已有可观察改动，时钟/版本自然不变；
- 排序加锁保证守卫之间无死锁；对象写锁仅在已持有全部守卫后、在单个临界区内短暂持有，
  锁序固定为「图锁 → 对象锁（按 ID 排序）」。

被放弃的方案：
- *阻塞式 Lock 排队*：无法表达「争用即拒绝且拒绝前零改动」——排队期间虽无改动，
  但把争用延迟成了超时问题；`TryLock` 使拒绝是确定性的同步判定；
- *版本号 CAS 重试*：CAS 失败通常发生在「已读旧值、准备写回」阶段，
  容易滑向「先改后回滚」，与「拒绝前零改动」的强表述不匹配。

### 3.5 全局逆操作登记编号

- `Graph.entryCounter` 是单个 `atomic.Uint64`，每次「生效+登记」单元分配一个号；
  钩子无业务副作用也占号，保证跨流程编号不重复、不缺失（对拍断言为连续 1..N）；
- 编号只用于追踪与污染溯源，不参与补偿选取，因此原子自增无竞争热点风险。

### 3.6 时钟戳与版本号

- 属性修改：所属对象 `clock++`、`version++`；
- 链接创建/删除：两端对象各 `clock++`（删除不改端点 version，创建随首次建立 +1），
  链接自身 `version` 每次存在性翻转递增；
- 钩子只读，不触碰任何时钟/版本；
- 逆操作做对称的递减/恢复；干净补偿后所有时钟与版本回到动作前值，由
  `TestSingleStepFailure`、`TestLinkCreateDeleteRollback` 断言。

## 4. 执行流程（`Executor.Execute`）

```
0. 污染预检（动作涉及的全部对象）            CONTAMINATED → 立即返回，零改动
1. 排序 TryLock 全部守卫                    CONTENTION   → 立即返回，零改动
2. 持锁后二次污染检查（封住预检-获锁窗口）   CONTAMINATED → 释放守卫并返回
3. 按序生效：Check → effectAndRegister
     - Check=false / 结构错误：记 BUSINESS_REJECTED，停止生效
     - 成功：结果与登记编号进入结果集
4. 若全部成功：OK
5. 逆序补偿：失败/异常 → 记录并冻结；触及已冻结对象 → 跳过
6. 无补偿失败 → BUSINESS_REJECTED；
   有补偿失败 → commitTaints（只写首次）→ COMPENSATION_FAILED
7. defer 释放全部守卫
```

失败子操作与其后子操作从未进过逆操作栈，因此「只补偿已生效部分」是数据结构层面的保证，
不依赖标志位约定。

## 5. 与朴素顺序模型对拍

`naive_test.go` 用完全独立的第二套实现（无锁、无守卫、map 直改、独立补偿循环）建模同样的语义。
`TestDifferentialAgainstNaiveModel` 以固定种子随机生成 400 组动作序列（每组 1–4 个连续动作），
随机注入：业务拒绝点、逆操作失败、逆操作异常、不同属性/链接与钩子，逐字段比较：

- 每个对象每个属性的最终值；
- 每个对象的版本号与时钟戳；
- 每条链接的存活态；
- 每次调用的判定类别；
- 污染对象集合及其最早失败子操作编号。

两侧共享的只有输入结构（`SubOp`）与结果枚举（`Category`），算法各自独立。

## 6. 本地验证方法

```bash
go test -race -v ./compensation/      # 全量用例 + 竞态检测
go test -race -count=10 ./...         # 对拍重复 10 轮（4000 组随机序列）
go vet ./...
gofmt -l .
go run ./cmd/compensation-demo        # 打印四类典型场景的输入/逐步结果/最终判定
```

测试失败时用例的 cleanup 会自动打印该用例的完整动作-补偿日志（通过 `LogTracer` 缓冲）。
