# 持久卷 / 卷声明绑定控制器 — 设计说明

## 1. 模块划分

代码位于 `pvbinding/`，按职责拆成相互协作的小模块：

| 文件 | 职责 |
| --- | --- |
| `types.go` | 卷、声明、状态、快照与指派结果的纯数据定义 |
| `errors.go` | 五类错误（参数非法 / 不存在 / 状态冲突 / 无满足卷 / 容量不足）与优先级 |
| `match.go` | 单一候选谓词 `candidateFilter.matches`（不含节点约束）与节点约束判定、深拷贝工具 |
| `store.go` | 按存储类分桶、桶内按 `(容量升序, 名称字典序)` 有序的可用卷索引 |
| `assign.go` | 延迟联合绑定的最优互不相同指派求解器（带回溯的穷举搜索 + 剪枝） |
| `controller.go` | 对外 API、加锁、立即绑定与重评估、回收、扩容、联合绑定编排、观测计数 |
| `invariants.go` | 可调用的全量一致性自检 `CheckInvariants` |
| `validation.go` | 输入合法性校验（错误类别优先级的最高层） |

关键取舍是让“规则”只有一个事实来源：立即绑定与联合绑定共用
`candidateFilter.matches`，节点约束作为联合绑定独有的额外谓词；两个测试模型
（主实现与朴素模型）都只依赖该规则的语义描述而不是代码。

## 2. 核心规则落点

### 2.1 立即绑定

- `AddClaim`（立即模式）以及“新卷加入 / 卷释放回可用（管理员重置）/ 卷被修改”
  之后统一走 `reevaluateLocked`。
- 重评估按声明名称升序逐个处理待绑定的立即声明；前一个声明拿走的卷立刻从
  可用索引移除，自然实现声明之间的互斥。
- 选卷只扫描声明所属存储类的有序桶，第一个通过全部候选谓词的卷即
  “最小容量、同容量名称字典序最小”。立即绑定时**不检查节点约束**。
- 声明指定 `VolumeName` 时谓词强制卷名相等；指定卷不满足条件时声明保持
  待绑定，任何后续事件都不会改选。

### 2.2 预绑定预留

- 卷的 `ReservedClaim` 体现为 `Available` 卷上的 `ClaimName`；候选谓词要求
  预留名非空时必须等于当前声明名。
- 预留可以指向尚不存在的声明；被实际绑定后预留字段清除；回收时同样清除，
  历史身份不带入 `Released`。

### 2.3 延迟联合绑定（`assign.go`）

- 调用方给出 `(节点, 延迟声明列表)`。声明先按名称排序；每个声明的候选集 =
  通用候选谓词 ∧ 节点约束；任一声明候选为空直接判定无解。
- 求解器对“声明 × 互不相同卷”做带回溯的穷举枚举，目标函数：
  1. 总浪费 `Σ(卷容量 − 请求容量)` 最小；
  2. 总浪费并列时，按声明名称升序得到的卷名称序列字典序最小。
- 剪枝只在“剩余最小浪费下界 **严格大于** 当前最优总浪费”时生效；下界相等
  时必须保留，因为可能存在字典序更小的解（这是开发中实际踩到并被
  `TestDelayed_*` 抓住的坑，见下文“被放弃的方案”）。
- 找到可行解不是终点：搜索完整空间以保证全局最优；输出按声明排序返回，
  与调用方输入顺序无关。结果全有或全无，仅在确定有解后才提交状态变更。
- 错误判定顺序保证类别优先级：结构参数（空节点 / 空列表 / 重复名）→
  全部存在性 → 已存在声明的模式合法性（参数非法优先于不存在）→
  已绑定（状态冲突）→ 无满足指派。

### 2.4 回收

- 删除已绑定声明：卷先离开可用索引；`Delete` 策略直接从系统移除；
  `Retain` 策略转为 `Released` 并清空 `ClaimName` 与 `ReservedClaim`。
- `Released` 卷永远不进索引、不参与任何匹配；只有管理员 `ResetVolume`
  才回到 `Available` 并触发一次重评估。
- 删除待绑定声明不触碰任何卷。

### 2.5 扩容

仅允许已绑定声明：新值必须为正、不得降低、不得超过所绑卷容量；任一条件
不满足都拒绝且状态不变。降低归为参数非法，超容量归为容量不足。

## 3. 错误类别与优先级

优先级从高到低：`ErrInvalidArgument > ErrNotFound > ErrConflict >
ErrNoMatch > ErrCapacityExceeded`。所有错误为带 `Kind/Op/Detail` 的
`ControllerError`，可用 `KindOf(err)` 判别。实现中所有操作都按此顺序组织
校验（例如 `ExpandClaim` 先判正数，再查存在性，再查绑定态）。

## 4. 并发模型

控制器持有一把 `sync.Mutex`，所有变更与查询在临界区内完成；联合绑定的
求解在锁内进行（候选集是深拷贝出的指针列表，状态只在求解成功后提交）。
因此任意并发调用的可观察结果等价于某一个串行交错，同一卷不可能并发绑给
两个声明。查询接口（`Snapshot`/`Stats`/`CheckInvariants`）同样取锁，
读到的总是一致状态。

被放弃的方案：分片锁 / 乐观版本号。原因是本题规模下规则判定很轻，
单锁最简单且把“全有或全无的联合绑定 + 绑定后触发重评估”天然串行化，
避免了多锁下的死锁与部分提交问题；性能压测（~600ns/次选卷）表明锁不是
瓶颈。若未来需要更高吞吐，可在存储类桶级别做分片并以两阶段方式提交。

## 5. 性能取舍与可验证性

- 立即选卷的复杂度为“该声明存储类桶内的候选顺序扫描”，与其他存储类的
  卷数量无关。桶内有序插入/删除为 O(桶大小)，扫描在命中最优卷时通常提前
  停止。
- 被放弃的方案 1：每个桶维护容量小顶堆 + 惰性删除。堆无法高效处理“标签 /
  访问模式 / 指定卷名 / 预留”等谓词导致的跳过，有序切片的顺序扫描既满足
  最坏检查数可预测，又让“同容量取名称最小”零成本。
- 被放弃的方案 2：全局卷表线性扫描。实现最简单，但选卷开销随无关存储类
  卷数线性增长，直接违反需求。
- 验证方式：`Stats()` 暴露累计检查卷数 `ExaminedTotal`；
  `TestImmediateSelection_OnlyScansOwnStorageClass` 构造“无关卷 100 →
  20000、目标桶恒为 50”的两组场景，断言检查数恒为 50；目标桶扩大到 200
  时检查数才变成 200。基准测试 `BenchmarkImmediateSelection` 显示无关卷
  1k/10k/50k 时每次选卷均在 ~600ns 量级。

## 6. 联合绑定：被放弃的贪心方案

最直觉的做法是“按声明顺序、每个声明贪心地选当前最小浪费的卷”。它在
`TestDelayed_GreedyFailsButJointSucceeds` 的构造下会失败：声明 `a` 只能用
`shared`，声明 `b` 两个卷都能用；若贪心先把 `shared` 分给 `b`，`a` 无卷，
但整体指派 `a→shared, b→big` 明明存在。因此最终采用穷举最优指派，保证
“存在能同时满足全部声明的指派时必须成功”。

开发中第一版求解器在“浪费下界等于当前最优”时提前剪枝，丢失了同浪费下
字典序更小的解（被并列用例测出），最终规则收敛为：只做严格下界剪枝，
完整比较 `(总浪费, 卷名序列)`。

## 7. 一致性自检

`CheckInvariants()` 在锁内校验：双向绑定一致性、待绑定声明无卷名、
`Released` 卷无属主、可用索引与 `Available` 卷集合严格一致、索引有序性、
数值容量约束等。每个确定性测试、随机对照的每一步、并发测试结束后都会
调用它。

## 8. 本地验证方法

```bash
# 注：本环境 go 位于 /usr/local/go/bin，缓存重定向到可写目录
export PATH=$PATH:/usr/local/go/bin GOCACHE=/tmp/gocache

go test ./...                                   # 全量
go test -race ./pvbinding/                      # 竞态
go test -run TestRandomDifferential -v ./pvbinding/  # 40 个随机种子逐步对照
go test -run TestImmediateSelection_OnlyScansOwnStorageClass -v ./pvbinding/
go test -bench BenchmarkImmediateSelection -run NONE ./pvbinding/
go vet ./... && gofmt -l .
```

随机对照测试（`naive_test.go` 中的朴素模型）不使用生产代码的索引与求解
路径：立即绑定用 map 线性扫描，联合绑定用无剪枝全枚举；每一步操作后
比较双方的成功/失败、错误类别、全量状态指纹，并交叉执行
`CheckInvariants`。每条操作都通过测试日志打印“输入 / 实际输出 / 判定
依据”（`go test -v` 可见）。
