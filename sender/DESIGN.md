# 设计说明：发送端小段合并调度器

本文记录 `sender` 包的语义定义、关键取舍、被放弃的方案与本地验证
方法。目标是让“小段发送的抑制、选项开关与零窗口探测的相互作用”
可以被**精确复现**：同样的配置与事件序列（含事件时刻）必然产生
同样的段序列、错误与查询结果。

## 1. 状态模型

调度器不保存字节内容，只保存计数器（段的内容对调度决策无影响）：

| 状态 | 含义 |
| --- | --- |
| `unsent` | 缓冲中尚未发出的字节数 |
| `inFlight` | 在途字节数（已发送未确认，含探测字节） |
| `sentTotal` | 下一个待发送序号（累计已发） |
| `ackedTotal` | 累计已确认字节数 |
| `wndRight` | 对端窗口右边缘 = 累计确认 + 最新通告窗口 |
| `noDelay / cork / closed` | 选项与生命周期标志 |
| `corkSince` | 软木塞保留批次锚点（见 §3） |
| `zeroSince` / `lastProbe` | 零窗口锚点与上次探测时刻（见 §4） |
| `lastTime` | 最近一次被接受事件的时刻 |

可发送上限 `usable = wndRight - sentTotal`。确认事件携带的
`acked` 是**本次确认的字节数**（确认本身是累计语义的：确认前序
全部在途数据），新右边缘 = `ackedTotal + acked + window`，小于已知
右边缘即窗口收缩。

## 2. 发送决策

每个被接受的事件处理完毕后立即执行一次发送决策：

1. 计算窗口可容纳的满段数 `fulls = min(unsent/M, usable/M)` 与小段
   长度 `piece = min(unsent, usable) - fulls*M`（恒小于 M）。小段既
   可能是数据尾部，也可能是**被窗口截短的段**——截短的段不再视为
   满段，受小段规则约束。
2. 先发全部满段（满段在窗口允许范围内总是可发）。
3. 再判定小段是否放行。**判定在本批满段发出之后进行**：默认模式
   下“在途为空”指的是包含本批满段之后的在途——一次写入
   `2M+1` 字节时，两个满段发出后尾部 1 字节被保留，等待在途清空
   或后续写入凑满。这与 Nagle 的经典语义一致。
4. 零窗口探测（见 §4）。

小段放行条件（按优先级）：

- 已关闭：放行（忽略一切保留约束）。
- 软木塞打开：仅当保留已满超时（边界取等号：恰好到达超时即解除）。
- 不延迟打开：放行。
- 默认：在途为空才放行。

两个选项同时打开时软木塞优先（软木塞分支先于不延迟分支判定）。

## 3. 软木塞锚点

“自最早一批被保留数据进入缓冲时起满软木塞超时”落地为：

- **锚定**：软木塞打开期间，首次出现“窗口可容纳的小段”的时刻即
  为保留批次起点。
- **解除**：锚点起满超时后保留解除，解除是**粘性的**——此后该批
  次数据只受窗口约束，即使窗口随后关闭再打开也不再重新计时。
- **清除**：批次数据全部发出（缓冲中不再有窗口可容纳的小段且窗口
  非零）、软木塞关闭或连接关闭时清除锚点；下一批保留数据重新锚定。

推论：窗口为零期间锚点保留但**不重新起算**；窗口打开时若保留批次
早已超时，数据随窗口开放立即发出。

## 4. 零窗口探测

- 条件：缓冲非空、在途为空、可用窗口为零（`usable <= 0`）。在途非
  空（包括探测字节本身在途）时不探测。
- 计时基点：`max(窗口变为零的时刻, 上次探测时刻)`。“窗口变为零”
  指可用窗口由正变为零（含被本端发送填满），在事件边界观测；只要
  可用窗口持续为零，锚点不重置。
- 触发：距基点满探测间隔即在当前事件发出一字节探测段（边界取等
  号）。探测字节取自缓冲、计入在途；它被确认后，其余数据是否可发
  只取决于最新窗口。
- 间隔为零时，条件满足即立即探测。

## 5. 错误与拒绝

固定优先级：参数非法 > 时钟回退 > 关闭后写入 > 缓冲已满 > 窗口收
缩 > 确认越界。每个事件方法按此顺序检查，命中即返回对应哨兵错误，
**不触碰任何状态**（包括时钟——`lastTime` 只被被接受的事件推进）。
因此“先回放、再复现”时，被拒绝的事件可以完全跳过。

时钟回退判定：事件时刻小于**上一次被接受事件**的时刻（等于允许）。

## 6. 关键取舍

1. **计数器而非字节队列**。缓冲只记字节数，不记内容、不记逐字节
   到达时间。这使每个事件的处理开销为 O(1)（外加本次发出的段数），
   且状态可整体快照对比。代价是无法按“每个字节的入缓冲时刻”锚定
   软木塞——见 §7 被放弃的方案。
2. **保留的字节数按“当前窗口下本可发出但被扣留”定义**。
   `Retained()` 在窗口为零时返回 0：此刻数据是被窗口而非保留规则
   挡住。这与发送决策共用同一段 `pending()` 计算，保证查询与行为
   严格一致。
3. **软木塞锚点按“首次出现窗口可容纳的小段”起算**，而非数据入
   缓冲的时刻。窗口为零时写入的数据，其保留计时从窗口首次可容纳
   它的事件起算。这使锚点维护为 O(1)，且与“窗口不足以容纳整个小
   段时只发窗口允许的部分”的窗口优先原则自洽。
4. **被窗口截短的段按小段处理**。窗口剩余不足一个满段时，截短部
   分参与 Nagle/软木塞判定，而不是“满段总是可发”的例外。这复现
   了真实 TCP 中窗口受限的小段同样被 Nagle 抑制的行为。
5. **同批满段计入在途后再判定小段**（见 §2.3）。否则任何大批量
   写入的尾部都会绕过 Nagle 立即发出，“后续写入凑满满段”的规则
   将形同虚设。
6. **探测锚点取窗口归零与上次探测的较晚者**。在途清空不重置计时：
   探测字节被确认时若距上次探测已满间隔，下一探测在该确认事件立
   即发出。这直接对应“自窗口变为零或上次探测起满探测间隔”。
7. **互斥串行化实现并发等价**。所有方法在同一把互斥锁内完成
   “检查—变更—发送决策”，线性化点明确，并发调用自然等价于某个
   串行顺序；未引入更复杂的无锁结构，因为事件处理本身是 O(1)。
8. **时钟完全注入**。不设真实定时器、不读系统时钟：`Advance` 是
   唯一的时间来源，`NextDeadline` 告诉调用方下一次需要推进到何时。
   测试与生产走同一条代码路径。

## 7. 被放弃的方案

1. **逐字节（或逐写批次）队列 + 入缓冲时间戳**。可以按“数据进入
   缓冲的时刻”锚定软木塞，但状态与内存随缓冲内批次数增长，违反
   “开销不得随缓冲总量增长”的约束；且“被保留数据”的边界在窗口
   截短场景下本来就随窗口移动，逐字节时间戳并不能给出更自洽的
   答案。改用单锚点（§3）。
2. **事件溯源 / 历史回放**。保存全部事件以支持审计与重放，会让内
   存与查询开销随历史事件数增长。改为：被拒绝的事件不产生任何副
   作用，调用方若需重放可自行记录事件流。
3. **内置定时器堆 / 真实时钟**。引入 `time.Timer` 会让行为依赖
   调度延迟，无法精确复现，也使测试必须等待真实时间。改为注入时
   钟 + `NextDeadline` 查询。
4. **窗口截短段视为满段直接发出**。实现更简单，但与“被窗口截短
   的段不再视为满段”的明确要求冲突，且会丢失 Nagle 在窗口受限时
   的抑制行为。
5. **探测计时在在途清空时重置**。更保守（避免确认事件立即触发下
   一探测），但与“自上次探测起满探测间隔”的字面语义不符。
6. **关闭作为终态拒绝一切后续事件**。规格只要求关闭后拒绝写入；
   确认、时间推进在关闭后仍须驱动残余数据排空。重复关闭实现为幂
   等空操作。

## 8. 本地验证方法

```bash
# 全部测试：确定性用例 + 1200 组随机事件序列对照
go test ./sender/

# 并发串行化（需 -race）
go test -race ./sender/

# 查看随机对照的逐步日志（输入、输出、判定依据）
go test -v ./sender/ -run 'TestAgainstNaiveModel/seed=7'

# O(1) 开销证据：稳态事件零分配 + 基准
go test ./sender/ -run TestEventCostIsConstant -v
go test ./sender/ -run xxx -bench . -benchmem
```

验证体系分四层：

1. **确定性用例**（`scheduler_test.go`）：满段/小段边界、窗口恰好
   等于小段与差一字节、软木塞超时恰在边界、两选项同时打开、关闭
   后窗口受限分批排空、零窗口探测的开始/重锚/取消、错误优先级与
   拒绝后状态不变、时钟回退、查询只读。
2. **随机对照**（`model_test.go`）：独立的朴素模型（逐字节缓冲、
   逐段循环、输出判定依据）与正式实现跑 1200 组随机事件序列，逐
   步比对段序列、错误与全部查询结果，逐步打印日志。
3. **开销证明**（`bench_test.go`）：实现侧，状态为定长计数器、无
   任何随缓冲总量或历史事件数增长的结构（可代码审查）；测试侧，
   `TestEventCostIsConstant` 在十万级历史事件后断言稳态事件堆分配
   恒为零；基准显示单事件开销与历史无关（每次事件的成本只随本次
   发出的段数增长，段输出本身是调用方要求的产出）。
4. **并发**（`bench_test.go` + `-race`）：多协程混合调用事件与查
   询，竞态检测器验证串行化，结束后校验不变量。
