# 区域运力调度与高峰加价：设计说明

1. 包 `surge`，8 个 Go 文件按职责拆分：
   `errors.go` 可程序化区分的错误类别；`config.go` 构造参数与校验；
   `ledger.go` 区域/骑手/订单状态与增量计数；`tier.go` 档位纯函数；
   `events.go` 档位事件与补贴条目；`operations.go` 全部状态变更操作；
   `system.go` 系统、锁、时钟；`queries.go` 只读查询。
2. 档位用整数索引：0 为基础档，`Thresholds[i]` 对应升档到 i+1。
   目标档=满足 `ratio>=threshold` 的最高档；`待派>0 且运力=0` 为无穷大到最高档；皆零为 0。
3. 状态机为纯函数 `applyEvaluation`：上调立即跳到目标档并清零确认；
   下调每次只降一档并清零计数，确认不足只累计；目标等于当前档清零。
   所有不变量集中在此函数，易独立推理与单测。
4. 供需计数增量维护：区域保存 `available/pending`。
   可用运力变化只在“持单跨过上限边界”时发生：派单使 held 变为上限则减一，
   完成使 held 从上限回落则在骑手当前区域加一；移动、上下线同理。
   因此评估只做一次除法与阈值扫描，O(档位数)，与骑手/订单数量无关；
   派单与完成是 map 查找加常数次计数更新，O(1)。
5. 订单在创建时快照 `lockedTier`；倍率与补贴只看锁定档，档位后续变化无影响。
   补贴资格（骑手进入本区时刻 `<=` 订单创建时刻）在派单瞬间快照到订单，
   使完成结算成为纯 O(1)，也不受骑手之后移动影响。
6. 并发取一把全局 `sync.Mutex`：操作天然等价于某串行顺序，拒绝先于任何修改发生，
   故持单上限、可用运力、待派数为强不变量；重放确定。
7. 被放弃方案：每区域/每骑手细粒度锁（跨区移动与派单需多锁，易死锁、难证明）；
   评估时全量扫描骑手/订单（随规模增长，违背性能要求）；
   完成时再回溯骑手进入时刻（移动后信息已变，无法可靠判定）。
8. 时钟：接受操作的时刻单调非降，回退在任何状态读取前判定；
   被拒操作不推进时钟、不触碰账本。评估间隔“取等合法”（`at-last >= min`）。
9. 错误次序：非法参数 → 时钟回退 → 对象不存在（骑手/区域/订单）
   → 状态错误 → 派单资格（不在线/不在本区/持单已满）→ 评估过频，仅报首个。
10. 本地验证：
    `go test -race -v ./surge`（含全部指定场景与并发竞态检测）；
    `TestNaiveDifferential` 用独立朴素模型（每次全量重算供需）跑随机序列逐步对比，
    `-v` 打印每步输入、双方输出与判定依据；
    `go test -bench . -run '^$' ./surge` 对比 1000/10000 规模耗时以验证 O(1)。
