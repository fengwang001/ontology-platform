# 批量导入属性级权限守门器 — 设计说明

## 1. 问题与范围

一次批量导入包含多条记录，每条记录对某个对象（创建或更新语义）写入若干属性字段。
守门器在写入前统一施加：

- **执行模式**（整批声明一次）：`atomic`（任一字段无权限 ⇒ 整条记录失败）或
  `lenient`（无权限字段跳过，其余字段写入，跳过后重新判定必需属性约束）。
- **字段级写权限**：以「发起时刻权限快照」为准，执行期间的权限变更对本批不可见。
- **必需属性约束**：创建语义下没有旧值可沿用，缺任何必需属性即失败；更新语义下
  可以沿用对象已有旧值。宽松模式跳过字段后必须二次判定。
- **记录隔离**：记录各自独立判定与写入，失败不传染。
- **并发等价串行**：批内并发处理、以及与其他批的交错，最终可观察结果等价于某个
  全局串行顺序。

代码位于 `importguard` 包，无外部依赖。

## 2. 关键类型

- `Mode`：`atomic` / `lenient`；`Semantic`：`create` / `update`。
- `Entry`：`{ObjectID, Type, Semantic, Fields}`。
- `RecordResult`：`success` / `partial_success`（仅宽松模式，带 `Skipped` 字段清单）
  / `failed`（带分类化 `Failure`）。
- `Failure.Category` 为以下可区分错误（整批级两类、记录级四类）：
  `batch_invalid_parameter`、`subject_not_found`、`object_type_not_found`、
  `semantic_mismatch`、`field_permission_denied`、`required_property_missing`
  （其中前两类为整批级）。
- `Store`：对象类型、主体、对象、只增不改的权限历史（`PermissionEntry` 带
  单调递增 `RevSeq`）。
- `Snapshot`：发起时刻的不可变深拷贝 + 折叠后的「有效权限索引」。

## 3. 处理流程

### 3.1 整批级（命中则整批不处理、不改任何状态）

1. 模式参数缺失/非法 ⇒ `batch_invalid_parameter`（优先级最高，先于主体检查，
   因此主体同时缺失时仍报参数非法）。
2. 获取全局临界区，**在锁内**拍摄快照。
3. 发起主体在快照中不存在 ⇒ `subject_not_found`。

### 3.2 记录级（两阶段，失败仅影响本条）

**阶段一（并发，只读不可变输入）** 对每条记录的每个字段做一次权限判定。

**阶段二（按索引顺序串行提交）** 严格按拒绝优先级：

1. 对象类型不存在 ⇒ `object_type_not_found`；
2. 创建/更新语义与实际存在性不匹配（对不存在对象 `update`、对已存在对象
   `create`）⇒ `semantic_mismatch`；存在性以「快照 + 本批此前已提交记录」的
   串行叠加视图为准，保证同批重复目标对象时也等价于串行；
3. 字段权限：`atomic` 下存在任何被拒字段 ⇒ 整条 `field_permission_denied`，
   不写任何字段；`lenient` 下被拒字段进入跳过清单；
4. 跳过之后的必需属性二次判定：
   - `create`：被跳过/未写入的必需属性一律缺失 ⇒ 失败回退；
   - `update`：若该对象在串行叠加视图中已有该属性的旧值，则约束满足；否则失败。

只有通过全部检查才实际写入（创建=插入，更新=补丁并自增版本）。失败路径在写入
之前全部返回，因此天然是「整体回退、不改已有对象」。宽松模式全部通过且存在跳过
字段时为 `partial_success`，结果中列出 `Skipped`。

### 3.3 为什么把部分判定拆成两阶段

记录内并发判定若直接读取可变对象状态，会产生数据竞争并破坏可串行性。因此：

- **只依赖权限快照的判定（字段权限）在阶段一并发完成**；
- **可能观察本批此前记录写入的判定（语义存在性、必需属性旧值沿用）在阶段二对
  串行叠加视图 `overlay` 顺序执行**。

权限判定结果一旦由快照得出即固定，后续不再访问任何可变权限状态；两阶段组合的
最终结果与「严格按索引串行、每条记录用批起始快照判权限」完全一致。

## 4. 权限快照与规模无关性（可验证）

权限历史只增不改，一个类型的历史条目数 H 可无限增长。直接逐条扫描会让单条记录
判定随 H 线性增长。快照在批起始时把全部历史**折叠一次**为 map：

```
perm[(subject,type,action,field)] = 最新 RevSeq 条目的 allow 决定
```

因此：

- 单个字段的判定 = **恰好一次 map 查找**，缺失单元格默认拒绝；
- 单条记录的权限条目访问数 = **该记录字段数**，与批大小、与该类型历史条目总数
  均无关；
- 折叠成本 O(H)，每批仅一次，不按记录数重复。

测试 `TestScaleIndependentPermissionLookups` 以可执行方式证明：在 10 000 条历史
条目、批大小 1/16/128 下，直接检查 3 个字段恰产生 3 次查找；经完整流水线，4
字段记录的计数恰为 4，且历史长度从 0 到 5000 不变。

## 5. 并发控制与隔离

- `Store.mu` 覆盖「拍照 + 全部判定 + 全部提交」，**每批一个临界区**，因此任意多
  个并发批的最终状态等价于按获取锁顺序的全局串行排列，不可能出现半批交错或丢失
  更新。
- 批内阶段一使用有界 worker 池（只读快照与按记录的局部计数器），阶段二单线程
  按索引提交；`go test -race` 下验证无竞争。
- 被拒整批/记录在任何状态修改前返回，不改变对象也不改变权限记录；权限变更 API
  在批临界区外排队等待，天然不能影响进行中的批次。

### 放弃的方案

- **MVCC / OCC 乐观并发 + 重试**：可缩小临界区、提升吞吐，但显著增加正确性面
  （版本号、重试、快照 GC），在本题「结果必须可证明等价串行」的要求下性价比低，
  故放弃，改用整批粗粒度锁换取可证明性。
- **阶段一直接读实时对象状态**：有数据竞争且会在同批重复 ID 上产生与串行不一致
  的结果，放弃；改为权限并发判定 + 存在性/必需约束顺序复核。
- **判定时线性扫描权限历史**：违反规模无关性能要求，放弃；改为批起始一次性折叠
  为有效权限索引。
- **宽松模式先写后补回滚**：会产生可观察的中间态，放弃；采用「先算变更集、全
  部通过才提交」，失败即零写入。

## 6. 判定日志

`DecisionLogger` 记录每次判定的 `stage / inputs / output / basis`，包括：批级
校验、快照折叠（含历史条目数）、逐字段权限（有效权限单元格取值或默认拒绝）、
必需属性二次判定、串行提交。提供 `TextLogger`（单行结构化输出，默认 stderr）
与 `SliceLogger`（测试断言）。

## 7. 测试覆盖面（`go test -race -v ./importguard/`）

- `TestModeDifferenceSameInput`：两种模式下相同输入产生不同结果（原子失败零写入
  vs 宽松部分成功并列出跳过字段）。
- `TestLenientRequiredRecheck`：宽松模式必需属性二次判定的正（更新沿用旧值 ⇒
  部分成功）反（创建缺失回滚；更新无旧值 ⇒ 失败回滚）两面。
- `TestCreateUpdateOldValueDifference`：创建/更新语义与沿用旧值差异
  （对已存在对象创建、对不存在对象更新均语义不匹配）。
- `TestSnapshotStableDuringExecution`：批执行期间并发追加授权，本批 50 条记录
  全部仍按发起快照跳过该字段；新批才观察到授权。
- `TestRejectionPriorityAndIndependence`：整批级（参数非法 > 主体缺失）与记录级
  （类型不存在 > 语义不匹配 > 字段权限 > 必需属性）优先级，以及记录间失败隔离、
  原子失败不改变既有对象。
- `TestScaleIndependentPermissionLookups`：规模无关性能的可执行证明。
- `TestConcurrentBatchesSerializable`：12×25 并发批的唯一创建不丢、共享对象更新
  版本号精确等于更新次数（等价某串行顺序）。
- `TestDifferentialAgainstNaive`：400 组随机世界（类型/必需属性/权限历史含覆盖与
  拒绝/对象存在性/语义/字段组合/偶发未知主体与不存在类型）与**独立编写的朴素
  顺序模型** `NaiveBatchImport` 对照，要求逐记录结果与最终对象状态完全一致。
- `TestDecisionLogging`：日志含每次判定的输入、输出与依据。
