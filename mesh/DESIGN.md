# 服务网格流量路由模块（mesh）设计说明

## 1. 模块划分与协作

| 文件 | 职责 |
| --- | --- |
| `types.go` | 全部领域类型（配置/规则/匹配项/目标/策略/请求/结果）与七类错误 `Kind`。错误优先级即常量声明顺序。 |
| `match.go` | 纯匹配逻辑：去查询串、按 `/` 切段的段边界前缀、头条件三种形态（精确/前缀/存在）、多值头"任一满足"、以及**发布期覆盖判定**所需的路径覆盖 `pathCovers` 与头蕴含 `headerEntailed`。 |
| `policy.go` | 策略逐字段继承 `mergePolicy` 与生效策略两条不等式校验。 |
| `validate.go` | 发布四阶段校验：结构（参数非法）→ 权重 → 策略 → 遮蔽，阶段顺序即错误优先级，阶段内按规则序号最小者。 |
| `registry.go` | 子集与端点注册；维护 `readyCount` 使路由就绪查询为 O(1)，与端点数无关。 |
| `index.go` | 发布期构建的路径段前缀树（trie），把"可能命中"的匹配项压缩到请求路径链上。 |
| `mesh.go` | 编排：原子快照 + 乐观版本 CAS 发布、首命中路由、相邻分桶选目标、端点可用性判定、深拷贝隔离。 |

请求流：`Service.Route` 一次性 `Load` 快照 → trie 取候选匹配项（按 `(规则序号, 匹配项序号)` 有序）→ 第一个实际匹配者胜出 → 合并生效策略 → 按分桶选目标 → O(1) 就绪查询。任一步失败都在结果上明确区分 `NoRoute` / `NoEndpoint`，不回退、不改状态（路由本身是只读操作）。

## 2. 关键语义与取舍

- **段边界**：路径在匹配前先 `?` 截断查询串，再按 `/` 切段，尾斜杠不产生空段（`"/a/"` 与 `"/a"` 同链）。前缀关系逐段比较，因此 `/api` 不覆盖 `/apix`（半个段），但覆盖 `/api/x` 与 `/api` 本身。
- **头条件**：名字在入口统一小写（请求头与配置头都按不区分大小写比较），值始终区分大小写；同名多值时任一值满足。覆盖判定与请求匹配共用同一套"存在 ⊂ 前缀 ⊂ 精确"蕴含方向：精确蕴含同值前缀/存在，长前缀蕴含更短前缀/存在，跨名字不蕴含。
- **遮蔽规则的覆盖定义**：规则 R 被遮蔽当且仅当 R 的**每一个**匹配项都被其**前面任意一条**规则的**某个**匹配项覆盖；覆盖者可以来自不同前序规则（并集覆盖），但不允许用后序规则论证。路径上 nil 条件覆盖一切，精确只覆盖相同精确，前缀按段边界覆盖更深的精确/前缀；头条件上要求"覆盖者的每个头条件都能在被覆盖者中找到一个蕴含它的条件"（AND 随匹配项走，因此条件越少、越宽松的匹配项覆盖力越强）。
- **分桶**：权重 w 恰好拥有声明顺序上 `w*100` 个相邻整数桶，零权重拥有空区间；实现为累加切点比较，边界点（如 1999/2000、9999）归属精确。
- **策略继承**：三个字段分别独立取"规则覆盖 → 服务默认 → 未设置(nil)"；兜底目标不经过任何规则，纯用服务默认。校验作用于**生效后**的策略（含兜底所用默认策略）：`perAttempt ≤ timeout`、`retries*perAttempt ≤ timeout`（仅在相关字段全部已设置时成立不等式）。
- **发布语义**：`sync.Mutex` 串行化发布，读路径无锁（`atomic.Pointer[snapshot]`）。先比版本（版本冲突），再深拷贝入参后校验，全部通过才一次性 `Store` 新快照（含预建 trie）。失败既不 `Store` 也不自增版本；请求期间持有快照指针，物理上不可能观察到"发了一半"的配置。
- **不可变**：`cloneConfig` 对入参做全深拷贝（含 `PathCondition`、策略指针），`Config()` 返回的也是独立深拷贝；调用方改入参或改读取结果都无法影响线上状态。
- **端点与状态**：路由只读；选中子集未注册或 `readyCount==0` 直接 `NoEndpoint`，不改道、不触发任何写。就绪翻转在注册中心的写锁内维护计数。

## 3. 性能设计与可验证证据

朴素实现每请求线性扫描全部规则。本模块在发布期把匹配项挂到路径 trie 的节点上：节点的 `prefix` 列表表示"绑定在此段的前缀条件"，`exact` 列表表示"等于到此节点整条路径的精确条件"。请求沿自身段链下行一次，沿途只收集：

1. 无路径条件的 `matchAll`（每个请求都要考察）；
2. 链上各节点的 `prefix` 匹配项；
3. 终节点的 `exact` 匹配项。

因此**根在无关路径子树上的匹配项永远不会被枚举**，单请求开销只随路径段数与"路径上可能命中"的匹配项数增长，不随服务内无关规则总数线性增长；就绪判断是 `readyCount>0` 的 O(1) 读，不随端点总数增长。

可验证方式（`concurrent_perf_test.go` 中 `BenchmarkRouteUnrelatedRules`）：同一服务放 1000 与 4000 条位于无关深路径的规则，只保留一条与请求路径相关的规则。本机测量（`go test -run=NONE -bench=. -benchtime=200000x ./mesh/`）：

- 1000 条无关规则：约 **383 ns/op**
- 4000 条无关规则：约 **405 ns/op**

规则数 4 倍、耗时仅约 1.06 倍，明确排除线性关系。最坏情况（所有规则都是无路径条件或同一前缀）仍退化为线性，这是"首命中有序规则"语义的固有下界，已在文档中承认。

## 4. 被放弃的方案

- **头条件也建索引（按头名分桶/位图）**：可进一步压缩候选数，但三态蕴含（存在/前缀/精确）使发布期索引更新与遮蔽分析复杂化，而典型规则集的头条件数很小。当前 trie 已满足"不随无关规则总数线性增长"的硬性要求，头条件索引作为未来可叠加优化保留。
- **读侧用 RWMutex 包住配置**：实现简单，但每次路由都拿锁，发布时阻塞全部请求；改用原子快照后读路径零锁，发布的复制成本一次性在发布期承担。
- **端点选择纳入结果（返回具体 Addr）**：需求只要求判定有无就绪端点且 O(1)，返回具体端点会引入负载均衡策略选择，故只返回子集；注册中心仍保留全部端点与就绪翻转能力。
- **配置原地修改 + 序号回滚**：失败回滚容易遗漏字段且无法保证读一致性；深拷贝 + 原子换指针只有一个提交点，失败天然无副作用。
- **遮蔽分析用"构造请求样本反证"**：样本法不完备，无法精确复现；最终采用严格的集合包含判定（路径覆盖 + 头蕴含），并有独立朴素实现做随机交叉验证。

## 5. 并发与串行化论证

- 发布互斥：两把机制分工——`pubMu` 保证"读当前版本→校验→换快照"的原子性，`snap` 原子指针保证读侧无锁且与发布可线性化；每次成功发布严格把版本 +1，并发发布者只有一个能 CAS 成功，其余得到 `VersionConflict`，整体等价于某一串行顺序。
- 路由：进入时取一次快照指针，之后全部基于该不可变快照；端点注册中心用 `RWMutex`，就绪查询只取读锁且不修改任何状态。
- 测试：`-race` 下 4 发布者 × 8 路由者并发，发布者在冲突时重试，并用独立版本台账核对每次成功发布恰好 +1；路由结果只可能命中规则或兜底，不可能出现半成品状态。

## 6. 本地验证方法

```bash
export GOCACHE=/tmp/gocache          # 若默认缓存目录只读
go test ./...                        # 全量
go test -race -count=1 ./...         # 竞态
go test -v -run TestSegmentBoundary ./mesh   # 查看逐操作日志
go test -run=NONE -bench=. -benchtime=200000x ./mesh
go vet ./... && gofmt -l mesh
```

测试日志由 `opLog` 打印每次操作的输入、实际输出与判定依据（`go test -v` 可见）。
