# 能量隔离上锁挂牌（LOTO）工作票系统 — 设计说明

本包 `loto` 实现生产现场的"能量隔离上锁挂牌"工作票全流程：申请、审批、多人多锁隔离、
零能量验证、开工、进出登记、完工、试运行、逾期强制摘除与只读送电判定。

核心安全目标（本实现逐条可验证）：

> **任何设备只要有人可能在其上作业，就物理上不可能被送电。**

该目标由两道相互独立的闸门保证，缺一不可：

1. **锁闸门**：设备依赖的任一隔离点上只要存在任何一把在位锁，该点保持隔离。
   隔离是"锁的全局并集"，与锁属于哪张票无关——多票共享一个隔离点时，
   必须所有票的所有锁都摘除，点才解除隔离。
2. **占用闸门**：只要存在涉及该设备、处于"开工/试运行之外"的占用态票，
   设备不得送电（此时可能正在上锁、验证或处于逾期挂锁状态）。
   开工（working）与试运行（trial）阶段票本身不再通过占用闸门阻断送电
   （该阶段是否真能送电完全由锁闸门决定），但**逾期票在任何阶段都恢复阻断**。

| `trial.go` | 试运行开始/恢复、逾期票主管双人强制摘除 |
| `energize.go` | 只读送电判定与人类可读的"判定依据" |
| `query.go` | 只读快照、审计日志、时钟与计数查询 |

| 文件 | 职责 |

## 状态机

```
pending ──批准生效──▶ effective(已上锁子状态随锁集合增长)
                        │ 全员全部上锁 + 外部人零能量验证
                        ▼
                     verified ──开工(时刻∈[start,end))──▶ working
                        ▲                                     │
                        │ 试运行恢复后重新验证                 ├─ 全员离场 ─▶ completed
                        │                                     ▼
                        └──── Verify ◀── effective ◀── EndTrial ◀── trial
```

说明（关键取舍）：

- **"已上锁/已验证"不是独立 phase，而是 `effective` 上由锁集合推导出的子状态。**
  这样试运行结束后"回到已验证状态"在实现上是回到 `effective`，必须再次 `Verify`
  才能 `StartWork`；这与规格"试运行结束……票回到已验证状态，须再次执行零能量验证
  才可重新开工"完全等价，且避免了 verified 与 locked 的双源真值。
- **逾期是叠加标记 `Overdue`，不改写阶段。** 它由单调时钟在每次"被接受"的
  带时钟操作提交时幂等置位（`at >= end` 且票尚未完成）。
- **被拒绝的操作严格不产生任何效果**：不改任何状态、不推进时钟、不消耗批准名额。
  实现上每个变更操作分两步：`checkClock`/全部前置校验只读进行，全部通过后才调用
  `advanceClock`（标记逾期并提交时钟）再落状态。

## 锁模型（多人多锁）

- 登记在票上的每位作业人员，必须对该票的**全部**隔离点各挂一把**属于自己**的锁
  （点集合是申请时按设备依赖取并集的快照，设备配置之后的变更不影响本票）。
- 唯一键 `(permit, worker, point)`：同一人在同一点对同一票只能一把锁。
- 每把锁有三个布尔位：`TrialRemoved`（试运行暂解，保留记录）、
  `Removed`（已摘除）、`Forced`（曾被主管强制摘除）。
- 全局索引 `lockOwners[point]` 只统计**物理在位**的锁：
  普通摘除、试运行暂解、强制摘除都会从该集合删除对应 `(permit,worker)`；
  重新上锁再放回。
  因此"点是否隔离"就是 `len(lockOwners[point]) > 0`；
  "最后一把锁摘除"就是该集合从非空变空的那一刻，审计会显式记录
  `LAST lock removed: isolation released`。
- 摘锁只能由持锁人本人执行（完工后）；逾期票的锁禁止本人摘除，
  只能由主管双人强制摘除。被强制摘锁的人，`Enter` 前的"本人全部上锁"检查会失败，
  必须先对全部点重新上锁才能再次进场。

## 试运行

- 开工后持票人（申请人）可申请试运行：全员必须已离场；
  本票所有在位锁置 `TrialRemoved` 并从 `lockOwners` 物理移除，但记录保留。
- 试运行期间共享点若还有**其他票**的锁，该点天然仍隔离
  （因为 `lockOwners` 是跨票并集）。审计会列出仍被他票锁压住的点及锁数。
- 结束试运行必须由**原持锁人逐把重新上锁**（在 `trial` 阶段调用 `PlaceLock`，
  仅允许恢复本人暂解的那把）；全部恢复后 `EndTrial` 把票置回 `effective`，
  必须重新 `Verify` 才能再次 `StartWork`。

## 逾期与强制摘除

- 到达或超过 `end` 仍未完成的占用态票自动逾期（幂等，记审计）。
- 逾期后正常完工、试运行、本人摘锁全部关闭。
- 强制摘除条件：非空理由 + 两名**互不相同**的主管（执行与确认），
  且票确为逾期未完成。每次强制摘除写审计（执行人、确认人、理由、剩余锁数）。

## 冲突判定（批准时）

- 时段为左闭右开：`[a0,a1)` 与 `[b0,b1)` 相交当且仅当 `a0 < b1 && b0 < a1`；
  故**首尾相接 `[0,10)`、`[10,20)` 不冲突**。
- 两张占用态票设备集合相交且时段相交才冲突；**双方都是只读观察票时豁免**
  （观察 vs 普通/高风险仍冲突）。
- 冲突只在"使票生效的那次批准"判定；高风险票的第一次批准不生效，因此不做冲突检查。
  冲突拒绝不消耗批准名额。

## 错误次序

所有操作统一遵守（编号小者优先）：

```
InvalidParam > ClockRollback > NotFound > PermissionDenied > StateNotAllowed > Conflict > ConditionNotMet
```

`differential_test.go` 与 `scenario*_test.go` 对该次序有显式断言。
几个容易踩错、本实现刻意固定的次序：

- 批准：状态(pending) → 冲突 → 条件(批准人≠申请人、同一人不重复计数)。
  这保证"被冲突拒绝的批准不消耗名额"，也保证申请人在存在冲突时先得到冲突结论。
- 上锁：点是否属于该票（InvalidParam，紧随票 NotFound 之后）先于人员角色权限。
- 开工：阶段须为 verified；逾期/到达终点是状态错误；起点之前开工才是条件错误。
- 摘锁/强制摘除：锁对象 NotFound（先）→ 人员角色/票内身份权限 → 票状态 → 条件。
- 只读送电查询也校验参数非法与时刻回退，但**不推进时钟、不改逾期标记**。

## 并发正确性

`System` 内部用**单一互斥量**保护全部状态。每个公开操作在锁内完成
"校验→提交时钟→落状态/读快照"全过程。因此：

- 任意并发操作的历史都等价于某个按互斥量获取顺序排列的串行历史（互斥串行化）；
- 配合所有时刻单调约束，该串行历史是合法历史，不会出现读到半更新状态；
- 只读查询与写操作也共用同一把锁，快照一致。

`go test -race` 下的 `concurrent_test.go` 验证了并发上锁 + 并发只读送电无数据竞争、
最终状态自洽。

## 关键复杂度与"判定不随历史增长"的证明

设：

- `H` = 系统中历史票总数（含已完成）；
- `A(d)` = 当前**占用态**且涉及设备 `d` 的票数（`activeByDevice[d]` 的大小）；
- `L(p)` = 隔离点 `p` 上当前在位锁数（`lockOwners[p]` 的大小）。

维护的两个索引只包含"活跃/在位"成员，票一生成生效即加入、一完成即摘除；
锁一物理挂上即加入、一摘除（普通/暂解/强制）即摘除：

- **送电判定** `CanEnergize(d)` 只遍历 `d` 的依赖点（查 `lockOwners`）
  与 `activeByDevice[d]`。复杂度
  `O(|points(d)| + Σ_{p∈points(d)} L(p) + A(d))`，**完全不含 H**。
- **冲突判定**（使票生效的批准）只遍历候选票设备上的 `activeByDevice` 成员，
  复杂度 `O(Σ_{d∈devices(t)} A(d) · |devices(t)|)`，**完全不含 H**。
  朴素参考模型则是 `O(H·|devices|)`，随历史线性增长——这正是对照的意义。

经验证据（本机 `go test -run '^$' -bench BenchmarkScaleCompare -benchtime=3000x`，
活跃票/锁数固定，仅历史票从 5,000 增到 50,000）：

```
history=5000/CanEnergize       ~1.9 µs/op
history=50000/CanEnergize      ~1.0 µs/op
history=5000/ApproveConflict   ~0.66 µs/op
history=50000/ApproveConflict  ~1.2 µs/op
```

历史票扩大 10 倍，两类判定的 ns/op 基本持平（噪声范围内），与上面的不含 H 分析一致。
`TestScaleFlatness` 用 1k/10k 两档固定迭代做自动断言（比值 < 3 的宽松阈值，防 CI 抖动）。

## 被放弃 / 未采用的方案

1. **每点一把锁、锁上挂票标签的单锁模型**：放弃。无法表达"每位作业人员各挂一把
   属于自己的锁"与"只能本人摘自己的锁"，也无法支撑试运行时按人暂解/恢复。
   现模型的最小单元是 `(permit,worker,point)`。
2. **用独立 phase 表示"已上锁/已验证/试运行后待验证"**：放弃。多阶段会产生
   非法组合与双源真值；改为 `effective` + 锁集合推导 + `Overdue` 叠加标记，
   试运行恢复后强制再走一次 `Verify`。
3. **后台定时器/扫描线程自动置逾期**：放弃。系统是离散事件、纯函数式状态机，
   引入后台线程会破坏并发可串行性与确定性。逾期在"被接受操作提交时钟"时惰性、
   幂等标记，语义等价且更易测试。
4. **细粒度分片锁以提升并发**：放弃。正确性优先；单互斥量给出最强、最易论证的
   串行等价性，且操作均为内存 map 更新，吞吐足够。需要横向扩展时可在其外部分片。
5. **送电判定允许回退时刻的只读"历史视图"**：放弃。规格要求带时刻操作单调，
   只读判定也遵守回退检查（但不推进时钟），避免用旧时刻读到新状态造成歧义。

## 本地验证方法

```bash
# 环境（本机 Go 在 /usr/local/go/bin）
export PATH=$PATH:/usr/local/go/bin GOCACHE=/tmp/gocache GOPATH=/tmp/gopath

# 全量测试（含 400 条随机差分序列）
go test ./...

# 竞态 + 并发串行化
go test -race ./loto

# 差分测试日志（输入 IN / 输出 OUT / 送电判定依据 WHY），输出到包目录 testlogs/
go test ./loto -run TestDifferentialRandom -loto-log=testlogs/differential.log

# 历史票两档规模对照
go test ./loto -run '^$' -bench BenchmarkScaleCompare -benchtime=3000x
go test ./loto -run TestScaleFlatness -v

go vet ./loto && gofmt -l .
```

差分日志格式：

```
[123] IN  Approve(tk7 by=apvA at=41)
      OUT real=Conflict naive=Conflict
[124] IN  CanEnergize(devB at=41)
      OUT real=OK naive=OK | energize real=false naive=false
      WHY BLOCK point=p2 holds 3 lock(s) ... -> isolated | BLOCK permit=tk3 ...
```

一旦真实系统与朴素模型在**错误码、送电布尔结论、逐票状态/在场/在位锁/批准数**
任一维度不一致，测试立即失败并打印种子（seed）与分歧步，可据日志完整重放。
