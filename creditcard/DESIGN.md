# 信用卡账户出账 / 计息 / 还款分配 / 滞纳金系统 — 设计说明

包路径：`ontology/creditcard`。金额为非负整数最小货币单位（`int64`），
时间为整数天，每个操作携带 `now`。

## 模块划分

| 文件 | 职责 |
| --- | --- |
| `types.go` | 公开类型：`Category`（取现/分期/购物）、`Params`、`Bill`、`PaymentRecord`、哨兵错误 |
| `account.go` | 单账户核心状态机：增量计息累积、出账、还款分配、溢缴款（不感知并发） |
| `service.go` | 多账户门面：全局时钟、错误优先级、`sync.RWMutex` 串行化、只读查询 |
| `naive_test.go` | 独立朴素参考模型（逐日重放事件日志），仅供对照测试 |
| 其余 `*_test.go` | 场景边界测试、随机对照、并发守恒、复杂度与基准 |

`account` 不自己加锁；`Service` 用一把读写锁把所有写操作串行化，
因此"并发调用等价于某个串行顺序"由互斥锁直接保证，查询走读锁且
返回拷贝，不修改状态。

## 核心机制：增量计息

规则要求"某日的计息基数 = 该日开始时的余额 × 年化利率（基点）"，
自上一出账日次日至本次出账日（含）逐日累计。直接逐日循环会让
出账开销随间隔天数增长，因此采用**增量累积器**：

- 每类余额维护 `accBase`（`big.Int`，累计 `Σ 余额×利率`）与 `rem`
  （上期结转零头，`< 10000×365`）。
- 不变式：`accrualDay == lastOpDay + 1`，即"下一个尚未累计的天"。
- 任何被接受的操作先调用 `accrue(now)`：若 `now > lastOpDay`，则
  `accrualDay..now` 这些天的起始余额都等于当前余额（期间无操作、
  当日操作尚未生效），一次性累加 `balance × rate × 天数`，
  每操作 O(1)。
- 出账时：`interest = (accBase + rem) / (10000×365)` 向下取整，
  新零头写回 `rem`，`accBase` 清零，利息加入对应余额。

由于不变式保证同一自然日内第一笔操作就已把"当日起始余额"计入基数，
当天后续操作（含出账）不会重复或错误累计——这正是"当天操作不影响
当天基数"语义的实现方式。

## 关键取舍

1. **全局时钟而非每账户时钟**。错误优先级要求"时钟回退 > 账户不存在"，
   只有服务级时钟才能在账户不存在时仍判定回退。代价是并发下不同账户
   的操作可能因时钟竞争被拒，但语义明确、重放确定。
2. **`big.Int` 累积基数**。`余额×利率×天数` 在极端输入下溢出 `int64`；
   累积器每账期清零，大小只与本账期相关，开销可忽略。
3. **免息期购物类基数丢弃、零头保留**。购物类被免息时，本账期累计
   基数不再转为利息（免息的意义），但"此前结转的零头"按"不得丢失"
   的要求保留到下一个计息账期。这是对规则中未明确之处的选定解释，
   朴素模型采用同一解释以便对照。
4. **最低还款额只看最近一张账单**。旧账单未付足的最低还款额已转化为
   滞纳金计入新账单，不再参与后续还款的"最低部分"判定。
5. **最低还款额钳制顺序**：先 `max(计算值, M0)` 再 `min(_, 账单总额)`；
   总额为零时为 0。
6. **溢缴款不计息、不计入账单总额**，只在消费入账时优先抵扣。
7. **还款中"最低部分"未冲减完的部分流入超出部分**继续按利率序冲减，
   最终剩余记溢缴款——与分别处理结果一致，代码更简单。

## 被放弃的方案

- **逐日快照 / 逐日循环计息**：出账开销随间隔天数增长，违反复杂度
  要求（朴素模型故意保留此写法以对照正确性）。
- **查询时懒结算利息**：查询不得修改状态，且"任意时刻余额可复现"
  要求余额只由已接受操作决定，懒结算会让语义依赖查询时点。
- **定点 `int64` 累计基数**：溢出风险无法在不限制输入的前提下排除。
- **每账户独立时钟**：使"时钟回退 > 账户不存在"的优先级无从体现。

## 出账复杂度证明（可验证）

`account.bill` 只访问固定大小的状态：3 个累积器、3 个零头、最近一张
账单的 4 个字段；不遍历历史账单与历史交易。历史数据仅以追加方式
写入（摊还 O(1)）。验证方式：

- `TestBillCostIndependentOfHistory`：5 个账期与 2000 个账期的账户，
  单次出账分配次数相同（实测均为 10.00 allocs/op）。
- `BenchmarkBillAfterLongHistory`：1 万个历史账期、3 万笔历史交易后，
  单次出账约 673 ns（arm64），与无历史时持平。

## 本地验证方法

```bash
export PATH=$PATH:/usr/local/go/bin
go test ./creditcard/                 # 全部单元与对照测试
go test -race -count=3 ./creditcard/  # 竞态 + 重复运行
go test -v -run TestDifferentialRandom ./creditcard/  # 查看逐操作日志
go test -run xxx -bench . ./creditcard/               # 复杂度基准
gofmt -l . && go vet ./...
```

测试覆盖：到期日当天 vs 次日还款、还款恰等最低还款额 vs 差一、
全额恰等账单总额、免息只看上一张账单、利息零头跨账期结转、
单笔还款跨最低部分与超出部分、溢缴款抵扣消费、被拒绝操作不留痕
（含错误优先级）、重放确定性、出账复杂度、并发守恒不变量
（余额合计 − 溢缴款 = 消费 + 利息 + 滞纳金 − 还款），以及 60 个
随机种子 × 150 步操作与朴素模型的全状态对照（日志打印每步输入、
输出与判定依据）。
