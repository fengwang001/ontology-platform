# refupdate 设计说明

1. 模块划分：`ref.go`（名字模型/词法/分段前缀）、`graph.go`（只增提交图与后代查询）、
   `rules.go`（保护规则与段 trie）、`store.go`（并发引用表、审计、对外类型）、
   `txn.go`（整批裁决与原子提交），外加包文档与两个测试文件，共 8 个 `.go`。
2. 并发模型：`Store` 单一互斥锁覆盖「读状态 → 逐条裁决 → 批内检查 → 写引用 → 追加审计」
   全过程，推送严格串行化；读者在同一把锁上取快照，只能看到某批完整提交后的状态。
   放弃了分片锁/STM 方案：引用更新彼此可能经前缀冲突耦合，分片锁仍需全局栅栏，复杂度无收益。
3. 规则快照：规则只在持锁裁决时读取，`SetRules` 抢同一把锁原子替换整个 trie，
   裁决中途不可能观察到规则变更。放弃了版本号+RCU：单锁已提供同一保证。
4. 快进判定：从新值沿父边 DFS（按查询代际打标，免每次分配 visited），只遍历新值的祖先锥；
   `Graph.CommitsVisited` 暴露实际检查的提交数，测试证明加入 1 万个无关提交不改变该计数。
   放弃了预计算「generation/拓扑序号」：合并提交（多父）没有单一序号，且预计算违背只增模型下
   新提交即时可达的简单语义。
5. 规则匹配：模式按 `/` 切段建成 trie，`*` 为单段通配子节点；匹配沿名字段下行，
   每段至多访问「字面 + 通配」两个节点，探测数为 O(名字段数)。命中规则的四种开关与名单取并集。
   `ruleNode.probes` 计数被测试用来证明规则数从 10 增到 10000 时探测数不变。
   放弃了线性扫描与双段通配 `**`：前者 O(规则数) 不达标，后者使语义与代价都复杂化。
6. 裁决顺序严格按题设优先级短路；批内检查（重复引用、标签同批删建、最终态前缀冲突）
   只对逐条通过的指令运行，一旦有冲突则所有通过项带 `batch-conflict`；
   仅因他项被拒的通过项带 `skipped-other-rejected`。前缀冲突按「最终态」判定，
   故同批删父建子（目录重命名式重构）允许。放弃了按初始态判定（会错误拒绝合法重构）。
7. 拒绝路径在触碰引用表和审计切片前直接返回：引用、序号、审计均零变更；
   成功路径先全部写入引用再追加一条含全部前后值的审计，序号自增无空洞。
8. 标签：存在即不可更新（强制也不行），只能先删后建；同批删建在逐条阶段即以
   旧值不匹配/批内重复暴露，批检查另有显式标签删建判定兜底。
9. 本地验证：`go test -race -v ./refupdate`（逐用例打印输入、实际输出、判定依据）；
   `go test -run 'Cost' -v ./refupdate` 查看两条性能不变量；`go vet ./... && gofmt -l .`。
   随机差分测试（400 轮随机 DAG/规则/指令批）与独立朴素模型逐条比对裁决、原因、最终引用与审计序号。
