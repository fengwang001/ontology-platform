# 配送异常上报与无法送达处置 — 设计说明

1. 模块划分：`types.go`（状态/枚举/快照）、`errors.go`（稳定可程序化区分的 `ErrorCode`，编号按拒绝次序）、`clock.go`（全局单调时钟）、`state.go`（订单/异常可变状态与并发入口）、`disposition.go`（到期转化、无法送达处置、结算、非变异时刻视图）、`operations.go`（14 个操作的校验与落地）、`naive.go`（独立朴素对照模型）。
2. 时间模型：所有时刻为整数秒；`clock.maxT` 只在操作被接受后推进，拒绝绝不推进时钟，保证“被拒绝操作不改状态、计时记录与时钟”。
3. 到期转化是时刻的纯函数：`effectiveStatus/hasOpenException` 只做投影不改存储；操作先读“截至 t 的视图”校验，确认接受后才由 `applyTimeEffects` 惰性落地。窗口右端点一律不包含（`t >= end` 即到期/超窗）。
4. 关键取舍：端点操作（提交纠正、商家确认）在恰为右端点时报窗口类错误，并把该时刻作为已接受的时间观察落地转化；之后同订单再操作即按终态/进行中异常报错。这统一了“视为已转化”和“窗口错误优先于距离、状态类错误优先于窗口错误”两条要求。
5. 联系不上判定只读当前异常的 `cnt` 与 `start`，不保存也不扫描任何联络序列，故判定为 O(1)；窗口到期只看该订单自身的 `windowEnd`，不遍历平台异常表，同样 O(1)。联络间隔仅保留 `lastContactT`。
6. 用户回应关闭异常、保留历史但新异常计数从零；拒收成立即无法送达；处置补偿由订单级 `compPaid` 布尔保证每单至多一次，在进入无法送达时统一发放。
7. 责任归属：联系不上/拒收/地址未纠正归用户；退回超窗未确认归商家（在到期转化时覆盖原用户责任）。
8. 并发：单一平台互斥锁串行化每个操作，结果等价于某串行序；同订单至多一个进行中异常、至多一次补偿由状态+锁共同保证。
9. 被放弃的方案：(a) 后台定时器/堆扫描——会引入额外线程与不确定性，且到期本就是时刻函数；(b) 保存联络全量列表用于判定——无法满足 O(1)；(c) 拒绝时立即落地转化——会让拒绝改变后续状态，违反“拒绝无副作用”，改为非变异视图。
10. 对照模型 `NaiveModel` 独立实现：保存被接受事件日志，每次重放重建订单状态；事件在其自身时刻先 mature 再折叠。差分测试对两模型注入相同随机序列，逐步比对错误码与完整快照。
11. 本地验证：`go test -race ./...`；`go test -bench=. -run=^$ ./delivery/`（predicate_100 与 predicate_100000 均约 0.5ns/op，平台规模基准与异常总数无关）；`go test -run TestRandomDifferential -v` 打印每步输入、输出与判定依据。
