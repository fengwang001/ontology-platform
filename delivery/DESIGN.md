# 设计说明（配送异常上报与无法送达处置）

1. 时刻为整数秒，系统维护已接受操作最大时刻；回退操作在存在性检查之后被拒，且绝不推进时钟、不改状态。
2. 模块：types/errors（值与错误码）、system（时钟/订单/惰性到期）、exceptions（三类状态机）、settlement（处置与补偿）、naive（事件溯源对照）。
3. 关键取舍：到期不做后台扫描，改为“惰性、按订单、时刻的函数”；任何不早于窗口右端点的操作或查询先完成该订单转化。
4. 退回确认窗口只在查询与商家确认时判定，骑手送回本身不提前结算旧窗口，避免送回动作被历史窗口误拒。
5. 联系不上判定只读“起点、联络计数、上次联络时刻”三个标量，明细仅留审计；复杂度 O(1)，不随历史联络总数增长。
6. 窗口到期只访问该订单自身字段，O(1)，不随平台异常总数增长；以基准 BenchmarkJudgeConditionCheck / BenchmarkSettleSingleOrder 证明。
7. 补偿在进入无法送达时发放且以 CompPaid 幂等；就地处理立即终态，退回则进入退回途中。
8. 拒收上报成立即无法送达；证据有效期使用 evidenceAt >= at-valid（恰等允许）。
9. 纠正使用曼哈顿距离，距离恰等允许；纠正右端点 at >= deadline 一律拒绝，不先触发转化。
10. 拒绝次序固定：参数→时钟→不存在→状态类（含类型不匹配/活动校验的细分顺序）→证据→联络过密→条件→窗口→距离；每操作只报首个错误。
11. 并发：单一互斥锁串行化全部变更，回应与判定同刻竞争只有一个生效；-race 下反复验证。
12. 放弃方案一：每订单独立锁。虽可提高并行度，但跨订单到期与全局时钟的组合正确性更难论证，且本系统吞吐并非瓶颈。
13. 放弃方案二：定时器/后台协程主动到期。引入真实墙钟与副作用，破坏“相同序列重放结果一致”，且需扫描全部异常，违背 O(1) 要求。
14. 放弃方案三：判定时遍历联络记录计数。直观但复杂度随历史增长，改为维护计数标量。
15. 朴素对照模型是算法独立的事件溯源实现：追加事件日志为唯一事实，重放时按事件时刻完成地址到期、按查询时刻完成确认窗口到期。
16. 差分测试对两个实现施加相同随机序列（5 个种子 ×1500 步、允许同刻操作），逐步比对错误码、异常 ID 与全量快照。
17. 本地验证：
18.   go test ./...
19.   go test -race -v ./delivery/
20.   go test ./delivery/ -run TestDifferentialAgainstNaive -v   # 打印每步输入/输出/依据
21.   go test ./delivery/ -bench 'BenchmarkJudgeConditionCheck|BenchmarkSettleSingleOrder' -run '^$'
22.   go vet ./... && gofmt -l delivery
23. 责任归属：联系不上/拒收/地址未纠正归用户；退回未确认在确认窗口到期时改写为商家，骑手仍获补偿。
24. 用户回应关闭异常但保留历史联络备查；新一次上报是全新异常对象，计数与间隔从零开始。
