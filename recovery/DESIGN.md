# 快照损坏修复与动作重放原子性协调器 — 设计说明

## 1. 问题与语义

协调器读入一份**快照**（若干对象在快照时刻的状态记录，逐条带校验）和一份
**动作日志**（快照之后发生的动作，每条声明涉及对象集合与逐对象变更，整条带
校验），产出**对象级**修复报告。

四类事实必须严格区分：

| 事实 | 表达 |
| --- | --- |
| 对象在快照时刻不存在（墓碑） | 快照记录完好，`exists=false`，来源仍为 `snapshot` |
| 对象快照记录损坏、时刻状态不可读 | `SnapshotUnreadable=true`，来源初始为 `unknown` |
| 对象经后续动作重建 | 来源 `rebuilt`，并记录**首个提供起点的动作序号** `AnchorSeq` |
| 对象不在快照与日志覆盖范围内 | 请求级错误 `object_out_of_coverage` |

重建**不得回溯**：对象只能从“第一条成功应用且为它提供起点锚点（`Start`）的
动作”开始恢复；该动作之前的状态永远判为不可读。

## 2. 动作模型与原子性

一条动作对每个涉及对象给出：

- `Start *State`：可选的**起点锚点**。对象此前状态未知时，以该锚点作为本动作
  之前的状态；为 `nil` 表示本动作不提供起点，要求对象此前必须已知。
- `Change State`：本动作产生的变更。组合规则 `Apply(prev, change)=change`
  采用覆盖语义（协调器不解释状态本体语义，替换为业务合并函数即可复用）。

判定规则（全部对象同进同出）：

1. 记录校验失败 ⇒ `corrupt`，**整条不可采信**，不从中抢救任何字段；
2. 记录完整但集合中存在“此前未知 **且** 本动作未给锚点”的对象 ⇒ `blocked`，
   对集合中**所有**对象（包括本来已知的对象）整体放弃；
3. 否则 `applied`：未知对象以锚点起步、来源记 `rebuilt`；已知对象沿链推进，
   来源沿用其链起点（`snapshot` 不降级，`rebuilt` 不升级）。

关键性质：`blocked` 不改变任何对象的已知性，因此“连续多个动作中间夹损坏或
被放弃记录”的传播是自然的——后续动作看到的已知对象集合与从未插入该记录时
完全一致（见 `TestCorruptRecordBetweenActionsPropagation`）。

## 3. 关键取舍与被放弃的方案

1. **快照损坏按“对象头/对象负载”两级定界，而不是给整个文件一个总校验和。**
   对象帧 = `头部{id} + 头部CRC + 负载 + 负载CRC`。负载损坏可归因到具体对象
   （对象级不可读）；只有对象头自身损坏这种无法归因的情形才上升为硬错误。
   放弃的方案：整文件单一校验和——任何 1 bit 翻转都会丢失对象级定位能力。

2. **动作帧不做字段级部分采信，只用整帧 CRC32-C。** 损坏 ⇒ 整条 `corrupt`，
   从编码层保证“不得只采信部分可解析字段”。放弃的方案：逐字段 CRC——会诱导
   “半个动作生效”，直接违反原子性。

3. **起点锚点显式建模为动作的 `Start` 字段**，而不是从 `Change` 反推。
   放弃的方案：“看到未知对象就把 Change 当起点”——无法区分“无锚点动作”，
   也就无法实现部分对象未知时的整体放弃。

4. **版本衔接只做一种判定：日志起点必须恰好等于快照基线版本**
   （`logStart == snapshotBase`）。放弃的方案：容忍前缀缺口/自动跳过——会把
   “不衔接”静默降级成“状态缺失”，使错误类别混报。

5. **修复与追加共用一把 `sync.RWMutex`，且恢复结果在加载/追加时一次性物化。**
   放弃的方案：读不加锁或逐对象两阶段加锁——会让新动作观察到部分恢复的中间
   状态。当前方案下，`Append` 返回之后的任何读都看到该动作对全部涉及对象的
   最终效果，不存在部分恢复窗口；可观察结果等价于某个全局串行顺序。

6. **请求拒绝优先级在编码层固定：超范围 > 版本不衔接。** 构造期只记录
   `version_mismatch` 状态且**不重放**（防止不衔接的日志被任何状态采信）；
   每次修复/查询先做覆盖范围检查，首个未覆盖对象返回
   `object_out_of_coverage`；全部命中后才返回 `version_mismatch`；两者都
   不命中时逐对象报告，正常报告**不视为错误**。向不衔接的协调器追加动作
   同样被拒绝。

## 4. 规模无关的来源定位（可验证）

协调器增量维护每对象一条投影条目：

```
known[object] = {exists, state, source, anchorSeq}
```

加载与每次追加时，只有“真正应用到该对象”的动作会覆写该条目一次。因此：

- `Lookup(object)` 只执行一次 map 读取，**检查的动作记录数为 0**，
  与日志总长度 N 无关；时间 O(1)，空间 O(M)（M 为覆盖对象数）。
- 构造/追加成本保持 O(涉及对象数)，没有倒排链、没有回溯扫描。

可验证证据不是口头断言，而是测试 `TestLookupScaleIndependent`：分别在
2,000 条与 20,000 条动作日志下用 `testing.Benchmark` 测量单次 `Lookup`，
断言 10 倍日志长度的 ns/op 之比 ≤ 3 且 **0 次额外分配**（实测比值约 1.0，
0 allocs/op，数值打印在测试日志中）。

## 5. 错误类别（彼此不混报）

| Kind | 触发位置 | 粒度 |
| --- | --- | --- |
| `snapshot_record_corrupt` | 快照解码 | 对象级（可归因）或无法归因的硬错误 |
| `action_record_corrupt` | 动作解码/追加 | 记录全局序号 |
| `version_mismatch` | 构造期 | 请求级 |
| `object_out_of_coverage` | 修复/查询 | 对象级 |

损坏但可继续处理的记录进入报告（`SnapshotCorruptions`、`Judgments`），
而不是作为 Go error 抛出；只有无法继续定界/无法建立恢复基线的情形才返回
error。

## 6. 判定日志

`DecisionLogger` 接口接收 `{stage, input, output, reason}` 四元组，覆盖：
快照逐对象加载、版本衔接检查、动作逐条判定（corrupt/blocked/applied 及
阻塞对象）、逐对象请求结论及其依据。`TextLogger` 打印形如：

```
[decision] stage=action_judge
  input : record_index=0 seq=1 objects=[a,b]
  output: blocked
  reason: atomic precondition failed for [b]; whole action discarded ...
```

## 7. 本地验证方法

```bash
go test -race -v ./...
go test -run TestLookupScaleIndependent -v ./recovery   # 查看规模无关数据
go test -run TestRandomDifferentialVsNaive -v ./recovery # 朴素模型对拍
go vet ./... && gofmt -l .
```

对拍模型 `NaiveReplay` 是独立实现：不维护投影，逐条线性扫描判定，只用于测试。
随机构造器以固定种子生成约 1/3 快照记录损坏、1/4 动作帧损坏、随机动作集合
（1–3 个对象）与随机锚点，共 300 轮，逐对象比对状态/来源/锚点，并逐记录比对
corrupt/blocked/applied 判定序列。

## 8. 已知边界

- 损坏若恰好破坏动作帧的**长度前缀**导致帧流失步，解码返回定界硬错误
  （无法再与后续帧可靠对齐）；帧内任何负载/CRC 损坏都仍是记录级 `corrupt`。
- 状态组合采用覆盖语义；接入真实本体状态时以业务合并函数替换 `Apply`。
