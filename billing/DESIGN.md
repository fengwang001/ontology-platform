# 带宽采样计费结算器 — 设计说明

## 1. 问题回顾

周期含 `N`（1..10^6）个固定 300 秒槽位。槽位可收到带版本号的
入向/出向速率采样，提交可能乱序、重复或被更正：

- 有效值 = max(入向, 出向)；
- 有效槽位 K 个，丢弃 `d = floor(0.05 * K)` 个最大有效值后，
  剩余最大值为计费速率；K=0 时无定义；
- 撤回只移除“当前版本恰好相等”的采样，但该槽位见过的最高版本号
  永久保留为再提交门槛；
- 结算校验缺失比例 `missing*10000 > tolerance*N`，通过后封存周期，
  重复结算返回首次结果；
- 提交/查询开销不得随已收到采样数线性增长；并发等价于某串行顺序。

## 2. 数据结构与关键取舍

### 2.1 槽位状态：定长数组 O(1)

`slots []slotState` 按槽位下标索引，每项保存：

- `has / version / inbound / outbound`：当前采样；
- `highestVersion`：该槽位**见过的最高版本**，撤回不清空。

空间 O(N)，所有按槽位的判定（越界、覆盖、幂等、冲突、过期、撤回）
都是一次数组访问。

### 2.2 有效值集合：带份数计数的随机化 treap（顺序统计多重集）

提交/撤回/查询的性能瓶颈是“丢弃前 5% 后的最大值”，本质是动态多重集
上的第 `d+1` 大顺序统计。方案对比：

| 方案 | 提交/撤回 | 查询 | 取舍 |
|---|---|---|---|
| 每次全量排序 | O(1) 写 | O(K log K) | 被放弃：查询随 K 线性以上增长 |
| 有序切片 + 二分插入 | O(K) 移动 | O(1) | 被放弃：写入随 K 线性增长 |
| 堆 | O(log K) | 难支持“丢前 5% 后取最大” | 被放弃：单堆不直接支持丢弃任意个并列最大值 |
| 定长 10^12+1 桶 | O(1) | 值域相关 | 被放弃：值域 10^12，内存不可接受 |
| 线段树/动态开点 | O(log V) | O(log V) | 可行但实现与常数更重 |
| **随机 treap（份数计数）** | **期望 O(log K)** | **期望 O(log K)** | **采用** |

treap 节点键为有效值，`cnt` 为该值重复份数，`sub` 为子树份数和。
并列值只增加 `cnt`，因此“并列各自占位”由份数自然表达：第 r 大查询
按子树份数下降，与“把每个槽位展开成独立元素”完全等价。

节点优先级不由全局随机源生成（避免额外锁与不可复现的种子），而由
原子自增计数器经 splitmix64 混合得到：无锁、跨平台、跨运行可复现。
这是“关键取舍”：用确定性的伪随机优先级换取可验证的树结构，同时
保留随机 treap 的期望高度性质（输入顺序与优先级序列解耦）。

提交在 treap 上是“删旧有效值 + 插新有效值”两次期望 O(log K)；
查询是一次 kth-largest，也是期望 O(log K)，均不遍历 K。

### 2.3 并发：单一互斥锁 + 不可变快照

所有读写方法在入口获取同一把 `sync.Mutex`。临界区只做常数次数组访问
与 treap 指针操作，故串行化等价性直接成立（任何并发执行的可观察结果
都等价于某次锁获取顺序），且锁内无 I/O、无回调，不存在死锁路径。
查询与概览返回值拷贝，调用方无需持锁即可读取。

被放弃的方案：读写锁（写操作只改一棵树，拆分锁域反而增加复核成本）、
无锁 treap（GC/ABA 复杂度远超需求）。

### 2.4 版本语义的三条短路

提交时对槽位 `cur` 按序判定：

1. `s.Version <= cur.highestVersion` 时：
   - 当前有采样且版本、入向、出向全相等 → 幂等成功，状态不变；
   - 当前有采样且版本相等但内容不同 → `version_conflict`；
   - 其余（含撤回后重发旧版本）→ `stale_sample`；
2. 版本严格大于历史最高 → 接受；覆盖前先从 treap 删除旧有效值。

撤回后槽位 `has=false`、负载清零，但 `highestVersion` 保留；
因此旧版本再提交一定走第 1 条的过期分支，版本门槛跨撤回存活。

### 2.5 错误优先级的落实

需求给定的优先级为：

```
参数非法 > 已结算 > 版本冲突/过期采样/版本不符 > 不存在 > 无采样/数据不足
```

实现方式是在每个方法里按此顺序早返回，且所有拒绝分支都发生在任何
状态修改之前：

- 参数校验不触碰状态；
- 封存标志在参数合法后才检查；
- 提交的冲突/过期、撤回的版本不符都在 treap 增删之前判定；
- 撤回在槽位为空时只能报不存在（空槽位没有“当前版本”可比），
  非空槽位版本不等报版本不符；`TestRejectPriority` 固定这一解释；
- 结算先判数据不足（不封存、可补齐重试），通过后若 K=0 报无采样。

刻意选择：结算时**先做缺失比例检查，再取计费速率**。因此“无任何采样
且容忍不足”报数据不足，“无采样但容忍 100%”才报无采样；数据不足
永远不会被计费动作消耗掉，补齐后可重试。

### 2.6 结算封存与重复返回

首次成功结算把完整结果（速率、基数、有效/缺失数）冻结在
`settlement`，并置 `settled=true`。后续 `Settle` 即使参数不同，也在
参数合法性检查通过后返回冻结结果的拷贝并置 `Repeated=true`。
参数仍非法时优先报参数非法（重复结算成功本身不是错误，不占用
“已结算”错误码）。

## 3. 整数与溢出

- 速率字段全部为 `int64`；
- 缺失比例用整数交叉相乘：`int64(missing)*10000 > int64(tol)*int64(N)`，
  最大约 10^10，远小于 int64 上限，无浮点误差；
- 丢弃数 `K*5/100` 用整数除法即“向下取整”。

## 4. 本地验证方法

所有命令在仓库根目录执行（若 Go 不在 PATH，先
`export PATH=$PATH:/usr/local/go/bin`；受沙箱限制可加
`GOCACHE=/tmp/go-cache GOPATH=/tmp/go-path`）：

```bash
# 全量测试（含 1200 组随机差分、并发与竞态检测）
go test -race ./billing

# 仅快速子集（跳过差分测试）
go test -short ./billing

# 复杂度证据：treap 查询/提交基准 + 朴素查询对照
go test ./billing -run '^$' -bench 'BenchmarkQuery|BenchmarkSubmit' -benchtime=100x

# 结构证据：100 万键树高与 4*log2(K) 上界
go test ./billing -run TestTreapShape -v

# 静态检查与格式
go vet ./billing
gofmt -l billing
```

实测（本机 arm64）：查询 `K=1000→1000000` 约 `30ns→84ns`（零分配），
朴素排序对照 `4.0µs→4.8ms`；100 万键 treap 高度 53，
不超过 `4*log2(10^6)≈80` 的宽松上界。数字与“期望 O(log K)、不随 K
线性增长”一致；treap 优先级确定性派生，任何机器重跑得到相同树高。

### 4.1 测试清单

- `TestDiscardJump`：K=19/20/39/40 的丢弃数 0/1/1/2 跳变；
- `TestTiesOccupySlots`：全并列、双最大值、单最大值分别占位；
- `TestHigherVersionLowersRate`：高版本覆盖使计费速率下降；
- `TestWithdrawKeepsVersionFloor`：撤回回缺失且版本门槛保留；
- `TestToleranceBoundary`：N=10000、容忍 1% 的恰边界与差一槽位；
- `TestInboundOutboundMax`：入向/出向互为较大；
- `TestSettleRepeatsAndSeals`：重复结算以首次为准、封存后拒绝写；
- `TestIdempotentAndConflict`：幂等重复与同版本冲突；
- `TestInvalidArguments` / `TestRejectPriority` / `TestNoSamples`；
- `TestRandomDifferential`：1200 组确定性随机操作序列，逐步与
  `NaiveBiller` 对照（速率、结算、概览、错误码全等），
  日志 `/tmp/billing-differential.log` 打印每步输入、双方输出与判定依据；
- `TestConcurrentSerializable`：8 写 4 读并发 + `-race`，
  终态与朴素串行重放一致，日志 `/tmp/billing-concurrent.log`。

## 5. 被放弃/未采用方案汇总

- 以“时间戳”定位槽位：需求以槽位下标通信，起始时刻仅作元信息保存，
  不参与判定，避免时钟域问题；
- 全局 RNG treap：改用计数器 + splitmix64，可复现且无锁；
- RWMutex / 无锁结构：单锁临界区极短，可验证性优先；
- 在 Biller 内缓存计费速率：会让撤回/覆盖产生额外失效分支，
  treap 顺序统计已足够快，不缓存即无陈旧风险。
