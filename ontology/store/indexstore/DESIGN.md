# 带唯一二级索引的主表存储与索引追赶恢复 — 设计说明

包路径：`ontology/ontology/store/indexstore`

## 1. 问题与不变量

- 主表按主键存行，每行有可空二级键；WAL 从 LSN=1 连续追加，记录
  upsert/delete 及变更前二级键。
- 主表与 WAL **同步提交**，崩溃后与日志末尾一致；二级索引与水位
  **独立持久化**，允许落后。
- 水位 `watermark`：`LSN <= watermark` 的效果必然已在索引中；水位
  允许落后于索引实际吸收位置，但**绝不超前**。
- 追赶完成后的索引，与对主表当前内容做完整重建的结果**逐项相同**，
  且该性质对任意初始索引状态（停在水位处、已含水位之后任意长前缀、
  介于之间）都成立，并可在任意点崩溃后重复追赶。

## 2. 模块划分

| 文件 | 职责 |
| --- | --- |
| `types.go` | 行/日志/错误码/差异/操作记录等纯类型与错误优先级 |
| `disk.go` | 确定性、可注入崩溃的持久层：暂存改动 + 单提交步骤原子可见；WAL 编解码 |
| `wal.go` | 只追加日志：加载、与主表改动同步骤追加 |
| `table.go` | 主表内存映射 + 与 WAL 同步骤提交；维护 `secOwners`（最新二级键属主） |
| `index.go` | 索引条目、`applied`/`watermark`、幂等归并 `applyOne`、完整重建、逐项自检 |
| `store.go` | 一把锁串行化全部对外操作；写入判定、分批追赶、重启加载与不变量校验 |
| `crash.go` | 把注入崩溃转成可重启的 `Run` 辅助 |

## 3. 关键取舍

### 3.1 唯一性判定只看主表，O(1)

主表侧额外维护 `secOwners: 非空二级键 -> 主键`，与主表在同一提交步骤
更新。写入时若 `secOwners[newSec]` 存在且不等于本行主键即冲突；
同一主键沿用自己的键不冲突。判定**从不读取可能落后的索引**，因此
既不会因索引落后放过冲突（属主是别人、索引里暂时没有），也不会误报
（属主是自己）。被拒绝的写入在产生 LSN/落盘之前就返回，天然不留痕。

基准（`BenchmarkConflictDecisionVsLag`，落后 0/64/256/1024 条）：
每次判定恒定约 0.55–0.69 µs、5 次分配，**不随后落量变化**。

### 3.2 两个进度：`applied` 与 `watermark`

- `applied`：索引内容实际吸收到的 LSN，随每个键效果在**同一崩溃原子
  步骤**里推进（键增删 + `applied=k` 一起提交），因此“某条效果在索引
  中”与“`applied >= 该条`”在崩溃点上等价。
- `watermark`：题目语义水位，只在**批次边界且已触到日志末尾**时推进。

恒等式：`watermark <= applied <= tail`。崩溃后常见现场就是
`watermark < applied`（索引含若干超过水位的前缀效果）。

### 3.3 幂等追赶：每个键两个来源 LSN

朴素地“见到旧键就删、见到新键就放”只在从空索引顺序重放时正确；
一旦索引已含**任意长前缀**（题目明确要求覆盖），就会出现：

- 旧键条目其实属于“被本次写入挤走的另一个主键”的更早效果，不能删；
- 较晚的释放已把键清空，较早的 put 重放时不能再把它放回去。

因此索引为每个非空二级键持久化两份来源信息（与条目同步骤落盘）：

- `indexlsn:<sec>`：当前条目来自哪次 Put；
- `indexrm:<sec>`：最近一次释放（改走/置空/删除）的 LSN（墓碑）。

重放 `e@L` 时仅做 LSN 新旧仲裁：

- Put 非空 sec：仅当 sec 的 putLSN 与 removedBy **都 < L** 时写入；
- 释放 oldSec：仅当 removedBy < L 时记录墓碑；若在场条目属主为本主键
  且其 putLSN < L 才移除条目；
- 同键沿用（oldSec==newSec）不产生释放。

这是标准的 LWW/状态归并：**结果只取决于每个键最后一次 put 与最后一次
release 的相对 LSN**，与起始含哪些前缀效果无关，所以对任意初始状态
幂等；重复追赶时 `LSN <= applied` 的整段跳过。每条日志只访问自己涉及
的至多两个键，O(1)。

基准（`BenchmarkApplyOneIsolated`，索引 64/1024/16384 条）：
单条约 0.73–0.83 µs、87 B，**不随索引规模变化**。

### 3.4 批次、并发与“追赶中的新写入”

- `CatchUp(maxBatch)` 先扫描本批窗口要求 LSN 恰为连续序列；发现
  缺口立即返回 `ErrLogGap`，**在任何修改之前**，索引与水位不变。
- 全部对外操作由一把容量 1 的信号量串行化，因此写入与追赶的并发
  结果等价于某个串行顺序；该顺序下查询要么 stale，要么与完整重建一致。
- 追赶期间的新写入只追加 WAL：若本批结束时 `applied < tail`（被并发
  写入推远），本批**不推进水位**，新条目靠 `applied` 记账，下批继续；
  已应用条目凭 LSN 不重复，未应用条目不会被跳过。

### 3.5 持久化与崩溃模型

`Disk` 用内存 map 模拟崩溃原子存储：`stagedCommit(step,changes,deletes)`
在提交步骤前询问 `CrashHook`，返回真则整批改动（含内存）丢弃；对同一
`Disk` 再次 `Open` 即等价重启。这让“崩溃点”成为确定性、可枚举的输入，
从而能精确复现“相同写入序列 + 相同崩溃点 → 完全相同的日志、主表、
追赶后索引”。生产实现只需把每个提交步骤映射成一次真实的
fsync/事务提交，算法不变。

## 4. 被放弃的方案

1. **用索引本身做唯一判定**：索引落后时既会漏报（别人占了键但还没
   被吸收）也可能误报，且追赶会反过来依赖写入路径，耦合不清。改为
   主表侧 `secOwners`，判定 O(1) 且永远基于最新状态。
2. **仅维护 `applied`、不记录每键来源 LSN/墓碑**：在“索引已含任意
   前缀”的初始状态下无法区分“更晚的转交/释放”，归并不幂等（差分
   测试 seed=1 即暴露）。加入 put/remove 双 LSN 后才对所有前缀长度
   成立。
3. **水位随每条推进**：题目要求水位允许滞后、崩溃后可能含超水位前缀；
   若逐条推进水位就无法表达“批次边界才确认”的语义，也无法枚举各类
   崩溃前缀。水位只在触底批次边界推进。
4. **追赶时全量重建**：实现 O(n)、每次重启代价高，且无法分批返回进度。
   完整重建只保留在朴素模型与 `index.rebuildFrom` 中作为对照基准。
5. **多版本/MVCC**：本题只有“最新值”语义，单锁 + LSN 归并即可满足
   可串行化，避免不必要复杂度。

## 5. 错误模型（优先级从高到低）

`ErrInvalidArgument` > `ErrLogGap` > `ErrIndexStale` >
`ErrPrimaryNotFound` > `ErrUniqueConflict`。

实现里每个入口按此次序短路；例如追赶未完成时查询一个不存在的键，
先报 `index-stale` 而不是“未找到”。

## 6. 自检

`Verify()` 在追赶完成前报 `ErrIndexStale`；否则对“主表全量重建视图”
与索引逐项比对，输出三类可区分差异：
`DiffExtra`（多余）、`DiffMissing`（缺失）、`DiffWrongOwner`（错指）。
自检只读，不修改任何状态。

## 7. 本地验证方法

```bash
export PATH=$PATH:/usr/local/go/bin
go test -race -count=1 ./ontology/store/indexstore/
go test -run XXX -bench 'Benchmark(Conflict|ApplyOne)' -benchtime=1000000x \
  ./ontology/store/indexstore/
go run ./ontology/store/indexstore/cmd/demo
```

- 确定性枚举：索引领先水位的前缀长度 `0..N`、水位 `0..applied`
  全组合；崩溃点遍历每个 `index-apply` 与 `watermark` 提交步骤；
  日志缺口遍历每个位置；批大小 1/2/3/4。
- 随机差分：400 个固定种子 × 全前缀/水位组合，同脚本驱动实现与
  独立朴素模型（全量重建派），逐条比对错误类别、成功输出、最终索引、
  自检与水位；失败时打印双方操作日志与模型主表，可直接复现。
- 复现保证：相同种子与崩溃点两次运行，磁盘文件内容与最终索引逐字节
  相同（`TestDeterministicReplay`）。
