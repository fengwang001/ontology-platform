# 链接记录修复裁决组件（`ontology/linkrepair`）设计说明

## 1. 目标与范围

快照中的链接实例记录可能因局部损坏出现：结构残缺、引用了同次恢复中不可用的
对象实例、同一单一基数上的多个不同对方实例（基数冲突）、以及指向同一对对象的
重复副本。本组件在恢复这些记录时：

- 保证恢复结果始终满足每种链接类型在两端各自声明的基数约束；
- 对四类异常给出**互斥、可区分、顺序固定**的判定；
- 裁决规则固定，重复/并发执行结果字节级一致；
- 不修改原始损坏数据；
- 工作量随记录总数线性扩展，额外排序代价只发生在真正超限的局部范围。

入口为 `Repair(Snapshot) Report`（`repair.go`），纯函数，无包级可变状态。

## 2. 组件划分

组件按"单条 → 引用 → 关系"三个层次拆分，职责互不重叠：

| 文件 | 组件 | 职责 |
| --- | --- | --- |
| `validate.go` | `validator` | 单条记录结构有效性：链接类型缺失/未知、任一端对象信息丢失 |
| `references.go` | `referenceChecker` | 两端引用是否指向同次恢复中可用的对象实例 |
| `cardinality.go` | `arbiter` | 去重与基数冲突裁决，输出保留集合与可复核依据 |
| `repair.go` | `Repair` | 编排三个阶段、汇总逐条裁决、确定性排序输出 |

类型定义集中在 `types.go`（`LinkType`、`RawRecord`、`Snapshot`、`Reason`、
`Verdict`、`Report`）。

## 3. 四类判定与固定优先级

`Reason` 四个舍弃值互斥，且严格按下列顺序逐条短路裁决——一条记录在靠前的阶段
被判定后，不再进入后续阶段，这也定义了"一条记录同时像多种异常时算哪一种"：

1. **`malformed`（结构损坏无法解析）**：链接类型标识为空、指向未知类型，
   或 A/B 端任一对象标识为空。只残留一端的不完整记录在此被**整体舍弃**，
   绝不用默认值或猜测补全缺失端。
2. **`referenced_object_unavailable`（引用对象不可用）**：结构完整，但至少
   一端不在同次恢复的可用对象集合中。只要一端不可用，整条舍弃，从而保证
   保留结果中不存在任何引用不可用对象的链接记录。
3. **`cardinality_conflict`（基数约束冲突）**：通过前两关的记录，在
   `(链接类型, 端, 锚点对象)` 的局部范围内超出声明上限。
4. **`duplicate`（内容重复）**：与另一条最终保留记录的**内容键**
   （链接类型 + A 端对象 + B 端对象）完全相同。

**为什么是这个顺序**：结构是可解析性的前提；引用可用性是记录在本次恢复世界
中的存在性前提——前两者是"这条记录本身能不能算数"，后两者是"算数的记录之间
如何取舍"。基数先于重复：重复是"某条已合法存在的记录的多余副本"，若该内容
在基数裁决中本就不该存在，则其所有副本都属于基数冲突，而不是重复。

## 4. 基数裁决规则（固定不变）

- **局部范围**：按 `(链接类型, 端(A/B), 锚点对象)` 分组。不同链接类型之间、
  两端之间、不同对象之间的裁决完全独立。同一对象同时卷入多种链接类型冲突时，
  每种类型独立裁决，互不影响。
- **固定优先规则**：在一个局部范围内，将**不同对方实例按其标识的字典序升序
  排列**。声明上限为 `max`（`max>0`）时保留前 `max` 个对方，其余舍弃；
  `max<=0` 表示无上限，全部保留。规则不依赖记录输入顺序、map 遍历顺序或时间戳。
- **两端取交集**：一条边同时属于 A 端与 B 端两个局部范围，只有在两端都胜出
  时才保留；任一端落败即以基数冲突舍弃（`Detail` 中固定先报告 A 端）。
- **去重**：同一内容键下输入下标最小的记录为规范代表（输入位置稳定、永不重复，
  不依赖可能已损坏的链接实例自身标识）；其余为重复副本。规范边胜出则副本判
  `duplicate`；规范边落败则该内容全部判 `cardinality_conflict`。

被舍弃的候选数量不设上限：单一基数下候选 2、3、…、N 个，以及带上限多值基数
恰好超出的情形，都由同一条规则覆盖。`Verdict.Detail` 给出可复核依据，例如
对方实例的字典序名次与上限。

## 5. 确定性、并发与不可变性

- `Repair` 不写输入（`Snapshot` 的切片与 map 均只读），不使用包级可变状态；
  所有临时映射在调用内新建，因此并发调用互不干扰且无需加锁。
- 所有遍历最终都经由显式排序落地：内容键排序、局部范围内对方标识排序、
  输出按内容键排序。Go map 的随机遍历顺序不影响结果。
- 对同一份快照重复执行任意次，`Report.Kept` 与 `Report.Verdicts` 完全一致。

## 6. 工作量与"只与冲突局部范围相关"

设记录总数为 N，设真正超限的局部范围集合为 C，其中范围 g 的大小为 s_g：

- 阶段 1、2 为 O(N)；
- 阶段 3 的建组为 O(N)；
- **只有超限的局部范围才执行字典序排序**（`max<=0` 或候选数 ≤ `max` 的范围
  直接全部胜出），排序总量为 Σ_{g∈C} O(s_g log s_g)；
- 未发生冲突时整条流水线为 O(N)。

因此当损坏只影响少量局部范围时，额外代价只由这些范围的大小决定，与快照总
规模脱钩。可复核方式：

- 代码层面，`arbiter.decideEndGroup` 对未超限范围不排序，路径可直接审查；
- 基准 `BenchmarkRepairConflictFree`（1 万条互不相交记录）与
  `BenchmarkRepairLocalConflicts`（同样 1 万条 + 仅 50 个超限范围）展示
  线性扩展及冲突代价的局部性：

```bash
go test -bench=. -benchmem ./ontology/linkrepair
```

## 7. 被放弃的方案

- **用记录输入顺序/时间戳决定单一基数取舍**：放弃。快照记录顺序可能随恢复
  过程变化，无法保证反复执行结果一致；改为对方标识字典序这一无状态全序。
- **用链接实例自身 ID 选择代表**：放弃。重复副本的实例 ID 可能损坏或冲突；
  改用输入下标作为稳定定位，仅用于选代表与报告，不参与业务等价判定。
- **把重复检测放在基数裁决之前**：放弃。会出现"重复了一条本不该存在的边"
  的矛盾归类；按第 3 节论证，基数优先。
- **自动补全缺失端 / 容忍悬空引用**：明确禁止。不完整记录整体判 `malformed`，
  悬空引用判 `referenced_object_unavailable`，不做任何默认值或猜测。
- **全局排序所有记录后再裁决**：放弃。无法体现代价局部性；改为只对超限范围
  排序，其余线性通过。

## 8. 本地验证方法

```bash
# 全量测试（含 2000 组随机对照、跨链接类型独立性 200 组、并发与幂等）
go test ./...

# 竞态检测
go test -race ./...

# 将每次裁决的输入/输出/逐条判定依据导出为 JSONL（每行一个用例）

  go test -run TestDifferentialAgainstNaiveModel -v ./ontology/linkrepair

# 开销基准
go test -bench=. -benchmem ./ontology/linkrepair

```

## 9. 测试与朴素参照模型

- `repair_test.go`：单一基数候选 1/2/4 个、带上限多值基数恰好达到与恰好超出、
  不完整记录与重复混合、引用不可用（含单端/双端）、基数优先于重复、
  多链接类型同对象冲突独立、B 端基数、并发 32 路 + 重复 10 次幂等、
  输入不可变、保留边不引用不可用对象。
- `naive_model_test.go`：独立编写的朴素参照模型 `naiveRepair`，用"逐条打阶段
  标签 + 集合运算重建局部范围"的不同写法实现同一套规则。
- `diff_test.go`：2000 组随机构造的损坏链接集合与朴素模型逐条对照（保留/舍弃
  与四类原因完全一致），并断言四类判定均被实际覆盖；另含多链接类型同对象
  冲突独立性的随机构造（单独裁决与混合裁决结果一致）与两个基准。
