# 动作事务审计溯源子系统 · 设计说明

本包（`ontology`）为单个对象类型（Object Type）提供一套「动作事务审计
溯源」能力：每一次动作执行——无论最终提交还是整体回退——都在一条
不可篡改、单调有序、无空洞的审计序列中留下与最终状态完全自洽的记录；
仅凭该序列即可独立重建任意历史时刻的对象状态。

三个协作者：

| 角色 | 类型 | 职责 |
| --- | --- | --- |
| 动作事务执行模块 | `Executor` | 校验参数、执行多实例写入、与审计模块协作完成「审计 + 状态」的同生同灭、处理订正 |
| 审计记录生成与存证模块 | `AuditStore` | 单调分配序号、只追加存储、哈希链防篡改、订正点查索引、故障注入 |
| 重放重建模块 | `Replayer` | 按序号区间重放、用快照把开销限制在区间长度量级、独立重建状态 |

另提供 `NaiveModel`：独立维护、每次从头线性扫描全部记录的朴素黄金模型，
仅供测试逐条对照。

## 1. 数据模型与序号语义

每条审计记录 `Record` 含：动作标识 `ActionID`、记录种类 `Kind`
（`ACTION` / `CORRECTION`）、结果 `Outcome`（`COMMITTED` /
`ROLLED_BACK`）、本次写入涉及的**全部实例及其变更前后值** `Changes`、
被订正序号 `CorrectionOf`（仅订正记录）、单调序号 `Seq`、以及哈希链
`PrevHash`/`Hash`。

- 序号在**同一对象类型范围内**从 1 开始严格递增、无空洞。不同对象类型
  使用不同 `AuditStore`，序号空间相互独立（见
  `TestIndependentTypeSequences`）。
- 提交与回退**都占用**一个序号。回退记录中每条 `Change` 的
  `Before == After`，明确标记「未生效」，与提交记录区分。
- 只有「审计写入失败」这一种情况**不占用序号**：失败发生在序号计数器
  推进之前，因此不会产生空洞。

## 2. 审计与状态「同生同灭」

`ExecuteAction` 在 `Executor` 的单把互斥锁内执行，事务提交点定义为
「审计记录成功 append 并返回」：

1. 先做参数校验（目标实例是否存在），非法立即返回 `InvalidInputError`，
   完全不触碰状态、也不申请序号。
2. 计算 `Before/After`（回退时 `After=Before`），调用
   `AuditStore.append`。`append` 在 store 锁内完成「序号分配 + 持久化」，
   二者不可分割；故障注入时直接失败、序号不前进。
3. **仅当** append 成功返回后，才把变更发布到内存状态。若 append 失败，
   状态从头到尾未被修改，天然达成回退；不会出现「状态已变但审计缺失」
   或「审计存在但状态未变」。

这是一种「write-ahead audit」：对外可见性以审计记录为准。并发动作在
两把锁的嵌套顺序（始终 `Executor` → `AuditStore`）下等价于某个全局
串行顺序，序号唯一、连续（见 `TestConcurrentSequentialNumbers`，
3200 个并发动作 → 序号 1..3200 无重号无空洞）。

> 说明：内存态在本实现中就是权威状态载体；真实系统里第 2、3 步应落在
> 同一存储事务 / WAL 中。本包通过「先审计成功、后发布状态、失败即不发布」
> 的次序与故障注入，精确刻画并验证了该原子性。

## 3. 订正（追加，不替换）

- 订正只能**追加**为一条 `Kind=CORRECTION` 的新记录，占用新序号，
  含被订正动作序号 `CorrectionOf` 与订正后的正确值；原动作记录在序列中
  **原样保留、不被物理替换**（`TestCorrectionOverride` 显式校验原值仍在）。
- 订正具有**追溯语义**：一条订正一旦写入，重放完整序列时它覆盖所指
  动作对所有历史时刻的影响。某实例在任意时刻的有效值恒等于
  「其最近一次**有效提交动作**的写入值，再叠加该动作的最新订正（若有）」。
  回退记录不是有效提交，永不贡献状态。
- 同一动作可被多次订正，**最新订正胜出**（以追加序号比较）。
- `AuditStore` 增量维护点查索引 `corrected[targetSeq][instance]`：
  订正追加时 O(1) 更新，重放以 O(1) 点查拿到「最新订正后的有效值」，
  无需为一次重放扫描订正历史。

参数校验（均为 `InvalidInputError`，优先级高于审计失败）：
订正集合为空；被订正序号不存在；被订正序号本身是订正记录
（订正不得指向订正）；订正实例不在原动作涉及集合内。允许只订正原动作
涉及实例的一个子集。

## 4. 错误次序与可区分性

两类错误是不同类型，可用 `IsInvalidInput` / `IsAuditWriteFailure` 判别，
且严格「只报第一个命中」：

1. **参数非法**：目标实例不存在、被订正序号不存在、被订正序号本身是
   订正记录、空写入 / 空订正。参数校验在任何审计写入之前完成，
   因此即使 store 被注入故障，参数非法仍先报（`TestErrorOrdering`）。
2. **审计写入失败**：仅在参数合法后、append 失败时报 `AuditWriteError`，
   状态整体撤销且不占序号。

## 5. 区间重放与复杂度

`Replayer.ReplayRange(lo, hi)` 重放开区间 `(lo, hi]`：

- 提交动作为每个涉及实例产出一条有效变更事件（`Before/After` 为
  追溯订正后的正确值）；回退动作与订正记录各产出一条
  `Action=nil` 的「尝试事件」，只表示发生过一次尝试，不作为状态来源。
- 重放同一区间任意多次结果完全相同（`TestReplayDeterministic`）。

复杂度控制（要求：开销只与区间长度相关，不随历史记录总数增长）：

- 每隔 `SnapshotInterval=64` 条记录有一张快照，只存「每实例当前值」与
  「每实例最新有效动作序号」，大小随**活跃实例数**增长，与历史条数无关。
- 重放选取不晚于起点的最近快照作为基线，随后只需扫描
  至多 `SnapshotInterval + (hi-lo)` 条记录；每条提交动作的值经
  `corrected` 点查（O(1)）获得追溯订正后的有效值。
- 快照在常驻 `Replayer` 上**增量构建并缓存**：每次只读取上一边界之后的
  新增段，摊销构建成本 O(N)，稳态区间重放 O(区间长度)。
- `ScanCost()` 返回最近一次重放实际读取的记录条数，作为**可验证度量**。
  `TestReplayComplexityBound` 在同一条持续增长的序列上证明：N 从 128
  增到 8192，固定宽度区间的稳态扫描恒为 64（≤ 间隔+宽度=74），
  而朴素模型扫描量随 N 线性增长（128/1024/…/8192）。测试打印这张对照表。

朴素模型 `NaiveModel` 刻意不用任何快照 / 索引，每次查询都从序号 1 线性
扫描全部记录，与优化重放器共享同一套追溯订正语义，作为黄金参照。

## 6. 不可篡改

- `AuditStore` 仅暴露追加与只读接口；`Get/All/Range` 返回深拷贝，
  外部无法借返回值改动内部序列（`TestImmutableAndHashChain`）。
- 记录以 SHA-256 哈希链串接：`H(prevHash || 规范化字段)`，字段按实例
  标识排序以保证确定性。内容篡改会使自哈希失配；删除中间记录会造成
  序号 / 链接断裂；执行器基于被破坏序列重开时拒绝恢复。

## 7. 被放弃 / 未采用的方案

- **物理更新或删除原记录**：直接违反「原样保留、不可篡改」，放弃；
  改为只追加订正。
- **订正只改变「当前值」、不回溯历史**：会导致历史时刻状态无法重建出
  正确值，与「审计序列独立重建任意历史时刻」冲突，故采用追溯语义。
- **重放时先线性扫描收集区间内订正**：跨边界、订正在区间外时会漏；
  改为在 store 增量维护全局点查索引，重放 O(1) 取值，既正确又有界。
- **快照携带全部订正覆盖历史**：使快照大小随历史订正值增长，违背
  「快照大小与历史条数无关」；改为快照只存最新动作序号，有效值靠点查。
- **订正直接改写活状态而不维护索引**：恢复 / 重开时无法重建，放弃。

## 8. 本地验证

```bash
# 需 Go 1.26+（仓库根 go.mod 声明 go 1.26.5）
go test ./...
go test -race -v ./ontology          # 竞态 + 详细输入/输出/依据打印
go test -v ./ontology -run TestRandomDifferential
go test -v ./ontology -run TestReplayComplexityBound
go vet ./...
gofmt -l .
```

测试覆盖（均会打印输入、实际输出与判定依据）：

- 提交 vs 回退记录的区分、回退不占状态但占序号；
- 审计写入失败导致状态与审计一致回退、序号无空洞；
- 订正覆盖原记录完成历史重建、原记录不被替换、多次订正最新胜出；
- 参数非法先于审计失败、两类错误可区分、订正不得指向订正；
- 3200 并发动作序号唯一连续无空洞、等价某全局串行顺序、哈希链完整；
- 不可篡改（深拷贝隔离、内容篡改 / 中间删除被哈希链检测）；
- 4000 步随机「提交/回退/订正/故障注入」序列下，优化重放器与朴素模型
  在每个序号 `StateAt` 与随机区间 `ReplayRange` 上逐条一致；
- 区间重放扫描量不随历史总量增长（打印对照表）与重放确定性；
- 执行器重开恢复与多对象类型序号空间独立。
