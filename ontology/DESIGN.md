# 阅卷分配与双评仲裁引擎 — 设计说明

## 关键取舍
- 单一互斥锁串行化所有公开操作：并发调用等价于某一串行顺序，所有不变量只需在锁内论证。
- 选择只依赖评卷人记录：`load`（在手未完成数）增量维护，回避/配对为 O(1) map；
  `chooseLocked` 对固定评卷人集合做一次线性扫描，开销 O(R)，与答卷数、已完成任务数无关。
  `chooseScans` 计数在测试中被断言恒等于评卷人总数，提供可验证证明。
- 确定性：评卷人按 ID 排序扫描；候选先比 `load` 最小，再比 ID 最小；与调用历史无关。
  待分配队列 FIFO；任何能改变可行性的操作后统一 `assignPendingLocked`。
- “同一评卷人对同一学生只出现一次”在**分配时**即登记配对（即使随后撤回也不再给该生），
  取语义最严格解释；同卷重复由“已提交评卷人封禁”另作约束。
- 网格靠合用 `ceil(avg/step)*step`（钳制到满分）；参考模型改为逐网格点上走来独立实现。
- 撤回/停用都保留旧任务作审计证据，另建同角色新任务，并把退出者永久封禁出该答卷。

## 被放弃的方案
- 按组维护最小堆：更新（load 变化、停用、配对）需惰性失效，复杂度证明不直观；
  R 通常为有限常数，线性扫描的确定成本更易复现与验证。
- 按调用历史缓存候选：会破坏“与历史无关”的确定性要求。
- 提交时才登记配对：撤回后可能又被分给同一学生的其他题，违背更严格的业务读法。
- 仲裁立即强制成功：第三组暂缺时应进入待分配，待新评卷人到位后由触发操作领走。

## 模块划分
- `engine.go` 状态与锁；`config.go` 配置入口；`assign.go` 选择/待分配/约束；
  `scoring.go` 提交/撤回/停用/仲裁/终分；`audit.go` 审计与快照；`types.go`/`errors.go` 模型与错误分类；
  `naive.go` 独立朴素参考实现。

## 本地验证
- `go test ./...` 全量用例（分差恰等阈值、网格靠拢、等距取高、双双超阈、撤回、停用、
  配额恰满、回避+配对归因、拒绝优先级逐对、待分配补领）。
- `go test -run TestRandomDifferential -v` ：60×400 步随机序列，逐步打印输入/输出/判定依据，
  与朴素模型全量深比对。
- `go test -race ./...` 并发可线性化；`TestSelectionCostIndependentOfHistory`
  断言扫描数不随 5→500 份历史答卷变化。
- `go vet ./...`、`gofmt -l .`。
