# applier：按键有序、故障隔离的变更应用组件

`applier` 包把变更事件按“键”分组应用：同键事件严格按提交顺序定案，一条事件
应用失败只会阻塞它所属的键，其他键照常提交与应用。

## 核心模型

每个键独立维护以下状态：

- 是否阻塞（`blocked`）
- 队首事件及其已尝试次数（`head` / `attempts`）
- 先进先出的缓冲队列（`buf`）
- 已成功应用的事件列表（`applied`）

全局还维护：死信队列（`dead`）与等待定案事件总数（`pending`）。

## 阻塞、重试、死信与排空

- **立即尝试**：未阻塞键收到事件时立即调用 `ApplyFunc` 尝试一次。
- **阻塞**：尝试失败且未达 `MaxAttempts` 时，该键进入阻塞，队首事件保留，
  后续同键提交进入 FIFO 缓冲（返回 `buffered`），不影响其他键。
- **重试**：`Advance()` 对每个当前阻塞键的队首事件再尝试一次；返回结果按键名
  排序，保证输出顺序确定。
- **死信**：队首事件达到 `MaxAttempts`（含首次）仍失败，转入死信队列，
  记录事件与尝试次数，随后解除该键阻塞。
- **排空**：队首进入死信后，缓冲事件按 FIFO 依次立即尝试：成功则继续下一条；
  失败则该键重新阻塞、剩余事件留在缓冲，等待后续 `Advance()`；全部处理完则
  缓冲排空、键保持未阻塞。

## 非法输入（拒绝且无副作用）

`Submit` 在改动任何状态前完成校验，拒绝时返回下列可区分的哨兵错误：

- `ErrEmptyKey`：事件键为空。
- `ErrSequenceNotIncreasing`：同键事件序号未严格递增（必须大于该键上一个已
  接受的序号；相等或更小都拒绝）。
- `ErrBufferLimitExceeded`：所有键等待定案事件总数（各键队首 + 缓冲）已达
  `MaxBuffered`。

被拒绝的提交不会改变任何键的阻塞状态、尝试次数、缓冲、死信队列、已应用列表，
也不会占用缓冲名额。

## 并发与确定性

- `Submit` / `Advance` / 各查询方法均可并发调用，内部用互斥锁串行化，保证
  每个键的定案次序与“逐键串行”参照一致。
- 同键的应用次序即提交次序（序号严格递增）；失败事件不会越过后续事件。
- 对同样的输入序列重复计算，得到完全相同的输出（已应用列表、死信、阻塞键、
  待决数量）。
- 标准库 `log` 会打印每次提交的输入、每次尝试的定案结果（`applied` /
  `retrying` / `dead` / `buffered`）及判定依据（尝试次数、失败原因、触发场景）。

## 配置

`Config{MaxAttempts, MaxBuffered}`：

- `MaxAttempts`：单条事件的最大尝试次数（含首次），零值默认 `3`。
- `MaxBuffered`：全部键等待定案事件总数上限，零值默认 `1024`。

## 本地验证

```bash
# 全量测试（带竞态检测与详细日志，日志中可见输入、定案结果与判定依据）
go test -race -v ./applier

# 全仓库测试 / 覆盖率
go test -race ./...
go test -coverprofile=coverage.out ./applier
go tool cover -html=coverage.out

# 代码检查
go vet ./...

```
