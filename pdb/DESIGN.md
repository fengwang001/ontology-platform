# PDB 驱逐裁决服务 — 设计说明

面向节点排空（node drain）场景的 PodDisruptionBudget 驱逐裁决库。所有时间均由调用方
注入（逻辑时钟），便于对“放行—确认/取消—到期回补”做精确、可复现的判定。

## 1. 模块划分

代码全部位于 `pdb` 包，按职责拆成彼此协作的小文件：

| 文件 | 职责 |
| --- | --- |
| `types.go` | 领域类型：`Pod`、`BudgetSpec`、`Value`、`Selector`、`Phase`、`BudgetStatus`，以及内部的 `eviction` 记录 |
| `errors.go` | 可程序化判别的错误类别 `Reason` 与 `DecisionError`（含出错 Pod 与批量下标） |
| `budget.go` | 纯函数：预算定义校验、绝对值/百分比解析（上取整/下取整）、必须就绪数、额度、选择器匹配 |
| `index.go` | 两个倒排索引及其维护；按标签命中候选预算、按预算枚举命中 Pod |
| `heap.go` | 按截止时刻排序的最小堆，驱动到期回补 |
| `service.go` | 服务骨架、互斥串行化、逻辑时钟、`begin/commit`、到期处理、驱逐收尾 |
| `mutations.go` | Pod/预算的新增、修改、删除 |
| `evict.go` | 单个驱逐、整批驱逐、确认、取消、预算查询 |
| `inspect.go` | 测试/排障用的检视接口与工作量埋点开关 |

## 2. 核心规则与取舍

### 2.1 统计范围与选择器

- 仅 `Running`/`Pending` 属于统计范围且可被驱逐；`Succeeded`/`Failed` 既不计入
  `expected/ready`，也不能被裁决驱逐。
- 空选择器是“什么都不匹配”（规格明确约定，不同于 Kubernetes 语义）。
- 选择器要求所有键值全等，且预算只匹配同命名空间 Pod。

### 2.2 预算推导（每次查询由当前状态现算）

- `expected`：匹配且在统计范围内的 Pod 总数，随 Pod/预算变更用索引增量维护。
- `minAvailable` 百分比按 `ceil(expected*p/100)`；`maxUnavailable` 百分比按
  `floor(expected*p/100)`；绝对值原样使用。
- `required = minAvailable` 或 `expected - maxUnavailable`，只夹到非负（绝对值
  minAvailable 可以大于期望总数，此时额度自然为 0 且查询如实汇报）。
- `allowance = max(0, currentReady - required)`。额度从不缓存，任何状态变更
  （就绪、标签、阶段、增删 Pod、增删改预算）都通过索引计数器即时生效。

### 2.3 单个驱逐裁决

错误优先级固定：参数非法 &gt; 时钟回退 &gt; Pod 不存在 &gt; 阶段不可驱逐 &gt; 已在驱逐中
&gt; 配置冲突 &gt; 额度不足。实现严格按此顺序短路返回。

- 无预算匹配：直接放行。
- 匹配 ≥2 个预算：配置冲突，拒绝。
- 匹配 1 个且未就绪：`currentReady >= required` 才放行，不消耗额度。
- 匹配 1 个且就绪：`allowance > 0` 才放行；放行瞬间该 Pod 变为未就绪并进入驱逐中，
  预算 `ready` 计数立即减一（即消耗一个额度）。
- 已在驱逐中：再次驱逐拒绝；在驱逐中改变就绪状态同样按“已在驱逐中”拒绝
  （标签、阶段、删除等其余变更不受此限制）。

### 2.4 驱逐生命周期与逻辑时钟

- 放行时记录 `(预算引用, 放行前就绪状态, 起始时刻, deadline=起始+宽限)`。
  预算引用在放行时刻固定：之后删除/替换该预算不会影响在途驱逐的回补记账。
- `Confirm`：删除 Pod；`Cancel`：立即恢复到放行前就绪状态。
- 到期：任何裁决或查询（`begin`）之前先应用到期。到期取**左闭**——恰在
  `start+grace` 那一刻即视为失效并回补。
- 时钟单调性：注入时刻不得早于此前任何**被接受**操作的时刻。参数非法在时钟检查
  之前判定，因此非法调用不移动时钟；被拒绝的操作不推进时钟。参数校验通过后才做
  回退检查，回退拒绝同样不改任何状态。

### 2.5 整批驱逐

- 先做参数校验（含批内重复 Pod，按下标报告最先出问题的位置），再统一加锁。
- 加锁后先应用到期，再按提交顺序逐 Pod 判定；任一失败立即返回其位置与原因，
  且**不产生任何状态变更**（计划只保存在局部切片里）。
- 就绪 Pod：按预算累计消耗，`Σ已消耗(预算) + 1 ≤ allowance` 才通过。
- 未就绪 Pod：门控只读取**批开始**的预算状态（`currentReady >= required`），
  不受同批就绪 Pod 消耗影响，也不消耗额度。
- 全部通过后才在同一临界区内一次性提交，对其他调用表现为不可分割的一次串行操作。

### 2.6 并发

刻意只用一把 `sync.Mutex` 把所有调用串行化。批量在锁内完成“判定+提交”，因此
天然不可分割；同一预算的额度不可能被并发超额消耗。这是有意识的取舍：该领域逻辑
临界区很短（索引探针 + 少量整数运算），粗粒度锁换来最强的可证明线性一致性，避免
分片锁/乐观重试与“先查后扣”窗口带来的复杂度。所有公开方法满足
`-race` 检测，其可观察结果等价于某个串行顺序。

## 3. 数据结构与性能

- `podByLabel[(namespace,key,value)] → set(pod)`：在统计范围内的 Pod 按每个标签建倒排。
- `budgetsByKey[(namespace,key)] → set(budget)`：非空选择器预算按选择器中的每个键建倒排。
- 预算计数 `expected/ready` 为增量维护：Pod 增删改、预算增删改只触碰
  “标签键有交集”的对象。

判定一个 Pod 命中哪些预算时，只遍历该 Pod 标签键对应的预算候选集合；因此工作量
只与**相关**预算（同命名空间且共享至少一个选择器键）有关，与无标签键交集的预算
和其他命名空间的 Pod/预算无关。终态 Pod 不进 Pod 倒排。预算查询枚举命中 Pod 时，
只访问至少携带该预算某个 `(key,value)` 的 Pod 桶。

“不随无关对象数量增长”不是用耗时来声称的：`complexity_test.go` 打开内部埋点
（`BudgetScans` = 单次驱逐实际触碰的候选预算数；`PodScans` = 预算查询实际触碰的
Pod 桶项数），在无关对象规模为 1/100/500 三档下断言探针计数完全相同且非零。
这是结构性证明：若实现退化成全扫描，探针数会随规模线性增长，测试立即失败。

## 4. 被放弃的方案

- **预计算并缓存每个 Pod 的匹配预算 / 缓存额度**：会在标签、预算变更时产生失效
  问题，容易出现与当前状态不符的陈旧额度。改为每次由索引计数器现算。
- **分片锁 / 每预算原子额度**：在冲突、未就绪门控、批量全有或全无等复合判定下，
  仍需一个全局一致点，复杂度高且难以证明。改为单锁串行，简单且可证明。
- **延迟应用到期（仅查询该 Pod 时才处理）**：无法满足“任何失效都必须在下一次
  裁决或查询之前体现”。改为统一最小堆 + 每次 `begin` 先清空到期。
- **空选择器匹配全部（Kubernetes 语义）**：与题目明确约定冲突，严格按“不匹配任何
  Pod”实现，并由测试锁定。
- **把 minAvailable 绝对值夹到期望总数**：会掩盖超额配置；改为只夹非负，让查询
  如实反映 required、额度自然归零。

## 5. 本地验证

```bash
# 全量测试（仓库根目录；Go 1.26+）
go test ./...

# 竞态 + 详细日志
go test -race -v ./...

# 只跑随机差分（默认 12 个种子 × 400 步）
go test -run TestRandomDifferential -v ./pdb

# 结构性复杂度证明
go test -run TestComplexity -v ./pdb

go vet ./...
gofmt -l .
```

每次操作的“输入 / 实际输出 / 判定依据”都会写入 `pdb/../testlogs/<测试名>.log`
（例如 `testlogs/TestRandomDifferential.log`），同时出现在 `go test -v` 输出中。
