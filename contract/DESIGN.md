# 合同版本叠加与自动续签服务 — 设计说明

包路径：`ontology/contract`（纯 Go 库，无外部依赖）。

## 1. 领域模型与时间

- 时间为整数“日序号”，所有输入时刻、生效日、到期日均为 `int64`。
- 单调时钟为**服务级**：每个被接受的写操作携带 `now`，必须 `now >= 上一次被接受操作的 now`，
  否则返回 `CLOCK_ROLLBACK`；相等允许。被拒绝操作不推进时钟、不改变任何状态。
  选择服务级而非合同级时钟，是为了让“时钟回退”在错误优先级上能先于“合同不存在”判定，
  且语义上对应“上一次被接受操作”这一全局操作日志。
- 主合同包含：双方及其签署授权窗口 `[AuthFrom, AuthUntil]`（含两端）、条款 `编号->整数`、
  锁定条款集合、起始日、到期日，以及三个固定续签条款：
  `AUTO_RENEW`（1/0）、`RENEWAL_TERM`（>0）、`NOTICE_DAYS`（>=0）。

## 2. 补充协议与生效

一份协议要么包含 `Changes`（条款修改），要么包含 `Revokes`（撤销目标协议 ID），二者恰居其一。

生效条件（全部满足才生效）：
1. 双方都签署；每方签署时刻落在其授权窗口内（含两端）。
2. 若第二方签署时刻严格大于“第一方签署日 + `signingDeadlineDays`”则超期拒绝；
   恰等于仍可签（常量当前为 10，见 `helpers.go`，如需可参数化）。
3. 触及锁定条款时须有法务会签。会签可在签署完成之后补齐，**自补齐时刻起方可生效**。

实际生效日：

```
effective = max(declaredEffective, completionDay, cosignDay-if-needed)
```

声明生效日早于完成日会自动后移到完成日。

提前终止：双方各自调用一次 `AgreeEarlyTermination`，第二次被接受当日合同终止。
生效日晚于终止日的协议永不生效；终止日当日及之前已生效的修改保持；终止后仅允许查询。

## 3. 版本叠加与撤销

某日某条款有效值 = 在该日“活着的”、对该条款有修改、生效日不晚于该日的协议中：

1. 生效日最晚者优先；
2. 生效日相同则签署完成时刻（全局单调序号）较晚者优先；
3. 再相同用创建序号兜底，保证结果全序确定。

无候选时取主合同原值。来源返回 `MAIN` 或 `AMENDMENT + 协议 ID + 生效日`。

撤销是“协议”这一对象上的一层时间区间效应：撤销协议自其自身生效日起，
使目标协议的全部修改在该日失效；撤销协议可被再次撤销，从而恢复目标协议效力，
判定按同样的递归规则进行。撤销**不级联改写**后续协议的取值——
后续协议按自己的 `Changes` 独立生效。历史日期查询天然不受未来撤销影响。

为支持上述判定，服务维护：

- `byClause[clause] -> []*amendment`：只包含**已生效**且修改该条款的协议；
- `revokerChildren[target] -> []*amendment`：撤销某目标的协议列表。

判定 `aliveAt(a, day)` 只遍历以 `a` 为根的撤销子树，配合 `byClause`，
单条款查询不扫描与该条款无关的协议。

### 查询复杂度（可验证）

设该条款的候选协议数为 k、撤销链平均规模为 r、合同协议总数为 N：

- 有效值查询为 O(k·r)，**与 N 无关**；
- 无任何修改的条款为 O(1)（直接返回主合同值，不检查任何协议）。

`contract/perf_test.go` 用 `queryMetrics` 探针统计一次查询实际检查的协议/撤销节点数：
在 N=10/100/500 个无关协议下，查询未触及的条款检查数恒为 0；
新增 50 份只改其它条款的协议后，目标条款的检查数不变。

## 4. 自动续签

`simulate(observeDay)` 从原始到期日出发，逐个到期边界推演：

1. 在到期日 `E` 当日，用**当日有效值**读取 `AUTO_RENEW / RENEWAL_TERM / NOTICE_DAYS`；
2. 若存在任一方不续签通知满足 `noticeDay <= E - NOTICE_DAYS`（恰等于算及时），
   则在 `E` 到期终止；
3. 提前终止日 `<= E` 时在提前终止日终止；
4. 观察日 `<= E` 时，续签/终止尚未发生，当前到期日仍是 `E`；
5. 否则若自动续签开启且期长为正，则从 `E+1` 起续签一期，新到期日 `E + RENEWAL_TERM`，
   写入一条 `RenewalRecord`，并继续判定下一期限。

这保证了“每次判定均取各自到期日当日的有效值”，并可连续续签。
在期区间为 `[startDay, 到期日/终止日]`（两端都在期）。

## 5. 错误模型

统一返回 `*ServiceError{Code, Message}`，类别按优先级只报第一个：

```
INVALID_PARAM > CLOCK_ROLLBACK > NOT_FOUND > ILLEGAL_STATE
             > AUTH_EXPIRED > MISSING_COSIGN > SIGNING_EXPIRED
```

实现中每个写方法严格按此顺序短路；“缺少会签”不是一种被拒绝的写操作错误，
而是协议处于“已签署但未生效”的状态，补齐会签后自动激活，因此不会出现错误顺序冲突。

## 6. 并发与确定性

- 服务以单个 `sync.Mutex` 串行化所有读写，所有方法持同一把锁，
  因此并发调用的结果严格等价于某个串行交错顺序；
- 所有取舍都由 `(生效日, 完成序号, 创建序号)` 全序决定，无 map 遍历依赖；
  相同操作序列重放得到逐字段一致的结果（`TestReplayDeterminism`）。
- `TestConcurrentEquivalence` 在并发交错后，提取实际被接受的操作序列，
  用朴素模型按该顺序重放并逐日比对。

## 7. 朴素参考模型

`contract/naive.go` 是**独立编写**的第二套实现：

- 不维护 `byClause` / `revokerChildren` 索引；
- 每次查询全量扫描全部协议、递归全量扫描撤销；
- 续签推演独立重写一份。

`TestRandomDifferential` 生成 40 组、每组 120 步随机操作（增协议/双方签署/
补会签/撤销/再撤销/不续签通知/提前终止，时钟单调），每步后在多个历史与未来日期
比对两模型的条款值、来源、到期日、在期状态、续签记录与错误码。
日志经 `t.Log` 打印每步输入、两模型输出错误码与查询判定依据；服务侧 `SnapshotLog()`
提供中文判定依据，失败时一并输出。

## 8. 关键取舍与被放弃方案

- **服务级时钟 vs 合同级时钟**：取服务级，以满足错误优先级中“时钟回退”先于“不存在”。
  代价是不同合同的操作也共用一条时钟线；这符合“操作日志”式复现的诉求。
- **撤销建索引 vs 查询全量扫描**：生产模型建 `revokerChildren` 以保证 O(与 N 无关)；
  朴素模型故意全量扫描，作为差分 oracle。两套实现刻意不共享查询代码，避免同源错误。
- **生效时刻不可后补倒签**：晚到的会签使生效日为会签日（`max(...)`），
  而不是声明生效日，避免“未满足前置条件时协议已生效”的悖论。
- **提前终止用双方两次合意而非新协议**：终止不是条款修改，走独立的协商动作，
  这样“终止日后协议不生效”不会被签署/会签流程绕过。
- **不引入新条款编号**：补充协议只能改主合同已有编号，保证“无修改取主合同原值”
  对所有条款都有良定义基线，避免动态基线带来的歧义。
