# 多层限额账引擎设计说明

## 模块划分
- `engine.go` 门面：多保单登记表（引擎级读写锁），参数校验（不依赖保单上下文的部分）后路由到保单。
- `policy.go` 登记与账簿：成员/项目/理赔表、家庭年度已用、最晚发生日；保单级互斥锁使并发理赔等价于某串行顺序。
- `limit.go` 限额序列：基础限额 + 按保单年度索引的批改（有序数组二分查找），同一年度后写覆盖先写。
- `claim.go` 结算与冲正：固定次序校验 → 明细按（项目,发生日）稳定排序 → 五者取 min 逐明细扣减并留痕。
- `endorse.go` 批改：生效日归入所在保单年度，对该年度及之后生效；早于活跃理赔最晚发生日报「追溯批改」。

## 关键取舍
1. 已用额为唯一真相，剩余额 = max(0, 限额-已用) 派生：批改降额自然得到"剩余为零且不追索"；
   冲正按留痕精确减退后剩余额永不超过批改后限额，"超过部分不恢复"无需特判。
2. 「已封顶」为派生状态（终身已用 == 终身限额）：冲正恢复为正即自动解封，无状态机不一致风险。
3. 冲正按结算时记录的年度/项目精确退回，与后续批改无关 ⇒ 增量账恒等于全量重放（差分测试证明）。
4. 最晚发生日：结算时 O(1) 取 max；仅当冲正删掉最大值时才扫描重建（不在结算路径上）。
5. 性能：全部哈希表 + 每对象批改二分；结算只触碰本笔明细涉及的桶，`ops` 计数器供测试断言
   开销与历史理赔数、成员数、项目数无关，只随明细数线性增长。

## 被放弃的方案
- 存储剩余额并在批改/冲正时 clamp：家庭共享桶下会破坏"活跃赔付合计 ≤ 限额"不变量。
- 全局引擎锁：牺牲跨保单并行；保单内串行已满足串行等价与可重放。
- 已封顶锁存标志：与"冲正恢复即解封"叠加易产生边界不一致。
- 堆维护最晚发生日：给结算路径引入 O(log n)，违背性能约束。

## 本地验证
- `go test ./limitbook/ -v`：单元测试（年度边界、跨年理赔、五层各自为最小值、同项目顺序扣减、
  封顶/解封、降额不追索、冲正不超新限额、追溯取等、非末笔不留痕、并发争抢、拒绝次序逐对）。
- `go test ./limitbook/ -run TestDifferentialRandom -v`：朴素模型对照，打印输入/输出/判定依据。
- `go test ./limitbook/ -run TestSettleCostIndependentOfHistory`：性能不变量（ops 计数）证明。
- `go test -race ./limitbook/`、`go test -bench=BenchmarkSettle ./limitbook/`：竞态与墙钟佐证。
