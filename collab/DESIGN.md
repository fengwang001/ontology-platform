# 离线协作文档同步服务 — 设计说明

本文档说明 `collab` 包的关键设计取舍、被放弃的方案以及本地验证方法。

## 1. 数据模型

- **文档 `doc`**：`schema map[string]Kind` 声明字段种类；`fields map[string]*field`
  保存可变状态；`revision` 为文档修订号，创建时为 0。
- **字段 `field`**：`kind`、`value`、`version`、`present`。
  - 覆盖型（`KindSet`）字段可不存在：`present=false`、`version=0`。
  - 累加型（`KindAdd`）字段恒存在，初值 0、版本 0。
- **客户端状态 `clientState`**（按 `{client, docID}` 索引）：
  - `maxSeq`：已处理的最大操作序号；
  - `lastNow`：最近一次被接受批次的时钟；
  - `ring resultRing`：最近 `RetainWindow=1000` 个操作结果的定长环形缓冲。

所有可变状态集中在 `Server.mu sync.Mutex` 一把锁后。`Create` / `Sync` /
`Get` / `Pending` 均在锁内完成读改写，因此天然等价于某个全局串行顺序，
同一批次对其他批次原子可见。这是刻意选择的最简单正确方案（见 §5）。

## 2. Sync 的处理顺序

批次级检查严格按规格的先后执行，任一失败即整批拒绝、零副作用，只报第一个：

1. **参数非法**（在持锁前后两段完成）
   - 持锁前：`client/docId` 非空、`now` 范围、批大小 `[1,500]`、
     每个操作的字段/类型/组非空、批内序号连续递增、组标识相邻、
     组内 `Depends` 一致、第一个组不得声明依赖；
   - 持锁后：文档存在、字段在 schema 内、Set 值与 Add delta 合法；
     组内对同一覆盖型字段多次 Set（仅统计新操作，重放操作携带历史内容不参与）。
2. **时钟回退**：`now < lastNow`。
3. **重放过期**：批首序号 `<= maxSeq - 1000`。
4. **序号缺口**：新操作必须恰从 `maxSeq+1` 起连续。

将“重放前缀”与“新后缀”按序号切分（`newStart`）。批内序号连续、窗口为
1000、批长 ≤500，这三个约束共同保证：重放操作必在批的前部、且与新后缀
之间不可能出现“既过期又缺口”的重叠；因此四类拒绝次序是确定可实现的。

## 3. 重放语义

- 重放判定只看序号，不看内容：序号 `<= maxSeq` 即视为重放，结果**原样**
  从环形缓冲取出（包含成败类别以及冲突时的当前值/版本快照）。
- 重放不再次改变文档状态，也不再次推进 `maxSeq`；但批次时钟 `lastNow`
  仍会更新到本次 `now`（批次被接受）。
- 环形缓冲用数组实现，槽位 `(seq-1) % 1000`，写入覆盖、读取比较槽内
  实际序号。查找 O(1)，空间恒定 1000，与客户端历史长度无关。
- **纯重放组**的“成功/失败”按其历史 verbatim 结果汇总：全为
  applied/merged 才算成功，供同批后续新组的依赖判定使用；纯重放组本身
  **不重新评估依赖**（它在历史上已被解决过一次）。这是差分测试中暴露并
  固化的关键语义。

## 4. 事务组判定

对每个含新操作的组：

1. 在**组开始时刻**为被触碰字段拍快照（只拍组内出现的字段，O(组大小)）。
   组内每个操作都基于该快照判定，不看组内前序操作效果。
2. 顺序评估新操作，命中第一个失败即停止后续判定：
   - 种类不符 → `kind_mismatch`；
   - Set：`version<baseVer` → `ahead`；`version>baseVer` 且当前值等于写入值
     → `merged`（无变化），否则 `conflict`（带回当前值/版本/present）；
     `version==baseVer` → 通过；
   - Add：相对组快照累加，净结果越界 `[-10^15,10^15]` → `overflow`。
3. 首失败操作报具体原因；同组其余**新操作**一律 `group_aborted`（连带）。
   重放槽位保持 verbatim，不被连带覆盖。
4. 组全成功才提交：
   - Set 仅当“使不存在字段出现”或“写入值与快照不同”才算有效变更；
   - Add 仅当净增量非零才算有效变更；
   - 至少一个有效变更时，文档修订号 +1，所有有效变更字段版本置为新修订号。

**依赖**：声明依赖前组的组，若前一组不是“全 applied/merged”（含因依赖
而失败），整组直接 `dependency_failed`，不判定；该失败继续向后传播。
依赖判定与“前一组是否也声明了依赖”无关，只看前一组的最终成败。

每个新操作无论成败都消耗序号；整批被拒绝不消耗。

## 5. 关键取舍与被放弃的方案

- **单把全局锁 vs 分片锁/无锁 CRDT**：选择单锁。规格要求“结果等价于某个
  串行顺序 + 批次原子可见 + 确定性重放”，单锁直接且可证明地满足；Add 的
  并发可交换性、Set 的版本仲裁都在同一临界区内完成，避免了跨字段提交的
  部分可见问题。分片锁能提高吞吐，但跨字段同事务组的原子提交需要两阶段
  协调，复杂度高且无额外正确性收益，故放弃。
- **每客户端只留 1000 结果 vs 全量历史**：用定长环。规格明确只要最近 1000，
  全量 map 会让内存随历史无限增长，放弃。
- **组快照只拍触碰字段 vs 全文档拷贝**：生产实现只拷贝组内字段，O(组大小)。
  对照用的朴素模型故意全量拷贝文档，两者结构不同以便交叉验证。
- **Add 组内判定**：不顺序写临时值，而是相对组快照累加“净增量”，既符合
  “都基于组开始状态”，又能在越界时整组回滚。
- **拒绝在持锁前后分两段**：纯结构错误无需抢锁即可快速拒绝；需要 schema
  的错误在持锁后判定。两段合起来仍构成“参数非法”这一个优先级类别。

## 6. 复杂度

- `Sync`：时间 O(k)（k 为批内操作数），与文档字段总数、文档总数、
  客户端历史长度均无关；额外空间 O(k)。
- 重放结果查找：O(1)/操作；环空间 O(1000)/客户端文档。
- `Get`：O(F)（F 为该文档字段数），仅用于读取快照，不在 Sync 热路径。

Benchmark（`go test -bench .`）显示：schema 字段从 10 增至 10000、外加
1000 个无关文档时，固定 50 操作批次的耗时不随之增长；满环重放查找约
~180ns/操作、3 次小分配（结果拷贝）。

## 7. 本地验证方法

```bash
export PATH=$PATH:/usr/local/go/bin
go test ./... -race -count=1          # 全量 + 竞态
go test ./collab -run TestRandomDifferential -v   # 2000 组随机差分
DIFF_TRIALS=20000 go test ./collab -run TestRandomDifferential  # 加大组数
VERBOSE_DIFF=1 go test ./collab -run TestRandomDifferential     # 落完整日志
go test ./collab -run xxx -bench .     # 性能边界
go vet ./... && gofmt -l collab
```

差分测试的日志在不一致时通过 `t.Log` 打印每个批次的输入（序号、Set 值/
基线版本、Add delta、组、依赖）、输出（每操作类别与冲突时的当前值/版本）
和拒绝原因；`VERBOSE_DIFF=1` 时另写 `/tmp/collab_diff.log`。生产侧可用
`Server.SetLogger(NewTextLogger(w))` 打开等价的审计日志。

## 8. 文件组织

- `types.go`：常量、枚举、`Op`/`OpResult`/`DocSnapshot`、拒绝错误。
- `state.go`：文档/客户端/环形缓冲、`Create`/`Get`/`Pending`。
- `sync.go`：`Sync` 批次校验、重放切分、依赖传播、`executeGroup` 提交。
- `logger.go`：输入/输出/判定依据的文本审计日志。
- `*_test.go`：手工用例、朴素模型、随机差分、并发可串行化、benchmark。
