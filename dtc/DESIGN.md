# 车载诊断故障码（DTC）生命周期管理器 — 设计说明

`dtc` 包根据监测结果、点火循环与暖机循环事件，维护每个故障码的
待定（pending）、确认（confirmed）、愈合（healed）与清除，并管理全车唯一的
冻结帧槽位。本文档记录模块划分、关键取舍、被放弃的方案与本地验证方法。

## 模块划分

| 文件 | 职责 |
| --- | --- |
| `types.go` | 配置 `Config`、事件 `Event`、查询快照 `Snapshot`、判定 `Judgment` 等公共类型与配置校验 |
| `errors.go` | 可区分、有序的错误码 `ErrCode` 与错误类型 `Error` |
| `debounce.go` | 单故障码、单点火循环的去抖计数器（纯值逻辑，无副作用） |
| `cycle.go` | 一个点火循环的上下文：本循环内有上报的故障码条目 + 暖机判定（冷却液最低/最高采样） |
| `state.go` | 单个故障码的持久生命周期记录及其状态机迁移（待定/确认/愈合/自动清除） |
| `freezeframe.go` | 全车唯一冻结帧槽位的占用、按严重度替换与释放 |
| `manager.go` | 门面：事件校验（按优先级）、路由、点火关结算、诊断仪清除、查询、并发控制 |

协作关系：`Manager` 持有注册表（配置）、生命周期记录表（历史）与当前
`cycleContext`；监测上报先经 `debouncer` 判定，再驱动 `dtcState` 迁移并可能
触发 `freezeFrameSlot` 竞争；点火关时 `Manager` 只遍历本循环上下文中的条目，
调用 `dtcState` 的结算方法完成确认/愈合/自动清除。

## 关键取舍

- **循环数据与历史数据分离**。去抖值、本循环判定、发生次数是否已计等
  “每循环”数据全部放在 `cycleContext` 里，点火关时整体丢弃（无需逐个清零）；
  持久记录 `dtcState` 只含计数器与标志位，内存与历史循环数无关。
- **点火关结算只访问“本循环有上报”的故障码**。规范决定了无上报的循环对任何
  计数器都无影响（监测未完成的循环既不增加也不清零连续失败数；无上报则无暖机
  计数资格），因此结算成本只与受影响故障码数相关。该性质用
  `Manager.WorkUnits()` 工作量计数器对外暴露，并由
  `TestCostIndependentOfHistory` 以 100 / 100000 两档历史对照验证（两档工作量
  必须完全相等）；`BenchmarkIgnitionOffSettlement` 提供时间维度的旁证。
- **并发模型：单互斥锁**。所有公开方法在同一把 `sync.Mutex` 下执行，任意并发
  调用天然等价于某个串行顺序（线性化点即锁的获取）。在故障码数量级下锁竞争
  不是瓶颈，换来的是实现与推理的极简。
- **发生次数按“每个失败循环计一次”解释**。规范中“本次点火循环内首次判为失败
  时……发生次数加一”按循环解读：同一循环内通过转失败不再计，下一个失败循环
  再计一次；已愈合码再次失败同样加一并重新进入待定。冻结帧的捕获则严格按
  “进入待定”这一跃迁（首次失败或愈合/清除后再失败）触发。
- **愈合与自动清除共用同一个“连续无故障暖机”计数器**。愈合（达到
  `HealWarmupCycles`）后计数器不清零而是继续累积，达到 `AutoClearWarmups` 时
  彻底删除记录；其间任何失败循环在点火关结算时将其清零。计入资格统一为
  “暖机循环 ∧ 监测完成 ∧ 无失败”。
- **冻结帧数据来源**。车速与冷却液温度取自触发失败判定时刻之前最近一次被接受
  的环境采样（从未采样则为零值），里程与时刻取自失败判定事件本身。槽位只在
  占用者被彻底清除（自动清除）或诊断仪清除时释放，不自动让位。
- **错误优先级用检查顺序保证**。`Handle` 依次执行：参数非法 → 时刻/里程回退 →
  事件顺序非法 → 故障码未登记 → 状态不允许；任一失败即返回，且所有校验先于
  任何状态修改，因此被拒绝的事件（包括时间/里程水位线）不改变任何状态。
  “诊断仪清除时点火未关”归入“状态不允许”，使五类错误各有明确触发路径。
- **注册与生命周期分离**。`Register` 是配置而非事件（无时刻、随时可调用）；
  诊断仪清除只清状态与历史，保留注册；自动清除删除的是生命周期记录，已注册
  但无记录的故障码查询返回零快照，未注册的查询返回“故障码未登记”。

## 被放弃的方案

- **事件溯源/全量历史回放**：保留全部事件、查询时重放。语义最直白，但单次
  查询与结算开销随历史增长，违反复杂度约束，仅作为测试中的朴素对照模型
  （`naive_test.go`）存在。
- **点火关时遍历全部故障码做结算**：实现简单，但开销随注册/历史故障码总数
  增长；被“只遍历本循环有上报的故障码”取代。
- **读写锁（RWMutex）**：查询用读锁可提升并发度，但查询会读取被写者更新的
  循环上下文与冻结帧，收益有限且增加数据竞争风险；先保持单锁，确有瓶颈再
  演进。
- **为每个故障码持久保存去抖值**：规范要求点火关清零，放入循环上下文随循环
  销毁即可，持久化反而需要在点火关时逐个重置（O（故障码总数））。
- **冻结帧释放后自动让给次严重故障码**：规范明确“不自动让给他人”，故不维护
  候选队列。

## 本地验证方法

```bash
export PATH=$PATH:/usr/local/go/bin   # 如 go 不在 PATH
go test ./dtc/                        # 全部单元 + 差分 + 复杂度测试
go test ./dtc/ -race                  # 并发正确性（竞态检测）
go test ./dtc/ -run TestDifferentialRandom -v   # 打印每个事件的输入/输出/判定依据
go test ./dtc/ -run TestCostIndependentOfHistory -v  # 两档历史的工作量对照
go test ./dtc/ -bench BenchmarkIgnitionOffSettlement -benchtime 1000x
gofmt -l dtc/ && go vet ./dtc/
```

测试构成：

- `manager_test.go`：确定性场景 —— 去抖恰到两条判定线并夹紧、同循环
  失败→通过→失败、监测未完成/空循环、确认与愈合恰好满足与差一、暖机温升
  恰等阈值、冻结帧严重度相等不替换/更高替换、诊断仪清除释放槽位与里程基准、
  自动清除释放槽位、已愈合码再次失败、五类错误的优先级与“被拒绝事件不改变
  状态”（含水位线不前进）、并发压力（配 `-race`）。
- `differential_test.go` + `naive_test.go`：独立编写的全量重放朴素模型与增量
  管理器在 40 组种子 × 400 个随机事件（含约 8% 故意构造的非法事件）上逐事件
  对照错误码、全部故障码快照与冻结帧；日志打印每个事件的输入、两者输出与
  判定后的完整状态。
- `complexity_test.go`：用 `WorkUnits` 计数器证明单次监测上报与点火关结算的
  工作量与历史循环总数无关（两档对照必须完全相等），并给出基准。
