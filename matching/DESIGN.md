# 单品种限价撮合引擎设计说明

支持普通限价、冰山（Iceberg）与隐藏（Hidden）委托。目标是让“同价位显示量 →
冰山补充 → 隐藏量”的成交次序，以及改量/撤单对排队位置的影响，在任何操作序列下
都有**唯一确定**的结果。

## 1. 模块划分

| 单元 | 文件 | 职责 |
| --- | --- | --- |
| 对外类型 | `types.go` | `Side / OrderType / Status / OrderParams / Order / Fill / DepthAtPrice` |
| 可分类错误 | `errors.go` | `EngineError` + `ErrorKind`，错误只报第一个且按优先级 |
| 引擎与锁 | `engine.go` | `Engine`、`Submit / Cancel / ReplaceQty`、全部只读查询 |
| 撮合规则 | `core.go` | 参数校验、逐价位/逐批撮合、记账守恒、挂簿、摘除、快照 |
| 价位内队列 | `book.go` | 显示批双链表、隐藏委托双链表、显示量汇总 |
| 价位索引 | `treap.go` | 以价格为键的 treap：极值/前后继/增删均 O(log L) |

`naive/` 是**完全独立**的第二实现（切片 + 线性扫描，按规格文字直译），
仅供 `difftest/` 差分对照，生产代码不依赖它。

## 2. 关键数据结构

- 每侧一棵 `priceTree`（treap），键为价格，节点即 `level`。
- 每个 `level` 含：
  - 显示批双链表 `visHead…visTail`，节点 `batch{order,left}`：
    - 普通委托：一个批，`left = 剩余量`；
    - 冰山委托：一个批，`left = min(显示量参数, 剩余总量)`；
  - `visSize`：该价位所有当前显示批 `left` 之和，即公开显示总量；
  - 隐藏委托双链表（按接受/重排顺序即序号顺序）。
- 委托内部结构 `order` 同时保存账本（total/filled/remaining）与簿内定位指针
  （`batch` 或 `hiddenNode`、所在 `level`），撤单/改量可 O(1) 摘除，无需扫描。

“同价位成交次序”直接由两个链表表达：显示链从队头吃；冰山批吃完后把新批
**append 到队尾**；只有显示链为空（意味着所有冰山储备也已以补批形式耗尽）时，
才进入隐藏链，按链序（序号升序）吃。

## 3. 撮合规则要点

1. 交叉判定：买价 ≥ 卖价（恰等成交）；成交价始终取被动方价格。
2. 主动委托按对手价“由优到劣”推进：买吃卖取最低卖价、卖吃买取最高买价，
   通过 treap 的 `min/max` 与 `succ/pred` 定位。
3. 一次成交（一条 `Fill`）**只消耗一个显示批或一个隐藏委托的一次撮合量**，
   绝不跨批；主动委托不足时，被动批保留在队头、位置不变。
4. 冰山当前批被完全吃完且仍有剩余：立即以 `min(showParam, remaining)` 补批，
   追加到显示链队尾，失去原时间优先；新批在**同一次**吃单的后续循环即可被吃到。
5. 隐藏委托：显示链清空之前不参与；隐藏委托之间按序号升序；部分成交后仍占队头。
6. 主动冰山：先以全部量参与撮合，仅把未成交剩余挂簿，挂簿时才切第一个显示批，
   因此“只有挂簿部分才有显示量”。
7. 价位节点仅在显示链与隐藏链都为空时删除；主动方量尽时立即停止，不越价。

## 4. 撤单与改量

- 撤单：凭 `order.batch/hidden` 指针 O(1) 摘除，已成交部分不动，状态置撤销。
- 改量入参为“新的剩余总量”，内部令 `total = filled + newRemaining`，
  从而始终满足 `filled + remaining = total`。
  - 减量（新 ≤ 旧）：保留原排队位置；若当前显示批 `left > 新剩余`，把该批截短到
    新剩余（同时修正 `visSize`）。
  - 加量（新 > 旧）：取下一个全局序号（失去时间优先），从原位置摘除后排到同价位
    队尾；冰山以满批 `min(showParam, 新剩余)` 重新开始；隐藏委托移到隐藏链队尾。
- 已完成/已撤销的委托拒绝撤单与改量。

## 5. 错误分类与优先级

`ErrorKind`：`ErrInvalidParam > ErrDuplicateClientID > ErrOrderNotFound >
ErrOrderCompleted > ErrOrderCancelled`（后两者用于改量/撤单，完成先于撤销判定）。

- 新委托：先校验参数，再查编号重复；被拒不分配序号、不写 map、不产生成交。
- 改量/撤单：先校验新量为正，再查存在性，再查终态。

## 6. 并发、确定性与查询

- 引擎以单一 `sync.Mutex` 串行化所有公开方法；并发调用等价于某个（由锁决定的）
  串行顺序。共享状态不向调用方泄漏内部结构：查询返回拷贝。
- 确定性：所有序号、成交序号、排队顺序只依赖操作输入顺序；treap 使用固定种子，
  即使树形态也与重放无关（功能结果本与形态无关）。相同操作序列重放得到逐笔相同的
  成交序列（`TestReplayDeterminism`）。
- 查询：最优买卖价、`VisibleDepthAt`、`SnapshotDepth`（从优到劣）、`GetOrder`、
  `Fills` 均为只读，在锁内取拷贝。

### 关于“隐藏委托是否决定最优价”的取舍

规格明确要求隐藏量不计入**显示量汇总**，但最优买卖价代表“真实可立即成交的价位”。
若最优价只看显示量，会出现“查询说该侧无价、新委托却在该价位成交”的矛盾。
因此本实现让**最优价包含隐藏流动性**（隐藏仍不出现在任何显示量数字中）。
朴素模型采用同一语义，差分测试对二者逐字段比对，保证取舍一致、可复现。

## 7. 撮合开销（可验证的论证）

设一次 `Submit` 触及 K 个价位、B 个显示批（含补出的新批）、H 个隐藏委托次。

- 定位每个价位：treap `min/max` + `succ/pred`，O(log L)；价位清空时删除 O(log L)。
- 每个显示批：链表头取/尾插/摘除均 O(1)；一次循环恰好处理一个批。
- 每个隐藏委托：链表头取/摘除 O(1)。
- 撤单/改量摘除 O(1)，加量重入队尾 O(1)，加量涉及的价位插入仅在价位缺失时 O(log L)。

因此一次撮合的时间为 O((B + H) + K·log L)，**只与被触及的批数与价位数有关**，
不随簿内委托总数或同价位委托数增长。论证的可执行验证见
`BenchmarkSweepFixedTouches`：簿规模从 1,000 增至 100,000（100 倍），
固定只触及 1 价位 1 批时，单次耗时保持在约 1µs 量级，不随规模线性增长；
`BenchmarkAggressiveNoCross` 展示大簿中的插入/撤单往返仅受价位数的对数影响。

## 8. 被放弃的方案

- **每侧一个有序 map（红黑树）价位 + 价位内 Go slice**：撤单/改量需在 slice 中
  线性定位委托，单价位委托多时开销退化，违背“不随同价位委托数增长”。改用双链表 +
  委托回指针，摘除 O(1)。
- **价位用堆（heap）**：撤空任意价位后堆删除需要懒标记，且“跨价位顺序推进”要反复
  弹堆；treap 的 succ/pred 更直接，极值与前后继都是 O(log L)。
- **冰山储备单独建队列**：会造成“显示批与储备”两处状态需要同步，减量截短与撤单
  容易不一致。最终只保留“当前显示批 + order.remaining”，储备由 remaining 隐式表达。
- **改量也触发重新撮合**：规格把改量定义为簿内排队调整，不产生成交，故
  `ReplaceQty` 不返回成交、不触碰对手盘。
- **无锁/分段锁并发**：会使“等价于某个串行顺序”的证明与重放确定性复杂化；
  单锁在该规模下已足够，且让可串行化成为显而易见的不变量。

## 9. 本地验证方法

```bash
go test ./...                       # 全量单元 + 随机差分
go test -race ./...                 # 竞态检测（含并发混合调用）
go test -v ./difftest/ -run TestDifferentialLogging
                                    # 打印输入/输出/守恒判定日志
go test -run=NONE -bench=. ./matching/
                                    # 开销不随簿规模增长的基准证据
go vet ./... && gofmt -l .
```

- `matching/scenario_test.go`、`matching/reject_test.go`：规格点名的全部边界场景。
- `difftest/diff_test.go`：400 条、每条 250 个随机操作的双实现差分，
  比对错误分类、最优价、全价位显示深度、完整成交序列；失败时打印完整输入日志与
  逐委托状态差异。
- `difftest/invariant_test.go`：filled+remaining=total 守恒、台账与逐笔成交吻合、
  重放确定性、并发安全（配合 -race）。
