# 分层备份保留管理服务 — 设计说明

包路径：`ontology/backupretention`（无第三方依赖，仅用 Go 标准库）。

## 1. 模块划分与职责

| 文件 | 职责 |
| --- | --- |
| `doc.go` | 包级概念文档。 |
| `errors.go` | 可区分错误类别 `ErrorKind`、`ServiceError`、`ErrorKindOf`。 |
| `backup.go` | 备份记录与注册表。登记=单次 map 插入，`O(1)`，不随存量增长。 |
| `policy.go` | `Policy`（日/周/月数量）与 0..1000 范围校验。 |
| `periods.go` | UTC 周期序号：日（自纪元整日）、周（周一首日的日序号）、月（连续公历月序号）。 |
| `recovery.go` | 损坏沿祖先链传播的**线性**可恢复性计算。 |
| `planner.go` | 三层选举、法律保留、依赖闭包，以及计划的确定性排序。 |
| `service.go` | 并发安全门面：加锁、错误优先级、单调时钟、登记/损坏/法律/策略/计划/清理。 |
| `logger.go` | 每条操作输入、输出与判定依据的结构化日志。 |

模块协作方向：`service → planner → recovery/periods + registry/policy`；
`planner` 不触碰锁与时钟，是对 `(注册表, 策略, now)` 的纯函数，便于独立验证。

## 2. 关键数据与算法

### 2.1 周期序号（全部 UTC，单位为秒）

- 日：`floor(now / 86400)`，自 1970-01-01 起的整日数。用向负无穷取整的
  `floorDiv` 处理负时刻；Go 的 `/` 对负数向零截断，不能直接用。
- 月：先用 Howard Hinnant 的 civil-from-days 算法把日数换成 `(年,月,日)`，
  再取 `年*12 + (月-1)`。28/29/30/31 天不等的月长因此天然正确，无需月表。
- 周：先得到整日数 `d`，再减去“距本周一的偏移” `weekday0(d)`（周一=0…周日=6，
  由 `1970-01-01 是周四` 推出），得到“本周一的日序号”。周可自然跨年、跨月。

选举窗口：当前周期 `c = periodOf(now)`，每层数量 `N`，则考虑周期
`[c-N+1, c]`，**含当前周期且空周期照样占用名额**。窗口外备份一律不直接保留。

### 2.2 选举

每层对备份单次扫描，按周期分桶并维护“当前胜出者”，比较规则为
`(createdAt 更大)` 或 `(createdAt 相等且 ID 字典序更大)`。
候选条件：`createdAt <= now` 且可恢复。整桶不存在即该周期无代表。
三层选举结果取并集，同一备份可在多层当选，原因里同时列出各层。

### 2.3 可恢复性：为什么不是每备份走一遍父链

朴素做法对每个备份沿父链走到根，单链场景是 `O(n^2)`。
`recovery.go` 用“每条父边只消费一次”的摊还算法：
对一个尚未定案的备份，沿父指针向上记录路径，直到遇到已定案祖先、损坏节点或根，
再把结论沿路径向回传播。每条父边至多进入某条路径一次，
总时间 `O(n + 所有链长度之和)`，额外空间 `O(n)`。

### 2.4 依赖闭包：同样不重复走链

保留根 = 直接代表 ∪ 法律保留。对每个根沿父链向上，把祖先标记为
`Dependency`；用一个全局 `visited`，一旦走到此前已闭包的祖先即停止。
整个闭包阶段每条父边最多被跟随一次，仍是 `O(n + 链长之和)`。

关键点：依赖原因只打在“被后代需要”的祖先上；法律保留的根自身带 `LegalHold`，
其祖先带 `Dependency`（二者可在同一备份叠加）。损坏祖先也必须保留，
因为依赖保护不看可恢复性。

### 2.5 清理与“无孤儿”

`Cleanup = computePlan(now)` 后删除 `Deletable`。由于依赖闭包，
“可删除集合对后代封闭”：若某备份的祖先可删而它自身保留，祖先会被闭包进保留集合，
矛盾。因此删除集合内的每个备份，其任何存活后代也在删除集合内，
删除后注册表中不存在父缺失的增量。

幂等：同一时刻连续两次 `Cleanup`，第二次基于“第一次删除后”的状态重新计算，
此时保留根仍保留、其依赖闭包仍在，删除集合为空。第二次不删任何备份。
删除后标识不再已登记，但允许同标识重新登记（map 中无历史痕迹）。

## 3. 时钟与错误优先级

所有带时刻方法在锁内按固定顺序判定，**只报次序最靠前的一类**：

- 登记全量：参数非法 → 时钟回退 → 标识重复。
- 登记增量：参数非法（含空父 id）→ 时钟回退 → 标识重复 → 父不存在 → 时序矛盾。
- 损坏/法律：参数非法 → 时钟回退 → 备份不存在。
- 策略：时刻参数非法 → 时钟回退 → 层数量越界（`KindLayerOutOfRange`）。
- 计划/清理：参数非法 → 时钟回退。

只读 `Plan` 也推进时钟基线（它是“带时刻操作”），否则无法对后续更早的时刻报回退。
被拒绝操作在任何状态写入之前返回，故不留痕。

关于 `KindTimeContradiction`：在“全局单调时钟 + 父必先于子登记”的合法外部序列里，
新子备份的时刻 `>= 时钟基线 >= 父登记时刻`，该错误通常先被时钟回退吸收；
但判定仍按题面独立保留并规定次序，白盒测试（构造晚于时钟的父）验证该分支可达。

## 4. 并发

单 `sync.Mutex` 串行全部读写。正确性优先，临界区为 map 操作与线性时间计划，
无 I/O 阻塞（日志为内存/普通 writer 写入）。`go test -race` 下并发登记、
损坏、法律、只读计划均通过，且多次计划结果逐字节一致。

## 5. 复杂度（可验证）

- 登记：`O(1)`（参数校验 + map 插入），不遍历存量。
- 计划/清理：可恢复性 + 三层选举 + 依赖闭包均为线性，
  总 `O(n + 链长之和)`（实现上每条父边至多被跟随常数次）；
  另有输出排序 `O(n log n)`，不影响“判定阶段线性”的结论。
- 空间：`O(n)`。

基准（本机 arm64，见 `complexity_test.go`）：

```
BenchmarkRegister/existing=1000      ~207 ns/op
BenchmarkRegister/existing=100000    ~235 ns/op     # 存量 ×100，耗时基本不变
BenchmarkPlanDeepChain/n=10000       ~7.4 ms/op
BenchmarkPlanDeepChain/n=100000      ~104 ms/op     # n ×10，时间约 ×14（线性）
```

## 6. 关键取舍与被放弃的方案

- **放弃“每备份独立向上走链”**：实现简单但 `O(n^2)`，改为路径摊还 + 全局 visited。
- **放弃为每层/每周期预分配 map 的窗口式存储**：周期窗口可能很大（N 最大 1000），
  且绝大多数周期为空；改为单遍扫描 + 分桶，空周期零成本。
- **放弃读写锁/无锁结构**：清理会批量改 map，读计划也依赖一致快照；
  单锁最简单且可证明串行等价，复杂度要求并未受限。
- **法律保留的祖先不带 `LegalHold` 原因**：题面区分“被保留原因”，
  祖先仅因被依赖而保留，记 `Dependency`；法律原因只属于被显式设置的备份本身。
  二者可在同一备份叠加。
- **时刻单位固定为 UTC 秒、上限 `2^62-1`**：覆盖远超现实的范围，
  同时保证周期计算不溢出 int64。
- **朴素模型不复用生产算法**：周期用标准库 `time` 重算、计划逐层逐周期逐备份扫描，
  刻意保持“题面直译”，作为独立参照实现。

## 7. 本地验证方法

```bash
# Go 工具链（仓库要求 1.26+）
export PATH=$PATH:/usr/local/go/bin
export GOCACHE=/tmp/gocache   # 如默认构建缓存目录只读

go test ./...
go test -race -count=3 ./backupretention
go test -v ./backupretention -run TestNaiveDifferential   # 随机差分（固定种子）
go test -v ./backupretention -run TestDifferentialLogIsPrinted  # 打印操作日志
go test ./backupretention -bench Benchmark -run '^$'       # 复杂度基准
go vet ./...
gofmt -l .
```

差分测试 `diff_test.go` 以 7 个固定种子各重放 1500 条随机操作
（登记/增量/损坏/法律/策略/计划/清理 + 时钟回退与层越界注入），
逐条比对：错误类别、保留/删除集合、每个备份的保留原因、实际删除集合、最终注册表。
真实服务的日志通过 `WithLogger` 输出；朴素侧日志由测试打印，均包含输入、输出与判定依据。
