# 厢式货车配载与卸货顺序校验 —— 设计说明

## 1. 模块划分

代码位于 `vanload` 包，按职责拆分为相互协作的小模块：

| 文件 | 职责 |
| --- | --- |
| `cargo.go` | 领域类型：货物 `Cargo`、类别 `Category`、分区配置 `Compartment`、拒绝原因 `RejectKind` 及其严重度、错误类型 `Reject` |
| `state.go` | 可变状态及其**聚合**表示：每分区总载重/总容积、各类别件数、停靠点序号分布；状态深拷贝 |
| `constraints.go` | 纯函数约束判定：四类约束的逐分区“首个失败原因”与整体严重度归并 |
| `system.go` | 线程安全门面：单件装货、卸货、三类只读查询；拒绝优先级的执行顺序 |
| `batch.go` | 批量装货：副本试装 + 原子提交，全有或全无 |
| `log.go` | 日志接口 `Logger`、文本日志器与输入/输出/判定依据的摘要格式 |
| `naive.go` | **独立编写**的朴素参考模型（枚举全部在车货物），仅供测试对照 |
| `cmd/vanload-demo` | 可运行演示，打印每次操作的输入、输出与判定依据 |

## 2. 核心模型

### 2.1 顺序约束的等价判定

题设顺序约束（跨分区）：

> 卸货序号更小的货物，其分区编号不得**小于**序号更大货物的分区编号。

即“更早卸的货物必须更靠后（分区编号更大或相等）”。同分区混装任意停靠点不做限制。

设待放货物停靠点为 `t`，候选分区为 `k`：

- 若 `k` **前方**任一非空分区存在停靠点 `< t` 的货物，则该货物更早卸却在更前分区 → 冲突；
  只需知道前方各分区的 `minStop < t`。
- 若 `k` **后方**任一非空分区存在停靠点 `> t` 的货物，则该货物更晚卸却在更后分区 → 冲突；
  只需知道后方各分区的 `maxStop > t`。

因此对所有候选分区统一成立，只需两个长度为分区数的数组：
`prefixMin[k]`（分区 1..k 的最小停靠点）与 `suffixMax[k]`（分区 k..N 的最大停靠点），
每个候选分区的顺序检查为 O(1)。

### 2.2 隔离约束

仅与**同分区**货物有关。分区聚合状态保存 `foodCount / flammableCount / oxidizingCount`
三个计数（普通货物无需计数）：

- 易燃入区：区内 `oxidizingCount>0` 或 `foodCount>0` 即冲突；
- 氧化入区：区内 `flammableCount>0` 或 `foodCount>0` 即冲突；
- 食品入区：区内 `flammableCount>0` 或 `oxidizingCount>0` 即冲突；
- 普通：永不冲突。

### 2.3 载重与容积

区内保存总载重与总容积；放入后 `used + x <= limit`（相等允许），否则分别记超重/超容。

### 2.4 单件放置算法

1. 计算 `prefixMin / suffixMax`（仅依赖分区聚合）；
2. 按分区编号 1..N，依次按“顺序→隔离→超重→超容”的严格顺序找该分区**首个**失败约束；
3. 第一个无任何失败的分区即答案（编号最小）；
4. 全部失败时，整体原因取各分区首个失败原因中**严重度最低**者
   （顺序冲突 > 隔离冲突 > 超重 > 超容，数值越靠后越“轻微”，越容易被整体报出），
   同时在返回值中保留每个分区的具体原因，供日志与测试核验。

## 3. 关键取舍与被放弃的方案

- **放弃“枚举在车货物两两比较”作为生产实现。**
  朴素实现（`naive.go`）每件货物判定需扫描全部在车货物，记录考察数随车上件数线性增长；
  生产实现只维护分区聚合与前/后缀数组，单件判定考察的“货物记录数”恒为 0——
  它只读取 N 个分区的标量字段，时间复杂度为 **O(N)**，与车上已装货物总件数 M **无关**。
  朴素模型被保留为随机差分测试的对照预言机。

- **放弃“每件货物都参与顺序判断”，改为每分区两个极值。**
  顺序关系只与跨分区的停靠点相对大小有关，同区内允许混装，
  因此每分区只需 `minStop / maxStop`（由 `stopCount` 在卸货后精确维护）。

- **批量装货放弃“边装边回滚”，采用“克隆状态试装 + 一次性指针替换”。**
  试装在深拷贝上进行，任何一件失败只丢弃副本，真实状态零改动；
  全部成功后在写锁内用一个指针赋值提交。读操作持读锁返回自建切片，
  因而要么读到整批之前、要么读到整批之后，绝无半批状态。

- **并发控制选择单把 `sync.RWMutex`。**
  要求所有操作可并发且等价于某串行顺序，单锁最简单且可验证；
  读写锁保证只读查询可并发且彼此一致。未采用分段锁/无锁结构，
  因为正确性与可审计性优先于吞吐；分段锁可在不改变接口的前提下以后优化。

- **拒绝原因采用显式优先级短路。**
  参数非法 → 编号重复 → 停靠点已过 → 四类约束，按顺序检查、命中即返回，
  天然满足“被拒绝操作不改变任何状态”（所有变更都发生在全部检查通过之后）。

- **卸货顺序错误的判定**只看车上货物最小停靠点：
  `minOnboard < stop` 即拒绝；这样不必关心历史上是否到过哪些停靠点。
  “已处理”只看 `stop <= arrivedStop`；空停靠点成功并推进 `arrivedStop`。

- **确定性**：放置只依赖状态与确定性的编号升序扫描；
  卸货返回编号按升序排列（插入排序，零依赖）；map 只用于查找不参与输出顺序，
  因此相同操作序列重放得到完全相同结果。

## 4. 拒绝原因严重度与归并

| 原因 | 严重度序 | 含义 |
| --- | --- | --- |
| 顺序冲突 | 最高 | 违反“早卸靠后”的跨分区位置关系 |
| 隔离冲突 | 次高 | 易燃/氧化互斥，食品与二者互斥 |
| 超重 | 次低 | 放入后分区载重超过上限 |
| 超容 | 最低 | 放入后分区容积超过上限 |

各分区按上表自上而下取首个不满足约束；整体取所有分区结果中严重度**最低**的一类。
所以“只要有分区仅因容积不足而失败，就报超容”。

## 5. API 摘要

- `New(compartments, ...Option) (*System, error)`
- `Load(Cargo) (LoadResult, error)`：返回确定分区；失败为 `*Reject`
- `BatchLoad([]Cargo) (BatchLoadResult, error)`：全有或全无，失败报最小下标
- `Unload(stop int) (UnloadResult, error)`：`UnloadOK / UnloadEmpty / UnloadAlreadyProcessed`
- `RemainingCapacities() []Capacity`、`Locate(id) (int,bool)`、`ArrivedStop() int`
- `WithLogger(Logger)`：记录每次操作的输入、输出与判定依据

## 6. 并发与不变量

- 所有写操作在写锁内完成；所有查询在读锁内基于当前状态复制出返回值。
- 任何时刻（锁保护下）分区载重/容积不超限，跨分区顺序与同区隔离恒成立；
  变更只通过“已验证可行后”的 `addCargo` 生效，卸货通过对称的 `removeCargo` 生效。
- 批量原子提交，查询不可能读到批量中间态（测试 `TestConcurrentSnapshotNeverPartial`
  在高并发下断言车上件数恒为批量大小的整数倍）。

## 7. 本地验证方法

```bash
# 本仓库 Go 位于 /usr/local/go/bin；如不在 PATH 请先 export
export PATH=$PATH:/usr/local/go/bin
export GOCACHE=/tmp/gocache   # 仅当默认缓存目录只读时需要

go test ./vanload -v                       # 全部用例（含随机差分、并发、重放）
go test -race -count=3 ./vanload           # 竞态检测 + 重复运行
go test -coverprofile=cover.out ./vanload  # 覆盖率（当前约 94%）
go tool cover -html=cover.out
go vet ./...
go run ./cmd/vanload-demo                  # 打印输入/输出/判定依据日志
```

随机差分测试 `TestRandomDifferential` 生成数百条随机操作序列
（单件装货、跳号/重复卸货、查询），每一步把聚合实现与朴素枚举实现的
成功/失败、归并原因、逐分区原因、卸货明细、剩余容量与全部货物位置逐项比对。
