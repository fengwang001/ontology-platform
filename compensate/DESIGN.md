# 变更流消费与恰好一次补偿子系统 — 设计说明

包路径：`compensate`（Go）。

本子系统消费表示「本体动作已成功执行」的变更事件，并对每条事件**恰好触发一次**
关联的补偿型动作。补偿由若干项幂等副作用组成，以 saga 风格逐项提交；消费端在
任意时刻崩溃重启后能够精确续作，绝不重复施加已生效的副作用。

---

## 1. 要解决的问题与硬约束

1. 同一条变更事件可能因网络重试被重复投递；补偿必须恰好一次（连部分副作用都不能重复）。
2. 「内容完全等价的两次独立真实调用」必须各自补偿一次——它与重复投递表面相似但本质不同。
3. 补偿对多个对象的多项副作用要求原子性语义：要么全部生效，要么停在已确定的边界上续作。
4. 崩溃可能发生在「只有部分副作用已提交」时，重启后必须识别边界并补齐，而非从头重放。
5. 撤销（undo）与补偿并发到达时，裁决必须确定，不随到达的具体时刻产生不一致。
6. 四类错误必须互斥分类、按优先级只报一类，且任何错误都不得让副作用越过已确定边界。
7. 任意并发操作组的最终可观察结果，必须等价于某个全局串行顺序（严格可串行化）。
8. 去重判定开销必须与历史事件总量无关（O(1)），并可独立验证。

## 2. 核心概念与身份约定

### 2.1 区分「重复投递」与「独立等价调用」（唯一依据：EventID）

- `Event.EventID` 即动作执行标识（ActionExecutionID），由生产者在**动作提交的同一
  事务**内一次性分配并随变更流持久化，全局唯一、不可变、永不复用。
- 同一次动作执行无论被网络重试投递多少次，`EventID` 永远相同 → 判为重复，跳过补偿。
- 调用者在另一时刻再次发起、参数与效果恰好等价的调用是一次**全新执行**，生产者必须
  分配全新的 `EventID`（哪怕 `ActionType`/参数/结果完全一致）→ 各自补偿一次。

系统**不**依据动作参数、时间窗口、内容相似度或业务幂等键做任何去重推断。
这是一个刻意的取舍：把「这两次是不是同一回事」的判断完全前移给生产者的身份分配，
消费端只做机械的、可证明正确的 `EventID` 定点对照，避免启发式误判。

- 同 `EventID` 但**负载内容指纹不同**（`Fingerprint`，见 `identity.go`）被视为
  身份关系不可判定（ID 冲突或流损坏），报 `E3_AMBIGUOUS_IDENTITY`，绝不「按像的那个猜」。

### 2.2 补偿记录状态机（`state.go`）

```
              ┌ record 不存在，裁决事务与撤销标记原子竞争
   (无记录) ──┤
              ├─ undo 标记先提交 ─▶ SUPERSEDED（终态：永久放弃补偿）
              └─ 领取先提交 ─────▶ CLAIMED（补偿不可撤销点）
                                      │ 逐项提交副作用（每项独立事务）
                                      ├─ 崩溃重启 → 按独占键识别已生效前缀，续作
                                      ├─ E1/E2/E4 → FAILED（冻结边界，不扩大副作用）
                                      └─ 全部生效 → COMPLETED（终态）
```

重复投递到达任意终态/中间态都不产生新副作用：`COMPLETED`/`SUPERSEDED` 幂等返回，
`FAILED` 原样返回冻结时的同一类错误，`CLAIMED` 触发续作。

记录键 `comp/rec/<EventID>` **本身就是去重索引**：判定重复只需对该键做一次定点
`Get`，无需任何历史扫描（见 §7）。

## 3. 存储与并发控制：严格可串行化

`Store`（`store.go`）抽象为「在可串行化事务内执行函数体，提交冲突自动整体重试」。
进程内实现 `MemoryStore`（`store_mem.go`）采用：

- 事务开始获取全库版本快照，所有读基于快照；
- 记录读集合（键 → 读到的版本，「键不存在」记为版本 0）；
- 提交临界区内校验：每个读过的键当前版本必须与读集合一致，否则 `ErrConflict` 中止重试；
- 缺失键谓词锁表 `absentLocks`：裁决事务对「读为不存在」的 `record`/`undo` 键登记
  谓词，提交后保留并标记已提交，拦截后到的插入者（first-committer-wins）。

谓词锁只对 `comp/rec/`、`comp/undo/` 前缀开启（`EnablePredicateLocksFor`），
审计序号、对象业务键等不参与裁决冲突，避免无关读写被误判或产生活锁。

**实现过程中被修复的两个关键正确性陷阱（也是被放弃/警惕的做法）：**

1. *快照缺失读不能二次查当前存储登记版本*。曾为登记「当前版本」而在缺失路径回查
   实时存储，导致返回值（NotFound）与登记版本（可能已存在）矛盾，产生幻读：
   领取事务以为撤销标记不存在而写 CLAIMED，却通过了版本校验。修复为严格以事务开始
   快照登记版本 0，键在事务期间被创建则提交时必然中止重跑。
2. *静默兑现谓词是危险的*。存储层曾在「写 record 时发现 undo 已存在」就直接放行，
   但那次 fn 是在旧快照里执行的、业务逻辑走的是 CLAIMED。修复为：存储层绝不改变
   fn 的语义判断；只在读集合（已通过版本校验、与当前一致）确实观察到配对裁决键存在
   时才允许兑现，而此时 fn 必然已据此走了 SUPERSEDED 分支。

生产环境可把 `Store` 替换为 PostgreSQL `SERIALIZABLE`、FoundationDB 或 etcd 事务；
本包的正确性论证不依赖内存实现的具体并发原语。

## 4. 补偿的原子性与崩溃续作

### 4.1 每项副作用独占一个标记键

每个 `Effect` 必须实现 `OwnedKey(ev, i)`，返回该项副作用**独占拥有**的键
（约定 `comp/fx/<EventID>/<i>`）。Apply 通过 `EffectClaimer.CreateIfAbsent`
对该标记做原子条件插入：

- 标记不存在 → 本事务是施加者：写业务副作用 + 写标记，同一事务提交；
- 标记已存在 → 幂等返回，绝不重复施加业务变更。

并发的重复投递/崩溃续作中，两个事务不可能都成功插入同一此前不存在的标记
（后提交者读集合版本 0 与现实不符而中止；重试时标记已存在）。

### 4.2 崩溃边界（saga 前缀）

每项副作用在**独立的可串行化事务**内提交，因此任意崩溃时刻都存在确定边界：
提交成功前崩溃 ⇒ 该项与后续项均未生效；提交成功后崩溃 ⇒ 重启时按独占键精确识别。
`Record.Applied[]` 位图仅作快速提示，续作时以 `HistoryInspector.EffectApplied`
（默认直接探测独占键）为准重新核实，二者不一致时以实际存储为准。

续作只补齐未生效项，已生效项按标记跳过——这就是「不从头重放、不部分重复」。
故障注入由 `CrashAwareProcessor.SetCrashHook` + `OneShotHook` 提供，
`TestResumeAfterCrashAtEveryBoundary` 对全部 5 个边界逐一验证。

### 4.3 与无关并发修改共存

补偿事务的读集合只包含：补偿记录、本项及后继项的独占标记键、`TargetExists`
显式选择的目标存活键。它**不**读目标对象的其他字段。因此另一条无关事件修改对象
的「负载字段」不会让续作中止；只有真正改动这些依赖键的操作才构成冲突，由 OCC
排序后安全重试。见 `TestResumeCoexistsWithUnrelatedConcurrentModification`。

## 5. 撤销与补偿的裁决

规则（`Processor.UndoArrived` 与领取逻辑共用同一可串行化存储）：

- **领取点（CLAIMED 落库）是唯一线性化分界。**
- 撤销标记在领取之前已提交 → 领取事务读到标记，落 `SUPERSEDED`，永久放弃补偿；
  此后任何重复投递仍是 `SUPERSEDED`，零副作用。
- 领取已提交（哪怕一项副作用都还没做）→ 撤销返回 `UNDO_TOO_LATE`，补偿必须
  继续直至完成；撤销不能中途打断。

领取与撤销在同一个可串行化存储上排序，谁先提交谁生效，不存在「取决于撤销发生在
补偿的哪个瞬间」的模糊窗口。`TestUndoRaceIsDeterministic` 以 200 次随机交织验证：
两种结果互斥且各自的副作用计数严格自洽。

## 6. 错误分类与优先级

| 类 | 含义 | 优先级 |
|---|---|---|
| `E3_AMBIGUOUS_IDENTITY` | 标识无法判定与历史事件的关系（空 EventID、同 ID 不同内容、记录不可读） | 40（最高） |
| `E2_HISTORY_MISSING` | 部分生效后续作所需历史记录缺失，无法确定边界 | 30 |
| `E4_ATOMICITY_VIOLATION` | 顺序原子性校验失败（后继已生效而前驱缺失），记录与现实不符 | 20 |
| `E1_TARGET_GONE` | 补偿目标在消费时已不存在/已被撤销 | 10 |

判定顺序即优先级顺序（见 `applyEffects`：先核实历史 → 再校验顺序原子性 →
最后检查目标存在），因此同一条事件同时满足多类条件时**只报最高优先级一类**。
任一错误都会在同一事务内把记录置为 `FAILED` 并**冻结**：已生效副作用保持不动，
未生效的绝不补做；后续重复投递原样返回同一错误，边界不被跨越。

`TestErrorPriority_*` 覆盖 E3>E2>E4>E1 的两两压制；`FaultyHistory` 注入 E2。

## 7. O(1) 去重与可独立验证性

- 记录键即去重索引，判定一次新事件只对 `comp/rec/<EventID>` 做一次 `Get`。
- 每次去重判定都写一条 `DEDUP_DECISION` 审计，字段含输入 `event_id`、
  `probes`（本次按 EventID 的索引探测次数）与 `conclusion`。
- `TestDedupLookupConstantTime` 在已有 N ∈ {1,64,4096}（race 构建用 {1,64,512}）
  条历史后投递新事件及其重复，断言两次判定的 `probes` 恒为 `"1"`。
  这是一个可独立读取审计、不依赖阅读实现即可复核的 O(1) 证据。

## 8. 审计：判定可事后核查 + 全局顺序证据

`AuditLog`（`audit.go`）的每条记录与触发它的业务写在**同一存储事务**内提交：
业务写不提交则审计不可见，业务写提交则审计必然可见（不会出现「副作用生效却无判定
记录」）。记录带单调递增 `Seq`，已提交 `Seq` 的全序即为并发事务组的一个合法全局
串行顺序证据。审计种类：`HANDLE / DEDUP_DECISION / CLAIM / RESUME /
SUPERSEDED / EFFECT_APPLY / COMPLETE / TERMINAL_ERROR`。

## 9. 差分测试（与独立朴素模型逐条对照）

`NaiveModel`（`reference.go`）是独立实现的朴素一次性消费者：单线程、无崩溃、
无并发，按操作的因果序（首次投递先于其重复投递）顺序施加全部副作用。
`TestDifferentialAgainstNaiveModel` 用 40 个随机种子生成操作序列（投递 / 完全重复 /
独立等价调用 / 先撤销），以「事件组」为单位并发喂给真实处理器，再逐条对照：

- 全部业务键的效果多重集一致（组内并发顺序不影响集合语义）；
- 全部副作用标记键一一对应；
- 审计 `Seq` 严格递增，覆盖全部已处理事件。

## 10. 关键取舍与被放弃的方案

- **放弃按内容/参数/时间窗去重**：无法可靠区分等价的独立调用，改由生产者 EventID 承担。
- **放弃单一大事务包住整个补偿**：副作用可能耗时/跨资源，长事务持锁不可行；改为
  每项独立可串行化事务 + 独占标记的 saga，崩溃边界清晰且可续作。
- **放弃「检测到对象被改过就拒绝续作」的保守策略**：会误杀大量无关并发修改。
  读集合精确到依赖键，无关字段改动不构成冲突。
- **放弃存储层静默裁决**：谓词冲突必须让整个 fn 用新快照重跑，由业务逻辑决定终态，
  存储层不得替 fn 做语义选择（§3 陷阱 2）。
- **去重不维护随时间增长的去重表扫描**：记录即索引，定点探测 O(1)。

## 12. 本地验证方法

```bash
# 全量测试
go test ./...

# 竞态检测 + 详细输出（race 构建自动缩小压力测试规模）
go test -race -v ./...

# 覆盖率
go test -coverprofile=coverage.out ./...
go tool cover -func=coverage.out

# 静态检查与格式
go vet ./...
gofmt -l .

# 可运行文档示例
go test ./compensate/ -run ExampleProcessor -v
```

关注点：`TestResumeAfterCrashAtEveryBoundary`（崩溃续作）、
`TestDedupBoundaryExhaustive`（重复 vs 独立等价 7 边界）、
`TestErrorPriority_*`（错误优先级）、`TestDedupLookupConstantTime`（O(1) 证据）、
`TestUndoRaceIsDeterministic`（撤销竞争）、`TestConcurrentExecutionsAreSerializable`
（并发可串行化）、`TestDifferentialAgainstNaiveModel`（随机差分 40 种子）。
