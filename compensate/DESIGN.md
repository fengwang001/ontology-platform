# 动作副作用补偿回滚子系统 — 设计说明

包路径：`ontology/compensate`（Go，零第三方依赖）。

## 1. 问题模型

一次动作声明若干条**副作用分支**：

- 分支内部是一串**顺序子操作**，必须严格按声明顺序生效。
- 分支之间用 `Deps` 声明依赖：被依赖分支**完全生效**后，依赖方才能开始。
- 无依赖关系的分支彼此独立，可任意交织生效。
- 任一分支失败（子操作自身失败，或其上游最终失败）即触发**补偿**：撤销该动作
  全部已生效副作用。

补偿顺序约束：

- **跨分支**：被依赖方必须等所有依赖它的分支补偿完，才能补偿自身（依赖边的逆向）。
- **分支内**：对已生效子操作严格逆序。
- 逆操作失败只影响它所在分支与等待它的上游，独立记录、互不遮蔽。

## 3. 关键取舍

### 3.1 补偿就绪判定为何是 O(1)

声明阶段一次性（O(V+E)）为每条分支初始化整数
`remainingDownstream = 有已生效副作用的直接下游分支数`。某分支补偿完成时，对其每条
直接依赖边把上游的该计数减 1。于是“分支 x 现在能否开始补偿”这一问题，只需读取
`x.remainingDownstream == 0`，**单次判定 O(1)，不遍历分支集合，也不随分支总数线性增长**。
（线性的工作只发生在一次性初始化与“完成时沿出边递减”，每条边恰好一次。）

### 3.2 无依赖分支是否允许并发补偿：**允许**

明确结论：**允许并发补偿**，理由是声明期强制约束
“**无依赖关系的两条分支不得写同一对象图槽位**”（`validateWriteSetDisjoint`）。
于是这些分支的逆序恢复操作作用在互不相交的槽位上，天然可交换：

- 无论各分支补偿的相对快慢如何，最终对象图都相同；
- 该结果等价于“存在至少一个合法的逆向拓扑顺序，按该顺序逐一补偿”的结果。

存在依赖关系的分支因为有确定先后，允许写同一槽位（其逆操作顺序被调度器强制）。

### 3.3 确定性逆操作

每个子操作在提交前由 `CommitSet` 捕获旧值（含“此前是否存在”），构成确定性逆操作
`UndoRecord`：补偿时恢复旧值或删除该属性，不需要业务方再提供回调。逆操作失败
（`FailCompensate` 注入或真实失败）时该槽位副作用保留，并记录 `INVERSE_FAILED`。

### 3.4 失败传播

- 分支 goroutine 等齐所有声明依赖到达终态后再判定；任一依赖不是 `applied`，该分支
  被动失败（`UPSTREAM_FAILED`），尚未开始的子操作永不开始。
- 同时在生效收口（`applyDone` 关闭）时沿依赖边做一次失败传递闭包，保证所有
  “上游链上有终态失败”的未生效分支都被一致地标记为被动失败，与具体 goroutine
  调度无关；每个被动失败分支各有一条独立记录。

### 3.5 直接补偿请求的拒绝

`RequestDirectCompensation(branch)` 在补偿调度器下做最终判定：

- 该分支 `remainingDownstream > 0`（尚有未完成补偿的下游）→ 拒绝
  `COMPENSATION_ORDER_DENIED`，**拒绝不改动任何已生效状态**；
- 或该分支因下游逆操作失败而被永久阻塞，同样拒绝；
- 只有全部下游都补偿完（计数归零）才允许执行。

### 3.6 逆操作失败为何不会遮蔽其它分支

`compensateBranch` 对分支内子操作逐条逆序尝试：单个逆操作失败只记录该
“分支+子操作”，`continue` 继续本分支其余逆操作，也不影响其它在飞分支。失败分支
不递减上游计数，其上游祖先永不满足就绪条件，最终进入 `Report.Blocked`。因此两条
无依赖分支同时补偿失败时，两条 `INVERSE_FAILED` 记录都完整保留。

### 3.7 跨动作可串行化

采用**动作级严格两阶段锁（2PL）**：

- 生效开始前，按槽位全局排序一次性获取动作声明的全部写槽位（排序加锁杜绝跨动作
  加锁顺序环），同动作对槽位去重；
- 锁一直持有到**全部补偿恢复操作完成**之后才统一释放（成功动作在提交点释放）。

效果：两个动作若槽位相交则被整体串行（谁先拿到交集谁先完整执行+补偿），槽位不相交
则完全并行。因此任意并发交错都等价于某个动作串行顺序。`TestCrossActionSerializability`
以 50× 多轮压力验证。

锁管理器把所有权/排队/持有集合放在同一把临界区内原子交接，唤醒信号在“新 owner +
held 登记”完成后才发出，避免交接竞态；同动作多 goroutine 请求同槽位共享一个等待事件。

## 4. 错误分类与固定优先级

`ErrKind` 的数值即报告优先级，从高到低：

1. `KindDependencyCycle` 依赖环被拒绝（声明阶段，最高）
2. `KindUpstreamFailed` 分支因上游失败被动失败
3. `KindSubOperationFailed` 子操作自身生效失败
4. `KindCompensationDenied` 违反补偿顺序的直接补偿请求被拒绝
5. `KindInverseFailed` 逆操作执行失败（最低）

`Report.Records` 按此优先级稳定排序，`Report.Primary()` 返回最高优先级记录；
多条件同时满足时按优先级从高到低报告，但全部记录都保留、互不覆盖。

## 5. 被放弃 / 未采用的方案

- **回调式补偿（用户提供 Undo 闭包）**：放弃。无法在声明期校验写集，也就无法证明
  独立分支并发补偿的可交换性；且闭包的逆操作未必确定。改为“提交时捕获旧值”的
  确定性逆操作。
- **每分支独立锁/逆序简单加锁**：放弃。无法保证跨动作严格可串行化（两动作在同一
  槽位上交错提交会让彼此捕获的旧值失效）。改为动作级严格 2PL。
- **补偿就绪时遍历全部分支判断**：放弃。会使单次判定 O(V)。改为每分支一个
  `remainingDownstream` 计数，单次 O(1)。
- **一个逆操作失败即中止整个补偿**：放弃。会遮蔽其它分支/子操作的失败信息。改为
  逐子操作独立尝试、独立记录，仅阻塞其上游祖先。
- **让等待者自行重算拓扑决定可否补偿**：放弃。并发下需要全局锁且开销高。改为
  中央调度器 + 计数驱动唤醒。

## 6. 本地验证方法

```bash
# 需 Go 1.26+；若 GOCACHE 默认目录只读，可指向 /tmp
export GOCACHE=/tmp/gocache GOPATH=/tmp/gopath

go test -race -v ./compensate                       # 全量 + 竞态检测
go test -race -run TestRandomDifferentialAgainstNaive -count=100 ./compensate  # 4 万组对拍
go test -race -run TestCrossActionSerializability -count=100 ./compensate      # 跨动作压力
go vet ./...
gofmt -l .
```

对拍以 `RunNaive`（朴素串行：确定性拓扑生效 + 严格逆序补偿）为独立见证，比较最终
对象图、已生效集、已补偿集、阻塞集、各类错误计数与逆操作失败位置。

审计日志（`TextLogger`）逐条打印每次尝试的 `phase / 分支#子操作 / 输入 / 结果 /
判定依据 / ALLOWED|REJECTED`，可用于核对补偿顺序与拒绝理由。
