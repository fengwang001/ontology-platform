# 信号配时控制与绿波协调 — 设计说明

## 架构
- `types.go`：相位规格、方案、请求/查询类型、七类哨兵错误（按规定的判定次序校验）。
- `engine.go`：确定性事件引擎。状态只在相位结束/服务结束事件处变化；`advanceTo` 重放事件。
- `priority.go`：紧急跳相/延长、公交调整、相邻循环跳相登记。
- `intersection.go`：并发门面。每个写操作在引擎克隆体上校验并执行，成功才整体提交，
  因此被拒操作对状态、队列、时钟零痕迹；互斥锁串行化，并发等价于某串行序，重放确定。

## 关键取舍
- O(1) 跨循环快进：无优先活动、无待生效方案且处于标准循环起点时，每循环回归调整量
  在偏差收敛前为常数，循环长度呈分段等差，可解析地一次跳过任意多个循环；`steps` 计数器
  由测试断言：推进 1e9 秒仅处理有界个事件。被干扰的遍历（`atWrap=false`）禁止快进。
- 偏差在循环边界（wrap）测量：`devR=(τ-anchor-offset) mod C`，<半周期缩短、>=半周期延长
  （半周期取延长）；方案生效瞬间 anchor 重置、偏差归零。优先打断后下一 wrap 自然重测。
- 跳相集合在请求受理时按当前相位计算并登记到所属循环（越界跳相拆到两个循环）；
  排队请求的实际起跳可能滞后，登记以受理时为准（简化，已确定且可重放）。
- 克隆-校验-提交替代回滚：拒绝路径不写任何共享状态，时钟只在接受时前进。
- 公交请求仅在无紧急请求排队/服务时生效，否则直接记 Preempted；紧急启动服务时
  所有 Applied 公交请求转为 Preempted，相位自然结束时转为 Completed。

## 被放弃的方案
- 逐秒推进主模型：实现简单但查询开销随循环数增长，不满足 O(1) 要求（仅作对照模型）。
- 事件溯源/历史回放：内存随时间增长，且重放成本同样随历史增长。
- 偏差连续跟踪（按秒插值）：语义复杂且与"每循环逐步回归"的规格不符。

## 本地验证
- `go test ./signal/`：边界绿时、循环末换方案、目标即当前相位、相邻跳相拒绝、
  公交/紧急同时到达、半周期回归方向、回归中途被打断、时钟回退与拒绝不留痕。
- `TestConformanceRandom`：25 种子 x 400 随机操作，与独立逐秒朴素模型比对错误类别、
  任意时刻查询与全部请求终态，逐条日志记录输入/输出/判定依据。
- `TestQueryCostIndependentOfCycles` 用事件计数证明查询复杂度；`TestConcurrentOps`
  配 `-race`；`TestReplayDeterminism` 验证重放一致。
