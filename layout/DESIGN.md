# 复合类型内存布局与二进制兼容子系统 — 设计说明

## 模块划分
- `config.go`：`Config`（指针/空类型/尺寸上限/允许对齐集合）与全部错误类别。
- `types.go`：输入模型（`Field`/`CompositeSpec`）、结果模型（`Layout`/`FieldLayout`/`Snapshot`）、三态 `CompatKind`、`Logger`。
- `layout.go`：纯函数 `computeLayout`，只依赖直接字段的已解析布局，O(字段数)。
- `compat.go`：纯函数 `classify`，按位置逐字段比较，产出完全兼容/追加兼容/不兼容与判定理由。
- `registry.go`：登记、直接内嵌正反向边索引、`Modify` 的传播重算与原子提交；单把 `sync.RWMutex` 保证可串行化与同瞬快照。

## 关键取舍
- 布局内核是纯函数，登记与传播只是“取依赖布局 → 调内核”，使朴素模型与增量实现天然可对照。
- 间接引用大小/对齐由配置固定，允许前向与自引用目标；只有直接内嵌参与环检测与传播。
- 修改先在候选状态上做拓扑序（Kahn）试算全部受影响类型，全部通过才提交；任一依赖者超限即整体拒绝，天然无需回滚逻辑。
- 传播判定只沿“布局实际改变”的边前进；某级三态为完全兼容且布局一致时该分支停止。版本号与累计重算次数仅在布局真正改变时增加。
- 紧凑字段不参与对齐；当类型只有紧凑字段时对齐取允许集合最小值。`MaxAlign` 只缩小字段有效对齐，不改变紧凑行为。

## 被放弃的方案
- 全局锁 + 修改后立即就地更新并在失败时回滚：回滚路径多、易漏字段；改为“先试算后提交”。
- 深度优先逐层重算：钻石依赖会重复计算且停止点难判定；改为可达集 + 拓扑序单次求值。
- 朴素模型每次查询重算作为生产实现：O(类型总数) 违背复杂度目标，仅保留为差分测试 oracle。

## 复杂度（可验证）
- 单类型布局：`computeLayout` 对每字段一次 map 查找，`BenchmarkLayoutOneType` 显示注册表扩大 100 倍时 ns/op 持平。
- 修改触达集：仅经直接内嵌反向边 BFS + 子图拓扑排序，无关类型不出现；`TestOnlyReachableDependentsRecompute` 与 `BenchmarkModifyReachability` 验证。

## 本地验证
```bash
go test -race -v ./layout
go test -run NONE -bench . -benchtime=200x ./layout
```
随机差分测试对 5 个固定种子各跑 600 步登记/修改，与独立朴素模型逐字段、逐版本比对；每条输入/输出/理由经 `Logger` 打印。
