# 货位分配系统设计说明

## 1. 模块划分

代码位于 `slotting/` 包，按职责拆分为相互协作的小模块：

| 文件 | 职责 |
| --- | --- |
| `model.go` | 领域类型：`Coord`、`LocationConfig`、`Pallet`、`Category`、`LocationStatus`、只读快照 `LocationView`；坐标字典序。 |
| `errors.go` | 可区分错误：`SlotError{Reason, Detail}` + 哨兵错误（`errors.Is`），拒绝优先级表 `rejectionPriority` 与 `FirstReason`。 |
| `constraints.go` | 纯函数约束：参数校验、相邻坐标、`checkPut` 一次算出冻结/品类/净高/承重/混放/相邻隔离/容量七个布尔位，按优先级取首个原因。无锁、无状态、可单测。 |
| `treap.go` | 泛型确定性 treap 有序集合（自定义比较器），支持按字典序插入/删除/取最小/有序遍历。 |
| `store.go` | 唯一权威占用账 + 候选索引；持有 `sync.RWMutex`，所有"校验—记账—索引更新"在临界区内原子完成。 |
| `service.go` | 业务操作：自动/指定上架、移库、取出、冻结/解冻、批量事务、只读查询；拒绝原因优先级、回滚都在这一层。 |
| `logging.go` | `LoggedService` 装饰器：与服务共享同一个 `Store`，逐操作打印输入、输出与判定依据，不改变任何语义。 |

朴素参考模型与全部测试放在 `*_test.go` 中（包内测试），不会进入生产二进制。

## 2. 数据结构与账目

`Store` 维护：

- `locs map[Coord]*locEntry`：货位配置与在位托盘切片、在位总重。
- `pallets map[string]*Pallet` 与 `where map[string]Coord`：托盘反查表，托盘编号唯一归属。
- `empties`：状态正常且完全为空的货位有序集合。
- `nonFull`：状态正常且仍有剩余容量的货位有序集合。
- `byProduct[product]`：状态正常、仍有剩余容量、且当前存放该商品的货位有序集合。
- `productAll[product]`：存放该商品的全部货位（含冻结），仅供商品货位查询。

每次 `place`/`remove`/`setFrozen` 同步维护上述全部索引；账与索引永远在同一临界区里一起改，因此不存在不一致窗口。

## 3. 自动上架选择次序与可验证的复杂度

`autoPickLocked` 只访问两个集合：

1. `byProduct[p.Product]`（同商品、正常、有余位），按字典序逐个试约束，取首个可行者；
2. 若阶段一无可行候选，则遍历 `empties`（正常、空），同样取字典序首个可行者。

候选集合里的每个键只可能因为"该托盘"而被跳过（承重/净高/品类/隔离等），
因此被考察货位数的函数是：

> `O(k_product + k_empty_to_first_fit)`

- 不遍历全部货位：装着"别的商品"的货位不同时出现在这两个集合中；
- 不随与该商品无关的在位托盘数变化：索引键是货位，与在位托盘数量没有比例关系；
- 与货位总数解耦：新增货位若被别的商品占用（非空、非本商品候选），考察量不变。

验证方式：

- `autoPickCountLocked` 返回实际调用 `checkPut` 的货位数；
- `TestExaminedIndependentOfTotalScale` 在 100/1000/5000 个无关货位与无关托盘下，
  断言同商品分支考察量恒为 1；
- `TestExaminedEmptySearchBounded` 断言空货位分支只考察 1 个空候选，与 2000 个占用货位无关。

说明：被放弃的更"强"方案是对承重/净高做二维范围索引。由于空货位本身与托盘无关、
且题目要求的是"不随货位总数/无关托盘数增长"，商品候选集 + 空集两段式已满足，
二维范围索引会显著提高维护成本（每次放入/取出/冻结都要改多维索引），故放弃。

## 4. 约束与拒绝原因优先级

`checkPut` 同时计算七个布尔位，`conflict.reason()` 按规定顺序报第一个：

```
货位不存在 → 冻结 → 品类不允许 → 净高不足 → 承重不足
→ 混放冲突 → 相邻隔离冲突 → 容量已满
```

- 承重/净高按"恰好等于上限允许"实现（`>` 才拒绝）。
- 同货位必须同商品；`AllowMixedBatch=false` 时还必须同批次。
- 相邻 = 同通道、同层、`|位序号| = 1`；只有实际存在的相邻货位参与检查。
- 相邻隔离只针对"易燃 ↔ 食品"，对双方放入对称检查；普通品类不参与。
- 冻结货位中的托盘仍出现在相邻检查中（`neighbors` 不过滤状态），隔离约束持续生效。

全局错误优先级：参数非法 → 对象不存在（货位/托盘）→ 重复 → 各类约束原因 → 无可用货位。
参数在取锁前校验；"托盘不存在"与"货位不存在"按操作语义区分：
移库以托盘为操作主体，先确认托盘在位，再判定目标货位。

## 5. 移库、冻结与批量事务

- **移库**：托盘先从源货位下账（重量/容量随之释放），再以"不含该托盘自身"的状态对目标做
  `checkPut`；通过则上账到目标，失败则把托盘放回源货位。整个过程持写锁，
  外部只能看到"未动"或"已移完"，观察不到半完成状态。移到自身货位返回 `same_location`。
- **冻结**：只切状态与候选索引，托盘保留；冻结货位离开 `empties/nonFull/byProduct`，
  但仍留在 `locs`、`where`、`productAll` 与相邻关系中，故可取出/移出、持续参与隔离。
  解冻按当前占用情况重新进入相应索引。
- **批量**：参数与批内编号重复（含批外已存在）先一次性校验；随后逐托盘自动分配，
  每个托盘看到前面各托盘放入后的状态；任一失败即按逆序 `remove` 回滚已放入的托盘，
  返回 `BatchError{Index, Err}`，`Index` 为最小失败下标，全有或全无。

## 6. 并发模型与一致性

- 单一 `sync.RWMutex`：写操作持写锁串行化，结果等价于某一全局串行顺序；
  查询持读锁并在锁内复制出快照（切片与品类集合均重新分配），绝不外泄内部引用。
- 被放弃方案：按货位分片加锁。移库同时触及两个货位、相邻隔离触及邻居货位，
  分片锁需要多锁排序并处理锁升级，复杂度高且易错；在单机内存模型下，
  单锁临界区只是纯内存 map/切片操作，吞吐足够，简单可证正确。
- treap 使用固定随机种子，仅决定树形态；选择只依赖键的全序，
  因而相同操作序列重放得到完全相同的分配结果（`TestDeterministicReplay`）。

## 7. 本地验证方法

```bash
# 单元测试 + 朴素模型随机差分（60 个种子、每种子 200 操作）
go test ./...

# 竞态检测 + 并发混合读写不变量校验
go test -race ./slotting/

# 复杂度与确定性验证（详细输出）
go test -run 'Examined|Replay' -v ./slotting/

# 输入/输出/判定依据日志演示
go run ./cmd/demo
go test -run TestDifferentialAgainstNaiveLogged -v ./slotting/

go vet ./...
gofmt -l .
```

`go test -cover` 可查看覆盖率。差分测试每一步都同时比较拒绝原因、分配货位与全量账目。
