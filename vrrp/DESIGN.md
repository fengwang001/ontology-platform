# VRRP 风格单设备主备状态机设计

## 范围与模型

`vrrp` 包只实现一台设备的确定性状态机，不直接访问墙钟、网络或 goroutine。调用方向方法注入单调时间、对端通告和操作事件；方法同步返回当前事件立即产生的通告。

角色只有：

- `RoleInitialize`：初始态。
- `RoleBackup`：备态，维护主设备失活监视和优先级 0 让位等待。
- `RoleMaster`：主态，维护下一次通告到期时刻。

多台设备的组网行为由调用方负责转发：调用 `Start`、`ReceiveAdvertisement` 或 `Stop` 得到通告后，在同一模拟时刻或稍后调用其他设备的 `ReceiveAdvertisement` 即可。测试中的 `TestMultiDeviceElectionAndFailover` 用三台设备演示地址属主、普通高优先级设备和低优先级设备的联合选主与故障切换。

## 公开事件

| 方法 | 语义 |
| --- | --- |
| `Start(now)` | 初始态启动；地址属主立即为主并发通告，其他设备进入备态并启动初始失活监视。已启动时幂等。 |
| `Stop(now)` | 回到初始态；主态发送优先级 0 通告。 |
| `ReceiveAdvertisement(advert, now)` | 处理一条对端通告。 |
| `AdvanceTime(now)` | 只处理备态的失活与等待定时；不主动推通告。 |
| `TakeAdvertisements(now)` | 主态拉取通告，每次最多一条；其他角色无输出。 |
| `SetPriority(priority, now)` | 只改变后续通告和比较，不立即切换角色。 |
| `SetPreempt(preempt, now)` | 只改变后续比较，不立即切换角色。 |

通告通过 `Advertisement` 表示。普通通告优先级为 1–255；优先级 0 仅用于原主主动让位或主态停止。

## 关键状态与定时

设备只保存定长状态，不保存事件历史：

- 当前角色、优先级、抢占开关、本机 ID 和通告间隔。
- 最近一次被接受事件时间。
- 一个主设备失活截止时间。
- 一个优先级 0 让位等待截止时间。
- 一个主态通告到期时间和一个“升主后的首条待发通告”布尔值。

### 备态监视

- 非地址属主启动时即进入备态，截止时间为 `now + 3 × 本机通告间隔`，因此没有任何主设备时可以自主选主。
- 被采纳的通告把截止时间设为 `接收时间 + 3 × 发送者通告间隔`。
- 时间满足 `now >= deadline` 即超时；因此恰好三倍间隔的时刻超时，差 1ms 不超时。
- 备态收到优先级 0 时设置 `now + floor(发送者通告间隔 / 4)` 的让位等待，不立即升主。等待期间收到普通且被采纳的通告会取消等待。
- 普通低优先级通告在抢占打开时被忽略，且不改变任何现有定时；抢占关闭时被采纳并重置三倍监视。
- 优先级相同且发送者 ID 更大时采纳；发送者 ID 与本机相同则报 `ErrIdentityConflict`。
- 双 255 报地址属主冲突，错误也映射为 `ErrIdentityConflict`。

### 主态通告

- 地址属主启动立即发送一条通告。
- 非地址属主因定时升主时，通告被标记为待发，随后由 `TakeAdvertisements` 拉取；这样时间推进仍保持纯定时语义，不隐式发送网络消息。
- 周期性通告按“上一次实际取出通告的时间 + 本机通告间隔”计算。跨越多个周期后每次拉取仍只返回一条，不补发历史积压。
- 非属主主态收到优先级 0 探测时立即返回一条通告，并把下一次周期通告重置为当前时间加本机通告间隔。
- 地址属主在主态忽略所有非 255 通告；收到另一个 255 通告报地址属主冲突。
- 非属主主态收到更高优先级，或同优先级且 ID 更大的通告时降为备态，并按发送者通告间隔重新监视。

### 停止与重启

主态 `Stop` 返回优先级 0 通告并清空所有定时；备态停止只回到初始态。重启时重新执行启动规则，测试覆盖属主停止后再次立即成主。

## 错误优先级

错误按以下固定顺序判定：

1. `ErrInvalidArgument`：配置、通告、优先级或通告间隔非法。
2. `ErrClockRegression`：时间小于最近一次被接受事件。
3. `ErrNotStarted`：初始态收到通告。
4. `ErrIdentityConflict`：同 ID 同优先级冲突，或双地址属主冲突。

被拒绝事件在校验失败前不会修改任何状态或定时；只有通过校验并被接受的事件才更新最近事件时间。

## 并发与复杂度

每个公开方法持有同一把互斥锁，方法内执行完整状态转换并在释放锁前返回结果。因此并发调用的可观察结果等价于按各方法加锁顺序形成的某个串行执行；不存在等待另一个网络或时钟事件的锁内阻塞，也不会产生死锁。

所有方法只读取和更新固定数量的标量字段：

- 不保存历史事件，所以处理时间不随历史事件数增长。
- 时间推进只比较两个截止时间，不从上次时间逐毫秒循环，所以处理时间不随跨越时间长度增长。
- 通告队列最多一条，周期通告不按积压数量展开。

因此每个事件的时间复杂度为 `O(1)`，空间复杂度为每设备 `O(1)`。`TestConcurrentOperationsAreSerializeable` 在竞态检测下并发调用方法；可以用 `go test -race` 验证无数据竞争。

## 关键取舍

- **拉取通告而非内部回调**：状态机不启动 goroutine，也不持有发送器；主态周期通告由调用方在取通告时驱动，便于测试和确定性重放。
- **时间推进不直接发通告**：升主通告作为待发项由下一次 `TakeAdvertisements` 取走，避免 `AdvanceTime` 同时承担定时和网络发送职责。
- **初始非属主也启动三倍监视**：否则多台同时启动但没有任何主设备时，无人可以升主。
- **同优先级用全序 ID 打破平局**：只在优先级相等时比较 ID；低优先级不会因为 ID 更大而获胜。
- **饱和加法处理 `uint64` 上溢**：合法时间和间隔本身都在有限范围内，饱和到 `math.MaxUint64` 可避免非法回绕。

## 放弃的方案

- **保存通告事件列表并在每次推进时扫描**：实现直观但处理开销随历史增长，不满足 `O(1)` 要求，已放弃。
- **按毫秒循环推进内部虚拟时钟**：简单但与跨越时长成线性关系，也会把模拟粒度写死为 1ms，已放弃。
- **主态主动回调网络发送接口**：可模拟真实设备，但会引入 I/O、并发和测试不确定性，且单设备库无法保证调用方串行投喂，已放弃。
- **升主时在 `AdvanceTime` 立即返回通告**：会让时间事件变成网络发送事件；为了保持职责边界，改为待发通告模型。
- **为通告积压维护队列**：需求明确不补发积压，周期通告只需要一个截止时间和至多一个待发布尔值，因此未使用队列。

## 本地验证

推荐使用仓库内 Go 1.26.5：

```bash
GOCACHE=/tmp/go-cache-ontology /usr/local/go/bin/go test -v ./vrrp
GOCACHE=/tmp/go-cache-ontology-race /usr/local/go/bin/go test -race ./vrrp
GOCACHE=/tmp/go-cache-ontology /usr/local/go/bin/go test -cover ./vrrp
/usr/local/go/bin/gofmt -w vrrp
```

若本机 Go 已在 `PATH`，可把绝对路径替换为 `go` 和 `gofmt`。

## 测试覆盖

- 三倍超时恰好到期与差 1ms。
- 同优先级 ID 大小比较和同 ID 冲突。
- 抢占打开/关闭时低优先级通告的差异。
- 优先级 0 让位等待、取消和主态探测。
- 地址属主启动、忽略非属主、周期通告、冲突和停止重启。
- 主态降为备态及后续监视。
- 参数、时钟、未启动、冲突的拒绝次序。
- 主态通告不补发积压。
- 1000 组、每组 24 步的确定性随机事件序列与独立朴素模型对照。
- 三台设备通过互相喂入输出复现选主与故障切换。
- 并发方法调用的竞态检测。

随机对照测试通过 `go test -v` 对每一步打印输入、真实输出、朴素模型输出和判定依据。
