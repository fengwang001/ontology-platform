# 快照和解组件设计说明

`reconcile` 包把多个副本节点各自独立产出的快照归并为一份**唯一确定**的和解结果。
本文档记录数据模型、三条核心规则的落地方式、错误分类与固定判定顺序、复杂度论证、
被放弃的方案，以及本地验证方法。

## 数据模型

- `Position`：逻辑位点（单调递增序列号）。快照整体有位点，每个属性取值也携带
  最后一次写入的位点（`VersionedValue.WrittenAt`）。
- `Snapshot`：一个副本的一次快照，包含副本元信息 `ReplicaMeta{ID, Priority}`、
  快照位点、以及 `对象ID -> 属性 -> 版本化取值` 的内容映射。
- `Priority`：副本自身携带的可比较标识，是冲突裁决的**唯一**依据（数值小者胜）。
- 快照以 JSON 序列化形式（`[]byte`）进入和解组件，组件内部解码；原始输入永不被修改。

## 组件划分

| 组件 | 文件 | 职责 |
| --- | --- | --- |
| quarantine | `codec.go` | 解码并做结构校验，隔离损坏快照 |
| baseline | `baseline.go` | 取所有可读副本位点的最小值作为基准位点 |
| arbiter | `arbiter.go` | 对同一对象实例的冲突取值按固定规则裁决 |
| Reconciler | `reconciler.go` | 编排三者，产出 `Result`（内容 + 诊断 + 统计） |

## 核心规则的落地

### 1. 位点基准：最早位点代表的状态

基准位点 = 所有**可读**副本快照位点的最小值。合并时，任何 `WrittenAt > 基准` 的
取值一律被过滤（计入 `Stats.ValuesFiltered`），不参与后续裁决。因此位点靠后的副本
不会因为"内容更丰富"而影响结果；一个对象的全部写入若都在基准之后，该对象不出现在
和解结果中。

### 2. 固定裁决规则：只看副本自带标识

同一对象实例的同一属性出现不同取值时，按 `Priority` 数值最小者胜。规则是候选集合的
纯函数：裁决前候选先按 `(priority, replicaID, value)` 排序，结果与副本数量、到达顺序
无关（有专门测试覆盖：两个/三个副本、输入乱序、并发重复调用）。

### 3. 损坏副本隔离

解码失败（JSON 不可解析、缺副本 ID、空对象/属性名）或结构不自洽
（`WrittenAt > 快照位点`）的副本整体被隔离，记入 `Result.Quarantined`，
不参与内容裁决；其余副本照常和解。只有可读副本数低于 `MinReplicas`（默认 1，
即全部损坏）时才以 `ErrInsufficientReplicas` 整体失败。

### 4. 标识并列 → 不可和解

若最优 `Priority` 被两个及以上**不同取值**共享，说明可比较标识本身冲突，
固定规则没有更细一层依据。此时**不允许**退回到达顺序等与内容无关的方式强行裁决，
该对象实例直接判为不可和解：从 `Result.Objects` 中剔除，列入
`Result.Irreconcilable`，并在 `Result.Conflicts[].Unresolved` 中记录并列候选与原因。
同一对象的其他属性即使可裁决，整个对象实例仍判不可和解（按题面要求以对象为粒度）；
其他对象不受影响。

## 错误分类与固定判定顺序

三类错误互不相同，判定顺序固定为：

1. **`insufficient_replicas`（致命）**：可读副本数不足以确定位点基准。
2. **`corrupted_snapshot`（非致命）**：副本结构性损坏，被隔离。
3. **`irreconcilable`（非致命）**：按固定规则裁决后仍存在并列冲突的对象实例。

理由：三个阶段互为前置条件——基准位点需要足够数量的可读副本才能确定；
隔离决定参与裁决的副本集合；裁决只能在幸存参与者上进行。因此顺序不是偏好，
而是依赖关系的直接反映。第 1 类发生时返回 `ErrInsufficientReplicas`，
但 `Result` 仍非空，携带已收集的隔离记录，保证诊断信息不丢失。

## 确定性与并发安全

- `Reconciler` 无可变状态，`Reconcile` 是对输入的纯函数，可并发调用。
- 所有输出（对象、冲突记录、隔离记录、不可和解列表）在发出前按内容排序；
  隔离记录不包含输入下标等任何与到达顺序相关的字段。
- 合并前参与者按 `(replicaID, priority, position)` 排序，裁决器内部再对候选排序，
  双重保证顺序无关。
- 测试：`TestConcurrentReconcileIdenticalResults`（16 goroutine × 50 次，`-race`）
  与 `TestDeterministicAcrossRunsAndInputOrder`（100 次随机打乱输入顺序）要求结果
  逐字节一致，且输入字节在和解前后不变。

## 复杂度与可复核证明

合并是对所有可读取值的**单次线性扫描**：`ValuesScanned` 恒等于可读副本的取值总数
（属性测试逐例断言）。候选列表只在某属性首次观察到不同取值后才开始收集，
裁决器仅对真正冲突的属性运行：`ArbitrationsRun == ConflictsFound`（同样逐例断言）。
因此总开销为 `O(取值总数) + O(冲突属性数 × 每属性候选数 log)`，不存在
`副本数 × 对象数` 的乘积项（无两两副本比较）。`Result.Stats` 随每次和解返回，
任何人都可以用这些计数器复核一次运行的开销构成；`TestStatsScaleWithConflictsOnly`
给出具体断言示例（8 副本 × 50 对象零冲突时 `ArbitrationsRun == 0`）。

## 被放弃的方案

- **以写入位点（last-write-wins）参与裁决**：同一属性在不同副本的 `WrittenAt`
  不同时，看似"新者胜"更合理，但题面明确要求冲突裁决只依据副本自带的可比较标识；
  且副本位点本就不可比（各自独立推进），跨副本比较写入位点会引入隐性假设。
  `WrittenAt` 仅用于基准过滤，不进入裁决。
- **多数决（quorum of values）**：取值相同的副本多者胜。违反"裁决结果不得因参与
  和解的副本数量不同而改变"，放弃。
- **并列时退回到副本 ID 字典序或到达顺序**：副本 ID 与 `Priority` 是同一类标识，
  若运营方给两个副本配了相同 `Priority`，用 ID 字典序强行裁决会掩盖配置错误；
  到达顺序则与内容无关，明确被题面禁止。并列即不可和解。
- **局部损坏只剔除损坏对象**：快照局部不可读时无法界定损坏边界，信任其余部分
  风险不可控；按题面要求整个副本隔离。
- **不可和解以属性为粒度**：题面要求"该对象实例必须被判定为不可和解"，故任一属性
  并列即整个对象剔除。

## 本地验证方法

```bash
# 全量测试（含竞态检测）
go test -race ./reconcile/

# 随机对照测试：与朴素参照模型对拍，默认 3000 例；
# 每次和解的输入、输出与判定依据记录为 JSONL
RECONCILE_PROPERTY_LOG=/tmp/recon.jsonl go test ./reconcile/ -run TestAgainstNaiveReferenceModel -v

# 换随机种子复跑
RECONCILE_PROPERTY_SEED=12345 go test ./reconcile/ -run TestAgainstNaiveReferenceModel

# 静态检查
gofmt -l reconcile/ && go vet ./reconcile/
```

朴素参照模型（`naive_test.go`）是规格规则的逐条直译：先取最小位点，再逐对象逐属性
收集候选，最后按"最小 Priority 胜、最优 Priority 上有多个不同取值即不可和解"判定。
优化实现与它在大规模随机多副本组合（含损坏、并列、位点交错）上逐例对照，
要求基准、和解内容、不可和解集合、隔离数量完全一致。
