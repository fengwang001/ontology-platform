# 链接级联删除与孤儿对象清理 — 设计说明

## 1. 模型与配置

- 对象：以字符串 ID 标识。链接：有向三元组 `(Src, Dst, Type)`，带唯一 `Link.ID`。
- 每种链接类型独立配置三个要素（`LinkType`）：
  - `OutRule`：源对象被删除时，对目标对象生效的规则；
  - `InRule`：目标对象被删除时，对源对象生效的规则；
  - `KeepAlive`：该类型入边是否参与「存在即保留」的孤儿判定。
- 规则三选一：`RuleCascade`（级联删除另一端）、`RuleSetNull`（置空/删链保留对象）、`RuleRestrict`（另一端存活则拒绝）。

方向是规则的一部分：同一条边在两端各按各自的规则独立处理，一端拒绝不影响另一端的判定与置空结果。

## 2. 最终状态的数学定义（顺序无关性的依据）

在请求开始时的**不可变快照**上定义两个单调算子：

1. **规则闭包算子 R**：对删除集合中的对象，按规则把新的对象并入：
   - `Cascade` 把另一端并入集合；
   - `SetNull` 仅并入受影响的链接；
   - `Restrict` 不并入对象，只在终态校验。
2. **孤儿闭包算子 O**：若对象 `x` 在快照中存在至少一条来自「将被删除源」的保留性入边，而在删除集合对应的终态里不再有任何来自存活源的保留性入边，则把 `x` 并入。

删除集合 `D` 是算子 `O ∘ R` 从根集合 `{root}` 出发的**最小不动点**。两个算子都单调（只增不删），由 Knaster–Tarski 定理，最小不动点存在且与算子的应用次序无关；任何合法处理顺序只是同一单调闭包的不同遍历方式，必然收敛到同一 `D`。

实现上每轮：先做规则闭包（`planner.go` 的 Operator 1），再做一轮孤儿扫描（Operator 2）；任一轮没有新增对象即停止。由于 `D` 单调增长且受有限对象全集上界约束，迭代次数 ≤ 对象数，**必然终止**。

### 两类删除身份

- `Normal`（普通删除）：根对象与所有级联目标。它们对自己的全部出边和入边规则负责。
- 孤儿：按题意只对自己的**出边**规则负责；其入边随对象一并消失，不触发入边规则。

若一个先被孤儿清理的对象随后又被某条 `Cascade` 到达，它会被「提升」为普通删除，随后补处理其入边规则。因为我们求的是最小不动点，这种身份提升不改变最终集合，仅影响遍历路径。

### Restrict 何时生效

不动点求完后统一判定：对每条触及 `D` 的链接，
- 删除端是源（任何删除身份）且 `OutRule = Restrict`、目标不在 `D`；或
- 删除端是目标且删除身份为 `Normal`、`InRule = Restrict`、源不在 `D`，

则该规则「仍在引用另一端」，请求整体拒绝。两端都在 `D` 时引用随双方一起消失，不构成拒绝（等价于任意顺序下二者都被删除）。统一在不动点后判定，避免了「先看拒绝时对象还没被级联到」这类顺序假象。

## 3. 原子性：规划/提交分离，无需回滚

`Engine.Delete` 持引擎级互斥锁，期间：

1. 在锁内取一份不可变快照；
2. 规划器只写局部的 `Deleted / Normal / RemovedLinks` 集合，**不触碰存储**；
3. 若任何一步判定拒绝/配置错误，直接返回，存储零修改，因此不需要撤销中间状态；
4. 成功时由存储执行单次 `commit`（同一把锁内删对象、删链接），对外表现为一次原子状态跃迁。

被放弃的方案：先执行再记录撤销日志（undo log）。它在本模型里既多余又更容易出错——纯集合运算在快照上即可完成全部判定，失败路径天然无副作用。

## 4. 错误类型与固定次序

三类错误互斥，判定顺序固定（`planner.go`）：

1. `ErrObjectNotFound`：根对象不存在；最先判定，不依赖任何链接配置。
2. `ErrRestricted`：不动点达成后，按链接 ID 排序取第一条生效的拒绝规则上报。
3. `ErrUndefinedLinkType`：仍未拒绝时，按链接 ID 排序取第一条触及 `D` 但类型未配置的链接上报。

拒绝优先于未定义：先做完整闭包再统一分类，确保「同图里两种问题并存」时结果不随实现而变。规则的互相独立体现在：每一端的规则都被独立求值并体现在不动点中，只是只要有一条生效拒绝，整体不提交。

## 5. 并发与串行化

`Engine` 用一把互斥锁把「快照 + 规划 + 提交」整体串行化；`AddLink` 也走同一把锁。因此：

- 任意删除与新建链接的并发历史等价于这些操作按某个全局顺序逐个执行；
- 孤儿判定读取的保留性入边只可能来自提交前或提交后的完整状态，读不到半条新链接。

被放弃的方案：读已提交（RC）多版本 + 细粒度锁。RC 下孤儿判定可能读到未提交链接的中间状态；要满足题目等价串行的要求需要 SSI/可串行隔离，复杂度高且对内存图无收益。单写锁 + 不可变快照把正确性证明压缩为「一段临界区」。

## 6. 终止性去重开销不随全图增长

递归终止依赖「对象是否已在 `D` 中」的去重，实现为 `map[string]bool`，单次探价期望 O(1)，且**只会对本次受影响子图中实际到达的对象发起探测**。规划器在 `Plan.DedupProbes` 中显式统计该探测次数：

- 它只随「被删除对象数」增长，不随未触及的对象/链接总数增长；
- `TestDedupCostIndependentOfGraphSize` 在同一固定 2 节点级联子图上，把无关背景图从 10 放大到 10000，断言探测次数保持同一常数，测试中可复现核对。

注意：规划本身需要扫描当前快照中的边来寻找邻接，这部分是图遍历成本，不属于「保证终止所依赖的已处理对象去重开销」。

## 7. 审计日志

每个请求无论成功失败都追加一条 `Entry`：

- `Root`：输入；
- `Deleted`：最终受影响对象集合（失败为空）；
- `Steps`：每一步判定依据（`root/cascade/orphan/restrict/undefined`、对象、触发链接、链接类型/原因）；
- `Reject`：失败时的错误码与细节。

步骤内部以排序后的 ID 打破平局，因此对同一输入的日志也是可复现的。

## 8. 被放弃的方案汇总

- **DFS 递归 + visited 集合**：天然能处理环，但「判定孤儿」需要在多路子树全部结束后进行，DFS 时机选择会引入顺序差异；改为显式不动点。
- **边删边判 Restrict**：可能因级联尚未到达而误报；改为不动点后统一判定。
- **先删后回滚事务**：失败路径有副作用与回滚遗漏风险；改为快照规划 + 单次提交。
- **乐观并发 / MVCC**：无法简单保证不读到半提交链接；单写锁满足串行等价且可验证。
