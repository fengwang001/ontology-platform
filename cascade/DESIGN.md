# 对象级联删除控制器 — 设计说明

本包 `cascade` 实现一个带“属主引用（ownerReference）+ 终结器
（finalizer）”的对象级联删除控制器，语义对标 Kubernetes 垃圾收集器的
核心规则，并把三种删除策略、多属主依赖者、终结器阻塞与前台删除的
先后关系做成精确、可复现、可差分验证的行为。

## 一、对外接口

`Controller` 是线程安全的单一入口（`cascade/controller.go`）：

- `New()`：创建空控制器。
- `Create(id, owners []OwnerRef, finalizers []string) error`
- `Delete(id, strategy) error`：策略为 `Background / Foreground / Orphan`。
- `AddFinalizer(id, name)` / `RemoveFinalizer(id, name)`。
- `ReplaceOwners(id, owners)`：整体替换某对象的属主引用集合。
- `Get(id)` / `Exists(id)` / `Snapshot()`：只读查询。

时间戳：控制器内部维护一个单调时钟，每个改变状态的操作 `clock++`，
删除标记与级联标记都使用“当前操作时刻”，保证同一操作的整条级联
时间一致。

## 二、对象与索引（存储层）

每个对象（`object`，内部结构）保存：

- 全局唯一非空 `id`；
- `owners []OwnerRef`：按属主 ID 升序、无重复、无自引用；
- `fins`：终结器名集合；
- `deleting / strategy / deleteAt`：删除标记与策略、时刻；
- 三个**增量维护的派生计数**，使所有规则判定都是 O(1)：
  - `aliveOwners`：仍存活（未被移除）的属主边数；
  - `deletingOwners`：存活且处于删除中（任意策略）的属主数；
  - `fgOwners`：存活且处于**前台**删除中的属主数；
  - `blockingAliveDeps`：“仍存活且阻塞”的依赖者数（挂在属主侧）。

控制器另有反向索引 `dependents[ownerID] -> {dependentID}`，让“摘除
某属主的全部入边”与“前台传播向下展开”都只触达真实相邻对象。

这些派生量在 `Create / markDeleting / removeObject / relink` 四个
入口被成对维护，并有测试期不变量检查器 `checkInvariants`（见
`invariants_internal_test.go`）从前向切片全量重建后逐字段比对。

## 三、规则的形式化

记对象 `x` 的存活属主集合为 `Own(x)`（边的属主仍在对象表中）。

**删除请求**（幂等 + 单调升级）：
- 对象未删除中 → 置删除中，记录策略与时刻；
- 已删除中 → 无操作成功；仅当原策略为 Background 且新请求为
  Foreground 时升级为 Foreground；Orphan、Foreground 及反方向不变。

**移除条件**：`deleting && finalizers 为空 && (strategy != Foreground
|| blockingAliveDeps == 0)`。满足即移除，不允许延迟。

**前台传播**：对象 `x` 仍存活（或仅处于后台删除中，见下）且
`Own(x) 非空 && fgOwners(x) > 0 && deletingOwners(x) == |Own(x)|`，
则 `x` 进入/升级为前台删除。含义即规格原话：至少一个属主在前台
删除中，其余存活属主也都“已不存在或同样处于删除中”。该规则对
非阻塞依赖者同样适用，但非阻塞依赖者不阻塞其属主移除。

**移除时对依赖者的处理**（先摘边，再按属主策略）：
- Orphan：依赖者保留，即使零属主；
- Background / Foreground：摘边后若依赖者“原本有属主、现在一个属主
  也不剩”，则该依赖者连带进入后台删除，时刻取当前操作时刻。

**终结器**：同名追加幂等；删除中对象拒绝追加（Conflict）；移除不
存在的终结器报错（NotFound）；移除最后一个终结器会在同一操作内
触发该对象及其整条级联的移除，操作返回时结果已全部生效。

**属主修改**：删除中对象禁止改属主；新引用必须全部存在、不处于
删除中、无自引用、无重复、合入后不成环。校验失败不改变任何状态。

### 关于“后台删除中对象是否可被前台传播升级”

这是实现中最微妙的顺序敏感点。考虑：`x` 因零属主被连带标记为
Background（带终结器而停留），随后它的某个属主其实仍存活并进入
前台删除。为满足“结果与规则触发先后无关”，前台传播允许把**仅处于
后台删除中**的对象升级为 Foreground（单调升级）；但一旦对象已是
Foreground 或 Orphan 就不再被级联改变策略。这与“显式删除请求仅
允许 bg→fg 升级”一致，且朴素模型与生产实现采用完全相同的约定。

## 四、收敛引擎（为什么唯一、为什么顺序无关）

`cascade/engine.go` 的 `settle` 采用**两遍式不动点**，在单个临界区内
运行，直到状态不再变化：

1. **前台传播闭包（propagateForeground）**：在“不移除任何对象”的
   前提下，从候选集合沿 `dependents` 边向下，把所有满足传播条件的
   对象统一标记为前台删除，反复到不再新增。
2. **移除（removeLoop）**：反复移除当前满足移除条件的对象；每移除
   一个就摘除其全部入边、更新派生计数、按策略对零属主依赖者做后台
   连带删除，并把受影响对象重新入队。

传播严格先于同批移除，保证依赖者总能观察到“属主删除中”的窗口，
而不是因为属主在同一操作稍后被移除就只看到“零属主”。两步整体循环，
因此移除开启的新传播窗口也会被继续处理。

**不动点唯一性**：所有状态变化都是单调的——只会“进入删除中”、
“被移除”，策略只会沿 Background→Foreground 单向升级，终结器只减
不增（在收敛期内）。单调算子在有限格上的不动点与扫描顺序无关，故
任何触发顺序都收敛到同一稳定状态。

**复杂度**：每个对象仅在自身或相邻边发生变化时才入队，每条边在一次
操作中只被增删/扫描常数次，因此一次操作的总代价是
`O(被影响对象数 + 被触达引用数)`，与无关对象总数无关。
`perf_test.go` 用两组实验可复现地验证了这一点（见下文）。

## 五、错误类别与优先级

`cascade/errors.go` 定义单一错误类型 `GCError{Kind, Msg}`，`Kind` 从
高到低：

1. `InvalidArgument`：空 ID、空终结器名、非法策略、重复属主引用、
   创建已存在对象等；
2. `NotFound`：对象不存在、移除不存在的终结器；
3. `Conflict`：对删除中对象做“追加终结器 / 修改属主”；
4. `Cycle`：自引用、合入后成环（环检测优先于属主缺失，缺失属主按
   无出边终点处理，因此“既环又缺属主”仍稳定报环）；
5. `OwnerMissing`：属主不存在，或属主已处于删除中。

所有校验在写入前完成，被拒绝操作不改变任何状态（无副作用）。

## 六、并发

`Controller` 用一把 `sync.Mutex` 串行化所有公开方法；级联收敛在锁
内完成。因此：

- 每个“顶层操作 + 它引发的整条级联”是一个不可分割的临界区；
- 任意并发历史都等价于按获锁先后排成的某个串行顺序（可串行化）；
- `Get/Snapshot` 也取同一把锁，观察者只能看到某个完整操作之后的
  稳定状态，永远观察不到“半条级联”。

这里刻意选择单把锁而非细粒度锁：正确性论证简单、可证明，且复杂度
已限定在“影响面”内；吞吐是可以以后在不改变语义的前提下优化的
正交问题。

## 七、测试策略

1. **场景测试** `scenario_test.go`：三种策略的依赖者去向、多属主
   存活与连带删除、前台等待阻塞依赖者、终结器阻塞与解除后的整条
   级联、重复删除与策略升级、环与自引用、错误优先级。
2. **朴素参考模型** `internal/testutil/naive`：与生产实现零代码共享，
   每次操作后对全体对象反复全量扫描，直接按自然语言规则推导到
   不动点。
3. **随机差分测试** `diff_test.go`：60 个确定性种子、每种子数百步
   随机操作（创建/三策略删除/终结器/改属主/对删除中对象重复删除），
   逐步对照两侧的“错误类别”和“完整规范化状态”；日志逐步打印每个
   操作的输入、两侧实际输出与判定依据，失败时回放完整轨迹。
4. **不变量测试** `invariants_internal_test.go`：每个差分操作后从前向
   切片重建全部索引与派生计数逐字段比对。
5. **并发测试** `concurrency_test.go`：`-race` 下的高争用压力 +
   互不相交子图的并发结果必须等于串行结果。
6. **性能测试** `perf_test.go`：
   - `TestComplexityIndependentOfTotalSize`：无关对象从 2000 增至
     20000（10 倍），固定小链删除的单次耗时比率断言 `< 3`
     （实测约 0.6，即完全不随总数增长）；
   - `BenchmarkCascadeDepth`：级联链深 100/1000/10000，实测总耗时
     严格线性（约每对象亚微秒级）。

## 八、关键取舍与被放弃的方案

- **放弃“单一遍历 + 边遍历边删”的早期工作队列**：它在“对象已排队、
  同轮又收到属主变化”时会吞掉重新评估，导致前台链偶发卡死。改为
  “传播闭包 → 移除”两遍式，从结构上消除该顺序漏洞，也让唯一性
  论证更直接。
- **放弃细粒度锁 / 无锁结构**：可串行化是硬性要求，单把锁把“操作 +
  级联”天然变成原子事务；在复杂度已与总数解耦的前提下，锁竞争不
  影响渐进复杂度，正确性却最容易证明。
- **放弃把规则判定写成临时全图扫描**：虽然最直观，但单次操作代价
  随对象总数增长，违反性能要求。改为增量计数 + 反向索引，只在局部
  收敛；同时用“朴素全图模型 + 随机差分”来保证增量实现与全图推导
  等价。
- **环检测优先于属主缺失**：避免同一请求同时成环与缺属主时的二义；
  DFS 把缺失属主当作无出边终点，结论与边的存在顺序无关。

## 九、本地验证方法

```bash
# 需 Go 1.26+（仓库声明 go 1.26.5）
go test ./cascade -v                       # 全量场景 + 差分 + 不变量
go test -race ./cascade                   # 竞态检测（含并发用例）
go test ./cascade -run TestComplexity -v  # 复杂度断言（打印比率）
go test ./cascade -bench BenchmarkCascadeDepth -run '^$'
go vet ./... && gofmt -l .
```

差分测试默认即打印每步操作的输入、两侧输出与判定依据；需要查看某
个种子的完整轨迹可直接运行对应子测试：

```bash
go test ./cascade -run 'TestDifferentialAgainstNaive/seed7' -v
```
