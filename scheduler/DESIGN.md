# 多路径发送侧调度器 — 设计说明

`scheduler` 包实现一个事件驱动的多路径传输连接发送侧调度器：在多个
子流之间分配带连接级序号的数据段，区分子流级确认与连接级确认，处理
子流失效后的重新注入与连接级接收窗口约束。时钟不参与，一切状态推进
均由事件驱动。

## 1. 模型与术语

- **连接级序号**：字节序号。数据按写入顺序从 0 起连续编号，按最大段长
  M 切段（尾段可不足 M）。段 `[seq, seq+len)` 是发送与重新注入的原子单位。
- **子流在途**：已发送但尚未被该子流确认的字节（及对应的段列表）。
- **连接级确认**：累计确认到 `ackSeq`（不含），并通告接收窗口 `window`。
  约束：新发送后 `已发送最大序号+1 <= acked + window`。
- **待发队列**：逻辑上为 `[重新注入段（按序号升序）] + [新数据段（写入序）]`。
  发送决策总是从队首开始，队首无法发送即停止（队首阻塞，后续段不得越过）。

## 2. 关键语义裁定

规范有若干处需要明确解释，裁定如下（均已在测试中固定行为）：

1. **子流确认是累计值**。事件参数为该子流按发送顺序累计确认的字节数，
   新增确认量 = 累计值 − 已记录累计值。新增量必须恰好落在在途段边界上
   （否则报“确认非整段”），且不得超过当前在途（否则报“确认越界”）。
   累计值倒退报“过期确认”；累计值不变是合法空操作。
2. **连接级确认越界的界定**：`ackSeq > 已发送最大序号+1`（即确认了从未
   发出的数据）报“确认越界”。由此保持 `acked <= sentMax <= nextSeq`，
   新数据段永远不会被连接级确认部分或完全覆盖，只有重新注入段需要
   “被覆盖即丢弃”的处理。
3. **重新注入段永久排除失效来源子流**。“不得再选择该失效子流”按严格
   字面实现：即使该子流随后恢复，源于它的待发重新注入段也不选它
   （段上记录 `excluded` 字段）。若规范只打算约束失效期间，该字段也无害，
   因为失效子流本就不是活跃候选。
4. **失效时的重新注入按全局升序合并**。多次失效产生的重新注入段在待发
   队列前部统一保持按连接级序号升序（而不是新一批简单压到旧一批之前），
   与“排到待发队列最前，按连接级序号升序，且优先于尚未发过的新数据”
   的队列不变量解读一致。同一序号的待发重新注入段只保留一份（防御性
   去重；在纯事件驱动下重复本不可达，见下条）。
5. **“重复副本”段落的解读**。规范称“同一连接级序号可以同时在两个子流
   的在途中（原发与重新注入）”。在纯事件驱动 + “失效即清除在途”的规则
   下，该状态在**记账意义上不可达**：一个段要被重发，必须先因持有它的
   子流失效而被清除出该子流的在途，因此任意时刻每个序号至多有一份
   在途副本（对事件序列长度归纳即证）。该段落的可操作含义——连接级
   确认不释放任何子流的在途、各子流窗口只由各自的子流确认释放——已
   完整实现并由 `TestConnAckDoesNotReleaseSubflowInflight` 固定；
   记账规则本身另由白盒测试 `TestDuplicateCopiesAccounting` 直接构造
   双副本状态验证。
6. **恢复只重置窗口与在途**。子流恢复后拥塞窗口回到添加时的初始值、
   在途为零；累计确认/累计发送计数保留（规范未要求重置），恢复前的
   旧确认若迟到抵达，按现行计数判定（通常为“确认越界”或“过期确认”）。
7. **初始接收窗口为 0**。首个连接级确认到达前，新数据不可发送；
   重新注入段不受连接级窗口约束，仍可发送。
8. **幂等事件**。重复失效、重复恢复为合法空操作；失效子流的子流确认
   为迟到确认，忽略且不报错（但参数非法仍最先报告）。

## 3. 错误模型

错误以 `Error{Code, Detail}` 返回，`CodeOf` 提取分类码。五类错误按固定
优先级检查（高优先级先报）：参数非法 → 子流不存在 → 过期确认 →
确认非整段 → 确认越界。所有校验先于任何状态变更，被拒绝的事件不改变
任何状态（`TestRejectionOrder` 逐项验证且比对前后快照）。

## 4. 数据结构与复杂度

| 结构 | 用途 | 操作代价 |
| --- | --- | --- |
| `segQueue`（切片+头游标） | 新数据 FIFO、各子流在途 FIFO | push/popFront/front 均摊 O(1) |
| `treap`（确定性优先级树堆） | 待发重新注入段（按序号有序） | insert/min/popMin 期望 O(log n) |
| `map[string]*subflow` | 子流索引 | O(1) |
| 计数器 | `activeNormal`、各在途字节数等 | O(1) |

**单事件开销证明（均摊）**。把每个段的生命周期拆成有限次“生命周期
事件”：新数据段 = 入队 1 次 + 出队发送 1 次；每份在途副本 = 入队 1 次
+ 出队 1 次（子流确认释放或失效清除，二者恰居其一）；每份重新注入段
= treap 插入 1 次 + 删除 1 次（重发或被覆盖丢弃）。因此：

- 队列元素操作总数 ≤ 写入段数 + 发送段次数 + 释放/清除段次数，与队列
  中待发数据量、历史事件数无关；
- 选路调用 ≤ 发送段次数 + 事件数（每次发送决策循环只在队首阻塞时
  多查一次），每次选路为 O(子流数)——子流数是配置维度，不随数据量
  或历史增长；
- treap 操作次数 ≤ 失效清除段次数 × 2，单次期望 O(log 待发重新注入段数)，
  是全部结构中唯一的对数项；
- 被拒绝的“确认非整段”校验需沿在途段前缀扫描，不超过该子流在途段数
  （受其子流拥塞窗口约束，同为配置维度）。

**可验证性**。`Stats` 计数器记录每类基本操作次数，
`TestComplexityInvariants` 在 3 万事件负载后断言上述线性界逐条成立
（如 `PickCalls ≤ SegmentsSent + Events`、`TreapRemovals ==
SegmentsResent + SegmentsDropped`、操作总量 ≤ 5×(事件+写入段+发送段)）；
`TestComplexityScaling` 以 4 倍负载验证操作总量近线性增长（对数因子
留足余量）。测试即证明的可执行部分。

## 5. 并发与串行等价

所有公开方法持有同一把 `sync.Mutex`，每次事件处理（校验 → 变更 →
发送决策）原子完成，因此并发调用天然等价于某个串行顺序（可线性化）。
`TestConcurrentEvents` 在 `-race` 下以 8 goroutine × 2000 事件施压，
并校验终态不变量（序号有序、在途字节守恒、失效子流在途为零、待发
重新注入段升序且未被覆盖等）。

## 6. 被放弃的方案

1. **重新注入段用切片+有序合并**：单次失效需 O(待发重新注入段数) 合并，
   反复失效会使同一待发送段被反复扫描，总代价随历史事件数增长，违反
   复杂度要求，故改用 treap。
2. **子流确认按增量（delta）解释**：与“累计确认”字面不符，且丢失累计
   语义带来的幂等性（重复确认是合法空操作），放弃。
3. **连接级确认时同步释放子流在途**：与“两份副本仍占用各自子流窗口，
   直到各自子流确认释放”直接冲突，放弃；连接级确认只推进确认序号、
   更新窗口、丢弃被覆盖的待发重新注入段。
4. **失效子流的在途保留到恢复**：会使“从其在途中清除”无法成立，且
   恢复时“在途为零”仍需清除，徒增中间态，放弃（见 §2 第 5 条）。
5. **选路用堆维护候选子流**：候选资格依赖“拥塞窗口−在途 ≥ 段长”这一
   随段长变化的动态条件，堆无法直接维护；子流数为配置维度，线性扫描
   已满足复杂度要求，放弃。
6. **允许连接级确认超过已发送范围**：会破坏 `acked <= sentMax` 不变量，
   使“确认覆盖待发新数据”的幽灵状态出现，故界定为“确认越界”。

## 7. 本地验证方法

```bash
# 全部测试（确定性用例 + 1200 组随机对照 + 复杂度 + 并发）
go test ./scheduler/

# 竞态检测
go test -race ./scheduler/

# 查看随机对照的逐步骤日志（输入、输出、判定依据、对照结论）
go test ./scheduler/ -run TestRandomAgainstNaive -v | less

# 单项确定性用例
go test ./scheduler/ -run TestBackupSwitchTiming -v

# 静态检查
gofmt -l . && go vet ./...
```

测试清单与规范要求的对应：

- 普通/备用切换时机：`TestBackupSwitchTiming`
- 时延并列：`TestRTTTieBreak`
- 窗口恰好够与差一字节：`TestWindowExactVsOneByteShort`
- 失效重新注入顺序与重复副本：`TestFailureReinjectionOrder`、
  `TestReinjectPriorityOverFresh`、`TestConnAckDoesNotReleaseSubflowInflight`、
  `TestDuplicateCopiesAccounting`
- 失效子流迟到确认：`TestLateAckFromFailedSubflow`
- 窗口收缩后的发送：`TestWindowShrink`
- 拒绝次序：`TestRejectionOrder`、`TestValidation`
- 随机对照（1200 组 × 80 事件，逐步日志）：`TestRandomAgainstNaive`
- 复杂度：`TestComplexityInvariants`、`TestComplexityScaling`
- 并发串行等价：`TestConcurrentEvents`（配 `-race`）
