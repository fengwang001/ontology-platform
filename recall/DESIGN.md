# 医院药品批次召回与追溯锁定系统 — 设计说明

## 1. 模块划分

系统只暴露 `recall.System` 一个入口，内部按职责拆为三个协作模块：

| 模块 | 文件 | 职责 |
| --- | --- | --- |
| 编排层 | `system.go` | 参数校验、单调时钟、单一互斥锁、错误优先级编排、追回清单汇总 |
| 召回登记 | `recalls.go` | 按药品隔离的召回表；批号闭区间覆盖判定；有效等级与并列召回集合 |
| 库存台账 | `inventory.go` | 批次多位置库存、发放记录（带全局先后序号）、FIFO 退药抵扣、患者持有量 |

错误模型集中在 `errors.go`，对外请求/响应结构集中在 `types.go`。

## 2. 关键数据结构与取舍

### 2.1 单调时钟与并发串行化

- `System` 内只有一把 `sync.Mutex`。所有读写操作（含查询）都在锁内完成，
  因此任意并发交错的结果都**严格等价于某个串行顺序**，且该串行顺序就是
  互斥锁实际授予的顺序，不需要版本号/CAS/多段锁等更重机制。
- 时钟 `lastNow` 只在操作被**接受**后更新；被拒绝的操作在任何状态写入之前
  就返回，因此不会污染时钟与业务状态。
- 被放弃的方案：按药品分片锁。它能提高吞吐，但会引入"跨药品操作
  （本系统没有）与全局时钟"的定序复杂度；本规格只有一把全局逻辑时钟，
  分片锁无法在不增加额外协调的前提下保证"并发等价于某个串行序 + 时钟单调"，
  收益不明确，故放弃。

### 2.2 召回索引：按药品隔离 + 解除即摘除

- `byID map[id]*recallEntry` 保存全部召回（含已解除，供"解除后清单不可查"
  与"编号不可复用"判定）。
- `byDrug map[drug][]*recallEntry` **只保存未解除召回**：
  - 登记时追加；
  - 解除时把条目从切片摘除（条目仍留在 `byID` 并置 `active=false`）。
- 有效等级判定 `effective(drug, batch)` 只遍历 `byDrug[drug]`，因此其开销
  **只与覆盖该药品的未解除召回数有关**：
  - 已解除召回不进入该切片 → 与已解除总数无关；
  - 其他药品是另外的切片 → 与其他药品召回总数无关。
- 被放弃的方案：
  - *区间树/线段树*：批号是任意字符串字典序，召回区间动态增删且数量通常很小，
    区间树常数大、实现复杂，线性扫描该药品的未解除召回即可满足需求；
  - *扫描全部召回再过滤已解除/其他药品*：实现最简单，但违背题设复杂度要求，
    朴素模型（测试代码）刻意采用这种写法作为对照。

### 2.3 库存与患者持有量守恒

- 每个批次有不可变的 `total`（入库量）。
- 恒等式：`sum(各位置 stock) + sum(患者未退回数量) == total`，
  在差分测试每一步后都做断言。
- 退药只写入 `stock[药库]`，因此"退回药品只进入药库"由唯一写路径保证。

### 2.4 退药 FIFO 抵扣与追回清单

- 每次发放追加一条 `dispenseRecord{seq, at, patient, qty, returned}`，
  `seq` 是该批次单调递增的发放序号，天然表示"同刻的发放先后"。
- 退药只抵扣**该患者本人**的记录，按 `(at, seq)` 从早到晚。
  实现为每个患者维护一个**抵扣游标** `heads[patient]`：游标之前的本人记录
  都已抵扣满。配合每患者聚合的 `held[patient]`（O(1) 判定退药超量），
  每条发放记录被任何患者的退药扫描越过的总次数有界，摊销线性。
- 被放弃的方案：
  - *每次退药全量重排本人记录*：正确但最坏 O(n²)，仅保留在朴素模型中作对照；
  - *把"未退回余量"维护成全局队列*：发放可交错属于不同患者，
    全局队列无法表达"只抵扣本人"的语义。
- 追回清单：定位召回 → 取该药品的全部批次（按批号有序）→ 只对区间内批次
  汇总 `at >= issueAt` 发放的未退回数量。因此
  **不遍历其他药品的批次与发放记录**，开销与其他药品发放总数无关。
  抵扣先消耗始发时刻之前的发放，清单数量自然随之变化；汇总为 0 的
  (患者,批次) 不列出；结果按 (批号, 患者) 排序，保证可复现。

### 2.5 判定顺序与错误优先级

固定顺序（在 `System` 每个操作中一致执行）：

1. 参数非法（纯函数校验，不加锁）；
2. 时钟回退；
3. 对象不存在；
4. 召回禁止（一级/二级规则）；
5. 需知情确认（三级发放）；
6. 库存不足；
7. 退药超量；
8. 状态不符（重复入库/重复编号/重复解除、三级或已解除召回查清单）。

特殊点：`召回登记` 中"始发时刻晚于 now"属于参数语义问题，但其判定需要
读到 `now`，安排在时钟检查之后、仍以 `参数非法` 上报；这与"始发时刻
不晚于 now"作为参数约束的性质一致。

级别规则集中在编排层，便于按矩阵核对：

- 一级：禁发放、禁一切调拨（冻结）；
- 二级：禁发放，调拨仅允许目标位置为药库；
- 三级：不限制调拨，发放必须携带知情确认；
- 退药：任何等级都允许，且无需知情确认。

## 3. 可复现性

- 列表类输出（批次库存、生效召回集合、追回清单）一律排序后返回。
- 召回编号由调用方提供并要求唯一；同一操作序列在新系统上重放
  （相同输入、相同时间戳）得到完全相同的错误码序列与查询结果。
  `TestRandomDifferential` 对每组随机种子都跑两遍并逐位比对结果。

## 4. 本地验证方法

```bash
export PATH=$PATH:/usr/local/go/bin:$PATH
export GOCACHE=/tmp/gocache GOPATH=/tmp/gopath   # 本机默认缓存目录只读时需要

go test ./...                          # 全量测试
go test -race ./recall/                # 竞态检测（含并发串行化用例）
go test ./recall/ -run TestRandomDifferential -v   # 1500 组随机差分
go test ./recall/ -run TestScaleComparison -v      # 两档规模对照
go test -bench . -benchmem ./recall/               # 基准测试
go vet ./...
gofmt -l .
```

差分测试的逐步日志（每步输入、朴素/生产两侧输出与判定依据）写入
`${TMPDIR:-/tmp}/recall_diff_trace.log`（Linux 下通常即
`/tmp/recall_diff_trace.log`）。

### 两档规模实测（参考值，arm64）

| 指标 | 小档 | 大档（噪声放大约 100~1000 倍） | 比值 |
| --- | --- | --- | --- |
| 已解除召回数 | 20 | 2000 | 100× |
| 其他药品召回数 | 6 | 60 | 10× |
| 其他药品发放记录 | 200 | 200000 | 1000× |
| 有效等级判定 | 74.01 ns/op | 74.25 ns/op | 1.00 |
| 追回清单 | 60.9 µs/op | 65.8 µs/op | 1.08 |

噪声放大百倍至千倍，目标操作耗时基本不变，直接验证第 2.2/2.4 节的复杂度承诺。

## 5. 测试对照模型

`naive_test.go` 中的朴素模型独立实现全部规则：有效等级全量扫描所有召回，
退药每次全量重排本人发放，追回清单扫描全部药品的全部批次。
随机差分测试（1500 组 × 60 步）把同一步操作同时喂给两侧，
逐位比对错误码、批次查询与追回清单，并在每一步后校验库存守恒与
患者持有缓存一致性。
